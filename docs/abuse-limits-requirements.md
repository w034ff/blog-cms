# 荒らしの上限 要件定義

- 状態: 設計済み、未実装（2026-10-19）
- 作成: 2026-10-19、記事の作成時に重い画像を保存し続ける荒らしへの対策の相談から
- 関連: `docs/multi-author-requirements.md` §4.3・§9・§12.3、`docs/project-status.md` §7.3、`app/api/uploads/route.ts`、`scripts/gc-uploads.mts`

ログインした著者が、サーバーのディスクと DB を埋められないようにするための設計記録。コードでの名前は、アップロードの側が `upload quota`、本文の側が `body limit`。

---

## 1. 目的と前提

アップロード（`/api/uploads`）は、ログインしていれば誰でも使える（`docs/multi-author-requirements.md` §4.3）。今の上限は 1 枚ごとのものだけである。5MB 以下、png / jpg / gif / webp、長辺 2000px への縮小（`lib/uploads.ts` の `MAX_UPLOAD_BYTES`、`lib/upload-image.ts` の `MAX_IMAGE_EDGE`）。1 人が上げられる枚数と総量には上限が無い。

そのうえで、今の仕組みでは次の手口が止まらない。

- 中身の違う画像（ノイズなど）を上げ続ける。保存名は中身のハッシュなので、重複をまとめる仕組みが効かない。
- 上げた画像を下書きに貼っておく。掃除（`gc:uploads`）は DB の本文と下書きを参照として数えるので、貼られた画像は消えない。
- 自動保存（`/api/drafts`）に長い本文を送り続ける。Route Handler には Server Action のような 1MB の上限（`serverActions.bodySizeLimit` の既定）が無い。

参加方針が「招待した人だけ」（`docs/multi-author-requirements.md` §9.4）の間は、相手を管理者が知っているので、この手口は現実の脅威になりにくい。この文書の上限は、方針を「誰でも」に切り替える前に入れておくものである。

## 2. 決定

- **著者 1 人ごとに、画像の総量と 24 時間あたりの枚数に上限を置く**。数えるために、誰がどの画像を上げたかの台帳を持つ（§4）。
- **参加して間もない著者の上限は小さくする**。使い捨てのアカウントで上限を使い切る手口が、1 アカウントあたりで割に合わなくなる。
- **著者全体の画像の総量にも上限を置く**。アカウントを増やせば著者ごとの上限は回避できる（参加方針が「誰でも」なら、Google アカウントはいくらでも作れる）。著者全体の上限が無いと、止めるのが空きの下限だけになり、ディスクの空きのほとんどを埋められる。
- **サーバーの空きが下限を切ったら、著者のアップロードを断る**。ほかのものがディスクを使って著者全体の上限が手前で効かなくても、ホストのディスクが尽きないための保険である。
- **本文の長さに上限を置く**。自動保存と公開の両方で確かめる。
- 管理者は、画像の上限（著者ごと、著者全体、空きの下限）の対象にしない。管理者が自分のサイトの作業で締め出されないためである。本文の長さの上限は、管理者にもかける（普通の記事が届く長さではないので、分けても得るものが無い）。
- 連打の抑制、アニメーション画像の別枠、停止した人の一括の掃除、下書きの本数の上限、上限に達した人を管理者に知らせる仕組みは作らない（§9）。著者ごとの総量の上限があれば、どれも被害がその中に収まる。

## 3. 上限の値

値はすべて名前の付いた定数にする（オーナー、2026-10-19）。

| 定数                         | 値      | 意味                                                 |
| ---------------------------- | ------- | ---------------------------------------------------- |
| `UPLOAD_QUOTA_BYTES`         | 200MB   | 著者 1 人が持てる画像の総量（保存した後のバイト数）  |
| `UPLOAD_DAILY_LIMIT`         | 50      | 著者 1 人が直近 24 時間に足せる画像の枚数            |
| `NEW_AUTHOR_DAYS`            | 7       | 参加してから、小さい上限がかかる日数                 |
| `NEW_AUTHOR_QUOTA_BYTES`     | 20MB    | 参加して間もない著者が持てる画像の総量               |
| `NEW_AUTHOR_DAILY_LIMIT`     | 10      | 参加して間もない著者が直近 24 時間に足せる画像の枚数 |
| `AUTHORS_UPLOAD_TOTAL_BYTES` | 10GB    | 管理者以外の著者全員が持てる画像の総量の合計         |
| `UPLOAD_MIN_FREE_BYTES`      | 5GB     | 著者のアップロードを受ける、ディスクの空きの下限     |
| `BODY_MAX_CHARS`             | 100,000 | 本文の長さの上限。文字（コードポイント）で数える     |

- 200MB は、本文の画像 1 枚が縮小の後でおおむね 1MB 未満なので、数百枚にあたる。25 人がすべて使い切って 5GB である。
- 20MB・10 枚は、画像のある記事を 1〜2 本書いて試すのに足りる量である。
- 「参加して間もない」は、`users.created_at`（`docs/multi-author-requirements.md` §10.2）が `NEW_AUTHOR_DAYS` 日の内にあることで決める。`created_at` が null の行は、その列ができた 2026-10-18 より前からいる利用者なので、間もない扱いにしない。
- 10GB は、空き（下の 99GB）の 1 割で、200MB を使い切った著者 50 人分にあたる。
- 24 時間は、暦の日ではなく直近の 24 時間で数える。日付の境目とタイムゾーンを持ち込まないためである。
- 5GB は、2026-10-19 の時点でディスク（251GB）の空きが 99GB なので、平常の運用では届かない。
- 100,000 字は、UTF-8 の日本語でおおむね 300KB で、公開の Server Action の 1MB の上限より手前にある。上限が 1MB の向こうにあると、公開では Next.js の汎用のエラーが先に出て、§7 の文言が届かない。

## 4. 台帳

移行は `db:generate` → `db:migrate` の経路で作る（`docs/project-status.md` §2）。

| 列                   | 型               | 中身                                               |
| -------------------- | ---------------- | -------------------------------------------------- |
| `uploads.name`       | TEXT NOT NULL    | 保存名（`<sha256>.<ext>`）。`/uploads/` は付けない |
| `uploads.user_id`    | INTEGER NOT NULL | 上げた利用者の id                                  |
| `uploads.bytes`      | INTEGER NOT NULL | 保存したファイルのバイト数                         |
| `uploads.created_at` | TEXT NOT NULL    | その利用者が初めて上げた時刻（ISO 8601）           |

- `(name, user_id)` で一意にする。同じ画像を 2 人が上げれば 2 行になり、それぞれの総量に数える。どちらが先に上げたかで総量が変わらないためである。
- 同じ人が同じ画像を上げ直しても、行は増えず、枚数にも数えない。
- 外部キーは張らない。利用者を消すときは、§6 の関数が台帳の行を明示的に消す（`post_revisions` に外部キーを張らないのと同じ理由。`lib/db/schema.ts` の `postRevisions` の注記）。
- 台帳は参照ではない。掃除の参照の走査（`scripts/upload-refs.mts` の `referencedInDb`）に台帳を入れない。入れると、上げたすべての画像が参照されていることになり、何も消えなくなる。
- 移行の前からあるファイルには行を作らない。誰が上げたかが分からないうえ、今の本番の利用者は管理者だけなので、総量に数える相手がいない。

## 5. アップロードの検査

`app/api/uploads/route.ts` の今の検査（ログイン、形式、5MB、読める画像か）の後に、次の順で確かめる。

1. 保存名を作る（今と同じく、縮小の後のバイト列のハッシュ）。
2. その人の台帳に同じ保存名の行があれば、上限を確かめずに今と同じ URL を返す。
3. 管理者なら、4〜7 を飛ばす。
4. ディスクの空き（`UPLOAD_DIR` のあるファイルシステム）が `UPLOAD_MIN_FREE_BYTES` を切っていれば断る。
5. 管理者以外の利用者の台帳の `bytes` の合計にこの画像を足すと `AUTHORS_UPLOAD_TOTAL_BYTES` を超えるなら断る。同じ画像を持つ 2 人の行は 2 回数える（多めに数えるほうへ倒す）。
6. 直近 24 時間のその人の台帳の行が、24 時間の上限（参加して間もなければ `NEW_AUTHOR_DAILY_LIMIT`、そうでなければ `UPLOAD_DAILY_LIMIT`）に達していれば断る。
7. その人の台帳の `bytes` の合計にこの画像を足すと、総量の上限（参加して間もなければ `NEW_AUTHOR_QUOTA_BYTES`、そうでなければ `UPLOAD_QUOTA_BYTES`）を超えるなら断る。
8. 台帳に行を足し、ファイルが無ければ書く。ファイルを書けなかったら行を消し、500 を返す。

- 5〜8 の行の追加は、1 つの同期のトランザクションで行う。同時に来た 2 枚が両方とも上限の手前で通らないためである（better-sqlite3 のトランザクションは同期で、その間にほかの要求は割り込めない）。
- 断ったときの応答と、エディタに出る文言。エディタは今と同じく「アップロードに失敗しました: 」に続けて `error` を出す（`lib/upload-client.ts` の `uploadImageFile`）。

| 理由                       | 状態 | `error`                                                                            |
| -------------------------- | ---- | ---------------------------------------------------------------------------------- |
| 空きの下限、著者全体の総量 | 507  | サーバーの空き容量が足りないため、画像を保存できません。管理者に知らせてください。 |
| 24 時間の枚数              | 429  | 画像は 24 時間に 50 枚までです。時間をおいてから試してください。                   |
| 総量                       | 507  | 画像の保存容量（200MB）を超えます。記事から外した画像は、1〜2 日で容量が空きます。 |

- 文言の数は、その人にかかっている上限の定数から作る。参加して間もない著者には、24 時間の枚数と総量の文言の後に「参加から 7 日間は、上限を小さくしています。」を足す。日数は `NEW_AUTHOR_DAYS` から作る。
- 著者全体の総量で断るときも、空きの下限と同じ文言にする。ほかの著者の使い方を、断られた本人に明かさないためである。
- 「1〜2 日」は、掃除の猶予（24 時間）と、夜ごとの実行（`deploy/systemd/uploads-gc.timer`）を合わせた長さである。ほかの人の記事も同じ画像を使っていれば、その画像は消えず、容量も空かない。珍しい場合なので、文言には書かない。
- 今ある英語の `error`（形式と 5MB）は、この文書では変えない。

## 6. 台帳の掃除

- **掃除**（`scripts/gc-uploads.mts`）: ファイルを消したら、同じ実行で、その保存名の台帳の行をすべて消す。これで、記事から外した画像が総量から外れる。そのため掃除は DB を書き込みで開き（`scripts/open-db.mts` の `openDb`）、行の削除は `.immediate()` のトランザクションで行う。掃除は動いているアプリと別のプロセスなので、読んでから書く遅延のトランザクションは、アプリの書き込みの後で書き込みに上がれずに失敗する（`deleteUserAccount` と同じ理由）。`--delete` の無い実行は、今と同じく何も書かない。
- 掃除が消さないファイル（参照されているもの、猶予の内のもの）の行は残す。
- **利用者の削除**: `lib/user-delete.ts` の `deleteUserAccount`（`docs/multi-author-requirements.md` §12.3）は、同じトランザクションで、その人の台帳の行を消す。ファイルは今と同じく、ほかの行が参照していなければ次の掃除が消す。
- 停止しても台帳の行は消さない。停止中の人はアップロードできない（`docs/multi-author-requirements.md` §5）ので、行が残っても新しい画像は増えない。

## 7. 本文の長さ

- 本文を書き込む経路は 2 つで、どちらも `BODY_MAX_CHARS` を超える本文を DB に書かずに断る。記事と走り書きを区別しない。公開中の記事の手元の版（`draft_content`）も、自動保存の経路なので同じく断る。
  - `/api/drafts`（自動保存）: 413 と `error: 'body too long'` を返す。
  - `submitPostAction`（公開・更新）: `error` に「本文が長すぎます。100,000 字までにしてください（今は N 字）。」を返す。
- 自動保存が 413 で断られたら、エディタの保存の状態（`components/PostEditor.tsx` の「保存に失敗」）を「本文が長すぎます（100,000 字まで）」にする。色と消えない扱いは「保存に失敗」と同じ。ほかの失敗の表示は今のまま。
- 版の復元（`restoreRevisionAction`）は確かめない。過去の版は、書いたときに上限を通っている。

## 9. 先送り

- 短い間の連打の抑制（例: 1 分に 10 枚）。24 時間の枚数の上限と役割が重なる。縮小の処理で CPU を占められることが実際に起きたら足す。単一のプロセスなので、`lib/login-throttle.ts` と同じくメモリの上で足りる。
- アニメーション画像の別枠。今は縮小を通らず、5MB のまま保存される（`lib/upload-image.ts` の `prepareUploadImage`）。総量の上限の中に収まるので、残るのは読者の側の転送量で、`docs/project-status.md` §6 の本文画像の配信の最適化と一緒に考える。
- 停止した人の下書きと、その人だけが使う画像を一括で消す管理の操作。台帳があれば書ける。実際に荒らされるまでは、1 本ずつの削除と、要ればその場のスクリプトで足りる。
- 下書きの本数の上限。画像は総量で、本文は長さで抑えられるので、残るのは DB の行数だけである。
- 上限に達した人を管理者に知らせる仕組み。通知の仕組みが今は無い。参加方針を「誰でも」に切り替えるときに、`docs/multi-author-requirements.md` §12.9 の削除の記録と一緒に決める。
- 使っている容量を著者と管理者に見せる画面（アカウントの設定、利用者の詳細のページ）。断られたときの文言で上限が分かるので、最初は作らない。
