# 記事の検索 要件定義

- 状態: 設計済み、未実装（2026-10-15）
- 作成: 2026-10-15、サイトのヘッダーを作り直した後、次の機能として
- 関連: `docs/project-status.md` §6、`docs/site-header-requirements.md` §3.1、`lib/excerpt.ts`、`lib/posts.ts`
- 見た目の案: オーナーと描き比べた案のうち「案 1」と「検索のページ」（描き比べはリポジトリの外にある）

読者が言葉を打って、公開中の記事と走り書きを探す機能の設計記録。画面での名前は「検索」、コードと URL での名前は `search`。

---

## 1. 目的と前提

記事を探す入口は、新しい順の一覧・カテゴリ・タグしか無い。覚えている言葉から記事を探す手段が無い。

公開中の記事は数本で、数十本になるまでは一覧で足りる見込みだった（`docs/project-status.md` §6、2026-06-29）。それでも作るのは、走り書きが加わって探す先が 2 つの一覧に分かれたためである。規模は小さいままなので、仕組みは小さく保つ（§3）。

## 2. 決定

- 対象は公開中の記事と走り書き。結果の各行に種類の札を付けて見分ける。走り書きはホームと RSS には混ぜていないが、検索は読者が自分で探しに来る場所なので含める（オーナー、2026-10-15）。
- 探す範囲はタイトルと本文。本文は読者に見える文字だけで探す（§3.2）。説明文は本文の書き出し（`lib/excerpt.ts`）なので、本文を探せば含まれる。タグとカテゴリの名前は探さない。それぞれの一覧ページがある（オーナー、2026-10-15）。
- 入口は、ヘッダーの「記事 ▾」のメニューの最後の「検索」（§5.1）。ヘッダーに入力欄やアイコンは置かない。ヘッダーの形が幅とログインの有無で変わらず、幅 360px・ログイン中の 1 行にアイコンの入る余地（約 29px）が無いため（オーナー、2026-10-15）。ヘッダーの入力欄は §7 に先送りした。
- 検索のページは `/search?q=…`。言葉は URL に載せ、結果のページを再読み込み・共有できるようにする。

## 3. 探し方

### 3.1 仕組み

公開中の行をすべて読み、サーバーのメモリの上で絞り込む。索引の表も、SQLite の全文検索（FTS5）も、クライアントの索引も使わない。

- FTS5 の既定のトークナイザは日本語の語の境目を扱えない。SQL の `LIKE` も、`ASCII` の外の大文字と小文字や、全角と半角を同じに扱えない（§3.3）。
- 読者に見える文字を取り出すには Markdown を解析する必要があり（§3.2）、これは SQL の中ではできない。
- 読者に見える文字は、本文ごとにサーバーのメモリに覚えておき（`id` ごとに、元の本文と取り出した文字の組）、覚えた本文と今の本文が違う行だけ解析し直す。検索のたびに解析し直すと、本文 5000 文字の記事が 50 本で 1 回 0.3 秒ほどかかり、その間サーバーはほかのページも返せない（2026-10-15 に測った。4 本・平均 592 文字で 5ms、50 本ぶんに増やして 36ms。時間は本文の長さにほぼ比例する）。サイトは外に公開しているので、検索を繰り返し送られるだけでサイト全体が遅くなりうる。
- 変わったかどうかは、`updatedAt` ではなく本文そのものを比べて決める。本文を書き換えても `updatedAt` を動かさない経路（`npm run fix:glued-images` など）を取りこぼさないため。覚えた行のうち、今の公開中の行に無い `id` は捨てる。覚えたものはサーバーを起動し直すと消え、最初の検索で作り直す。
- 行は検索のたびにすべて読む。読み出しは軽い（本文 5000 文字の行で、50 本 1.5ms、300 本 8.5ms、1000 本 28ms。2026-10-15）。ホームも公開中の記事をすべて読んでいるので、検索 1 回の DB の仕事はホームを 1 回開くのとほぼ同じである。数百本になったら、読む列を絞ることを考える（§7）。

読むのは `lib/posts.ts` の `listed` が通す行だけ（種類ごとに、`draft` でも `unlisted` でもないもの）。公開中の記事に未公開の変更（`draft_content`）があっても、探すのは公開中の本文である。

### 3.2 本文の読者に見える文字

本文の Markdown を `lib/excerpt.ts` と同じ解析器（`remark-parse` と `remark-gfm`）で木にし、読者に見える文字だけをつないだものを探す。

- 入れる: 段落・見出し・リスト・引用・表の文字、リンクの文字、インラインのコード、コードブロックの中身（技術の記事では関数名などで探すため）。
- 入れない: Markdown の記号、リンクと画像の URL、画像の代替テキスト、生の HTML（リンクカードや埋め込みの部品）、脚注の参照の記号。
- 段落やブロックのあいだは改行 1 つでつなぐ。改行をまたいで見つかることはない。

### 3.3 言葉の比べ方

- 全角と半角、大文字と小文字を区別しない。比べる前に、言葉と本文の両方を Unicode の NFKC で正規化し、小文字にする。正規化はコードポイントごとに行い、元の文字列の位置に戻せるようにする（§4 の印のため）。そのため、半角カナと濁点の 2 文字（`ｶﾞ`）は「ガ」と同じにならない。
- 空白（半角と全角）で区切った語がすべて含まれる行だけを出す（AND）。語の順は問わない。
- 語は 5 つまで、言葉は全体で 100 文字まで。超えた分は捨てる（`SEARCH_MAX_TERMS`・`SEARCH_MAX_CHARS`）。
- 空の言葉、空白だけの言葉では探さない（§4 の初めの状態）。

### 3.4 並び

タイトルにすべての語を含む行を先に、そのほかを後にする。それぞれの中は公開日の新しい順（同じ日なら id の大きい順）。件数は絞らず、ページ分けもしない（規模が小さいため。§7）。

## 4. 検索のページ

`/search` は `app/(site)` の下のページで、サイトの殻（ヘッダーとフッター）をかぶる。

- 見出しは「検索」。画面のタブのタイトルは、言葉があれば「「<言葉>」の検索結果」、無ければ「検索」。
- `robots: { index: false }` を出す。結果のページは言葉ごとに無数にでき、検索エンジンに載せる中身ではない。
- 見出しの下に入力欄と「検索」のボタン。`<form method="get" action="/search">` と `name="q"` の入力欄で作り、JavaScript が無くても動くようにする。入力欄には今の言葉を入れておく。言葉が無いときは入力欄にフォーカスを置く。
- 言葉があれば、入力欄の下に「「<言葉>」の検索結果：N 件」。0 件なら「「<言葉>」の検索結果：見つかりませんでした」とだけ出す。画面のタブのタイトルと同じ言い方にそろえる（オーナー、2026-10-15）。
- 言葉が無ければ、入力欄だけを出す（件数の行も結果も無い）。
- 結果の各行:
  - 種類の札と公開日。札はライブラリと同じ色（記事は灰色、走り書きは `--chip-bg` と `--chip-fg`。`docs/library-requirements.md` §6.2）。
  - タイトル。公開側のページへのリンク（記事は `/posts/<slug>`、走り書きは `/scribbles/<slug>`）。
  - 抜粋。本文で最初に見つかった語の前後を、およそ 120 文字（`SEARCH_SNIPPET_CHARS`）切り出す。語の前は 30 文字ほど残す。切った側には「…」を付ける。タイトルにだけ見つかり本文に無いときは、本文の書き出し（`excerptFromBody`）を出す。
  - タイトルと抜粋の中の語すべてに印（`<mark>`）を付ける。印の背景の色は `app/globals.css` の変数にし、明るい配色と暗い配色の両方で決める。
- 言葉と本文は、文字列としてだけ描く。印は、文字列を「印あり・印なし」の区切りの配列に分けて React で描き、HTML として解釈させない（`dangerouslySetInnerHTML` を使わない）。

## 5. ヘッダー

### 5.1 入口

「記事 ▾」のメニューの最後に、区切り線を挟んで「検索」（`/search`）を足す。虫眼鏡のアイコンを文字の前に付ける。ほかの項目と性質が違う（一覧のページではなく道具である）ことを、区切り線とアイコンで示す。`/search` にいるときは、この項目に `aria-current="page"` を付ける。

### 5.2 区画

`/search` と `/search/…` は「記事」の区画にする（`docs/site-header-requirements.md` §3.1）。入口が「記事」のメニューにあるので、そこが濃くなるのが自然である。結果に走り書きが混ざっても変えない。

## 7. 先送り

- 結果の行の種類の札の地。札の地（`bg-zinc-100`）はページの地（`--background`）とほとんど見分けられず、札の形が見えにくい。札の文字は読めるので、記事一覧を行からカードの形に変えるときに、結果の行を白い紙に載せるかと一緒に決める（オーナー、2026-10-15）。画像の無い記事の絵（`docs/category-mark-requirements.md`）は一覧の行の形を変えなかったので、まだ決めていない。
- ヘッダーの入力欄（見た目の案の「案 3」）。記事が数十本に増えて検索が使われるようになったら、広い画面にだけ足す。狭い画面とログイン中は §5.1 の入口のままにできるので、作り直しは要らない（オーナー、2026-10-15）。
- タグとカテゴリの名前で探すこと。
- 打つたびに結果を出す（インクリメンタルな）検索、候補の表示。
- ページ分け。結果が数十件を超えるようになったら考える。
- 行を毎回すべて読むことの見直し（読む列を絞る、取り出した文字を列に持つ、索引）。数百本になって読み出しが目立ったら考える。
- 管理画面のライブラリの検索（`docs/library-requirements.md` §7）。この機能の関数を使えるかもしれないが、対象と並びが違うので別に決める。

## 8. 複数の著者との関係

対象は公開中の行なので、著者が増えても誰の記事かにかかわらず同じように探す。著者の名前で探すこと、著者で絞ることは、表示名が決まってから（`docs/project-status.md` §7.1）考える。
