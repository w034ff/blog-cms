# 要約ブロック 要件定義

- 状態: **設計のみ・未着手**（2026-09-21。入れるかどうか自体がまだ保留）
- 作成: 2026-09-21、記事の設定ドロワーの批評から続いた相談で
- 関連: `docs/cms-features.md`「説明文の自動抽出」（この機能が上書きする既定の挙動）、`docs/accordion-requirements.md`（保存形式と入れ子の前例）、`lib/excerpt.ts`

著者が書いた要約を、記事の説明文（`<meta name="description">`、`og:description`、一覧のカード本文、RSS、内部リンクカード）として使うためのブロック。この文書は着手前に書いている。決定済みの事項と未決の事項を分けて持ち、未決の事項は着手時に決めて §5 を受け入れ基準の表に置き換える。

---

## 1. 目的と前提

**目的**: 本文の書き出しが前置きや注意書きで、自動抜粋が記事の中身を伝えない記事でも、著者が説明文を明示できるようにする。

**前提**: 記事に説明欄は無い（2026-09-21 に廃止、`docs/cms-features.md`「説明文の自動抽出」）。説明文は `excerptFromBody` が本文の書き出しから導く。この機能はその既定値を上書きする手段であって、説明欄を戻すものではない。

**説明欄より筋が良い理由**: 説明欄は読者に見えないので、書かれず、本文を直しても放置された。要約ブロックは本文の一部として読者に見えるので、本文と一緒に保守される。

**着手の目安**: 自動抜粋が記事の中身を伝えない実例が出たとき。設計時点の投稿は 3 件で、どれも自動抜粋がそれなりの文になっている。

## 2. 決定

- **新しいノードにする。** callout の段階を足す案（`> [!SUMMARY]`。`lib/callout-types.ts` に 1 つ足せば公開側の sanitize まで通る）は安いが、採らない方向である。GitHub 本家に無い段階で、保存した markdown が他所で素の引用になる点も理由の一つ。
- **優先順位**: 要約ブロックがあればその文、無ければ自動抜粋。中身が空の要約ブロックは「無い」と同じに扱い、自動抜粋に落とす。
- **位置は問わない。** 先頭でも末尾でもよい。

## 3. 設計の論点（推奨を付してあるが未決）

### 3.1 中身は地の文だけ

推奨: content を `paragraph+`（インラインの装飾まで）に制限する。リスト・コード・画像・入れ子のブロックは入れさせない。

理由: 説明文は地の文でなければ使えない（箇条書きを繋いでも文にならない）。加えて抽出側が「ノード内の段落を繋ぐだけ」になり、自動抜粋の除外規則を通さずに済む。

### 3.2 1 記事に 1 つ、doc 直下だけ

- **個数**: 2 つあると、どちらを使うか決められない。content expression では「どこにでも置けるが最大 1 つ」を表現できないので、挿入 UI を無効にするだけでは足りない。貼り付けと複製でも増えない守りが要る。**実装コストの大半はここにある。** 抽出側も規則として「最初の 1 つ」を持つ。
- **入れ子**: アコーディオンの中を許すと、畳まれて読者に見えない文が説明文になる。doc 直下だけにする。

### 3.3 保存形式

推奨: `<details>` の前例に倣い、開始タグと終了タグを独立した HTML ブロックにして、間に markdown を置く（例: `<div class="summary">` … `</div>`）。`lib/render.ts` の sanitize 許可リスト（`divClasses`）にクラスを 1 つ足す。

抽出は、`lib/excerpt.ts` がアコーディオンの中身を飛ばしている仕組み（`detailsDepthChange`。HTML ブロックの開閉を数える）をそのまま使い、「飛ばす」を「拾う」に変えるだけで書ける。

### 3.4 長さ

著者が書いた文を `EXCERPT_MAX_CHARS`（120 字）で黙って切ることは避ける。NodeView に文字数と目安を出したうえで、公開面では切らないか、切るなら切れることを編集中に見せるかを決める。

### 3.5 見出しの文言

位置を問わないので、先頭でも末尾でも読める語が要る。「まとめ」は先頭で浮き、「この記事で分かること」は末尾で浮く。「要約」のような中立の語にするか、アコーディオンのタイトルのように著者が編集できるようにするか。後者は保存形式が一段複雑になる。

### 3.6 書き手への誘導

説明文を読むのは、検索結果・SNS・一覧で「読むかどうか」を決める人である。末尾に書く要約は、読み終えた人向けの文（「以上、〜を紹介しました」、本文で定義した用語を前提にした文）になりやすい。位置を縛る代わりに、NodeView で次のように吸収する:

- placeholder を「記事を読んでいない人にも伝わる 1〜2 文」にする
- ノード内に「説明文として使われます」と小さく出す

## 4. 先に入れてよい関連変更: 記事の設定に現在の説明文を出す

要約ブロックの有無にかかわらず価値がある。説明欄の廃止で、著者が説明文を確かめる手段が無くなった。記事の設定ドロワーに、読み取り専用のプレビューと出所（「要約ブロック」／「本文から自動」）を出す。要約ブロックが入った後は、どちらが使われているかがここで一目で分かる。

## 5. テストの置き場（着手時に受け入れ基準の表へ置き換える）

`AGENTS.md`「Where an editor test goes」に従う。

- **vitest**: 抽出の優先順位、空の要約ブロックが自動抜粋に落ちること、個数の述語、入れ子の禁止、markdown の往復（`components/editor/test-schema.ts` の schema は `postEditorExtensions` から作る）
- **E2E**: 貼り付けと複製で 2 つ目が入らないこと（述語は vitest が持ち、spec は守りが各経路に付いていることだけを示す）、NodeView の表示と文字数
