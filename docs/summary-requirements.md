# まとめ・TL;DR ブロック 要件定義

- 状態: **実装済み**（2026-09-30）
- 作成: 2026-09-21、記事の設定ドロワーの批評から続いた相談で。2026-09-30 に詳細設計して実装した
- 関連: `docs/cms-features.md`「説明文の自動抽出」（TL;DR が上書きする既定の挙動）、`docs/accordion-requirements.md`（保存形式と入れ子の前例）、`lib/excerpt.ts`、`components/editor/summary-extension.ts`、`components/editor/summary-rules.ts`、`lib/rehype-summary.ts`

記事を要約する 2 つのブロックの設計記録。TL;DR は記事を読むかどうかを決める人への紹介で、記事の説明文になる。まとめは読み終えた人への総評で、良かった点・気になった点を添えられる。2 つは見た目と仕組みを共有し、役割と置き場所で分かれる。

---

## 1. 目的と前提

**目的**: 本文の書き出しが前置きや注意書きで、自動抜粋が記事の中身を伝えない記事でも、著者が説明文を明示できるようにする（TL;DR）。あわせて、レビュー記事の結論を「総評 + 良かった点 + 気になった点」の形で書けるようにする（まとめ）。後者の構造は gadgeteer.jp のレビュー記事末尾の「SUMMARY / まとめ」から借りた。借りたのは情報の構造だけで、見た目は §10 のとおり独自に決めた。

**前提**: 記事に説明欄は無い（2026-09-21 に廃止、`docs/cms-features.md`「説明文の自動抽出」）。説明文は `excerptFromBody` が本文から導く。TL;DR はその既定値を上書きする手段であって、説明欄を戻すものではない。

**説明欄より筋が良い理由**: 説明欄は読者に見えないので、書かれず、本文を直しても放置された。TL;DR は本文の一部として読者に見えるので、本文と一緒に保守される。

## 2. 決定

- **ブロックは 2 種類。** 見出しは「TL;DR」と「まとめ」で固定し、著者は編集できない。1 種類のまま区画の有無で使い分ける案は採らなかった。1 記事 1 個の制限のもとで冒頭の TL;DR と末尾のまとめを両立できず、位置で見出しを変えると移動しただけで見出しが変わるためである（2026-09-30）。
- **説明文になるのは TL;DR だけ。** 文字のある TL;DR があればその文、無ければ自動抜粋。空の TL;DR は「無い」と同じに扱う。まとめの総評は説明文にも自動抜粋にも使わない。末尾の総評は読み終えた人向けの文（「以上、〜を紹介しました」、本文で定義した用語を前提にした文）になりやすく、読むかどうかを決める人には伝わらない。
- callout の段階を足す案（`> [!SUMMARY]`）は採らない。GitHub 本家に無い段階で、保存した markdown が他所で素の引用になる。

## 3. 設計の決定

### 3.1 中身

| ブロック                     | content                               | 備考                                                                    |
| ---------------------------- | ------------------------------------- | ----------------------------------------------------------------------- |
| `tldr`                       | `paragraph+`                          | 説明文は地の文でなければ使えない（箇条書きを繋いでも文にならない）      |
| `summary`                    | `paragraph+ summaryGood? summaryBad?` | 総評は必須。区画はそれぞれ任意で、順序は良かった点 → 気になった点に固定 |
| `summaryGood` / `summaryBad` | `bulletList`                          | 見出し・表・引用は入れさせない                                          |

区画の中の `listItem` は他のリストと共有の型（`paragraph block*`）なので、スキーマだけでは区画にコードブロックや表が入る。区画に置けるのは入れ子を含む箇条書きの文字だけで、これは `sectionsHoldOnlyLists` が編集ごとに確かめる（§3.2）。

区画を足して何も書かなければ、空のまま保存し、空のまま読み戻す。保存時に消さない。壊れる入力ではないからである。公開ページは空の区画を描かない（§8）。

### 3.2 個数と位置

**TL;DR もまとめも 1 記事に 1 つ、doc 直下だけ。まとめは記事の末尾に置く。** 末尾とは、まとめの後ろに空の段落と脚注セクションしか無いことをいう。空の段落は TrailingNode が文書末に置くキャレットの逃げ場で、脚注セクションは doc の content 式で最後に固定されている（`docs/footnote-requirements.md` §3）。doc の content 式・TrailingNode・ドラッグ落とし先ガードは変えていない。

どれも content 式では表せない（「どこにでも置けるが最大 1 つ」「空行と脚注を除いて最後」）。そこで**スキーマは保存済みの markdown が含みうるものを受け入れ、編集が残すものを規則で縛る**。規則は `summary-rules.ts` の `newRuleBreak` 1 つで、編集の前後の文書を比べ、その編集が新たに破る規則を返す。

| 経路                                                | 扱い                                                                                           | 機構                                                                                                                                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 挿入（スラッシュ、＋ドロワー）                      | すでにあれば出さない／押せない                                                                 | `setSummary` / `setTldr` の拒否を `can()` で問う                                                                                                                                                                       |
| 貼り付け                                            | 規則を破るなら、貼る側を降格して入れる（§7）                                                   | `handlePaste` が一度置いてみて `newRuleBreak` に問う（`pasteSlice`）                                                                                                                                                   |
| ドロップ                                            | まとめの下、すでにある型のコピー、doc 直下以外への落下は拒否して通知し、その位置に線を出さない | `dropRuleBreak` を `handleDrop` と drop cursor が共有する。ドラッグハンドルは移動を組み立てて `newRuleBreak` に問い、通らない位置には線を出さない。行き先で直すと元の削除の後になる（`docs/editor-pitfalls.md` §11.2） |
| 打鍵・ドラッグハンドル・その他のコマンド・undo/redo | 規則を破る編集は拒否して通知                                                                   | `filterTransaction`                                                                                                                                                                                                    |
| 読み込み                                            | 2 つ目以降と doc 直下以外を降格する                                                            | `appendTransaction`（`setContent`）と `onCreate`（最初の文書は取引を通らない）                                                                                                                                         |

**「新たに」破る規則だけを数える。** 規則より前に保存された記事がすでに規則を破っていても、編集を凍らせないためである。余分な箱は読み込みで降格されるので、残るのは「まとめの後ろに本文がある」だけで、これは動かさずにエディタ上で知らせる（まとめの下に「この後ろに本文があります。まとめは記事の末尾に置いてください」）。自動で動かすと、書いた順序が黙って変わる。同じ理由で、文書全体を置き換える取引（`setContent`）は `filterTransaction` の対象から外している。

まとめを入れると、キャレットの位置にかかわらず文書の末尾（脚注の前）に入る。末尾の空の段落があればそれを置き換える。ただし挿入を受け付けるのは、キャレットがトップレベルの行にあるときだけである。挿入の行はどれも「ここにブロックを置けるか」に答えており、表のセル・引用・囲み枠の中では `/` を文字のまま残す規則（`e2e/editor-slash-menu.spec.ts`）を、まとめだけが破らないようにした。

**入れ子**: アコーディオンの中を許すと、畳まれて読者に見えない文が説明文になる。引用やリストの中も同じ扱いにする。

### 3.3 保存形式

`<details>` の前例に倣い、開始タグと終了タグを独立した HTML ブロックにして、間に markdown を置く。

```markdown
<div class="tldr">

要点の文。

</div>

<div class="summary">

総評の文。

<div class="summary-good">

- 良かった点

</div>

<div class="summary-bad">

- 気になった点

</div>

</div>
```

- 使わない区画は `<div>` ごと出力しない。総評が空なら総評の行も出ない（空の段落は何も書き出さない）
- 見出し・区画名・枠は保存しない。NodeView と `lib/rehype-summary.ts` が描く
- 4 つのクラスは `lib/summary-types.ts` の `SUMMARY_DIV_CLASSES` にあり、`lib/render.ts` の sanitize 許可リストはそこから読む

### 3.4 長さ

TL;DR の文は、自動抜粋と同じ `EXCERPT_MAX_CHARS`（120 字）で切って `…` を付ける。NodeView に文字数は出さない（2026-09-30 決定）。書いた文が黙って切れる点は残る。§4 のプレビューも見送ったので、切れたかどうかは公開後に内部リンクカードや SNS の共有カードで確かめる。記事一覧のカードは 2026-10-18 から説明文を出さない（`docs/home-requirements.md` §2）。

### 3.5 見出しの文言

「まとめ」と「TL;DR」。保存しないので、変えても既存の記事には影響しない。TL;DR の見出しは「要点」「Quick summary」と比べて決めた（2026-09-30）。「Quick summary」は末尾の「まとめ」と同じ語を別の言語で言うことになり、2 つの役割の違いが伝わらない。

### 3.6 書き手への誘導

説明文を読むのは、検索結果・SNS・一覧で「読むかどうか」を決める人である。placeholder は何を書くかだけを短く言う。TL;DR の空の段落には「記事の要点」、まとめの空の総評には「総評」を出す。読み手の立場の説明（「記事を読んでいない人にも伝わる 1〜2 文」）や長さの目安は付けない。区画には出さない。すぐ上の区画名がすでに何を書くかを言っており、繰り返しになる（2026-09-30）。

## 4. 記事の設定に現在の説明文を出す（見送り）

**見送る（2026-09-30）。** 案は、記事の設定ドロワーに説明文の読み取り専用のプレビューと出所（「TL;DR」／「本文から自動」）を出し、どちらが使われているかと 120 字で切れたかを見せるものだった。

**理由**: TL;DR を書いた記事では、説明文は書き手が書いた文そのものである。TL;DR の無い記事も、公開後に実際の説明文を確かめられる。記事一覧のカードは 2026-10-18 から説明文を出さないので、確かめる場所は内部リンクカード・SNS の共有カード・トップのピックアップの枠である（`docs/home-requirements.md`）。見送りで残るのは、公開前に説明文を確かめられないことと、TL;DR が 120 字で切れることに書いている間は気付けないことの 2 つで、どちらも壊れる入力でもデータの喪失でもない。

**見直す条件**: 自動抜粋が記事の中身を伝えない文を選んだ実例か、TL;DR が切れて意味が通らなくなった実例が出たとき。

## 6. Markdown の往復（2026-09-30 実測）

実装前に、第一候補の保存形式を試作の拡張と E2E で測った。

- **公開側**: 入れ子の `<div>` と中の markdown（強調・リンク・`<`・`&`・箇条書き）は描画されるが、許可リストに無いクラスは `class=""` に落ちる。4 つを足せば通る
- **markdown-it**: 正規形では、開始タグと `</div>` がそれぞれ独立した `html_block` になり、中が `paragraph` / `bullet_list` になる。`総評。</div>` のように閉じタグを行末に書くと `<p>総評。</div></p>` に壊れる。空行を省いた入力は全体が 1 つの HTML ブロックになり、`- 多機能` が文字のまま残る。エディタに読むと `- \- 多機能` に正規化され、文字は失われない
- **往復**: `<` は初回の保存で `&lt;` になり、空の箇条書き `-` は `- ` になる。どちらもまとめの外と同じ挙動で、2 回目以降は変わらない
- **総評が空の入力**: ProseMirror の DOMParser は、content 式の先頭で必須の段落を補わない。区画をまとめの外へ押し出し、2 つの箇条書きを 1 つに結合した（データが壊れる）。`updateSummaryDOM` が空の `<p>` を補う。判定は空白だけのテキストノードを飛ばした最初の子で行う。`firstElementChild` で判定すると、空行のない入力で総評が 2 段落に割れ、不動点が崩れた
- **区画の順序**: 気になった点 → 良かった点の順の入力では、良かった点がまとめの外へ出た。`updateSummaryDOM` が並べ替える

## 7. 降格

箱のまま置けないブロックは、捨てずに通常のブロックに戻す。TL;DR は段落に、まとめは総評の段落と、区画ごとに「**良かった点**」「**気になった点**」の太字段落 + その箇条書きになる。公開ページで見出しとして見えていた区画名が文字として戻るので、降格した後もどちらのリストかが分かる。読み込み・貼り付けで同じ形にする（`demotedBlocks`）。

途中から選ばれた箱（片側だけ切れたスライス）は降格ではなく開く。区画名は選択された文字ではないので付けない。開く深さは辺ごとに違い、総評を通る辺は 1 段、区画を通る辺は 2 段である（`unwrapHalfSelectedBoxes`）。`createBoxSliceRepair` は深さを型ごとに 1 つ持つので使えない。

## 8. 公開側

`lib/rehype-summary.ts` が sanitize の後で見出しを足し、エディタの NodeView と同じ DOM（箱 > 見出し行 + 本文、区画 > 区画名 + 本文）を組む。`app/globals.css` の規則は 1 組で両方を塗る。

- 見出しと区画名は `<p>` で、見出し要素にしない。目次に入らず、記事の節として読み上げ順に割り込まない
- 文字の無い区画と、文字の無い箱は描かない
- 区画 2 つは 2 列、1 つは全幅。幅 40rem 未満は 1 列（grid と `:has()`）
- 脚注セクションは文書末に固定されるので、まとめ → 脚注の順になる

## 9. エディタの導線

- **スラッシュ**: 「リンク」の直後に「まとめ」「TL;DR」。使えない行は出さない（`available`、他の行と同じ）
- **＋ドロワー**: コードブロックと脚注の間に「TL;DR」「まとめ」。使えないときは押せない。ポインタ用ツールバーには出さない（`InsertControls` の `labelled` 分岐、`docs/accordion-requirements.md` §7.9 と同じ扱い）
- **区画**: まとめの下部に、無い区画の「＋ 良かった点」「＋ 気になった点」ボタン。各区画の見出し行に削除ボタン。`<input>` は使わない（`docs/editor-pitfalls.md` §15.2）
- **キー**: 中身が空の段落 1 つだけの箱で Backspace を押すと段落に戻る。総評の最後の空の段落で Enter を押すと最初の区画へ（区画が無ければまとめの下へ）移る。区画の最後の空の項目で Enter を押すと、次の区画かまとめの下へ出る。区画の中では箇条書き／番号付きの切替を断る（`docs/editor-pitfalls.md` §8.4）
- **まとめの削除**: 「まとめ」の見出し行に削除ボタンを置き、区画ごと消す。ハンドルが無いのでブロックを選ぶ手段が無く、区画を 1 つずつ消して総評を空にしてから Backspace、という手順しか無かった（2026-09-30）。TL;DR には付けない。ハンドルで選んで消せる
- **ドラッグハンドル**: TL;DR には付け、まとめには付けない。まとめは末尾から動かせる先が無い

## 10. 見た目（2026-09-30 選定）

3 案を公開ページの実物で撮って比べ、案 B を選んだ。

- **B（採用）**: 囲み枠の家族。枠線を持たず、サイトの紫を薄く敷いた面（`--summary-bg`）に、区画を記事の面（`--surface`）で載せる。見出しは紫の文字（`--chip-fg`）。囲み枠の段階の色を使わないので、4 つ目の段階に見えない
- A: アコーディオンの家族（1px の枠とタイトル行の塗り）
- C: A を軽くしたもの（外枠 1 本、区画を区切り線で分ける）

区画は色・アイコン・区画名で区別する。良かった点は緑（`--good`、ブログのカテゴリ色と同じ値だが別のトークン）と `CheckIcon` の形、気になった点は `--caution` と `AlertTriangleIcon` の形。絵文字は使わない（OS ごとに見た目が変わる）。参考サイトの見出し行（赤枠の英字タグ + 見出し + 右へ伸びる横線）とクラス名・色の値は使っていない。
