## 1. 目的と非目標

**目的は「保存できない形を作らせないこと」の一点である。** 表は画面上は壊れずに、保存した Markdown だけが壊れる。エディタ上の見た目からは分からないので、規則はすべて「書けてしまう形」を先に塞ぐ側に倒してある。

非目標:

- 結合セル（`colspan` / `rowspan`）を作る導線。GFM パイプ形式に対応物が無い。既にそうなっている文書は読み込めるが、新しくは作れない
- セル内のブロック構造（リスト・コードブロック・入れ子の表）
- 列幅の保存。`min-width` は raw HTML フォールバックにしか乗らない

## 2. 中心規則 — セルは段落しか持てない

**決定: セルの `content` を `block+` から `paragraph+` に狭める**（`ParagraphTableCell` / `ParagraphTableHeader`）。

**理由は保存形式である。** Markdown はセルの中にブロック構造を持てない。パイプ形式は 1 行のインライン内容であり、raw HTML フォールバックですら段落しか生き残らない。標準の `block+` のままだと、セル内のコードブロック・囲み枠・リスト・入れ子の表が**保存時に黙って本文だけに潰れる**。

**機構はスキーマそのものである。** 結果として導線が副作用でまとめて塞がる — ブロックの入力ルールはセル内で発火せず、ブロック挿入はセルの中ではなく表の外に落ちる。述語を 1 つずつ足す必要が無い。

### 2.1 4 つの経路が同じ答えを返す

スキーマだけでは、外から流し込む経路が塞がらない。段落以外のブロックがセルに入ると、ProseMirror はスキーマを満たすために表をその要素の前で閉じて後ろで開き直す — つまり**表が 2 つに割れ、後半は見出し行を失う**。実測（2 列の表の本文セル「セルの中身」に囲み枠を貼る）:

```
before  table(row(th, th), row(td("セルの中身"), td("二つ目")))
after   table(row(th, th), row(td("セル"), td)), callout(…), table(row(td("の中身"), td("二つ目")))
```

本文セルのどの位置でもこうなる（先頭・中間・末尾のいずれも）ので、**許してよい位置は無い**。

| 経路         | 答え                                 | 実装                                            |
| ------------ | ------------------------------------ | ----------------------------------------------- |
| 貼り付け     | 拒否し、理由を通知する               | `tableCellPasteGuard`（`pasteIntoCellRefused`） |
| ドロップ     | 拒否する。内容起因のときだけ通知する | `tableDropGuard`（`tableDropRefusal`）          |
| ドロップ標識 | 拒否する位置では出さない             | `drop-cursor-guard.ts` が同じ述語を引く         |
| 入力・挿入   | スキーマが受け付けない               | §2                                              |

述語が `table-cell-rules.ts` にあるのは**依存の向きのためである**。`isolating-boundary.ts` は `drop-target.ts` に取り込まれ、それを `table-extensions.ts` が取り込む。述語をノード側に置くと import が循環する。

**`isolating-boundary.ts` の `handleDrop` は `tableDropGuard` より先に問われる。** コードブロックの端をまたぐ選択はそちらがクランプし、ドロップ自体をそちらが実行してしまうので、**フォールスルーを足すまでは同じ内容の貼り付けが拒否される一方でドラッグは表を割っていた**。新しいドロップ経路を足すときは、この 2 つの順序を先に確かめること（`table-drop-guard.spec.ts` の `BLOCKS` にコードブロックが引用と別に並んでいるのはこのためである）。

**決定: 修復ではなく拒否する。** 囲み枠の貼り付けガードは修復側を採っているが、ここでは採らない — どの要素にも合う修復が 1 つも無い。囲み枠や引用は本文に開けるが、コードブロックはフェンスを失い、画像や入れ子の表は残す本文を持たない。ノード種別ごとに別の修復を書き、その下にどのみち拒否を敷くことになる。

**拒否は無言なので、通知が唯一のフィードバックになる。** 拒否された貼り付けはクリップボードも文書も変えないため、通知が無いと著者は何も知らされない。文言は貼り付けとドロップで**同一の 1 本**（`TABLE_CELL_BLOCK_BLOCKED`）— 規則が 1 つだからで、「貼り付け」と書くとドロップに対して嘘になる。

### 2.2 ドロップだけが厳しく問う

`carriesNonParagraphBlock` の `allowTable` は貼り付けでだけ真になる。**好みの問題ではない。**

- **貼り付け**: prosemirror-tables 自身の `handlePaste` が表を含む貼り付けをすべて引き取り、セル単位で融合する。これがセル間コピー＆ペーストを成立させている当のコードで、ここのガードより先に走る。除外は「この場合の持ち主は誰か」を明示するもので、プラグイン順に委ねない
- **ドロップ**: `handleDrop` の対応物が prosemirror-tables に無い。落ちてきた表のスライスは通常の fitting を通り、他の 4 種と同じように受け手の表を裂く。実測 — 表全体を覆う選択を別の表のセルへドラッグすると、見出しの無い `table(tableRow(tableCell("元二")))` が残り、raw HTML で保存される

### 2.3 位置起因の拒否と内容起因の拒否

`TableDropRefusal` は 2 値を区別する。**通知するに値するのは片方だけだからである。**

- `'structure'` — **位置**が移動を表構造に変えてしまう。表の中でセルの外（セル間・行間の隙間。ProseMirror が余分なセルを作り、`fixTables` がそれを丸ごと 1 列に矩形化する）、またはセルの中でもブロック境界（段落が 2 つになりパイプ形式を失う）。**無言**でよい — 標識がホバー中に既に消えているので、答えはマウスを離す前に届いている
- `'content'` — **スライス**がセルの持てないブロックを抱えている。セル内のどこに落ちても同じなので前触れが無く、貼り付けと同じ通知を出す

## 3. GFM パイプ形式を保つ

### 3.1 パイプ形式である条件

`isPipeTable`: **1 行目が全て header セルで、どのセルも span を持たず、ブロックを 2 つ以上持たない**。満たさない表は tiptap-markdown 自身と同じく raw HTML で書き出す。

**失うものが 3 つある。** 列の揃え（`align="…"` は生き残るが、フォールバックのインライン `text-align` は rehype-sanitize に落とされる）、`<thead>`、`<colgroup>`。加えて Markdown が Markdown でなくなり、`min-width: 50px` や `colspan="1"` の雑音が入って手で編集できなくなる。

### 3.2 事後に修復する

**決定: 貼り付けとドロップの直後にだけ、パイプ形式に戻せる崩れを直す**（`tablePipeFormRepair`）。

**スライスの時点ではなく事後に直す理由**は §2.2 と同じ — 経路 B（表をセルに貼る）を実行しているのは prosemirror-tables の `handlePaste` であり、それはセル間ペーストを正しく動かしているコードでもある。競走すれば守ろうとしているジェスチャを壊す。

**適用範囲が両方向に効いている。**

- セル内の Enter は**ジェスチャ側の問題**であり修復の仕事ではない。無条件に join すると打った端から Enter が取り消される。だから変えたのは Enter の挙動のほう（§4）で、修復には見えるものが残らない
- 同じ形は `setContent` からも来る。既に raw HTML で保存された記事を開いたときにそれを直すと、著者がしていない編集を自動保存に渡すことになる

**機構は `handleDOMEvents`。** あらゆる `handlePaste` / `handleDrop` の主張者より前に座れる唯一のフックで、まさに先を越してくる prosemirror-tables の `handlePaste` がその理由である。フラグはトランザクションではなく次のマイクロタスクで下ろす — ガードが拒否したジェスチャはトランザクションを 1 つも作らず、フラグが次の打鍵まで立ち続けてしまうため。貼り付けとドロップが送出するものは全て同期なので窓は正確である。

### 3.3 修復しない表

`repairRestoresPipeForm` は `isPipeTable` から修復で届く 2 条件を引いたもので、**結合セルと「1 行目が見出しでない表」だけを弾く**。

後者は「見つけたものを直す」にしない理由である。ツールバーの見出し行ボタン（`toggleHeaderRow`）は意図的に見出しの無い表を作る。自分の理由で HTML フォールバックに入っている表は、セルを書き換えられても何も得しない。**著者が置いたままにする。**

## 4. セル内の Enter は hard break

**決定: セルの中では Enter・Shift+Enter・Mod+Enter の 3 つとも hard break を作る**（`hardBreakInCell`）。

**理由。** セルは `paragraph+` なので 2 つ目の段落は合法で、見た目も崩れない。だがブロック 2 つのセルにはパイプ形式が無く、**その打鍵から先で表全体が黙って raw HTML になる**。保存できない形は、打鍵で作れてよい形ではない — セルを `block+` から狭めたのと同じ論法である。

新しい形を持ち込むわけでもない。Shift+Enter は以前からここで hard break を作り、tiptap-markdown は `inTable` の間それを `<br>` として書き、`| x<br>y |` は byte 単位で往復する。§3.2 の修復も貼られた 2 つ目の段落をこの形に変える。**4 つの経路が同じ答えに揃う。**

**キーマップだけで、スキーマは `paragraph+` のまま。** 既に HTML フォールバックで保存された記事は今日と同じに読み込まれる。新しく書ける形だけが変わる。

**3 キーとも自前に通すのが必須である。** `@tiptap/extension-hard-break` は Shift+Enter と Mod+Enter を `setHardBreak` に直結しているので、放置すると §4.1 のガードを迂回する。この拡張は PostEditor の配列で StarterKit より後に登録され、`ExtensionManager` がそれを反転するので先に問われる。

**セルの外へ出る選択はこの束縛の担当ではない。** `selectionInsideCell` は両端を問い、片端でも外なら false を返してキーを手放す。範囲がセル境界をまたぐ場合は §5 のクランプが先に答える。

### 4.1 Tab が残す選択を額面どおり受け取らない

`setHardBreak` は挿入なので、選択されているものを置き換える。そして Tab 直後の選択は移動先セルの内容全体である（prosemirror-tables の `goToNextCell` が表計算の上書き入力を模して全選択する）。著者が選んだものではなく、失おうとしていることも見えない。**Tab → Enter は「ここへ移って 1 行足す」と読めて、実際にはセルを消して break だけを残していた。**

**決定: その形（`isWholeTextblockSelected`）のときは末尾へ畳んでから挿入する。** 内容が残り、Enter はセル内での唯一の仕事をそのまま行う。手で作った部分選択はそのままなので、自分で選んだ範囲への上書き入力は従来どおり置き換わる。手作りの全セル選択は Tab のものと区別できないので同じ非破壊の枝に入る — undo はどちらも 1 段である。

**矢印キーが同じ欠陥を同じ理由で持っていた。** prosemirror-view の `selectVertically` は空でない TextSelection に対して何もしないので、Tab 直後の ArrowDown はブラウザ既定に落ちて選択を端に畳むだけになり、Tab が下ではなく横に動いたように見える。`tableVerticalArrow` がその形だけを認識し、prosemirror-tables 自身の（空選択専用の）矢印キーマップと同じ移動を行う。

## 5. isolating は 2 階層 — クランプは内側を採る（issue #7）

**表はセルと表の両方が `isolating` である。** これは範囲削除のクランプ（`isolating-boundary.ts` の `isolatingCutDepth`）にとって固有の形で、**外側を採ると壊れる**。

**実バグの経路**: 表の上の段落から本文セルへ範囲選択して Backspace すると、削除が**表の**内容端すなわち 1 行目から走り、**見出し行が消えた**。見出しの無い表にパイプ形式は無いので、記事は raw HTML で保存された（issue #7、2026-07-28 修正）。

**規則: 端点が入っている「箱」はセルであり、表はその外枠にすぎない。** `isolatingCutDepth` は浅いほうから走査して最も深い該当 depth を残すので内側が採られ、外枠は別の piece が外側で止める。

この形は表だけのものではない。脚注の定義セクションと定義（`docs/footnote-requirements.md` §5.1）、アコーディオンの `details` と `detailsSummary`（`docs/accordion-requirements.md` §6.2）が同じ 2 階層である。**新しく `isolating` なノードを足すときは、2 階層になっていないかを必ず問うこと。**

## 6. 表を新しく置けない場所

**決定: セルの中と、アコーディオンのタイトルには表を作れない**（`insertTable` の上書き）。

- **セルの中**: セルは段落しか持てないので、中から挿入すれば受け手の表がその表を囲んで 2 つに割れる（§2.1）。ピッカーは表の中では無反応になる
- **アコーディオンのタイトル**: `detailsSummary` は `text*` なので表は入らず、fitter がアコーディオンを表の周りで割り、`<details>` 2 つとして保存される。本文はこの名前に触られず、`docs/accordion-requirements.md` §6.3 が明示的に求めているとおり表を受け付ける

**述語は `isInTable` ではなく `selectionTouches` を使う。** `isInTable` は `$head` だけを読むので、表から上へ引きずり出した選択は head が外にあって検査を通り、`insertTable` が範囲を置換して**既存の表が空の新しい表に差し替わり中身が消えた**（`d6ccaf8`、2026-07-27）。`selectionTouches` は `selection.from`/`to` が正規化済みなので向きに依存せず、素のキャレットの場合も従来どおり覆う。

**この述語は 3 つで共有されている** — `table-extensions.ts` の `insertTable`、`callout-extension.ts` の `setCallout`、`useImageUpload.ts`（と対になる `Toolbar.tsx` の `imageBlocked`）。**ブロックを置く導線を新しく足すときは、この 3 つ目として登録すること。**

## 7. 選択の見え方

**クロスセルのドラッグ選択のハイライトは自前で描く。** prosemirror-tables の `tableEditing` は CellSelection を作り各セルに `.selectedCell` を付けるが、ハイライト自体はこのリポジトリが取り込んでいない prosemirror-tables のスタイルシートにある。無いとドラッグは効いているのに何も見えず、「セルをまたいでドラッグできない」と読める。

同時に、ブラウザ標準の選択ハイライトを覆い隠す必要がある（`12752c1`）。それを消すはずの prosemirror-view の `.ProseMirror-hideselection` も取り込んでおらず、そもそも `selectionToDOM` がドラッグ中は focus 判定で降りるので mouseup 後にしか付かない。**機構は `.selectedCell` を鍵にした `::selection` マスク**（`app/globals.css`）— `.selectedCell` はドラッグ中ずっと存在する。**`::selection` と `::-moz-selection` は別の規則に分けること**（未知の擬似要素が 1 つあるとセレクタリスト全体が落ちる）。

**どちらもエディタ限定である** — `.selectedCell` は公開側の GFM テーブルには現れない。

## 8. ツールバー

**浮遊メニューは選択ではなく表の左上セルに固定する**（`TableToolbar.tsx`）。キャレットがセル間を動いてもメニューが揺れない。`z-20` は sticky な主ツールバーの `z-30` より下 — **固定ツールバーとそのパネルがこのメニューに覆われてはならない。**

- **`updateDelay={0}`。** 既定の 250ms だと、この表を動かすブロックドラッグが終わった瞬間に CSS の抑止（`body.block-dragging`）が同期的に外れ、ドロップのトランザクションによる再配置が `setTimeout` に載る。メニューが古い位置に最大 250ms 見えてから飛ぶ — ドロップが隠すはずだった動きそのものになる
- **props は全て参照安定に保つ。** `shouldShow` / `appendTo` / `options` / `getReferencedVirtualElement` の参照が変わるたびに BubbleMenu はトランザクションを送出し、`shouldRerenderOnTransaction` がこちらを再描画するので、毎回インラインで渡すと無限ループする
- **`表を削除` は仕切りの向こうに隔離し、赤で塗る。** 加算的な行・列操作の中で誤って押される場所に置かない
- セル内でリンクのカードと競合したときは**カードが勝つ**。機構は `shouldShow` ではなく CSS（`docs/link-requirements.md` §5.5.4）

**列の揃えは列単位でしか設定できない**（`setColumnAlign`）。GFM の揃えは列単位なので、1 セルだけ変えても往復しない。`@tiptap/extension-table` はセルごとに `align` 属性を持つが、tiptap-markdown 内蔵の表シリアライザは常に `---` を書いて揺れを捨てるため、表ノードの Markdown シリアライザだけを上書きしている。

この節は実装後に書いているので、**すべて既存の spec が現に測っている項目である**。新しく測るべきものではなく、退行したときにどこが赤くなるかの対応表として使う。

## 11. 列幅は内容ではなくグリッドが決める（2026-08-12）

**決定: `.prose table` に `table-layout: fixed` を足す**（`app/globals.css`）。列幅は内容量に依存しない。

**機構は `width: 100%` との組み合わせにある。** `@tailwindcss/typography` は `.prose table` に `width: 100%` と `table-layout: auto` を両方当てている（`src/styles.js` の `table:` エントリ）。表は横幅いっぱいで固定されているので**伸びる余地が無く、ある列が得た幅は隣の列から奪われる**。3 列の表（項目 / 説明 / 可否）の真ん中のセルに打ち込んだときの実測:

| 追加した文字数 | 項目 | 説明 | 可否 |
| -------------- | ---- | ---- | ---- |
| 0              | 255  | 255  | 255  |
| 20             | 76   | 612  | 76   |
| 80             | 44   | 678  | 44   |

`fixed` では同じ入力で 255 / 255 / 255 のまま動かない。

### 11.1 同じ 1 行がはみ出しも直す

**`overflow-wrap` では届かない欠陥がある。** `.prose :not(pre)` の `break-word` は**仕様上 min-content 幅の計算に参加しない**のに、auto レイアウトはまさにその min-content から列幅を決める。結果、空白の無い 300 文字の連続文字列は列を 2339px にし、**表がエディタの枠を 1618px 越えてページ全体を横スクロールさせた**（実測 2026-08-12）。

幅が先に決まっていれば同じ文字列はセルの中で折り返す（実測: 幅 255px・高さ 305px、セルからはみ出さない）。**`overflow-wrap: anywhere` を重ねても測定値は 1 つも変わらない**ので、足さない。

**`th`/`td` にだけ `overflow-wrap` を書く案は効かない**（採らなかった理由として記録する）。エディタはセルの中身を `<p>` で包み、`.prose :not(pre)` はその `<p>` に直接マッチするので、セルに書いた値は継承で負ける。

~~長い URL もこの欠陥の実例である。~~ **URL では測れない。** Chrome は `/`・`?`・`&` を改行機会として扱うので、210 文字の URL でも自前で折り返し、`fixed` の有無にかかわらず spec が通ってしまう（実測。基準 19 がハッシュを使うのはこのため）。改行機会をまったく持たないもの — ハッシュ、トークン、識別子 — が実例である。

### 11.2 等幅の代償は受け入れる

**代償は、狭くてよい列も等分を抱えることである。** ○/× だけの列が 255px を持ち、本文の多い列は行数が増える。auto は面積効率を、`fixed` は安定性を採る。

**調整可能にはしない。** GFM のパイプ形式に列幅の構文が無いため、`@tiptap/extension-table` が持つ `colwidth` 属性は — `resizable: true` にして著者がドラッグできるようにしたとしても — パイプ形式のシリアライザに落とされ、次の保存で失われる。保持できるのは raw HTML フォールバックだけで、それは §3 が表を入れまいとしているものである。**内容比例の列幅は最初から著者が制御できていない**ので、等幅は機能の後退ではなく保存形式に見た目を合わせる措置である。§1 が列幅の保存を非目標に挙げているのはこの理由による。

**両方の面に当てる。** エディタだけに当てると、公開ページが持たないレイアウトをエディタが見せることになる。内容が短く均等な表は auto と `fixed` で同一に描画されるので（実測、どちらも 255 / 255 / 255）、既存記事の見た目は変わらない。

## 12. 狭い画面ではツールバーを折り返す（2026-08-21 報告・修正）

**決定**: `.table-toolbar` に `max-width: calc(100vw - 1rem)` を与える。既に持っている `flex-wrap` が折り返しを引き受け、入り切らない画面では 2 段になる（現在それに当たるのは 320px 級だけである — §12.1 でラベルが短くなった）。

**報告**: スマートフォンの幅でツールバーが画面からはみ出す。**実測（2026-08-21）**: 幅 441px に対し、390px の画面で 51px、320px の画面で 121px がはみ出す。切れるのは右端の配置ボタンと「表を削除」で、**「列を削除」が「列を削」になる**。

**位置の問題ではない。** `TableToolbar` は floating-ui の `shift` を有効にしていて、実測では `left` が 1px — **もう寄せきった状態**である。中身が画面より広いので、置き場所では解けない。

**`flex-wrap` は最初から書いてあった。** 効いていなかったのは**折り返す相手の幅が無かった**からである — 絶対配置の箱は包含ブロックに対する shrink-to-fit で幅が決まり、その包含ブロックが画面より広かった。上限を 1 つ与えると、既にある宣言がそのまま仕事を始める。

**代償は高さである。** 折り返した段の分だけ、ツールバーは表の左上セルの上でより広い面積を占める。**ポインタ端末では、その分だけ sticky な主ツールバーに覆われる面積が増える** — §8 が「固定ツールバーがこのメニューに覆われてはならない」と決めているとおり、覆う側の優先度は変えていない。著者が少しスクロールすれば出てくる。（2026-08-21 の実測は 390px で 30px → 56px。現在の 390px は §12.1 により 1 段 30px に戻っている。）

タッチ端末では覆う相手が上ではなく下になった（§12.5 で主ツールバーが画面下端へ移った、2026-09-15）。重なりは実機で確認していない — §12.5 の実機確認と併せて見る。

**1 行のまま横スクロールさせる案は採らなかった**（プロトタイプを作って画面で比較した）。高さは 46px に収まるが、`flex` の子が縮むのでボタンのラベルが「見出し / 行」「表を削 / 除」と 2 行に割れ、**折り返しより読みにくい**。ボタンを縮ませない指定を足せばラベルは保てるが、そのときは横スクロールで隠れた操作が「そこに何かある」と言わない — 折り返しは全部見せる。

**上限は `calc(100vw - 2rem)` で、`shift` にも `padding: 8` を渡している**（2026-08-21 の続報を受けて `1rem` から変更）。幅を切り詰めるだけでは端に張り付いたままになり、右端がちょうど `100vw` に着地する — 実機ではそこが切れて見えることがある。理由は `docs/link-requirements.md` §5.5.19 に書いた。**基準 21 は「はみ出していないこと」ではなく「片側 8px の余白があること」を測る。**

### 12.1 スマホでは行・列のボタンを `＋行` / `－行` / `＋列` / `－列` にする（2026-08-22 依頼・実装）

**決定**: `sm`（640px）未満では、行・列の 4 つのボタンのラベルを `＋行` `－行` `＋列` `－列` に縮める。`sm` 以上は `行を追加` のままである。§12 が高さで払った代償を、狭い画面に限って幅で払い直す。

**記号は全角である。** 半角の `+行` と並べて実機エミュレーションのスクリーンショットで見比べた上での選択で、幅の代償は 16px（4 ボタン分）。半角なら 327px、全角は 343px で、360px の上限 328px を超える — **記号を全角にした時点で、ラベルだけでは 1 行に戻らない。**

**足りない 15px はボタンの左右 padding から取る。** `sm` 未満だけ `px-2` → `px-1.5`（`[&_button]:px-1.5 sm:[&_button]:px-2`）。ラベルではなく padding を削るのは、著者が読むのはラベルのほうだからである。実測: 315px、押せる面積は 34x24px で、WCAG 2.5.8 の 24x24 を満たしている。`sm` 以上は何も変わらない。

**実測（エミュレートした Pixel 7、実装後）**: ツールバーは 441px → 315px。412 / 390 / 375 / 360px はいずれも 1 行（高さ 30px）で、片側の余白は 8px 以上ある。

**320px は 2 段のままである**（実測 288x56px — §12 が測った高さと同じで、そこが軽くなったわけではない）。上限が `calc(100vw - 2rem)` = 288px なので、あと 27px 足りない。次に削る先は padding の残り（`px-1` で 32px 戻る）だが、押せる幅が 30px を切りはじめる。`見出し行` と `表を削除` を縮める案も採らない: 前者は状態を切り替えるボタン、後者は唯一の破壊操作で、**記号に置き換えて意味が落ちるのはこの 2 つのほうである。**

**読み上げ名は縮めない。** `aria-label`（`ToolbarButton` の `title`）が `行を追加` を持ち、差し替わるのは目に見えるラベルだけである。`－列` は読み上げでは指示にならないし、`getByRole('button', { name: '行を追加' })` で引いている既存の spec もそのまま通る。`tooltipHidden` を添えるのは、`sm` 以上ではラベルが見えていてツールチップが同じ語を繰り返すだけになり、スマホ側では `hover: none` がどのみちツールチップを消すからである（`docs/link-requirements.md` §5.5.19）。

**機構は 2 つの span である**（`sm:hidden` と `hidden sm:inline`）。幅を読む hook ではない。選ぶのはレイアウトの側なので、最初の描画で間違ったほうが出る瞬間が無く、hydration の不一致も持ち込まない — 判定に使う幅は、容器の上限が書かれているのと同じ `100vw` の側にある。

基準 12i（`docs/link-requirements.md` の 12 系と同じ `editor-narrow-menus.spec.ts`）。見た目は `innerText` で、名前は role で引く — **長いラベルはどの幅でも DOM にあり、選んでいるのは `display` だけ**なので、`textContent` で測ると両方が混ざる。基準は 360px に置く — 390px は全角でも padding のままで収まるので、詰めを外しても緑になる。

### 12.2 タッチ端末ではボタンに枠を描かない（2026-08-22 報告・実装、2026-09-19 撤回）

**現在**: リングは無い。`@media (hover: none)` でも、`.toolbar-button`・リンクカードの見出し・埋め込みの見出しのどれにも `box-shadow` を付けない。主ツールバーの行だけを先に外した §12.12（2026-09-18）の decision を、2026-09-19 に残り全部（表のツールバー・リンクカード・埋め込みヘッド・コールアウトメニューなど）へ広げ、この節自身を置き換えた。押せる範囲は、グリフ・ラベルそのものと `:active` の一時的な塗り（§12.7）、主ツールバーでは `.toolbar-mark-divider` が示す。

**判定は幅ではなく `hover: none` である。** 足りないのは hover の見え方そのものなので、問いは画面の広さではなくポインタの種類である。タッチ画面とマウスを両方持つノート PC は `hover: hover` を名乗り、ポインタの見た目のままになる — ツールチップを消す規則（`docs/link-requirements.md` §5.5.19）と同じ判定を使っている。

基準 12j は撤回。「枠がある・段数が保たれる」という測定対象自体が無くなったので、`editor-narrow-menus.spec.ts` 側もこの節の現在の決定（枠が無いこと）を測るものへ書き換えている。

### 12.3 タッチ端末ではボタンの高さを 40px にする（2026-09-09 報告・実装）

**決定**: `@media (hover: none)` のとき、エディタの押せる部品を `min-height: 40px` にする。正方形のもの（リンクバブルの丸ボタン、カード帯のアイコン）は `min-width` にも同じ値を採る。§12.2 と同じく**この節は表のツールバーの規則ではない** — 規則は `app/globals.css` の `hover: none` ブロックにあり、主ツールバー・表のツールバー・リンクバブル・画像バブル・ドロップダウンの行・カード帯に同時に効く。

**実測（2026-09-09、Pixel 5 エミュレート・393px）**: 主ツールバーと表のツールバーのボタンは一律 24.0px、画像バブルは 25.6px、ドロップダウンの行は 28px、リンクバブルの 1 行目（`.link-bubble-open`。押すとタブが開く）は 84.5×20px、カード帯のアイコンは 23×23px。24 CSS px はおよそ 4.2mm で、指の接触面 7〜9mm より小さい。隣との隙間は 2px なので、外したときに起きるのは**空振りではなく隣の発火**である（太字のつもりで斜体）。

**適合ではなく快適さの問題である。** WCAG 2.2 SC 2.5.8（AA）の下限は 24×24 で、最小の B / I / S / A はちょうど 24.0×24.0 に乗っていた — 満たしてはいるが、padding を 1 段動かせば割る余裕の無さである。下回っていたのはカード帯の 23×23 だけで、これは AA を外している。44px は SC 2.5.5（AAA）と Apple HIG の値で、`docs/link-card-requirements.md` §22.2 が「届かない」と書いているのはこの線である。採るのは 40px — 指には既に足りており、残り 4px は下の代償に見合わない。

**上げるのは縦だけである。** 幅は既に尽きている側で、高さはそうではない。ツールバーは折り返す（§12.5 の現行配置で 393px 以下は 2 段・実測 87px、412px で 1 段）ので、ボタンを横に広げれば段が増える。段が増えるとソフトキーボードを出したときの可視領域 319px（`docs/embed-requirements.md`、2026-09-02 実測）からさらに 42px 取られる。高さの代償は 1 段あたり 16px で、一度きりである。

_この段落は 2026-09-15 に書き直した。決定（縦だけ 40px）は変わっていないが、当時の根拠は「上に貼り付いたツールバーが可視領域を削る」ことだった — 現在ツールバーは画面下端にあり、キーボードに押し上げられる（§12.5）。段が本文の取り分を削ることは配置が変わっても変わらないので、理由はそちらに書き直してある。_

**機構は 4 つの hook である** — `.toolbar-button`（`ToolbarButton.tsx`。§12.2 の枠と同じ hook）、`.dropdown-item`（`ToolbarDropdown.tsx` の `DropdownItem`）、`.link-bubble-open`（`LinkBubble.tsx`）、`.prose .link-card-head button`。カード帯の `min-width` だけは離れた場所に書いてある: 同じセレクタが持つ `min-width: 0`（ラベルを省略記号にして帯の高さを守るための保険）より後ろでなければ勝てないので、その隣に置いている。帯は 3 つで 136px（隙間込み）、320px の画面で帯の幅は 220px なので、その保険が守っている折り返しには届かない。

**箱を広げることと中身を中央に置くことは別である。** `<button>` は縦だけは自分で中央に置く（40px の箱に 16px のアイコンで上下 12px ずつ、実測）。横は置かない — アイコンは block レベルの `<svg>` なので `text-align` が届かず、`min-width` が足した 12px が**全部その右側に寄った**（左 6px・右 18px、2026-09-09 実測。出荷当日に指摘を受けている）。丸ボタン（`.toolbar-button-round`）と帯のアイコンは flex で中央に置く。ツールチップの span は `position: absolute` なので flex item にならず、動かない。基準 12k は寸法だけでなくこの左右差も測る — 大きさの検査では素通りする種類の崩れだからである。

**§12.2 の除外はそのままである。** パネルの行に枠を描かないのは「全幅の行が縦に並べば一覧として読める」という理由であって、押しやすさとは別の軸なので、行は高さだけを受け取る。

**埋め込みの帯（`.prose .embed-head button`）は高さを取らない。** ここだけ条件が逆である: ボタンは行に 1 つきりで、どの幅でもラベルを保ち、**110.8×26.6px** ある — アイコン 1 個の約 5 倍の面積で、AA の 24px も上回っているので、40px が足すものが無い。足したのは損だけだった: 帯は `min-height: 2.2em`（35.2px）なので 40px のボタンが帯をちょうど埋め、ボタンと映像のあいだの 4.3px が 0 になって**枠が映像に接した**（2026-09-09 に指摘、実測 0px）。当たり判定だけを 40px に保つ道（枠を擬似要素に描いて内側に入れる、さらに `margin-block` を負にして帯を 35.2px に戻す）は検討して採らなかった — 得るものが無い側の的にその複雑さは合わない。カード帯がアイコン 3 個で逆の事情なのと対にして読むこと。基準 12k はこの除外を**隙間があること**として測る。除外が事故ではなく決定だからである。

基準 12k。4 つの hook から 1 つずつ測っている — クラスが 1 つ外れたときに落ちてほしいからで、規則の有無ではなく実際の箱を測る。

### 12.4 スマホのツールバーに元に戻す／やり直すを置く（2026-09-09 依頼・実装）

**決定**: 主ツールバーに「元に戻す」「やり直す」をアイコンで置き、**`hover: none` のときだけ描く**（位置は§12.13で末尾に移っている）。この 2 つだけ 40×40 にする（`.toolbar-button-history`）。§12.2 と同じくこれは表のツールバーの規則ではない — 主ツールバーの話をここに書くのは、この節群がそうなっているからである。

**ポインタ側には出さない。** そちらには `Mod-z` があり、2 つはタッチのための導線でしかない。判定は §12.2・§12.3 と同じ `hover` で、タッチ画面とマウスを両方持つノート PC は `hover: hover` を名乗って今までのツールバーのままになる。**書き方は「hover があるとき隠す」であって「無いとき出す」ではない** — マークアップはどの幅でも同じで、描くかどうかだけを 1 つのクエリが決める。React で `matchMedia` を読むと最初の描画が一度間違ってから直ることになり、それは §12.1 が表のツールバーのラベルで避けた hydration の不一致そのものである。

**理由はタッチに経路が無いことである。** コマンド自体は `Mod-z` にあり、スマホのソフトキーボードに Ctrl は無い。iOS の「シェイクで取り消す」「3 本指スワイプ」は `beforeinput` の `inputType: historyUndo` として届き、**このエディタはそれに応答する**（実測 2026-09-09: イベントは `preventDefault` され、打った 5 文字がまとめて戻った。`historyRedo` も同様に処理される）。Android には OS 側の取り消し操作が無く、Gboard にも該当のキーが無い — つまり**片方の OS では唯一の経路になる**。画像バブルに「削除」を足したのと同じ形で、`docs/link-card-requirements.md` §22.1 がその前例である。

**やり直すもタッチでは常に出す。** アンドゥの取り消し手段はリドゥしかなく、押しやすくしたボタンを誤爆したときに戻す道が要る。「`can().redo()` のときだけ出す」案は、ツールバーの高さがアンドゥの瞬間に 42px 伸びて本文が下がるので採らなかった。

**段数（実測 2026-09-15、現行配置）**: 412px は 1 段（45px）、393px 以下は 320px まで 2 段（87px）。

_測り直しは 2026-09-15、§12.5 で挿入系の 4 つがこの行を離れたためである。この 2 つの追加が段を増やす幅は、現在はどこにも無い。_

**幅が無料なのはこの 2 つだけである。** 40px にしても段数は上の実測のままで、B / I / S / A（24px。§12.9 で引用がこの並びを離れる前は 5 個だった）は違う。測ったのは 2026-09-09 の配置（12 個が 1 行に並んでいた状態）で、そこでは 30px までは 390px 以上で 2 段のままだが、32px にすると 390px・393px が 3 段になり、375px では 28px でも 3 段になった。**§12.5 で行が 8 個に、§12.9 で 7 個に減った今、この境界は測り直していない** — 広げる提案が出たときに測ればよく、決定（広げるのはこの 2 つに限る）を動かす材料は無い。アイコンは flex で中央に置く — `min-width` が足す幅は、放っておくと全部アイコンの右に落ちる（§12.3）。

**位置は行の末尾である。** 当初は行の先頭に固定していた理由（折り返しで動かない位置が先頭しか無い）は §12.11 が行を横スクロールに変えたことで前提ごと崩れ、§12.13（2026-09-18）で末尾へ移した——頻度の低いこの2つより、手前に並ぶマークの方が押される頻度が高いという判断からで、詳しい経緯は同節にある。

基準 12k（寸法）と `editor-history-buttons.spec.ts`（押したら戻る・進む、履歴が空のときは灰色、**ポインタでは描かれず、その穴も開かない**）。後者は端末をエミュレートして走らせる — 幅を狭めただけのビューポートは `hover: hover` のままなので、隠れているボタンを相手にテストが全部緑になる。

### 12.5 スマホでは書式を画面下端に、挿入をヘッダの ＋ に置く（2026-09-15 依頼・実装）

**決定**: `@media (hover: none)` のとき、主ツールバーを画面下端に固定し、ソフトキーボードが出たらその上に乗せる。並ぶのは書式だけ（元に戻す・やり直す・大見出し・小見出し・B / I / S・強調・リスト）で、挿入系（囲み枠・表・リンク・画像）は**ページヘッダの ＋ の中へ移す**。ポインタ側は一切変えない — 1 本のツールバーがフレーム上端に貼り付いたまま、12 個すべてがそこにある。引用は出荷時こそここに残ったが、§12.9 でこの列へ移っている。

**理由は、打っている最中の道具が画面の反対側にあったことである。** ツールバーはヘッダの下に貼り付いており、キャレットは本文の中ほどか下にある。しかもソフトキーボードを出したときの可視領域は 319px（`docs/embed-requirements.md`、2026-09-02 実測）で、そこに 2 段 87px のツールバーが乗っていた。下端なら親指とキャレットの両方に近く、キーボードは道具を覆うのではなく押し上げる。

**挿入系だけを外へ出すのは、打鍵中に要らないからである。** 書式は打っている語に掛けるもので、囲み枠・表・リンク・画像は「今から別の物を置く」操作である。後者に下端の常設の幅を使わせない。**効果は段数に出た**（実測 2026-09-15）: 412px は 1 段 45px、393px から 320px までは 2 段 87px。§12.4 の配置では 375px 以上が 2 段、360px と 320px は 3 段だったので、**狭い側で 1 段返している。**

**機構は 1 つのメディアクエリで、マークアップはどの幅でも同じである。** 挿入系は DOM に 2 部あり（ツールバーの中と ＋ の中）、`hover` が描かれる側を決める — §12.4 と同じ書き方で、理由も同じである（React で `matchMedia` を読むと最初の描画が一度間違ってから直る）。重複が spec を壊さないのは、**`getByRole` が既定で hidden を拾わない**からである（ARIA の tree exclusion。`playwright-core/types/types.d.ts` の `includeHidden` の説明がその出典）。`リンク`・`囲み枠`・表の 2 つを名前で引いている既存の spec はそのまま通る。**通らないのは `data-testid` と CSS セレクタの側**で、画像の隠しファイル入力は ＋ 側だけ `image-picker-touch` を名乗り、寸法を測る 12k は `:visible` で描かれている側だけを見る。

＋ のパネルは行の一覧であって、ボタンの列ではない。4 つは幅いっぱいに伸び、中身は左端から始まる（`.insert-menu-rows`）——伸ばさないと各自が自分の幅を取り、§12.2 の枠が段違いの箱を 4 つ描く（画面で確認、2026-09-15）。**囲み枠 はここでは名前を出す**: 隣の 表・リンク・画像 は言葉を持っており、しかも**タッチにツールチップは無い**（`docs/link-requirements.md` §5.5.19）ので、アイコンだけの行はこの列で唯一何も言わない行になる。ツールバー側は今までどおりアイコンのままである — あちらは幅が希少で、ツールチップもある。

＋ の読み上げ名は「ブロックを追加」である。**「挿入」にはしない** — `getByRole` の `name` は既定で部分一致なので、`挿入` は `挿入する`（`InsertDialog`）にも `2行2列の表を挿入` にも当たり、後者は ＋ のパネルの中で同時に可視になる。

**キーボードぶんの持ち上げは 2 つの機構で、足し合わさらない。** Android は `app/admin/posts/layout.tsx` の `viewport.interactiveWidget: 'resizes-content'` — レイアウトビューポート自体が縮むので `bottom: 0` がそのままキーボードの上に来る。iOS Safari はこのキーを見ない（縮むのはビジュアルビューポートだけ）ので `components/editor/useKeyboardInset.ts` が `window.innerHeight - (visualViewport.height + visualViewport.offsetTop)` を測って `--editor-kb-inset` に出す。**Android ではこの式が ~0 を返す**ので、両方入れても二重には上がらない。`offsetTop` の項は iOS でキーボードを出したままスクロールしたときに要る。`viewport` の export をルートではなくエディタのシェルに置いたのは、キーボードが開いているあいだの `position: fixed` の挙動を公開側まで変えないためである。

**下端に移ると、バーからぶら下がっている箱が画面外に落ちる。** 拒否通知の `EditorToast` は同じ CSS ブロックで上向きに反転させてある — 装飾ではなく、挿入の拒否理由を述べているので黙って画面外に出るのは欠陥である。リストのパネル（`ToolbarDropdown` の `direction='up'`）も当初はここで同じ反転を受けていたが、§12.11 でパネルごと無くなっている（囲み枠と表は ＋ の中＝画面上端なので、最初から下向きのままで足りていた）。

**本文の下余白はバーの実測高である**（`--editor-toolbar-h`、`components/editor/useMeasuredHeight.ts`）。320px で 2 段になるので定数では足りない。このフックは `--editor-header-h` と共用で、**コールバック ref であること**が効いている: ツールバーは `editor &&` の中にあり、この画面をマウントするコミットには存在しないので、`useRef` だと null を読んで二度と走らず、フォールバック値が居座る。

`next dev` の開発インジケータは E2E では切ってある（`next.config.ts`、`NEXT_DIST_DIR` があるときだけ）。あのバッジは画面左下隅に固定された `<nextjs-portal>` で、下端のバーの左端＝「元に戻す」に重なる。Playwright はオーバーレイに飲まれるクリックを拒否するので、その端のボタンを押す spec が軒並みタイムアウトした。`next dev` にしか存在せず、出荷されるページは何も変わらない。

実機での確認は未実施である。エミュレーションにソフトキーボードは無く（`docs/link-requirements.md` §5.5.21 と同じ限界）、**この節の中心にある「キーが出ると上に上がる」は E2E では一度も測れていない。** 見てもらうのは 4 点: ①iOS / Android それぞれで、キーボードを出したときにバーがその上に乗るか、②二重に持ち上がっていないか、③キーボードが出た状態で横スクロールの帯（§12.11）が指で動かせるか、④キーボードを出したままスクロールしてもバーが下端に留まるか。加えて §12 の表のツールバーとの重なり。結果はここに日付を添えて書き足す。

基準 24〜27（`editor-mobile-toolbar.spec.ts`）。寸法は §12.3 と同じく 12k が測る — ＋ とそのパネルの中身もそこに入っている。

### 12.6 スマホではヘッダの 記事一覧 を ← にする（2026-09-15 依頼・実装）

**決定**: ページヘッダ左端の 記事一覧 を左向き矢印 1 つで描く。**2026-09-21 からポインタ側も同じである**（当初はタッチだけで、ポインタは言葉だった）。ポインタでは名前をホバーのツールチップが返す。

**理由は行の幅である。** §12.5 でヘッダに ＋ が増え、この行には 記事一覧・限定公開のチップ・保存状態・＋・記事の設定・更新 が並ぶ。最初に言葉を落とせるのは、**記号で通じるもの**である — 書き手の画面の左上隅にある左向き矢印は、ラベルが無くても「戻る」と読める。これは §12.1 が表のツールバーで `行を追加` → `＋行` としたのと同じ判断で、あちらが「記号に置き換えて意味が落ちる」として `表を削除` を除外したのと同じ線の反対側にある。

**判定は幅ではなく `hover` である。** §12.1 は幅（`sm`）で切り替えたが、この行の混雑は ＋ が増えたことによるもので、その ＋ 自体が `hover: none` にしか出ない。幅で切ると、狭いデスクトップ窓で「← はあるが ＋ は無い」という、どちらの配置でもない見た目が出る。

**機構はもう無い。** 描くものが両面で同じなので、§12.4 の 2 span の対も、どちらを描くか決めるメディアクエリも消えた（2026-09-21）。両面に広げた理由は幅ではなく**ヘッダが 1 種類のものになること**である: ヘルプ（`docs/cms-features.md`「書き方ヘルプ」）がglyph として言葉 2 つの隣に増え、言葉側に揃えるなら `?` にラベルを付けることになる。いまのヘッダはアイコン 3 つと、公開するボタン 1 つである。

**読み上げ名は `aria-label` が持つ。** 可視テキストはもうどちらの面にも無いので、名前はこれだけである（WCAG 2.5.3 は描かれていない文字には掛からない）。ツールチップは `aria-hidden` で、AT が別経路で既に持っている名前を二度読ませない。

**当たり判定は正方の円で、タッチは 40×40（ヘッダ内は §12.3 の例外で 34）、ポインタは 36×36 である**（ポインタ側は 2026-09-21。それまでは言葉だったので箱の形を持っていなかった）。`toolbar-button` を着せて §12.2 の枠と §12.3 の高さを受け取り、`min-width` を足して正方にする — アイコン 1 つに高さだけ与えると細片になるのは `.toolbar-button-history` とカード帯のアイコンが先に踏んだところで、中央寄せを手で書く理由も同じ（block レベルの `<svg>` は `text-align` が届かない）。`<a>` がこのクラスを着るのは初めてだが、`<button>` でない部品としては主ツールバーの `画像`（`<label>`）が先例である。

**ポインタ側で負のマージンを持つのは 記事一覧 だけで、9px に引き直してある**（記事の設定 のぶんは 0 に戻した——歯車の右にあるのは列の端ではなく区切り線と 投稿 で、引き寄せると 36px の箱が区切り線に乗る）。 字だったころの `-mx-1`（4px）は「文字の左端を下のタイトルの左端に合わせる」ためのもので、36px の箱はアイコンを 10px 内側に抱えるので、そのままだと矢印が目に見えて字下げされる。**グリフは 18px**（アイコン部品の既定は 16px）。16px では 36px の箱の 44% しかなく、箱の中で泳いで見える——2026-09-17 にタッチのヘッダについて指摘されたのと同じ現象で、この面が同じ形になったので同じように出た。18px は箱のちょうど半分で、GitHub（16/32）と Material（24/48）が揃ってそこに居る。20px は 投稿 の 14px のラベルの隣で主張が強すぎたので採らなかった（3 サイズを描いて比較、2026-09-21）。タッチ側は 16px のままである——あちらは ＋ も同じ行に居るので、揃えるならそちらとである。**箱の中でグリフが何 px 内側に来るかはグリフの寸法で動くので、負のマージンとグリフのサイズは一緒に変える。**実測 2026-09-21: 矢印の左端 232.5px、タイトル入力の左端 232.5px。

### 12.7 タッチでは押下そのものを見せる（2026-09-15 依頼・実装）

**決定**: `@media (hover: none)` のとき、エディタの押せる部品に `:active` の背景を描く（light は zinc-300、dark は zinc-600）。セレクタは §12.3 の高さと同じ「押せる部品」一式に、カード帯と埋め込み帯の `<button>` を加えたものである。

**理由は、既定で出ていたものを消していたことである。** Tailwind の preflight が `html` に `-webkit-tap-highlight-color: transparent` を置いている。これは自前の押下表現を持つページにとっての正しい既定で、このページは**その前提の片側だけ**を受け取っていた。 `hover:` のユーティリティはすべて `@media (hover: hover)` の中にコンパイルされる（ビルド後の CSS で確認）ので、`hover:bg-zinc-100` もここでは一度も発火しない。

**実測 2026-09-15**（エミュレートした Pixel 7、`CSS.forcePseudoState` で疑似クラスを強制して `getComputedStyle` を読む）: 平常時・強制 `:active`・強制 `:hover` のいずれでも、`.toolbar-button` と ← のリンクの背景は `rgba(0, 0, 0, 0)` だった。`-webkit-tap-highlight-color` も `rgba(0, 0, 0, 0)`。つまり押下に対する反応は 1 つも無かった。

**埋めているのは「結果が出ない押下」の穴である。** ここのコマンドは同期で、結果は本文に出る — 太字は字が変わり、＋ はパネルが開き、← は画面が変わる。多くの部品は既に結果で答えているので、この規則が効くのはそうでない場合である: タッチでは**押し始めがスクロールに変わる**ことが普通にあり、そのときコマンドは発火しない。 押す前と後で画面が同一なので、「効かなかった」と「そもそも押していない」が区別できなかった。

**色は `active` の塗りと別である。** あちらは「このマークが今オンである」（`bg-zinc-200` / dark `bg-zinc-700`、`ToolbarButton.tsx`）で、同じ色を使うと既に太字になっているボタンを押したときだけ何も変わらない。 各スキームで地から 1 段ぶん遠いほうを採っている。

無効な部品はこの規則の外で、そのままにしてある。 `pointer-events-none` を持ち、無効な `<button>` はそもそも `:active` に一致しない。タッチにはツールチップも無い（`docs/link-requirements.md` §5.5.19）ので、「押しても何も起きないのが正常」であることは依然として `opacity-40` だけが言っている — この節はそこには手を入れていない。

**spec は実際のタップでは書けない。** タップは down と up が 1 呼び出しで、押されている瞬間に読む隙が無い。基準 29 は `CSS.forcePseudoState` で `:active` を強制して測る — **強制する node と背景を読む要素は同一でなければならない**（別々にすると、片方に状態を掛けて別のものを測ることになり、当然どちらも動かない。実装中に一度踏んだ）。

基準 29。

### 12.8 スマホでは 記事の設定 を歯車にする（2026-09-17 依頼・実装）

**決定**: ヘッダの 記事の設定 トグルを歯車 1 つで描く。§12.6 と同じく **2026-09-21 からポインタ側も同じ**で、言葉は `aria-label` とホバーのツールチップが持つ。`aria-expanded` はそのまま——パネルが開いているかどうかは、glyph には載せられない。

**選んだのは ⋮ ではなく ⚙ である。** §12.1 の判定基準（記号だけで意味が通じるか）をここにも当てる: ⋮（縦 3 点）は「その他の操作」というオーバーフローメニューの慣習を指し、この特定の意味は伝わらない。記事の設定は毎回の投稿で触るカテゴリ・タグ・サムネイル・限定公開という 1 つの名前付きの集まりを開くもので、雑多な副次操作の入れ物ではない。⚙ は記号だけで「設定」を指す点で ⋮ より特定的で、この開閉トグルの実体（Gutenberg の投稿設定パネルが同じ歯車を使う）とも一致する。

**枠は落とし、丸くする。** §12.6 の ← および ﹢ と同じ理由: このグループの間隔は `gap-2`（8px）で、ツールバーの詰まった 2px ではないので、丸いボタン同士の境目はリングが無くても分かる。`.editor-settings-link` に `border-radius: 9999px; box-shadow: none` を当て、40×40 の当たり判定は `.toolbar-button` から受け取る。

基準 30。

### 12.9 引用も ＋ に移す（2026-09-17 依頼・実装）

**決定**: `@media (hover: none)` のとき、主ツールバーの 引用 を外し、囲み枠・表・リンク・画像と同じ ＋ の中へ移す。機構は既存の `InsertControls`（Toolbar.tsx）に加えるだけで、新しい仕組みは無い — ポインタ側は `compact` のアイコンのまま、＋ のパネルでは `labelled` で言葉付きの行になる。ポインタ側は変わらない。

**§12.5 の境界を動かす。** あの節は「書式は打っている語に掛けるもの、挿入系は今から別の物を置く操作」と分け、引用を書式の側に置いていた。この決定はそこを動かす — 著者本人の申告では、引用を使う頻度は 囲み枠 と同じで、表・リンク・画像と同じ「ときどき使う、一発の操作」である。§12.5 が実際に測っていたのは打鍵中かどうかであって、マークかブロックかではなく、その物差しに沿って引用の側を引き直した。

**きっかけは別の相談だった。** 主ツールバーの §12.2 の枠を消したいという申し出があり、それは退けた — 密に並んだ行の境界が分からなくなるという、枠を入れた理由（2026-08-22）がそのまま戻るからである。その後に出たのがこの提案で、枠を消す代わりに行の中身を減らす側を採っている。

基準 31。

### 12.10 見出しは大見出し／小見出しでなく H2／H3（2026-09-17 依頼・実装）

**決定**: 主ツールバーの見出しボタン 2 つを、見た目だけ「大見出し」「小見出し」から「H2」「H3」にする。`hover` では分岐しない — この節群の他の決定と違い、ポインタ・タッチ両方が対象である。読み上げ名とツールチップの文言は「大見出し」「小見出し」のまま、`ToolbarButton` の `title` props で保つ。

**理由は表記の粒度を揃えることである。** 同じクラスタの B / I / S / A は既に「太字」「斜体」ではなく単一のラテン文字に短縮されている。大見出し・小見出しだけが日本語の単語のまま残っていたのは一貫性を欠いており、この 2 つがクラスタの中で最も幅を取る項目でもあった。

**`title` は「見た目の文字が名前を兼ねる」側から「アイコンボタン」側へ移る。** これまでは大見出し自身の可視テキストが読み上げ名を兼ねており、ツールチップはショートカットだけを出していた（`太字` のようなアイコンボタンは名前とショートカットの両方を出す）。H2/H3 に変えると可視テキストだけでは「大見出し」という意味は伝わらないので、`title='大見出し'` を足して太字と同じ形に移した — `editor-tooltip.spec.ts` の「text button: shortcut only」という区分はこれで実例を失い、テストもその移行を反映して書き直してある。

基準 32。

### 12.11 主ツールバーは折り返さず横スクロールする（2026-09-17 依頼・実装）

**決定**: `@media (hover: none)` のとき、元に戻す・やり直すの2つを行の左端に固定し、残り（H2/H3/B/I/S/A・箇条書き・番号付き・挿入系の隠れたポインタ用コピー）を1行の横スクロールにする。`flex-wrap: wrap` から `flex-nowrap; overflow-x: auto` へ、`.toolbar-scroll`（Toolbar.tsx）だけの変更で、ポインタ側は今までどおりの折り返す1行のままである。右端に24px幅のマスクでフェードを掛け、隠れている続きがあることを示す — スクロール位置に関わらず常に掛かる静的なフェードで、末端まで送っても消えないのは既知の簡略化である。

**きっかけは §12.2/§12.3 のマーク幅を広げたいという依頼だった。** 24pxはAAの下限であって快適さの基準ではなく(§12.3)、それでも上げなかったのは折り返しの行budgetが理由だった。実測（2026-09-17、現在の構成・引用が§12.9で抜けた後）: 24px幅なら412pxから320pxまですべて1行で収まる。広げると: 32pxで360px以上、36pxで390px以上、40pxは412pxのみが1行を保ち、320pxは28pxの時点で2行になる——320pxはソフトキーボード表示時の実質幅（docs/embed-requirements.md、2026-09-02実測）そのものであり、そこだけ2行を許すかどうかの選択を著者に問うたところ、折り返しをやめて横スクロールにする方を選んだ。

**幅の budget という制約そのものが消える。** §12.2の「幅は既に尽きている」という前提が変わったので、`.toolbar-button-wide`（`min-width: 40px`）をH2/H3/B/I/S/A・強調の全マークに足した——40pxは`.toolbar-button-history`が既に持っていた値と同じで、undo/redoだけが幅をもらえた理由（測定済みの2つを除いて行が増える）はもう成り立たない。

**元に戻す・やり直すは行の末尾にある。** 当初は横に動く行の外側に固定していたが、§12.13（2026-09-18）で行の末尾へ移り、他のマークと同じく横スクロールする側に含まれている——理由と測り直しは同節にある。

**`overflow-x: auto` は `overflow-y` も暗黙に `auto` にする。** CSS の仕様どおりの挙動で、`.toolbar-scroll` の中に住んでいたリストのドロップダウン（トリガー+パネル、`ToolbarDropdown.tsx`）のパネルが、開いても実際には見えなくなっていた——`getBoundingClientRect()` は要素自身の寸法しか返さないので、パネルの位置だけを見る既存の spec はこのクリップを一度も検出しなかった（発見時のスクリーンショットで確認）。

**タッチだけドロップダウンでなくす**のが採った修正である。ポインタは元のリストのドロップダウンを保つ——タッチだけが `.toolbar-scroll` の中に住んでいたので、クリップされるのもタッチだけだった。機構は §12.4/§12.5 と同じ「DOM に両方、`hover` が描く側を決める」idiom そのものである: `.list-dropdown`（`<ListMenu>` を包む）は同じ span が併記する `pointer-only` でタッチから消え、`.list-buttons`（箇条書き・番号付き の直接トグル2つを包む、ショートカットは元の `Mod-Shift-8`/`Mod-Shift-7` のまま）は `touch-only` でポインタから消える。`display: none` を宣言しているのは `.pointer-only`（`hover: none`）と `.touch-only`（`hover: hover`）の2ルールだけで、形状名の側はもう gate を持たない——どちらの面に属するかが TSX の行だけで読めるようにするため（2026-09-20）。どちらの span も常に `contents` なので、内側の要素はこのツールバー行の直接の flex item のままである。`ToolbarDropdown` の `direction` prop（`up` 用。§12.5 で導入）は、リストのドロップダウンがポインタ専用になった今も呼び出し元が無い——ポインタ側のツールバーはフレーム上端にあり、下向きで足りるからで、削除したままにしている。

基準 33。

### 12.12 マークの列は枠をやめて区切り線にする（2026-09-18 依頼・実装）

**決定**: `.toolbar-scroll .toolbar-button`（主ツールバーの H2/H3/B/I/S/A・強調・箇条書き・番号付き・元に戻す・やり直す）から §12.2 のリングを外す。代わりに、H3/B の間と強調の右に `.toolbar-mark-divider`（1px、light は zinc-300、dark は zinc-600、`shrink-0`、`hover: none` のみ表示）を置く。**リングを外す範囲はここでは主ツールバーの行だけだったが、2026-09-19 に §12.2 側で残り全部（表のツールバー・リンクカード・コールアウトメニューなど）からも外し、以降はどのコンポーネントもリングを持たない** — この節が今も担うのは区切り線を置く決定のほうである。

**依頼は note と Google Docs のモバイル版ツールバー（どちらも枠なし）との比較だった。** 検討順序: (1) 枠だけ外し gap は据え置き — H2/H3 のような複数文字ラベルは読めるが、B/I/S のような単一文字は静止時の境界がやや曖昧。(2) Docs 方式の広い gap（8px） — 表のツールバーと同じ 328px/360px の幅 budget を食う。主ツールバーは §12.11 でスクロールに変わっており budget から外れたので安全だが、表のツールバーは今も `flex-wrap` のままなので同じ変更はできない（そこは触っていない）。(3) 最終的に採ったのが区切り線: gap は既定の 2px（`gap-0.5`）に戻し、グループの境界だけを線で示す。

**`shrink-0` が要る。** 中身の無い区切り span の min-content 幅は 0 で、`.toolbar-scroll` の `flex-nowrap` は既定の `flex-shrink: 1` のもとで空の flex item を真っ先に 0px まで潰す（`wide` マークは `min-width: 40px` が潰れを止めている）。実測 2026-09-18: `shrink-0` を欠いたまま出荷すると、区切り線はどの幅でも見えなかった。

基準 34（`.toolbar-mark-divider` が 2 本・幅と高さが正・ポインタでは非表示、主ツールバーの `.toolbar-button` にリングが無いこと）。表のツールバー等に「残っている」という半分は §12.2 の 2026-09-19 の更新で崩れており、そちらの現在の基準（リングがどこにも無いこと）に統合されている。

### 12.13 元に戻す・やり直すを列の末尾へ移す（2026-09-18 依頼・実装）

**決定**: 元に戻す・やり直すを `.toolbar-scroll` の先頭固定（§12.11 の配置）から列の末尾へ移す。固定を解いたので、他のマークと同じく横スクロールで隠れたり現れたりする。

**依頼は「固定は使用頻度に見合っていないのでは」だった。** §12.11 で固定した理由（スクロールした指がすぐ戻れる動線）は計測に基づく決定ではなく、この移動の理由（マークの方が押される頻度が高いはず）も同様に未計測である——判断材料は note の実機で、そちらも undo/redo を列の末尾に置いている。

**ヘッダへ移す案（Google Docs 方式）は幅が足りず不採用。** 実測 2026-09-18、§12.14 でバッジと保存状態を圧縮した後の数字: 360px で左側 100px・右側グループ（＋/歯車/投稿）187px から始まり、空きは 87px。元に戻す・やり直すは 40px×2＋gap で約 88〜97px 必要で、ほぼ境界線上。§12.11 がツールバーに課している下限の 320px では、空きは 47px しかない——必要な幅の半分ほどで、成立しない。

基準 35（列の末尾にあること・スクロールで現れること・現れた状態で実際に押せること）。

**同日中に試して戻した案がある。** ＋を（元に戻す・やり直すが§12.11以前に居た）行の先頭固定へ、元に戻す・やり直すをヘッダの＋の位置へ、という入れ替えを実装して screenshot まで確認した——note が＋を行の先頭に置いていることを根拠にしていた。戻した理由は、ヘッダで 記事一覧 の ← の隣に元に戻すの ↺ が並ぶと紛らわしいという見た目上の判断で、コード上の痕跡は残していない（＋は §12.5 のままヘッダに、元に戻す・やり直すは上のとおり行の末尾のまま）。

### 12.14 ヘッダーのバッジと保存状態はタッチでは圧縮する（2026-09-18 報告・実装）

**決定**: `@media (hover: none)` のとき、限定公開バッジをテキストのチップから `LockIcon`（`components/editor/svg/LockIcon.tsx`）のみへ、保存状態の 保存中… を非表示へ、保存済み ✓ を ✓ のみへ圧縮する。保存に失敗はどちらの端末でもフルテキストのまま変えない。バーの左 padding（`px-2`）もタッチだけ 0 にする。

**報告は §12.13 の調査中に出た**: 限定公開のバッジと保存状態が同時に出ている実際の状態（下書き保存中の限定公開記事）で、360px のヘッダが 2 行に折り返っていた——undo/redo とは無関係で、既存コードに元からあった状態である。

**消すのではなく縮める。** バッジと 保存に失敗 はどちらも事故防止のための表示で（バッジ: 著者が公開範囲の変更を忘れやすい。保存に失敗: 唯一のデータロス検知経路）、消せば同じ事故が起こり得る。**全廃したのは 保存中… だけである** — `unsaved` が真である間ずっと出続ける表示で、ポインタ側の理由（自動保存が生きている証拠を常に示す）はタッチの画面幅には見合わないと判断した。保存に失敗は変わらず割り込むので、圧縮後も「何も出ていない」は「問題ない」のままである。

**バッジの色分けは保つ** — ✓ は green-600 のまま、ロックアイコンは violet-500 のままで、状態はグリフの意味と色の両方で読める。`aria-label` が読み上げ用の全文（「限定公開」「保存済み ✓」）を持つ。

基準 36（タッチでロックアイコンが出てチップが出ないこと・行が 1 段に収まること・保存中は無音で保存済みは ✓・保存に失敗はどちらの端末でも出ること・バーの左 padding が 0 なこと）。

### 12.17 元に戻すの左にも区切り線を置く（2026-09-18 依頼・実装）

**決定**: 番号付きの右・元に戻すの左に `.toolbar-mark-divider` をもう1本置く。§12.12 と同じクラス・同じ見た目（1px、light は zinc-300、dark は zinc-600、`shrink-0`、`hover: none` のみ表示）。

### 12.18 ＋のパネルは下から上に開くシートにする（2026-09-18 依頼・実装）

**決定**: `InsertMenu.tsx` の ＋ パネルを、トリガーの右端に固定した小さな箱（`absolute right-0 top-full`）から、画面幅いっぱいの `fixed` シートに作り替える。半透明の背景（`z-[45]`、書式バーの `z-40` より上）とセットで、シート自体は `z-50`、`bottom` は書式バーの `var(--editor-kb-inset, 0px)` と同じ値——書式バーを覆う形で、バーは隠れる。

_縦位置は一度「バーを覆わずその真上に」（`bottom` に `--editor-toolbar-h` を足す）と変えたが、同日中に戻している——note も Google Docs も、このパネルを開いている間は自分のツールバーを隠す形だったため、確認のうえ元に戻した。_

**note の実機がこの形で ＋ を開く**ことが動機で、§12.13 の議論中に出た「＋も先頭固定にしたい」という提案（§12.13 の追記を参照、コードには残っていない）とは別の軸——位置ではなく開き方を note に寄せる決定である。

**アンカーが要らなくなる。** 画面幅いっぱいの `fixed` シートは `left`/`right` のどちらから測るかという選択自体が無くなる——旧パネルが「トリガーの右端」に固定されていたのは、ヘッダが折り返す環境で左右どちらから測っても幅の関数になるのを避けるためだったが（実測 320〜412px で全域そのまま）、シート化するとその制約ごと消える。

**背景は`useDismiss`の外側判定を素通りする。** 画面全体を覆うので、`useDismiss` の「外側を押したか」の判定にとって「外側」が存在しなくなる——`ref` はシート本体だけに絞り、背景自身の `onClick` で閉じる（Escape は引き続き `useDismiss` が担当）。

**背景は本文への押下も塞ぐ。** 旧パネルは本文の外への press が同時にパネルを閉じつつ press 自体は本文に届いていた（`mousedown` の document リスナーが先に発火するため）。背景付きの実モーダルではその通り抜けが無くなり、閉じる press と本文を操作する press は別になる——`editor-narrow-menus.spec.ts` の 12k は、パネルを開けたままにして次のクリックへ進む書き方だったため、この変化で赤くなった（Escape を挟むよう直した）。

**`document.body` への `createPortal` が要る。** `InsertMenu` はヘッダの中にあり、ヘッダ自身が `sticky` + `z-40`——スタッキングコンテキストを作る。`fixed` な子要素はこれを z-index の点では抜けない: シートの `z-50` はヘッダの中だけで比較され、トップレベルでは「ヘッダも書式バーも `z-40`」の同点勝負になり、DOM で後にある書式バーが勝つ。**「バーを覆う」と書いた直後の実装がまさにこれで壊れていた**——シート側の `getBoundingClientRect()` は書式バーの矩形を完全に含んでいたにもかかわらず、実際の画面ではバーが上に描画されていた（報告 2026-09-18: 「ツールバーが見えてます」）。`InsertDialog` がトリガーの位置に関わらず `PostEditor.tsx` から直接マウントされているのと同じ理由で、ポータルでヘッダの外に出して直す。

**縦幅は `min-h-[40vh]`（依頼 2026-09-18）。** 5 行だけなら 740px 画面で実測 237px（32%）まで自然に収まっており、当初の `min-h-[33vh]` はその高さをほぼ変えなかった（237→244px）ため、40vh まで上げている（実測 296px＝ちょうど 40%）。`max-h-[70vh]` は変えていない——縦幅を増やしたのは足りない側で、ソフトキーボードで押し上げられたときに上端が画面外に出る側の上限はそのまま。

基準 38（背景が出ること・背景タップで閉じて本文に何も起きないこと・パネルが画面幅いっぱいであること・縦幅が画面高の 40% 以上であること）。

**枠線は一度外し、丸みを縮めたあとで戻した（2026-09-19）。** `rounded-t-2xl` のときは丸み＋影＋暗くなった背景で境界が十分読めるとして `border-t border-zinc-300` を削除したが、丸みを 8px（`rounded-t-lg`）まで縮めた結果、境界の主張が弱まったという指摘を受けて戻している。ドラッグハンドル（`mx-auto h-1 w-10 rounded-full`）は別の理由（ドラッグで閉じる操作が無く見た目だけの飾りだった）で削除したままである。**見出し「挿入」は逆に追加している** — note と Google Docs の両方がこの位置に見出しを持つのが根拠で、枠線・ハンドルと違って影や丸みでは代替できない情報（「これは挿入メニューである」）を運ぶため。トリガーの `aria-label`（「ブロックを追加」）とは文言をあえて揃えず、見出しはプレーンテキストの `<h2>` として `aria-labelledby` でパネルに紐付ける——ボタンの accessible name として「挿入」を使うと `getByRole('button', { name: '挿入' })` が「挿入する」や「2行2列の表を挿入」まで拾ってしまう問題（`InsertMenu.tsx` 冒頭のコメント）を、見出しは `button` ロールを持たないことで避けている。

基準 39（パネルの見出しが「挿入」であること、`role="dialog"` と `aria-labelledby` で紐付いていること）。

**角の丸みは `rounded-t-lg`（8px、2026-09-19、依頼）。** 元の `rounded-t-2xl` はどちらの実物とも一致しなかった——Google Docs のシートには丸みが無く、note にはあるが `rounded-t-2xl` より明らかに控えめ。同日中に一度正方形の角（丸み無し）まで落としたが、この節群の主な参照元である note からの乖離が大きすぎると判断し、4px に戻した。さらに 4/6/8px をスクリーンショットで並べて比較し、最終的に 8px を採用している。note・Docs いずれの半径も実測はしていない、目視比較のみの選択である。

### 12.19 ＋パネルの各行はカードではなく横幅いっぱいの行にする（2026-09-19 依頼・実装）

**決定**: `.insert-menu-rows .toolbar-button`（`app/globals.css`、`hover: none` 限定）で、パネル内の各行（囲み枠・引用・表・リンク・画像）からリング（§12.2）と角丸を外し、幅を 100% にする。パネル自体の左右 padding（`p-2`）も外して行を画面幅いっぱいまで伸ばし、代わりに見出しと行それぞれが自分の `px-4` を持つ。行どうしの区切りは `gap-0.5` ではなく `divide-y`（薄い罫線 1 本）に変えている。

**セレクタ 1 本で 4 コンポーネントに効く。** 囲み枠（`CalloutMenu`）と表（`TableGridMenu`）は `ToolbarDropdown` 越しに `ToolbarButton` を描くが、そのトリガーも `.insert-menu-rows` の子孫である（`ToolbarDropdown` 自身がどのメニューから呼ばれても `.relative.flex` ラッパーごと `.insert-menu-rows` の中に入る）。引用・リンクの素の `ToolbarButton` と、画像の `<label className="toolbar-button ...">` も同じクラスを持つので、4 つの呼び出し元に prop を通す代わりに `app/globals.css` の 1 セレクタで揃えている。

**リングが外れるのは§12.12とは別の理由からである。** 主ツールバーの行は note/Docs のボーダーレスな見た目に寄せた決定だったが、こちらは「カードでなく横幅いっぱいを押せるようにしたい」という依頼——結果としてどちらも `box-shadow: none` になるが、根拠は別の節に分けて記録している。

**囲み枠・表のシェブロンは行の左寄せのまま**——ラベルのすぐ右に来ており、行の右端には寄せていない。今回の依頼は押せる範囲の話で、シェブロンの位置までは触れていない。

基準 40（パネルの各行が幅いっぱい・角丸なし・リングなしであること）。

### 12.20 囲み枠・表はフローティングパネルでなくシート自身にドリルダウンする（2026-09-19 依頼・実装）

**決定**: `.insert-menu-rows`内の 囲み枠・表 は、タップしても`ToolbarDropdown`自身のフローティングパネル（§12.15 以前の小さな吹き出し）を開かない。代わりに`InsertMenu.tsx`が持つ「ドリルダウンスロット」に、その行のピッカー（囲み枠の 3 種・表のグリッド+ダイアログ）を portal で差し込み、シートの見出しを行の名前に、行一覧を 戻る ボタンに置き換える。ポインタ側の`ToolbarDropdown`は無変更 — `components/editor/insert-menu-nav.ts`の`InsertMenuNavContext`が`null`のときは従来どおりのフローティングパネルを開く。

**`render(close)`を InsertMenu へ渡すだけでは壊れる。** 最初に試した版は、行を押した瞬間に`ToolbarDropdown`の子（`(close) => ReactNode`）をそのまま`InsertMenu`の state に保存し、`InsertMenu`側で描画していた — 見た目は動くが、`CalloutMenu`/`TableGridMenu`自身は元の位置（`view`が非 null の間は描画されない分岐）で**アンマウントされる**。`TableGridMenu`のグリッドのホバー状態・「行数・列数を入力…」ダイアログの開閉状態はどちらもその component instance が持っているので、アンマウント後は`setHover`/`setDialogOpen`が誰も見ていない fiber を更新するだけの no-op になる — グリッドのハイライトは二度と動かず、ダイアログは二度と開かない。**修正は `createPortal` で DOM 出力だけを動かすこと**: `CalloutMenu`/`TableGridMenu`は常にマウントされたまま（`InsertMenu.tsx`の行一覧側`<div hidden>`は`hidden`属性を切り替えるだけで、条件分岐による着脱はしない）、`ToolbarDropdown`が`nav.activeTitle === title`のときだけ自分の子を`nav.portalTarget`（ドリルダウン側の`<div ref={setPortalNode}>`）へ portal する。

**`<dialog>`はさらにもう一段 portal がいる。** 「行数・列数を入力…」の`TableSizeDialog`は`showModal()`でトップレイヤーに昇格するが、祖先に`display:none`があると（`InsertMenu.tsx`が行一覧側を`hidden`にした状態で、その子孫である`TableGridMenu`の下にこのダイアログが居座っていると）トップレイヤーでも描画されない。`TableGridMenu.tsx`はこのダイアログ単体をさらに`document.body`へ`createPortal`し直して逃がしている — `InsertDialog.tsx`が既に別の理由（スタッキングコンテキスト）で使っている手と同じ形。

**実測した回帰: `useDismiss`が枠の外へのクリックとしてシート全体を閉じていた。** 上の 2 段目の portal を入れた直後、ダイアログは開くのに「追加」を押しても`insertTable`まで届かない不具合が起きた——`elementFromPoint`でボタン自身がクリック位置に居ることは確認済みで、原因は別にあった。`InsertMenu.tsx`の`useDismiss(open, () => setOpen(false))`は`mousedown`の`event.target`が`ref.current`（`.insert-menu-panel`）に**DOM として**含まれるかで判定しており、`document.body`に portal されたダイアログはその判定上「外側」になる。ダイアログ内の mousedown がバブルして`document`に届くと、シート全体の`setOpen(false)`が先に走り、`TableGridMenu`（とその portal であるダイアログ自身）がクリックの完了前にアンマウントされて`submit()`が呼ばれないまま消えていた。修正は`InsertDialog.tsx`の中身用 div が既にやっている`onMouseDown={(event) => event.stopPropagation()}`と同じもので、`TableSizeDialog`の中身用 div にも足した。

**`ChevronIcon`の回転は使われなくなった。** 囲み枠・表 の行に付けた ＞（`.chevron-icon`, `rotate(-90deg)`）は、この節より前は開閉で `rotate-180`（下向き）にも切り替わっていたが、ドリルダウンでは`ToolbarDropdown`自身の`open` state が一度も真にならない（トリガーは`nav.activate(title)`を呼ぶだけ）ので、その切り替え先の CSS は書いても当たらない。削除して、＞ で固定にしている。

基準 41（タッチ端末で、囲み枠・表 の行を押すとフローティングパネルでなくシート自身の見出し・行一覧が置き換わり、戻るで元に戻ること）。
基準 42（タッチ端末で、表 の「行数・列数を入力…」がドリルダウンの中からでも開き、実際に表を挿入できること）。

### 12.21 エディタに一度も触れていないとき、＋の行が RangeError を投げる（2026-09-19 報告・修正）

**症状**: 表・囲み枠・箇条書きなどで終わる記事を開き、本文を一度もタップせずに ＋ → 引用（または囲み枠・表）を押すと、`Uncaught RangeError: Applying a mismatched transaction`。§12.20 が 囲み枠・表 をドリルダウンにしたことで見つかった不具合だが、原因はドリルダウンにはなく、`Toolbar.tsx`の 引用 ハンドラも含め`editor.chain().focus().X().run()`という形そのものにある。Android/iOS の UA でのみ再現し、Chrome デスクトップでは再現しない（下記参照）。

**機構**: `@tiptap/core`の`focus`コマンドは、Android/iOS では`view.dom.focus()`を**同期的に**呼ぶ（`node_modules/@tiptap/core/dist/index.js`、`isiOS() || isAndroid()`の分岐）。この呼び出しはブラウザのネイティブ`focus`イベントを同期的に発火させ、`FocusEvents`拡張(`handleDOMEvents.focus`)がその場で`view.dispatch(...)`する——これは今組み立て中のチェーンとは**別の**トランザクションで、`trailing-node-extension.ts`の`appendTransaction`もこれに乗って走る。記事の最後のブロックが段落でなければ(表・囲み枠・箇条書きなど)、末尾に空段落が挿入され`editor.state.doc`が進む。一方、`.focus()`を呼んだ側のチェーン(`toggleBlockquote`等)は、チェーン開始時点の`state`から作った`tr`をまだ抱えたままで、これを`.run()`で dispatch した瞬間に`tr.before`と現在の`view.state.doc`が食い違い、`RangeError`になる。**`editor.commands.focus()`のように2文に分けても直らない** — `commands.focus()`自身の dispatch が、まさに同じ理由で同じ不整合を起こす（実測: 分けても例外は消えなかった)。

**修正**: `editor.view.dom.focus()`という生の DOM 呼び出しを、tiptap のどのコマンドの外でも先に実行する。ネストした dispatch(=FocusEvents の`appendTransaction`込み)がここで完結してから、`editor.chain().X().run()`を全く別の呼び出しとして組み立てる——このときの`tr`はすでに append 後の`editor.state`から作られるので食い違わない。`components/editor/focus-then-run.ts`の`focusThenRun(editor, (c) => c.X())`がこの2段をまとめた共通ヘルパーで、`Toolbar.tsx`(引用・大見出し・小見出し・太字・斜体・取り消し線・強調・箇条書き・番号付き(リスト用ドロップダウン・タッチの直接トグル両方)・リンク)、`CalloutMenu.tsx`の`choose`、`TableGridMenu.tsx`の`insert`——`.chain().focus().X().run()`という形を使っていた箇所のうち、実際にその形へ到達しうるもの全てに適用済み。

**報告後に確認が広がった経緯**: 最初に直したのは実際に踏んだ 引用・囲み枠・表 の3箇所のみで、「同じ形の他のボタンは未検証」と一旦書いていたが、主ツールバーの太字系・見出し系でも同じ`RangeError`が実測されたため、`.chain().focus().X().run()`という形を持つ箇所を洗い出して揃えた。**元に戻す・やり直すだけは元の形のまま残している** — この2つは`disabled`が履歴の有無で立つので、「一度も触れていない」状態では押せない。履歴が生まれるのは何らかのトランザクションが着地した後で、着地させる側のボタンは全て`focusThenRun`を通るようになった以上、着地の時点で必ず一度フォーカスが済んでいる——つまり元に戻す・やり直すが押せる状態になった時点で、この不具合の前提(未フォーカス)はもう成立しない。

基準 43（タッチ端末で、表・箇条書きなどで終わる記事を開き直し、本文に触れずに ＋ の 引用・囲み枠・表(グリッド・ダイアログとも)・リンク、および主ツールバーの太字・大見出し・箇条書きを押しても例外にならず、実際に効くこと）。
