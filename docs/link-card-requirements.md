## 0. 前提 — 今どれだけ使われているか

2026-08-12 に `data/blog.db`（`-wal` ごとコピーして集計。`sqlite-copy-needs-wal.md`）を見た結果:

- 投稿 3 件（`hello-world` / `second-post` / id 36「テスト」）
- 本文（`body` + `draft_content`）に含まれる markdown リンク 2 件、いずれも id 36 の中
- ほかに `\[電話\](tel:+81312345678)` という**エスケープ済みのリテラル 1 件**がある。これはリンクではない（§2.2.1 の「打った `[]()` は潰れる」がそのまま残っている物証で、§2.4 のプロトコル検証の残骸である）

**そして 2 件のうち 1 件は、既に「行に単独で置かれたリンク」である。** id 36 の本文 59 行目、前後が空行:

```text
[https://zenn.dev/zenn/articles/markdown-guide#脚注](https://zenn.dev/zenn/articles/markdown-guide#%E8%84%9A%E6%B3%A8)
```

リンク文字列と href は percent-encode の差しかないので、`<...>` の山括弧形式にはならず `[]()` の形で保存されている（§2.2 が書いている「ちょうど同じとき」に当たらないため）。href 側が encode されているのは §2.2.2 の往復の結果である。

**この 1 行は、著者が何もしなければカードにならない。** §14 が外部 URL のカードを作ったあとも同じである — §4.1 の (a) と (d) が昇格を却下し、入口は意図的な操作だけに限られている（2026-08-12 実測。§5.1、§5.2-1、§14.6）。バブルの「カードにする」を押せばカードになるが、それは著者の操作である。この機能は過去の記事の見え方を 1 行も書き換えない。

この行の意味は証拠のほうである。`link-requirements.md` §0 は 2026-08-09 時点でリンクを 1 件と数えていた。増えた 1 件がこれである。つまりこれは前日 2026-08-11 の §5.5 バブルの動作確認で入った**テストの残骸であって、著者が「カードにしたい」と思って書いた行ではない**。

**したがって §0 は「需要がある」の根拠にはならない。** 実投稿でのリンク使用は依然ゼロに近く、`link-requirements.md` §0 が②を延期した状況と変わっていない。この文書が書かれているのは需要が測れたからではなく、保存形式の決定を今やるほうが安いからである（§4 冒頭）。

## 1. 目的と非目標

**目的**: 行に単独で置かれた URL／自サイトの記事へのリンクを、タイトルの読めるブロックとして公開ページに出す。文中のテキストリンクはこれまで通りテキストリンクのまま残す。

**この文書は `docs/link-requirements.md` §1 の非目標を 1 行取り下げる。** あちらは「リンクカード／URL の展開表示（Zenn の `@[card]` に相当するもの）」を対象外と書いている。取り下げるのはその行だけで、他の非目標（リンク切れ検査、`title` 属性の編集 UI）はそのままである。

**非目標**（この文書でも対象外）:

- **外部 URL のカード** — §4〜§7 が決めるのは内部カードだけである。外部カードの要件と設計は §14 にあり、§8 の延期は 2026-08-18 にそこで解除した
- リンク切れ検査、カードの手動リフレッシュ UI

## 3. 現状 — 今この形は何になるか（実測 2026-08-12）

| 行に単独で置いたもの           | エディタ                       | 保存形式                | 公開ページ     |
| ------------------------------ | ------------------------------ | ----------------------- | -------------- |
| `https://example.com` をタイプ | 段落内の autolink              | `<https://example.com>` | 段落内の `<a>` |
| 同上を選択範囲にペースト       | 経路 (a) のリンク              | `[text](href)`          | 段落内の `<a>` |
| `/posts/foo`                   | **リンクにならない**（§2.1.1） | ただのテキスト          | ただのテキスト |

3 行目が §2.1.1 の穴そのもので、2026-08-11 のバブルで「URL 欄に打てば作れる」ところまでは塞がった。**ただし作れるようになったのはテキストリンクであって、カードではない。**

公開側のパイプライン（`lib/render.ts`）に「行に単独のリンク」を特別扱いする段は無い。remark-gfm が普通の段落内リンクとして処理して終わりである。

## 4. 決定① — 保存形式は「参照だけを持つ raw HTML」

**この決定を今やる理由**: 保存形式を間違えたときの移行コストは、対象記事が増えるほど上がる。§0 の通り現在の該当行は 1 行、しかもテスト残骸である。移行コストが実質ゼロなのは今だけで、以後は単調に増える。他の項目（見た目、NodeView の作り込み）は来月やっても値段が変わらないので、決定の順序はこれが先になる。

### 4.1 候補を選別する試験 — 「エディタの往復を曖昧さ無しで生き延びるか」

| 候補                                             | 往復                                                           | 判定     |
| ------------------------------------------------ | -------------------------------------------------------------- | -------- |
| (a) 行に単独の裸 URL をそのままカードと解釈する  | 解釈する以上パーサ側も昇格させる必要がある                     | 却下     |
| (b) `@[card](url)` のような記法                  | 手で打つと別物になる（下記）。ノードが書けば生き残る           | 却下     |
| (c) **参照だけを持つ raw HTML**                  | ノードシリアライザが raw で書くのでエスケープを踏まない        | **採用** |
| (d) 行に単独の**相対パスのリンク**をカードにする | 曖昧さは無い（相対パスは autolink されないため）が、代償がある | 却下     |

- **(a) の落ちる理由**: 昇格させると、行に単独の裸 URL を「ただのリンク」として書く手段が永久に無くなる。今その形は実在する（§0 の 67 行目）。往復の対称性のために表現力を 1 つ失うのは高すぎる。
- **(b) の落ちる理由**: 同じ記法が出所によって別のものになる。 ノードが生成した `@[card](url)` はそのまま生き残るのに、著者が手で打った同じ文字列は**カードにならない** — 判定当時（2026-08-12）は text ノードの直列化が `[` `]` を無条件にエスケープするので `\@\[card\]…` に潰れて死んでいた（`state.text(escapeHTML(node.text))` — `tiptap-markdown.es.js:628` → `prosemirror-markdown` の `esc()`）。`docs/link-requirements.md` §5.4 の入力ルールが入った 2026-08-17 以降は、潰れる代わりに `@` + 普通のリンクになる（実測、`e2e/editor-link-markdown-syntax.spec.ts`）。**却下の理由は動いていない。** 死に方が変わっただけで、手で打った記法がカードにならないことは同じであり、入力ルールが `@` を特別扱いする理由も無い。
- **(d) の落ちる理由**: 曖昧さが無いのは本当で、そこは (a) より優れている。しかし行に単独の内部テキストリンクが書けなくなる。「詳しくはこちら」だけの段落は普通に書きたい形なので、(a) と同じ種類の損失が相対パス側で起きる。**検討したうえで却下したのであって、思い付かなかったのではない**（§11）。

### 4.2 なぜアコーディオンの前例が移らないか

`details-extension.ts` の `serializeDetails()` は `<details><summary>…</summary>…</details>` という HTML を焼き込む形で保存している。カードもこれに倣いたくなるが、**倣ってはいけない**。

違いは中身の出所である。アコーディオンの中身は著者が書いたものなので、焼き込んだ HTML が唯一の正本でよい。カードの中身（記事タイトルと説明）は別のレコードから導かれるもので、そのレコードは独立に変わる。記事タイトルを直したのに、リンク元の記事に古いタイトルが焼き付いたまま残る、という形になる。

**したがって保存されるのは参照だけである。** 形は次のとおり:

```html
<div class="link-card" data-href="/posts/f377f7a9a768a5b4d6f2"></div>
```

空要素であることが重要で、表示に出る文字は 1 つも保存しない。`markdown-it` は `html: true`（`PostEditor.tsx:290`）、公開側は `rehypeRaw` が既に居るので、両方向とも新しいパーサを足さずに通る。`accent-emphasis` が「native な markdown 記法が無いので raw `<span>` で往復させる」（`lib/render.ts` のコメント）のと同じ形であり、前例は 2 つある。

### 4.3 sanitize スキーマに要ること（実測 2026-08-12）

`hast-util-sanitize` の `defaultSchema` を読み出して確かめた:

| 事実                                           | 値                                                 |
| ---------------------------------------------- | -------------------------------------------------- |
| `tagNames` に `details` / `summary`            | どちらもある（だからアコーディオンは無改造で通る） |
| `tagNames` に `div`                            | ある                                               |
| `attributes['*']` に `className`               | 無い                                               |
| `attributes['*']` に `data-*` のワイルドカード | 無い（`data` で始まる項目はゼロ）                  |
| `attributes.div`                               | `["itemScope","itemType"]` のみ                    |

つまり `class` も `data-href` も**明示的に足さない限り両方落ちる**。落ちたときカードは中身の無い `<div>` になるので、黙って消える。足し方には既に踏まれている落とし穴が 1 つある:

**`link-card` は `div` に 2 本目の `['className', …]` を足す形では書けない。** `lib/render.ts` のコメントが理由を書いている — `hast-util-sanitize` の `findDefinition` は名前が一致した最初の項目で返るので、同じ属性名のタプルを 2 本目に足しても死んだままになる。既存の `alertClasses` タプルに値として混ぜるしかない。

`data-href` は hast のプロパティ名（キャメルケース）で書く。`attributes.a` に `dataFootnoteBackref` / `dataFootnoteRef` という前例がある。

### 4.4 `data-href` は許可リストに守られない — 参照は解決側が検証する

**2 つの属性は守られ方が違う。** `className` は値の許可リスト（`['className', 'markdown-alert', …]` の形）なので、列挙した名前だけが通る。`data-href` はただのプロパティ名なので、足した瞬間にどんな値でも通る。

ここが穴になる。保存形式は raw HTML であり（§4.2）、`markdown-it` は `html: true` なので、著者は `<div class="link-card" data-href="javascript:…">` を手で書ける／貼れる。`lib/render.ts` は「非管理者も投稿を書くようになった以上、MDX 中の生 HTML は信頼しない」と明記していて、その前提はカードにもそのまま掛かる。

そして §6 の通り解決段は sanitize の後ろに置くので、そこで生成する `<a href>` は `rehypeSanitize` のプロトコル検査を一度も通らない。`link-protocols.ts`（エディタ側）も許可スキーマ（sanitize 側）もこの経路には居ない。

**したがって検証は解決側の責務である。** `resolveCard` は `data-href` を信頼せず、内部記事の参照として妥当な形（`/posts/<slug>`）であることを自分で確かめ、外れたものは解決せずに落とす。述語は**指してよい形の許可リスト**である — 内部カードは「`/posts/` で始まり既知の slug であること」、外部カードは `http(s):` だけを通すスキーム許可リスト（§14.2）。どちらも、禁止したいものを並べる形では書かない。

`link-requirements.md` §2.4 がプロトコル許可リストのずれ 1 件に丸ごと 1 節を使っているのと同じ種類の穴であり、同じ轍を踏まないために先に書いてある。

## 5. 決定② — 入力の引き金

**§4 とは別の話である。** §4 は「保存された形が何か」、ここは「どの操作でその形が生まれるか」。(c) を採ったので、位置は保存形式の一部ではなく、入力時の判定にすぎない。

### 5.1 URL と相対パスは同じ経路では来ない

これが設計の実際の形で、要望の文面からは見えない部分である。

| 作りたいもの      | 到達経路                                                                      |
| ----------------- | ----------------------------------------------------------------------------- |
| 外部 URL のカード | ペースト経路に乗せられる（linkifyjs が URL を認識する — §2.1）                |
| 内部記事のカード  | **ペーストでは絶対に来ない。** linkifyjs は相対パスをリンクと見ない（§2.1.1） |

したがって内部カードは「貼ったら勝手になる」があり得ず、**意図的な操作からしか作れない**。外部カードは経路としてはペーストに乗せられるが、乗せない — 入口は 2 つとも意図的な操作である（§14.6）。

### 5.2 規則

1. **カードは行を占有するブロックであり、文中には入らない。** 段落の途中に挿入することはできず、ペーストやドロップで文中に着地することもない（§5.4）。カードが生まれるのは著者の意図的な操作からだけで、パーサも入力ルールも昇格させない — §4.1 が却下したのはそちらである。既存のリンクをカードに変える経路はバブルの「カードにする」1 つで、これも著者の 1 クリックである（2026-08-18 追加、§14.6）。文中の `詳しくは[この記事](/posts/foo)を参照` はテキストリンクのまま残る。
2. 内部カードをゼロから作る入口は**スラッシュメニュー**とする（`slash-command.ts`。既存のブロック挿入と同じ場所で、ツールバーを増やさない）。既にリンクになっているものをカードにする経路は §14.6 が別に持ち、そちらは内部・外部を問わず同じボタンである。
3. 挿入時は**自分の記事を検索して選ぶ**。これが Google Docs の内部リンクの実際の肝であり、§2.1.1 の「内部リンクを作る経路が無い」を正面から埋める。データ源は `getPostBySlug` と同じ `posts` テーブルなので、カードの表示と挿入時の検索は同じクエリを共有する（§5.3）。
4. `draft` の記事も検索に出すが、選んだ場合はその旨をエディタ上で示す。カードの中身は公開時に解決され、draft を指したカードは素のテキストリンクに落ちる（§6）ので、ここで防がないと公開後に気付くことになる。
5. **検索結果の行は記事の顔を出す** — サムネイル・タイトル・カテゴリの 3 つで、`draft` はタイトルに連結せずバッジにする（2026-09-01 追加、§20）。

### 5.3 記事を引く経路を 1 本作る

この文書で唯一「まだ無いものを作る」と言っている部分なので、明示しておく。

保存形式は参照だけを持ち（§4.2）、表示文字列を含まない。したがって**エディタ側の NodeView は、描画のたびにタイトルを引く必要がある**（§7）。§5.2-3 の記事検索も同じものを要る。

ところが `lib/posts.ts` は drizzle を直接叩くサーバ側のモジュールで、**クライアントから到達する経路が無い**。そこで route handler を 1 本置く — `app/api/posts/search/route.ts`。`?slug=` が NodeView の引き当て、`?q=` が挿入時の検索で、同じクエリを 2 つの用途が共有するので 1 本で足りる。`app/api/drafts/route.ts` と同じく `getOptionalSession` で塞ぐ（draft のタイトルを返すため）。

これを書いていないと、実装時に「NodeView からタイトルが引けない」ところで初めて気付く形になる。**先に作らない場合の縮退も決めておく: 経路が無いうちは NodeView はパスだけを表示する**（カードの形はしているがタイトルが空）。公開側は §6 の `resolveCard` があるので影響を受けない。

### 5.4 カードを置けない場所は、ジェスチャとスライスの両方で塞ぐ

§5.2-1 の「文中には入らない」を実際に守るのは 2 つの別の機構であり、**片方だけでは半分しか塞がらない**。

- **ジェスチャ**: スラッシュメニューの行に `available` 述語を付ける（`slash-command.ts`。既存の 5 行すべてが持っている形で、`hasAnyItem` がトリガーごと止める）。`setLinkCard` が `canPlaceAfterCaret`（`code-block-extension.ts` から export。コードブロックの行と同じ述語）を訊くので、テーブルのセル（`paragraph+`）とアコーディオンのタイトル（`text*`）では行が出ない。
- **スライス**: ペーストとドロップは `available` を一度も通らない。**ここに新しいガードは要らなかった**（2026-08-12 実測、`link-card-placement.test.ts`）。

**既存の 2 つのガードが既に答えている。** `titleAcceptsSlice`（`details-slice-guard.ts`）も `carriesNonParagraphBlock`（`table-cell-rules.ts`）も、拒むノード型を列挙するのではなく「その行き先が何を受け入れるか」として書かれている — 前者は「後から足されたブロックノードを名指しせずに覆うため」とコメントに明記している。カードはまさにその後から足されたブロックノードなので、書いた側の意図通りに覆われた。

**そしてここが脚注との分かれ目である。** 脚注の参照は **inline** atom で、`titleAcceptsSlice` は inline を意図的に通す（その質問は `accordion-requirements.md` §6.5 が持っている）。だから脚注は 2026-08-08 に自前の `handlePaste` を要した。カードは **block** atom なので、同じ線の覆われている側に落ちる。**カードを inline に変えるなら、この判断ごと見直すことになる** — `link-card-placement.test.ts` がそのとき赤になる。

この節を書いているのは、この repo が同じ穴を 2 度踏んでいるためである（脚注 × アコーディオン 2026-08-08、脚注 × codeBlock 2026-08-09）。どちらも「2 つの機能が互いについて一度も訊かれていなかった」形で出た。訊いた結果が「既に覆われていた」でも、訊いたこと自体は記録に値する。

## 6. 決定③ — 公開側の解決は「注入する」

`renderMdxToHtml()` は現在純粋で、`server-only` であり、公開ページとエディタのプレビューが共有し、`lib/render.test.ts` が直接呼んでいる。カードがタイトルを `posts` から引くと、このパイプラインが DB 依存になる。

**採る形**: 解決関数を引数で渡す。

```ts
renderMdxToHtml(source, { resolveCard });
```

`lib/render.ts` は DB を import しない。テストはスタブを渡せる。これを記録しているのは、あとから来た者が `getPostBySlug` をパイプラインに直接 import するのが自然に見えるからで、そうなってからでは戻しにくいためである。

解決は rehype 側の 1 段で行う（`div.link-card` を見つけて中身を作る）。`rehypeSanitize` の後に置けば、生成する中身は許可リストの対象外になる — `rehypeCodeFilename` / `rehypePrettyCode` が既に取っている位置と同じ理屈である。ただしその場合でも §4.3 の `class` / `data-href` の許可は要る（sanitize を通過して rehype 段に届く必要があるため）。

### 6.1 解決できなかったカードは素のリンクに落ちる

`data-href` の行き先は 3 つである（2026-08-12 決定）:

| `data-href`                      | 出力                 |
| -------------------------------- | -------------------- |
| `/posts/<slug>` で解決できる     | カード               |
| `/posts/<slug>` だが解決できない | 素の `<a href>` 1 本 |
| それ以外                         | 何も出さない         |

**2 行目が draft の記事と未知の slug の両方を受ける。** `getPostBySlug` は draft の記事に `null` を返すので（`lib/posts.ts`）、解決側からこの 2 つは同じ分岐に見える。素のリンクに落とすのは、形が `/posts/<slug>` である以上それが同一オリジンの相対パスであって §4.4 のプロトコル問題が起きないからで、読者には壊れて見えず、著者は公開後に自分で気付ける。

3 行目が §4.4 の穴を塞ぐ行である。形が妥当でないものは `<a href>` を一度も生まないので、`javascript:` はリンクにならない。

## 7. エディタでの見え方とバブルとの関係

**カードはエディタでも NodeView としてカードに見える。** WYSIWYG のエディタでカードだけが見えないのは編集モデルの後退であり、`link-requirements.md` §3 が「エディタと公開側のズレを開かない」を理由に `autolink: false` を却下したのと同じ判断である。

バブルとの関係は、この文書が答える義務のある項目である（カードの仕様が決まらないと答えが存在しないため）:

1. **カードの中にキャレットは入らない**（atom として扱う）。したがって `isActive('link')` は真にならず、**バブルは出ない**。バブル側の変更は不要である。
2. カードの編集（差し替え・カード解除）はカード自身の NodeView 上の操作とする。バブルに寄せると、出す条件が「リンクの中」でなくなり `shouldShow` が 2 つの意味を持つことになる。
3. **「カードをテキストリンクに戻す」を用意する。** これが無いと、一度カードにした行を元に戻す手段が無くなる。

### 7.1 操作ボタンはカード上端の固定帯に置く（2026-08-12 追記）

**決定**: NodeView の 2 状態は同じ高さの帯を先頭に持ち、そこに検索ボックス（未解決）または「変更」「リンクに戻す」（解決済み）を置く。帯は `.link-card-head`、高さは `min-height` で固定する。

**理由**: 解決済みのカードは 3 行、ピッカーは検索ボックス＋結果リストで、ピッカーのほうが高い。カードの末尾に置いたものは、解決した瞬間に結果行が占めていた帯へせり上がる。初版がこの形で、ボタンは 1 行目の結果行の 3px 以内に出ていた。記事を選んだ直後の 2 回目のクリックが「変更」（行の左端 47px）か「リンクに戻す」（その右 92px）に当たり、作ったばかりのカードが未解決に戻るか、テキストリンクに落ちる。ピッカー側でこの帯を占めているのは検索ボックスで、そこへの誤クリックは文書を変えない。

**機構**: `renderCard` と `renderPicker` が同じ `head()` を先頭に置く。ボタンを末尾に戻すと `editor-link-card.spec.ts` の 4c が赤になる。`setHref` の 1 フレーム遅延も入れてあるが、**これは修正ではない** — 帯を戻して遅延だけを残すと 250ms 後の 2 発目は依然としてカードを壊す（両方向とも実測）。遅延が止められるのは同一フレーム内の 2 発目だけで、これは人間の操作では起きず、Playwright の `dblclick()` では起きる。spec が 2 回のクリックを離しているのはそのためである。

この節は実使用で壊れた 1 件から書いている。`data/blog.db-wal` に `data-href="/posts/…"` → `data-href=""` → `[タイトル](/posts/…)` が 1 回の autosave 窓の中に残っており、そこから再現した。既存の 12 spec が全部緑のまま通っていたのは、どれも 1 回しかクリックせず、しかも Playwright の既定クリック位置が行の水平中央 — ボタンが唯一届かない場所 — だったためである。

### 7.2 カードはブロックドラッグハンドルの対象である（2026-08-14 追記）

**決定**: `block-drag-handle.ts` の `DRAGGABLE_TYPES` に `linkCard` を入れる。カードは他の 6 種と同じく左のガターにハンドルを持ち、同じ操作で並べ替えられる。

**理由**: これは判断の記録ではなく抜けの補修である。初版がこの許可リストに触れていないのは意図ではない — 根拠は 3 つある。(a) `image` も atom の block で `draggable: true` だが許可リストに入っており、「atom だから要らない」では説明が付かない。(b) `unsetLinkCard` の `at` 引数のコメントが「ハンドルで掴んだカード（NodeSelection）も解除できるように」と、存在しない経路を前提に書かれていた。(c) 本書に検討や却下の記録が無い（アコーディオンは `docs/accordion-requirements.md` §6.2 の表で明示的に追加している）。

**実測（2026-08-14）**: ハンドルが無くてもカードは動いていた。カードを直接掴むネイティブドラッグで `doc(linkCard, paragraph("後の段落"))` → `doc(paragraph("後の段落"), linkCard, paragraph)` になり、`data-href` は保たれ `pageerror` も無い。`draggable: true` に対して prosemirror-view が `dom.draggable = true` を立てるのは NodeView の `dom` にも及ぶためである。**したがって補修しているのは操作の可否ではなく、他のブロックと揃った掴みどころの有無である。**

**現在、選択が NodeSelection であるかぎり本体を直接掴むネイティブドラッグは型・深さを問わず拒否する（2026-08-22 導入、2026-08-23 に対象を全 NodeSelection へ拡大）。** `block-drag-handle.ts` の `handleDOMEvents.dragstart` は `selection instanceof NodeSelection` だけを条件に `preventDefault` で取り消す。トップレベルの `DRAGGABLE_TYPES` ブロック（カード含む）は同じ押下をこのプラグイン自身のドラッグとして続ける（`handleDOMEvents.mousedown`）ので、その範囲では操作は失われない。**理由**: 青い枠（NodeSelection）が出た状態でブロック本体を掴むと、その瞬間にエディタが固まる報告が実使用から上がった — キーもクリックも Escape も一切効かず、`view.dragging` が立ったまま（`drop` も `dragend` も `view.dom` に届いていない）。合成入力は Chrome の OS ドラッグループに入れないため（`e2e/native-drag.ts`）何がそこで止めているかは未解明で、経路ごと閉じている。当初は報告どおりトップレベルの `DRAGGABLE_TYPES` に絞ったが、この機構自体は型もトップレベルかどうかも見ていない — Ctrl/Cmd+クリック（prosemirror-view 自身の `selectNodeModifier`）はどの selectable ノードもNodeSelection化でき、atom は plain クリック一つで同じ状態になる（引用の中のカードを含む）。実測（2026-08-23）: 引用に入れたカードを 1 回クリックしただけで `draggable="true"` になり、旧スコープでは `dragstart` は無防備だった。上の 2026-08-14 の実測は当時の事実として残す — ネイティブ経路が動いていたこと自体が、この補修を「掴みどころの追加」と位置づける根拠だからである。

**機構**: 許可リストの 1 行だけ。ハンドルは widget decoration なので NodeView 側には何も足さない。対象は文書の直接の子だけなので、引用やリスト項目の中のカードにハンドルは出ない（他の 6 種と同じ範囲であり、`block-drag-handle.ts` の `decorations` が `state.doc.forEach` で走ることの帰結である）。落とし先は `findBoundary` が返すトップレベルの隙間に限られ、この経路は `handleDrop` を通らないので、§5.4 が塞いでいるセルとタイトルへの新しい入口は増えない（トップレベルのカードを直接掴むネイティブドラッグは 2026-08-22 に閉じ、引用やリスト項目の中のカード — ハンドルを持たないもの — も 2026-08-23 に同じ `dragstart` ガードで閉じた。代わりのドラッグ手段は無い — 元々ハンドルもリオーダー手段も持たないので、押しても単に何も起きなくなるだけである。実測 2026-08-23：`doc(blockquote(linkCard))` でカードをクリックして得た NodeSelection への `dragstart` は取り消される）。併せて、種類を数え上げていたコメント 2 か所（`block-drag-handle.ts` と `app/globals.css`）を許可リストの現状に合わせた。どちらも `details` を足したときから 5 種のままだった。

### 7.3 カードの削除は上流の atom の規則のままにする（2026-08-14 追記）

**決定**: 隣の段落の端で Backspace（または Delete）を 1 回押すとカードは消える。この挙動は変えない。代わりに担保するのは戻り道で、**undo は参照ごとカードを戻す**。

**機構**: `prosemirror-commands` の `joinBackward` に atom を丸ごと消す分岐があり（dist の `// If the node before is an atom, delete it`、条件は `before.isAtom && $cut.depth == $cursor.depth - 1`）、`joinForward` に対の分岐がある（`after.isAtom`）。TipTap の Backspace の連鎖は `undoInputRule → deleteSelection → joinBackward → selectNodeBackward` で、`joinBackward` が true を返すため「まず選択し 2 回目で消す」段（`selectNodeBackward`）には落ちない。このリポジトリはカードに Backspace を割り当てていないので、既定がそのまま出ている。

**理由**: 同じ atom の block である `image` と同一であり、カードだけ例外を作る側にコストがある。§7.1 の事故は参照が黙って壊れる形だったが、こちらはカードそのものが消えるので著者に見える。危ないのは戻したときに参照が失われている場合だけで、そこは基準 4e が測る。

なお 4e が測るのは編集セッション内の undo であって、保存の耐久性ではない。削除と undo の間に autosave が挟まれば保存済みの本文からは参照が消えている — これはカードに限らずどのブロックでも同じで、この文書の対象外である。

### 7.4 参照先を開く口を帯に置く（2026-08-21 決定・実装）

**決定**: 解決済みカードの帯を `開く / 変更 / リンクに戻す` の 3 つにする。「開く」は `window.open(href, '_blank', 'noopener,noreferrer')` — バブルの href 行と同じ呼び出しである。安全な操作から破壊的な操作へ、という並び順にした。

**理由**: **カードから参照先を開く手段が無かった。** `link-requirements.md` §3 が `openOnClick: false` でエディタから開く操作を取り上げ、テキストリンクには §5.5 のバブルがそれを返したが、カードには返っていない。実際に踏む手順は「リンクに戻す」でカードを壊し、テキストリンクにキャレットを置き、バブルの href 行を押し、カードを作り直す、である。「変更」は空のピッカーを開くだけなので URL すら見えない（外部カードが最下行に出すホストと、内部カードのタイトルが手がかりの全部である）。

**タイトルや画像のクリックで開く形は採らない。** 報告された不便はこの形で解けるが、代金が 4 つある。

1. **カードは atom で、本体のクリックはノード選択である** — 削除とドラッグの起点がそれである（§7.2・§7.3）。いちばん自然な選択対象を遷移に使うと、編集面でクリックの意味が読めなくなる。`link-requirements.md` §3 がテキストリンクから取り除いたのと同じ種類の驚きを、カードに入れ直すことになる。
2. **画像は当たり判定が大きい。** 編集中の誤爆が日常的に起きる位置にある。
3. **画像は `alt=''` である**（§14.4 の理由 — タイトルが同じ場所にある）。押せるようにすると名前が要り、タイトルと二重に読み上げられる。
4. 公開カードは全体が 1 つの `<a>` だが、エディタのカードは帯を内側に持つので**同じ形にはできない**。タイトルだけ押せる形は WYSIWYG を揃えず、どこが押せるかを示すものも無くなる。

**§5.5.6 の「表示が開くボタンを兼ねる」はここへは移らない。** あちらはバブルの表示が href そのものだったからで、カードのタイトルは href ではない。

**機構**: `renderCard` が `head()` に足す 3 つ目の `button()`。別タブで開くのは公開カードと揃えたためで、そちらの規則は `link-requirements.md` §7.2 が同日に決めている。基準 4i。

**帯の見た目は幅で 2 通りになる（2026-08-21、同日の追加）。**

**決定**: 広いとき（>30rem）は今までどおりラベルで、**「リンクに戻す」だけが赤い**。狭いとき（≤30rem）は 3 つともアイコンになる。

**赤の出所は既にある。** `ToolbarButton` の `destructive`（red-600 / dark は red-400）で、テーブルの「削除」と、**バブルの 解除 が同じ赤を着ている** — カードの「リンクに戻す」はその 解除 と同じ操作の別 surface なので、2 面が揃う。**枠は塗らない。** `LinkBubble.tsx` が塗りつぶしを一度試して戻しており、理由は「ラベルに色を付けるほうが、他のクロームと同じ重さで同じことを言える」である。ここでも同じ判断を採る。等間隔に並んだ 3 つのうち**カードを壊すものだけが違って見える**ことが目的で、右端へ離す案（プロトタイプで比較）はカードが 830px 幅あるため遠すぎて採らなかった。

**幅の区切りは `30rem`**、`app/globals.css` の既存のメディアクエリの中である。これはこのスタイルシート唯一の幅ブレークポイントで、カードの高さと説明文の出し分け（§16.1）が既にそこにある。カードの中に「狭い」の定義を 2 つ作らない。

**アイコンは常に DOM にあり、ラベルも常に DOM にある。** 出し分けは CSS だけがやる。**ラベルは `display: none` ではなく視覚的に隠す**（`clip` 方式）— ラベルはボタンのアクセシブル名そのものなので、木から外すと狭い幅で名前の無いボタンが 3 つ並び、`getByRole('button', { name: … })` で引いているこの file の spec も道連れになる。基準 4j がそこを測る（スクリーンショットでは区別が付かない差である）。

**アイコンの形は React の `PencilIcon` / `UnlinkIcon` と共有する。** NodeView は素の DOM を組むので JSX を import できず、パスを写すと 2 つに分かれてずれる — `UnlinkIcon` の形は 16px での見え方を測って調整したものである。`components/editor/svg/icon-shapes.ts` が形状データと DOM 側の組み立てを持ち、React 側は `IconSvg` がそれを描く。「開く」のアイコン（箱から出る矢印）はここで新しく足した 1 つで、React 側にはまだ使い手がいない。

### 7.4.1 「変更」はまだ何も書き換えない（2026-09-04 決定・実装）

**決定**: 「変更」はもう `setHref('')` を呼ばない。NodeView に持たせたローカルな真偽値（`editing`）を立てて再描画するだけで、href 属性には触れない。ピッカーには「変更」から来たときだけ「キャンセル」ボタンが付き、Escape とカード外クリックも含めた 3 つの出口すべてが、同じ真偽値を戻して再描画するだけである。href が実際に書き換わるのは、記事か URL を選んだ瞬間だけになった。

**理由**: 「変更」はカードを検索ピッカーの見た目に切り替えるだけの操作のはずが、実装は `setHref('')` という独立した編集トランザクションだった。ピッカー側には「やめる」に相当する手段が無く、Escape はフォーカスをエディタへ戻すだけで元のカードを組み立て直さない。押し間違えた著者の戻し先は Ctrl+Z しか無く、記事や URL まで選んでしまっていれば 2 回正確に押す必要があった。

**キャンセルにアイコン単独の ✕ は使わない**（`components/editor/svg/icon-shapes.ts` の `BACK_SHAPES` のコメントに同じ理由がある）。`link-requirements.md` のバブル編集欄が一度、✕ 付きの「取り消し」を試して外した前例があり、隣の「解除」と見分けが付かなかったことが理由だった。ピッカーの帯に「解除」は同時に出ていないが、この帯の他のボタンは全部アイコンとラベルの両方を常に持つ（§7.4）ので、そこに合わせてラベル付きの「キャンセル」にした。

**機構**: `addNodeView()` の `render` が `editing` を読み、真なら href の有無に関わらずピッカーを描く。`renderCard` の「変更」は `setHref` の代わりに `editing = true` を立てて `render` を呼ぶだけになった。`renderPicker` は新しい第 6 引数 `onCancel`（変更から来たときだけ非 null）を取り、非 null なら帯に「キャンセル」を足し、Escape のハンドラからも呼ぶ。カード外への mousedown は NodeView の生成時に一度だけ `document` へ登録し、`editing` が真の間だけ `dom.contains` の外を見て同じく戻す — NodeView の `destroy` で外す。`setHref` 自身も編集の終わりを兼ねて `editing` を戻す。基準 4m。

**Escape がスクロールバーを飛ばした（実測 2026-09-04、修正）。** キャンセル後にエディタへフォーカスを戻す口は、当初 `editor.view.dom.focus()` の生呼びだった。実測すると、「変更」を押した瞬間の ProseMirror の選択は依然どこか別の場所にある — カードの帯は `contenteditable="false"` の島なので、そこにあるボタンのクリックはネイティブのキャレットを一切置かない。したがって `.focus()` はカードではなく、著者が最後にキャレットを置いた場所（多くの場合、文書の先頭に近いどこか）をスクロールで暴く。`@tiptap/core` の `focus` コマンド自身が同じ症状を Safari 向けに `preventScroll` で回避しているのが `node_modules/@tiptap/core/src/commands/focus.ts` に残っている——「選択をセットする前に `focus` を呼ぶとエディタの先頭へスクロールしてしまう」。**修正**: `cancelEditAndFocus`（`onCancel` の実体）が `render` の直後に `editor.chain().setNodeSelection(pos).focus().run()` を呼び、キャンセル後のカード自身へ選択を明示的に移してからフォーカスする。カード外クリックの `onOutsidePointerDown` はこれを呼ばない——クリックが著者をエディタの外（タイトル欄など）へ連れて行った直後にフォーカスを奪い返すのは、その操作と衝突する。基準 4m がスクロール量を測る。

### 7.5 ゴーストはカードの顔を運び、操作は運ばない（実測 2026-08-25、修正）

**決定**: ブロックドラッグのゴーストからカードの操作を落とす（`stripCardControls`、`components/editor/block-drag-handle.ts`）。運ぶのはタイトル・ホスト・画像 — 公開カードが見せているものと同じである。箱には幅を与える（`.block-drag-preview:has(.link-card)`、`app/globals.css`）。

**理由**: **ゴーストの中でいちばん目立つものが、押せないボタンであってはならない。** `embed-requirements.md` §10.10 が埋め込みのゴーストについて同じ判断を先に下しており、カード側に届いていなかっただけである。

実測（修正前）はその言い方より悪かった。ゴーストの箱は中身で幅が決まるので、§7.1 の帯がそこに収まらない。内部カードで測ると、**271x252 のゴーストのうち 112x141 が帯**で、3 つのボタンは縦に積まれ、「リンクに戻す」は 1 文字ずつ改行されていた。どのカードを運んでいるかを言える唯一のもの — タイトル — は上から 186px の位置にあった。**外部カードでは帯だけで `max-height: 300px` を超え**、`overflow: hidden` がタイトルもホストも切り落としたので、見えているのは 3 つの押せないボタンだけになった。ゴーストはカードの絵ではなく、**カードが崩れた姿**を運んでいた。

**機構**: 落とすのは `.link-card-head`（§7.1 の帯 — 解決済みカードの 3 ボタンとピッカーの検索欄が同じ帯にいるので、1 つ消せば両方消える）と `.link-card-results`（ピッカーの押せる行）である。2026-09-01 に検索欄の説明文が 3 つ目として加わり、2026-09-02 に説明文ごと消えた（`embed-requirements.md` §24.1）— **押せないものもここを通る**ことは、そのとき一度実測している（消し忘れるとゴーストの本文がその 1 文だけになった）。

**幅は書いて与える。** 帯が実質の幅出しをしていたので、外すだけだと 114px の縦長の破片になる — §10.10 が 92px で踏んだのと同じ罠である。ブロック自身の幅から導く形は採らない。カードは本文カラム幅（実測 768px）なので「本当の幅」は常に 480px の上限に張り付き、その幅で測るとタイトルが 1 行を独占して間延びして見える。**400px** は 320・480 と 3 つ並べて選んだ（320 はタイトルが画像に押される）。上の `max-width` が残るので、窓が狭いときはそちらが勝つ。

**箱は本文用の寸法を持っている。** カードの `margin: 1.25em 0` は前後の段落との間隔で、`min-height: 8.5rem` は編集面のカードどうしを揃える床である（§16.4）。**カーソルの下に浮いている箱には、上も下も隣も無い。** 実測（2026-08-25）で 192px の内訳は、余白 40px・床 136px・プレビュー自身の padding 16px だった。余白は丸ごと落とす。床は 0 にはせず **4.5rem** に下げる — 0 にするとタイトルしか無いカードが 72px になり、絵が 54px の帯に切り取られて何も写らなくなる。4.5rem なら絵に 70px 残り、しかも床が効くのはその一番低いカードだけで、ホスト行を持つカードは自前の高さの方が高い。結果は **192px → 88px**（外部カードは 97px、自分の 2 行で決まる）。

**ピッカー状態には運ぶ顔が無い。** タイトルも画像も、返ってきた答えも無い。空の枠だけを出すのは §10.10 が名指しした方の失敗なので、タイトルの位置に「リンク先未設定のカード」の 1 行を置く — 埋め込みのトークンが名前だけを運ぶのと同じ理由で、**見せられないものも名指しはする**。状態の判別は `href` 属性ではなく `.link-card-title` の有無で行う（`renderCard` は必ずこの span を作るので、無いことがピッカーであることを意味する）。ゴーストが参照を読む理由は無い。

**この節はカードだけを直している。** コードブロックのゴーストも同じ性質のクローム（ファイル名の `<input>` と言語の `<select>`）を運んでいるが、測っていないし直していない（§10）。

### 7.6 動く行き先があるとき、ドラッグ元は「切り取られた姿」になる（2026-08-25 決定・実装）

**決定**: ドロップ位置の線が出ている間、ドラッグ元のブロックを**切り取られた跡として描く** — 薄くして破線で囲み、選択のリングは覆って隠す（`markCut`・`.block-drag-cut`）。線と同じ答えに紐付いているので、**2 つは必ず一緒に出て一緒に消える**。落としても何も動かない区間（`pos === current.to`）では、どちらも出ない。

**理由**: 並べ替えは「ここから抜けて、そこに入る」という 1 つの操作で、**跡と線はその 2 つの端**である。片方だけでは半分しか言っていない。

**逆に置いて、読み違えられた（2026-08-25、同日に反転）。** 最初の版はこの印を**動かない区間の側**に出し、「ここに戻ってくるスロット」の意味を持たせていた。著者は一目で「切り取りのプレビュー」と読んだ。**その読みの方が正しい** — 薄くして破線で囲んだ箱はどのツールでも「ここは今そこに無い」を意味する記号なので、ブロックが出ていくときに出すべきものである。描画は 1 ピクセルも変えていない。変えたのはどちらの分岐で出すかだけである。

**動かない区間には印を置かない。** そこは元々フィードバックが 1 つも無く、しかも高さは**掴んだブロックの高さ + 次のブロックの半分**なので、実測（2026-08-25）で引用ブロック（69px）が 100px、画像付きカード（136px）が 160px — 動かすのが大変な背の高いブロックほど無言の距離が伸びる。それでもここを埋めないのは、**「落としても何も起きない」の正しい絵は「何も起きていない絵」＝素のブロックだから**である。この区間の無言は、線と跡が同時に現れる瞬間との対比で読めるようになる。

**却下: 元の位置に破線を引く案（2026-08-25、ブラウザで並べて比較）。** カード下端にグレーの破線と「ここに戻ります」のラベルを出す形で、本物のインジケータと視覚言語が揃うのが利点だった。**採らない理由は、揃いすぎることである。** 線はこのエディタで「ここに挿入する」を意味する記号で、同じ記号を同じ場所に置いて「挿入しない」を言わせると、区別するものが日本語のラベルだけになる。しかも線は次のブロックのすぐ上に出るので「次のブロックの前に挿入」と読めてしまう。

**機構は `position: fixed` の箱であって、ブロックに付けるクラスではない。** クラスで実装して測ったところ**持たなかった**（2026-08-25）: `decorations()` は状態が変わるたびに新しい DecorationSet を作り、その widget は `key` を持たないので ProseMirror は古いものと突き合わせられず、周辺の desc ごと作り直す。**次のマウス移動で `view.nodeDOM(from)` が別の `<blockquote>` を返し**、クラスは外れた要素に残っていた。ドラッグ中にトランザクションは自然に 1 つ来る（掴んだときの NodeSelection がテキスト選択に戻る）ので、これは例外ではなく通常経路である。インジケータとゴーストが同じ形（body 直下の `fixed`）なのも同じ理由で、この file が自分で持つクロームにしてある。

箱はブロックの矩形を `CUT_INFLATE`（4px）だけ外へ広げて描く。選択リングが `outline: 2px` を `outline-offset: 2px` で描いていて外側 4px まで届くので、**覆ってしまわないと薄くなったブロックの外に青い枠だけが残る**。箱側の破線は同じ量だけ内側へ戻してブロックの実際の縁に載せている。薄くするのは `::before` の方で、破線まで一緒に褪せないようにしてある。

**ブロックの高さは触らない。** ドラッグ元の見た目を変える案は一度戻されているが（`applyMove` のコメント）、あれは高さを 0 に潰す案で、追えなかったのは下の内容が動く reflow だった。ここはレイアウトを一切動かさない。

## 8. 延期 — 外部 URL のカード（2026-08-18 に解除、§14）

**この延期は 2026-08-18 に解けた。外部カードの要件と設計は §14 にある。** 以下は 2026-08-12 に延期を決めたときの見積もりで、§14 が答える入力として残してある。

### 8.1 理由

内部カードは `posts` に `title` と `description` が揃っているので DB クエリ 1 本で完成する。外部 URL のカードは以下が全部要る:

- 対象ページの HTML 取得と `og:` タグの解析
- 取得結果のキャッシュ（置き場所と失効の設計）
- **SSRF 対策**。任意の URL をサーバから取りに行く機能なので、プライベート IP・`localhost`・リダイレクト追跡の扱いを決める必要がある。このサイトは `https://blog.example.ts.net` で公開されている
- 失敗時の表示（404・タイムアウト・OGP を持たないページ・bot を拒むサイト）

**見た目を共有するだけの別プロジェクトである** という見積もりで延期した（`link-requirements.md` §0 が②を延期したのと同じ判断）。需要が測れていない状況は §0 のまま変わっていないが、4 つのうち取得と SSRF は §5.5.10 が別の用件で払い済みであり、残る 2 つは §14.1 が「読者のリクエストでは取得しない」形にすることで消える。

### 8.2 サムネイルは入った（2026-08-15）

`posts.thumbnail` が入り、カードは画像を持つ。値は著者が選んだ `/uploads/…` のパスで、未設定なら本文の最初の画像が使われる（`lib/thumbnail.ts` の `resolveThumbnail`）。記事一覧・このカード・`og:image` の 3 面が同じ 1 本の関数を読む。**本文にも画像が無ければ、カードだけはサイトのマークを出す**（2026-08-22、§17。一覧と `og:image` は変わらない）。

この節はもともと「列が無いので画像付きカードは作れない」と書いてあった。作れないという判断ではなく、前提が無いという報告だったので、前提のほうを作った。**外部 URL のカードが 2026-08-18 まで延期だったのは §8.1 の理由であって、画像の有無ではない。** §14.4 は逆に、外部カードには画像を出さないと決めている — 出所が第三者だからで、これも画像の有無の話ではない。

## 12. 公開カードに日付は出さない（2026-08-15 追記）

公開ページのカードは**タイトルと説明、および対象記事の画像**である。文字は左の列に積み、画像はその右に固定サイズで置く（`link-card-text` と `link-card-image`）。**内部カードは必ず画像を持つ** — 記事が画像を持たなければサイトのマークが入る（2026-08-22、§17）。空の枠を出さないという規則はそのままで、当てはまるのは og:image を持たない外部カードだけである。

日付はここに無い。3 行目に出していたが 2026-08-15 に落とし、同じ日にその場所を画像が取った。

**理由**: リンクカードの最下段は出所を出す場所で（どのサイトか、誰が書いたか）、クリックする価値の判断はそこに乗る。内部カードの行き先は常にこのブログなので、その枠には言うことが無い。日付は `posts` に列があったから座っていただけで、判断の結果ではなかった。加えて、遷移先を開けば同じ日付が見えるうえ、古い記事へのカードで日付が先に目に入ると、カードが促したいクリックを自分で抑える方向に効く。

説明が空の記事を指すと、カードは 1 行のタイトルと画像になる（`cardElement` は空文字の行を出さない）。これは説明を入れて直すことであって、日付を代打に置く理由にはしない。

画像は `resolveThumbnail`（`lib/thumbnail.ts`）が答える。カードは列の値を直接読まない — 記事一覧と `og:image` も同じ関数を読んでおり、3 面が別々に決めるとカードと一覧で違う絵が出る。**カードは `thumbnail` を再検証しない。** `data-href` は著者が本文に書いた値で sanitize のプロトコル検査を抜けて来るが、画像は注入された resolver が `resolveThumbnail` を通して作るので、出所が違う（`lib/rehype-link-card.ts` の `cardElement` にも書いてある）。

**`.link-card-meta` は生きている。** エディタの NodeView がこの class で下書き・不明の参照を知らせるので（`link-card-extension.ts` の `renderCard`。href を出す枠だったのは 2026-08-18 まで — §13.1）、CSS 側は `.prose .link-card-view .link-card-meta` にスコープを絞ってある。公開カードに出ないことは `render.test.ts` と `public-link-card.spec.ts` の両方が名指しで測る — class が残っている以上、消えたことは仮定できない。

外部カードでは、この枠にドメイン名が入る。日付ではない（§14.4）。

- **外部 URL のカードを内部カードと同時に作る** — §8.1。取得・キャッシュ・SSRF・失敗表示が全部付いてくる別プロジェクトであるため。同時には作らなかった。単体の設計は 2026-08-18 の §14 である。
- **`data-href` を sanitize の許可リストに任せる** — §4.4。`className` と違って値の検査が無く、解決段は sanitize の後ろに居るのでプロトコル検査も通らない。検証は `resolveCard` の責務にした。
- **解決できなかったカードをノードごと落とす** — §6.1。最も安全だが、著者から見ると本文が黙って消える。形が妥当なら素のリンクに落とすほうが、読者にも著者にも情報が残る。
- **`draft` を指すカードを「未公開です」と表示する** — §6.1。読者に内部事情が漏れる。解決側から draft と未知 slug は区別できないので、そもそも正確に出せない。

**このリストにサムネイル付きカードは無い。却下したことは一度も無く、当時は `posts` に列が無くて選択肢に上がらなかっただけである。**列は 2026-08-15 に入り、カードは画像を持つ（§8.2・§12）。エディタ側は 2026-08-18（§13）。

## 13. エディタのカードも画像を出す（2026-08-18 追記）

エディタの NodeView は、公開カードと同じ位置・同じ大きさで対象記事の画像を出す。**文字の列が左、画像はその右に固定サイズ** — `.link-card-view` が `display: flex` の行になり、画像は公開カードと同じ `.prose .link-card-image`（`object-fit: cover`。寸法は §15）が受け持つ。**画像を持たない記事のカードはサイトのマークを出す**（2026-08-22、§17）。読者が見るものと同じであることがこの節の主張なので、公開側がマークを出すならエディタも出す。

**理由**: 編集中のカードは `<div>` なので、ホバーしても行き先がどこにも出ない（同じ日に下段のパスも落ちたので、いまカードが指す先を言うのはタイトルと画像だけである — §13.1）。狙いは取り違えの防止ではない — `resolveThumbnail` が答えを返す記事は実測（2026-08-18）で 3 件中 1 件で、判別が要る場面（同じタイトルの下書きが 2 本ある）でこそ画像は空になりやすい。狙いは、編集中に見えるものが読者の見るものと同じであること。§7 が NodeView を placeholder ではなく実物のカードにしたのと同じ理由で、その主張から画像だけが抜けていた。

左右は右で決まっている。画像の有無が混在するので（内部カードが必ず持つようになった今も、外部カードは持たないことがある — §17）、左に置くとタイトルの開始位置が画像とすき間のぶんだけカードごとに動く。右なら、画像を持たないカードは flex の子が 1 つになり、行になる前とまったく同じに収まる。

**機構**: パスは `/api/posts/search` が `resolveThumbnail` を通して返す（`PostSearchResult.thumbnail`。`null` は「画像が無い」という正常な答えで、`slug` のように `''` に潰さない）。エディタが本文から自分で拾わないのは、記事一覧・公開カード・`og:image` とこのカードの 4 面が同じ 1 本の関数を読むためである（§8.2）。これは「検索が記事を読む手段になってはいけない」（`PostSearchResult` の宣言）に対する唯一の例外で、渡るのは解決済みの `/uploads/…` パス 1 本、route は管理者のみ（session が無ければ 401）、返すのは resolver の答えであって読んだ本文ではない。

**キャッシュは答え全体を持つ。** `postCache` は以前タイトルだけを持っており、`renderCard` は「キャッシュにあれば fetch しない」ので、答えから導くものは最初の描画にしか現れなかった。未公開の注記（§5.2-4）が既にその状態で、画像を足せば同じ穴に落ちる。描画は `draw(post)` 1 本にまとめ、キャッシュ命中と fetch の到着が同じカードを描く。

遅れて届いた答えは捨てる。`renderCard` の `.then()` は以前 `title` と `meta` にしか書かなかったので、`body.replaceChildren()` で外れた要素に書くだけで無害だった。`setImage` は NodeView の `dom` に触るため、`変更` を押してピッカーに戻ったカードに古い問い合わせの答えが届くと、検索欄の横に画像が付く。`title.isConnected` で降りる（構築中も false だが、ProseMirror が `dom` を挿すのは同じ同期ブロックの後なので、遅れて来るこの経路だけが該当する）。

画像はドラッグの的にはならない。`<img>` は既定でドラッグ可能だが、ProseMirror の `dragstart` が先に取るので、サムネイルを掴んで引くとカードごと動く（実測 2026-08-18: `doc(paragraph, linkCard, paragraph)` → `doc(linkCard, paragraph, paragraph)`、画像ノードは増えず pageerror も無し）。`draggable = false` は要らない。トップレベルのカードでは 2026-08-22 以降その `dragstart` 自体が取り消され、押下はハンドルと同じドラッグになる（§7.2）ので、サムネイルを掴んだときの行き先も同じである。この 1 件は基準にしていない — 上流の挙動であり、崩れたときに測るべきなのは画像ではなくカードのドラッグそのもの（基準 4d）だからである。

**この穴は最初の描画からは見えないので、基準 4f はいったん別の文書を読み込んでからカードを読み直す。** 同じ内容を読み直すだけでは ProseMirror が NodeView を作り直さず、古い DOM がそのまま残って何も測らない（実測 2026-08-18: キャッシュ命中で画像を描けないコードに対して、その形の assertion は緑のままだった。文書を空けてから読み直す形にすると赤になる）。箱の寸法も測っている — 公開カードのために書かれた `.prose .link-card-image` が NodeView にも届くことは、`.link-card-view` を行にした今回の変更では仮定であって前提ではない。

### 13.1 下段はパスをやめ、異常だけを言う（2026-08-18）

エディタのカードの 2 行目（`.link-card-meta`）は、**参照先について言うことがあるときだけ出る**。下書きを指していれば「未公開の記事」、route が記事を見つけられなければ「記事が見つかりません」。どちらでもなければ行そのものが無い（空の span でもない — 行の上マージンはこの要素が持っている）。

**理由**: ここには `/posts/<slug>` を出していたが、スラッグは `generateUniqueSlug` の 20 桁 hex で、人には何も言わない。カードが**どのレコードを指しているか**はタイトルと画像（§13）が答えており、パスはその 2 つが答えたあとに何も足していなかった。解決できなかったときはタイトル自身がパスに落ちる（§5.3）ので、同じ文字列が 2 行並んでもいた。

出さない代わりに、**状態は 3 つに分けた**。「まだ答えが返っていない」と「route が無いと答えた」はデータの上ではどちらも `null` だが、カードの上では別物である — 前者で「記事が見つかりません」を出すと、文書を開くたびに数十 ms のあいだ全部の参照が壊れていると言うことになる。`Lookup` が `unknown` / `found` / `missing` を持ち、404 だけが `missing`、通信の失敗や 401 は `unknown`（セッション切れは記事の不在ではない）。

取り違えの防止をここに戻すなら、入るのは日付である（`PostSearchResult.date` は既に届いていて未使用）。パスではない。§12 が公開カードから日付を落とした理由は読者についてのもので、編集画面には当てはまらない — 今回は入れていない。

基準 4g・4h が 3 状態のうち 2 つを測る（`unknown` は route を止めないと作れないので測っていない）。3 本とも、下段を href に戻す 1 箇所の変異で赤になることを確認した。

## 14. 外部 URL のカード（2026-08-18 設計・実装）

§8 の延期をここで解除する。この節は外部 URL のカードの要件と設計であり、実装より先に書いた（§0〜§13 と同じ順序）。実装で分かったことは日付を添えてその節に書き足してある — §14.5.1（自サイトの URL の扱い）と §14.8（ホスト名を出す場所）がそれである。**決めるのは 6 つ** — 取得がいつ走るか（§14.1）、保存形式（§14.2）、取得結果の置き場所（§14.3）、カードに何を出すか（§14.4。画像をどう出すかを含む）、取得器（§14.5）、入口（§14.6）。

内部カードの決定は 1 つも動かない。保存形式は §4 のまま、公開側の解決は §6 の注入のまま、置ける場所は §5.4 のままである。動くのは `data-href` が取りうる形と、`resolveCard` が引く先が 2 つになることだけである。

### 14.1 決定① — 取得は著者の操作で走る。読者のリクエストでは走らない

**これがこの節の背骨で、他の 5 つはここから落ちてくる。** 公開ページは `export const dynamic = 'force-dynamic'`（`app/posts/[slug]/page.tsx`）なので、`renderMdxToHtml` は読者のリクエストごとに走る。そこに外部ページの取得を置くと、第三者の応答時間がそのまま TTFB に乗る。実測（2026-08-18、Node の `fetch` から 10 件、いずれも初回）:

| 取得先                                   | 状態 | 時間   |
| ---------------------------------------- | ---- | ------ |
| `example.com`                            | 200  | 113ms  |
| `wikiwiki.jp`                            | 200  | 133ms  |
| `developer.mozilla.org/ja/docs/Web/HTML` | 200  | 141ms  |
| `www.npmjs.com/package/next`             | 403  | 147ms  |
| `github.com/facebook/react`              | 200  | 340ms  |
| `zenn.dev/zenn/articles/markdown-guide`  | 200  | 498ms  |
| `ja.wikipedia.org/wiki/HTML`             | 200  | 610ms  |
| `nextjs.org/docs`                        | 200  | 874ms  |
| `qiita.com/items`                        | 200  | 890ms  |
| `tiptap.dev/docs`                        | 200  | 2450ms |

`rehypeLinkCard` は見つけたカードを `Promise.all` で並行に解決するので、待ち時間は枚数に比例しない — が、いちばん遅い 1 枚が決め、上限は `TIMEOUT_MS` の 5 秒である。それは読者が待つ時間であり、失敗もそのまま読者に見える。**キャッシュが必須になるのはこの形を採ったときだけで、§8.1 が「別プロジェクト」と見積もったコストの大半はそこから出ている。**

**採る形**: 取得はエディタからの要求で走る。管理者のみ、一度に 1 件、失敗しても直せるのは著者である。これは `link-requirements.md` §5.5.10 がバブルのタイトル取得で通した論法をカードに当てたもので、あちらが「§8.1 の見積もりは公開ページのカード向けである」と書いた差をここで清算する。

**公開側は 1 本も要求を出さない。** `resolveCard` は保存済みの行を引くだけで、行が無ければ何もしない。その先は既にある — 解決できなかったカードは素のリンクに落ちる（§6.1）。したがって公開ページに、取得の失敗も、タイムアウトも、SSRF の面も増えない。

**帰結を 1 つ引き受ける**: 行が無いカードは、参照として妥当でも素のリンクとして公開される。手で `<div class="link-card" data-href="https://…">` を書いた場合がこれに当たる（`parseHTML` はこの扉を開けてある — §4 の「著者が raw HTML として貼れる」）。エディタで開けば取得が走って行ができるので、直し方は「一度開く」である。

### 14.2 決定② — 保存形式は内部カードと同じ。参照だけを持つ

```html
<div class="link-card" data-href="https://example.com/article"></div>
```

内部カードと同じノード、同じ class、同じ属性である。**新しい記法もノードも作らない。** §4.1 の試験（往復を曖昧さ無しで生き延びるか）の答えは href が絶対 URL になっても変わらないはずで、(c) が採られた理由もそのままである — **ただし絶対 URL の往復そのものは測っていない**（§14.10）。sanitize の schema も動かない — `dataHref` は既に許可されており、値の検査が無いことが §4.4 の出発点だからである。

**`CARD_HREF` は 2 つの形を持つ。** 内部は今のまま `/^\/posts\/[\w~-][\w.~-]*$/`、外部は `http:` と `https:` だけを通すスキーム許可リストで書く。**禁止したいものを並べるのではない** — この段は sanitize の後ろに居るので、ここが通した href は他の誰の検査も受けずに `<a href>` になる（§4.4）。`javascript:` を弾く述語ではなく、`http(s):` 以外を表現できない述語にする。判定は `new URL()` に解かせ、`protocol` を見る。文字列の前方一致では `java\tscript:` の類を取りこぼす。

**鍵は保存された文字列そのものである。** `?utm_source=` の有無で別の行になるが、正規化はしない — 著者が本文に書いた参照と、取得しに行った URL と、公開ページの `<a href>` が同じ 1 本の文字列であることのほうが、行の重複より安い。

#### 14.2.1 述語が追加で 2 つ拒むもの（2026-08-18、実装後の確認で見つけた）

**① 壊れた percent-escape は、例外ではなく「該当なし」にする。** `new URL()` は `https://…/posts/%zz` の `%zz` を pathname に残し、`decodeURIComponent` はそれで throw する。自オリジンの書き換え（§14.5.1）はその decode を通るので、**投げた例外は `resolveCard` から `rehypeLinkCard` の `Promise.all` に届き、カード 1 枚ではなく記事のページごと 500 にする。** 参照 1 つで本文全体が落ちる形なので、`try` で受けて `null`（＝ポストを指していない）にした。`app/api/link-title/route.ts` の `ownTitle` が同じ 1 行を持っていたので、そちらも同時に直してある。

**② 資格情報を持つ URL は参照にしない。** `https://user:pass@host/` は URL として妥当に parse され、そのままだと**取得時に相手へ送られ、公開ページの `<a href>` に読者全員が見える形で載る。** カードはページを名指すものであって、秘密を運ぶ場所ではない。`javascript:` と同じ扱い（解決段がノードごと落とす）にした。

どちらも `link-card-href.test.ts` が固定している。**2 つとも「URL として妥当なのにカードの参照としては妥当でない」形**で、§4.4 が「検証は解決側の責務」と決めた線の内側にある。

### 14.3 決定③ — 取得結果は表 1 本に持つ

`link_previews`（`lib/db/schema.ts` に追加、`db:generate` → `db:migrate` で 1 本のマイグレーション。`db:push` はこの repo には無い）。

| 列            | 型      | 意味                                   |
| ------------- | ------- | -------------------------------------- |
| `url`         | text PK | `data-href` の文字列そのもの（§14.2）  |
| `title`       | text    | 取得できたタイトル。失敗時は空         |
| `description` | text    | 同上。無いページがあるので空は正常な値 |
| `status`      | text    | `ok` / `failed`                        |
| `fetched_at`  | integer | epoch ミリ秒。TTL の判定にだけ使う     |

**`posts` に足さない。** カードは記事に属さない — 同じ URL を 3 本の記事が指せば行は 1 つで足りる。加えて `posts` は populated な DB に対して末尾への `ADD COLUMN` しか通らない（`schema.ts` の `draftContent` と `thumbnail` のコメント）。新しい表にはその制約が無い。

**プロセス内の Map にしない。** `/api/link-title` のキャッシュ（`OK_TTL_MS` / `MAX_ENTRIES` の Map）はエディタの中だけで完結するので消えても著者が待つだけだが、公開側が読む値が消えると**再起動のたびに全部のカードが素のリンクに落ちる。** 永続化は §14.1 の「読者は取得しない」を成立させる条件そのものであって、速度の話ではない。

**鮮度は TTL で、更新 UI は作らない。** NodeView は描画のたびに参照を引く（§7）ので、route は行が新しければそれを返し、古ければ取り直して書き換える。**`failed` の行の TTL は `ok` より短い** — `/api/link-title` が同じ判断をしており（`FAIL_TTL_MS` は 10 分、`OK_TTL_MS` は 6 時間）、理由も同じである。403 は速く落ちるので、長く覚えていると直った相手をいつまでも素のリンクのままにする。表は普通の編集で温まる。**手動リフレッシュ UI は §1 の非目標のまま置く** — 押す理由が著者に分かる場面が無く（表示が古いかどうかは対象ページを開かないと分からない）、押せるものを増やすと押さない場合の意味が変わる。

**引き受ける帰結**: 二度と開かれない記事のカードは、対象ページのタイトルが変わっても古いままである。リンク切れ検査を非目標に置いたのと同じ種類の割り切りで、直し方も同じ（記事を開く）。

#### 14.3.1 行は「古さ」だけでは陳腐化を表せない（2026-08-18 報告・修正）

報告は「フラグメント付きの URL（`…/markdown-guide#脚注`）をカードにすると画像が出ない」だった。**フラグメントは無関係だった。**

実測（`link_previews` の `fetched_at` と、`image` 列を足したマイグレーションの時刻を並べる）:

| 行が書かれた時刻 (UTC) | 画像 | URL                                    |
| ---------------------- | ---- | -------------------------------------- |
| 11:44                  | 無し | `…markdown-guide#脚注`                 |
| 11:55                  | 無し | `qiita.com/…#リンク`                   |
| 12:53                  | —    | **`image` 列を足したマイグレーション** |
| 13:45                  | 有り | `…markdown-guide`（フラグメント無し）  |

画像の無い 2 行はどちらも**画像を読む機能より前に書かれている**。別のフラグメント（`#インライン記法`）で新しく作れば画像は出る（実測）ので、切れ目は URL の形ではなく時刻にあった。

**機構**: `status='ok'` の行は 7 日使われる。古い版が書いた行は `image` が空のまま `ok` なので、**TTL が切れるまで直らない** — 記事を開き直しても、カードを作り直しても同じ行が返る。**これは古さでは表せない種類の陳腐化である。** 行が古いのではなく、行を書いた側が古い。

**決定: 行に版を持たせる。** `PREVIEW_VERSION`（`lib/link-previews.ts`）を列に書き、**版が違う行は TTL に関わらず使わない**。読む内容を変えたら上げる、が規則である。既にある行は版 0 になるので、この変更自体が上の 2 行を解放した（実測: 報告された `#脚注` の URL でカードを作り直すと 1200 × 630 の画像が出る）。

**併せて `partial` を足した。** 「ページが画像を持っていない」と「持っていたのに引けなかった」は同じ空文字だが、待つべき時間が違う。前者は答えが出ている（7 日）、後者は相手側の一時的な不調でありうる（30 分）。`status` が 3 値になり、`readLinkPreview` は `partial` もカードとして出す — 題も説明もあるのに、来ないかもしれない絵のために素のリンクへ落とす理由が無い。

**公開側は版が古くても出す。** 読者のリクエストで取り直すことはしない（§14.1）ので、落とせば絵ではなくカードごと消える。直るのは著者が次にその記事を開いたときで、それが §14.3 の「表は普通の編集で温まる」の一部である。基準 14t がこの規則を固定している。

#### 14.3.2 覚えた失敗は、著者が直したことを知らない（2026-08-29 報告・修正）

報告は「Google Slides の共有設定を有効にしたのに、カードが『タイトルを取得できませんでした』のままになる」だった。

実測（`link_previews` の行、2026-08-29）: 同じデッキに `failed` の行が 2 本（12:47:12 と 12:47:57 JST）。**8 分後に同じ URL を `fetchLinkPreview` に通すと、題も 1 枚目の画像も返る。** 失敗したのは共有が効く前で、`FAIL_TTL_MS` の 30 分がそれを覚えていた。

**機構**: NodeView は描画のたびに route を訊くが、route は行が新しければ行を返す。失敗の行も 30 分は新しい。**著者が対象側を直しても、こちら側は訊きに行かない** — §14.3 が手動リフレッシュ UI を非目標に置いているので、待つ以外の手が無い。

**決定: 著者の明示的な「カードにする」だけが、覚えた失敗を無視して訊き直す。** `/api/link-preview` の `force=1` が `resolveLinkPreview(url, force)` に渡る。付けるのは `linkToCard` の 1 箇所だけで、NodeView 自身の描画時の照会には決して付かない。自動の経路は 30 分の壁の内側に残る。

**新しいボタンは足していない**ので、§14.3 が非目標に置いたリフレッシュ UI はそのままである。失敗したカードは「リンクに戻す」を持ち、戻せば参照はバブルの中に落ちて「カードにする」が出る — 押す理由が分かる場面でだけ現れる 2 クリックであって、いつでも押せる 3 つ目のボタンではない。

**`ok` の行は force でも使う。** 答えの出ているページを訊き直すのは §14.3 が断ったリフレッシュそのもので、しかも失うほうが大きい — 相手が一瞬落ちていれば、良いカードが失敗に置き換わり、その失敗を行が 30 分覚える。実測 2026-08-29: この条件を入れる前は、解決済みの外部リンクをカードに変える E2E が種の行ではなく実際のネットワークを見に行って落ちた。

**フラグは最初の照会で消える — 相手がまた失敗しても消える。** 残せば次の通常描画がネットワークに出てしまい、それは行が防いでいる経路そのものである。

文言も変えた（`RETRY_NOTE`）: 「タイトルを取得できませんでした（リンクに戻してカードにし直すと再取得します）」。**記事カラムの幅では 1 行に収まり、カードの高さは 136px のまま変わらない**（実測 2026-08-29、766px のカードで前後とも 136px）。

### 14.4 決定④ — 出すのはタイトル・説明・ドメイン・画像。画像は自分のプロキシから出す

**§12 の最終行をここで現金化する。** あちらはカードの最下段を出所の枠と定め、そこに入るのはドメイン名であって日付ではないと書いている。内部カードでは行き先が常にこのブログだから言うことが無かった枠で、外部カードでは初めて意味を持つ。

**日付は入れない。** §12 の 2 つの理由（遷移先を開けば同じ日付が見える／古い記事へのカードで日付が先に目に入ると、カードが促したいクリックを自分で抑える）は行き先が外部でも変わらない。§12 の判定は動かず、理由の 1 つ目（出所の枠に言うことが無い）だけが役目を終える。

**説明は og:description と `<meta name="description">` の両方を見る。** 実測（2026-08-18、上の 10 件）:

| 取得できたもの                         | 件数 |
| -------------------------------------- | ---- |
| タイトル（og:title または `<title>`）  | 9/10 |
| og:title                               | 6/10 |
| og:description                         | 4/10 |
| og:description または name=description | 6/10 |
| og:image                               | 6/10 |
| og:site_name                           | 3/10 |

og:description だけを見ると 4 件、`name="description"` に落とすと 6 件になる。**`zenn.dev` はどちらも持たない** — 説明の無いカードはタイトル 1 行になり、これは §12 が既に持っている分岐である（`cardElement` は空文字の行を出さない）。10/10 に届かない 1 件は `www.npmjs.com` の Cloudflare 403 で、`link-requirements.md` §5.5.10 が測ったのと同じ落ち方をし、同じ規則（2xx でなければ読まない）が同じように受ける。本文は `<title>Just a moment...</title>` を持っている。

**エンティティは 1 回だけ復号する。** 実測（2026-08-18）で `qiita.com` の og:description は `… 記録 &amp;amp; 公開 …` を返す — 相手側の二重エンコードである。HTML パーサが 1 回復号した値（`&amp;`）が DOM から読む消費者の受け取るものなので、**こちらもそこで止める**。2 回復号すると、`&amp;` を意図して表示しているページを壊す。カードに `&amp;` が見えていたらそれは相手の値である。

**出所はホスト名で出す。og:site_name は使わない** — 3/10 しか無く、7 件が空になる枠は枠として成立しない。`new URL(href).hostname` から先頭の `www.` だけを落とす。

**画像は出す。ただしホットリンクはしない。** og:image は 6/10 あり、値はいずれも第三者の CDN 上の絶対 URL である（`res.cloudinary.com` / `opengraph.githubassets.com` / `cdn.qiita.com` / `upload.wikimedia.org` と、動的 OG 生成の 2 件）。**その URL を公開ページの `<img src>` に置くことはしない** — それはホットリンクで、`lib/thumbnail.ts` が `UPLOAD_PATH` を「サイト相対のアップロードパスだけ」に絞る理由として名指ししている形であり、`link-requirements.md` §5.5.8 が「公開側に favicon を出す話が来たときにこの節を根拠にはできない」と先回りで釘を刺した場面でもある。

代わりに**自分のところを通す**。公開ページが出すのは `/api/link-image?url=…&sig=…` で、読者のブラウザはこのサイトに画像を求め、route がその瞬間に取りに行く。**読者のアドレスは相手に渡らず、相手が画像を差し替えてもこのブログが何を出すかはこちらの route が決める。** §14.4.1 の実測どおり、Zenn とはてなが両方ともこの形である。

**ディスクには保存しない。** バイト列を `/uploads/` に置く形も検討したが、`scripts/gc-uploads.mts` を参照元ごと増やすことになり、取り直しのたびに orphan が出る。プロキシならどちらも無い。

**署名は 2 つある脅威のうち 1 つしか止めない。ここを取り違えない。** この route だけは admin で塞げない（読者が読み込むのだから当然である）。`lib/link-image.ts` が URL に HMAC を付け、route は**何かを取りに行く前に**検証するので、**他人が自分の URL を持ち込むこと**は止まる。止まらないのは**こちらの URL を使い回されること** — 署名付きのパスは公開ページの HTML に印刷されており、公開で、恒久で、`Cache-Control` は相手が従う義務のない助言にすぎない。**同じカードに N 回要求すれば、素朴な実装では N 回の外向き取得になる。** Zenn とはてなが平気なのは前に CDN が居るからで、ここにはまだ居ない（§14.4.1）。

したがって外向き側を止めるのは署名ではなく**上限つきのキャッシュと in-flight の集約**である（どちらも `lib/link-image.ts`、プロセス内）。同じ URL への同時要求は 1 本の取得にまとまり、次の要求はメモリから返る。失敗も覚える。**1 枚あたりの上限はアップロードの 5MB ではなく 2MB** — 最大でも 200 × 128px に描くものであり（§15）、この数字は同時に「公開 URL 1 回あたりこのサーバが払う上限」でもある。CDN が前に入れば両方の仕事を引き取る。

**鍵は `SESSION_SECRET` から導いた別鍵で、未設定なら起動時に落とす。** `?? ''` で空鍵に落ちる形は degrade ではない — 鍵が誰にでも計算できる定数になり、admin で塞げないこの route が**動いているように見えたまま**オープンプロキシになる。`lib/site.ts` が `SITE_ORIGIN` を落とすのと同じ形の設定ミスである。

**画像が 6/10 であることは、この判断を変えない。** カードは `<img>` の有無で 2 通りになるが、公開側にもエディタ側にも「絵の無いカード」の描き方は先にある（当時は内部カードがその形を持っていた。内部カードは 2026-08-22 に必ず画像を持つようになり、この 2 通りは外部カードだけのものになった — §17）。

**`immutable` は嘘になりうるが、そのままにする（2026-08-29 実測）。** 署名付きパスは対象 URL から導出されるので対象が同じなら一定で、`Cache-Control: public, max-age=604800, immutable` は「この URL の中身は変わらない」と言っている。Google スライドはこれを破る — `og:image` の URL は編集をまたいで 1 文字も変わらず、Google は同じ URL の裏で描き直して `ETag: "v4"` を返す（実測 2026-08-29、あちらは `private, max-age=86400`）。それでも縮めないのは、**絵の古さが行の 7 日（`OK_TTL_MS`）と揃っているから**である — 絵だけ新しくすると、新しいスライドの横に古いタイトルが並ぶ。加えて route は `ETag` も `Last-Modified` も出していないので、`immutable` を外すと再検証が 304 ではなく全ダウンロードになる。外すなら検証子が先で、カード全体を新しくしたくなったときに触るのは `OK_TTL_MS` であってこのヘッダではない。

#### 14.4.1 他所のカードは画像をどうしているか（実測 2026-08-18）

§14.4 は画像を出さないと決めたが、**他がどうしているかを測らずに決めていた**ので、実ブラウザで 2 つ測った。どちらも**ホットリンクしていない。自分のインフラを通している。**

|        | 画像の出所                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------------------------- |
| Zenn   | `embed.zenn.studio/api/optimize-og-image/<20 桁の署名>/<元の og:image URL を percent-encode したもの>`          |
| はてな | `cdn.image.st-hatena.com/image/square/<ハッシュ>/backend=imagemagick;height=200;version=1;width=200/<元の URL>` |

読者のブラウザは `cdn.qiita.com` にも `upload.wikimedia.org` にも `opengraph.githubassets.com` にも触らない。**どちらも「保存」ではなく「プロキシ」である** — 元の URL をパスに埋めて、オンデマンドで取得し、CDN でキャッシュし、リサイズまでする（はてなは imagemagick と寸法がパスに書いてある）。**パスの署名／ハッシュは、その口が誰でも使える画像プロキシになるのを止めるためのものである。**

ついでに 1 つ: **Zenn は favicon を Google の favicon サービス（`www.google.com/s2/favicons?domain_url=`）から出している** — 相手のサイトにも直接行かない。この repo は `link-requirements.md` §5.5.8 で相手のオリジンの `/favicon.ico` を直接引くと決めているが、あれは**著者のブラウザ**から引く話なので、比較の対象が違う。

**これが変えること**: 選択肢は 2 つではなく 3 つである。画像用のエンドポイントを 1 本置く形（`<img src="/api/link-image/…">`）は、**§14.1 を壊さない** — §14.1 が禁じているのはページのレンダリングが外に出ることで、画像は別のリクエストであり、レンダリングは表を引くだけのままだからである。保存も GC も orphan も要らず、読者の IP も相手に渡らない。**採るなら、署名の無いパスにはしないこと。**

**この節が §14.4 を動かした。** 測る前は「出さない」で、理由は再配信の是非を決めていないことだった。測ったのは**大手 2 つが両方ともプロキシで出している**という事実で、それを見たうえで 2026-08-18 に出す側へ倒している。プロキシも再配信ではあるという点は変わっていない — 変わったのは、それが業界の実務であることが分かったことと、**プロキシなら保存も GC も要らない**ことが分かったことである。

### 14.5 決定⑤ — 取得器は共有し、保管だけ分ける

`lib/link-title.ts` は既に必要なものをほぼ全部持っている。**足すのは抽出だけである。**

- **そのまま効くもの**: `isBlockedAddress`（ループバック・リンクローカル・RFC 1918・CGNAT・マルチキャストと v6 の対応物）、ホップごとの `dns.lookup` 全レコード検査、`redirect: 'manual'` と `MAX_REDIRECTS`、`MAX_BYTES`（64KB）、`TIMEOUT_MS`（5 秒）、2xx 以外を読まない規則、`normalizeTitle` のエンティティ復号と `TITLE_MAX_LENGTH`（120 字）。
- **足すもの**: og:description → `<meta name="description">` の順で読む抽出（§14.4）と、その長さの上限。上限は 200 字とする — 見た目は CSS の 2 行クランプ（`.prose .link-card-description` の `line-clamp: 2`）が受けるので、これは**保存する第三者テキストを有界にするための値**であって表示のための値ではない。
- **og:image も抽出する**（2026-08-18、§14.4 で出すと決めたため）。値はページが書いたまま — 絶対 URL に解決するだけで、バイト列は保存しない。列に入るのは参照で、読者が読み込む `/api/link-image?…` はそこから毎回導く。導出を 2 度しないので、署名鍵が変わっても行を書き換える必要が無い。
- **取得器は 3 人目の利用者を得た。** ガードとリダイレクトのループは `lib/guarded-fetch.ts` に移してあり、HTML を読む 2 つの抽出器（この節）と、バイト列を読むプロキシ（§14.4）が同じ 1 本を通る。**何を取ってよいかは 1 か所でしか決まっていない**という性質は、利用者が増えたときにこそ効く。

**64KB の上限は外部ページでも足りる**（実測 2026-08-18）。10 件のうち本文が 64KB 以内に収まるのは 2 件（`example.com` 1KB、Cloudflare の 403 が 5KB）だけで、残りは 94KB〜602KB ある。それでも**先頭 64KB だけを復号して、上の表のタグはすべて見つかっている。** 打ち切りが効くのは `<head>` の位置であって本文の大きさではない、という形で残しておく。

**route は新しく 1 本置く** — `app/api/link-preview/route.ts`。`getOptionalSession` で塞ぎ、session が無ければ 401（`/api/posts/search` と同じ形）。`?url=` を受け、行が新しければそれを返し、古ければ取得して書き換えて返す。

**`/api/link-title` には相乗りしない。** あちらの答えは `{ title }` でキャッシュはプロセス内の Map、こちらの答えは行で保管は表である。混ぜると §5.5.10 の決定（TTL の 2 段構え、200 件の上限、自サイトを fetch しない短絡）を開け直すことになり、得るものは route ファイル 1 つである。**取得器は 1 つ、保管は 2 つ**にする。

#### 14.5.1 自サイトの URL は自分で fetch しない（2026-08-18 実装時に追加）

設計に無く、実装して最初に出た形である。**著者が自分の公開記事の URL を貼る**という、`/api/link-title` の route コメントが「ローカル作業中に公開 URL をそのまま貼る著者のため」と既に書いている場面がそれで、外部 URL の見た目をしているのに行き先はこのブログである。

**決定: 入口で内部参照に書き換える。** `normalizeCardHref`（`lib/link-card-href.ts`）が `https://<自分のオリジン>/posts/<slug>` を `/posts/<slug>` に直し、できるのは内部カードになる。理由は 2 つあり、どちらも単独で足りる:

- 内部カードは `posts` を描画のたびに引くので、改題に追随し、下書きなら警告も出す（§13.1）。外部カードにすると、同じ行の**スナップショットを表に保存する**ことになる。
- そのスナップショットを取るために、**サーバが Funnel 越しに自分自身へ要求を出す**。`/api/link-title` がまさにその要求を拒んでおり（「the one request the address guard cannot reason about」）、ここで作れば同じものを別の口から作ることになる。

**route 側も塞ぐ。** `/api/link-preview` はブラウザが送った `Host` と比べて自オリジンを拒む。`ownTitle` に当たる代替は持たない — 入口で書き換わっている以上ここへ届く自オリジンの URL は記事を指していないものだけで、カードにする先が無いからである。

**自オリジンで記事を指さない URL（`/about` など）は入口で断る。** 内部カードにはできず（記事が無い）、外部カードにもできない（route が取りに行かない）ので、カードを作ってから解決に失敗させるより先に断るほうが短い。

**入口だけでは足りない。第 3 の扉がある。** `parseHTML` は `data-href` を検証せず何でも受けるので（§4 の「著者が raw HTML として貼れる」）、**本文が最初からこのブログの公開 URL を持ったカードを運んでくることがある** — 手書き、あるいは他所からの raw HTML のペーストである。入口の書き換えはそこを通らない。そのままだと、カードは自分のサーバについて preview route に訊き、route に断られ、**著者自身の記事について「タイトルを取得できませんでした」と言う。**

**オリジンの比較は文字列の比較であり、今のオリジンとの比較である。** サイトが引っ越すと（Cloudflare Tunnel と独自ドメインは予定に入っている）、`https://blog.example.ts.net/posts/x` はもう自オリジンではなくなり、外部カードとして扱われる — route はそれを取りに行き、Funnel が生きていれば**サーバが自分の記事をインターネット越しに読んでスナップショットを保存する**、落ちていれば `failed` の行になる。

**それでも保存済みのカードは無事である。理由は入口で書き換えているからである。** 著者が自分の URL から作ったカードは、作った時点で `/posts/x` になって保存されている — オリジンを含まない参照なので、引っ越しても何も指さなくならない。上の経路に落ちうるのは、手書きの raw HTML が絶対 URL を持っていた場合だけである（第 3 の扉、下記）。**入口での書き換えは利便性ではなく、保存形式をオリジンから切り離す操作**だったことになる。

したがって書き換えは**解決側にも置く**: `lookupCard`（エディタ）と `resolveCard`（公開ページ）が、引く先を決める前に同じ関数を通す。**保存された参照は書き換えない** — 決まるのはどの表が答えるかであって、本文が何と書いてあるかでも、カードのリンクがどこへ行くかでもない。その結果このカードは**出所の行にこのブログのホスト名を出す**（href が絶対 URL である以上それは正しい）。基準 14n がこの経路を固定している。

#### 14.5.2 `sameSite: 'lax'` は入口を塞ぎきらない（2026-08-18 確認）

`app/api/link-title/route.ts` は「session cookie が `sameSite: 'lax'` なので、他所のページが著者のブラウザにこの route を呼ばせることはできない」と書いている。**トップレベルの GET ナビゲーションについては、これは正しくない** — lax が意図的に通すのがまさにその形である。したがって著者が踏んだページは、任意の `url` を付けてブラウザをここへ飛ばせ、要求は認証済みで届く。

**得られるものは限られており、その限りは全部意図して置いたものである**: 答えは著者自身のタブに出る JSON で、飛ばした側は同一オリジンポリシーにより読めない。取りに行ってよい先は `lib/link-title.ts` のアドレスガードが決めるので、私有ネットワークには向けられない。本文には上限があり、要求にはタイムアウトがある。残るのは**公開 URL への外向き GET 1 本と、`link_previews` の行 1 つ**である。

**つまりアドレスガードは保険ではなく本体である。** 入口自体を塞ぐなら `sec-fetch-site: cross-site` の拒否で、そのときは `/api/link-title` と `/api/posts/search` も同時にやることになる — 3 本とも同じ形をしている。**この文書では決めない**（カードだけの話ではないため）。

#### 14.5.3 og:image の値も実体参照を復号する（2026-08-19 修正）

§14.4 が「エンティティは 1 回だけ復号する」と決めたのは説明文についてで、**`extractImage` はその復号を通っていなかった**。属性の中の `&amp;` が残るので、クエリを持つ og:image は `amp;w` `amp;s` … という名前のパラメータを並べた別の URL になる。

**落ちるのは、送られたものを検証する相手だけである。** 実測（2026-08-19、7 サイト）:

| 取得先                                    | 値に `&amp;`  | 復号前   | 復号後                    |
| ----------------------------------------- | ------------- | -------- | ------------------------- |
| `qiita.com`（imgix。`s=` で署名）         | あり          | 取得不可 | 200 `image/jpeg` 1200×630 |
| `nextjs.org`（`/_next/image?url=&w=&q=`） | あり          | 取得不可 | 200 `image/png` 2400×1256 |
| `ja.wikipedia.org`                        | あり          | 200      | 200                       |
| `tiptap.dev`                              | あり          | 200      | 200                       |
| `zenn.dev` / `github.com`                 | なし          | 200      | 200                       |
| `developer.mozilla.org`                   | og:image 無し | —        | —                         |

`ja.wikipedia.org` と `tiptap.dev` は知らないパラメータを黙って捨てるので、復号前でも 200 を返す。**`&amp;` を含むのが 4 件、実際に落ちるのは 2 件**という比率がこれを隠していた。§14.4 で最初に測った `zenn.dev` の Cloudinary URL はクエリが 1 個しか無く `&` を持たないので、無傷だったのは偶然である。

**症状は「画像だけ無いカード」で、行は `partial` になる。** `usableImage` が `probeImage` の否を受けて画像を落とすだけなので、タイトルも説明も出たままであり、取得は成功しているように見える。

**`&amp;` が属性の中で意味を変えることは、保存側では既に分かっていた** — 基準 14o が `data-href` について同じ往復を測っている。抽出側に同じ目が向いていなかった、という形で残しておく。

**復号は `decodeEntities` に切り出して `normalizeText` と共有する。** URL に空白の畳み込みと字数の打ち切りを掛けるわけにはいかないので、共有するのは復号だけである。

#### 14.5.4 取得器の期限は 2 つあった（2026-08-31 報告・修正）

**Node は解決した複数のアドレスを競走させ、各試行に `autoSelectFamilyAttemptTimeout`（既定 250ms）を与える**（RFC 8305）。次に試す相手が無いとこれが接続の期限になり、§14.5 が「そのまま効くもの」に数えた `TIMEOUT_MS`（5 秒）とは別の、宣言されていない期限として働く。

実測 2026-08-31、asciinema.org。AAAA はこのホストから届かず（`ENETUNREACH` を即返すので切り替え自体は無コスト）、A のハンドシェイクは 249〜289ms でちょうど境界に乗る。両ファミリでは 3 回中 2 回が約 300ms で `ETIMEDOUT`、同じ名前を A だけに解決させると 3 回中 3 回が 274〜289ms で接続した — **単一アドレスには持ち時間が付かない。** カードが出るかどうかはコイン投げだった。

**症状は第三者が拒んでいる姿をしている。** 残るのは `link_previews` の `failed` 行だけで、相手のサイトは何も間違えていない。og:image が同じオリジンにあれば `probeImage` も同じ確率で落ちるので、ページ側が勝っても `partial` になりうる。

**決定: `lib/guarded-fetch.ts` で `setDefaultAutoSelectFamilyAttemptTimeout(1000)` を呼ぶ。** プロセス全体に効く — `node:net` の既定値で、undici の dispatcher を持ち込まない限り要求ごとの形が無い。変わるのは 1 つのアドレス族を諦めるまでの時間だけで、最初の族が無言でハングする相手のフェイルオーバが 250ms から 1 秒になる（`TIMEOUT_MS` の内側）。

**許すものは動かない。** `isBlockedAddress` とホップごとの全レコード検査は無変更で、禁止レンジ宛ては接続が始まる前に落ちる。増えるのは届く相手であって、許される相手ではない。

引き金は「AAAA を持ち、かつ届く側のハンドシェイクが 250ms を超える相手」で、既存の埋め込みプロバイダが踏まなかったのは全部 CDN の後ろにいる（約 20ms）からである。取得器が 1 本なので、直りも 3 人の利用者に同時に効く。

### 14.6 決定⑥ — 入口は 2 つ。ペーストは引き金にしない

1. **ピッカーの検索欄が URL を受ける。** NodeView のピッカー（§5.2-3）は記事タイトルで自分の投稿を検索する欄を持っている。入力が `http(s):` の絶対 URL として解けたときだけ、結果の代わりに「この URL をカードにする」の行を 1 つ出す。UI は増えず、内部と外部が同じ 1 つの入口に並ぶ。
2. **バブルに「カードにする」を足す**（`LinkBubble.tsx`）。バブルはキャレット位置のリンクを既に解決していて操作の行も持っているので、貼る → autolink → 1 クリック → カード、という順序で届く。

**2 は §5.2-1 を更新する。** あそこは「既存のリンクがカードに変わる経路は無い」と書いており、それが変わる。**変わらないのは §4.1 (a)/(d) の却下のほう** — 昇格するのはパーサではなく著者の 1 クリックで、保存されるのはその場で曖昧さの無い `<div>` である。

**ペーストは引き金にしない。** ペースト時の変換は §4.1 (a) の 2 つの却下理由のうち 1 つ目（パーサ側も昇格させることになる）は回避するが、2 つ目は回避しない — **行に単独の裸 URL を、素のリンクとして貼る手段が無くなる。** §0 はその形が実在すると測っており、`unsetLinkCard`（「リンクに戻す」）は事後の修復であって、最初からそう書けることの代わりにはならない。

**置ける場所の判定は §5.4 と同じ答えを出すが、同じ問いではない**（2026-08-18 修正）。スラッシュメニューが訊く `canPlaceAfterCaret` は「キャレットのテキストブロックの**後ろ**にブロックを置けるか」で、範囲選択を明示的に拒む。バブルのボタンがやるのは**テキストブロックの置き換え**なので、訊くべきは「親がその位置にカードを持てるか」（`parent.canReplaceWith(index, index + 1, type)`）である。

**取り違えたまま出して 2 つ踏んだ。** ①適用のあと `applyDraft` は選択をリンク全体を覆う**範囲**にするので、ボタンが消えた（報告 2026-08-18）。②リスト項目の**最初の**段落でボタンが出ていた — `listItem` は `paragraph block*` なので、置き換えると項目が頭を失う。正しい問いは両方を同時に直す。基準 14u。

スライス側（ペースト・ドロップ）に新しいガードが要らないことは変わらない — カードは block atom のままで、`titleAcceptsSlice` と `carriesNonParagraphBlock` が今と同じ理由で覆う。

### 14.7 エディタでの見え方

**エディタのカードはタイトルとホスト名の 2 行、および画像である。説明は公開カードにだけ出る。** 内部カードの NodeView も説明を出しておらず（`renderCard` が描くのはタイトルと `.link-card-meta` だけ）、§13 がそこへ足したのは画像であって説明ではない。この差は外部カードが持ち込むものではなく、引き継ぐものである。

**画像は公開カードとまったく同じ `<img src>` である** — `/api/link-preview` が署名済みのパスを返すので、エディタと公開ページが同じ 1 本の URL を描く。§7 が NodeView を実物のカードにすると決めた線がここまで届いており、副産物として**相手の生の URL がブラウザに 1 度も渡らない**。置き場所は §13 が決めた右で、`.prose .link-card-image` の 1 本がそのまま効く。

**§13.1 の 3 状態はそのまま使う。** `unknown` は答え待ち、`found` は取れた、`missing` は route が「取れなかった」と答えた場合で、外部カードでは下段が「タイトルを取得できませんでした」になる。**取れなかったカードのタイトルは URL そのものになる**（§5.3 の縮退と同じで、著者が直せるのは自分が書いた参照だからである）。「未公開の記事」は内部カードだけの状態で、そのまま残る。

`postCache`（`link-card-extension.ts`）は答え全体を持つ形になっている（§13）ので、外部の答えも同じ Map に同じ形で入る。**キャッシュ命中と到着が同じカードを描く**という §13 の規則は、外部でも守る。

### 14.8 公開側

**`lib/render.ts` は動かない。** §6 の注入がそのままで、パイプラインは DB も表も知らない。分岐は `app/posts/[slug]/page.tsx` の `resolveCard` が持つ — `/posts/` で始まれば `getPostBySlug`、絶対 URL なら `link_previews` を引く。**取得はしない**（§14.1）。

**ホスト名は resolver ではなく解決段が出す**（2026-08-18、実装時の変更）。`CardTarget` は `title` / `description` / `thumbnail` のままで、`cardElement` は自分が検証した href から `externalCardHost` で引く。resolver に持たせる形（`domain` を足す）で設計していたが、それは**参照が指す先とカードが名乗る出所という、食い違いうる 2 つの値**を作る。同じ 1 回のパースから両方を出せば食い違いようがない。`thumbnail` は両方が埋めるが、作り方が違う — 内部カードは `resolveThumbnail`（`/uploads/…`）、外部カードは `linkImageSrc`（署名付きの `/api/link-image?…`）。**同一オリジンであることだけが共通で、それがここで効く唯一の性質である。**

**`<a>` に `rel` は付けず、`target` はカード自身が決めない。** **カードは行き先を問わず新しいタブで開く** — 内部カードも外部カードも同じである。付けているのは `cardElement` ではなくパイプライン最後の `rehypeNewTabLinks` で、判定はその 1 か所にしかない（2026-08-21、`link-requirements.md` §7.2 の「カードの規則」）。**カードは本文の語に付いたリンクとは別の道具で、ブロックとして置いた「別の記事そのもの」である** — だから外部リンクと同じ扱いにするのではなく、カードという部品の側で揃える。外部カードだけが別タブだと、見た目の同じ部品が行き先によって挙動を変えることになる（ドメイン行の有無で見分けろとは言えない、§14.4）。

**解決に失敗したカード（§6.1 の素のリンク）はこの規則の外である。** `fallbackLink` はクラスを持たない `<a>` を出すので、カードの見た目を失ったものは今そこにある素のリンクとして扱われる — 内部なら同一タブ、外部なら「サイトを離れる」側の規則で別タブになる。

`rel` は本文のリンクと揃えて付けない（`noopener` は現代のブラウザが `target="_blank"` に暗黙適用し、`noreferrer` は `nofollow` を拒む理由と同じ理由で付けない）。

**第三者のテキストが公開ページの DOM に入る。** hast の text ノードとして入るので escape され、問題は injection ではなく**レイアウト**である（`TITLE_MAX_LENGTH` のコメントと同じ論法）。上限は取得側の 120 字／200 字と、CSS の 2 行クランプの二重で受ける。

### 14.10 未実測のこと

- **公開側の自オリジン書き換え**（§14.5.1 の第 3 の扉）。エディタ側は実測したが、公開側は E2E で測れない — ハーネスは `SITE_ORIGIN` を本番の URL にしたまま localhost で配信するので、**ブラウザのオリジンとサーバの `siteOrigin` がわざと食い違っている。** 本番では同じ 1 つの文字列であり、両側が同じ答えを出すのはそのときである。
- **IDN のホスト名**。`URL.hostname` は punycode を返すので、日本語ドメインのカードは `xn--` を出す。実測していないし、直すとしたら表示側である。
- **外部ページの日付が取れるか**（`article:published_time`）。§14.4 で日付を出さないと決めたので測っていない。出す話が来たら先に測ること。
- **文字コード**。`link-requirements.md` §5.5.10 が 10/10 UTF-8 と測っているが、それはこの節の 10 件とは別の集合である。
- **全数実行が 2 度、別々の形で赤くなった。どちらも再現していない。** 1 度目（2026-08-18）は `editor-link-bubble.spec.ts` の §5.5.15 の spec が 1 件。2 度目は 5 件で、内訳は同ファイルの別の 1 件、`editor-link-card` の 1 件（15 秒のアクションタイムアウト）、`publish-race-guard` の 1 件と `thumbnail` の 2 件。**後ろの 3 件はどれも「同じ記事が 2 行ある」形**である。

  **記事の行を作るのは autosave の経路であり、この節の変更はそこに 1 行も触れていない**（増えた書き込み先は `link_previews` だけで、バブルに足した `editor.can()` は書き込まない — `@tiptap/core` の `createCan` が `const dispatch = false` と `dispatch: void 0` で組む）。`editor-link-bubble` の 1 件はネットワーク依存の assertion で、バブルの 1 行目は「タイトルが取れたらタイトル、取れなければ URL」なのに spec は URL 側を期待している — 今回は `example.com` のタイトルが実際に取れて落ちた。

  **直後に単独で回すと 4 ファイル 57 件が全部緑**、そのあと全数 565 件も緑（12.5 分。赤かった回は 13.8 分）。**したがってベースラインとの比較はしていない** — 比較の条件（同じ場所で再現すること）が満たされなかったからである。**トレースは残っていない**（`test-results/` は実行のたびに消える。`link-requirements.md` §5.5.10 が同じ手違いを記録している）。**待ち時間もタイムアウトも広げていない。**

- **画像が実際に出ることは spec ではなく手で測った**（2026-08-18）。`https://qiita.com/` をピッカーに貼り、エディタと公開ページの両方で `<img>` の `naturalWidth` を見た: src は `/api/link-image?url=…cdn.qiita.com…&sig=…`、デコード後 1200 × 630、公開カードの箱はこのとき 128 × 80px だった（枠いっぱいに変えたのは翌日、§15）。**spec には持ち込めない** — 実 fetch を CI に入れない規則（§14.9）があり、ローカルで代用しようにもアドレスガードがループバックを弾くので、絵が出るところだけは外に出るしかない。測れないという理由は答えが出ても変わらない（`link-requirements.md` §8 末尾の規則）。
- **`partial` の経路**（§14.3.1）。「ページは og:image を持っているのに引けない」相手を、ネットワークに出ずに作る手立てが無いので測っていない。版の規則（基準 14t）は測ってある。
- **プロキシが実際に何回取りに行くか**。プロセス内キャッシュの命中率も、CDN が前に無い状態でのレイテンシも測っていない。**測るのは CDN を入れる前後である。**
- **読み込み時に相手の画像が消えていた場合**。カードを書いた時点では引けた画像が後から消えると、公開ページには壊れた画像が残る（静的な HTML なので、そこでは何も反応できない）。**次にエディタでその行が更新されると `image` が空になって消える**という自己修復の経路はあるが、実際にその順序で起きるところは測っていない。
- **表の伸び方**。カードの実使用がまだ無い（§0）ので、行数の上限も掃除も要ると分かっていない。

### 14.11 却下した案

- **読者のリクエストで取得してキャッシュする** — §14.1。第三者の応答時間が TTFB に乗り、失敗が読者に見え、キャッシュの設計が §8.1 の見積もりの大半である。
- **公開時に本文へタイトルと説明を焼き込む** — 表も route も要らなくなり、公開側は今のまま 1 行も変わらない。**それでも採らない**: §4.2 が内部カードで断った形そのもので（他のレコードから導かれるものを本文に持たない）、焼き込んだ値は取り直す方法が無く、著者が書いていない第三者のテキストが本文の保存形式に入る。
- **og:image を公開カードに**ホットリンクで**出す** — §14.4。`lib/thumbnail.ts` の決定に反し、`link-requirements.md` §5.5.8 が明示的に「根拠にはできない」と書いた場面である。**画像そのものは 2026-08-18 に出す側へ倒した**が、出し方は自分のプロキシ経由であって、相手の URL を `<img src>` に置く形ではない。
- **取得した画像を `/uploads/` に保存する** — §14.4。プロキシで同じ絵が出せて、`scripts/gc-uploads.mts` に参照元を増やす必要も、取り直しの orphan も無いため。
- **og:site_name を出所に使う** — §14.4。実測 3/10。
- **`/api/link-title` のキャッシュを公開側と共有する** — §14.5。プロセス内の Map なので再起動で全カードが落ち、共有すると §5.5.10 の TTL 設計を開け直すことになる。
- **ペーストで自動的にカードにする** — §14.6。§4.1 (a) の 2 つ目の却下理由（裸 URL を素のリンクとして貼れなくなる）が消えない。
- **外部カード用に別のノード・別の class を作る** — §14.2。往復の性質も置ける場所も内部カードと同じで、分けると `CARD_HREF` の 1 本の述語で済む話が 2 つの機構になる。

### 14.13 200 なのに読めるものが 1 つも無いページがある（2026-08-21 実測）

§14.4 の表は取得の失敗を 2 通りで数えている — 2xx でないもの（`www.npmjs.com` の Cloudflare 403）と、2xx で読めたのに `og:` を持たないもの（`zenn.dev` の説明）。**3 つ目がある。200 で、`text/html` で、本文も届くのに、`MAX_BYTES` の内側に読むものが 1 つも無い形である。**

実測（2026-08-21、`https://www.youtube.com/watch?v=yVhDjqD5rw0` を `fetchGuarded` と同じ形で取得）:

| 見たもの                             | 値                                 |
| ------------------------------------ | ---------------------------------- |
| 応答                                 | 200 / `text/html` / 265ms / 1.19MB |
| `og:title` のバイト位置              | 693,270                            |
| `<title>` のバイト位置               | 690,464                            |
| 先頭 64KB にある `<title>` と `meta` | **1 つも無い**                     |

**原因は相手の応答ではなく上限の側にある。** `fetchPageHtml` は `readCapped` で 64KB を切ってから抽出器に渡す。`MAX_BYTES` のコメントはその上限を実測で支えている — 「10 サイトすべてで、存在する `og:` タグは先頭 64KB の内側にあった」。**その実測は正しく、一般ではない。** YouTube は head のメタデータの前に約 690KB のインライン JS を置く。

**YouTube 固有の話ではない。** 同じ形になるのは、メタデータの前に数百 KB を置くページすべてである。分かれ目は相手が何を返したかではなく、どこに置いたかにある。

**著者に何が見えるか**: `fetchLinkPreview` が null を返すので §14.7 の `missing` になり、カードのタイトルは URL そのもの、下段は「タイトルを取得できませんでした」になる。公開時は §6.1 で素のリンクに落ちる。失敗そのものは伝わる。伝わらないのは理由のほうで、403 と見分けが付かない（この見え方は §14.7 から読んだもので、測ったのは取得側だけである）。

**上限は動かさない。** 64KB は防御であって調整値ではない。上げれば、この形のサイトのために全部の取得が数百 KB を読む。`fetchPageHtml` のコメントが書いている通り、避けたいのは「megabytes を decode して初めて分かること」そのものである。

**したがってこの穴は塞がない。該当するサイトには専用の経路を与える。** YouTube については `docs/embed-requirements.md` §9 が埋め込みを選んでおり、埋め込みは取得を 1 本も要求しないので、この節の問題は消える側に回る。

## 15. 画像はカードの枠いっぱいに出す（2026-08-19）

**決定: 画像はカードの上下と右の枠線まで届き、高さはカードいっぱいになる。幅は `16rem`（`max-width: 40%`）。** §8.2 と §13 が決めた「文字の列の右に固定サイズ」は動かない — 動くのはその固定サイズが `8rem × 5rem` の島だったことだけである。

**理由は比率である。** 外部カードの og:image は実測（§14.4、§14.5.3）でどれも約 1.9:1 だが、箱は 1.6:1 だった。`object-fit: cover` は短い軸に合わせて切るので、**幅の 16% が常に落ちていた**。Qiita のようにタイトル文字を焼き込んだ画像では、落ちるのが文字の端であり、残った文字も 7px で読めない。

**幅は高さから決まる。** カードの高さが 136px に固定されたので（§16）、画像の箱は 256 × 134 になる。この比は 1.91 で **og:image の 1.905 とほぼ一致し、切り取りは縦横とも消える**。幅を先に決めて高さを後から固定すると比が崩れるので、この 2 つは 1 つの決定である。

**実測（2026-08-19、Chrome、1280px）:**

|                          | カード高 | 画像    | 見えている割合      |
| ------------------------ | -------- | ------- | ------------------- |
| 横長 1200×630（外部）    | 136px    | 256×134 | **幅も高さも 100%** |
| 縦長 350×696（自サイト） | 136px    | 256×134 | 幅 100% / 高さ 26%  |
| 横長（390px の電話）     | 136px    | 126×134 | 幅 49%              |

**機構 — `align-self: stretch` と負のマージンは 1 つの決定である。** padding の内側で伸ばすと上下に 12px の帯が残り、それは「小さい絵」ではなく「置き場所を間違えた絵」に見える。角丸は箱側で切る（`overflow: hidden` を `.prose a.link-card` と `.prose .link-card-view` の両方に）— 画像側の `border-radius` では、画像が接している 1px の枠線が角で四角く残る。

**天井は `calc(8.5rem - 2px)` で、引き算が要る。** 著者のアップロードは任意の形で、種データの 350×696 はこの幅では自然高が 397px になる。ただし引き算を落とすと、天井そのものと横長画像の自然高（134.4px）がカードの `min-height` を上回り、**高さを決めるのが画像になる** — 実測でカードが 136.39 / 136.39 / 138 の 3 通りになった（§16 が消したかったものである）。

**`max-width: 40%` はブレークポイントの代わりである。** このスタイルシートは幅のブレークポイントを 1 つも持たない。固定 256px は電話のカードを食い尽くすので、カード幅がおよそ 640px を切ったところでだけ効き、テキストの列に場所を返す。**電話では切り取りが戻る**（実測 49%）が、そこは画像より文字の場所のほうが要る。

## 16. カードの高さは 1 つにする（2026-08-19）

**決定: カードの高さは `min-height: 8.5rem`（136px）で 1 つ。タイトル 2 行・説明 1 行・ドメイン 1 行のクランプがそれを保証する。**

**理由は他所の実装である。** 参考にしている 2 サイトがどちらも高さを揃えている（Zenn と Qiita、実測 110px + 枠線 1px。別の 1 サイトは 133px）。**この文書は一度「揃えなくてよい」と判断した** — カードは全幅のブロックで縦に積まれるので、横に並ぶグリッドと違って下端の不揃いが見えない、という理由だった。**それは弱い根拠だった。** 揃える利益は下端の見た目ではなく、**カードが中身で伸縮する箱ではなく 1 つの部品として読めること**にあり、それは縦に積まれていても効く。実装が 3 つとも揃えているのは、その利益のほうを見ていたからである。

**高さを固定するとタイトルにクランプが要る。** 今までタイトルは行数無制限だった。固定した高さに対してそれは「背の高いカード」ではなく「`overflow` が黙って切ったタイトル」になる（§15 で角を切るために `overflow: hidden` が入っている）。行数の内訳と必要な高さ:

| 構成                          | カード高 |
| ----------------------------- | -------- |
| タイトル 1 行 + 説明 2 行     | 125.3px  |
| **タイトル 2 行 + 説明 1 行** | 128.5px  |
| タイトル 2 行 + 説明 2 行     | 150.9px  |

**説明は 2 行から 1 行になり、その 1 行はタイトルへ行った。** クリックを取るのはタイトルのほうであり、説明は §14.4 で測ったとおり本文の頭を機械的に切っただけのことが多い（Qiita は文の途中で切れている。Zenn は説明そのものを持たない）。

**`height` ではなく `min-height`。** 予期しない中身は、切られるより伸びるほうがよい。クランプがある以上そこには届かない（最大 102.45px に対して内側は 110px）が、届いたときの壊れ方を選べるなら伸びるほうである。**実測: タイトルを保存上限の 120 字にしてもカードは 136px のまま動かない。**

**エディタの `.link-card-view` には入れない。** あちらはピッカー状態（検索欄 + 結果リスト）を持ち、そちらは伸びる必要がある。高さを固定すると §7.1 で直したコントロール帯の事故に戻る。**揃えるのは読者が見るカードだけである。**

### 16.1 狭い画面ではカードを低くする（2026-08-19）

**決定: 幅 `30rem` 以下で、説明を出さず、カードの高さを `6.5rem`（104px）にする。** これがこのスタイルシートの**最初の幅ブレークポイント**である。

**高さを決めているのは画像ではなく文字である。** 390px では文字の列が 165px しかないので、タイトル 2 行 + 説明 1 行 + ドメインで 102px 積み上がり、カードは 136px になる。**実測した 2 サイトのどちらより高い**（Zenn 122px、gadgeteer 88px）。

**消すのは説明である。** 165px の列に 1 行の説明は十数文字しか出ず、26px を払う値がない。タイトルは 2 行のまま残す — クリックを取るのはタイトルであり、1 行に落とせばさらに 26px 下がって 82px になるが、**10 文字ほどで切れるタイトル**と引き換えになる。

**実測（2026-08-19、Chrome。3 枚のカードの高さ / 外部カードの画像）:**

| viewport | 3 枚の高さ      | 画像    | og:image の見える幅 |
| -------- | --------------- | ------- | ------------------- |
| 1280px   | 136 / 136 / 136 | 256×134 | **100%**            |
| 700px    | 136 / 136 / 136 | 228×134 | 89%                 |
| 560px    | 136 / 136 / 136 | 178×134 | 70%                 |
| 480px    | 104 / 104 / 104 | 146×102 | 75%                 |
| 390px    | 104 / 104 / 104 | 110×102 | 57%                 |
| 320px    | 104 / 104 / 104 | 82×102  | 42%                 |

**§16 の「1 つの高さ」は幅ごとに保たれる。** 3 枚が常に同じ高さであることは変わらず、その値が幅で 2 段になっただけである。**gadgeteer も同じ形で**、あちらは 135px と 88px の 2 段だった（実測 2026-08-19）。幅をまたいで 1 つの数にしているサイトは、測った 3 つのうち Zenn だけである（122px）。

**切り取りは副産物として改善する。** 高さが減ると枠が縦長でなくなるので、390px での見える幅は 43% から 57% になる。**これは目的ではない** — 画像の比率を固定して切り取りを構造的に消す形（gadgeteer が採っている）は採らなかった。それには文字の構成を幅ごとに 2 通り持ち、「文字が画像の高さに収まるか」を 2 か所で維持することになり、電話でのサムネが装飾であることに対して代金が高い。

**ブレークポイントは端末の寸法ではなく、1 行の説明が高さに見合わなくなる幅に置いている。**

### 16.2 画像の無いカードは文字を縦中央に置く（2026-08-19）

**決定: `.prose a.link-card:not(:has(img))` に `align-items: center` を当てる。高さも文字量も変えない。**

高さを固定した代償がいちばん出るのがこの形である。og:image を持たないサイトは実測で 10 件中 2 件（`developer.mozilla.org` など、§14.4）で、そのカードは 136px の枠に 3 行しか入らない。**この節が当てはまるのは外部カードだけである** — 内部カードは 2026-08-22 から必ず画像を持つ（§17）。**余りが全部下に溜まると「余裕」ではなく「何かが抜けている」に見える。**

**問題は余白の量ではなく寄り方である。** 中央に置けば同じ余白が上下に分かれる。実測（2026-08-19）:

|                          | 文字の上 | 文字の下 |
| ------------------------ | -------- | -------- |
| 画像なし（中央寄せ後）   | 30px     | 30px     |
| 画像あり（上寄せのまま） | 13px     | 46〜72px |

画像のあるカードは `flex-start` のままである。あちらの下の空きは絵が埋めているので、寄せ直す理由がない。

**却下した案:**

- **画像の無いカードだけ高さを下げる** — カードの高さが 2 種類になり、§16 と正面からぶつかる。
- **空いた場所を説明で埋める**（説明 2 行 + タイトル 1 行）— 情報は増えるが、**画像の有無でタイトルの行数が変わる**規則が 1 つ増える。長いタイトルのカードで、なぜそこだけ 1 行で切れるのかを説明できない。

**セレクタをアンカーに限っているのは、エディタの NodeView に届かせないためである。** あちらは上端にコントロール帯を持ち、その下だけを中央に寄せると 2 つの状態でボタンの位置がずれる — §7.1 が一度払った代金である。

### 16.3 画像はレイアウトの高さ計算から外す（2026-08-19 修正）

**症状: エディタのカードだけ、画像の下に 7px の帯が残った**（著者の報告。`umamusumelabo.com` の記事のカードで再現）。右下に細い枠のように見える。

**原因は §15 と §16 が持ち込んだ結合である。** 画像の天井 `max-height: calc(8.5rem - 2px)` は**公開カードの高さ**から導いた値だが、規則は 2 つの面で共有されている。エディタのカードは上端にコントロール帯を持つぶん背が高く、実測で 142px — 画像は 134px で頭打ちになり、8px 足りないまま止まる。

|                    | カード  | 画像    | 上 / 下 / 右  |
| ------------------ | ------- | ------- | ------------- |
| 公開（修正前）     | 750×136 | 256×134 | 1 / 1 / 1     |
| エディタ（修正前） | 750×142 | 256×134 | 1 / **7** / 1 |

**決定: 画像を絶対配置にして、カードの高さ計算から外す。** `position: absolute; top: 0; right: 0; height: 100%` を、`position: relative` にしたカードに対して当てる。絶対配置の包含ブロックは**パディングボックス**（＝枠線の内側）なので、パディングを手で打ち消さなくても三辺に接する。

**天井も床も要らなくなる。** フレックスアイテムだった間は画像の比率が行の高さに参加していたので、縦長のアップロードがカードを膨らませないよう天井が要り、その天井が上の不一致を生んでいた。**配置してしまえば画像は与えられた高さを取るだけで、高さに寄与しない** — 面ごとに歩調を合わせる数字が消える。

**`bottom: 0` ではなく `height: 100%` である。** `<img>` は置換要素なので、高さが `auto` だと画像自身の高さに解決され、`bottom` は over-constrained として捨てられる。実測（2026-08-19）でこれをやると、**この節が直そうとしている 7px がそのまま残った。**

**文字の列は同じ値で場所を空ける。** 画像が流れの外に出たぶん `gap` が効かないので、`--link-card-image-width`（`min(16rem, 40%)`）をカードに 1 つ宣言し、画像の幅と、`:has(img)` のときの文字列の `padding-right` の両方がそれを読む。**幅の出どころが 1 つなら 2 つはずれない。**

**修正後（実測 2026-08-19）**: 公開 750×136 / 画像 256×134、エディタ 750×142 / 画像 256×140 — **どちらも上 1 / 下 1 / 右 1**。

### 16.4 §16 の高さをエディタのカードにも与える（2026-08-21 修正）

**症状: 同じ画像が、公開ページとエディタで違う切り取りになる**（著者の報告）。`<img src>` は両面で同一なので（§14.4・§13）、違うのは箱だけである。

**原因は §16 の適用範囲である。** `min-height: 8.5rem` は `.prose a.link-card` に付いており、NodeView は `<div>` なのでそこに届かない。§16.2 は同じことをアンカーに限った理由を書いているが、§16 は書いていない — 意図した除外ではなく、漏れである。そして §16.3 以降、画像はカードの高さを取る（`height: 100%`）ので、カードの高さの差はそのまま切り取りの差になる。エディタのカードは高さを持たないまま中身なりに伸縮しており、**実測で 3 通りあった**: 90.78px（タイトルだけ）、116.13px（ホスト名つき）、142px（2 行タイトル、§16.3 の実測）。

同じ幅の段で 2 つ目の不一致も出ていた。 §16.1 の狭い画面用に残っていた画像の天井 `max-height: calc(6.5rem - 2px)` は、§16.3 が通常幅の天井を外したときに残ったもので、エディタの外部カード（116.13px）で画像を 102px に抑え、下に 13.13px の帯を作る — §16.3 が消したはずの症状である。公開カードは 104px に収まるのでこちらでは出ない。

**決定は 2 つで、互いに独立している。** 片方がもう片方を直すことはない。

1. `.prose .link-card-view` に `min-height`（通常 `8.5rem`、`max-width: 30rem` で `6.5rem`）。直るのは高さのばらつきである。
2. 狭い画面の `.prose .link-card-image { max-height: … }` を削除する。直るのは帯である。§16.3 の機構がそのまま理由になる — **流れの外にある画像に天井は要らない**。天井を残すと、それが導かれた面（公開）と当たる面（エディタ）が食い違う。

**実測（2026-08-21、Chrome、1280px / 400px。計測用の spec は残していない — この表がその成果物である）:**

| 幅・面                | 修正前                               | 修正後                       |
| --------------------- | ------------------------------------ | ---------------------------- |
| 1280 公開（3 枚とも） | 750×136 / 画像 ×134                  | 変化なし                     |
| 1280 エディタ 内部    | 766×90.78 / ×88.78                   | 766×136 / ×134               |
| 1280 エディタ 外部    | 766×116.13 / ×114.13                 | 766×136 / ×134               |
| 400 公開（3 枚とも）  | 319×104 / ×102                       | 変化なし                     |
| 400 エディタ 内部     | 319×90.78 / ×88.78                   | 319×104 / ×102               |
| 400 エディタ 外部     | 319×116.13 / 画像 ×102、下に 13.13px | 319×116.13 / ×114.13、下 1px |

**残る差は帯 1 つである。** コントロール帯は 35.19px あり、読者は見ない。1280px では中身が 136px に収まるので差は消えるが、400px の外部カードのように中身が床を超えるカードは公開より高いままで、画像もそれに合わせて伸びる。**帯を動かす話は §7.1 が二重クリックと引き換えに決めた位置に触ることなので、ここでは追わない。** この修正が消したのは、エディタのカードどうしが違う高さになることのほうである。

**ピッカーは 175.5px で、どちらの床より高い。** 同じ class を NodeView の根に付けている（`link-card-extension.ts` の `dom.className = 'link-card link-card-view'`）ので `min-height` はピッカーにも当たるが、当たっても何も動かない。セレクタを絞る必要は無い。

## 17. 画像を持たない自サイトの記事には、このサイトのマークを出す（2026-08-22）

**決定: 内部カードは必ず画像を持つ。** サムネイルが選ばれておらず本文にも画像が無い記事 — `resolveThumbnail` が `null` を返す記事 — を指すカードは、その枠にこのサイトのマーク（`public/link-card-placeholder.svg`）を出す。公開ページとエディタの両方で同じものを同じ枠に出す。

**外部カードには出さない。** og:image を持たない外部ページのカードは、これまでどおり文字だけのカードである（§16.2）。理由は 1 つで足りる — **このブログが書いていないページに、このブログのマークが乗る。** 出所は外部カードの下段が既にホスト名で言っており（§14.4）、そこに別のサイトを名乗る絵を足すのは、その行と矛盾する。相手の favicon を出す道は別の節が塞いでいる（§14.4・`link-requirements.md` §5.5.8）。

### 17.1 2026-08-19 に favicon を却下した理由は、ここには当たらない

この 2 つは形が似ているので、混ぜないために書いておく。**あれは相手のサイトのアイコンで、これは自分のところの静的ファイルである。** 却下の理由は 3 つあり、**どれも同一オリジンの自前アセットには当たらない**:

| 却下の理由（favicon）                                                                                           | このマークでは                                                     |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 第三者オリジンなので `/api/link-image` の署名プロキシに乗せる必要がある                                         | 同一オリジンの静的ファイル。プロキシも署名も要らない               |
| ルートの `/favicon.ico` しか見ないので不在が多く、公開側は `onError` を持たない静的 HTML なので壊れた画像になる | 常に在る。E2E が `naturalWidth` で「実際に届いていること」まで測る |
| 不在を潰すには列と `PREVIEW_VERSION` の更新が要る                                                               | 保存するものが無い。参照は定数 1 つ                                |

逆に、あの節が残した宿題はここでも宿題のままである — 外部カードの出所の枠にアイコンを足す話は、これで前例ができたわけではない。

### 17.2 機構

- **`resolveThumbnail` は広げない。** あの関数の答えは `og:image` にもなり、形は `scripts/gc-uploads.mts` の `UPLOAD_REF` と対になった `/uploads/…` に絞ってある（`lib/thumbnail.ts`）。そこから `/link-card-placeholder.svg` を返させると、アップロードの掃除に対する契約が壊れる。 マークはカードの調度であって記事の画像ではないので、決めるのは 1 つ上の層である。
- **決めるのは `lib/link-card-image.ts` の 1 本で、両面がそれを呼ぶ。** 公開側は `app/posts/[slug]/page.tsx` の `resolveCard`、エディタ側は NodeView の `lookupCard` で、どちらも `internalCardImage(resolveThumbnail の答え)` を通る。§13 と §16.4 は、この 2 面が絵について別々に決めたときに何が起きるかの記録である（同じ画像が違う箱で描かれ、キャッシュ命中のカードだけ絵を失った）。外部側は `externalCardImage` で、こちらは `null` を `null` のまま返す — 片方だけが分岐を持つことを型で見えるようにするためである。
- **運ぶのは `{ src, placeholder }` で、`src` から後で見分けはしない。** カードはこの絵を写真とは違う描き方をする（下記）ので、`src` を定数と比べて描き分ける形にすると、ファイル名を変えた日に静かに写真の描き方へ戻る。
- **`<img>` は class を 2 つ持つ。** `link-card-image link-card-placeholder` で、2 つ目だけが `object-fit: contain`・内側の余白・地色を足す。`cardElement`（`lib/rehype-link-card.ts`）と NodeView の `setImage` が同じ 2 つを書く。NodeView 側は毎回 `className` を代入し直す — 同じ `<img>` を使い回すので、マークのカードが写真のカードに変わったとき class が残ると、写真が地色の上に縮小して乗る。
- **枠は写真とまったく同じである。** 幅 `--link-card-image-width`、高さはカードいっぱい、三辺が枠線に接する（§15・§16.3）。**変えるのは埋め方だけ** — `cover` で切るのではなく `contain` で収める。
- **内側の余白だけは狭い画面で減る**（通常 `1.25em`、`max-width: 30rem` で `0.5em`）。枠の幅は §16.1 のもので動かせないので、マークに場所を返せる項はこれしか無い。実測（2026-08-22）: 320px で絵の枠は 94.8×102 になり、`1.25em` のままでは中の絵が 54.8px 幅 = 文字の高さ約 9px で、§15 が Qiita の焼き込み文字について「7px で読めない」と書いたのと同じ大きさになる。`0.5em` なら 78.8px 幅・約 13px、390px では約 18px である。

### 17.3 マークは色スキームごとに 1 枚。選ぶのはページで、画像ではない

**文字はサイトの前景色である** — light は黒（`#171717`）、dark は白系（`#e6edf3`）。罫はアクセントで、light `#cf222e` / dark `#f85149`（`.accent-emphasis` が dark で取る値）。算出したコントラストは文字が 15.38:1 と 13.7:1、罫が 4.59:1 と 4.83:1 である。**この配色は著者が選んだ**（2026-08-22。当初はアクセント 1 色で、その理由ごと機構が変わっている — 下記）。

地色は CSS（`.prose .link-card-image.link-card-placeholder`）が light で `#eaeef2`、dark で `#1c2128` を敷く。ダークのほうはカードのホバー塗り（`#161b22`）**ではない** — ポインタが乗っているあいだも絵の区画がカードから見分けられる必要がある。SVG 自身は背景を持たない。

**したがって SVG は 2 枚あり、選ぶのは `<picture>` の `media` である。**

```html
<picture
  ><source media="(prefers-color-scheme: dark)" srcset="/link-card-placeholder-dark.svg" />
  <img class="link-card-image link-card-placeholder" src="/link-card-placeholder.svg" alt=""
/></picture>
```

**1 枚の SVG の中に `prefers-color-scheme` を書く形は採らない。** それが効くことを確認できたのは Chrome だけで（実測 2026-08-22）、WebKit と Firefox はこの環境にブラウザが無く測れない。**前景色そのものを切り替える絵では、無視されたときの結果が「少し違う色」ではなく「見えない」である** — 黒い文字が dark の地に乗ると 1.11:1 になる。`<source media>` を読むのは画像ではなくページなので、この不確かさが消える。`<img>` の `src` は light 版のままで、`<source>` を読まない環境が落ちる先もそこである。

`<picture>` は箱を変えない。レイアウトの規則はすべて `.link-card-image`（＝中の `<img>`）に付いており、`<picture>` は自分では何も描かない。**そして写真のカードには付けない** — 1 枚しかない絵に選択肢は要らない。

**フォントはシステムのスタックで、サイトの Geist ではない。** 画像として読み込まれた SVG は外部リソースを取りに行けないので、webfont は届かない。同じ理由で、ロックアップは og.png（`scripts/make-og-image.mts`）と同じもの — アクセントの罫の下にサイト名 — にしてある。生成物が 2 つあるのではなく、同じ意匠を 2 つの寸法で描いている。**2 枚のファイルは幾何が同じで、違うのは 2 つの色だけである。**

### 17.4 却下した案

- **`/og.png` を流用する** — 比率は枠とほぼ一致する（1.9 対 1.91）ので、1280px では綺麗に入る。**電話で壊れる**: §15 の実測で、390px のカードでは og:image の幅の 57% しか残らない。文字を焼き込んだ画像がそこで切られる形は、§15 が Qiita の画像について既に記録している。
- **`app/favicon.ico` を拡大する** — 32px しか無く、枠は 256px ある。
- **`resolveThumbnail` にフォールバックを足す** — 上記（§17.2）。記事一覧と `og:image` が巻き添えになり、掃除に対する契約も壊れる。
- **外部カードにも何かを出す** — §17 冒頭。出所を偽ることになる。
- **1 枚の SVG に `prefers-color-scheme` を持たせる** — §17.3。Chrome では動く（実測）が、他で測れない仕組みに**見えるか消えるか**を預けることになる。`<picture>` なら判定はページ側で、`<img>` の `src` が落ち先になる。
- **記事一覧にも同じマークを出す** — **保留**（2026-08-22、著者の判断で後回し）。カードと一覧で絵の有無が食い違うが、破綻はしない — カードは 136px の枠を必ず埋める部品で（§16）、一覧の項目はそうではない。決めるまでは、マークはカードの調度という位置づけのままにする。

### 17.5 受け入れ基準（実測 2026-08-22）

§9 の表とは別に持つ。あちらの件数は動かさない（§14.9 と同じ理由）。**4 件のうち 4 件を実測した。**

| #   | 基準                                                                            | 実測                                                                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

## 18. 編集中の記事は、自分自身をカードにできない（2026-08-22）

**決定: いま開いている記事を指すリンクカードは作らせない。** エディタ側の入口を 4 つとも塞ぐ。カードにならなかった参照は、著者が書いたリンクや文字のまま残る — 消したり書き換えたりはしない。

**理由は、そのカードが読者に何も渡さないことである。** カードが出すのはタイトル・説明・画像で（§14.4）、自分自身を指すカードではその 3 つとも読者がいま見ているページのものになる。押せば同じページに戻ってくる。§13.1 が「異常だけを言う」と決めた下段も、ここでは言うことがない — 壊れてはいないからである。

**テキストリンクは対象外である**（著者の判断、2026-08-22）。同じ記事への `[…](/posts/<slug>)` は書ける。リンクは文中の言い回しの一部で、見出しへの `#anchor`（`link-requirements.md` §5.5.17）と地続きであり、そこまで塞ぐと「この記事の後半で書いた」と書けなくなる。カードだけがブロックを 1 つ占める部品で、自分自身を指す理由が無い。

### 18.1 入口は 4 つある

| #   | 入口                                     | 拒む場所                           | 著者に見えるもの                                            |
| --- | ---------------------------------------- | ---------------------------------- | ----------------------------------------------------------- |
| 1   | ピッカーの検索結果から選ぶ               | `renderPicker` の `show`           | 候補に出ない。自分 1 件しか一致しなかったときだけ理由を出す |
| 2   | ピッカーに自分の公開 URL を貼る          | `renderPicker` の `input` ハンドラ | 「この記事自身は参照できません」。カードにする行は出さない  |
| 3   | バブルの「カードにする」                 | `LinkBubble` の `toCard`           | ボタンが出ない（この画面が「提供しない」を言う既存の形）    |
| 4   | 既に本文にある `data-href`（貼り付け等） | `lookupCard`                       | カードは残り、下段が「この記事自身は参照できません」と言う  |

1 が実際に踏まれる道で、2 は §14.5.1 が自サイトの URL を内部参照に書き換えるので同じ判定に落ちる。**4 だけは既にある文書のためにある** — この規則より前に作られたカードや、生の HTML として貼られたものは他の 3 つを通らない。実際、実装時点の DB に 1 本あった（`f377f7a9a768a5b4d6f2` の公開本文）。

### 18.2 機構

- **述語は `isOwnPostHref(href, ownSlug)` 1 本**（`lib/link-card-href.ts`）で、4 つの入口がそれぞれ自分で聞く。渡すのは正規化済みの参照で、`ownSlug` が `''`（まだ行の無い新規記事）なら常に false である。
- **`normalizeCardHref` に混ぜてはいけない。** あれが `null` を返すと `lookupCard` の `normalizeCardHref(href, origin) ?? href` が生の参照へ落ち、内部カードとして普通に解決される — 一番塞ぎたい入口 4 で、判定が黙って消える。独立した述語なのはこのためである。
- **slug はエディタの storage で運ぶ**（`editor.storage.linkCard.ownSlug`、`PostEditor.tsx` が書き、NodeView が描画のたびに読む）。オプションでは遅い: 拡張の配列は最初のレンダーのものを `useEditor` が持ち続けるのに対し、新規記事の slug は最初の autosave が行を作った時に決まるからである。ExtensionManager は `this.editor.extensionStorage[extension.name]` を各コンテキストに渡すので、`addNodeView` が読む `this.storage` は著者が書いた当のオブジェクトである。
- **その slug を autosave が返すようにした**（`app/api/drafts/route.ts` の作成分岐が `slug` を含めて返し、`useAutosave` の `onCreated(id, slug)` が渡す）。行と一緒に slug は既に決まっていたが、これまでエディタに伝える必要が無かった。公開まで待つと、書いている最中がまるごと無防備になる。
- **一覧は「自分を外す」＋「0 件になったときだけ理由を言う」の 2 段である**（`show`）。押せない行を並べるのはピッカーの目的に反するので候補からは外す。ただし外した結果 1 件も残らなかったときは、空の文言を「一致する記事がありません」ではなく「この記事自身は参照できません」にする — 記事はあるのに無いと言うのは、そこだけで起きる嘘だからである。他に候補が残る場合は黙って 1 件減るだけでよい（選べる行が見えているので、説明する相手がいない）。
- **`lookupCard` が返すのは `missing` で、`found` + 下段ではない。** `cardCache` に入るのは `found` だけなので、指してはいけない参照が「顔」として残らない。**代償は、そのカードにタイトルが 1 つも出ないことである** — 上段は参照（`/posts/<20 桁>`）に落ち、「リンクに戻す」が戻すリンクの文字列も同じパスになる。§13.1 が下段からパスを追い出した理由がそのまま当てはまる形だが、指してはいけない参照に顔を与えるよりはこちらを取る。直すのは著者で、直せば消える。
- **コマンド `setLinkCard(href)` 自体は塞いでいない。** 呼んでいるのは slash メニューの `chain.setLinkCard()` 1 か所だけで、href を渡していない（`slash-command.ts`）。href を持って来る道は上の 4 つで、そこで既に聞かれている。将来ここに href を渡す呼び出しを足すなら、5 つ目の入口として同じ述語を聞くこと。

### 18.3 却下した案

- **行は出して押せなくする**（`{タイトル}（この記事）` と書いた不活性な行）— 却下（2026-08-22、著者の判断）。最初はこの形で実装したが、押せない行を並べることはピッカーの目的（押せるものを並べる）に反する。避けたかったのは「一致する記事がありません」という嘘の 1 点だけで、それは候補が 0 件になった場面の文言で塞げる（§18.2）。
- **公開側でも拒む**（`app/posts/[slug]/page.tsx` の `resolveCard` が自参照に `null` を返せば、§6.1 の素のリンクに落ちる）— **保留**。求められているのは「作れないこと」であって、保存済みの本文の見え方を黙って変えることではない。入口 4 が編集画面でそれを見せ、直すのは著者である。必要になれば 1 行で足せるが、そのときは `e2e/public-link-card.spec.ts` に自参照の題材が無いことから始める。
- **記事 ID で判定する** — 貼り付けられた URL が持っているのは slug だけで、ID を照らすには `/api/posts/search` の答えに ID を足して突き合わせることになる。入口 2 と 3 は slug しか手にしていない。
- **カードを消す・リンクに書き戻す** — 著者が書いたものを黙って別物にすることになる。§4.2 が「保存するのは参照だけ」と決めているのと同じ理由で、判断は著者に残す。

## 19. 選択済みのカードを本体で再クリックしても、選択は外れない（実測 2026-08-25、修正）

**決定**: 選択済み(リング表示)のリンクカードを、その箱の内側(タイトル下の余白を含む)でもう一度クリックしても、選択はそのカードのまま保たれる。

**機構**: 埋め込みと共有の穴で、`embed-requirements.md` §8.3 に機構と修正の全文がある。`block-drag-handle.ts`（このカードとも共有するファイル）が「リング済みのブロックを本体で再クリックする」操作を掴み直しとして扱い、ドラッグにならなかった場合の着地先を `Selection.near(posAtCoords(...).pos)` で決めていたが、atom には中身の位置が無いので、余白のクリックは境界の先— 次のブロック — に着地していた。修正は `finished.node.isAtom` のとき `NodeSelection.create` で選択を立て直す一箇所で、カードと埋め込みの両方に効く。

**受け入れ基準**: `e2e/editor-block-drag-handle.spec.ts`「a plain re-press on a ringed link card or embed keeps it selected」（`embed-requirements.md` E14 と同じ1本のテストが両方を測る）。

## 20. 挿入時の検索結果は記事の顔を出す（2026-09-01 実装）

**決定**: ピッカーの結果行が、記事のサムネイル・タイトル・カテゴリを出す。`draft` はタイトル文字列に連結せず「未公開」のバッジにする。

検索欄の下には、入力が埋め込みになるかカードになるかを言う 1 行が 2026-09-01 から 09-02 まで置かれていた。**今は無い** — あの 1 行の仕事は「この欄は埋め込みも作る」と知らせることだったが、対応 9 件のうち 2 件しか名乗れておらず、直すべきは説明文ではなく入口の名前だった。埋め込みはスラッシュメニューに自分の行を持つ（`embed-requirements.md` §24.1）。

**理由**: 行が出すものは既に全部来ていた。`/api/posts/search` は §13 以来サムネイルを返しており、カード本体はそれを描いているのに、**行はそれを捨ててタイトルだけを出していた**。著者は題名の一覧から選び、絵は選んだ後にしか見えない。§13 が「編集面と公開側が同じものを見せる」ために画像を入れたのと同じ理由が、選ぶ側にも要る。カテゴリは同じ列（`posts.category`）から来るので、`PostSearchResult` に 1 つ足すだけで、クエリは増えない。

**参考にした形から移さなかったもの**（§16 で高さを実測したのと同じサイトの挿入ダイアログ）:

- **モーダルにしない。** 挿入 UI をカードの中に置いたのは §5.2-2/§5.2-3 の決定で、理由は 2 つとも今も立っている — スラッシュメニューの先に 2 つ目の UI 機構を要らないこと、そして挿入を途中でやめた著者の手元に「未完成のカード」が見えたまま残ること。モーダルはどちらも手放し、フォーカスと Escape の面倒を自前で持つことになる（`popover-api-pitfalls` が並べている穴）。
- **「自分の記事 / 全記事」のタブは無い。** 単著のブログなので、全記事が自分の記事である。
- **「検索」ボタンは置かない。** 入力のたびに引いており、ボタンは 1 クリック増えるだけになる。

**機構**:

- 絵は `internalCardImage`（`lib/link-card-image.ts`）を通す。行はすべて自サイトの記事なので**どの行にも必ず絵がある**（§17 のハウスマーク）。1 行だけ枠が空くと壊れた画像に見えるうえ、行頭のタイトル位置が行ごとにずれる。
- **ボタンのアクセシブル名は `aria-label` で書いて固定する。** 行が 3 つのものを描くので、放っておくと名前が「タイトル 未公開 カテゴリ」になる。`e2e/editor-link-card.spec.ts` は `getByRole('button', { name: CARD_TITLE })` で行を掴んでおり、これは完全一致である。名前はタイトル（＋未公開）だけにし、カテゴリと絵は入れない。
- **カテゴリは `DEFAULT_CATEGORY`（`uncategorized`）のとき行ごと出さない。** 空欄の番人であって、誰かが選んだ分類ではない。
- 一覧の `max-height` は 12em から **16em** に上げた。行が 1 行の文字だった頃の 12em は 8.7 行を見せていたが、53.8px の行では 3.5 行にしかならない。16em は 4.75 行で、スクロールの存在を示す半端な 1 行は残る。

**実測（2026-09-01）**: ハウスマークの行だけが 109.8px で、実写の行は 53.8px だった。**原因は Tailwind Typography が `picture` にも `img` と同じ `margin: 2em 0` を当てていること** — `.link-card-result-image` の `margin: 0` はラッパーに届かず、flex アイテムの margin は行の高さに乗る。この行の 14px で 2×28px = 56px、差分と一致する。変異で確かめた: `margin: 0` だけで揃い、代わりに `display: block` や `line-height: 0` を置いても [54, 110] のまま赤になる。カード本体の画像がこれを踏まなかったのは §16.3 が絵をフローの外に出しているからで、ラッパーには押し合う相手が無い。

**ピッカーの横幅が 3 割強むだになっていた**（報告 2026-09-02、修正）。カードが自分の絵のために空けておく右の余白は `:has(img)` で付けていたが、この述語は**子孫のどの `img` にも当たる** — 行がサムネイルを持った瞬間、ピッカー状態でも余白が付き、そこには置かれる絵が無い。実測で 766px のカードに対し行は 460px、`min(16rem, 40%) + 1em` = 272px がまるごと空いていた。述語を `:has(.link-card-image)` に変える（カード自身の絵だけが持つクラスで、公開側の `rehype-link-card.ts` と NodeView の `setImage` が両方これを付ける。行の絵は `.link-card-result-image`）。修正後は行が本文列いっぱいの 732px になり、解決済みカードの 272px はそのまま残る。

**この変更が既存の spec を 1 本赤くした。** 4b（2 度目のクリックでカードが消えない）は行の箱から座標を取るが、行が 2.4 倍高くなったぶん一覧に収まらなくなり、`boundingBox()` は隠れた行にもそのまま答える — 返る点が行の上に無いので、クリックはどこか別の場所に落ちていた。spec 側に `scrollIntoViewIfNeeded()` を足した（人はスクロールしてから押す）。
