## 0. 前提 — 今どれだけ使われているか

2026-08-21 に `data/blog.db`（`-wal` ごとコピー。`sqlite-copy-needs-wal.md`）を見た結果、対象になりうる URL は id 36「テスト」の中にだけある:

| 形                                                             | 件数 | 今の姿                               |
| -------------------------------------------------------------- | ---- | ------------------------------------ |
| `<https://www.youtube.com/watch?v=hDPybQwAuVo>`                | 1    | 行に単独の autolink                  |
| `<div class="link-card" data-href="https://x.com/ClaudeDevs">` | 1    | 外部カード（解決できている — §10.1） |

どちらも需要の証拠ではない。 2 行は隣り合っており、外部カードの動作確認の並びの中に置かれている。`link-card-requirements.md` §0 が Zenn のリンクについて下した判定と同じ形で、**テストの残骸である**。実投稿での使用はゼロで、需要は測れていない。

この文書が書かれているのは需要が測れたからではなく、カード側が YouTube に対しては動かないと分かったからである（§9.1）。動かないものを放置するか、別の形を与えるかの選択が発生した。X はそれとは別の理由で入っている（§10）。

## 1. 目的と非目標

**目的**: 著者が外部サービスの URL を 1 クリックで埋め込みブロックに変えられる。読者は公開ページ上でそれを再生・表示できる。

**非目標**（この文書でも対象外）:

- **カードと埋め込みの両対応** — 1 つの URL に対して結果は 1 つである（§3.3）
- 再生・表示のオプションを著者が UI で設定すること（YouTube の開始時刻だけは URL から引き継ぐ — §9.3）
- サムネイルを出してクリックで本体に差し替える形（ファサード）。§8 で保留として記録する
- §9・§10 以外のプロバイダ。同じ機構で足せるが、本書は決めない
- **JSFiddle** — CodePen（単一ファイルのデモ）と CodeSandbox（複数ファイル・依存ありのデモ）で役割が揃っており、JSFiddle は前者と機能的に重なるだけで独自の役割を持たない。プロバイダ 1 つにつき mark・ペースト正規表現・NodeView・E2E 計測の固定コストがかかる（§14〜§17 の先例）ので見送る（2026-08-29）。既存記事の JSFiddle デモを救うなど個別の必要が出たら測り直す
- **Claude Artifacts** — 共有設定の影響を受けやすく、案内はリンクカードで足りる（2026-08-29）
- **Google Slides** — カードが題・説明・1 枚目のスライド画像を返すので、埋め込みが足すのは「その場でめくれる」の 1 点で、それに 1 本 82 リクエスト（`docs.google.com` に 69。SlideShare の 40 の倍で本書中最大）かかる。著者はログイン済み・読者は未ログインなので、**著者の画面では描画され、読者だけが壁を見る**状態が起こりうる — §14.6・§15.6・§16.6 が受け入れの根拠にした「著者は挿入した瞬間に同じものを見る」がここだけ成立しない。読者に PDF / PPTX ダウンロードと「エディタで開く」が出る点も他に例がない。Figma と同じ key 形（`/d/<ID>/embed`、取得なし、箱は `calc(56.25% + 36px)`）で足せること自体は実測済み（2026-08-29）。著者が自分のデッキを貼る記事が出たら測り直す

## 2. 出発点 — 本書を書き始めた時点で、これらの URL が何になったか（実測 2026-08-21）

| 行に単独で置いたもの | 「カードにする」を押すと | 公開ページ                     |
| -------------------- | ------------------------ | ------------------------------ |
| YouTube の動画 URL   | カードのノードになる     | **素のリンクに落ちる**（§9.1） |
| X の投稿 URL         | カードのノードになる     | **カードになる**（§10.1）      |

2 行の違いが本書の出発点である。 前者は押せてしまうのに結果が押さなかった場合と同じになり、後者は既に動いている。同じ「埋め込みたい」という要求でも、答えるべき問いが違う。

**今はどちらも埋め込みになる**（§9、§10）。X のアカウント URL だけがカードのままで、それは §10.4 の決定による。

## 3. 決定① — 埋め込みにするかどうかは、プロバイダごとに測って決める

手順を決める。プロバイダごとの答えは §9 以降に置く。

### 3.1 訊く順序

1. **そのサイトのカードは動くか**（`fetchLinkPreview` が題・説明・画像を返すか）を実測する
2. 動かないなら、埋め込みが唯一の選択肢である（§9 の YouTube）
3. 動くなら、**埋め込みがカードに対して何を足すのかを 1 行で言えるか**を訊く。言えないなら足さない（§10 の X はここを通った — 答えは §10.2）

**「動く」の基準は取得できることであって、見栄えではない。** カードが出る以上、埋め込みは追加の機能であり、追加の代償（§8）を正当化する差を名指しできなければならない。

### 3.2 埋め込みは取得を要求しない

これが埋め込みの構造上の利点で、プロバイダによらない。 参照は URL の文字列から解けるので、`link_previews` の行も、TTL も、`PREVIEW_VERSION` も、画像プロキシも要らない。`link-card-requirements.md` §14.1 が「読者のリクエストでは取得しない」と決めた線を自明に満たす — 取得という段が存在しない。`link-card-requirements.md` §14.3.1 が扱った「行が古いのではなく、行を書いた側が古い」種類の陳腐化も、保存するものが第三者の値の写しではないので発生しない。

### 3.3 カードと埋め込みの両対応は採らない

**選ばせるものが増えることのほうが代償である。** 動画に対して「カードにする」を押す理由を著者に説明できない。`link-card-requirements.md` §14.3 が手動リフレッシュ UI を非目標に置いたときの論法がそのまま当たる — 押せるものを増やすと、押さない場合の意味が変わる。

言及するだけで再生させたくない場合の逃げ道は、カードではなく素のテキストリンクである。 それは既にあり、何も足さずに使える。

## 4. 決定② — 保存形式は参照だけを持つ raw HTML。ノードは 1 つ

```html
<div class="embed" data-href="https://www.youtube.com/watch?v=hDPybQwAuVo&amp;t=90"></div>
```

`link-card-requirements.md` §4.2 と同じ形で、同じ理由による — ノードのシリアライザが raw で書くので `[` のエスケープを踏まず、`markdown-it` は `html: true`、公開側には `rehypeRaw` が既に居るので、両方向とも新しいパーサを足さずに通る。あちらの §4.1 の (b)（`@[youtube](url)` のような記法）が却下される理由も動かない。

**class は `link-card` と分ける。** ノードが 2 つある以上 `parseHTML` の照合も 2 つで、`div.link-card` と `div.embed` は互いに一致しない。往復の曖昧さがここで消える。

**プロバイダごとに class もノードも増やさない。** `youtube-embed` / `x-embed` と分ける形は採らない — §4.1 の通り、class を 1 語足すたびに `divClasses` を触る必要があり、しかもそこは足し忘れが静かに壊れる場所である。プロバイダは `data-href` から解けるので（§4.3）、属性にも持たせない。保存形式に現れる語は `embed` の 1 つで、プロバイダを足しても増えない。

**保存するのは ID ではなく、著者が渡した URL そのものである。** ID を抜いて属性に入れる形も考えたが、採らない:

- 付随する情報（YouTube の開始時刻など）が属性を増やす。URL 1 本ならその中に既に入っている
- 「リンクに戻す」（`link-card-requirements.md` §7-3 の `unsetLinkCard` に相当するもの）で戻す文字列が、著者が書いたものではなく再構成した正規形になる
- 抽出はどのみち両側でやることになる。**述語を 1 本共有する形は `lib/link-card-href.ts` に前例がある** — エディタが作れると言った埋め込みを公開側が拒む、という不一致だけが engineering する価値のある不一致である

したがって `lib/embed-provider.ts` を作り、`resolveEmbed(href): EmbedTarget | null` をエディタと `rehypeEmbed` の両方が訊く。`link-card-requirements.md` §14.2 が「鍵は保存された文字列そのものである」と決めたのと同じで、URL の正規化はしない。

### 4.1 sanitize スキーマに要ること

`embed` を **`lib/render.ts` の `divClasses` タプルに値として足す**。2 本目の `['className', …]` を `div` に足す形では書けない — `hast-util-sanitize` の `findDefinition` は名前が一致した最初の項目で返るので、2 本目は死んだままになる（`link-card-requirements.md` §4.3 が踏み済み）。

`dataHref` は `div` に対して既に許可されているので、属性側の変更は無い。足りないのは class 1 語だけで、**プロバイダを足してもここは二度と触らない**。落ちたときは中身の無い `<div>` になって黙って消えるので、触らずに済ませられることに意味がある。

公開側が出す `.embed-youtube` のようなプロバイダ別の class は、sanitize の後段で作られるので許可リストに載らない（§6）。**許可リストに載る語と、CSS が見る語は別物である。**

### 4.2 参照は解決側が検証する

`link-card-requirements.md` §4.4 の線がそのまま掛かる。`dataHref` は値の許可リストではなくただのプロパティ名なので、著者は `<div class="embed" data-href="javascript:…">` を手で書ける。そして解決段は sanitize の後ろに置くので（§6）、そこで組み立てる `iframe` の `src` は誰の検査も通らない。

**したがって述語は「妥当な形」の許可リストで書く。** 禁止したいものを並べる形にはしない:

- ホストは許可リスト。判定は `new URL()` に解かせる。文字列の前方一致は `java\tscript:` の類を取りこぼす
- ID はプロバイダごとの形（YouTube なら `/^[\w-]{11}$/`）。この形を通ったものだけが `src` に入る
- **`src` はこちらが組み立てる。** `data-href` の文字列が `src` になることは無い

壊れた percent-escape で例外を投げないこと（`link-card-requirements.md` §14.2.1 の ①）も同じ理由で要る。`rehypeEmbed` から投げた例外は記事のページごと 500 にする。解けなければ「該当なし」にする。

### 4.3 プロバイダはレジストリで足す

`lib/embed-provider.ts` が持つのはプロバイダの配列 1 本で、各要素は「ホストの許可リスト」「URL から `EmbedTarget` を作る関数」「`iframe` を組む関数」を持つ。`resolveEmbed` は先頭から訊いて最初に解けたものを返し、どれも解けなければ null を返す。

**プロバイダを足す作業は、ふつうはこの配列に 1 要素足すことである。** ノードも class も sanitize もエディタの入口も動かない。§4 と §4.1 が禁じている「増える語」を 1 か所に閉じ込めるための形である。

**動かないのは保存形式の側であって、`iframe` の組み方ではない。** `EmbedTarget` には 2026-08-29 に `srcdoc` と `sandbox` が加わり、そのとき両方の描画段（`lib/rehype-embed.ts` と NodeView）と、高さを受ける 2 面（`components/EmbedFrames.tsx` と NodeView の `onMessage`）が触られた — 保存されるものは何ひとつ変わらないまま、フレームの組み方と、フレームが喋るかどうかがプロバイダごとに違いうるからである。理由は §18.5（高さを知る手段が他に無い）と §18.6（第三者の markup を記事から隔てる）にある。

## 5. 決定③ — 入口は既存の 2 つ。行は増やさない

`link-card-requirements.md` §14.6 が作った 2 つの入口をそのまま使い、URL の形で結果が決まる:

1. **バブルの行**（`LinkBubble.tsx`）。`resolveEmbed` が解ければラベルが「埋め込みにする」になり、押すと埋め込みノードができる。解けなければ今まで通り「カードにする」
2. **ピッカーの検索欄**（`link-card-requirements.md` §5.2-3）。URL として解けたときに出る 1 行が、同じ規則でラベルを変える。カードのノードは埋め込みのノードに置き換わる。**この行は mousedown ではなく click で作用させる** — 行はカードの NodeView の中に居るので、mousedown で自分を unmount すると mouseup が document に落ち、キャレットが動いてノードごと持って行かれる（同じ部品で実測済みの経路。2026-08-18）

**バブルには 3 つ目の結果がある。** `github.com/…/blob/…` は埋め込みではなくコードブロックになり（§19）、この節の入口 1 に並ぶ。問う順序と「1 つの URL に意味は 1 つ」はそのままで、ピッカー（入口 2）は動いていない。

**行は 1 つのままである。** 2 行並べて選ばせる形は §3.3 で却下した理由により採らない — 1 つの URL に対して意味は 1 つになる。

**スラッシュメニューには足さない。** URL を持っていることが前提の機能なので、貼ってから 1 クリックのほうが短い。カードのピッカー経由でも届く（入口 2）。

**ペーストは引き金にしない。** `link-card-requirements.md` §14.6 が書いた 2 つ目の理由がそのまま当たる — 行に単独の URL を素のリンクとして貼る手段が無くなる。§0 の YouTube の 1 行が実際にその形である。

**置ける場所の判定は既存のものを訊く。** 挿入は `canPlaceAfterCaret`（`code-block-extension.ts`）、バブルからの置き換えは `parent.canReplaceWith(index, index + 1, type)`。`link-card-requirements.md` §14.6 が「同じ答えを出すが同じ問いではない」と書いた区別を、ここで取り違えない。

**新しいスライスガードは要らない**（実測 2026-08-31、基準 E15・E16）。埋め込みはカードと同じ block atom なので、`titleAcceptsSlice` と `carriesNonParagraphBlock` が、カードを覆っているのと同じ理由で覆う。どちらの述語も「この行き先は何を受け入れるか」の形で書かれていて、あとから足したブロックノードは名指しされずに覆われる。覆いが外れる条件は 1 つで、**埋め込みが inline になったとき**である — `titleAcceptsSlice` は inline atom を意図的に通すので（`docs/accordion-requirements.md` §6.5 がその問いを持っている）、そこが変われば `components/editor/embed-placement.test.ts` のスキーマの行が赤になる。ノード名を明示的に並べている箇所は `block-drag-handle.ts` の `DRAGGABLE_TYPES` だけで、そこには 1 行足す（`link-card-requirements.md` §7.2 と同じ理由 — `draggable: true` の atom も例外ではない）。

## 6. 決定④ — 公開側は sanitize の後段で組む

**`iframe` を sanitize スキーマに足すことはしない。** `lib/render.ts` は「非管理者も投稿を書くようになった以上、MDX 中の生 HTML は信頼しない」と明記していて、`<iframe>` はそこで名指しされている 3 つのうちの 1 つである。許可すれば、著者の書いた任意の `<iframe src>` が公開ページに載る。

代わりに `rehypeEmbed` を `rehypeLinkCard` と同じ位置——sanitize の後ろ——に置く。この段が組み立てるものは全部このパイプライン自身のマークアップなので、許可リストに載せる必要が無い（`rehypeLinkCard` と `rehype-pretty-code` が既にその位置に居る理由と同じ）。段は純粋で、注入する resolver を持たない — カードと違い、引く表が無い。

**第三者のスクリプトを自オリジンで走らせることはしない。** 出すのは `iframe` だけである。`<script src="…">` を公開ページに置く形の埋め込み（X の公式ウィジェットがこれである）は、sanitize が `<iframe>` を落とす理由よりさらに強い理由で採らない — スクリプトはこのサイトのオリジンで走り、`iframe` は走らない。プロバイダがスクリプトしか提供しないなら、そのプロバイダは埋め込みに対応しない。

`resolveEmbed` が null を返した参照は、公開側では**素のリンクに落ちる** — `link-card-requirements.md` §6.1 と同じ扱いで、行き先も同じである。 **そのリンクは新しいタブで開く** — 落ちてくる参照は `externalCardHost` を通った http(s) だけなので必ず外部であり、パイプライン最後の `rehypeNewTabLinks` が本文の外部リンクと同じ規則で `target="_blank"` を付ける（2026-08-21、`link-requirements.md` §7.2）。

### 6.1 素のリンクに落とす側も、公開されるマークアップである（2026-08-21、実装時に見つけた）

**`resolveEmbed` が null を返したことは「安全な参照である」を意味しない。** 最初の実装は、どのプロバイダも名乗り出なかった参照をそのまま `fallbackLink` に渡していた。`javascript:alert(1)` はどのプロバイダも名乗り出ないので、**この段が `<a href="javascript:alert(1)">` を組み立てた** — sanitize の後ろで、誰の検査も受けずに。

`lib/render.test.ts` の E2 を書いた最初の実行が赤にした。**出口は 2 つあり、両方が拒まなければならない**（iframe と、素のリンク）。塞いだのは `externalCardHost`（`lib/link-card-href.ts`）で、外部カードの参照が既に通っている検査そのものである — http(s)、解けること、資格情報を持たないこと。落ちたものはリンクにせず捨てる。`rehypeLinkCard` が同じ入力に対してやることと同じである。

**教訓は §4.2 の言い直しではなく、その範囲である。** あそこは「`src` はこちらが組み立てる」と書いており、それは守られていた。守られていなかったのは、**同じ段が `src` 以外のものも公開している**という事実のほうである。

## 7. エディタでの見え方

NodeView は**公開側と同じ `iframe` を出す**。別物（静的なプレースホルダ）を出すと、何を貼ったのかが編集中に分からない。

**`iframe` はポインタイベントを飲む。** ドラッグハンドルも範囲選択も、`iframe` の上では反応しない。ノードが選択されていない間は `pointer-events: none` を掛け、クリックでノード選択に入ってから操作を許す。**クリックは frame に当たり、frame は NodeView のものなので ProseMirror が NodeSelection を作る** — その選択がプレーヤーにポインタを渡す、という順序である（実測 2026-08-21、`e2e/editor-embed.spec.ts`）。

操作ボタン（削除・リンクに戻す）はカードと同じくブロック上端の固定帯に置く（`link-card-requirements.md` §7.1）。カードと同じ理由でキャレットは中に入れない（`atom: true`）。

### 7.1 アコーディオンのタイトルは拒む対象ですらない（2026-08-21、実装時に分かった）

基準 E7 は当初「表のセル・アコーディオンのタイトルには挿入できない」と書いていた。**タイトルのほうは測れない。**

`detailsSummary` の内容は `marks: ''` で定義されている（`components/editor/details-extension.ts`）ので、**タイトルにはリンクが存在しえない**。入口 2 はキャレットのあるリンクから始まるものなので、そこにバブルは出ず、拒むべき操作が発生しない。

**したがって E7 が測るのは表のセルとリスト項目の先頭である。** どちらも `canReplaceWith` が答え、後者は `link-card-requirements.md` §14.6 が「リスト項目が頭を失う」として一度支払った形である。タイトルの側は、置ける場所の判定ではなく**スキーマがそこまで届かせない**という別の機構で閉じている。

### 7.2 ブロックは枠に入る（2026-08-21 決定）

**決定: エディタの埋め込みは 1px `#d0d7de`・6px の枠に入り、プレーヤーはその内側の padding の中に置く。公開側は枠を持たない。**

**枠は帯のためであって、プレーヤーのためではない。** 枠が無いと「リンクに戻す」が全幅の黒い矩形の上に浮き、どのブロックのものかを言う線が 1 本も無い。埋め込みは atom で、クリックすればブロック全体が選択されるので、どこで終わるのかは著者が見えている必要がある。枠そのものは他の 3 つのブロック構造（アコーディオン、コードブロックのカード、リンクカード）が既に持っているものと同じで、4 つ目も自前の色を増やさない。

**同じ枠を、解決できない参照の状態にも使う。** 以前は `.embed-unresolved` だけが枠を持っており、**ブロックが壊れているときにだけ輪郭を得る**という逆の形になっていた。今は 2 つの状態が 1 つの箱を共有する。

非選択状態で 3 案を描いて比べた（2026-08-21）:

| 案                            | プレーヤーの幅      | 見え方                              |
| ----------------------------- | ------------------- | ----------------------------------- |
| 枠なし                        | 公開と同じ          | 帯が浮く                            |
| **枠 + 内側 padding（採用）** | 公開より 1.5em 狭い | 帯とプレーヤーが 1 つの箱に入る     |
| 枠 + フレームが枠に接する     | 公開と同じ          | 帯が枠内の 1 行、その下にプレーヤー |

**3 つ目は設計としては優れている** — プレーヤーの幅が公開ページと変わらず、角丸も二重にならず、`link-card-requirements.md` §15 が画像について下した判断（枠いっぱいに出す）と同じ形である。**採らなかったのは見た目の判断による**（2026-08-21）。

**引き受ける代償**: エディタのプレーヤーは公開ページより padding 2 つぶん狭く、角丸は外枠とフレームで二重になる。§7 の「著者が見ているものが読者が得るもの」は、比率・中身・位置については保たれ、**幅については保たれない**。

### 7.3 バブルの「埋め込みにする」のアイコンはプロバイダで変わる（2026-08-24 決定）

**決定**: YouTube のリンクには枠 + 再生三角（`PLAY_SHAPES`）、X の投稿には X のモノグラム（`X_MARK_SHAPES`）を出す。プロバイダが増えたときの既定は `PLAY_SHAPES` のままで、ロゴを足すかはその都度決める。

**どちらを出すかは `embedMarkShapes` が 1 か所で答える**（`components/editor/svg/icon-shapes.ts`）。訊く側が 2 つあるからで、バブルのボタンと §10.10 のドラッグのゴーストが同じ問いを持つ。図形もそこに置いてある — JSX と素の DOM の両方が読むため（`buildIcon` / `IconSvg`）。2026-08-24 に §10.10 を入れたとき、それぞれが自前の絵を持つ形から移した。

**理由**: `CardIcon` が自分のファイルに「押すと何ができるかを、名前ではなく縮図で見せる」と書いているのと同じで、枠 + 再生三角は公開ページの YouTube プレイヤーの縮図である。X の投稿でできるのは文字の箱なので、同じ絵は再生できるものがあると言っていることになる。ボタンは 2 つが同時に出ることが無いので（§5）、カードと弁別するためにこの絵が要るわけではない。

**X のマークだけが枠を持たない。** 16px 表示（`h-4 w-4`）では枠の内側に 24 の viewBox で約 8 単位 ≒ 5 実ピクセルしか残らず、字形はそこに入らない。「同じ枠で、中身だけが違う」というこのセットの規則と、字が読めることは両立しないので、後者を採った。塗りであることも他と違う（`fill='currentColor'` + `stroke='none'`）— セット既定の `fill='none'` + `strokeWidth={2}` のままだと、字の輪郭だけが 2px で描かれて潰れる。

**第三者のマークをアイコンセットに入れることについて**: 著者側の面に相手先のマークが出るのは前例がある（`link-requirements.md` §5.5.8 — 同じバブルがリンク先の favicon を出す）。`link-card-requirements.md` §17 が却下したのは公開ページの話で、ここには当たらない。こちらはバンドル済みの静的な図形なので、要求は 1 本も飛ばない。**代償は改称で古くなることで、`twitter` → `X` で一度起きている。**

## 8. 引き受ける帰結（プロバイダによらない）

**① 読者のブラウザは第三者に要求を出す。** これは `link-card-requirements.md` §14.4 がカードの画像で避けたこと（ホットリンクをせず自分のプロキシを通す）を、埋め込みでは避けられないという意味である。埋め込みという機能の代償であって、実装の粗さではない。

サムネイルを出しておいてクリックで `iframe` に差し替えるファサードはこれを消せる。ポスター画像を `/api/link-image` の署名付きプロキシ（`link-card-requirements.md` §14.4）に通せば、読者が選ぶまで第三者への要求はゼロになり、公開ページ側のクライアント JS は `CodeCopyButtons` と同じ形で足せる。**採るかどうかは保留する** — 読み込み方の話であって、著者から見た意味（この URL は埋め込みになる）を変えないので、後から独立に足せる。

**② `iframe` の名前は総称になる。** 取得をしない以上、中身の題は手元に無い。`title="YouTube 動画"` の類は読み上げに対して「何の動画か」を答えない。題を 1 つ得るために取得を戻すと、表・TTL・版・失敗時の扱いの一式が戻ってくるので、割に合わない。周囲の本文が対象を紹介しているのが普通の書き方であるという前提に乗る。

### 8.1 `iframe` はページのマウスイベントを飲む（実測 2026-08-25、修正）

**決定**: ブロックドラッグが動いている間、埋め込みの `<iframe>` はヒット対象にならない（`body.block-dragging .embed-frame iframe`、`app/globals.css`）。

**機構**: ブロックドラッグはネイティブの HTML5 ドラッグではなく、window の `mousemove` で駆動している（`createDragController`、`components/editor/block-drag-handle.ts`）。`<iframe>` はポインタを飲む — 上を通っている間、親ページには **1 件も届かない**。実測: 同一オリジンのフレームを跨いで 32 回動かして親の受信は 0 回、`pointer-events: none` を付けると 32/32 に戻る。`mouseup` も同じく飲まれる。

著者に見えるのは、**ゴーストが箱の上で止まり、ドロップ位置の線が答えなくなる**という形である。そこでボタンを離しても離した瞬間は誰も知らないので、セッションは生きたまま残り、次にフレームの外へ動いたときの `event.buttons === 0` で `endSession()` に落ちる — つまり**ドロップは適用されずに捨てられる**。

**穴は「掴んだ埋め込み自身」だった。** フレームは静止時すでに不活性で（`.prose .embed-view .embed-frame iframe`、§7）、だから他のブロックを埋め込みの上で運ぶ経路は最初から無事だった。ただし `.ProseMirror-selectednode.embed-view` の側が、選択中のブロックにはポインタを返している — そして**ブロックを掴むという操作が、そのブロックを選択する操作そのもの**である。ドラッグ中に確実に生きている埋め込みは、いつでも「今ドラッグしているそれ」であり、ポインタは掴んだ直後にその箱へ入る。実測（修正前）: X の埋め込みをハンドルで掴むと、自分の 550x249 のフレームが `pointer-events: auto` のまま残っていた。YouTube でも同じ形になる。

**JS ではなく CSS で切る。** 掴んだ時点で `querySelectorAll('iframe')` を回す形は、ドラッグ中に解決してフレームを差し込む埋め込みを取りこぼす。`postMessage` には触れないので、高さの受け渡しと沈黙時計（§10.5）は前と変わらない。

**この節はネイティブドラッグの経路を含まない。** 枠の付いていないカード・埋め込み・画像を本体から押した場合は prosemirror-view 側のドラッグが立ち上がり、`body.block-dragging` は付かない。そちらの `dragover` とドロップカーソルが同じ `iframe` の盲点を持つかは**未測**である（§12）。

### 8.2 箱の右側の余白は、埋め込み自身のクリックとして扱う（実測 2026-08-25、修正）

**決定**: カラムより狭い埋め込みの箱（今日は X の埋め込みだけ、§10.9）の右側、同じ行の余白をクリックすると、その埋め込みが選択される。

**機構**: 箱は `max-width` で止めてあるので、その右側は `.embed-view` にもフレームにも属さない — カラムそのものの背景である。実測: そこをクリックすると `document.elementFromPoint` は `view.dom`（`.ProseMirror` 自身）を返し、`.embed-view` にもフレームにも当たらない。ProseMirror はそのままブラウザの caret-from-point 探索に落ち、直下の段落など**別のブロックへキャレットが飛ぶ**。埋め込みを選択済みかどうかは無関係で、未選択の状態から直接同じ座標をクリックしても同じ結果になる。

修正は `embed-extension.ts` の `addProseMirrorPlugins()` に足したプラグイン一つ（`handleDOMEvents.mousedown`）。`event.target === view.dom` のときだけ動き、ドキュメント直下の子を一巡して `embed` ノードのうち `clientY` がその DOM 矩形の縦域に入り、かつ `clientX` がその左右の外にあるものを探す。見つかれば `preventDefault` した上で `NodeSelection` をその位置に立てる。**プロバイダ名では判定しない** — 矩形がカラム幅まで届く埋め込み（YouTube、未解決の note 状態）はこの条件に最初から当たらないので、狭いのがどのプロバイダかをこちら側が知る必要がない。

**箱の外の余白だけを閉じている。** リンクカードの箱の中(タイトル下の余白など)を再クリックしたときの穴は別物で、§8.3 が閉じる。

### 8.3 リング済みの箱を本体で再クリックしても、選択は外れない(実測 2026-08-25、修正)

**決定**: 選択済み(リング表示)のリンクカード・埋め込みを、その箱の内側(タイトルや枠の下の余白を含む)でもう一度クリックしても、選択はそのブロックのまま保たれる。

**機構**: リング済みのブロックを本体でクリックし直す操作は、`block-drag-handle.ts` の `handleDOMEvents.mousedown` が「ハンドルを掴んだのと同じ」掴み直しとして拾う(`selectedHandledBlock` が現在の選択と一致する top-level ブロックを返し、`dom.contains(event.target)` が真になる)。ドラッグ閾値(4px)を越えずに離した「実質クリック」は `DragController.handleMouseUp` の `!finished.dragging` 分岐に落ち、`placeCaretAt(clientX, clientY)` が `view.posAtCoords` の `pos` を `Selection.near` に渡してキャレットを立てる — これは中身のあるブロック(引用ブロックなど、`e2e/editor-block-drag-handle.spec.ts` の「a plain click inside a ringed block lands the caret in it」が守る形)には正しい答えだが、**atom には中身の位置が無い**。実測: カード/埋め込みの箱の中で、タイトルやプレイヤーの実体の外(空白の余白)をクリックすると、`posAtCoords` は箱の**境界**位置を返し、`Selection.near` はその境界の先にある一番近い実テキスト — 次のブロック — を選ぶ。選択済みかどうかは無関係で、未選択の状態から直接そこをクリックしても同じ結果になる(§8.2 の余白の穴と同じ形だが、箱の外ではなく内側で起きる点が違う)。

**修正**: `handleMouseUp` の `!finished.dragging` 分岐で、`finished.node.isAtom` のときは `placeCaretAt` を呼ばず、`NodeSelection.create(view.state.doc, finished.from)` で選択を立て直す。atom は中身の位置を持たないので、その箱の中への素クリックが意味しうる答えは「このブロックを選択したままにする」の一つしかない — 実体(カードのタイトルなど)の上のクリックは、ドラッグセッションが始まる前に ProseMirror 自身の leaf-click 処理で解決しているので、ここには最初から届かない。

**受け入れ基準**: E14。

### 8.4 ブロックを並べ替えるとフレームは作り直される（実測 2026-08-31、引き受け）

**決定**: エディタでブロックを動かすと、飛び越された埋め込み、または運ばれた埋め込み自身の `<iframe>` が作り直され、読み込みが最初からやり直される。**直せることを測ったうえで、直さない。**

**機構**: prosemirror-view（1.41.9）の子ノード同期は前方一方向の一巡で、既存の desc を後ろから前へ動かす経路を持たない。移動したブロックの desc を再利用するには手前にある desc を捨てるしかなく、`destroyBetween` がそれをする（`findNodeMatch` と `updateNextNode` の両方が呼ぶ）。破棄された NodeView の代わりに作られるのは新しい `<iframe>` 要素であり、`iframe` を DOM から外すとブラウジング文脈がそこで消える。**§7 の NodeView が持つ 2 つのガードは効かない** — `iframe.src !== src` も `showing !== 'player'` も `update` の経路だけを守るもので、destroy → create はそこを通らない。

**測ったこと**（`.embed-view iframe` に印を付け、ドラッグ後も同じ要素かを見る）:

| 操作                             | 作り直されるもの     |
| -------------------------------- | -------------------- |
| 下のブロックを埋め込みの上へ移動 | 飛び越された埋め込み |
| 上のブロックを埋め込みの下へ移動 | 運ばれたブロック自身 |
| 埋め込みの上の段落で入力         | 何も起きない         |

**プロバイダによらない。** 同じ操作を Figma と YouTube で測って結果は同一である。目に付きやすいのは読み込みの重い Figma だが、機構にプロバイダは入っていない。

**答えるプロバイダは高さを言い直す**（実測 2026-08-31、基準 E17）。作り直しは `answered`・`visible`・沈黙時計をすべて初期化するので、作り直された箱は初回の読み込みと同じ道をもう一度通る — 新しい NodeView が新しい `instanceId` を `src` に焼き、フレームがその名前で答え、高さが戻り、再武装された時計は誤爆しない。**失われるのは読み込みの数秒だけで、投稿が「取得できない」に化けることはない**、というのがこの節が「引き受ける」と言える根拠である。X で測った。gist は同じ経路に乗るがエディタの中では測れない（§18.6）。

**ドラッグハンドルのウィジェット装飾は原因ではない。** `WidgetType.eq` は `spec.key` が無くても `toDOM` の同一性と `compareObjs(this.spec)` で一致するので、安定した `handleToDOM` と `{ side: -1 }` は毎回マッチする。`block-drag-handle.ts` の「装飾に key が無いので desc が作り直される」というコメントはドラッグ中のブロック自身について測ったものであって、一般には成り立たない。

#### 直せる形と、採らない理由

`Element.moveBefore()`（状態保存アトミック移動）は `iframe` の文脈を保つ。実測 2026-08-31、Chrome 151: `appendChild` で入れ直すと `load` が 2 回走り中に置いた印は消えるが、`moveBefore` では `load` は 1 回のままで印が残る。`display: none` の接続済みの保管所へ預けて戻しても、預けている間に元の親を `remove()` しても残る。NodeView の `destroy` で預けて次の NodeView で引き取る形は、したがって成立する。

ただし **未接続の親への `moveBefore` は `HierarchyRequestError` で落ちる**。ProseMirror は新しい NodeView の `dom` を未接続のまま作り、一巡の最後に挿す（`renderDescs`）ので、引き取りは一巡の後へ遅らせ、かつ新しい `iframe` は `src` を持たせずに組む必要がある。

**採らない。** 失われるのは数秒の読み込みだけで、起きるのは著者だけが見る面であり、公開ページは並べ替えを起こさないので読者には出ない。対して park & adopt はエディタ外の常設の保管所・引き取り手の付かなかったフレームの回収・`instanceId` の引き継ぎ（X と gist は id を `src`／`srcdoc` に焼き込む。Figma は使わない）・ブラウザ分岐の一式であり、**壊れたときの症状は「隠れた保管所でフレームが鳴り続ける」**という、今の症状より診断しにくい形になる。`moveBefore` の無い環境ではフォールバックが現行の挙動なので、この節はどのみち仕様として残る。

**prosemirror-view が `moveBefore` を採っても直らない。** 破棄されているのは DOM ではなく desc であり、上流が DOM の移し方を変えても NodeView の destroy → create は変わらない。

## 9. YouTube（2026-08-21 決定）

**決定: 埋め込みにする。カードは提供しない。** §3.1 の手順の 2 に当たる — カードが動かないので、埋め込みが唯一の選択肢である。

### 9.1 カードが動かないことの実測（2026-08-21）

`https://www.youtube.com/watch?v=hDPybQwAuVo` を `fetchGuarded` と同じ形（`Accept: text/html`、`redirect: 'manual'`）で取得した:

| 見たもの                                                                 | 値                                 |
| ------------------------------------------------------------------------ | ---------------------------------- |
| 応答                                                                     | 200 / `text/html` / 265ms / 1.19MB |
| `og:title` のバイト位置                                                  | 693,270                            |
| `<title>` のバイト位置                                                   | 690,464                            |
| `MAX_BYTES`（64KB、`lib/link-title.ts`）の内側にある `<title>` と `meta` | **1 つも無い**                     |

YouTube は head のメタデータの前に約 690KB のインライン JS を置く。`fetchPageHtml` は `readCapped` で 64KB を切って渡すので、**`fetchLinkPreview` は YouTube に対して null を返す**（ここまで実測）。その先は文書と実装を読んだ結果であって実測ではない: `resolveLinkPreview` が `status='failed'` の行を書き、`rehypeLinkCard` があちらの §6.1 の通り素のリンクに落とす。この失敗の形そのものは `link-card-requirements.md` §14.13 に記録した。

**カードを動かす手は 2 つあり、どちらも安くない。** 64KB の上限は意図的な防御なので、1 サイトのために動かすのは防御の側を壊す。もう 1 つは YouTube 専用の取得で、oEmbed（`https://www.youtube.com/oembed?url=…&format=json`）なら 1.2KB / 214ms で題・投稿者・サムネイルが返る（実測 2026-08-21）が、説明文は無く、§3.2 が消した機構が全部戻ってくる。

### 9.2 受け付ける URL の形

**ホストの許可リスト**: `www.youtube.com` / `youtube.com` / `m.youtube.com` / `youtu.be`。

| 形                         | ID の出どころ  |
| -------------------------- | -------------- |
| `youtu.be/<ID>`            | パスの 1 段目  |
| `youtube.com/watch?v=<ID>` | `v` パラメータ |
| `youtube.com/shorts/<ID>`  | パスの 2 段目  |
| `youtube.com/live/<ID>`    | パスの 2 段目  |
| `youtube.com/embed/<ID>`   | パスの 2 段目  |

**この 5 つが同じ 1 本の動画を指すことは、YouTube 自身が言っている**（実測 2026-08-21、`redirect: 'manual'` で `Location` を読んだ）:

| 要求                               | 応答                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| `youtu.be/hDPybQwAuVo`             | 303 → `www.youtube.com/watch?v=hDPybQwAuVo&feature=youtu.be`      |
| `youtu.be/hDPybQwAuVo?t=90`        | 303 → `www.youtube.com/watch?t=90&v=hDPybQwAuVo&feature=youtu.be` |
| `m.youtube.com/watch?v=…`          | 302 → `www.youtube.com/watch?app=desktop&v=…`                     |
| `youtube.com/watch?v=…`            | 301 → `www.youtube.com/watch?v=…`                                 |
| `youtube.com/shorts/…`             | 303 → `www.youtube.com/watch?v=…`                                 |
| `youtube.com/live/…`               | 200                                                               |
| `www.youtube.com/embed/…`          | 200                                                               |
| `www.youtube-nocookie.com/embed/…` | 200                                                               |

**この表は根拠であって、機構ではない。** 実装はリダイレクトを追わない — 取得を 1 本も出さないことが §3.2 の要点なので、ID は文字列から取る。表が言っているのは、どの書き方も同じ ID を含んでいるという 1 点である。

`www.youtube-nocookie.com` と `music.youtube.com` は**入力としては受けない**。実投稿での出現は測れておらず、許可リストは狭いほうから始める。出力側では前者を使う（§9.5）。

### 9.3 開始時刻は引き継ぐ

`?t=` / `?start=` があれば `iframe` の `start=<秒>` に写す。**著者が書いた「その瞬間」を黙って捨てない。**

受ける形は `90`・`90s`・`1h2m3s`（`h`/`m`/`s` は各々省略可）の 3 つで、いずれも秒の整数に直す。それ以外は開始時刻が無いものとして扱う — 解釈に自信の無い文字列を `src` に載せるより、頭から再生するほうが安い。`youtu.be/<ID>?t=90` の 303 が `t=90` を運んでいることは §9.2 の表で測ってある。

### 9.4 埋め込まない形

**`?list=`（`v=` の無いもの）・`/playlist`・`/@handle`・`/channel/…`・`/user/…` は埋め込まない。素のリンクのままにする**（2026-08-21 決定）。いずれも単一の動画を指さない。プレイリストの埋め込みは `src` も述語も別物（`/embed/videoseries?list=`）になるので、要るときは別の決定として足す。

**`watch?v=<ID>&list=…` は動画として埋め込む。** `v=` が解ければ動画であり、`list` は捨てる。

### 9.5 出す markup

```html
<div class="embed embed-youtube">
  <iframe
    src="https://www.youtube-nocookie.com/embed/<ID>?start=<秒>"
    title="YouTube 動画"
    loading="lazy"
    referrerpolicy="strict-origin-when-cross-origin"
    allow="accelerometer; clipboard-write; encrypted-media; gyroscope; picture-in-picture; web-share"
    allowfullscreen></iframe>
</div>
```

- **`youtube-nocookie.com` を使う**（`/embed/<ID>` が 200 を返すことは §9.2 の表で実測）。要求そのものは消えないが、消せるものは消しておく
- **`loading="lazy"`**。折り返しより下の埋め込みは、読者がそこまで巻くまで要求を出さない
- 枠は CSS の `aspect-ratio: 16 / 9` で持つ。`width`/`height` 属性は置かない

### 9.6 縦向きの動画は 16:9 の箱に入る

Shorts かどうかは URL からは分からず、`/shorts/<ID>` は 303 で `watch?v=` に化ける（§9.2 の表）。左右に黒帯が出る。比率を知るには取得が要るので、ここでは取らない。

## 10. X（2026-08-23 決定）

**アカウントはリンクカード、投稿は埋め込みにする。** §3.1 の手順の 3 を通った答えである。カードは動いているが、カードが出すのはアカウントであって投稿ではない（§10.1 の表）。

これは §3.3 が却下した両対応ではない。あちらが却下したのは 1 つの URL に対して著者に選ばせる形で、ここで分かれるのはプロフィール URL と `/status/<ID>` という別々の URL である。§5 の「URL の形で結果が決まる」がそのまま当たり、1 つの URL に対する意味は 1 つのままである。

### 10.1 カードは動いている（実測 2026-08-21）

`https://x.com/ClaudeDevs/status/2089798442306711646` を `fetchGuarded` と同じ形で取得した:

| 見たもの                | 値                                 |
| ----------------------- | ---------------------------------- |
| 応答                    | 200 / `text/html` / 172,963 バイト |
| `og:title` のバイト位置 | **3,830**（`MAX_BYTES` の内側）    |
| `twitter.com/...`       | 301 → `x.com/...`                  |

`link_previews` にも `status='ok'` の行が 2 本ある（プロフィールと投稿の両方）。**YouTube と違い、X はカードとして完成する。**

カードに出るもの:

| 枠       | 中身                                                                        |
| -------- | --------------------------------------------------------------------------- |
| タイトル | `ClaudeDevs (@ClaudeDevs) on X`（**アカウント名であって投稿の題ではない**） |
| 説明     | 投稿の本文（`DESCRIPTION_MAX_LENGTH` の 200 字で切れる）                    |
| 画像     | **アカウントのアイコン**（`pbs.twimg.com/profile_images/…_400x400.png`）    |
| 出所     | `x.com`                                                                     |

### 10.2 埋め込みが答える差は 2 つだけである

上の表から、**埋め込みでしか埋まらない差は 2 つに絞れる**:

1. **投稿に付いた画像・動画がカードに出ない。** `og:image` はアイコンなので、写真付きの投稿とテキストだけの投稿が同じ絵になる
2. **本文が 200 字で切れる**

これが §3.1 の手順の 3 が要求する「1 行」である。**答えは URL の形で分かれる** — カードの `og` が出すのはアカウントなので（§10.1 の表）、プロフィールには正しく、投稿には誤っている。投稿だけを埋め込みにすれば 2 つの差は埋まり、アカウントはカードのままでよい。

### 10.3 測った結果（実測 2026-08-23）

§10.2 の 1 行が言えたので、残りは実装できるかどうかだった。Playwright と system Chrome で、親に `widgets.js` を置かない素のページから測っている。

- **投稿は描画される。** `https://platform.twitter.com/embed/Tweet.html?id=<ID>` は、親がスクリプトを何も持たなくても投稿を出す（`article` 2 個・本文テキスト・画像 4 個）。`?id=` だけの素の形と `widgets.js` が組む全パラメータ付きの形で結果は同じで、走る JS は全て `platform.twitter.com` の中に留まる。§6 の「第三者のスクリプトを自オリジンで走らせない」を満たす
- **高さは自己申告される。** §10.5 の機構で受け取れる。§9 に無かった機構が要ることは変わらないが、成立することは測れた
- **安定性の階級は YouTube と違ったままである。** `/embed/<ID>` は YouTube が公開している入口だが、`platform.twitter.com/embed/Tweet.html` は `widgets.js` が内部で組み立てる URL であって、文書化された契約ではない。動くことは測れても、契約であることは測れない。**この 1 点だけは実測で消えないので、§10.6 のタイムアウトで有界にする**

読者のブラウザが出す要求は**埋め込み 1 枚あたり 14〜16 本**で、宛先は 4 ホスト（`platform.twitter.com`・`cdn.syndication.twimg.com`・`syndication.x.com`・`pbs.twimg.com`）。`loading="lazy"` は総数を減らさず時期をずらす。記事側のメインスレッドは巻き込まれない — Chrome のサイト分離で別プロセスに入るためで、埋め込み自身が軽いという意味ではない。§8-① が引き受けている代償の、X での規模がこれである。

### 10.4 受け付ける URL の形

`/<handle>/status/<ID>` と `/i/status/<ID>`。ホストは `x.com`・`www.x.com`・`twitter.com`・`www.twitter.com`・`mobile.twitter.com`。

ID は `/^\d{1,19}$/` で検証し、**この形を通ったものだけが `src` に入る**（§4.2）。ハンドルの区間は `[^/]+` のままにする — X のハンドル規則を写すと規則が変わったときにこちらが古くなり、しかも `src` に入るのは ID だけなので、ハンドルを厳しく見ても守るものが無い。

`src` には `lang=ja` を添える。変わるのはウィジェットの UI の言語だけで（`Follow` が「フォローする」になる）、投稿の中身には影響しない（実測 2026-08-23）。

**それ以外の同ホスト URL は埋め込みにならない。** プロフィール URL・リスト・検索結果はどれも `resolveEmbed` が null を返し、`normalizeCardHref` に落ちてカードになる。§10 の決定のうちアカウント側はこの落ち方そのもので、足すコードは無い。

### 10.5 高さは postMessage で受ける（実測 2026-08-23）

`iframe` は `e.origin === 'https://platform.twitter.com'` から JSON を送ってくる:

```
{"twttr.embed":{"jsonrpc":"2.0","method":"twttr.private.resize",
  "id":"<embedId>","params":[{"width":550,"height":473,"data":{"tweet_id":"…"}}]}}
```

順序は `twttr.private.initialized` → `results` → `resize` → `rendered`。実測で分かった性質が 3 つある:

1. **`embedId` を渡さないと、ページ上の全 `iframe` が `embed-0` を名乗る。** 別々の投稿の 2 枚が同じ id で resize を送るので、親が振り分けられない。したがって**インスタンス id は描画段が発行する** — `resolveEmbed` は参照から決まるものだけを返し、id は `rehypeEmbed` と NodeView が 1 枚ごとに作る。§4.3 のレジストリ契約は動かない
2. **視界の外では送られてこない。** `iframe` の中では投稿が正しい高さで描画済みなのに、可視になるまで resize が出ない（headless・headed の両方で同じ）。**高さの確定は読み込み時ではなく、読者がその埋め込みまでスクロールした時である**
3. **幅を変えると再送される。** 最初の 1 通で聞き終えることはできない

初期高さは 250px にする。実測した高さは 550px 幅で次の 5 件で、文字だけの 3 件はこの近辺に集まる:

| 投稿 ID               | 高さ |                                    |
| --------------------- | ---- | ---------------------------------- |
| `20`                  | 225  | 最古の投稿。消える見込みが最も低い |
| `1234567890`          | 225  | 2009 年                            |
| `987654321`           | 249  |                                    |
| `2089798442306711646` | 473  | §10.1 で測ったもの                 |
| `2091079277710397784` | 624  | 画像 2 枚付き。実測 2026-08-24     |

**画像付き投稿を x.com 本体の詳細ページと比べても、公開ページのほうが縦幅が大きいとは言えない**（実測 2026-08-24）。`2091079277710397784` を両面で開くと、公開ページの埋め込みは 624px（550px 幅）、x.com 本体の同じ投稿は 694px（566px 幅）だった。x.com 側が高いのは、本文を省略せず全文出すのに対し、こちらの埋め込みは既定で本文を「さらに表示」の手前で切るからである — 見えている情報量そのものが違う。動画付き投稿と、x.com のタイムライン表示（詳細ページではなく一覧上のカード）を比較対象にした場合はまだ測っていない。

**箱が飛ぶことは受け入れる。** Zenn も Qiita も同じ postMessage 方式で飛びを回避しておらず、Qiita のリンクカードは `height="29"` から 112 へ飛ぶ（実測 2026-08-23）。§9.6 の固定箱にはしない — 幅が変われば正しい高さも変わるので、携帯の幅で固定値は成り立たない。

### 10.6 取得できない投稿は素のリンクに落とす

削除済み・非公開・存在しない ID では `twttr.private.no_results` が来て、resize も rendered も来ない。そして **`iframe` の中身は空である** — 実測した 3 件はいずれも `body.innerHTML` が 122 バイトの空シェルで、テキストも `<a>` も無く、背景は透明だった（2026-08-23）。読者には記事の地の色がそのまま見え、著者が書いた参照は URL すら残さずに消える。`fallbackLink` のコメントが「誰にもデバッグできない結末」と呼んでいる状態である。

失敗側の実例を 2 つ残す。**この 2 つは落ちる層が違う。** `99999999999999999999` は 20 桁なので §10.4 の述語に弾かれ、ネットワークに出る前に落ちる（基準 X4）。`1878330297005854930` は述語を通るが X が返せず、`no_results` で戻ってくる（基準 X5）。

**したがってクライアント側の差し替えは任意ではない。** 公開側が出すものは `rehypeEmbed` の `fallbackLink` と同じ素のリンクで、**その markup は 1 本の関数から出す。**

揃えるのは 1 つの面の 2 経路である（2026-08-23、実装に入って範囲を絞った） — 描画時に `rehypeEmbed` が組んだリンクと、`no_results` を受けてクライアントが組んだリンクが、読者から見て同じものでなければならない。**`rehypeNewTabLinks` は build のパイプラインで走るので、クライアントが組むほうは `target="_blank"` を自分で付ける**（あちらの規則 1 は `http(s)` を見るだけで、埋め込みの参照は必ず該当する。`rel` は付けない）。

**エディタは 3 つ目の面であって、リンクは出さない。** 解決できない参照に対してエディタが `embed-note` で著者に告げることは §7.2 で決まっている。取得できない投稿も著者が直せる参照なので、同じ扱いにする — 読者に劣化した形を見せる面と、著者に何が起きたかを告げる面は別である。

落とす引き金は 2 つある:

1. `no_results` を受けたとき
2. **可視になってから 8 秒、resize も `no_results` も来ないとき。** 起点は読み込み時ではなく可視時でなければならない（§10.5 の 2）— 読み込み起点にすると折り返しより下の埋め込みが全て誤爆する。余裕は実測の約 7 倍で、resize の到達は cold で 1088ms、可視化からは約 600ms である

**差し替えは一方向である。** リンクに落とした後に届いた resize は適用しない。`iframe` を残してリンクを併置する形も採らない — 同じ失敗が読者に 2 通りで見える。

**答えは時計を止める。逆に、聞くのはやめない**（2026-08-23、実装時に基準 X6 が捕まえた）。resize が届いた埋め込みはもう「黙っている」候補ではないが、幅が変われば再送されるので聞き続ける必要がある（§10.5 の 3）。この 2 つを 1 つの操作にすると、**高さを受け取った正常な埋め込みが 8 秒後にリンクに置き換わる**。順序も仮定できない — 初回描画から見えている埋め込みは、可視の通知が届くより先に高さを答えうるので、時計を張る側が「もう答えたか」を訊く。

2 つ目の引き金が §10.3 の 3 つ目を有界にする。X が未文書の入口を変えても、読者が見るのは空白ではなくリンクになる。

**時計は X にだけ張る**（2026-08-24、エディタで実測）。YouTube のプレイヤーは自分で比率を持ち、親には何も送ってこないので、そこからの沈黙は報せではない。公開側は `.embed-x` で箱を選び、エディタの NodeView も同じ区別を持つ（2026-08-24 まで持っておらず、解決できた埋め込み全てに時計を張っていた — 著者がその位置までスクロールした 8 秒後に、動いているプレイヤーが「取得できない投稿です」に置き換わった。X の埋め込みが同じ文書にあるかどうかは関係が無く、単独の YouTube 1 枚で再現する）。あわせて、参照が変わったら前の参照の答えは持ち越さない — 高さを答えた投稿は、それを差し替えた参照については何も答えていない。

### 10.7 ラッパー方式は保留する（2026-08-23）

Zenn と Qiita は、埋め込みの種類によらず自前の `iframe` を 1 枚噛ませている（実測 2026-08-23）。`embed.zenn.studio/tweet` は `platform.twitter.com/widgets.js` を読み込むので、X の公式ウィジェットを使いながら、記事のオリジンでは第三者スクリプトが 1 本も走らない。参照は `src` ではなく親の `data-content` にあり、`{"type":"ready","data":{"id":…}}` → `{"type":"resize","data":{"id":…,"height":…}}` のハンドシェイクで渡す。Qiita も同形で、プロトコルは埋め込みの種類によらず 1 つである。

**この形は §10.3 の 3 つ目を消す** — `widgets.js` は X が公開している入口である。それでも今は採らない:

- **価値は第 2 のオリジンにある。** Zenn の分離は `embed.zenn.studio` という別ホスト名から来ている。このサイトのホスト名は 1 つで、2 つ目には別ノードか独自ドメインが要る
- **同一オリジン版は今より弱い。** Qiita の `qiita.com/embed-contents/tweet` は記事と同一オリジンなので、`widgets.js` が管理者セッションを持つオリジンで走る。`lib/session.ts` の Cookie は `httpOnly: true` なので読まれはしないが、`sameSite: 'lax'` かつ同一オリジンである以上、認証済みの同一オリジン要求は出せる。直接 `iframe` はオリジンに第三者スクリプトを 1 本も置かない
- **後戻りが自由である。** §4 が保存するのは参照だけなので、直接からラッパーへの移行は描画段の変更で済み、データ移行は無い

**引き金は独自ドメインである。** それが入った時点で第 2 ホスト名がほぼ無料になるので、そこで見直す。

**移るときはラッパーに `<html lang>` を書く**（実測 2026-08-24）。`widgets.js` は親ページの `lang` 属性をそのまま `Tweet.html` の `lang` に写し、属性が無いと `en` に落ちる — `embed.zenn.studio/tweet` が宣言しておらず、Zenn の埋め込みが英語 UI なのはこれである（Qiita の記事は `ja`）。§10.4 の `lang=ja` は今こちらが `src` に書いているが、ラッパーに移した瞬間にラッパーの宣言の問題になる。

### 10.8 iframe のスクロールバーは殺す（実測 2026-08-24）

**決定**: 埋め込みの `iframe` は `scrolling="no"` を持つ。プロバイダでは分けない。

`Tweet.html` は自分の `<html>` に `overflow-y: scroll` を指定している。これは「溢れたら出す」ではなく「常に軌道を確保する」指定なので、**225px の投稿を 250px の箱に入れても、スクロールする対象が無いまま右端に 15px のバーが出る**。バーは幅も食うため、投稿がレイアウトに使える幅は 550px ではなく 535px になり、§10.5 で受け取る高さもその狭い幅で計算されたものになる。

**この件は headed でしか再現しない。** headless Chrome はオーバーレイ型のスクロールバーを使うので、同じ iframe で `window.innerWidth - clientWidth` が 0 を返す。最初の測定はそれを見て「バーは無い」と答えた。E2E も headless なので、測れるのは属性であってバーの不在ではない。

YouTube 側では no-op である — プレイヤーは `<html>` と `<body>` の両方に `overflow: hidden` を持ち、箱を 200px まで縮めても `scrollHeight === clientHeight` のままだった（550/320/200px の 3 サイズで実測）。スクロールしてほしい埋め込みというものが無いので、プロバイダ分岐は作らず §4.3 のレジストリも動かさない。

`scrolling` は HTML5 で廃止された属性で、現行 Chrome は尊重する。CSS では届かない — あのバーは `platform.twitter.com` の文書のものである。尊重されなくなった日に戻るのは今の状態なので、壊れ方は穏当である。

### 10.9 箱は 550px で止める。中央には寄せない（2026-08-24 決定）

**決定**: `.embed-x .embed-frame` に `max-width: 550px` を置く。左揃えのままにする。

ウィジェットはカードを **548px** で組み、そこで止まる（実測 2026-08-24。750px の枠でも 550px の枠でも 548、420px の枠では 418 に縮む）。上限は X 側のもので、こちらからは動かせない。したがって箱を本文幅いっぱい（記事では 750px）にしておくと、**右のおよそ 200px は何も描かれないのにポインタを飲む** — 端まで iframe だからである。この帯を消すのが上限で、投稿の見え方は 1px も変わらない。

**中央には寄せない。** このサイトはカラムより狭いブロックを左端の線に付けており、カラムより狭い画像が既にそうなっている（`.prose img` に指定は無く、Tailwind Typography も中央には寄せない）。Zenn はこの埋め込みを中央に置くが、**狭い画像も中央に置いている** — 実測（`zenn.dev/zenn/articles/markdown-guide`、本文 708px）で 250px の画像が左右 229px ずつの位置にあり、埋め込みブロックの器はどれも左 0・幅 708 だった。つまりあれは「埋め込みをどうするか」ではなく**「カラムより狭いものをどうするか」という 1 段上の規則**で、Qiita は逆の規則を採っている。ここで埋め込みだけ中央に寄せると、同じ問いに 2 つの答えを持つページになる。

**エディタの箱も同じ幅で終わる。** 公開側の箱は枠線を持たないので、プレイヤーが使わない幅は見えない。エディタの `.embed-view` は枠線を描くので、同じ空きが「枠の内側の空白」になる。上限は `--embed-x-width` の 1 つから両方に配り、エディタ側はそれに `.embed-view` 自身の padding と border を足す。§7.2 が引き受けた「エディタのプレイヤーは公開より狭い」という代償は、この幅では消える — 550px より広いカラムでは両面とも 550px になる。

規則ごと乗り換える道は開いている — `margin-inline: auto` の 1 行と、画像への同じ答えが要る。**既存の全記事の画像が動く変更なので、埋め込みの議題とは分けて決める。**

### 10.10 クローンは第 2 の話者になる（実測 2026-08-24、修正）

**決定**: ドラッグプレビューは複製から `<iframe>` を取り除く（`blankClonedFrames`、`components/editor/block-drag-handle.ts`）。あわせて NodeView は、メッセージが**自分の** `iframe.contentWindow` から来たかを確かめる（`onMessage`、`components/editor/embed-extension.ts`）。

**機構**: `embedId` は置き場所の名前であって、フレームの名前ではない（§10.5）。要素を複製したものは名前ごと複製する。ブロックドラッグのプレビューは掴んだブロックの `cloneNode(true)` で、**複製された `<iframe>` は絵ではなく生きたブラウジングコンテキスト**になり、同じ src を読み直して同じ名前で喋り始める。

実測（修正前）: 埋め込みを掴んだ瞬間にページ上の X のフレームが 1 → 2 になり、どちらも `emb-view-1` を名乗った。プレビューの箱は本体より狭い（実測 92px）ので、クローンは**自分の幅に合わせた高さ**を返し、ドキュメント側に残っているブロックがそれを受け取って 1550px → 1092px に縮んだ。掴んでいる間ずっと、著者の目の前で。返ってくるのが `no_results` なら、ドラッグしただけで本体が §10.6 の「取得できない投稿です」に差し替わる。

**ゴーストはブロックを再現せず、名指しする。** 埋め込みを掴んだときカーソルが運ぶのは、プロバイダの印と `EmbedTarget.label` の 2 つだけで組んだ 1 行のトークンである。`label` は 2 枠あり、`lead` は URL がその個体について言える一番強いこと（投稿ならアカウント、動画には固有名が無いのでプロバイダ名）、`detail` は残りで言う価値のあるもの（動画の開始時刻、`/i/status/<ID>` 形式の投稿の ID）。どちらもプロバイダが埋める — 2 枠のどちらを答えられるかを知っているのはプロバイダだけだからである。

**種類は書かない。** X のモノグラムの横の「X の投稿」はどの投稿でも同じ文字列で、しかも投稿でない X の URL は埋め込みにならない（§10.4）ので、この語は何も区別していない。太字の位置に毎回同じ語が入ることが、最初の版が機械的に見えた理由である（2026-08-24 に作り直した）。`title` の方は動かさない — あれは 2 面の iframe のアクセシブルネームで、見えない人に種類を伝える文字列であり、印の横に置く文字列とは別の問いに答えている。

どのプロバイダも claim しない参照には印を出さず（既定の印は再生三角なので、再生できないものに再生を約束することになる）、ブロック自身と同じ文言（「埋め込みにできない参照」）を `lead` に、URL を `detail` に置く。長い URL はここで省略される唯一の値である。

箱を再現する形は 2 度試して 2 度やめた（どちらも 2026-08-24）。跡地に何も置かないと 480×300 の白い板になり、一番目立つのが押せない「リンクに戻す」ボタンになる。名前だけ置くと、`.embed-frame` の `width: 100%` が「中身で幅が決まる」プレビューの中で解決できず、92px の細片に潰れる（iframe が入っていたときも同じ 92px で、絵が描かれていたので見えていなかった）。**運べるのは名前だけであり、名前に箱は要らない。**

**直しが 2 つあるのは、症状と原因が別だからである。** クローンを消せば今日の経路は閉じるが、名前を名乗るのはメッセージの側のままで、要素を複製する経路が増えれば同じことが起きる。source の照合は「何かが言った」ではなく「自分のフレームが言った」を問う形にする。

**却下: ゴーストに本物の `iframe` を残す（実測 2026-08-24）。** `event.source` の照合が入った後は、クローンの `iframe` を残しても本体の高さは奪われない — この選択はもう安全の問題ではなく、費用と見え方の問題である。測った結果、クローン 1 枚が出す要求は 17 本で、1 枚目とまったく同じ内訳になる（`platform.twitter.com` 9・`syndication.x.com` 4・`pbs.twimg.com` 3・`cdn.syndication.twimg.com` 1）。うち 13 本は 1 枚目と同じ URL でありながらキャッシュに当たらず出直す（`requestStart` と `serverAddr` の 2 つの指標が一致。17 本ともヘッダ自体はキャッシュ可能な指定である）。残る 4 本は `syndication.x.com/i/jot/embeds` の `tfw_client_event` で、インスタンスごとに URL が違う — X の計測ビーコンなので、掴むたびに「埋め込みが 1 回表示された」と報告が飛ぶ。著者が編集中にブロックを動かしただけの操作が、表示数として第三者に渡る。加えて §10.5 の通り投稿が描かれるまで 600ms 以上かかるので、1〜2 秒で終わるドラッグの間はほとんど白いままである。**掴むたびに 17 本の要求と 4 本のビーコンを出して、見えるのはたいてい白い箱**という取引になる。

**ドロップ直後に一度 250px に戻ることは引き受ける。** ドロップはノードを消して入れ直すので NodeView は作り直され、新しい iframe が測り直すまで §10.5 の初期値に戻る。§10.5 が既に引き受けている「可視化のときに一度跳ねる」と同じ性質のもので、高さを憶えて持ち越す手はあるが、参照ごとの記憶を足すだけの価値はまだ無い。

- **削除済み・非公開・存在しない の区別**。`no_results` は `tweet_id` を返すだけで 3 者を区別しない（§10.6 は同じ扱いにする）
- `youtu.be` 以外のホストで `t=` が付いた実例
- Shorts の実 ID・ライブ配信の実 ID での `/embed/<ID>` の応答。§9.2 の表は通常動画の ID を 5 つのパスに当てて測っている
- **ネイティブドラッグ経路の `iframe` 盲点**（§8.1）。枠の付いていないブロックを本体から押したときに立ち上がる prosemirror-view 側のドラッグで、`dragover` とドロップカーソルが埋め込みの上で同じように止まるかは測っていない
- **公開ページの描画中にサーバが第三者へ要求を出さないこと**（基準 E10）。取得の段が存在しないことは読めば分かるが、測ってはいない
- **非公開・限定公開のデッキ**（§14）。ペイロードに `isPrivate` はあるが、非公開デッキは URL で辿れず、アカウント無しでは作れないので測定手段が無い
- **削除済みのデッキ**（§14.6）。埋め込み側の観測可能な出口は 2 種類の 404 だけで、どちらも無言である
- **作り直されたフレームが再び高さを報せるか、の gist の側**（§8.4、基準 E17）。X は実測して言い直すことが分かった。gist は同じ経路に乗るが、フレームが不透明でエディタの中では測れない（§18.6）ので、推論のままである。黙るプロバイダ（Figma、YouTube）は無関係である

markdown 往復（E1）はここから外れた — `e2e/editor-embed.spec.ts` が `&amp;` を含む形で測っている。**絶対 URL を `data-href` に入れた往復は、外部カードでは `link-card-requirements.md` §14.10 に未実測のまま残っている**。同じ経路を通るので、あちらの穴はこちらの測定では埋まらない。

## 13. 却下した案

- **YouTube をリンクカード形式にする**（§9.1）。64KB の上限の内側にメタデータが 1 つも無く、上限を動かすのは防御を壊す
- **カードと埋め込みの両対応**（§3.3）。1 つの URL に対して結果を選ばせる理由が著者に説明できない
- **プロバイダごとに class とノードを分ける**（§4）。`divClasses` を足し忘れると静かに壊れる場所を、プロバイダの数だけ触ることになる
- **`moveBefore` で `iframe` を預けて引き取る**（§8.4）。並べ替えでの作り直しは消せると測ったが、回収と `instanceId` の引き継ぎとブラウザ分岐を足す価値が、数秒の読み込みに見合わない
- **ID を属性に抜いて保存する**（§4）。付随情報が属性を増やし、「リンクに戻す」が再構成した正規形を返すようになる
- **`iframe` を sanitize スキーマに足す**（§6）。著者の書いた任意の `<iframe src>` が公開ページに載る
- **第三者のスクリプトを公開ページに置く**（§6）。X の公式ウィジェットがこの形である。スクリプトはこのサイトのオリジンで走る
- **ドラッグのゴーストに本物の `iframe` を残す**（§10.10）。掴むたびに 17 本の要求と、インスタンスごとの計測ビーコン 4 本が出る。それでいて投稿が描き終わる前にドラッグが終わる
- **`@[youtube](url)` のような記法**。`link-card-requirements.md` §4.1 (b) の却下理由が動いていない — ノードが書いた場合だけ生き残り、手で打つと別のものになる

## 14. SlideShare（2026-08-25 決定）

デッキの URL は常に埋め込みになる。§3.3 のとおり、カードとの二択は著者に出さない。

実測はすべて system Chrome + Playwright + ローカル HTTP 親（アプリを経由しない形）で取った。**headless では測れない** — SlideShare は headless Chrome に Fastly の "Client Challenge"（cookie が無効というページ）を返し、これは「その経路が存在しない」と見分けがつかない。headed では同じ URL が 6/6 描画する。

### 14.1 §3.1 の 3 問を通した結果

1. **カードは動く。** `fetchLinkPreview` が 267ms で題・説明・画像を返す（`og:title` / `og:description` / `og:image` が揃っている）。ここは YouTube と違う — §9.1 の「メタデータが 1 つも無い」状況ではない
2. 動くので 3 番目を訊く。**埋め込みが足すのは「読者がその場でデッキをめくれる」ことである。** カードが出すのは 1 枚目のサムネイル 1 枚で、43 枚のデッキも 1 枚に見える
3. 実測でめくれる（`266319371` で 1/43 → 2/43）。ただし操作は下端のコントロール列のボタンだけで、スライドのクリックでは進まず、ArrowRight はフレームをクリックして focus を入れてからでないと効かない

**初見の読者は、まず同意バナー（§14.5）を閉じるまで 1 枚もめくれない。** バナーがコントロール列を覆っており、Next の座標をクリックしてもカウンタは動かない（593×371 と 750×611 の両方で実測）。閉じた後は動く。zenn.dev の SlideShare 埋め込みも同条件である。

### 14.2 受け付ける URL の形

`/slideshow/<slug>/<id>` の 1 形だけを受ける。ID はパス末尾の数字で、`SLIDESHARE_ID` が桁を検証する（X_ID と同じ理由 — `src` に入る値だから）。

| 形                                                        | 結果                                                              |
| --------------------------------------------------------- | ----------------------------------------------------------------- |
| `www.slideshare.net/slideshow/<slug>/<id>`                | 埋め込み                                                          |
| `slideshare.net/…`（`www` 無し）                          | 埋め込み                                                          |
| 旧 `/<handle>/<slug>`                                     | カード（**この形は ID を持たない**。実測 2026-08-25、404 を返す） |
| `es.slideshare.net` などロケールホスト                    | カード                                                            |
| `/slideshow/embed_code/key/<KEY>`（埋め込みコードの URL） | カード                                                            |
| ID が数字でない・20 桁以上                                | カード                                                            |

ロケールホストは `www` へ転送され ID も同じ位置にあるが、集合が開いているので許可リストには入れない（§9.2 が `music.youtube.com` を外したのと同じ判断）。**埋め込みコードの URL 自体も受けない** — 受けると「リンクに戻す」が著者の持っていたページではなく素のプレイヤーの URL を `<a href>` に書くことになる。

### 14.3 `src` は数値 ID 形で組む

`https://www.slideshare.net/slideshow/embed_code/<id>` を組む。これは 302 で `embed_code/key/<KEY>` に転送される。

**転送を追うのは読者のブラウザなので、こちらに取得の段は要らない。** SlideShare が `twitter:player` と `iframeEmbed.url` で案内するのは key 形のほうで、KEY はデッキページの HTML にしか無い。key 形を使うなら取得が要り、§3.2 が消える。

数値 ID 形は SlideShare が明示していない別名である。消えた場合に壊れるのは `resolveEmbed` の `src` 導出だけで、§4 が保存するのは正規ページの URL なのでデータ移行は起きない。

### 14.4 箱と全画面

箱は `height: 0` + `padding-bottom: calc(56.25% + 38px)` で組む。**プレイヤーは「スライド領域」と「高さ 38px 固定のコントロール列」の 2 つでできており、1 つの比率では表せない** — 幅が広がるほどコントロール列の割合が減るので、全体を 1 比率で固定すると箱の形が幅によって変わってしまう。上の式は列を足し込んだうえでスライド領域を 16:9 に保つ。zenn.dev も同じ式である（`span.embed-slideshare` の `padding-bottom: calc(56.25% + 38px)`、708px 幅で 436.25px を実測）。

スライド領域が 16:9 でないデッキは帯が付く。プレイヤーは与えられた箱の中で letterbox / pillarbox するだけで、デッキ自身の比率は取得しないと分からない（§3.2）ので、これは §9.6 の縦向き動画と同じ扱いになる。実測したスライド原寸は 2048×1447 / 1582 / 1152 とばらつく。

2026-08-25 に `aspect-ratio: 597 / 486`（SlideShare 自身が案内する寸法、`"iframeEmbed":{"url":…,"height":486,"width":597}`）から変更した。**理由は上下方向の帯である** — 記事カラム 750px では、その式のスライド領域が 4:3 寄りになり、16:9 のデッキが上下に 78px ずつの帯を持つ。著者が見た目で選んだ結果、上下に伸びないほうを採る。4:3 寄りのデッキでは逆に左右へ帯が出る（実測: 1.415 のデッキで左右 71px、1.295 のデッキで 96px）。

**全画面は `allow` ではなく `allowFullScreen` が決める。** 2 面が出す markup（`allow=""` あり・`allowfullscreen` あり）で実測すると、SlideShare 自身のボタンで親の `document.fullscreenElement` が `iframe` になる。属性を外すと何も起きない。したがって `SLIDESHARE_ALLOW` は空文字列で、追加作業は無い。

`scrolling="no"`（§10.8）はこのプロバイダでは no-op である — 中身がはみ出さないので、YouTube と同じ立場になる。

### 14.5 読者が払うもの

- **埋め込み 1 本で 40 リクエスト**（`public.slidesharecdn.com` 25、`slideshare.net` 6、osano の CMP 4、sentry 1、`wa.slideshare.net` 1）。X の 17（§13）の倍以上ある。親のオリジンに cookie は 1 つも置かれない
- **iframe の中に Cookie 同意バナーが出る**（`.osano-cm-dialog`、122px）。SlideShare 自身のもので、親サイトからは消せない。zenn.dev も同じものを出す
- バナーは ✕ で閉じられ、**閉じた状態はブラウザに残り、他サイトの SlideShare 埋め込みにも引き継がれる**（ローカル親で閉じた後、同じブラウザで zenn.dev の埋め込みが既に非表示だった）。cookie は 0 件なので保持先は localStorage 等である。つまり「読者 1 人につき 1 回」であって毎回ではない

### 14.6 埋め込みを拒むデッキは、記事の中に SlideShare の 404 を出す

`isEmbedAllowed: false` のデッキ（推奨・人気デッキ 34 件を走査して 1 件）は、ページ自身は 200 で `twitter:player` も普通に載っているのに、埋め込むと 404 になる。出るのは空箱ではなく、検索バーと "Download free for 30 days" を載せた SlideShare の 404 ページである。存在しない ID は転送を挟まずより素朴な 404 ページになる。

**`resolveEmbed` はこれを区別できない** — URL の形も ID も正常である。無言（postMessage が来ない）なので §10.6 のフォールバックも張れない。

**この状態は受け入れる。** 著者は挿入した瞬間に自分の NodeView で同じ 404 を見る（2 面が同じ `iframe` を組むので、§7 がそのまま働く）。直したければ「リンクに戻す」からカードにできる。公開後にデッキ側が禁止へ変わった場合は防げない。

### 14.7 読者側の検知は採らない

| 手段                                       | 実測                                                                          |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| `<object>` の `error` / fallback           | **効く**。生きているデッキは `load`、404 は `error`（302→404 の連鎖でも飛ぶ） |
| `PerformanceResourceTiming.responseStatus` | 効かない。クロスオリジンで TAO が無く、3 例とも `0`                           |
| `iframe.contentWindow.length`              | 効かない。生きている 3 / 埋め込み禁止 3 で同じ                                |

`<object>` は唯一効く手段だが採らない。**`loading="lazy"` が効かず**（画面外でも 40 リクエストが即時に出る。`data-src` + IntersectionObserver で取り戻せるが JS 必須になる）、**全画面が死ぬ**（`allow="fullscreen"` も `allowfullscreen` も無視される）。SlideShare のコントロール列には全画面ボタンが描かれたまま残るので、押しても何も起きないボタンが他社 UI の中に残る。

エディタの挿入時に `isEmbedAllowed` を訊いて弾く案も採らない。著者へのフィードバックは §14.6 のとおり既にあり、買うのは言葉だけである。加えて `isEmbedAllowed` は非公開のフィールドで、名前が変われば fail-open なら 404 が全面復活、fail-closed なら全デッキが埋め込めなくなり、**どちらもテストは緑のまま**である。§3.2 の「取得の段が存在しない」もエディタについて偽になる。

### 14.8 マークとラベル

バブルの行と drag ghost が使うマークは `SLIDESHARE_MARK_SHAPES`（SlideShare のマーク）である。§7.3 が「ロゴを足すかはその都度決める」と置いた判断を、§16.7・§17.7 と同じく足す側に倒している。`embedMarkShapes` に分岐を 1 本足しており、足さなければ既定の再生マークが黙って出る。

**形は書き起こさず、公開されているパスを使う**（§16.7 と同じ理由）。出典は SlideShare の CDN の `favicon.*.svg` に入っている字形で、**橙の円は落とす** — 円は器であってマークではなく、ここの他のマークは器を持たないからである。**単色でも何も失わない**: 内側の面は同じ `d` の中の逆向きサブパスとして公開されており、色ではなく塗りの穴なので、重なった 2 面は 16px でも 2 面のまま読める（円付きの版と、置き換える前の画面と脚を並べて 16 / 24 / 40px を明暗 2 スキームで確認、2026-08-26）。

寸法は他のブランドマークと同じ合わせ方で、字形は favicon の原寸で 109×86 なので、**横幅を 21.5 に縮めて 24 の箱の中央**に置く（21.5×16.96）。`IconShape` は transform を持たないので変換は座標に焼き込んであり、小数 2 桁への丸めは焼く前の描画と画素比較して 16 / 24 / 40px のすべてで差 0 である。

2026-08-26 に `SLIDES_SHAPES`（画面と脚を描いた図形）から変更した。「デッキは再生するものではない」という §7.3 の理由は今も真で、既定の再生マークに戻したわけではない。**変えたのは、プロバイダを名指すマークのほうが著者に読めるからである** — X・Figma・Speaker Deck・Docswell が順にそうなった結果、画面と脚だけが「どのスライドサイトか」を言わないマークとして残っていた。`SLIDES_SHAPES` は使う側が無くなったので削除した。

ラベルは `{ lead: 'SlideShare', detail: '' }` で、slug は使わない。**slug は名前ではない** — 日本語の題は数字だけの slug になり、多くの slug は末尾に ID を再掲している。ゴーストが何を読むかは §10.10 の話で、そこでも YouTube と同じ — 取得なしにデッキを名指すことはできない。

## 15. Figma（2026-08-25 決定）

デザインファイルの URL を埋め込みにする。§3.1 の手順に掛けた結果が §15.1 で、受け付ける形が §15.2 である。

### 15.1 §3.1 の 3 問を通した結果

1. **カードは動かない。** `fetchLinkPreview` は 1121ms かけて null を返す。ページは 200 で `og:description`（「Created with Figma」）も `og:image`（サムネイル）も載っているが、**`<title>` と `og:title` がバイト位置 753,645 / 777,127 にある** — 818,081 バイトのページで、`lib/link-title.ts` の `MAX_BYTES`（64KB）より遥かに後ろである。`extractTitle` が null を返す以上、`fetchLinkPreview` も null になる（`link-card-requirements.md` §14.7 のとおり、カードは URL を出すだけになる）
2. 1 が「動かない」なので §3.1 の 2 番で足りるが、この理由は第三者の SPA のバイト位置であって、Figma が html の並びを変えれば消える。したがって 3 番も答えておく: **埋め込みが足すのは「読者がその場でデザインを拡大・移動し、ページを切り替えられる」ことである。** カードが出せるのは静止したサムネイル 1 枚である
3. 実測でそれができる（800×450 の箱に、左上のページ切り替え、右上の全画面、右下のズーム ±、下端にファイル名と「Figma で開く」が出る）

### 15.2 受け付ける URL の形

`/design/<key>` と `/file/<key>` の 2 形を受ける。key はパスの第 2 セグメントで、`FIGMA_KEY` が形を検証する（`YOUTUBE_ID` と同じ理由 — `src` に入る値だから）。slug は任意で、あっても使わない。

`FIGMA_KEY` の文字種は `YOUTUBE_ID` と同じ `[\w-]` で、**実測した key より広く取ってある**。手元にあるのは 22 桁の英数字 2 本（`7or4V8Tl8YbEFRmMSF3pXe`、`abttA1F3GxZdZlkI9t5s99`）だけで、2 本では字種は決まらない。ここを狭めて外すと、生きているファイルが黙って素のリンクになる。長さの上限も同じ性格で、Figma 自身の説明は 4 文字の key を例に使っている（`figma.com/design/pqrs/ExampleFile`）。

| 形                                                     | 結果                                                                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `www.figma.com/design/<key>/<slug>`                    | 埋め込み                                                                                                      |
| `figma.com/…`（`www` 無し）・slug 無し・末尾スラッシュ | 埋め込み                                                                                                      |
| `www.figma.com/file/<key>/<slug>`                      | 埋め込み（**同じファイルである**。Figma 自身の `og:url` が `/design/` の URL に対して今も `/file/` 形を出す） |
| `/proto/` `/board/` `/slides/`                         | カード（§15.2 末尾）                                                                                          |
| `embed.figma.com/…`                                    | カード（本書が出す側の URL であって、受ける側ではない — §9.2 が `youtube-nocookie.com` を外したのと同じ）     |
| `*.figma.site`                                         | カード（公開サイトであってファイルではない）                                                                  |
| key が `[A-Za-z0-9_-]` を外れる・65 文字以上           | カード                                                                                                        |

`/proto/`（プロトタイプ）・`/board/`（FigJam）・`/slides/` は保留する。**共有ダイアログが実際に出す URL を 1 本も測っていないためで、形の是非ではない。** `/proto/` は手で組んだ URL では描画されたが、`starting-point-node-id` や `scaling` / `content-scaling` を伴う形であり、`/design/` の `src` に落とすとそれらが黙って消える。保留を解くのに要るのは、その 3 形それぞれについて Figma の共有ダイアログが出した URL 1 本ずつである。落ちた形は素のリンクになる（カード側も題を取れないため）。§9.4 のプレイリストと同じ扱いである。

### 15.3 `src` は key 形で組む

`https://embed.figma.com/design/<key>?embed-host=tech-blog` を組む。これは 302 で `www.figma.com/design/<key>?…&viewer=1` に転送され、**転送を追うのは読者のブラウザなので、こちらに取得の段は要らない**（§3.2）。

`embed-host` は省けない。付けずに読み込むと、ファイルの代わりに `Not a valid embed context` という Figma のエラー画面が出る。値は「サイトを一意に、明確に識別するもの」を求められているので、`app/shared-metadata.ts` の `SITE_NAME` は取り込まず `FIGMA_EMBED_HOST` を別に置く — ヘッダの表示名を変えたときに第三者へ送る識別子まで変わるのは、別の話である。

**旧来の `www.figma.com/embed?embed_host=…&url=<ページ URL>` 形は採らない。** 今も描画されるが、著者の文字列がそのまま `src` に入る形であり、それを防ぐのが §4.2 でこのファイルに与えた仕事である。

`node-id` は引き継ぐ（§9.3 と同じ判断）。`5-2` と `5%3A2` の両方が書かれ得るが、`searchParams` が後者を復号して渡すので分岐は区切り文字 1 つで足り、**どちらも同じノードに着く**（パンくずが「Figma埋め込みサンプル · Figma」になる。`0-1` ならページ自身で「· サムネイル」）。`src` に入るのはハイフン形に組み直した数字である。解釈できない `node-id` は捨てて、ファイルの既定位置を出す。

落とすものが 2 つある。`p=f`（Figma 自身の UI のペインを指す。利用者のサンプル URL にも付いている）と `t=`（共有の attribution トークン）で、どちらも読者が見るものの関数ではない。slug も落とす — key だけで解決する。

### 15.4 箱と全画面

箱は `aspect-ratio: 16 / 9` の 1 ルールで足りる。ファイルページ自身が `twitter:player:width` / `:height` に 800×450 を出しており、ビューアは与えられた箱を埋めて中身を縮小して収める。360×640 と 1000×300 でも `canvas` は箱と同寸、`scrollWidth` / `scrollHeight` も箱と同値で、スクロールバーは出ない。デザインの縦横比が 16:9 でなければ余白が付き、これは §9.6 の縦向き動画と同じ扱いになる。

**枠線はこの箱が持つ。ビューア自身が縁を持たないためである。** Figma は四辺とも白を塗る — 上にコントロール列、下にファイル名の行 — ので、白い記事ページの上では埋め込みがどこで終わるのか見えない（実測 2026-08-25、スクリーンショットで上端・下端・ページが同じ白であることを確認した）。線はリンクカードとエディタの箱が使っている `#d0d7de` / `#30363d` で、**著者が同じフレームの周りに既に見ている線である**。`box-sizing` は border-box なので、上の比率は読者が見るブロックのままで、`iframe` はその 1px 内側に収まる。

同じ条件は SlideShare にも当たる（プレイヤーの上下も白い）。そちらに線を足すかは §14 の決定であって、ここでは触っていない。

**全画面は `allow` ではなく `allowFullScreen` が決める**（§14.4 と同じ）。`allow=""` のまま埋め込みの拡大ボタンを押すと、親の `document.fullscreenElement` が当の `iframe` になる。したがって `FIGMA_ALLOW` は空文字列である。

### 15.5 読者が払うもの

- **埋め込み 1 本を載せたページで 36 リクエスト**（SlideShare の 40 と同水準、X の 17 の倍）。`www.figma.com` / `static.figma.com` / `embed.figma.com` のほか、`errors.figma.com` と Datadog の RUM に出る
- postMessage は `INITIAL_LOAD` という文字列が 1 回来るだけで、高さの通知は無い。したがって §10.5 の `components/EmbedFrames.tsx` に足すものは無い
- iframe の中に同意バナーの類は出ない（§14.5 の SlideShare との差である）

### 15.6 公開アクセス可能でないファイルは、記事の中に Figma の案内を出す

Figma は公開アクセス可能なファイルしか他サイトに埋め込ませない。埋め込めない key（存在しない key で実測）では、`www.figma.com/embed/interstitial?…` が 404 を返し、iframe の中に「見つかりませんでした。…公開アクセス可能ではない可能性があります」という Figma 自身の案内が出る。無言（postMessage は来ない）なので §10.6 のフォールバックは張れない。

**この状態は受け入れる。** §14.6 と同じ理由で、著者は挿入した瞬間に自分の NodeView で同じ画面を見る（2 面が同じ `iframe` を組む）。直したければ「リンクに戻す」で素のリンクに戻せる。

共有がオフのファイルはこれと違う。**著者には表示され、読者には Figma のログイン画面が出る**（2026-08-25、著者の環境で実測。同じファイルを共有オフにすると、Figma にログイン済みのブラウザでは開き、シークレットウィンドウではログインを求められた。共有が「リンクを知っている全員」なら両方で同じデザインが出る）。

**このケースだけ §7 の「著者が見ているものが読者に出る」が偽になる。** 著者の NodeView は正常に描画されるので、SlideShare の §14.6 が寄りかかった「著者は自分の画面で同じ失敗を見る」がここでは働かない。

したがって**エディタの NodeView に 1 行を常時出す**（`embed-hint`、`components/editor/embed-extension.ts`）:

> 読者に表示するには、Figma の共有設定が「リンクを知っている全員」である必要があります。

判定はしない。判定するには Figma に訊く段が要り、§3.2 の「取得の段が存在しない」がエディタについて偽になる（§14.7 が SlideShare で断ったもの）。**買えるのは言葉だけだが、ここでは言葉しか手段がない** — SlideShare では著者が同じ 404 を見るので言葉が余計だった、という差である。既に共有済みの著者は当たらない 1 行を読むことになり、それは受け入れる。公開後に共有設定が変わった場合は防げない。

### 15.7 マークとラベル

マークは `FIGMA_MARK_SHAPES`（Figma のロゴ）である。§7.3 の理由がそのまま当たる — **デザインファイルは再生するものではない**。`embedMarkShapes` の分岐を足さなければ既定の再生マークが黙って出る。

**§7.3 が「ロゴを足すかはその都度決める」と置いた判断を、ここでは足す側に倒している。** ブランドマークは X に続く 2 例目で、塗りで描くのも 2 例目である（X は線画だと 16px で潰れるため、こちらは元が塗りの 5 図形であるため）。描いた形の候補も 16px で並べて比べたが、フレームツールの字形（罫線 4 本）は読み取りに一手要り、著者が選んだのはロゴだった。

図形は写したパスではなく、r = 3.4 の 3 行グリッドから起こしてある（左列 3 つは左が丸、右上 1 つは右が丸、右中は円）。**1.2 単位の隙間が要る** — 元のロゴで 5 図形を分けているのは色で、こちらは 1 色だから、隙間が無いと 1 つのシルエットに融ける。1x 画面では隙間が 1px 未満になって融けるが、そのときの形は隙間を入れなかった場合と同じものである。

ラベルは `{ lead: 'Figma', detail: '' }` で、slug も `node-id` も使わない。**どちらも名前ではない** — slug は著者の題を機械変換したもので、`5-2` は人が読むものではない。§14.8 と同じで、取得なしにファイルを名指すことはできない。

## 16. Speaker Deck（2026-08-26 決定）

プレイヤーの URL を埋め込みにする。**デッキページの URL は埋め込みにならない** — その理由が §16.3 で、このプロバイダの決定はほぼそれ 1 つである。

実測はすべて headed の system Chrome + Playwright + ローカル HTTP 親（アプリを経由しない形）で取った（§14 の手順）。headless で何が返るかは測っていない。ただし SlideShare で challenge を食った node fetch の経路は、ここでは通っている — `fetchLinkPreview` が 3 デッキとも 200 と全メタデータを返す（§16.1）。

### 16.1 §3.1 の 3 問を通した結果

1. **カードは動く。** `fetchLinkPreview` が 346–670ms で題・説明・画像を返す（3 デッキで実測）。`og:image` は 1 枚目のスライドである。SlideShare と同じ位置で、YouTube の §9.1 とは違う
2. 動くので 3 番目を訊く。**埋め込みが足すのは「読者がその場でデッキをめくれる」ことである。** §14.1 と同じ答えで、カードが出すのは 1 枚目 1 枚だけである
3. 実測でめくれる。前後の矢印・共有・全画面がスライドの上に重なって描かれ、SlideShare と違って同意バナーは出ない

### 16.2 受け付ける URL の形

`/player/<id>` の 1 形だけを受ける。ID はパス末尾で、`SPEAKERDECK_ID` が形を検証する（`YOUTUBE_ID` と同じ理由 — `src` に入る値だから）。

| 形                                                                                               | 結果                                                      |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `speakerdeck.com/player/<id>`                                                                    | 埋め込み                                                  |
| `www.speakerdeck.com/player/<id>`・末尾スラッシュ                                                | 埋め込み（`www` は apex へ転送され、ID は同じ位置にある） |
| `speakerdeck.com/<user>/<slug>`（デッキページ）                                                  | カード（**この形は ID を持たない** — §16.3）              |
| `/player/<user>/<slug>`・`/<user>/<slug>/embed`・`/<user>/<slug>/player`・`/embed/<user>/<slug>` | カード（4 形とも 404。実測 2026-08-26）                   |
| `speakerdeck.com/oembed.json?url=…`                                                              | カード（答えは持っているが、読むのは取得である — §3.2）   |
| ID が 16 進小文字 24–32 桁を外れる                                                               | カード                                                    |

ID は `[0-9a-f]{24,32}` である。長さが 2 通りあるのは世代の差で、今のデッキは 32 桁、古いものは 24 桁を持ち（`504229f1c53c970002012ba0`、`4fa4436e5f35f0002200b70b`）、どちらも再生する。**大文字は同じ ID ではない** — 32 桁をそのまま大文字にすると 404 になるので、字種に `A-F` は入れない。長さは**測った 2 値より広く取ってある**（25–31 桁も通る）。`FIGMA_KEY` と同じ判断で、ここを狭めて外すと生きているデッキが黙って素のリンクになる。

### 16.3 ID はデッキページの URL に無い

デッキページの URL（`speakerdeck.com/<user>/<slug>`）には ID がどこにも無い。ID があるのはページの HTML の中 — `og:image` の `files.speakerdeck.com/presentations/<id>/slide_0.jpg` と、`oembed.json` の答え — だけである。そして §16.2 の表のとおり、slug からプレイヤーに着く別名は存在しない。

**したがって選べる形は 2 つしかない**: プレイヤーの URL を受けるか、このプロバイダを持たないか。参照した 2 サイトも同じ制約を踏んでいて、Zenn は `@[speakerdeck](<id>)`、Qiita は `<script data-id="<id>">` で、どちらも著者に ID を掘らせている。

著者の手順は、デッキページの「Copy iframe code」が配る markup から `src` を取り出すことである。デッキページの URL をそのまま貼った場合はカードになる（§16.1 のとおり、題・説明・1 枚目が出る）。

`aspect-ratio` 相当の `data-ratio` も同じ markup にあるが、使わない。取得しなければ読めない値であり、箱は §16.4 のとおり 1 ルールで組む。

**§14.2 が SlideShare の埋め込みコード URL を断った論法は、ここでは当たらない。** あちらで断れたのは、ID を持つ正規ページの URL が別にあったからである。「リンクに戻す」が書くのは著者が渡した文字列そのもので（§4）、ここで著者が渡したのはプレイヤーの URL だから、返るものと持っていたものは一致する。§14.2 が避けたのは、ページの URL を持っている著者に別物を返す形だった。

エディタが取得して ID を埋める案は採らない。§14.7 が `isEmbedAllowed` で断ったのと同じで、**§3.2 の「取得の段が存在しない」がエディタについて偽になる**。加えて公開側は救えない — `rehypeEmbed` は記事の描画のたびに走るので、そこに取得は置けない。

### 16.4 箱と全画面

箱は `aspect-ratio: 16 / 9` の 1 ルールで足りる。**SlideShare の §14.4 で和が要ったのはコントロール列が場所を取るからで、Speaker Deck はスライドの上に重ねて描く** — 矢印も共有も全画面もフレームの内側に浮いているので、フレームがそのままスライド領域である。Speaker Deck 自身の iframe markup も 1 比率で書く（`aspect-ratio: 560 / 315`、4:3 のデッキでは `560 / 420`）。

16:9 を採るのは、今のデッキがその比率で公開されているからである（実測 5 デッキ中 4 デッキの `data-ratio` が 1.7778、1 デッキが 1.3333）。**外したデッキも切れはしない** — `.sd-player-slide` が `background-size: contain` なので、スライドは全体が描かれて帯が付く（1.3333 のデッキ `cf29dcf084890130af0d12313d053a9e` で実測）。デッキ自身の比率は取得しないと分からないので（§3.2）、これは §9.6 の縦向き動画と同じ扱いになる。

背景は `transparent` である。**プレイヤーは背景を一切塗らない** — iframe の中の `html` と `body` はどちらも `rgba(0, 0, 0, 0)` で、この箱が置いた色がそのまま帯と読み込み中の面積に出る。`#000` にすると箱全体が黒い矩形になることを実測した。SlideShare・Figma と結論は同じだが、理由は「プレイヤーが明るいカードを描くから」ではなく「何も描かないから」である。

全画面は §14.4・§15.4 と同じく `allowFullScreen` が決める。`allow=""` のままプレイヤーの全画面ボタンを押すと、親の `document.fullscreenElement` が当の `iframe` になる。Speaker Deck 自身の markup が書く `allow="web-share"` は採らない — 描かれる共有メニューはリンクの一覧で、Web Share API の呼び出しではない（§9.2 が `autoplay` を外したのと同じ判断）。

### 16.5 読者が払うもの

- **埋め込み 1 本で 23 リクエスト**（`speakerdeck.com` 7、`files.speakerdeck.com` 5、`d1eu30co0ohy4w.cloudfront.net` 4、fonts 3、GTM 2、GA 1、s3 1）。SlideShare の 40（§14.5）、Figma の 36（§15.5）より安く、X の 17 に近い
- **広告は 1 本も出ない。** デッキページのほうは prebid / doubleclick / criteo などを呼ぶが、プレイヤーはそれらを持たない
- 親のオリジンに cookie は置かれず、同意バナーも出ない（§14.5 の SlideShare との差である）
- postMessage は来ない。したがって §10.5 の `components/EmbedFrames.tsx` に足すものは無い

### 16.6 存在しない ID は、記事の中に Speaker Deck の 404 を出す

形は正しいが実在しない ID は、空箱ではなく "Sorry, the deck you are looking for can't be found." という Speaker Deck 自身のページになる。無言なので §10.6 のフォールバックは張れない。

**この状態は受け入れる。** §14.6 と同じ理由で、著者は挿入した瞬間に自分の NodeView で同じ画面を見る（2 面が同じ `iframe` を組む）。直したければ「リンクに戻す」で素のリンクに戻せる。

**Restrict embedding を掛けたデッキも同じ形になる（実測 2026-08-30）。** デッキページから `/features/restrict-embedding` を掛けたデッキを `/player/<id>` で埋め込むと、空箱ではなく "You do not have permission to view this deck." という Speaker Deck 自身の画面になる。未認証（シークレットウィンドウ）だけでなく、デッキの所有者本人（ログイン済み）で埋め込んでも同じ画面が出る — **この制限はビューアの閲覧権限ではなく、iframe 経由のアクセスそのものを拒んでいる。** postMessage が来ないことは §16.5 で別途測っており、ここでも新たに反証する動きはない。したがって §10.6 のフォールバックは張れず、この状態も受け入れる。著者は挿入した瞬間に自分の NodeView で同じ画面を見て、直したければ「リンクに戻す」で素のリンクに戻せる。

### 16.7 マークとラベル

マークは `SPEAKERDECK_MARK_SHAPES`（Speaker Deck のモノグラム）である。§7.3 が「ロゴを足すかはその都度決める」と置いた判断を、ここでも足す側に倒している — ブランドマークは X・Figma に続く 3 例目で、塗りで描くのも 3 例目である（元が塗りの字形だから）。`embedMarkShapes` の分岐を足さなければ既定の再生マークが黙って出る（§14.8 の注意がそのまま当たる）。

**Figma と違い、形は書き起こさず公開されているパスを使う。** あちらが幾何で書けたのは円と角丸矩形 5 つだからで、こちらは書体の曲線を持つ字形 2 つなので、書き起こせば「ロゴの絵」になる。X_MARK_SHAPES が同じ理由で公式のパスを使っている。

寸法だけは直す。公開されているマークは 32×20 で、24 幅に合わせると 16px で隣の 2 つ（いずれも約 21.5 幅）より重く出る。そこで**横幅 21.5 に縮めて 24 の箱の中央に置く**。16 / 24 / 40px を明暗 2 スキームで並べて確かめた（実測 2026-08-26）。

2026-08-26 に `SLIDES_SHAPES`（SlideShare と共有していた、画面と脚を描いた図形）から変更した。共有していた理由は「デッキはどちらのサイトにあっても再生するものではない」で、それは今も真だが、**著者が見た目で選んだ結果、プロバイダを名指すほうを採る**。SlideShare も同日にこの判断に揃い、`SLIDES_SHAPES` は使う側が無くなって削除された（§14.8）。

ラベルは `{ lead: 'Speaker Deck', detail: '' }` である。参照が持っているのは ID だけで、**ID は人が読むものではない**。§14.8・§15.7 と同じで、取得なしにデッキを名指すことはできない。

### 16.9 埋め込みコードのペーストを引き金にする（2026-08-26 決定）

**決定: Speaker Deck の埋め込みコードを本文に貼ると、埋め込みブロックになる。**

§16.3 の手順が高すぎた。Share →「Copy iframe code」で得られるのは markup であって URL ではないので、著者はそこから `src` の値を手で取り出す必要があった。**「Copy link」を押したくなるのに正解が「Copy iframe code」である**という点が、この 1 プロバイダだけ他と違うところで、手数はその後段にある。

#### 受ける 2 形

| 貼ったもの                                                                        | 結果                                                  |
| --------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `<iframe class="speakerdeck-iframe" … src="…/player/<id>" …>`（Copy iframe code） | 埋め込み                                              |
| `<script … class="speakerdeck-embed" data-id="<id>" …>`（Copy JS code）           | 埋め込み                                              |
| 素のプレイヤー URL                                                                | 今までどおり（リンク → バブルの「埋め込みにする」）   |
| 上の 2 形を、選択範囲の上に貼る                                                   | 今までどおり（`setEmbed` はキャレットのときだけ働く） |
| 上記以外のペースト全部                                                            | 今までどおり                                          |

判定は `speakerdeckSnippetHref`（`lib/speakerdeck-snippet.ts`）で、引き金は先頭が `<iframe` または `<script` であることに限る。スニペットを引用した文章まで拾うと、著者が残したかった文字を消すことになる。

#### §5 の「ペーストは引き金にしない」への例外である

§5 があの規則を置いたのは「行に単独の URL を素のリンクとして貼る手段が無くなる」からで、**埋め込みコードは素の URL ではない**。今のペースト挙動を実測した（2026-08-26）:

| 貼ったもの                                                     | 今どうなるか                                                               |
| -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| iframe コード（`text/plain` のみ — Copy ボタンが実際に書く形） | 文字列として入り、`src` の URL がオートリンクされる                        |
| JS コード（`text/plain` のみ）                                 | 文字列として入り、`//speakerdeck.com/assets/embed.js` が壊れたリンクになる |
| iframe コード（`text/html` を伴う、描画済み markup のコピー）  | schema が `<iframe>` を落とし、**何も残らない**                            |

守るべき挙動がここには無い。**コードブロックの中では発火させない** — 「このスニペットについて書く」用途は実質そこにあり、判定はノードの spec が `code` かどうかを訊くので、そう宣言するノードは自分で答える。

`text/html` 側は扱わない。3 行目の状態は今のままである。

#### 保存されるのは、組み直した正規形である

**スニペットから取り出した文字列がそのまま `data-href` に入ることはない。** 取り出すのは ID だけで、保存されるのは `https://speakerdeck.com/player/<id>` を組み直したものであり、しかも `resolveEmbed` が通した ID しか入らない。したがって保存され得る文字列は固定のプレフィックス + 16 進小文字に限られ、引用符もエスケープも percent-escape も原理的に含まれない。**著者が打てる文字列の形は広がるが、保存できる文字列の集合は広がらない。**

`iframe` 形では、ID を抜く前に、著者が貼った `src` そのものを `resolveEmbed` に訊く。抜いてから組み直すだけだと `<iframe src="https://evil.example/player/<id>">` が Speaker Deck のデッキに化ける — 描画されるものは無害だが、貼られた URL を黙って別のホストに付け替えるのはこの関数の仕事ではない。

`script` 形では `data-id` だけを読み、**`src` には触れない**。あの属性が指すのは Speaker Deck 自身の `embed.js` で、§6 の「第三者のスクリプトを自オリジンで走らせない」は例外を持たない。文字列から属性を 1 つ読むことはスクリプトを走らせることではないが、後日そこへ滑らないよう明示してある。

DOM は組まない。Speaker Deck のボタンは `data-clipboard-text` 経由で `text/plain` を書く（実測 2026-08-26。`text/html` を併せて書くかは測っていないが、読むのは `text/plain` なのでどちらでも同じ結果になる）ので入力は文字列であり、文字列のまま読めば「HTML パーサが攻撃者の markup をどう扱うか」という問い自体が発生しない。

#### 挿入位置

空の textblock に貼ったときはその block を置き換え、そうでなければキャレットのある textblock の後ろに入れる（`setEmbed`、`embed-extension.ts`）。**空行に貼って空段落が残る形は採らない** — エディタでは見えず markdown には在る行になる。文の途中に貼った場合に段落を割らないのは `insertCodeBlock` と同じ理由である。置ける場所の判定は `canPlaceAfterCaret` で、置けない場所（表のセル、アコーディオンのタイトル）では発火せず、ペーストは今までどおり文字列になる。選択範囲の上に貼った場合も同じで、`setEmbed` はキャレットのときだけ働く。

取引には `uiEvent: 'paste'` を載せる。この編集面の他の `handlePaste` が全部そうしているためで、prosemirror-history がこれを読んで直前の入力と束ねないようにする。実測では載せなくても束ならなかったが、あの grouping の形に依存しない。

#### 却下した 2 案

**ピッカーの検索欄でスニペットを受ける形**は §5 に一切触れずに済むが、「埋め込みコードをリンク検索欄に貼る」を思いつく著者はいない。§5 を守る代償として発見可能性を全部払うことになる。

**デッキページの URL のままエディタが ID を引く形**（`og:image` の `presentations/<id>/` から取る）は、他の 4 プロバイダと完全に同じ操作になる唯一の案である。採らないのは 2 つの代償による: `/api/link-preview` は image を署名済みプロキシパスで返すのでルートの改修が要ること、そして**埋め込みが成立するかどうかが取得の成否に依る**状態になること — §14.7 が `isEmbedAllowed` で断ったのと同じ線である。カードのための取得は既に走っているので新規リクエストは増えないが、増えないことは §3.2 の外側に出ない理由にはならない。

### 16.10 デッキページの URL には、どのボタンを押すのかを言う（2026-08-26 決定）

**決定: リンクバブルが speakerdeck.com のデッキページを指しているとき、1 行を添える。**

> 埋め込みにするには Share →「Copy iframe code」の内容を貼り付けてください

§16.9 が手数を減らしても、**押すべきボタンが「Copy link」ではないことは誰も教えてくれない**。デッキページの URL はどのプロバイダも名乗り出ないので、バブルに出るのは「カードにする」だけで、埋め込みが別の Copy ボタンの向こうにあるという事実は画面のどこにも無い。他の 4 プロバイダにはこの段が存在しない — アドレスバーの URL がそのまま埋め込みになるからである。

判定は `isSpeakerdeckDeckPage`（`lib/speakerdeck-snippet.ts`）で、`resolveEmbed` が拒んだ speakerdeck.com の URL のうちパスが 2 セグメントのものに出す。ユーザーページとトップページは外れる。**取得はしない**（§3.2）。ID がページのどこかにあるかどうかは訊かず、URL の形だけで決める。

置き場所はバブルの左の列で、題と URL の行が既に並んでいるところの 3 行目である。カードは 1 行のままで、`max-w` の制約（§5.5.19）も動かない。この行だけが折り返す — 他の行は truncate するが、これは文であって参照ではない。

折り返しは 1280px で 2 行、390px で 3 行、360px でも 3 行である（実測 2026-08-26）。**文を短くしても 360px では 3 行のままで**、語を削る 4 案を測っても行数は変わらない — 3 行目は幅の帯であって語数の問題ではない。

色はエディタ自身の琥珀色（`#9a6700` / dark `#d29922`）で、未完了の脚注 3 状態が既に話している声である。**最初は URL の行と同じグレーで出しており、計算後の色が完全に一致していた**（実測 2026-08-26）ので、エディタが言っていることではなく参照の 3 行目に見えていた。バブルの 3 色はこれで「青 = 押せる行き先、グレー = 参照、琥珀 = エディタの発言」と読める。

区切り線を引く案と ⚠ を付ける案も並べて比べた。線は favicon の列を跨いで折れて見え、高さも 9px 増える。⚠ はこれを誤りとして提示することになり、**この参照がカードになるのは誤りではない**という §16.10 の立場と合わない。

§15.6 の Figma の 1 行と同じ性格の機構である。あちらとの違いは出る面で、Figma は埋め込みが既にできた後の NodeView に出る（読者に見えないことを著者が知りえないため）のに対し、こちらは埋め込みがまだできていないバブルに出る。カードにする道は塞がない — この参照がカードになるのは正しい結果でもあるので、これは誤りの通知ではなく案内である。

## 17. Docswell（2026-08-26 決定）

スライドページの URL を埋め込みにする。§3.3 のとおり、カードとの二択は著者に出さない。

実測はすべて headed の system Chrome + Playwright + ローカル HTTP 親（アプリを経由しない形）で取った（§14 の手順）。SlideShare で challenge を食った node fetch の経路は、ここでは通っている — 3 デッキとも 200 で、題と 1 枚目が 40–451ms で返る。

### 17.1 §3.1 の 3 問を通した結果

1. **カードは動く。** `og:title` は先頭から 771 バイト目、`og:image`（1 枚目のスライド）は 1010 バイト目で、どちらも 64KB の上限の遥か内側にある。Figma の §15.1 のようにバイト位置で落ちることはない。ただし**説明はデッキのものにならない** — Docswell は `og:description` を `<meta name="og:description">` と綴っており（`property=` ではない、実測 2026-08-26）、`extractDescription` が読む og は `property=` の 2 順だけなので当たらない。落ちる先は `<meta name="description">` で、そこにあるのは「ドクセルはスライドやPDFをかんたんに共有できるサイトです」というサイト共通の 1 文である。つまりカードは題と 1 枚目を持ち、説明の行はどのデッキでも同じ文になる。これは §3.1 の「動く」の基準（取得できること）を満たしており、埋め込みを足す判断は 3 番目の問で決める
2. 動くので 3 番目を訊く。**埋め込みが足すのは「読者がその場でデッキをめくれる」ことである。** §14.1・§16.1 と同じ答えで、カードが出すのは 1 枚目 1 枚だけである
3. 実測でめくれる。前後の矢印・目次・全画面がコントロール列に並び、SlideShare と違って同意バナーは出ない

### 17.2 受け付ける URL の形

スライドページ `/s/<user>/<key>-<slug>` を受ける。key はパス第 3 セグメントの最初の `-` までで、`DOCSWELL_KEY` が形を検証する（`YOUTUBE_ID` と同じ理由 — `src` に入る値だから）。

| 形                                                      | 結果                                                                 |
| ------------------------------------------------------- | -------------------------------------------------------------------- |
| `www.docswell.com/s/<user>/<key>-<slug>`                | 埋め込み                                                             |
| `docswell.com/…`（`www` 無し）                          | 埋め込み（apex は転送せずそのまま 200 を返し、key は同じ位置にある） |
| `/s/<user>/<key>`（slug 無し）                          | 埋め込み（302 で slug 付きへ転送される）                             |
| `/s/<user>/<key>-<slug>#p5`・`/s/<user>/<key>-<slug>/5` | 埋め込み（ページを引き継ぐ — §17.3）                                 |
| `/s/<user>/v<key>-<slug>`（**動画**）                   | カード（§17.6）                                                      |
| `/slide/<key>/embed`（埋め込みの URL 自体）             | カード（§14.2 と同じ判断）                                           |
| `/user/<name>`・トップ・タグ・検索                      | カード                                                               |
| key が英大文字と数字以外を含む・33 文字以上             | カード                                                               |

key は `[0-9A-Z]{1,32}` である。実測した 92 件（トップ・タグ 2 種・ユーザーページ・検索結果から収集、2026-08-26）はスライドが全件 6 文字で、字種は `123456789DEGJKLMNPQRVWXYZ` に収まる。長さは測った 1 値より広く取ってある — `FIGMA_KEY` と同じ判断で、狭めて外すと生きているデッキが黙って素のリンクになる。

**小文字を字種に入れないことが、動画を外している機構でもある。** Docswell は動画をスライドと同じ `/s/<user>/<key>-<slug>` の下に置き、key の頭に `v` を付けて区別する（`vYN91PJ`、実測 6 件が全てこの形）。動画の埋め込みは別の口 — `/video/<key>/embed`、`v` を落とした key — なので、`/slide/vYN91PJ/embed` は 404 を返す。key はそもそも大小を区別し、`lk7j5v` は `LK7J5V` が生きているデッキでも 404 なので、**小文字を受けても 404 の `src` しか組めない**。パスも同様で、`/S/…` は 404 である。

### 17.3 `src` は key 形で組む

`https://www.docswell.com/slide/<key>/embed` を組む。これは Docswell 自身が oEmbed の `html` で配る形（`<iframe src="…/slide/LK7J5V/embed" allowfullscreen class="docswell-iframe" width="620" height="349">`）であり、Share の埋め込みコードが `data-src` に書く形でもある。

**このプロバイダには転送も取得も要らない。** スライドページの URL が持っている key が、そのまま埋め込みの key である。SlideShare（§14.3）が 302 を読者のブラウザに任せて §3.2 を保ったのに対し、こちらはその段自体が無い。Speaker Deck の §16.3 との差はさらに大きい — あちらは ID がページの URL に無いために著者に埋め込みコードを掘らせる必要があったが、こちらはアドレスバーをそのまま貼れる。

著者が配られる `<script class="docswell-embed">` は使わない（§6）。同じ markup にある `data-aspect` も使わない — 取得しなければ読めない値であり、箱は §17.4 のとおり 1 式で組む。

**ページは引き継ぐ。** スライドページのプレイヤーは自分のアドレスバーに `#p<n>` を書き（ページの markup に `#p1`…`#p13` が並んでいる）、埋め込みも同じ綴りを読む — `#p5` で 5 枚目から開く。もう 1 つの綴りである `/s/<user>/<key>-<slug>/5` は、ページ側で `#p5` に書き換えられる永続リンクなので、同じ数として扱って `src` の `#p5` に落とす。2 つが食い違う URL（`…/5#p7`）では断片を採る — プレイヤーが最後に書くのが断片だからである。範囲外は Docswell 自身が丸める（13 ページのデッキで `#p99` は 13、`#p0` は 1）ので、こちらがデッキの長さを知る必要は無い。`#p1` は書かない — プレイヤーが最初に開く場所だからである。数はパースした値から組み、著者の文字列は `src` に入らない（§9.3 の規則）。解釈できない断片（`#page5` など）は落とす — これも §9.3 と同じで、先頭から開くほうが未解釈の文字列を書き込むよりましである。

### 17.4 箱と全画面

箱は `height: 0` + `padding-bottom: calc(56.25% + 56px)` で組む。SlideShare の §14.4 と同じ形で、列の高さだけが違う。**プレイヤーは「スライド領域」と「高さ 56px 固定のコントロール列」の 2 つでできている** — 750px 幅と 400px 幅の両方で 56px を実測し、操作しないまま 3 秒おきに 24 秒見ても、ポインタを乗せても、隠れも動きもしない。この式なら列はスライドの下端にちょうど載る（750px 幅でスライドが 750×421.9、列の上端が 422）。列を足さずに 16:9 だけを与えると、同じ列が全スライドの下 56px を覆う — 列はスライドではなくフレームに対して位置を持つからである。

スライド領域を 16:9 に置くのは、今のデッキがその比率で公開されているからである（実測したスライド 18 件のうち 17 件の `data-aspect` が 0.5625 かその ±0.001）。

**16:9 でないデッキは、帯が付くのではなく下が切れる。** ここが §14.4・§16.4 との差で、あの 2 つが「外しても読める」と言えた根拠はこのプロバイダには無い。Docswell のプレイヤーはスライドをフレームの*幅*に合わせ、入り切らない分を捨てる — A4 縦のデッキ `K8NL49` は 750×478 のフレームの中で `#player-main` が 750×1061 になり、読者にはページの上 40% しか見えない。`?mode=extend` でも同じである（同じデッキで実測）。デッキ自身の比率は参照ではなくページの markup にあるので取得しなければ分からず（§3.2）、iframe からは postMessage も来ないので §10.5 の機構で直すこともできない。

**この状態は受け入れる。** §14.6 と同じ理由で、著者は挿入した瞬間に自分の NodeView で同じ切れ方を見る（2 面が同じ `iframe` を組む）。直したければ「リンクに戻す」でカードにできる。

背景は `transparent` である。プレイヤーの `body` は白を塗るので、`#000` は iframe が届くまでの間だけ黒い矩形として出る — §14.4 の SlideShare と同じ理由であって、何も塗らない Speaker Deck（§16.4）とは違う。

全画面は §14.4・§15.4・§16.4 と同じく `allowFullScreen` が決める。`allow=""` のままプレイヤーの「全画面」ボタンを押すと、親の `document.fullscreenElement` が当の `iframe` になる。

### 17.5 読者が払うもの

- **埋め込み 1 本で 26 リクエスト**（`bcdn.docswell.com` 13、`www.docswell.com` 3、GTM 3、video.js の CDN 2、GA・Cloudflare Insights・`t.docswell.com`・`www.google.com` 各 1）。SlideShare の 40（§14.5）と Figma の 36（§15.5）より安く、Speaker Deck の 23（§16.5）に近い

### 17.6 動画と、存在しない key

動画は §17.2 のとおりカードになる。カードは動く — `og:title` と `og:image`（動画のサムネイル）があり、説明は §17.1 のスライドと同じくサイト共通の 1 文になる。**これは劣化ではなく、別種のものを別扱いにした結果である。** `/video/<key>/embed` は素の iframe でそのまま描画する（video.js のプレイヤーが出る）ことも実測しているので、対応させるかどうかは §3.1 を通し直せば決まる話で、その 3 問には掛けていない。

形は正しいが実在しない key は、空箱ではなく「このページは、作成者が公開を停止したか、移動したため見つかりません」という Docswell 自身の 404 ページになる。無言なので §10.6 のフォールバックは張れない。§14.6・§16.6 と同じく受け入れる — 著者は挿入した瞬間に自分の NodeView で同じ画面を見る。

### 17.7 マークとラベル

マークは `DOCSWELL_MARK_SHAPES`（Docswell の立方体）である。§7.3 が「ロゴを足すかはその都度決める」と置いた判断を、§16.7 と同じく足す側に倒している。`embedMarkShapes` の分岐を足さなければ既定の再生マークが黙って出る（§14.8 の注意がそのまま当たる）。

**2 色は 1 つの `currentColor` に潰れるが、絵は保つ。** 立方体の右面が塗りではなく輪郭として公開されているので、潰しても「リボンの奥の面」として読め、面同士が融けて 1 つの塊になることがない（二色の原版と 16 / 24 / 40px を明暗 2 スキームで並べて確認、2026-08-26）。

寸法だけは直す。原寸は 35.21×32 でほぼ正方形なので、**横幅を 21.5 に縮めて 24 の箱の中央に置く** — 結果は 21.5×19.54 で、X の 21.3×19.5 とほぼ同じ占有になる。`IconShape` は transform を持たないので変換は座標に焼き込んであり、小数 2 桁への丸めは焼く前の描画と画素比較して 16px と 24px で差 0、40px で 1 画素である。

2026-08-26 に `SLIDES_SHAPES`（SlideShare と共有していた、画面と脚を描いた図形）から変更した。共有していた理由は「デッキはどちらのサイトにあっても再生するものではない」で、それは今も真である。**共有をやめたのは、単色に潰しても立方体が読めることを実測したからである** — 陰影が潰れて絵が壊れるという当初の見立てが外れた。SlideShare も同日に自分のマークへ移り、`SLIDES_SHAPES` は削除された（§14.8）。

ラベルは既定が `{ lead: 'Docswell', detail: '' }` である。slug は題を slug 化したもので**名前ではなく**、key は人が読むものではない（§14.8・§16.7 と同じ）。ページを引き継いだときだけ `detail` が `5 ページ目から` になる — YouTube の §9.3 が `detail` に開始秒を置くのと同じで、引き継いだ値を黙って持つのは形が揃わない。

## 18. GitHub Gist（2026-08-29 決定）

gist のページ URL を埋め込みにする。§3.3 のとおり、カードとの二択は著者に出さない。

参考にしたのは Zenn の `markdown-guide` と Qiita の記法チートシートで、どちらも「GitHub の埋め込み」として 2 つの別物を持っている — gist と、`github.com/<owner>/<repo>/blob/…` のファイルである。前者だけがここに入る。後者を外す理由は §18.9 に置く。

実測はすべて system Chrome + Playwright + ローカル HTTP 親（アプリを経由しない形）で取った（§14 の手順）。headed と headless の差は出ていない。

**このプロバイダだけは「レジストリに 1 要素」で済んでいない**（§4.3 に追記済み）。`EmbedTarget` に `srcdoc` と `sandbox` が増え、両方の描画段と `components/EmbedFrames.tsx`、NodeView の `onMessage` が触られている。保存形式・class・sanitize・入口は動いていない。

### 18.1 §3.1 の 3 問を通した結果

1. **カードは動く。** `og:title` はページ先頭から 20574 バイト目、`og:image` は 20264 バイト目で、64KB の上限の内側にある（Figma の §15.1 のようにバイト位置で落ちることはない）。ただし**カードは gist の中身を 1 文字も出さない** — `og:image` は `gist-og-image-54fd7dc0713e.png` という全 gist 共通のロゴ画像で、実測した 2 件が同じファイルを指す。`og:description` も `「<題>. GitHub Gist: instantly share code, notes, and snippets.」` という定型で、Docswell の §17.1 と同じ「サイト共通の 1 文」である。題だけが gist ごとに違う
2. 動くので 3 番目を訊く。**埋め込みが足すのは「読者がコードそのものを読める」ことである。** カードが出すのはロゴと題だけで、コードは記事の外にある
3. 実測で読める。`.pibb`（§18.3）はシンタックスハイライトされたコードと行番号を返す

### 18.2 受け付ける URL の形

gist のページ `/<owner>/<id>` と `/<id>` を受ける。id は `YOUTUBE_ID` と同じ理由で形を検証する（`src` に入る値だから）。

| 形                                                          | 結果                                                                       |
| ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| `gist.github.com/<owner>/<id>`                              | 埋め込み                                                                   |
| `gist.github.com/<id>`（owner 無し）                        | 埋め込み（302 で owner 形へ転送される — §18.3）                            |
| `…/<id>?file=<ファイル名>`                                  | 埋め込み（そのファイルだけ — §18.3）                                       |
| `…/<id>.pibb`（埋め込みの URL 自体）・`…/<id>.js`           | カード（§14.2 と同じ判断）                                                 |
| `…/<id>/revisions`・`/starred`・`/discover`・ユーザーページ | カード                                                                     |
| `gist.githubusercontent.com/…`（raw）                       | カード（`x-frame-options: deny` と CSP `sandbox`。埋め込める相手ではない） |
| id が小文字 16 進以外・19 文字以下・33 文字以上             | カード                                                                     |
| owner が英数字とハイフン以外・40 文字以上                   | カード                                                                     |

id は `[0-9a-f]{20,32}` である。2 つの長さが現役で、32 文字（`fa7df2b570a3f16b39e990b2d2c20aae`）と 20 文字（`6cad326836d38bd3a7ae`）の両方が描画する。Speaker Deck の §16.2 と同じ形の範囲指定になる。大文字は別の文字列で、同じ 32 文字を大文字にすると 404 を返すので、字種に `A-F` は入れない。

**owner はこのプロバイダで初めて「id 以外でも `src` に入るパスの一部」になる。** 入れざるを得ない — 違う owner を書いた URL は転送ではなく 404 を返すからである（`wrongowner/<id>.pibb`、実測）。したがって `GIST_OWNER` が形を検証する。GitHub のログインは英数字とハイフンで 39 文字までなので、それがそのまま上限になる。大小は区別しない（`QIITAN/<id>` は `qiitan/<id>` と同じ gist を返す）ので、正規化もしない。

### 18.3 `src` は `.js` で組み、自前の document の中で走らせる

`https://gist.github.com/<owner>/<id>.js` を組み、それを **こちらが書いた HTML document の中に置く**（`srcdoc`）。GitHub が frame 可能な形として配っている `.pibb` は採らない。

| URL                           | `x-frame-options`      | `frame-ancestors` |
| ----------------------------- | ---------------------- | ----------------- |
| gist のページ                 | `deny`                 | —                 |
| `.pibb`                       | `ALLOWALL`             | `*`               |
| `.js`（埋め込みスクリプト）   | `deny`                 | —                 |
| `github.com/…/blob/…`         | `deny`                 | —                 |
| `raw.githubusercontent.com/…` | `deny` + CSP `sandbox` | —                 |

**`.pibb` は描画できるが、測れない。** 返ってくるのは 5054 バイト（4 行の gist）の断片で、`<link rel="stylesheet">` 1 本と `<base target="_parent">` と `div.gist` だけからできており、**スクリプトを 1 本も持たない**。したがって自分の高さを親に言えない。外から測ることもできない — `.pibb` も `.js` も `access-control-allow-origin` を返さないので、読者のブラウザから中身を取って行数を数える道も無い（実測 2026-08-29）。§3.2 が取得を禁じている以上、`.pibb` を frame に入れると**箱は固定するしかなくなる**。それが何を招くかは §18.4 にある。

`.js` は同じ markup を `document.write` の呼び出しとして配る。frame としては `deny` だが、**document の中のスクリプトとして読む分には `x-frame-options` は掛からない**。だからこちらの document の中で走らせられ、その同じ document にこちらの reporter を置ける。高さも、描かれたファイル数も、そこから来る（§18.5）。

**取得も転送も要らない。** ページの URL が持っている owner と id が、そのまま `.js` の owner と id である。owner 無しの形だけが 302 を通るが、それは読者のブラウザが辿る（SlideShare の §14.3 と同じ arrangement）。**302 自身が返す `x-frame-options: deny` は描画を止めない** — 効くのは描画される最終応答の分だけである。

Qiita と Zenn が配る `<script src="….js">` を**そのまま記事に置く形**は採らない（§6）。あれは親のページに直接書き込む形で、こちらの保存形式にもサニタイズにも載らない。ここで使うのは同じ URL だが、走る場所が違う。

**`?file=` は引き継ぐ。** Zenn と Qiita が同じ綴りで文書化している機能で、複数ファイルの gist から 1 つだけを出す（実測: 2 ファイルの gist が 35026 → 13998 バイト。`.js` でも同じく効く）。**これはこのファイルで唯一、著者の文字列が `src` に入る場所である** — 他のプロバイダはすべて検証済みの ID から組み立てる。しかも `src` は HTML 属性の中に書かれる document の中に入るので、`encodeURIComponent` を落とすと属性を閉じてマークアップを書けることになる。`GIST_FILE` で形を検証したうえで必ず通す。除いているのは注入ではなく「ファイル名になりえない文字列」で、パス区切り・制御文字・256 文字以上がそれにあたる。実在しないファイル名は 404 かつ本文 0 バイトで、描かれるものが無いので §18.5 の「0 ファイル」に落ちる。

### 18.4 箱は gist の高さに合わせる

箱は `height: 250px` で公開し、**フレーム自身が報せてきた高さに書き換える**。X の §10.5 と同じ形で、機構も同じ（`components/EmbedFrames.tsx` と NodeView）。

**gist の高さは箱の幅の関数ではない。** 行は折り返さず、長い行は `.blob-wrapper` が横にスクロールするので、720px 幅と 420px 幅で高さが完全に一致する。高さは行数の 1 次式で、**`37 + 22 × 行数`** が実測 4 点すべてに誤差 0 で当たる。そして行数は参照に無い。`padding-bottom` の比率で組む §14.4・§17.4 の形は、ここでは原理的に使えない。

初期値の 250px は測定値ではない。**公開 gist 45 件は 59px から 223,378px まで散っており、X が 250px を採った「実測クラスタ」に当たるものが存在しない。** 記事に貼られるのは短い断片であることが多いので、跳ね幅が小さくなる側に寄せた値である（250px は約 10 行にあたる）。届いた時点で跳ねることは X と同じく受け入れる。

**縮む方向にも動くことが要点である。** 報せる高さは `<body>` の矩形であって `documentElement.scrollHeight` ではない。後者はフレーム自身のビューポートでクランプされるので、**今入っている箱より小さい値を報せられない** — 実測 2026-08-29、6 行の gist が 250px の初期値の中で 250 を報せ続け、下に 90px の白が残ったままになった。`<body>` の矩形を読むと 169px に縮み、これは同じ gist を単独で測った値と一致する。

**固定の箱は一度採って、測りなおして取り下げた。** 400px 固定＋フレーム内スクロールという形を実装し、公開ページを実際にホイールで下って測ったところ、ポインタがフレームに掛かった時点でホイールがフレームのものになり、記事が止まった（1874px の gist の内側が 323px 進み、`window.scrollTo` では 0 のまま — **ポインタ経由でしか起きないので自動テストの走査には出ない**）。これは §8.1 の「`iframe` はページのマウスイベントを飲む」系列である。箱を中身に合わせると、フレーム内にスクロールするものが無くなり、この問題自体が消える。したがって `scrolling="no"` は全プロバイダで無条件のままでよい（§10.8）。

箱は白く塗り、枠を引く。GitHub の markup はコード領域を四辺まで白く塗り、自分の縁を持たないので、白い記事の上では塊がどこで終わるか分からない — §15.4 の Figma と同じ形である。**枠の色は明暗どちらのスキームでも `#d0d7de` のままにする。** GitHub は `data-color-mode="light"` を markup に焼き込んでおり、`?color_mode=dark` などのクエリでは変わらない（4 通り試して全て同一バイト数）。暗色のページに出るのは明色のカードで、そこに暗色の枠を引くと、そうでないものの輪郭を描くことになる。

全画面は他と同じく `allowFullScreen` が決めるが、gist のプレイヤーにその口は無い。

### 18.5 フレームは自分の高さを報せる（このリポジトリで最初の自前プロトコル）

`srcdoc` に置く document がこちらのものなので、その中に reporter を書ける。送るのは 2 つ、**高さと、描かれた `.gist-file` の件数**である。読む側は `components/EmbedFrames.tsx`（公開）と NodeView（エディタ）で、X の §10.5 と同じ 2 面である。

**§10.7 が「自前オリジンのラッパーがあれば全プロバイダを 1 つの `resize` に正規化できる」と保留した形の、gist だけの縮小版である。** 違いはオリジンを立てないことで、document は属性の中にあり、サーバは 1 行も増えない。

**件数 0 は「取得できない gist」の合図である。** GitHub の `.js` は解決しない id に対して何も書かない（実測 2026-08-29）ので、沈黙とは別の、確定した失敗が読める。公開側はそれを素のリンクに落とし（§10.6 と同じ形）、エディタは「取得できない gist です」と言う（§7.2）。沈黙のほうは従来どおり §10.6 の 8 秒の時計が受け持つ。

**reporter は名乗るだけでなく、訊かれたら答える。** document はページと一緒に構文解析されるのに対し、聞き手が張られるのは hydration の後である。名乗りを 1 回だけにしていたとき、この隙間でメッセージが落ち、箱は初期値のまま二度と動かなかった（実測 2026-08-29）。したがって親は mount 時と `load` 時に `{ask}` を投げ、reporter はそれに同じ内容で答える。名乗りのほうは重複を許す — 同じ高さを 2 度当てても何も起きない。差分を見るのは ResizeObserver の経路だけである。

**メッセージの `event.origin` は文字列 `"null"` である。** `allow-same-origin` を与えていないので（§18.6）オリジンが opaque になる。したがって認証はオリジンではなく、エディタでは `event.source === iframe.contentWindow`、公開側では「その id がこちらの持っている箱を指していること」で行う。前者は X で既に使っている検査である。

**document は reporter の `</script>` で終わり、そのあとにタグを閉じない。** React のサーバレンダラはこの属性の中で `</script>` より後を再現せず、`</body></html>` を書いていたときは配信 HTML と RSC ペイロードが食い違って hydration の不一致が出た（React が記録する。実測 2026-08-29、YouTube だけの記事と埋め込みの無い記事では出ないことも確かめた）。どちらのタグも HTML では省略可能で、フレームの解釈は変わらない。**この document に何か足すときは、あのスクリプトより前に置く。**

### 18.6 sandbox — `<base target="_parent">` と、第三者の markup

`sandbox="allow-scripts allow-popups"` を付ける。

`allow-scripts` は、GitHub の `document.write` とその隣の reporter の両方が走る必要があるからである。`allow-popups` は、document が `<base target="_blank">` を置いているので、GitHub 自身の「view raw」がどこかに開けるようにするためである。

**`allow-same-origin` は入れない。** これが第三者の markup を記事のページから隔てている唯一の線であり、代償が §18.5 の opaque なオリジンである。

`.pibb` を採らない理由はもう 1 つあって、こちらの機構では起きない: `.pibb` の断片は `<base target="_parent">` を持ち、`view raw`・ファイル名・❤ の行がリンクである。**読者がその 1 本を押すと、記事そのものが `gist.githubusercontent.com` へ遷移する**（実測。新しいタブでもフレーム内でもない）。既存のどのプロバイダにもできないことだった。`.js` は `<base>` を書かないので、置くのはこちらの `target="_blank"` である。

### 18.7 読者が払うもの

- **埋め込み 1 本で 2 リクエスト**（`gist.github.com` に 1、`github.githubassets.com` の CSS に 1。CSS は複数の埋め込みで共有される）。**本書中で最も安い** — Speaker Deck 23（§16.5）、Docswell 26（§17.5）、Figma 36（§15.5）、SlideShare 40（§14.5）に対する 2 である
- 親のオリジンにも、ブラウザ全体にも cookie は置かれない。同意バナーも出ない
- **JavaScript が無いと箱は空のまま 250px で残る。** `.pibb` なら JS 抜きでも描画された（§18.3）ので、これは可変の高さと引き換えに払っているものである。記事のほかの部分（リンクカード・コードブロック・脚注）はサーバで組まれるので、この 1 ブロックだけの性質である

### 18.8 マークとラベル

マークは `GITHUB_MARK_SHAPES` である。出典は `primer/octicons` の `icons/mark-github-24.svg` で、GitHub 自身のアイコンセットにある 1 パスをそのまま使う（§16.7 と同じく、書き起こさない）。

寸法だけは直す。原寸は 24 の箱いっぱい（bbox 0.5〜23.5）で、16px では隣のマークより重く出るので、**横幅 21.5 に縮めて中央に置く** — 結果は 21.5×20.82 で、X の 21.3×19.5 と同じ占有になる。`IconShape` は transform を持たないので変換は座標に焼き込んであり、**丸めは 2 桁ではなく 3 桁である** — このパスはほぼ全部が相対曲線なので誤差が経路に沿って積み上がる。焼く前の描画と画素比較して、3 桁は 16 / 24 / 40px の明暗 2 スキームすべてで差 0、2 桁では 2 / 12 / 22 画素ずれた。

**ラベルはこのプロバイダだけが本当の名前を持てる。** SlideShare・Speaker Deck・Docswell が provider を lead に置いたのは「取得しなければ item に名前が無い」からだった（§14.8）が、gist の URL は owner を持ち、著者が `?file=` を書けばファイル名も持つ。X の §10.4 と同じ形になる — 既定は `{ lead: <owner>, detail: <ファイル名 or ''> }` で、owner を持たない形だけが `{ lead: 'GitHub Gist', detail: <ファイル名 or id> }` に落ちる。

### 18.9 `github.com/…/blob/…` は埋め込みにしない（2026-08-29 決定）

参考 2 サイトの「GitHub 埋め込み」のもう半分、ファイルへのリンク（`#L1-L3` の行指定を含む）はこのレジストリには入らない。

カードは動く（`og:title` は 28628 バイト目、`og:image` は 28111 バイト目）。しかしカードが出すのは `owner/repo` のソーシャル画像で、**コードは 1 行も出ないし、行指定も反映されない**。§3.1 の 3 番目の問には答えられている — 足すものは「読者がコードそのものを読める」ことである。

入らないのは §3.2 のためである。**GitHub は blob ページに frame 可能な形を持たない** — ページも raw のホストも `x-frame-options: deny` で、後者は CSP `sandbox` も返す。Zenn は `embed.zenn.studio` が、Qiita は自前のバックエンドが、いずれもファイル本文を取得して描画している。同じことをするなら `link_previews` と並ぶ取得層・TTL・バージョンが戻ってくる。「埋め込みは取得を要求しない」は §3.2 が埋め込みの構造上の利点として置いた条項で、1 プロバイダのために緩める理由にはならない。

**答えは別の機構に置く。** blob の URL は、エディタ側で挿入時に 1 回だけ取得して ` ```lang:filename ` の通常のコードブロックに変換する — 読者側の取得はゼロなので §3.2 も §4 も動かず、Shiki・ファイル名ヘッダ・コピーボタン・diff という既存の機構にそのまま乗る。permalink は ref が固定されているので、出典リンクの先もコピーした時のまま残る（ブランチ指定の URL はそうならない）。**どちらの形も受ける** — 実装と、そう決めた理由は §19 にある。

gist をこちらではなく埋め込みにしたのは、**gist が書き換わり続けるものだから**である。コピーを記事に焼き込むと記事が黙って gist と食い違い、GitHub 自身の帰属表示も失われる。X をアカウントと投稿で割った §10 と同じ、URL の形で結果が決まる判断である。

## 19. GitHub の blob（2026-08-29 決定・実装）

`github.com/<owner>/<repo>/blob/…` は埋め込みにならない。エディタが挿入時に 1 回だけファイルを読み、通常のコードブロックに書き換える。§18.9 が下した決定の実装で、本書で唯一「埋め込みでないもの」を書いた節である。

置かれているのは、`lib/github-blob.ts`（URL を読む純粋な半分）、`components/editor/github-blob-import.ts`（取得と挿入）、`lib/rehype-code-source.ts`（公開側のヘッダ）、`LinkBubble.tsx` のボタン 1 つ、両面ぶんの CSS である。**スキーマも保存形式も sanitize も動いていない** — 保存されるのは他のコードブロックと同じ ` ```lang:filename ` のフェンスで、増えたのは公開パイプラインの段が 1 つだけである。

### 19.1 なぜ取り込みで、なぜエディタのブラウザから取るのか

埋め込みにできないことは §18.9 が測った通りで、ページも raw のホストも `x-frame-options: deny` を返す。残る道は 2 つ、コードを 1 行も出さないカードか、1 回のコピーかであり、後者を採った。読者側の取得はゼロなので §3.2 も §4 も動かない。

取得がエディタのブラウザから出るのは、**`raw.githubusercontent.com` が `access-control-allow-origin: *` を返すから**である。200 でも 404 でも返す（実測 2026-08-29）ので、ステータスまで読める。したがってリンクカードが要した機構 — ルート・セッションの門・`lib/guarded-fetch.ts` のアドレス検査・キャッシュ — は**どれも要らない**。サーバが著者の選んだ URL を叩く場面が増えないことが、この設計の一番の性質である。

カードとの差はここにある。カードが読む相手のページは CORS ヘッダを返さないので、あれはサーバから取るしかなかった。

### 19.2 受け付ける URL の形と、バブルの並び

入口は §5 の 1 番目だけである。リンクバブルに 3 つ目のボタン「コードブロックにする」が出て、押した時に取得が走る。**ペーストは引き金にしない** — §5 の理由がそのまま当たる。ピッカーの行（入口 2）にも出さない: あの行はカードのノードを別のノードに置き換えるもので、ここで起きるのは段落の書き換えである。

問う順序は `resolveEmbed` → この節 → `normalizeCardHref` で、blob の URL にはカードを出さない。§3.3 の「1 つの URL に対して意味は 1 つ」を 3 つ目の結果へ伸ばした形である。

| 形                                                           | 結果                                                      |
| ------------------------------------------------------------ | --------------------------------------------------------- |
| `github.com/<o>/<r>/blob/<ref>/<path>`                       | コードブロック（`<ref>` はブランチでも 40 桁の SHA でも） |
| `…/blob/refs/heads/<branch>/<path>`                          | コードブロック                                            |
| `…/blob/<ref>/<path>#L12`・`#L12-L20`・`#L12C4-L20C9`        | コードブロック（その行だけ — §19.3）                      |
| `…/tree/…`（ディレクトリ）・`/blame/`・`/commits/`           | カード                                                    |
| `…/raw/…`                                                    | カード（raw のホストへの転送で、こちらが自分で組む形）    |
| リポジトリのページ・ユーザーのページ                         | カード                                                    |
| `raw.githubusercontent.com/…`・`gist.github.com/…`           | カード / gist の埋め込み（§18）                           |
| owner が 40 文字以上か英数ハイフン以外、repo が 100 文字以上 | カード                                                    |
| 拡張子がテキストでないもの（`.png`・`.pdf`・`.woff2` ほか）  | カード                                                    |

owner の形は §18.2 の `GIST_OWNER` と同じ理由で検証する（`src` ではなく取得先に入る値だから）。repo はドットと下線も許す点だけが違う。

**ref とパスの境目は URL に書かれていない。** ブランチ名はスラッシュを含めるので、`/blob/feature/x/a.ts` はブランチ `feature` のファイル `x/a.ts` とも、ブランチ `feature/x` のファイル `a.ts` とも読める。分けられるのはリポジトリの ref 一覧を訊いた時だけで、それは 2 本目の要求になる。訊かないことにした根拠は、**曖昧さが取得に届かない**ことである — `raw.githubusercontent.com` は `<ref>/<path>` をそのまま受けるので、どちらの読みでも同じ 1 本の URL になり、中身は正しい（実測 2026-08-29、`refs/heads/main` の形を含む）。届くのは表示されるパスのほうで、スラッシュ入りのブランチでは先頭に 1 階層余分に付く。ファイル名そのものは常に正しく、ヘッダのフィールドは編集できる。

**テキストでないファイルは取り込まない。** 拡張子が `BINARY_EXTENSIONS` に当たる URL はこのレジストリが名乗らず、カードに落ちる。Qiita は「ファイルのサイズが大きい場合や、テキストファイル以外の場合はリンクのみが表示されます」と書き、Zenn もテキスト以外は埋め込まない。両者はサーバで取得してから決めているが、ここは取得しないので URL だけで決める。

**拒否リストであって許可リストではない。** テキストファイルは拡張子を持たないことが多く（`LICENSE`・`Dockerfile`・`Makefile`・`.gitignore`）、許可リストはそれらを全部落とす。外し方の代償が非対称だからである — 拒否リストが漏らすと「押して失敗し、トーストが出る」（`readBlob` の content-type が第 2 の網で、こちらは欺けない）が、許可リストが漏らすと**取り込めるはずのファイルが取り込めない**。前者のほうが安い。この判定を入れる前は `.png` にもボタンが出て、**押せば必ず失敗した**（2026-08-29）。

**大きさのほうは URL から分からないので、押す前には決めない。** 64KB を超えたときに「行指定を付けてください」と言う形（§19.5）を保つ。Qiita の「リンクのみ」より、著者にできることを言っている。

`..` は防いでいない。**どの綴りでも `new URL()` が先に潰す** — `..`・`%2e%2e`・`%2E%2E`・`.%2e` の 4 つとも `/blob/main/../etc/passwd` を `/blob/etc/passwd` にする（実測 2026-08-29）。潰されずに残るのは区切り文字を書いた `%2f` と壊れた `%zz` で、こちらは拒む。

### 19.3 取ってくるもの

取得先は `https://raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>` で、**検証済みのセグメントから組む**。著者の文字列がそのまま取得先になることは無い（§6.1 の教訓が当たる唯一の場所である）。要求は資格情報を付けず、`referrerPolicy` は `no-referrer`、10 秒で打ち切る。

`#L…` の行指定は引き継ぐ。列まで書かれた形（`#L12C4-L20C9`）は列を捨てて行だけを読む — フェンスが持てるのは行単位だからである。行が指定されていれば、ファイル全体を読んだうえでその範囲を切り出す: raw に行の指定は無いので、`#L4000` に届くにはそこまでを読むしかない。範囲の終わりはファイル末尾で丸め、始まりが末尾を越えている時だけ失敗として言う。

言語は拡張子から決めるが、**範囲はコードブロック自身のメニューに限る**（`CODE_LANGUAGES`、28 個）。載っていない拡張子は `language: null`、つまり素の ``` フェンスになる — 著者が「Plain Text」を選んだ時と同じ状態で、後からドロップダウンで選び直せる。メニューに無い id を書き込むと、著者はそれを選び直せないし、公開側の Shiki に解決させたことも無い。

改行は CRLF を LF に正規化する。ネットワークから来るものはこのリポジトリが保存している形とは限らず、`\r` を持ったままのコードブロックは、各行が不可視の文字で終わるフェンスになる。

### 19.4 出来上がるもの — 出典はヘッダに入る

リンクのあった段落が、コードブロック 1 つに置き換わる。**ブロックの下には何も残らない。**

`filename` に入るのは**パスではなく blob の URL そのもの**である。これが成り立つのは、markdown の info string が空白を含まない文字列なら何でも通し、`lib/rehype-code-filename.ts` が**最初のコロン**で切るからで、` ```ts:https://github.com/o/r/blob/main/a.ts ` は language `ts`・filename `https://…` として往復する。この 1 点が、専用ノードも保存形式の新しい綴りも sanitize への追加も要らなくしている。

読み戻すのは `blobSourceFromFilename` で、エディタの NodeView と公開側の段（`lib/rehype-code-source.ts`）が同じ 1 つの関数を訊く。出るのは GitHub のマークと `owner/repo` とパスからなる 1 行のリンクで、ファイル名フィールドの**代わりに**立つ — 参照は名前ではないので、書き換えられる入力欄に生の URL を置いておく理由が無い。マークのパスは `lib/github-mark.ts` にある: 描く側が両端に分かれたので、両方から import できる `lib/` へ下ろした。

**リンクの当たり判定は、両面とも書いてある文字列の幅である。** 幅いっぱいのアンカーは幅いっぱいのクリック領域で、外れた一撃が読者を記事から連れ出す。行を埋めていたときは `o/r › a.ts` でも `packages/react/index.ts` でも箱は同じ 500px（公開側 748px）で、ヘッダの行がまるごとリンクだった（実測 2026-08-30）。今は 108px と 127px である。

ここが置き換えたファイル名の `<input>` は行を埋めていてよかった — 外れたクリックはフィールドに入るだけだからである。リンクは同じ面積を持てない。

**そのうえでセレクタ・トグル・ボタンは右端に残る。** 短い名前で真ん中に寄ってしまうのが、アンカーを縮めることの代償だった。押し出しているのは言語 `<select>` の `margin-left: auto` で、アンカーが伸びているのではない — **間の空きはどちらの当たり判定でもない**。ファイル名の `<input>` が出ているときは空きが無いので、この指定は 0 に解決し、普通のコードブロックのヘッダは 1px も動かない（実測 2026-08-30、入力欄 587px・右端との隙間 8px は前後で同じ）。

**ヘッダの名前は 1 色である。** `owner/repo` の側とパスの側を塗り分けていたが、1 つの参照ではなく 2 つのものに読めた（2026-08-29、著者の指摘）。分けているのは `›` で、これも同じ色である。**区切りに `/` は使わない** — `owner/repo` の中にもパスの中にも GitHub 自身が書いた `/` があり、同じ字が「文字列の一部」と「こちらが入れた境目」の 2 つを意味することになる。見分ける手がかりが前後の空白しか無かった（2026-08-29、著者の指摘）。塗り分けは、既に muted な色に不透明度を重ねる形でもあって、明色スキームで 1.70:1 まで落ちていた（実測 2026-08-29、下限は 4.5:1）。今は 12.6:1（明）と 13.7:1（暗）で、エディタと公開側が同じ 1 色を使う。公開側の色は継承ではなく**明示する**: `inherit` は `<figcaption>` に届き、そこは @tailwindcss/typography が `--tw-prose-captions`（L\*48 前後の灰）で塗っているので、ヘッダだけが薄く見えていた。

出典をヘッダに入れたのは、最初に採った「ブロックの下にリンクを 1 行」が画面で読みづらかったからである（2026-08-29、著者の指摘）。コピーである以上どこかに出典が要るのは §18.9 の理由のままで、変わったのは場所だけである。行指定は URL に残るので、リンクの先も行を指す。

見た目は Zenn の GitHub 埋め込みに寄せているが、**機構は寄せていない** — あちらは読者のページから毎回ファイルを取得している。ここが持っているのは挿入時のコピー 1 つで、読者側の取得はゼロのままである（§19.1）。

**戻る道も付いている。** 取り込んだブロックのヘッダには「リンクに戻す」があり、押すとブロックが元の blob URL のリンク 1 行に戻る。埋め込みとリンクカードが持っているのと同じ名前で、同じ振る舞いである。出るのは**参照を持っているブロックだけ**で、手で書いたコードブロックには戻る先が無いので出ない。参照は保存されたファイル名から読み直すので、別のセッションで取り込んだ記事を開いてもボタンはそこにある。書き換えたコードは捨てられる — 埋め込みの「リンクに戻す」がフレームに対してすることと同じで、Ctrl-Z 1 回で戻る。

**狭いヘッダが幅を渡す先は、そのブロックが名乗っているファイルである。** 30rem 未満では、`owner/repo` の側を truncate ではなく落とす。**「リンクに戻す」は幅で見た目が入れ替わる** — 広いところでは文字だけ（アイコンは流れの外）、狭いところではアイコンだけ（ラベルは視覚的に隠れ、アクセシブル名としては残る）で、リンクカードの操作帯が元から採っている規則にそのまま乗る（2026-08-29、著者の指摘）。両方を縮めると 420px で `fac… / pack…` になり、どちらの名前にもならなかった（実測 2026-08-29）。同じリポジトリの 2 つのブロックはパスで違うので、幅を持つ価値があるのはパスの側である。参照の全体はリンクの `title` に残る。

**挿入は 1 トランザクションなので、取り消しも 1 回である。** `prosemirror-history` の現在のイベントは `uiEvent` メタで閉じる: 閉じないと、直前の入力と同じイベントに入って Ctrl-Z が両方を巻き戻す（実測 2026-08-29）。

置ける場所の判定は `linkToCard` と同じ問いで、`canPlaceAfterCaret` ではない — ここで起きるのはリンクの居る段落そのものの置き換えだからである。リンクが行全体を占めていることも要る。

**取得が返るまでに文書は変わりうる。** これはこのエディタで初めての非同期の挿入で、他の入口はすべて同期である（`resolveEmbed` は純粋関数として作られている）。覚えておいた `{from, to}` はその間に落ちた編集の分だけ古いので、範囲は各トランザクションの `mapping` で写像し続け、返ってきた時点で「そこがまだ同じリンクだけの行か」を測り直す。違っていれば何も入れず、著者にそう言う。リンクの行の中で入力した場合も同じ答えになる — その行はもうリンクだけの行ではない。

### 19.5 失敗の言い方と、引き受ける帰結

失敗は `BLOB_NOTICES` の 6 つで、いずれもトーストで言い、**リンクはそのまま残る**。押して駄目でも著者は何も失わない。

- 取得できない（`GitHub からファイルを取得できませんでした`）。私有リポジトリ・消えたファイル・存在しない ref・ディレクトリはすべて 404 で、**外からは区別できない**（実測 2026-08-29）。文言が 1 つなのはそのためで、著者が確かめる先も 1 つである
- テキストでない。raw はソースを `text/plain` で、それ以外をそれ自身の型で返す（`.ico` が `image/vnd.microsoft.icon`、実測）。バイナリを文書に入れないのはこの 1 行である
- 大きすぎる。取得は 2MB、文書に書くのは 64KB で止める。**後者は著者が感じる数**で、全体では越えるファイルも行指定を付ければ通る
- 指定された行が末尾を越えている・取り込み中の二重押し・リンクが動いた

引き受けているもの:

- **コピーなので、記事は元のファイルと黙って食い違っていく。** permalink（40 桁の SHA）なら出典リンクの先も固定されるが、ブランチ指定の URL では先だけが進む。どちらも受けるのは、著者が実際に貼るのは大半がブランチの形だからである
- **取り込んだブロックのファイル名は、その場では書き換えられない。** 入力欄はリンクに置き換わっている。名前を付け直したいなら、URL でないファイル名を持つ普通のコードブロックにするしかない
- 行番号は出ない。コードブロックが元から出していないもので、gist の埋め込み（GitHub 自身の行番号が出る）とは見え方が揃わない。**行番号は blob ではなくコードブロック全体の問いである**（2026-08-29、別件として送った）

### 19.7 挿入時に SHA へ固定する案は採らない（2026-08-29 却下）

ブランチ形の URL を貼ったとき、その時点の SHA を解決して permalink の形で保存すれば、§19.5 の「コードは記事の中で止まっているのに、出典リンクの先だけ進む」食い違いが消える。**技術的にはできる。** `https://api.github.com/repos/<o>/<r>/commits/<ref>` に `Accept: application/vnd.github.sha` を付けると本文が 40 桁の SHA だけで返り、`access-control-allow-origin: *` なので raw と同じく著者のブラウザから直接叩ける。存在しないリポジトリは 404 で、これも CORS 付きである（実測 2026-08-29）。

**採らないのは、外部 API への依存を持ち込むからである。** §19.1 が持っている一番の性質は、取得が「制限も鍵も持たない要求 1 本」で済むことで、この API はそれを壊す:

- 未認証のレート制限は **60 回/時、しかも IP 単位**である（実測 `x-ratelimit-limit: 60`）。記事を書いている最中に「今は取り込めない」が起こりうる状態を、この機能が初めて持ち込むことになる
- §19.2 の ref とパスの曖昧さが、ここで初めて実害になる。`/blob/feature/x/a.ts` の ref が `feature` か `feature/x` か決められないので、どちらで叩くかが決まらない。両方試すか、ref 一覧をもう 1 本取るかで、要求はさらに増える

食い違いが問題になるなら、**取得を増やさない側で答える** — バブルに permalink を勧める 1 行を出す形（Speaker Deck の §16.10 と同じ、取得ゼロ）が候補である。こちらもまだ作っていない。

## 20. CodeSandbox（2026-08-30 決定）

サンドボックスのページ URL を埋め込みにする。§3.3 のとおり、カードとの二択は著者に出さない。

実測はすべて headed の system Chrome + Playwright + ローカル HTTP 親（アプリを経由しない形）で取った（§14 の手順）。カード側は `lib/link-title.ts` と同じ抽出器を写した node fetch で測った。

### 20.1 §3.1 の 3 問を通した結果

1. **カードは動かない。** ここが §9 以降のどのプロバイダとも違う点で、og が足りないのではなく**ページが 1 バイトも取れない**。`/p/sandbox/<id>`・`/s/<id>`・`/s/<slug>-<id>`・`/api/v1/sandboxes/<id>`・`…/screenshot.png` はいずれも Cloudflare Turnstile の 403（`<title>Just a moment...</title>`）を返す。UA は無関係で、ブラウザ相当のヘッダ一式・UA のみ・UA 無し・`Twitterbot/1.0` の 4 通りすべてで同じ 403 である。したがって `fetchLinkPreview` は `null` を返し、`status` は `failed` になり、`lib/rehype-link-card.ts` の `fallbackLink` が効いて**素のリンクに落ちる** — 題も説明も画像も無い

   **主張の範囲**: 測ったのは自動化されたクライアントだけである。headed の実 Chrome でも Turnstile は**クリアせず再現した**（`challenges.cloudflare.com/cdn-cgi/challenge-platform/…/turnstile/…` へのナビゲーションを実測）ので、「人の手のブラウザなら 200」という対照は取れていない。SlideShare の §14 が headless の artifact だったのとは逆の結果である。決定に効くのはそこではなく、**`fetchLinkPreview` がこのホストから出るサーバ側の node fetch であり、403 を食ったクライアント形そのものである**という点である

   例外が 2 つある。`/embed/<id>` は 200 を返し og を一式持つ（`og:title` はサンドボックスの題、`og:image` は `…/sandboxes/<id>/screenshot.png`）。テンプレートの別名 `/s/new` も 200 である。**ただし前者の `og:image` は実在 id では 403 を返す**ので、`/embed/` をカード側に落としても画像は死ぬ

2. 動かないので、§3.1 の 2 番により埋め込みが**リッチな扱いの**唯一の選択肢になる。ただしこれは「足さねばならない」ではない — §3.3 の素のテキストリンクが落とし所として常に残っており、足さないという判断も筋が通っていた
3. 実測で動く。実在 id 5 件が完全に描画した — エディタ（CodeMirror、タブ 3 枚）、プレビュー（`<id>.csb.app` で実際に動くアプリ）、下段のコンソール／Problems／React DevTools 列

### 20.2 埋め込みが足すもの — **`runonclick` によって半分が「クリックで」になる**

**答えは「読者がその場でコードを読め、クリックすればその場で動かせる」である。** §20.5 のとおり `runonclick=1` を付けて組むので、**プレビューは読者がクリックするまで走らない**。

これを 1 行として引き受ける。コードが読めることは読み込み直後から得られており、埋め込みの価値の重心はそちらにある — カードが取得できない以上、足さなければ読者が得るのは URL の文字列だけである。**動く結果は 1 クリック遠くなった**。この取り引きが §20.6 の数字を買っている。

### 20.3 受け付ける URL の形

**id を取り出さない。パスの最終セグメントをそのまま `/embed/` に渡す。** これは Zenn が出している形そのもの（実測: 著者が `eager-proskuriakova-2lcdqm` と書き、Zenn の `src` も `/embed/eager-proskuriakova-2lcdqm`）であり、CodeSandbox の埋め込み口が slug 付き・裸 id のどちらでも 200 を返すために採れる（`/embed/react-example-xgzdk` と `/embed/xgzdk` が同じサンドボックスを出す、実測 2026-08-30）。

**分解しないことが `react-new-devbox` の類を守っている機構でもある。** 最後の `-` の後ろを id とみなす規則を書くと、slug ではなく名前そのものであるセグメント（`react-new-devbox`）から `devbox` を切り出して、存在しないサンドボックスの `src` を組んでしまう。セグメントを触らなければその誤りは起こりえない。

| 形                                                  | 結果                                                                    |
| --------------------------------------------------- | ----------------------------------------------------------------------- |
| `codesandbox.io/p/sandbox/<seg>`                    | 埋め込み（現行の正規形 — `/s/new` が 307 でここへ転送される）           |
| `codesandbox.io/s/<seg>`（`<slug>-<id>` 含む）      | 埋め込み（レガシー。転送先と同じ `src` を組むので追跡は要らない）       |
| `www.codesandbox.io/…`                              | 埋め込み（`www` 付きも 200 を返す。§17.2 が apex を入れたのと同じ判断） |
| `codesandbox.io/p/devbox/<seg>`                     | **カード**（§20.13 — フレームを拒まれることを実測した）                 |
| `codesandbox.io/embed/<seg>`（埋め込みの URL 自体） | カード（§14.2・§17.2 と同じ判断）                                       |
| `/examples/…`・`/u/<name>`・トップ・検索            | カード                                                                  |
| セグメントが英数字とハイフン以外を含む・65 文字以上 | カード                                                                  |

セグメントは `[0-9A-Za-z-]{1,64}` である。`CODESANDBOX_SEGMENT` がこの形を検証する（`YOUTUBE_ID` と同じ理由 — `src` に入る値だから）。実測した id は 5・6・10 文字（`xgzdk`・`2lcdqm`・`y2lrywpk21`）で、slug 付きは 26 文字（`eager-proskuriakova-2lcdqm`）まで見ている。長さは測った値より広く取ってある — `FIGMA_KEY`・`DOCSWELL_KEY` と同じ判断で、狭めて外すと生きているサンドボックスが黙って素のリンクになる。

**大小は区別しない。** `/embed/XGZDK` は `/embed/xgzdk` と同じサンドボックスを返す（実測）ので、字種に両方を入れ、正規化はしない。Docswell の §17.2 が小文字を落として動画を外していたのとは事情が違う。

### 20.4 `src` は最終セグメント形で組む

`https://codesandbox.io/embed/<seg>?runonclick=1` を組む。取得も転送も要らない — ページ URL が持っているセグメントが、そのまま埋め込みのセグメントである。§3.2 がここで自明に成り立つ。

**出典**: Legacy Sandboxes 向けに CodeSandbox 自身が配っている形である（`codesandbox/docs` の `legacy-sandboxes/embedding.mdx`「エディタのヘッダの Embed から」）。Qiita と Zenn が配っているのも同じ形で、実測でも 200 を返して描画する。§17.3 の「プロバイダ自身が配る形を使う」を満たす。

ダイアログの画面そのものは見ていない（アプリのページが §20.1 の 403 の向こうにある）が、**それは docs で置き換えられる** — `codesandbox.io/docs/…` は 403 でも、`codesandbox/docs` は public のリポジトリなので raw から読める。§20.13 の原因もこの経路で分かった。

### 20.5 `runonclick=1` は著者の文字列に無く、こちらが足す

**Zenn の実装から採った。** 著者が書くのは `@[codesandbox](https://codesandbox.io/embed/…?fontsize=14&hidenavigation=1&theme=dark)` で、Zenn が出す `src` にはそこに無い `runonclick=1` が付いている（実測 2026-08-30）。§4 の「`src` はこちらが組み立てる」「著者の文字列は `src` に入らない」と同じ規律である。

同じ 60 秒の観測窓・同じ親・ネットワークリクエストのみで比較した:

| `src`                                                    | リクエスト | 起動したオリジン                                                                                   |
| -------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------- |
| `?runonclick=1`                                          | **64**     | `<id>.csb.app` 無し、`prod-packager-packages` 無し、`data.jsdelivr.com` 無し、`col.csbops.io` 無し |
| `?fontsize=14&hidenavigation=1&theme=dark`（Qiita の形） | 114        | 全部                                                                                               |
| パラメータ無し                                           | 111        | 全部                                                                                               |

**44% 減で、バンドラもプレビューの別オリジンも読者がクリックするまで起動しない。** クリック後は 112 まで戻る（実測）ので、これは総量の削減ではなく**支払いの延期**である — 押した読者は同じだけ払う。押さない読者が払わずに済むことが、この 1 語が買っているものである。

**他のパラメータは付けない。** `theme` / `fontsize` / `hidenavigation` / `view` はいずれも今も生きている（ピクセルで実測 — `theme=light` はエディタを明色にし、既定は dark、`hidenavigation=1` はプレビューのアドレスバー行を消し、`fontsize=14` は 500px の箱で 18 行を 21 行にする）。Qiita と Zenn は著者が書いたクエリを通しているが、**この repo は §4 のとおり `src` を組み立てる側なので、通す道が無い。** 足すなら「全著者にとっての既定」を 1 つ決めることになり、その根拠が無い。`runonclick=1` だけが根拠を持つ — §20.6 の数字がそれである。

### 20.6 箱は 500px の固定である

**サンドボックスに固有の縦横比は無い。** §14.4・§15.4・§16.4・§17.4 が使ってきた `padding-bottom: calc(<比率>% + <列>px)` の形はここでは書けない。500px は CodeSandbox 自身の埋め込みコード・Qiita・Zenn の 3 者が一致して配っている値である。

**フレームは高さを喋るが、当てにできない。** `{ src, context: 'iframe.resize', height }` という形の postMessage が来ることはあるが、既定ビューではこちらが与えた高さに関係なく 500 を返す（300・500・900 で実測、いずれも 500）。`view=editor` で一度だけ 612 が返ったが、**同じ条件の別走では再現せず、メッセージが 1 通も来ない走もあった**。したがって §10.5（X）や §18.5（gist）の高さ受け機構に繋げられる安定した信号は無く、`components/EmbedFrames.tsx` に足すものは無い。

背景は `#191d1f` である。CodeSandbox のエディタが既定で塗る色を実測して置いた — iframe が届くまでの間の矩形が、届いた後の色と揃う。**これは CodeSandbox の「既定テーマ」を追っている値であり、§20.5 のとおり `theme` を渡していないので、向こうが既定を明色に倒すとこの色だけが取り残される。** `.embed-gist` の枠線が `data-color-mode="light"` の固定を追っているのと同じ形の依存である。

全画面は §14.4・§15.4・§16.4・§17.4 と同じく `allowFullScreen` が決める。この属性は両方の描画段がプロバイダによらず付けており（`lib/rehype-embed.ts` の `allowFullScreen: true`）、このプロバイダのためにそこへ触れたものは無い。CodeSandbox のプレイヤーがそれを使う口を持つかは測っていない。

### 20.7 `allow` は空、`sandbox` は張る

**`allow=""` である。** CodeSandbox 自身の埋め込みコードは `accelerometer; ambient-light-sensor; camera; encrypted-media; geolocation; gyroscope; hid; microphone; midi; payment; usb; vr; xr-spatial-tracking` を要求し、**Qiita と Zenn はそれをそのまま写している**。ここでは写さない:

- §17.4 の「何も求めない」と §9 の「著者が求めていないものは引く」が両方ここを指す
- 埋め込まれるのは**第三者が書いた任意のコード**である。記事の中の箱に camera / microphone / geolocation / usb / payment を既定で渡す理由が言えない
- **この 2 つのサイトと分かれる点なので、ここに書いておく** — 次に読む人が「揃っていない」と見て戻さないように

**`sandbox="allow-scripts allow-same-origin allow-forms allow-modals allow-popups"` を張る。** Zenn が張っている値そのままで、買っているものは `allow-top-navigation` が**無い**ことである — フレームの中の第三者のコードが記事ごと別の場所へ飛ばせない。§18.6 の gist が `allow-same-origin` を**外して**第三者の markup を隔てたのとは逆で、こちらは入れる: CodeSandbox のエディタとプレビューは自分の storage と worker を使うので、不透明オリジンにすると動かない。

**この組み合わせ（Zenn の `sandbox` ＋ `allow=""`）は Qiita も Zenn も出荷していないので、実測した**（2026-08-30）。エディタは描画し、`Click to Run` を押すとプレビューが起動して `<id>.csb.app` が読み込まれ、TODO アプリが操作できた。§18.6 と同じく、`sandbox` はコピーではなく測った答えである。

### 20.9 非公開のサンドボックスは、著者に見えない壁である（2026-08-30 引き受け）

§14.6・§17.6 が拠り所にした「著者は挿入した瞬間に、自分の NodeView で読者と同じ壊れ方を見る」という防御が、このプロバイダでは成り立たない。

- 非公開のサンドボックスは、ログイン済みの著者のブラウザでは `codesandbox.io` の cookie が効いて**正常に描画される**
- ログアウトした読者のフレームには CodeSandbox 自身の文言が出る — 「Not Found — We could not find the sandbox you're looking for. If the sandbox is private, you might need to sign in and reload the page to see the sandbox.」
- つまり著者は、自分の画面では動いている埋め込みを公開できる

**これを引き受ける（2026-08-30、著者の決定）。** Google Slides を 2026-08-29 に却下した 2 つの理由のうち、リクエスト数のほうは §20.5 の `runonclick=1` で外れたが、こちらは外れていない。引き受ける根拠は 2 つ:

- **無言ではない。** SlideShare の §14.6 や Docswell の §17.6 が引き受けた「記事の中に第三者の 404 が出る」より状態が良い — 文言が原因（非公開である可能性とサインインの必要）を名指しており、読者はそれを読める
- 足さなければ、カードが取れない以上、公開・非公開を問わず**すべての**サンドボックスが URL の文字列になる（§20.1）

実際の非公開サンドボックスでは未実測である（このプロジェクトは CodeSandbox のアカウントを持っていない）。機構は上記の文言と §20.8 の cookie の挙動から確認したものである。

### 20.10 マークとラベル

マークは `CODESANDBOX_MARK_SHAPES`（正方形のリング）である。§7.3 が「ロゴを足すかはその都度決める」と置いた判断を、§16.7・§17.7 と同じく足す側に倒している。`embedMarkShapes` の分岐を足さなければ既定の再生マークが黙って出る（§14.8 の注意がそのまま当たる）。

**形は書き起こさず、公開されているパスを使う**（§16.7・§17.7 と同じ理由）。出典は CodeSandbox が `/embed/<id>` の document にインラインで載せている favicon の `<svg viewBox='0 0 100 100'>` で、`d='M81.8182 18.1818V81.8182H18.1818V18.1818H81.8182ZM10 90V10H90V90H10Z'` という `fill-rule='evenodd'` の二重正方形である。これまでのどのプロバイダより出典が近い — プロバイダ自身が、埋め込みのために配っている document の中にある。

`IconShape` は塗りではなく線が既定なので、**リングの中心線を 1 本の `rect` として描く**。100 の箱で外辺 10・内辺 18.1818 なら中心線は 14.0909、24 の箱では `x = y = 3.38`、`width = height = 17.24` になる。リングの幅 8.1818 は 24 の箱で 1.9636 で、`buildIcon` が既定で置く `stroke-width: 2` と 2% しか違わない — **線幅はアイコン集合のものに合わせてあり、ブランドの値そのものではない**が、この 1 語についてはその差が描画に出ない。

ラベルは `{ lead: 'CodeSandbox', detail: '' }` である。セグメントは題を slug 化したものか乱数であり**名前ではない**（§14.8・§16.7・§17.7 と同じ）。引き継ぐ値が無いので `detail` は常に空である — YouTube の開始秒（§9.3）や Docswell のページ（§17.3）に当たるものが、このプロバイダには無い。

### 20.13 フレームを拒むサンドボックスがある（実測 2026-08-30、引き受け）

**すべてのサンドボックスが埋め込めるわけではない。** `/embed/<seg>` が Cloudflare のチャレンジに落ちた場合、そのチャレンジページ自身が `X-Frame-Options: SAMEORIGIN` を返すので、**ブラウザがフレームごと拒否し、読者にはブラウザ自身の「codesandbox.io で接続が拒否されました」が出る**。空箱でも第三者の 404 でもなく、chrome-error のページである。

**頻度は 95 件中 6 件（6.3%）である。** 母集団は実際に記事へ公開された埋め込みで、Qiita の API（`rendered_body` が埋め込みの markup を持つ）と Zenn の検索から id を集めた。§14.6 の SlideShare が引き受けた 34 件中 1 件と同じ桁である。

拒まれた 6 件は `rust-rk69p3`・`python-in2qez`・`rust-sample-6f2825`・`tender-leaf-3fw5rd`・`admiring-ritchie-lo8jg4`・`testing-library-getbytext-normalizer-example-k3j75m` で、**Rust と Python が並んでいる**。この 2 つはブラウザ内では動かずコンテナを要する、つまり Devbox（v2）である。`/p/devbox/` を §20.3 が外しているのはこの実測による。

**これは自動化クライアント特有の現象ではない。** 調査中の 403 はすべて Playwright 経由のブラウザで測ったもので、そこだけなら §14 の SlideShare と同じ artifact でありえた。著者自身の通常のブラウザで `devbox-example-jzpsnn`（`/p/sandbox/` の URL である）と `state-example-y9x872` を素の `<iframe>` に入れて確認し、**どちらも同じく拒否された**（2026-08-30）。

**URL からは見分けられない。** `devbox-example-jzpsnn` は `/p/sandbox/` の下にあり、通る `eager-proskuriakova-2lcdqm` と字面の上で区別が付かない。セグメントの形でも長さでもパスでも判定できないので、**受け付ける URL を狭めて避けることはできない** — 狭めるなら `/p/sandbox/` を丸ごと落とすことになり、それは現行の正規形を捨てることである。

**引き受ける。** 根拠は §14.6・§17.6 と同じで、しかもそれらより強い:

- **著者は挿入した瞬間に、自分の NodeView で読者と同じ拒否を見る。** 2 つの描画段が同じ `iframe` を組み、この拒否は cookie ではなくヘッダで決まるので、§20.9 の非公開サンドボックスの壁とは別種である。壊れていることが著者に見える
- 6.3% は §14.6 が引き受けた率と同じ桁である
- 直したければ「リンクに戻す」でリンクに戻せる

**§20.9 との違いを取り違えないこと。** あちらは著者に見えない壁で、だからこそ「引き受ける」と明記する必要があった。こちらは見える壊れ方であり、このリポジトリが既に 2 度引き受けている形そのものである。

#### 機構（実測 2026-08-30）

拒否は 3 段でできている。

1. **Cloudflare が該当サンドボックスの `/embed/` に managed challenge をかけている。** 応答は `cf-mitigated: challenge` を持ち、本体は Turnstile の「Just a moment...」で、アプリページ（`/s/react-example-xgzdk`）が返すものとほぼ同一である。**CodeSandbox が独自に返す 403 ではない**
2. そのチャレンジページ自身が `X-Frame-Options: SAMEORIGIN` を返す
3. したがってブラウザはチャレンジの描画を拒む。**アクセスを許可しうる唯一のページが、iframe の中では原理的に表示できない**

**サンドボックスごとに決定的である。** 同一クライアント・同一 IP・同一セッションで 4 回ずつ叩いて、`xgzdk` は 4 回とも 200、`rust-rk69p3`・`python-in2qez`・`state-example-y9x872` は 4 回ともチャレンジだった。IP でもレート制限でもキャッシュでもない（`cf-cache-status` は 200 の側にも付かない）。

**そして「なぜそのサンドボックスか」は CodeSandbox 自身が書いている。** `codesandbox.io/docs/…` はこちらからは 403 だが、**`codesandbox/docs` は public のリポジトリで、raw.githubusercontent.com から読める**（§19.1 が使ったのと同じ経路）。そこには埋め込みの節が 3 つあり、製品が 3 種類に分かれている:

| 種別                   | docs が示す `src`                                                           |
| ---------------------- | --------------------------------------------------------------------------- |
| Legacy Sandboxes       | `codesandbox.io/embed/<id>` — **§20.4 が採っている形**                      |
| Browser Sandboxes      | `codesandbox.io/p/sandbox/<id>?file=…`（ページ URL をそのまま `iframe` に） |
| VM Sandboxes（Devbox） | 同上。「**現在ベータ**」と明記され、インライン編集は不可                    |

拒まれた 6 件が Rust と Python を含むのはこのためで、docs が VM Sandbox の例として挙げているのも Rust の `fork-syscall-example-7giodp` である。**あの 6 件には legacy の埋め込み口が無い。**

**ただしルートを変えても直らない。** その `fork-syscall-example-7giodp` は `/p/sandbox/` でも `/embed/` でも同じくチャレンジを返し、著者の通常のブラウザでも**どちらの形でも第三者ページの `iframe` には出なかった**（実測 2026-08-30、対照の `react-new` は同じページで両方とも出る）。CodeSandbox の docs があの例を載せられるのは docs 自身が codesandbox.io 上にあるからで、`X-Frame-Options: SAMEORIGIN` はそこでは当たらない。**VM Sandbox の埋め込みは、ベータであり、第三者サイトでは動かない。**

したがって §20.13 が引き受けているのは Cloudflare の気まぐれではなく、**プロバイダの製品境界**である。回復させるルートは存在しない。

**`cf_clearance` はこれを解かない、というのがこの節の要である。** 著者の通常のブラウザで `/embed/rust-rk69p3` を*通常のタブで*開くとチャレンジを通過してエディタが表示され、`cf_clearance` が発行される。その状態で同じ `iframe` を読み直しても**やはり拒否される**（実測 2026-08-30）。したがって:

- 拒否は一様である。チャレンジを通過した人にも、していない人にも、同じく拒まれる
- **§20.9 の壁がもう 1 つ増えるのではないか、という懸念は測って否定された。** 著者が CodeSandbox を見たあとでも、著者の NodeView は読者と同じ拒否を映す

### 20.14 キー入力の行き先はフォーカスが決める（実測 2026-08-31）

**CodeSandbox は、中身がエディタである最初の埋め込みである。** §7 は「フレームは休止状態で `pointer-events: none`、ブロックが選択されるまでポインタは通らない」までを決めていて、その先——フレームが生きたあと打鍵がどちらに行くか——が §20.12 の 1 番目だった。

**答えはフォーカスであって、選択ではない。** 状態は 2 つあり、クリックの回数で分かれる。

| 状態                                                          | `document.activeElement` | 打鍵の行き先                                     |
| ------------------------------------------------------------- | ------------------------ | ------------------------------------------------ |
| クリック 1 回。ブロックが選択され、エディタにフォーカスがある | エディタ本体             | 文書。選ばれたノードが打った文字に**置き換わる** |
| クリック 2 回目がフレームの中に着地した                       | `iframe`                 | フレームだけ。文書は 1 文字も変わらない          |

1 つ目は ProseMirror の NodeSelection の標準の挙動で、リンクカードと共通で、undo で戻る。**ここにキー入力のガードは足さない** — 足せば「ブロックを打鍵で置き換える」唯一の手段が消える。

2 つ目では Backspace も同じくフレームに行き、**§7.3 の 1 回押しの atom 削除は起きない**。著者がサンドボックスの中で消したつもりの 1 文字が、記事のブロックごと消すことは無い。

**リングは両方の状態で出たままである。** 選択は ProseMirror の state にあり、フォーカスは DOM にあるので、外枠は「次の打鍵がどこへ行くか」の合図ではない。倒れている向きは安全な側である — リングが出たまま打鍵がフレームに行くだけで、**著者がサンドボックスに打っているつもりの 1 打がブロックを消す、という向きには起きない**。

**測れたのは §20.7 が `allow-same-origin` を残したからである。** フレームが不透明でないので、`page.route` でサンドボックスをスタブに差し替えたうえで、中の要素を掴んでフォーカスを渡せる。§18.6 の gist のフレームはこれができない（`e2e/public-embed.spec.ts` の注記）ので、この測り方はこのプロバイダに固有である。

引き受ける帰結が 1 つある: **埋め込まれたエディタに書いたコードはどこにも残らない。** 記事が持つのは URL だけで（§20.4）、フレームの中身は CodeSandbox のものである。エディタを埋め込む以上これは避けられない。
