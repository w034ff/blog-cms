# 編集の手元のバッファ 要件定義

- 状態: 実装済み（2026-10-17）
- 作成: 2026-10-17、`docs/project-status.md` §6 の「自動保存の手元のバッファ」を次の機能に選んだ相談から
- 関連: `docs/editor-pitfalls.md` §13.1・§16.1、`docs/revision-requirements.md` §3、`components/editor/useAutosave.ts`（自動保存）、`app/api/drafts/route.ts`（保存の受け口）

エディタの編集内容を、サーバーへの自動保存とは別にブラウザの `localStorage` へ書き、サーバーに届かないまま失われた編集を次に開いたときに戻せるようにする機能の設計記録。画面での名前は「保存されていない変更」、コードでの名前は `draftBuffer`。

---

## 1. 目的と前提

自動保存はサーバー側だけで、次の保存が成功するまで編集は React のメモリにしかない。今は `beforeunload` の警告と、セッション切れの帯（「編集内容は保持されています」）で和らげているが、どちらもタブが生きている間しか守らない。編集を失うのは次の場面である。

| 場面                                                      | 今の守り                                     | 失うもの                                          |
| --------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------- |
| タブやブラウザのクラッシュ、OS の再起動、スリープ中の終了 | なし（`beforeunload` は発火しない）          | 最後に保存が成功した後の編集すべて                |
| セッション切れや回線断のまま、警告を無視して閉じる        | `beforeunload` の警告                        | 保存が失敗し始めてからの編集すべて                |
| アプリ内のリンクで移動する                                | なし（App Router に遷移を止める API が無い） | デバウンス（`AUTOSAVE_DELAY_MS`）の間の最後の打鍵 |

サーバー側の自動保存が主であることは変えない（`docs/project-status.md` §6）。バッファは、サーバーに届かなかった分を次の機会に届けるための控えである。

## 2. 決定

- **置き場所は `localStorage`**。画像は別にアップロードされ本文にはパスだけが入るので、記事 1 本の控えは文字だけで足りる。書き込みが同期なので、クラッシュの直前の編集まで残る。IndexedDB は非同期の書き込みがクラッシュに負けうるうえ、手間に見合わない。
- **戻すかどうかは著者が決める**（自動では戻さない）。別のタブや端末でサーバー側が先に進んでいるとき、自動で戻すと新しい内容を古い控えで上書きするため（オーナー、2026-10-17）。
- **戻した内容は通常の自動保存でサーバーへ送る**。戻す操作のための保存の経路は作らない。版の履歴（`docs/revision-requirements.md` §3）も通常の保存と同じ扱いになる。
- **控えが書けないときは黙って諦める**。`localStorage` が無い、容量が尽きた、例外を投げた、のどれでも、自動保存と編集はこれまでどおり動く。控えは守りの追加であって、編集の前提にしない。

## 3. 控えの形

### 3.1 キー

利用者と記事ごとに 1 件。

| 記事                             | キー                              |
| -------------------------------- | --------------------------------- |
| 行のある記事（編集画面）         | `draftBuffer:<userId>:post:<id>`  |
| 行がまだ無い新しい記事・走り書き | `draftBuffer:<userId>:new:<kind>` |

- `userId` を入れるのは、同じブラウザで別の利用者がログインしたとき、他人の控えを見せないため（`docs/project-status.md` §7 の複数の著者）。エディタはサーバーから自分の id を受け取る。
- 新しい記事の最初の保存が行を作ったら（`onCreated`）、控えを `new:<kind>` から `post:<id>` へ移す。

### 3.2 値

JSON で、次を持つ。

| フィールド     | 中身                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------- |
| `version`      | 形の版（数）。読めない版は捨てる                                                             |
| `content`      | `DraftContent`（`readDraftContent` と同じ 5 つ: タイトル、カテゴリ、タグ、本文、サムネイル） |
| `baseEditedAt` | 控えを書き始めたときの、サーバー側の `posts.edited_at`。新しい記事では空                     |
| `writtenAt`    | 最後に控えを書いた時刻                                                                       |

読み込みでは型を主張せず検証する（`docs/editor-pitfalls.md` §16.2 と同じ理由。形の違う古い控えが `undefined` を運ぶ）。

## 4. 書くときと消すとき

- **書く**: 編集のたびに（`markEdited`）、短い遅れ（定数、数百 ms 以内）の後に今の内容を書く。本文の hidden input は描画の後に更新されるので、`markEdited` の中で同期に読むと 1 打鍵古い。
- **消す**: 自動保存が成功し、そのとき送った内容が今の控えの `content` と一致したとき。送信中に打った分は控えに残り、次の保存の成功で消える。公開・更新・非公開化（`acceptSaved`）が成功したときも同じ比べ方で消す。
- **`baseEditedAt` を進める**: 保存が成功するたびに、応答の `editedAt` を控えの基準にする。`app/api/drafts/route.ts` は応答に `editedAt` を足し、編集画面はページの読み込み時の `edited_at` をエディタへ渡す。
- **古い控えを消す**: エディタを開いたとき、自分の控えのうち `writtenAt` が一定の日数（定数、30 日）より古いものを消す。
- ログアウトでは消さない。セッション切れの後にログアウトとログインをやり直す流れで、守りたい控えそのものを消すため。他の利用者からはキーの `userId` で分ける（§3.1）。

## 5. 戻す

### 5.1 帯を出す条件

エディタを開いたとき、自分のその記事の控えがあり、内容がサーバーから読み込んだ内容と違えば、帯を出す。

- 比べる前に本文の改行を LF に揃える（`docs/editor-pitfalls.md` §16.1）。
- 同じなら帯を出さずに控えを消す（保存は成功したが、控えを消す前にタブが閉じた場合）。
- 新しい記事では、`new:<kind>` の控えがあり、タイトルか本文が空でなければ帯を出す。

### 5.2 帯

タイトルの上、セッション切れの帯と同じ場所と形。

- 文言: 「保存されていない変更があります（10/17 14:32）。」と［復元］［破棄］。時刻は `writtenAt`。
- サーバー側の `edited_at` が控えの `baseEditedAt` より新しいときは、「別の端末等でこの記事が保存されています。復元すると、そちらの内容を上書きします。」を添える。
- ［復元］: 控えの内容をタイトル・カテゴリ・タグ・本文・サムネイルに入れ、編集として記録する（`markEdited`）。本文はエディタのコマンドで入れ、React の effect から dispatch しない（`docs/editor-pitfalls.md` §13.1）。帯を閉じる。
- ［破棄］: 控えを消し、帯を閉じる。
- どちらも押さずに編集を始めたら、帯は残したまま、その編集で控えを上書きしない。上書きすると、戻せるはずの控えが黙って消えるため。帯を閉じた後の編集から控えを書く。
- 帯が出ている間にその編集の自動保存が成功しても、控えには触れない（`baseEditedAt` も進めない）。進めると、帯の間に保存した編集を［復元］が上書きするのに、上書きの注意が出なくなる。

## 6. やらないこと

- 同じ記事を 2 つのタブで開いたときの調停。サーバー側の保存も今は後勝ちで、控えもそれに揃える。
- 控えの複数の版。1 件だけ持ち、版の履歴は `docs/revision-requirements.md` が持つ。
- アプリ内の遷移を止めること。控えがあるので、最後の打鍵も次に開いたときに戻せる。
- 画像のファイルそのものの控え。アップロードは即時で、本文はパスを持つだけである。
