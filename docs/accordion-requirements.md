# アコーディオン（折りたたみ）機能 要件定義

- 状態: **未実装 / 設計合意まで**
- 作成: 2026-08-03
- 関連: `docs/footnote-requirements.md`（文書の型）、`components/editor/callout-extension.ts`（最も近い前例）

Zenn の `:::details` に相当する折りたたみブロックを、エディタと公開ページの両方で扱えるようにするための要件。実装は未着手で、この文書は「作るとしたら何を満たす必要があるか」を確定させたもの。

---

## 1. 目的と非目標

**目的**: 長い補足・コード・前提知識・ネタバレを畳んで、本文の流れを切らずに置けるようにする。

**非目標**（初版では明示的に対象外）:

- アコーディオンの入れ子
- 「既定で開いた状態」の保存（`open` 属性の書き出し。§5 参照）
- 開閉のアニメーション
- タイトルへの装飾（太字・リンク・インラインコード。§2 の `text*` 制約）
- 既存記事の自動マイグレーション（対象記事が存在しないため不要）

---

## 2. データモデル

### 2.1 保存形式 — 生 HTML の `<details>`

Markdown を記憶形式とする既存方針は変えない。Markdown に折りたたみの記法が無いため、`accent-emphasis`（太字＋アクセント色を生 `<span>` で往復させている）と同じく生 HTML で保存する。

**保存する形は以下に固定する。空行 2 つが仕様の一部である。**

```markdown
<details>
<summary>タイトル</summary>

本文。**強調**もリストもここに書ける。

</details>
```

- `<summary>` の後の空行が無いと、本文が HTML ブロックに飲まれて素の文字列になる
- `</details>` の前の空行が無いと、閉じタグが直前のブロックに吸われる

`:::details` 記法（remark-directive + markdown-it-container）は**不採用**。依存を 2 つ増やす割に、生 HTML と違って他のどの Markdown 処理系でも表示されない。

### 2.2 検証済みの事実（実測、2026-08-03）

- **公開側** — 上記の形を `lib/render.ts` に通すと `<details>` / `<summary>` がそのまま出力され、中の `**強調**`・箇条書き・`<span class="accent-emphasis">`・`##` 見出しはすべて Markdown として解釈される。`details` / `summary` は rehype-sanitize の `defaultSchema.tagNames` に元から含まれ、`open` 属性も全要素共通の属性許可リストに入っているため通過する
- **エディタ側** — `Markdown.configure({ html: true })` なので markdown-it も同じ入力を同じ構造にパースする

逆向き（TipTap → Markdown）はこの機能の最大のリスクだったが、**スパイクで検証済み**（§4.4）。

### 2.3 ProseMirror スキーマ

`@tiptap/extension-details` の 3 ノード構成をそのまま使う（§3）。

| ノード           | 内容                            | 備考                                               |
| ---------------- | ------------------------------- | -------------------------------------------------- |
| `details`        | `detailsSummary detailsContent` | `group: block` / `isolating` / `defining`          |
| `detailsSummary` | `text*`                         | `isolating`。装飾不可なのは Zenn と同じ制約        |
| `detailsContent` | `block+`                        | 折りたたみ対象。閉じている間は `hidden` 属性が付く |

タイトルを属性ではなく子ノードにするのは意図的。NodeView に `<input>` を置くと、サーバーアクション保存で値が初期化される React 19 の罠（`docs/footnote-requirements.md` §9.2）を踏む。

## 3. 実装方針 — 公式拡張を採用する

`@tiptap/extension-details@3.28.0` を採用する。自前で書かない。

**採用理由**（いずれも実測で確認済み）:

- バージョンがこのリポジトリの固定値（`3.28.0` 系）と完全一致する。ファミリー一括バンプが不要
- MIT。かつては Pro 扱いだったが現在は npm 公開されている
- `parseHTML` が実物の `<details>` / `<summary>` を対象にしている（`div[data-type=...]` ではない）。保存形式と噛み合う
- `persist: false` が既定。**開閉状態がドキュメント属性にならない**（§5 がそのまま満たされる）
- `setDetails` / `unsetDetails`、末尾での Enter 脱出、Backspace での解除が実装済み

**新規依存**: `@tiptap/extension-details@3.28.0` と、その peer である `@tiptap/extension-text-style@3.28.0`（現在未インストール）。どちらも TipTap 公式・固定バージョン一致だが、依存追加の方針上ここで明示しておく。

**自前で足すもの**:

1. Markdown の直列化とパース（§4）— 公式拡張はこれを持たない
2. **`setDetails` の拒否条件**（§7）— 公式のコマンドは配置先を一切見ない
3. ガード群との統合（§6）

**注意**: 公式拡張のソースには `createBlockMarkdownSpec(...)` が含まれるが、これは TipTap 3 が持つ独自の Markdown 層のもので、このリポジトリが使う tiptap-markdown 0.9.0 は読まない。返すのは `parseMarkdown` / `markdownTokenizer` などのトップレベル spec キーであり、`addStorage()` を定義しないので、こちらの `.extend({ addStorage })` と衝突もしない（実測）。**動くように見えて無効**という誤解を招く箇所なので、実装時にコメントを残すこと。

## 4. Markdown の往復（この機能の最大のリスク）

### 4.1 直列化

prosemirror-markdown には「生 HTML ブロックで Markdown の子を包む」概念が無いため、`serializeCallout` と同じく手書きになる。§2.1 の空行 2 つを厳密に出すこと。

**タイトルは HTML エスケープが必要。** 本文は通常の Markdown として書き出されるので prosemirror-markdown のエスケープに乗るが、`<summary>タイトル</summary>` の行だけは生 HTML である。`a <b> c` というタイトルをそのまま書くと markdown-it が `<b>` をタグとして解釈し、往復で文字が消える。`&` も同じ。書き出し時に `&` と `<` をエスケープすること（DOM パース側が復号するので不動点は保たれる）。これは「見苦しい入力」ではなく「壊れる入力」であり、脚注要件 §5.3 と同じ種類の問題。

### 4.2 パース

`updateCalloutDOM` と同じ `parse.updateDOM` フックで、`<details>` 直下の `<summary>` 以外のブロックを `<div data-type="detailsContent">` に包み直す。公式拡張の `detailsContent` はこのタグを期待しており、保存された Markdown にはそれが無いため、この工程が無いと本文が落ちる。

**tiptap-markdown はパースのたびに `parse.setup` を再実行する。フックは冪等に書くこと**（脚注の件で踏んだ罠）。

### 4.3 受け入れの判定基準

**`getMarkdown()` → 読み込み → `getMarkdown()` が完全一致すること（不動点）。かつ中間の Markdown が §2.2 で確認した HTML を再現すること。**

以下を往復ケースに含める。

- 本文に callout（`> [!NOTE]`）を含むアコーディオン — 空行規則を最も強く突く組み合わせ。禁止していないので到達可能
- 本文にフェンスコードブロックを含むアコーディオン
- 本文にテーブルを含むアコーディオン
- タイトルが空のアコーディオン
- **タイトルに `<` と `&` を含むアコーディオン**（§4.1 のエスケープ）
- 本文が空のアコーディオン
- アコーディオンが文書の末尾にある場合

### 4.4 検証結果（2026-08-03、スパイクで実測）

**この節が最大のリスクとしていた不動点は、成立することを確認した。** §4.1 / §4.2 の方針どおりに書いた最小実装（マークダウン層のみ。ガードも導線も見た目も無し）で、上記の全ケースと以下が**初回から不動点**になった。

- 本文が callout / フェンス / テーブル / リスト / 複数ブロックのそれぞれ
- タイトルが空、本文が空、タイトルが `*強調*`（`state.text()` を使うと `\*` に化けるので、生の `write()` で書くこと）、タイトルが `<` と `&` を含む
- 前後に段落があるとき、文書末にあるとき
- 直列化された Markdown が公開ページで `<details>` として描画されること（callout / Shiki 付きコードブロック / エスケープされたタイトルまで確認）

**挿入経路の正規化は不要だった。** `setDetails` が作るノードと、パースが作るノードは同じ形になり、「エディタで作ってから保存」も「読み込んでから保存」と同じ出力に落ちる。両者がずれる可能性（コードブロックの幻の末尾改行と同じ非対称）を疑っていたが、起きなかった。

**既知の逸脱が 1 つ。** 空行を省いた非正規な入力（`<details>` / `<summary>` / 本文 / `</details>` を空行なしで書いたもの）を読み込むと、本文の末尾に**空の段落が 1 つ増える**。Markdown の出力は正規形に整えられ、そこから先は不動点になるので実害は小さいが、手書きの Markdown を取り込んだアコーディオンの末尾に空行が 1 行見える。仕様として許容する。

## 5. 開閉状態

**開閉はドキュメントに保存しない。** 公式拡張の `persist: false`（既定）のまま使い、開閉は NodeView のクラスと `hidden` 属性だけで表現する。

理由は autosave。開閉を属性にすると、エディタで畳むたびに文書が dirty になり保存が走る。閲覧操作が保存を起こすのは誤りである。

公開ページは常に閉じた状態で出力する（`open` を書き出さない）。「既定で開く」が必要になったら、開閉トグルとは別の明示的なコントロールとして後から足す。

### 5.1 空のタイトル・空の本文 — 公開時の検証は足さない

**タイトルが空でも本文が空でも、下書き保存も公開も通す。** 検証を追加しない。

脚注要件（§5.2 / §5.3）は逆の判断をしているが、そこでの理由がここには当てはまらない。脚注の空定義は「見苦しい入力」ではなく **Markdown の往復で壊れる入力**だったから公開前に潰す必要があった。アコーディオンの空タイトルは `<summary></summary>` として往復し、公開ページでもラベルのない三角として問題なく描画される（§9 の受け入れ基準 4 で確認する）。壊れないものを公開時に止めると、「保存はできるのに公開できない」状態を新たに作るだけで、得るものがない。

代わりに**執筆中に気づける形**にする。タイトルが空のあいだは NodeView にプレースホルダを表示する（§7.3）。これは `app/actions/posts.ts` の既存方針（必須項目の検証は公開時、autosave は寛容）とも矛盾しない — そもそも必須項目にしない、という判断だからである。

## 6. 既存ガードとの関係

ここは「後で考える」で済ませてはならない。同種の見落としが過去に 2 回、実バグになっている（テーブルの clamp が内側の isolating を取り違えた件、drop/paste/Enter がセル内で別々の規則に答えていた件）。

### 6.1 そのまま効くもの（型に依存しない実装のため）

| 場所                  | 効く理由                                                           |
| --------------------- | ------------------------------------------------------------------ |
| `table-cell-rules.ts` | 「段落以外のブロック」を一律に拒否する。セルへの流入は塞がれている |
| `slice-placement.ts`  | 開いたラッパを一般に剥がす。型名を見ていない                       |

### 6.2 手当て・確認が要るもの

| 場所                                        | 必要な作業                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| `block-drag-handle.ts` の `DRAGGABLE_TYPES` | `'details'` を追加する                                                  |
| `callout-slice-guard.ts` 相当               | details 版のスライスガードが要る（下記の落とし穴あり）                  |
| `drop-cursor-guard.ts`                      | 述語に details のネスト判定を足す。フックは 1 つでなければならない      |
| `isolating-boundary.ts`                     | 自動で対象になるが、**二重 isolating の形なので実測で確認する**（下記） |

**`isolating-boundary.ts` は「無償で効く」に入れない。** スキーマの `isolating` を読む実装なので `details` は自動的に対象になるが、`details` と `detailsSummary` の**両方が `isolating: true`** であり、これは issue #7（テーブルが 2 階層で isolating であるためクランプが内側を取り違えた件）とまったく同じ形をしている。現在のクランプは内側を取るよう直っているので恐らく問題ないが、一度実バグを出した形を「確認せず効くもの」に分類してはならない。§9 の 18・19 で明示的に確認する。

**落とし穴: 半選択の展開処理は callout から流用できない。** `unwrapHalfSelectedCallouts` と `flattenCallouts` は、箱の子を 1 階層そのまま親のフラグメントに差し込む。callout の子は `block+` なのでトップレベルで妥当だが、`details` の子は `[detailsSummary, detailsContent]` であり、これを差し込むとスキーマ不正になる。

details の展開は **2 階層**になる。`detailsContent` の子を取り出したうえで、**タイトル（summary）をどうするかを別途決める必要がある**（破棄する / 本文先頭の段落として残す）。`BOX_TYPES` のような形で共通化するなら、展開の深さは型ごとに持たせること。

### 6.3 配置の規則 — 新規作成はトップレベル限定

**アコーディオンを新しく作れるのは文書のトップレベル（`depth === 1`）だけとする。** 禁止先を列挙するのではなく、この一行を規則とする。引用・callout・テーブルセル・**リスト項目**・アコーディオンの中は、すべてこれ 1 つで拒否される。

| 組み合わせ                               | 判断 | 理由                                                                |
| ---------------------------------------- | ---- | ------------------------------------------------------------------- |
| アコーディオンの中のアコーディオン       | 禁止 | 非目標                                                              |
| 引用 / callout の中に置く                | 禁止 | 保存形式の問題ではない（下記）。初版のスコープを絞るための判断      |
| テーブルセルの中に置く                   | 禁止 | セルは段落しか持てず、既に専用ガードがある（`table-cell-rules.ts`） |
| リスト項目の中に置く                     | 禁止 | 保存形式の問題ではない（下記）。初版のスコープを絞るための判断      |
| アコーディオンの中の callout・表・コード | 許可 | 折りたたむ価値があるのはまさにこれら                                |

**この表のうちテーブルセル以外は、どれも「壊れるから」ではない**（2026-08-03、スパイクで実測）。当初は引用について「`> ` 付与を生 HTML が生き延びるかは未検証、試して壊すより拒否する」と書いていたが、実測すると

- `> <details>` … `> </details>` は**往復する**（引用の中でも callout の中でも不動点になる）
- 2 スペース字下げしてリスト項目の 2 つ目以降の子に置いた形も**往復する**
- アコーディオンの中のアコーディオンさえ**往復する**

**つまり配置の制限は、保存形式ではなく次の 2 点だけに立っている。**

- `block-drag-handle.ts` の対象はトップレベルのみ。入れ子にしたアコーディオンだけドラッグハンドルが出ず、並べ替えられない
- 初版の作業量を絞る。とくにリスト項目内に置くには、`setDetails` に「項目の先頭段落では変換せず次の子として挿入する」分岐が要る（下記）

**この 2 点は「壊れる」より弱い根拠である。**引用や callout の中を許したくなったら、スキーマも保存形式も変えずに拒否を外すだけで済む — 変更が要るのはドラッグハンドルの扱いだけ。そう判断したうえで初版は絞る。

**「入力ルールとメニューで挙動が違うのは不整合だ」という理由は採らない。** このリポジトリは同じ問いに既に答えを出している — `code-block-extension.ts` の `insertCodeBlock` は、リスト項目の先頭段落では変換が schema 上できないため**その次の子としてブロックを置く**という二分岐で作られており、` ```lang ` の入力ルールは変換専用のまま先頭段落で不発でよい、と明記されている。同じコメントは **callout とテーブルのボタンが以前からリスト項目内にブロックを置いてきた**ことを、正しい挙動として引き合いに出している。

つまり「wrap 型の入力ルールはリスト項目の先頭で不発、insert 型のコマンドは通る」という非対称は、このリポジトリでは欠陥ではなく既定の設計である。

**将来リスト内を許す場合の作り方**: `insertCodeBlock` と同じ二分岐（変換できるならする / できなければ項目の次の子として挿入）を `setDetails` に足し、`block-drag-handle.ts` の扱いを併せて決めること。入力ルールは変換専用のままでよい。

**禁止するのは操作であって、スキーマではない。** `detailsContent` の内容を制限したり、引用が `details` を持てないようにスキーマで縛ってはならない。`callout-slice-guard.ts:42-46` がその理由を述べている — スキーマで形を禁じると、その形を含む既存の Markdown を開いた瞬間に内容が黙って捨てられる。引用の中の `<details>` を含む Markdown は外部から流入し得るので、**読み込めるが新規に作れない**という状態が正しい。

**ただしリスト項目の先頭の子だけは例外で、これは選べない。** `listItem` の content は `paragraph block*`（`@tiptap/extension-list` の既定、このリポジトリは上書きしていない）なので、index 0 に段落以外を置けない。

実機で測った結果（2026-08-03、E2E ハーネス）はこうなる — **内容は失われず、入れ子だけが失われる**。ブロックはリストの外へ持ち上げられ、空のリスト項目が残る。

| 入力               | 読み込み後の文書                                                 | 保存される Markdown           |
| ------------------ | ---------------------------------------------------------------- | ----------------------------- |
| `- ```ts` + コード | `bulletList(listItem(paragraph)), codeBlock("const a = 1\n")`    | `- ` + トップレベルのフェンス |
| `- > 引用`         | `bulletList(listItem(paragraph)), blockquote(paragraph("引用"))` | `- ` + トップレベルの引用     |

コード本文も言語指定（`ts`）も残り、2 回目以降の往復は不動点になる。`<details>` を項目の先頭に書いた Markdown も同じ経路を通るはずなので、**受け入れ基準では「持ち上がること」と「文字が消えないこと」を確認する**。字下げして項目の 2 つ目以降の子に置いた形（`- 項目` の次の空行のあと）は schema が保持できるので、そちらはそのまま読み込めること。

判定は挿入位置の深さで行う（`setCallout` が使う `selectionTouches` の列挙ではなく、`:::` 入力ルールと同じ `depth === 1` の検査）。ただし**ドロップと貼り付けの拒否**は位置ではなくスライスを見る必要があるため、そちらは `selection-scan.ts` の `selectionTouches(state, ...typeNames)` を使う（§6.2 のスライスガード）。

**判定は必ず state 側の選択を読むこと**（クリックによるキャレット確定は `state.selection` に対して 20ms 遅れる。同じ罠で過去に「貼り付けが効かない」バグを出している）。

### 6.4 callout が直面しなかった 2 点

- **閉じたアコーディオンへのドロップ。** `resolveDropTarget` が `hidden` な内容の中を指し得る。著者から見えない場所にコンテンツが埋まるという、callout には存在しなかったバグの種類。受け入れ基準に含める（§9 の 16）
- **`allowGapCursor: false`。** 公式の `Details` はこれを設定しており、callout は設定していない。2 つの箱が境界で違う挙動になるので、**そのまま採るか上書きするかを実装時に明示的に決めて、コメントに残すこと**

## 7. 導線

| 経路                       | 採否       | 備考                                                                                                                                     |
| -------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| スラッシュメニュー         | **採用**   | ブロック要素なので `slash-command.ts` の `startOfLine: true` と噛み合う。`available` は `can().setDetails()`（ただし下記の上書きが前提） |
| `:::details ` の入力ルール | **採用**   | callout の `DIRECTIVE` と同じ形（末尾スペースで確定、トップレベル限定）                                                                  |
| ツールバー                 | **不採用** | スラッシュメニューと入力ルールで足りる（下記）                                                                                           |
| Backspace での解除         | **採用**   | 公式拡張の `unsetDetails` にそのまま乗る                                                                                                 |

挿入後のキャレットは**タイトル欄**に置く（公式の `setDetails` の挙動）。タイトルが空のまま本文を書き始める事故を減らせる。

**ツールバーには置かない**（2026-08-03 決定）。callout がツールバーに載っているのは 3 種類の型を選ばせる必要があるからで、単一のブロックであるアコーディオンにその理由は無い。スラッシュメニューと `:::details ` の入力ルールの 2 経路で足りる。ツールバーの列を増やさないぶん、狭い画面での折り返しも増えない。

### 7.1 `setDetails` は必ず上書きすること（前提条件）

**公式の `setDetails` には配置先の検査が一切ない。** 実装は「`$from.blockRange($to)` を取り、`detailsContent` の `contentMatch` に合えば挿入する」だけで、テーブル・引用・callout のいずれも見ていない。

したがってテーブルセルの中でも `can().setDetails()` は `true` を返す。セルの段落は `block+` に一致してしまうからで、スラッシュメニューの行はそのまま表示され、実行すればセルにアコーディオンが入って**テーブルが分断される** — `table-cell-rules.ts` が記録している、まさにその破壊。

`can().setCallout()` が `available` の述語として機能しているのは、`setCallout` 自身が `selectionTouches(state, 'table', 'blockquote')` の拒否を内蔵しているからである。公式のコマンドはそれを持たない。

**よって `Details.extend({ addCommands })` で `setDetails` を包み、§6.3 のトップレベル限定（`depth === 1`）の拒否を先に効かせる。それをして初めて `can().setDetails()` が正しい述語になる。** 順序を守ること。

### 7.2 キー操作

公式拡張が既に持っている挙動を**仕様として確定させる**（実装は乗るだけだが、書いていないと「決めていない」のか「そう決めた」のか後から分からなくなる）。

| キー               | 位置                       | 挙動                                                                             |
| ------------------ | -------------------------- | -------------------------------------------------------------------------------- |
| Enter              | タイトル欄（開いている）   | 本文の先頭へ移る。タイトルは 1 行なので改行はしない                              |
| Enter              | タイトル欄（閉じている）   | アコーディオンの**下**に新しいブロックを作る                                     |
| Enter              | 本文の末尾の空行           | アコーディオンの外へ出る（callout と同じ考え方）                                 |
| Backspace          | タイトル欄の先頭           | アコーディオンを解除する。**タイトルの文字は段落として残り**、本文がその後に続く |
| Backspace / Delete | アコーディオンの前後の境界 | callout と同じ（§6.4 の `allowGapCursor` の判断に従う）                          |

**タイトル欄の Enter は必ず自前で確認すること。** `detailsSummary` は `text*` なので、この束縛が無いと既定の分割が走って何が起きるか分からない。上表の 2 行目（閉じているときは下にブロックを作る）は公式の判断であり、**そのまま採る**。閉じたまま本文へキャレットを送ると、見えていない場所に文字を打ててしまうため。

Tab は束縛しない。このエディタでは Tab はリストのインデントに使われており、ここだけ意味を変えると一貫しない。

### 7.3 文言（すべて日本語）

サイト UI は日本語なので、公式拡張が入れる英語の `aria-label` は上書きする。

| 箇所                        | 文言                                                               |
| --------------------------- | ------------------------------------------------------------------ |
| 機能名（UI 上の呼び方）     | **折りたたみ**（`囲み枠` に倣い、カタカナ語を避ける）              |
| スラッシュメニューの行      | `折りたたみ`                                                       |
| 同・検索キーワード          | `details` / `accordion` / `toggle` / `アコーディオン` / `たたむ`   |
| タイトル欄のプレースホルダ  | `タイトル`                                                         |
| トグルの `aria-label`（閉） | `折りたたみを開く`                                                 |
| トグルの `aria-label`（開） | `折りたたみを閉じる`                                               |
| 配置を拒否したときの通知    | `折りたたみは引用やリスト、コールアウト、表の中には入れられません` |

`aria-label` は公式の `renderToggleButton` オプションで差し替える（既定は `"Collapse details content"` / `"Expand details content"`）。通知は `useEditorNotice` へ、callout の `CALLOUT_NESTING_BLOCKED` と同じ経路で出す。

## 8. 公開側

- 変換処理の追加は不要。生 HTML がそのまま出る（§2.2）
- **CSS は要素セレクタで書く。** sanitize が `details` / `summary` の `class` を通さないため、`globals.css` に `.prose details` / `.prose summary` として書く。既定の三角マーカーを Zenn 風の見た目に置き換えるのもここ
- **アコーディオン内の見出しは目次に載せない**（2026-08-03 決定。§8.1）
- 閉じた内容はブラウザの Ctrl+F と印刷に出ない。仕様として許容する

### 8.1 目次から外す理由と、その帰結

見出しをスキーマで禁じることはできない（§6.3 と同じ理由 — 禁じれば `<details>` の中に `##` を含む Markdown を開いた瞬間に見出しが落ちる）。エディタでも中で H2/H3 がそのまま打てる。決めるのは**目次に載せるかどうかだけ**であり、載せない。

- 目次は「見えている構造」の一覧である。著者が畳んだのは「本筋ではない」という判断なのに、目次はそれを本筋の見出しと同じ列に並べてしまう
- 閉じた `<details>` の中の id へフラグメント遷移したとき折りたたみが開くかはブラウザ依存である。Chrome 151 は**自動的に展開してスクロールする**（実測）が、Firefox / Safari は未検証で、非対応なら「リンクを踏んでも何も起きない」という最悪の壊れ方をする。目次に載せないかぎり、既定の導線からこの経路には入らない

**id は今までどおり付く。** `rehypeSlug` は場所を問わず h2/h3 に id を振り、sanitize が `user-content-` を付ける。目次は id を読み取って一覧を作っているだけなので、外しても id は消えず、本文中の `[…](#見出し)` も外部からの `#user-content-…` も従来どおりその見出しを指す（実測）。

**`hashchange` で祖先の `<details>` を開くスクリプトは入れない**（2026-08-03 決定）。目次から外した時点で、ブラウザ依存が残るのは著者が自分で本文に書いたリンクだけになる。折りたたみの中を指すリンクを書くこと自体が稀で、書いた本人が動作を確かめられる。**この判断は見落としではないので、Firefox で開かないことを理由に再検討しないこと。**

**実装**: `lib/rehype-collect-toc.ts`（29 行）に、`details` を先に走査して配下の h2/h3 を Set に集め、収集時にスキップする処理を足す。祖先を辿らずに済むので `unist-util-visit-parents` のような依存追加は不要。

### 8.2 見た目

`class` 属性が sanitize を通らない（§8）ため、すべて要素セレクタで書く。既存の callout / コードブロックのカードと**同じ角丸・境界・余白の系列に載せる**こと。折りたたみだけ違う語彙で描くと、記事の中で浮く。

| 対象         | 仕様                                                                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 既定の状態   | 閉じている（§5）                                                                                                                                         |
| マーカー     | ブラウザ既定の三角は消す（`summary { list-style: none }` と `::-webkit-details-marker { display: none }`）。開閉方向を示す記号は自前で `::before` に置く |
| タイトル行   | `cursor: pointer`、クリック領域は行全体。フォーカスリングは残す（キーボード操作で位置が分かること）                                                      |
| 本文         | タイトルとの境界を 1 本引き、余白はカードの内側余白に合わせる                                                                                            |
| ダークモード | 既存のカードが使っている変数をそのまま参照する。折りたたみ用に新しい色を足さない                                                                         |

エディタ側の NodeView も**同じ見た目に揃える**（callout が「公開ページと同じ 2 カラム DOM を NodeView でも作る」方針を採っているのと同じ理由 — 書いている時と公開後で見え方が変わらないこと）。ただしエディタ側だけはタイトル欄のプレースホルダ（§7.3）を持つ。

## 9. 受け入れ基準

E2E（`e2e/`）で確認する。エディタはブラウザ専用なので、tsc も vitest も実行時の振る舞いを見られない。

**往復（最重要 — §4.3）**

1. 挿入 → 保存 → 再読み込み → 保存で Markdown が不動点になる
2. 本文に callout を含むアコーディオンが往復する
3. 本文にフェンスコードブロック / テーブルを含むアコーディオンが往復する
4. タイトルが空、本文が空のアコーディオンが往復する
5. **タイトルに `<` と `&` を含むアコーディオンが往復し、文字が消えない**（§4.1）
6. 文書末のアコーディオンが往復する
7. 保存された Markdown が、公開ページで `<details>` として描画される

**導線**

8. `/` メニューから挿入でき、キャレットがタイトル欄に入る
9. `:::details ` の入力ルールが発火し、直後の Backspace 一回で元の文字列に戻る
10. テーブルセル内・引用内・callout 内・**リスト項目内**では、**入力ルールもメニュー行も出ない**。テーブルセルとリスト項目は、上書き前の `setDetails` が `true` を返す経路なので必ず確認する（§7.1）。入力ルールとメニューの**両方**を見ること（拒否経路が 2 つある）

**キー操作（§7.2）**

11. タイトル欄で Enter を押すと、開いていれば本文の先頭へ移り、閉じていればアコーディオンの下に新しいブロックができる（**閉じたまま本文へキャレットが入らないこと**）
12. タイトル欄の先頭で Backspace を押すとアコーディオンが解除され、**タイトルの文字が段落として残る**
13. タイトルが空でも下書き保存と公開の両方が通る（§5.1）

**開閉**

14. エディタで開閉しても文書が dirty にならず、autosave が走らない
15. 公開ページで開閉できる
16. **閉じたアコーディオンを含む範囲を Ctrl+A で選択して削除でき、1 回の undo で戻る**（本文は `hidden` だが文書には在る）

**ガード**

17. アコーディオンをブロックドラッグハンドルで並べ替えられる（**閉じたままでも**）
18. アコーディオンを引用 / callout / セルにドロップすると拒否され、`useEditorNotice` に §7.3 の文言が出る
19. アコーディオンの境界をまたぐ選択をドラッグしても、`detailsSummary` / `detailsContent` が裸で文書に落ちない（§6.2）
20. **閉じたアコーディオンの上にドロップしても、見えない場所にコンテンツが埋まらない**
21. アコーディオンの直後の行での Backspace、直前の行での Delete が callout と同じ挙動になる
22. **タイトルから本文へまたぐ選択**を削除・貼り付けしても構造が壊れない（二重 isolating、§6.2）
23. **本文からアコーディオンの直後のブロックへまたぐ選択**を削除・貼り付けしても構造が壊れない（同上）
24. 引用 / callout の中、リスト項目の**2 つ目以降の子**、アコーディオンの中のアコーディオンとして `<details>` を含む Markdown を読み込んでも、内容が捨てられず不動点になる（§6.3 — 新規作成は拒否するが、読み込みは通す。**スパイクで実測済み**、§4.4）
25. リスト項目の**先頭の子**に `<details>` を書いた Markdown を読み込むと、アコーディオンがリストの外へ持ち上がり、空の項目が残る。**タイトルと本文の文字は失われず、2 回目以降の往復は不動点になる**（§6.3 の例外。schema 上避けられないので、消えないことだけを担保する。**スパイクで実測済み**）

**公開側**

26. アコーディオンの中の見出しが**目次に出ない**。同じ記事のアコーディオン外の見出しは今までどおり出る（§8.1）
27. アコーディオンの中の見出しにも id が付き、本文中の `[…](#見出し)` がその id を指す（目次から外しても id は消えないこと）
28. トグルに §7.3 の日本語 `aria-label` が付く（公式拡張の英語既定が残っていないこと）

## 10. 段階リリース

- **第 1 段階**: ノードの導入、Markdown 往復、導線、キー操作と見た目（受け入れ基準 1〜16）
