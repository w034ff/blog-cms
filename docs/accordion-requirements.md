# アコーディオン（折りたたみ）機能 要件定義

- 状態: **実装済み（初版 2026-08-03、最終追加 2026-08-10）**。何がいつ入ったかは §10 が持つ（ここには書き足さないこと — 2 つの記録が競合する）
- 作成: 2026-08-03
- 実装: `components/editor/details-extension.ts`、`components/editor/details-slice-guard.ts`、`app/globals.css`、`lib/rehype-collect-toc.ts`
- 関連: `docs/footnote-requirements.md`（文書の型）、`components/editor/callout-extension.ts`（最も近い前例）、`docs/toc-requirements.md`（§8.1 の判断を目次側から参照している）

Zenn の `:::details` に相当する折りたたみブロックを、エディタと公開ページの両方で扱えるようにするための要件。**この文書は設計の記録であり、実装後もそのまま維持している** — 判断とその理由が書いてあり、コードだけでは復元できないのはそちらだからである。実測した結果は §4.4 と §6.3 に、当初の想定と違っていた点も含めて残してある。

## 1. 目的と非目標

**目的**: 長い補足・コード・前提知識・ネタバレを畳んで、本文の流れを切らずに置けるようにする。

**非目標**（初版では明示的に対象外）:

- アコーディオンの入れ子
- 「既定で開いた状態」の保存（`open` 属性の書き出し。§5 参照）
- 開閉のアニメーション
- タイトルへの装飾（太字・リンク・インラインコード）。**2026-08-10 に恒久的な決定へ格上げし、スキーマで断るようにした（§6.7）** — それまでは非目標と書いてあるだけで実際には適用でき、保存で黙って消えていた
- 既存記事の自動マイグレーション（対象記事が存在しないため不要）

## 2. データモデル

### 2.1 保存形式 — 生 HTML の `<details>`

Markdown を記憶形式とする既存方針は変えない。Markdown に折りたたみの記法が無いため、`accent-emphasis`（太字＋アクセント色を生 `<span>` で往復させている）と同じく生 HTML で保存する。

**保存する形は以下に固定する。空行 2 つが仕様の一部である。**

```markdown
<details>
<summary>タイトル</summary>

本文。**強調**もリストもここに書ける。

</details>
```

- `<summary>` の後の空行が無いと、本文が HTML ブロックに飲まれて素の文字列になる
- `</details>` の前の空行が無いと、閉じタグが直前のブロックに吸われる

`:::details` 記法（remark-directive + markdown-it-container）は**不採用**。依存を 2 つ増やす割に、生 HTML と違って他のどの Markdown 処理系でも表示されない。

### 2.2 検証済みの事実（実測、2026-08-03）

- **公開側** — 上記の形を `lib/render.ts` に通すと `<details>` / `<summary>` がそのまま出力され、中の `強調`・箇条書き・`<span class="accent-emphasis">`・`##` 見出しはすべて Markdown として解釈される。`details` / `summary` は rehype-sanitize の `defaultSchema.tagNames` に元から含まれ、`open` 属性も全要素共通の属性許可リストに入っているため通過する
- **エディタ側** — `Markdown.configure({ html: true })` なので markdown-it も同じ入力を同じ構造にパースする

逆向き（TipTap → Markdown）はこの機能の最大のリスクだったが、スパイクで検証済み（§4.4）。

### 2.3 ProseMirror スキーマ

`@tiptap/extension-details` の 3 ノード構成をそのまま使う（§3）。

| ノード           | 内容                            | 備考                                               |
| ---------------- | ------------------------------- | -------------------------------------------------- |
| `details`        | `detailsSummary detailsContent` | `group: block` / `isolating` / `defining`          |
| `detailsSummary` | `text*`                         | `isolating`。装飾不可なのは Zenn と同じ制約        |
| `detailsContent` | `block+`                        | 折りたたみ対象。閉じている間は `hidden` 属性が付く |

タイトルを属性ではなく子ノードにするのは意図的。NodeView に `<input>` を置くと、サーバーアクション保存で値が初期化される React 19 の罠（`docs/footnote-requirements.md` §9.2）を踏む。

## 3. 実装方針 — 公式拡張を採用する

`@tiptap/extension-details@3.28.0` を採用する。自前で書かない。

**採用理由**（いずれも実測で確認済み）:

- バージョンがこのリポジトリの固定値（`3.28.0` 系）と完全一致する。ファミリー一括バンプが不要
- MIT。かつては Pro 扱いだったが現在は npm 公開されている
- `parseHTML` が実物の `<details>` / `<summary>` を対象にしている（`div[data-type=...]` ではない）。保存形式と噛み合う
- `persist: false` が既定。**開閉状態がドキュメント属性にならない**（§5 がそのまま満たされる）
- `setDetails` / `unsetDetails`、末尾での Enter 脱出、Backspace での解除が実装済み

**新規依存**: `@tiptap/extension-details@3.28.0` と、その peer である `@tiptap/extension-text-style@3.28.0`（現在未インストール）。どちらも TipTap 公式・固定バージョン一致だが、依存追加の方針上ここで明示しておく。

**自前で足すもの**:

1. Markdown の直列化とパース（§4）— 公式拡張はこれを持たない
2. **`setDetails` の拒否条件**（§7）— 公式のコマンドは配置先を一切見ない
3. ガード群との統合（§6）

**注意**: 公式拡張のソースには `createBlockMarkdownSpec(...)` が含まれるが、これは TipTap 3 が持つ独自の Markdown 層のもので、このリポジトリが使う tiptap-markdown 0.9.0 は読まない。返すのは `parseMarkdown` / `markdownTokenizer` などのトップレベル spec キーであり、`addStorage()` を定義しないので、こちらの `.extend({ addStorage })` と衝突もしない（実測）。**動くように見えて無効**という誤解を招く箇所なので、実装時にコメントを残すこと。

## 4. Markdown の往復（この機能の最大のリスク）

### 4.1 直列化

prosemirror-markdown には「生 HTML ブロックで Markdown の子を包む」概念が無いため、`serializeCallout` と同じく手書きになる。§2.1 の空行 2 つを厳密に出すこと。

**タイトルは HTML エスケープが必要。** 本文は通常の Markdown として書き出されるので prosemirror-markdown のエスケープに乗るが、`<summary>タイトル</summary>` の行だけは生 HTML である。`a <b> c` というタイトルをそのまま書くと markdown-it が `<b>` をタグとして解釈し、往復で文字が消える。`&` も同じ。書き出し時に `&` と `<` をエスケープすること（DOM パース側が復号するので不動点は保たれる）。これは「見苦しい入力」ではなく「壊れる入力」であり、脚注要件 §5.3 と同じ種類の問題。

### 4.2 パース

`updateCalloutDOM` と同じ `parse.updateDOM` フックで、`<details>` 直下の `<summary>` 以外のブロックを `<div data-type="detailsContent">` に包み直す。公式拡張の `detailsContent` はこのタグを期待しており、保存された Markdown にはそれが無いため、この工程が無いと本文が落ちる。

**tiptap-markdown はパースのたびに `parse.setup` を再実行する。フックは冪等に書くこと**（脚注の件で踏んだ罠）。

### 4.3 受け入れの判定基準

**`getMarkdown()` → 読み込み → `getMarkdown()` が完全一致すること（不動点）。かつ中間の Markdown が §2.2 で確認した HTML を再現すること。**

以下を往復ケースに含める。

- 本文に callout（`> [!NOTE]`）を含むアコーディオン — 空行規則を最も強く突く組み合わせ。禁止していないので到達可能
- 本文にフェンスコードブロックを含むアコーディオン
- 本文にテーブルを含むアコーディオン
- タイトルが空のアコーディオン
- タイトルに `<` と `&` を含むアコーディオン（§4.1 のエスケープ）
- 本文が空のアコーディオン
- アコーディオンが文書の末尾にある場合

### 4.4 検証結果（2026-08-03、スパイクで実測）

**この節が最大のリスクとしていた不動点は、成立することを確認した。** §4.1 / §4.2 の方針どおりに書いた最小実装（マークダウン層のみ。ガードも導線も見た目も無し）で、上記の全ケースと以下が初回から不動点になった。

- 本文が callout / フェンス / テーブル / リスト / 複数ブロックのそれぞれ
- タイトルが空、本文が空、タイトルが `*強調*`（`state.text()` を使うと `\*` に化けるので、生の `write()` で書くこと）、タイトルが `<` と `&` を含む
- 前後に段落があるとき、文書末にあるとき
- 直列化された Markdown が公開ページで `<details>` として描画されること（callout / Shiki 付きコードブロック / エスケープされたタイトルまで確認）

**挿入経路の正規化は不要だった。** `setDetails` が作るノードと、パースが作るノードは同じ形になり、「エディタで作ってから保存」も「読み込んでから保存」と同じ出力に落ちる。両者がずれる可能性（コードブロックの幻の末尾改行と同じ非対称）を疑っていたが、起きなかった。

**既知の逸脱が 1 つ。** 空行を省いた非正規な入力（`<details>` / `<summary>` / 本文 / `</details>` を空行なしで書いたもの）を読み込むと、本文の末尾に空の段落が 1 つ増える。Markdown の出力は正規形に整えられ、そこから先は不動点になるので実害は小さいが、手書きの Markdown を取り込んだアコーディオンの末尾に空行が 1 行見える。仕様として許容する。

## 5. 開閉状態

**開閉はドキュメントに保存しない。** 公式拡張の `persist: false`（既定）のまま使い、開閉は NodeView のクラスと `hidden` 属性だけで表現する。

理由は autosave。開閉を属性にすると、エディタで畳むたびに文書が dirty になり保存が走る。閲覧操作が保存を起こすのは誤りである。

公開ページは常に閉じた状態で出力する（`open` を書き出さない）。「既定で開く」が必要になったら、開閉トグルとは別の明示的なコントロールとして後から足す。

### 5.1 空のタイトル・空の本文 — 公開時の検証は足さない

**タイトルが空でも本文が空でも、下書き保存も公開も通す。** 検証を追加しない。

脚注要件（§5.2 / §5.3）は逆の判断をしているが、そこでの理由がここには当てはまらない。脚注の空定義は「見苦しい入力」ではなく Markdown の往復で壊れる入力だったから公開前に潰す必要があった。アコーディオンの空タイトルは `<summary></summary>` として往復し、公開ページでもラベルのない三角として描画される（§9 の受け入れ基準 4 と 19 で確認する。描画そのものには手当てが要った — 空の `<summary>` は行ボックスを作らないので公開側だけタイトル行が潰れる。§8.3）。壊れないものを公開時に止めると、「保存はできるのに公開できない」状態を新たに作るだけで、得るものがない。

代わりに執筆中に気づける形にする。タイトルが空のあいだは NodeView にプレースホルダを表示する（§7.3）。これは `app/actions/posts.ts` の既存方針（必須項目の検証は公開時、autosave は寛容）とも矛盾しない — そもそも必須項目にしない、という判断だからである。

### 5.2 公開ページに既定のタイトルは足さない（2026-08-03 決定）

**無題の折りたたみは、公開ページでもラベルのないまま出す。** エディタのプレースホルダ（§7.3）を公開側にも出す案を検討し、採らなかった。

プレースホルダは著者への指示であって読者向けのラベルではない。読者はそれに対して何もできず、CMS の内部文言が記事に漏れたようにしか見えない。かつ見出しとして単純に間違っている — 「タイトル」という見出しは中身について何も言っておらず、開くかどうかの判断材料にならない。読者向けの既定語（「詳細」など）を当てる案もあるが、本文に無い言葉をすべての無題の折りたたみに足すことになる。無題のまま公開するのは意図的な操作（挿入時にキャレットはタイトルに入る）で頻度が低く、読者から見て壊れてもいない。

**承知している欠点**（実測、2026-08-03）: 無題のアコーディオンにはアクセシブルネームが無い。`aria` スナップショットで題ありが `group: 題あり` になるのに対し、無題は `group` のままで、`tabIndex` は 0 なのでキーボードでも読み上げでも到達する。つまり「名前のない操作子」が残る。上の判断はこれを承知のうえで下したものなので、**アクセシブルネームが無いことだけを理由に再検討しないこと。** 頻度と、全記事に本文外の語を足すコストとの比較で決めている。

再検討するとしたら、根拠は「無題の公開が実際に増えた」か「読み上げ利用者から実害の報告があった」のどちらかであり、そのときも**保存形式は触らない** — Markdown に既定タイトルを書き込むと §4.3 の不動点と、空タイトルが `<summary></summary>` として往復するという上の前提が壊れる。描画側だけで完結させること。なお `aria-label` で見た目を変えずに名前だけ与える案は、rehype-sanitize の既定スキーマを通るかを未確認のまま置いてある（`open` が通るのは全要素共通の属性許可リストによるもので、`aria-*` がそこに含まれるかは別の話。§2.2）。

## 6. 既存ガードとの関係

ここは「後で考える」で済ませてはならない。同種の見落としが過去に 2 回、実バグになっている（テーブルの clamp が内側の isolating を取り違えた件、drop/paste/Enter がセル内で別々の規則に答えていた件）。

### 6.1 そのまま効くもの（型に依存しない実装のため）

| 場所                  | 効く理由                                                           |
| --------------------- | ------------------------------------------------------------------ |
| `table-cell-rules.ts` | 「段落以外のブロック」を一律に拒否する。セルへの流入は塞がれている |
| `slice-placement.ts`  | 開いたラッパを一般に剥がす。型名を見ていない                       |

### 6.2 手当て・確認が要るもの

| 場所                                        | 必要な作業                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| `block-drag-handle.ts` の `DRAGGABLE_TYPES` | `'details'` を追加する                                                  |
| `callout-slice-guard.ts` 相当               | details 版のスライスガードが要る（下記の落とし穴あり）                  |
| `drop-cursor-guard.ts`                      | 述語に details のネスト判定を足す。フックは 1 つでなければならない      |
| `isolating-boundary.ts`                     | 自動で対象になるが、**二重 isolating の形なので実測で確認する**（下記） |

**`isolating-boundary.ts` は「無償で効く」に入れない。** スキーマの `isolating` を読む実装なので `details` は自動的に対象になるが、`details` と `detailsSummary` の**両方が `isolating: true`** であり、これは issue #7（テーブルが 2 階層で isolating であるためクランプが内側を取り違えた件）とまったく同じ形をしている。現在のクランプは内側を取るよう直っているので恐らく問題ないが、一度実バグを出した形を「確認せず効くもの」に分類してはならない。§9 の 18・19 で明示的に確認する。

**半選択の展開処理は callout と共有している。** `components/editor/box-slice-repair.ts` の `createBoxSliceRepair` が `unwrapHalfSelected` と `flattenClosed` を 1 つ持ち、両ガードがそれぞれの指定で呼ぶ（2026-08-18、`16cece4`）。共有できるようになった理由は、箱をほどく操作が関数として切り出されたことにある — かつてはここに「流用できない」と書いてあり、コードがそう書かれていた間はそれが正しかった。

差は 4 つで、すべて名前の付いた引数になっている。

| 引数                 | callout                 | details              |
| -------------------- | ----------------------- | -------------------- |
| `nodeName`           | `callout`               | `details`            |
| `unwrap`             | 子をそのまま 1 階層上へ | `detailsUnwrapped()` |
| `depthDrop`          | 1                       | 2                    |
| `recurseIntoRemoved` | `true`                  | `false`              |

`unwrap` が分かれている理由はここに書いてあったとおりである。callout の子は `block+` なのでトップレベルに差し込んで妥当だが、`details` の子は `[detailsSummary, detailsContent]` であり、同じ差し込み方をするとスキーマ不正になる。`detailsUnwrapped()` は `detailsContent` の子を取り出し、タイトルを本文先頭の段落として残す（空タイトルは捨てる。§7.5 と歩調を合わせること）。`depthDrop` が 2 なのも同じ理由で、設計時に「展開の深さは型ごとに持たせること」と書いた予測はそのまま当たっている。

**予測できていなかったのは `recurseIntoRemoved` である。** `flattenClosed` が取り除いた箱の中身を再走査するかどうかで、callout は再走査する（`> > [!NOTE]` が囲み枠の入れ子として読み込めるので、外側だけ剥がしても足りない）。アコーディオンは再走査しない — アコーディオンはアコーディオンの中に入らないため、差が出るのは持ち上げた本文の中に別の箱がある形だけで、そこは触らないのが従来からの挙動である。

合成順は引数ではない。`dropOpenWrappers` の位置は両ガードで違う（callout は自分の `transformPasted` に畳み込み、details は呼ばない）が、結果は変わらない — `dropOpenWrappers` が働く条件は「子が 1 つで両端が深さ 1 を超えて開いている」であり、それはちょうど `halfSelectedEdges` が手を出さない形だからである。到達可能な 10 形すべてで実測した（`components/editor/slice-guard-composition.test.ts`）。

### 6.3 配置の規則 — 新規作成はトップレベル限定

**アコーディオンを新しく作れるのは文書のトップレベル（`depth === 1`）だけとする。** 禁止先を列挙するのではなく、この一行を規則とする。引用・callout・テーブルセル・リスト項目・アコーディオンの中は、すべてこれ 1 つで拒否される。

| 組み合わせ                               | 判断 | 理由                                                                |
| ---------------------------------------- | ---- | ------------------------------------------------------------------- |
| アコーディオンの中のアコーディオン       | 禁止 | 非目標                                                              |
| 引用 / callout の中に置く                | 禁止 | 保存形式の問題ではない（下記）。初版のスコープを絞るための判断      |
| テーブルセルの中に置く                   | 禁止 | セルは段落しか持てず、既に専用ガードがある（`table-cell-rules.ts`） |
| リスト項目の中に置く                     | 禁止 | 保存形式の問題ではない（下記）。初版のスコープを絞るための判断      |
| アコーディオンの中の callout・表・コード | 許可 | 折りたたむ価値があるのはまさにこれら                                |

**この表のうちテーブルセル以外は、どれも「壊れるから」ではない**（2026-08-03、スパイクで実測）。当初は引用について「`> ` 付与を生 HTML が生き延びるかは未検証、試して壊すより拒否する」と書いていたが、実測すると

- `> <details>` … `> </details>` は往復する（引用の中でも callout の中でも不動点になる）
- 2 スペース字下げしてリスト項目の 2 つ目以降の子に置いた形も往復する
- アコーディオンの中のアコーディオンさえ往復する

**つまり配置の制限は、保存形式ではなく次の 2 点だけに立っている。**

- `block-drag-handle.ts` の対象はトップレベルのみ。入れ子にしたアコーディオンだけドラッグハンドルが出ず、並べ替えられない
- 初版の作業量を絞る。とくにリスト項目内に置くには、`setDetails` に「項目の先頭段落では変換せず次の子として挿入する」分岐が要る（下記）

**この 2 点は「壊れる」より弱い根拠である。**引用や callout の中を許したくなったら、スキーマも保存形式も変えずに拒否を外すだけで済む — 変更が要るのはドラッグハンドルの扱いだけ。そう判断したうえで初版は絞る。

**「入力ルールとメニューで挙動が違うのは不整合だ」という理由は採らない。** このリポジトリは同じ問いに既に答えを出している — `code-block-extension.ts` の `insertCodeBlock` は、リスト項目の先頭段落では変換が schema 上できないためその次の子としてブロックを置くという二分岐で作られており、` ```lang ` の入力ルールは変換専用のまま先頭段落で不発でよい、と明記されている。同じコメントは callout とテーブルのボタンが以前からリスト項目内にブロックを置いてきたことを、正しい挙動として引き合いに出している。

つまり「wrap 型の入力ルールはリスト項目の先頭で不発、insert 型のコマンドは通る」という非対称は、このリポジトリでは欠陥ではなく既定の設計である。

**将来リスト内を許す場合の作り方**: `insertCodeBlock` と同じ二分岐（変換できるならする / できなければ項目の次の子として挿入）を `setDetails` に足し、`block-drag-handle.ts` の扱いを併せて決めること。入力ルールは変換専用のままでよい。

**禁止するのは操作であって、スキーマではない。** `detailsContent` の内容を制限したり、引用が `details` を持てないようにスキーマで縛ってはならない。`callout-slice-guard.ts:42-46` がその理由を述べている — スキーマで形を禁じると、その形を含む既存の Markdown を開いた瞬間に内容が黙って捨てられる。引用の中の `<details>` を含む Markdown は外部から流入し得るので、読み込めるが新規に作れないという状態が正しい。

**ただしリスト項目の先頭の子だけは例外で、これは選べない。** `listItem` の content は `paragraph block*`（`@tiptap/extension-list` の既定、このリポジトリは上書きしていない）なので、index 0 に段落以外を置けない。

実機で測った結果（2026-08-03、E2E ハーネス）はこうなる — **内容は失われず、入れ子だけが失われる**。ブロックはリストの外へ持ち上げられ、空のリスト項目が残る。

| 入力               | 読み込み後の文書                                                 | 保存される Markdown           |
| ------------------ | ---------------------------------------------------------------- | ----------------------------- |
| `- ```ts` + コード | `bulletList(listItem(paragraph)), codeBlock("const a = 1\n")`    | `- ` + トップレベルのフェンス |
| `- > 引用`         | `bulletList(listItem(paragraph)), blockquote(paragraph("引用"))` | `- ` + トップレベルの引用     |

コード本文も言語指定（`ts`）も残り、2 回目以降の往復は不動点になる。`<details>` を項目の先頭に書いた Markdown も同じ経路を通るはずなので、受け入れ基準では「持ち上がること」と「文字が消えないこと」を確認する。字下げして項目の 2 つ目以降の子に置いた形（`- 項目` の次の空行のあと）は schema が保持できるので、そちらはそのまま読み込めること。

判定は挿入位置の深さで行う（`setCallout` が使う `selectionTouches` の列挙ではなく、`:::` 入力ルールと同じ `depth === 1` の検査）。ただし**ドロップと貼り付けの拒否**は位置ではなくスライスを見る必要があるため、そちらは `selection-scan.ts` の `selectionTouches(state, ...typeNames)` を使う（§6.2 のスライスガード）。

**判定は必ず state 側の選択を読むこと**（クリックによるキャレット確定は `state.selection` に対して 20ms 遅れる。同じ罠で過去に「貼り付けが効かない」バグを出している）。

### 6.4 callout が直面しなかった 2 点

- **閉じたアコーディオンへのドロップ。** `resolveDropTarget` が `hidden` な内容の中を指し得る。著者から見えない場所にコンテンツが埋まるという、callout には存在しなかったバグの種類。受け入れ基準に含める（§9 の 16）
- **`allowGapCursor: false`。** 公式の `Details` はこれを設定しており、callout は設定していない。2 つの箱が境界で違う挙動になるので、**そのまま採るか上書きするかを実装時に明示的に決めて、コメントに残すこと**

### 6.5 タイトルは `text*` である — インラインノードは入らない（2026-08-08 実測）

**§6.5〜6.8 は「タイトルは何を受け取るのか」という 1 つの問いに答えている。**節が 4 つあるのは答えが 4 種類だからではなく、同じ 1 つの穴を 3 日かけて別々に踏んだからである（§6.6 がそう書いている）。並びは発見の順なので、探すときはこの索引から入ること。**統合はしない** — §6.6 と §6.8 は `details-slice-guard.ts` から番号で名指しされている。

| 問い                                 | 答える節       | 断り方                                   |
| ------------------------------------ | -------------- | ---------------------------------------- |
| インラインのノードを置けるか         | §6.5（この節） | 内容表現 `text*`（＋脚注側の配置ガード） |
| ブロックを作るコマンドを通すか       | §6.6           | 3 つの拒否述語に `detailsSummary`        |
| マークを持てるか                     | §6.7           | スキーマの `marks: ''`                   |
| ドロップ・貼り付けのスライスはどうか | §6.8           | 構造を持つスライスだけ拒否               |

`detailsSummary` の内容表現は公式拡張が `text*` と決めており、**テキスト以外のインラインノードを受け取らない。**このエディタでインラインの atom を拒むテキストブロックは `codeBlock` とこれの 2 つだけである。

最初にここを踏んだのは脚注だった。タイトルにキャレットを置いて脚注を挿すと、ProseMirror の整形アルゴリズムがアコーディオンを 2 つに割って参照の置き場所を作り、タイトルの後半が本文に落ちて空タイトルのアコーディオンが生えた。詳細と対応は脚注要件 §6.5 にある（塞ぐのは脚注側の配置ガード 2 つで、アコーディオン側の変更は不要）。

**今後インラインのノード型を足すときは、ここが判定の対象になる。**タイトルは加えて `<summary>…</summary>` という生 HTML 1 行として往復し、`serializeDetails` が `textContent` で読む（§2.1・§4.1）ので、スキーマが通したとしても保存で消える。タイトルに何かを置きたくなったら、内容表現・シリアライザ・公開側レンダラの 3 点が揃って初めて成立する。

### 6.6 タイトルはセルと同じ扱いにする — ブロックもマークも入らない（2026-08-10 実装）

**脚注だけを塞いだのは足りていなかった。** §6.5 は脚注側で対応して閉じたが、同じ裂け方をする経路が 3 つ残っていた — 囲み枠・表・画像。同じ監査漏れはマークにもあり、それは §6.7 で塞ぐ（`text*` はノードの制約なのでマークには効かず、装飾は適用できて保存で消えていた）。ここで直したのは 4 つ目までを含む 1 つの穴であって、別々の発見ではない。どれもタイトルにキャレットがある状態でツールバーからもスラッシュメニューからも実行でき、実測（2026-08-10）ではこうなる。

```
before: details(detailsSummary("あいうえお"), detailsContent(paragraph))
after:  details(detailsSummary("あいう"),    detailsContent(paragraph))
        callout(paragraph)
        details(detailsSummary("えお"),      detailsContent(paragraph))
```

キャレットの位置で題が切れ、畳まれた無題のアコーディオンが 1 つ生える。Markdown も `<details>` 2 つとして保存されるので、表示の乱れではなく文書が壊れる。例外は出ない（`pageerror` 0 件）ため、保存するまで気づけない。

**塞ぎ方はセルと同じにする。** 3 つの拒否述語はどれも既に `table` を並べていたので、そこに `detailsSummary` を足すだけで済む — `callout-extension.ts` の `setCallout`、`table-extensions.ts` の `insertTable`、`useImageUpload.ts`（と対になる `Toolbar.tsx` の `imageBlocked`）。**`details` ではなく `detailsSummary`。** §6.3 は囲み枠・表・コードを本文の中では許可しており、そこは実測でも正常に動く。

これで導線は 2 つとも自動的に閉じる。スラッシュメニューは `can()` を訊いて行を隠し、ツールバーは `can()` で自分を無効化するので、経路ごとの手当てが要らない。両方から入れてしまっていたのは、どちらも同じ嘘の `can()` を信じていたからである。副次的に、タイトルでは全ての行が落ちるので `hasAnyItem` が false になり、`/` はセルの中と同じくただの文字になる（受け入れ基準 38）。

**拒否に通知は付けない。**押せなくなるので説明すべきジェスチャーが残らない — `setDetails` が「`setCallout` と同じく無言で断る」と書いているのと同じ理由である。画像だけは別で、ピッカーは灰色にできても貼り付けとドロップには灰色にする対象が無いため、既存の通知の仕組みに乗せる。文言はホストごとの定数から触れているホストを並べて組み立てる形に変えた（2 ホストで 3 つだった定数が、3 ホストなら 7 つになるため）。1・2 ホストの文面は変えていない。「アコーディオンのタイトル」という呼び方は脚注のガードが既に使っている語に揃えてある — 同じ場所が 2 つの名前で呼ばれるのは §7.3 が囲み枠／コールアウトについて記録している失敗そのものである。

### 6.7 タイトルの装飾は恒久的に持たない — スキーマで断る（2026-08-10 決定）

**マークもタイトルには入れない。** §1 は「タイトルへの装飾」を初版の非目標に挙げていたが、**実際には何も拒否していなかった** — `text*` はノードの制約であってマークの制約ではないので、太字・斜体・打ち消し・インラインコード・アクセント・リンクのすべてが `can()` = true で適用でき、文書は `detailsSummary(bold("タイトル"))` になる。そして `serializeDetails` が `textContent` で読むため、保存した瞬間に黙って消える（実測 2026-08-10）。非目標を「やらない」と書いておきながら、やれてしまい、しかも失われる状態だった。これを恒久的な決定に格上げする。

**コマンドごとのガードではなく `MarkdownDetailsSummary` の `marks: ''` で断る。** 理由は 3 つ。

- **経路を数えなくてよい。** ツールバーだけでなく Ctrl+B のようなキーボード経路も、貼り付けで持ち込まれる装飾も、Markdown 読み込みで入る `<summary><b>…</b></summary>` も、宣言 1 つで同時に閉じる。§6.6 の欠陥は「経路を数え落とした」形で起きており、同じ失敗を繰り返さない
- **UI 側に規則を持たせずに済む。** `can().toggleBold()` が false になるので、ツールバーは既存の `disabled` でひとりでに灰色になる
- **§6.3 の「禁止するのは操作であってスキーマではない」は、ここには当てはまらない。** あの原則の理由は「スキーマで形を禁じると、その形を含む既存の Markdown を開いた瞬間に内容が黙って捨てられる」ことだった。マークを落としても文字は残る（実測。`<summary><b>強調</b>と地</summary>` は `強調と地` として読み込まれる）。しかも装飾は今日すでに保存で消えているので、`marks: ''` は失うものを増やさず、**損失を「保存時に黙って」から「打った瞬間に見える形で」へ移すだけ**である

**再検討するときは、この 1 行だけでは足りない。** §6.5 の 3 点（内容表現・シリアライザ・公開側レンダラ）が揃って初めて装飾は成立する。

### 6.8 ドロップと貼り付けも同じ規則にする — ただし判定はスライスで（2026-08-10 実装）

**コマンドを塞いでも、スライスで運べば同じ裂け方をする。** §6.6 が導線を閉じたあとも、段落を跨いだ選択をタイトルへドラッグまたは貼り付けると、アコーディオンは同じように 2 つに割れる（ドラッグは実ブラウザで手動確認、貼り付けは実測 2026-08-10）。

```
before: details(detailsSummary("タイトル"), detailsContent(paragraph("本文"))), paragraph("一つ目の段落"), paragraph("二つ目の段落")
after:  details(detailsSummary("目の段落"),  detailsContent(paragraph)),
        paragraph("二つ目のタイトル"),
        details(detailsSummary, detailsContent(paragraph("本文"))), …
```

**判定は落とし先ではなくスライスの形で行う。** 段落を跨がない選択は純粋なインライン内容しか運ばず、タイトルに文字として正しく入る — これは著者が使うジェスチャーであり、奪ってはならない。ブロックの境界を跨いだ瞬間にスライスが構造を持ち始める、そこが分かれ目である。

規則はタイトルが受け取れるものの側から書く — **文字だけ**。拒否する型を並べるのではないので、この先ノード型が増えても古くならない（§6.3 が配置規則を `depth === 1` で書いたのと同じ理由）。実装は `details-slice-guard.ts` の `titleAcceptsSlice`。

| スライス                                          | 判定 | 理由                                         |
| ------------------------------------------------- | ---- | -------------------------------------------- |
| 段落内の範囲（両端が開いた 1 テキストブロック）   | 通す | インライン内容だけが置かれる                 |
| 裸のインライン内容                                | 通す | 素のテキスト貼り付けはこの形で届くことがある |
| 段落を跨いだ範囲（子が 2 つ以上）                 | 拒否 | 運んでいるのがブロック境界そのもの           |
| ノード選択で取った 1 ブロック（両端が閉じている） | 拒否 | どこへ置いてもブロック                       |
| インラインの atom を含む（段落は跨がない）        | 通す | この問いは §6.5 の担当（下記）               |

**このガードはブロック構造だけを問い、インラインの atom は意図的に通す。** `text*` のタイトルはそちらでも裂けるが、その問いは既に §6.5 の脚注の配置ガードが持っており、しかも拒否より良い答えを出している — 貼り付けでは参照をリテラルのテキストに落として著者の文字は着地させ、ドロップでは脚注を名指した文言で断る。ここで先に答えるとその両方を奪う（実測: 脚注のスペックが 2 件赤くなった）。**1 つのガードが 1 つの問いを持つ** — こちらはブロック構造、§6.5 はインラインノード。今後インラインのノード型を足すときに読むのは §6.5 であって、この節ではない。段落を跨いだスライスは atom を含んでいても拒否されるので、譲っても穴は開かない。

**ガードは `details-slice-guard.ts` の既存の `handlePaste` / `handleDrop` に足す。** 貼り付けはキャレットを、ドロップは `resolveDropTarget` が解決した位置を見る（ドロップの時点で `state.selection` はまだドラッグ元の範囲を指しているため）。**キャレットは必ず state 側から読む** — クリックは DOM のキャレットを 20ms 先に置くので、その窓の Ctrl+V は「さっきまでの居場所」に対して判定されてしまう。

拒否したときは**何も起きない＋通知**。文言は `アコーディオンのタイトルには段落やブロックを入れられません`。テキストだけ取り出して入れる案は採らない — タイトルは `text*` なので `hardBreak` すら置けず（表のセルが 2 段落を hardBreak で畳んでいる手が使えない）、段落の切れ目を黙って失う変換になる。

文言は入れられない側を名指す（2026-08-10 改定）。最初は `…には文字しか入れられません` と規則の側から書いたが、これは出た瞬間に外す — 著者が握っているものは本人の目にはたいてい「文字」（2 段落ぶんの文字）なので、文字しか入らないと言われると矛盾に読める。`改行` で言い換える案も検討して採らなかった: 断る 3 形のうち 2 つには改行が無い（ノード選択で取った 1 段落、貼り付けた囲み枠や表）ので、その 2 つで明白に嘘になる。構造を名指す形は 3 形すべてに対して真であり、兄弟の `アコーディオンは引用やリスト、コールアウト、表の中には入れられません` とも系統がそろう。

**ノード選択で取った 1 ブロックの扱いだけ、挙動が変わっている。** ガード以前これは破壊的ではなく、アコーディオンの手前に落ちていた。壊れてはいなかったが、タイトルに入れようとした内容が箱の外に出るのは説明のつかない着地であり、規則を 1 つにするほうがよい。

**エディタ内のテキスト選択のドラッグは E2E で駆動できる。** `e2e/native-drag.ts` の `dragSelect` と `cdpNativeDrag` がその手段で、ドロップまで完走する（`e2e/callout-drop-guard.spec.ts` が囲み枠の境界をまたぐ選択で実際に使っている）。ここにはかつて「駆動できない、CDP では `dragstart` が発火しない」と書いてあった。発火しないのは `dragstart` ではなく **`drop`** のほうである — 素のマウス操作（選択の内側で mousedown して少し動かす）は本物の `dragstart` を出し、`view.dragging` も立つ。ヘッドレス Chromium がテキスト選択のドラッグに対して `Input.dragIntercepted` を出さないだけなので、待たずに `DragData` を組み立てて `Input.dispatchDragEvent` で dragEnter / dragOver / drop を送る。落ちるスライスは `view.dragging` から来るため、実際のテキスト移動に忠実である。

分担そのものは変えていない。貼り付け側は `e2e/editor-details-title-guard.spec.ts`、**両者が共有する述語は `components/editor/details-title-slice.test.ts`（vitest）** で押さえてある。手動確認に頼る必要はもう無いので、ドロップ側を詰めるならこの手段を使うこと。

**なおブロックドラッグハンドルでタイトルへ落とす経路は最初から塞がっている**（ハンドルは HTML5 drag ではなく自前の mousedown ドラッグで、タイトル上では落とし先の指標が出ない）。この経路を CDP の drag イベントで測ると壊れていないものが壊れて見えるので、素のマウスで測ること。

## 7. 導線

| 経路                       | 採否               | 備考                                                                                                                                     |
| -------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| スラッシュメニュー         | 採用               | ブロック要素なので `slash-command.ts` の `startOfLine: true` と噛み合う。`available` は `can().setDetails()`（ただし下記の上書きが前提） |
| `:::details ` の入力ルール | 採用               | callout の `DIRECTIVE` と同じ形（末尾スペースで確定、トップレベル限定）                                                                  |
| ツールバー（ポインタ用）   | **不採用**         | スラッシュメニューと入力ルールで足りる（下記）                                                                                           |
| ＋ドロワーの行（モバイル） | 採用（2026-09-20） | §7.9。ポインタ用ツールバーには出さない                                                                                                   |
| Backspace での解除         | 採用               | 公式拡張の `unsetDetails` にそのまま乗る                                                                                                 |

挿入後のキャレットは**タイトル欄**に置く（公式の `setDetails` の挙動）。タイトルが空のまま本文を書き始める事故を減らせる。

**ポインタ用ツールバーには置かない**（2026-08-03 決定）。callout がツールバーに載っているのは 3 種類の型を選ばせる必要があるからで、単一のブロックであるアコーディオンにその理由は無い。スラッシュメニューと `:::details ` の入力ルールの 2 経路で足りる。ツールバーの列を増やさないぶん、狭い画面での折り返しも増えない。モバイルの＋ドロワーはこの制約の外にあり、§7.9 は別に決めている。

### 7.1 `setDetails` は必ず上書きすること（前提条件）

**公式の `setDetails` には配置先の検査が一切ない。** 実装は「`$from.blockRange($to)` を取り、`detailsContent` の `contentMatch` に合えば挿入する」だけで、テーブル・引用・callout のいずれも見ていない。

したがってテーブルセルの中でも `can().setDetails()` は `true` を返す。セルの段落は `block+` に一致してしまうからで、スラッシュメニューの行はそのまま表示され、実行すればセルにアコーディオンが入ってテーブルが分断される — `table-cell-rules.ts` が記録している、まさにその破壊。

`can().setCallout()` が `available` の述語として機能しているのは、`setCallout` 自身が `selectionTouches(state, 'table', 'blockquote')` の拒否を内蔵しているからである。公式のコマンドはそれを持たない。

よって `Details.extend({ addCommands })` で `setDetails` を包み、§6.3 のトップレベル限定（`depth === 1`）の拒否を先に効かせる。それをして初めて `can().setDetails()` が正しい述語になる。 順序を守ること。

### 7.2 キー操作

公式拡張が既に持っている挙動を仕様として確定させる（実装は乗るだけだが、書いていないと「決めていない」のか「そう決めた」のか後から分からなくなる）。表のうち Tab の 1 行だけは公式に無い自前の束縛で、判断そのものは下に書く。本文の先頭の Backspace の 3 行は後から測って書き足したもので、**この拡張が答えているのではない** — 大半は prosemirror-commands の既定であり、コードブロックの自己選択だけは `code-block-extension.ts` の自前の束縛である。そこを揃えないという判断は §7.8 にある。

| キー               | 位置                                                  | 挙動                                                                             |
| ------------------ | ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| Enter              | タイトル欄（開いている）                              | 本文の先頭へ移る（本文が空 1 行のときだけ自前。§7.4）。タイトルは改行しない      |
| Enter              | タイトル欄（閉じている）                              | アコーディオンの**下**に新しいブロックを作る                                     |
| Enter              | 本文の末尾の空行                                      | アコーディオンの外へ出る（callout と同じ考え方）                                 |
| Tab                | タイトル欄（開いている）                              | 本文の先頭へ移る。**何も挿入しない**（下記）                                     |
| Tab                | タイトル欄（閉じている）                              | 束縛しない（ブラウザの既定どおりフォーカスが移る）                               |
| Tab                | 本文の中                                              | 束縛しない（リストのインデントなど、他の拡張の Tab がそのまま効く）              |
| Backspace          | タイトル欄の先頭                                      | アコーディオンを解除する。**タイトルの文字は段落として残り**、本文がその後に続く |
| Backspace          | 本文の先頭（段落。中身があるか、本文がその 1 行だけ） | 何も起きない。タイトルへは吸わせない（§7.8）                                     |
| Backspace          | 本文の先頭（空段落で、後ろにブロックがある）          | その空行が消え、キャレットがタイトルの末尾へ移る（§7.8）                         |
| Backspace          | 本文の先頭（段落以外の型）                            | その型の既定に従う（リストは項目の持ち上げ、コードブロックは自己選択。§7.8）     |
| Backspace / Delete | アコーディオンの前後の境界                            | callout と同じ（§6.4 の `allowGapCursor` の判断に従う）                          |

**タイトル欄の Enter は必ず自前で確認すること。** `detailsSummary` は `text*` なので、この束縛が無いと既定の分割が走って何が起きるか分からない。上表の 2 行目（閉じているときは下にブロックを作る）は公式の判断であり、そのまま採る。閉じたまま本文へキャレットを送ると、見えていない場所に文字を打ててしまうため。

**タイトル欄の Tab は「今ある本文へ移る」だけの移動である（2026-08-04 追加）。** Enter で本文へ入ると、本文に何か書かれている場合は公式ハンドラが本文の 1 行目を挿入するため、著者が消す空段落が 1 つ残る（§7.4 の自前処理は、挿入と移動の結果が一致する「本文が空 1 行」の形だけを直している）。Tab はその形に依存せず、内容を一切変えずに移動できる唯一の手段として置く。表計算やテーブルのセル間と同じ「次の入力欄へ」の意味であり、意味を変えているわけではない。

当初は「Tab はリストのインデントに使うので束縛しない」としていたが、これはタイトル欄には当てはまらない。`detailsSummary` は `text*` で、リストもテーブルも中に入れないため、ここで他の拡張の Tab と競合することはない。束縛の順序にも依存しない。

閉じているときは束縛しない。**見えていない本文へキャレットを送らない**という上表 2 行目（閉じたタイトルの Enter）と同じ理由である。断ったあとの Tab はプロースの他の場所と同じくブラウザのフォーカス移動になる。

**本文からタイトルへ戻る Shift+Tab は入れない。** 本文は `block+` でリストを置けるため、そこでの Shift+Tab は既に `liftListItem` の意味を持つ。奪うには相応の理由が要るが、今のところ要望がない。**ここで断っているのは束縛であって、本文 → タイトルの移動が到達不能だと言っているのではない** — 上表の「本文の先頭（空行・後続あり）」がその移動を 1 つだけ提供している（§7.8）。鍵を奪っていないので、この決定と矛盾しない。

### 7.3 文言（すべて日本語）

サイト UI は日本語なので、公式拡張が入れる英語の `aria-label` は上書きする。

| 箇所                        | 文言                                                                   |
| --------------------------- | ---------------------------------------------------------------------- |
| 機能名（UI 上の呼び方）     | **アコーディオン**（2026-08-03 改定。下記）                            |
| スラッシュメニューの行      | `アコーディオン`                                                       |
| 同・検索キーワード          | `details` / `accordion` / `toggle` / `折りたたみ` / `たたむ`           |
| タイトル欄のプレースホルダ  | `タイトル`                                                             |
| トグルの `aria-label`（閉） | `アコーディオンを開く`                                                 |
| トグルの `aria-label`（開） | `アコーディオンを閉じる`                                               |
| 配置を拒否したときの通知    | `アコーディオンは引用やリスト、コールアウト、表の中には入れられません` |

**「折りたたみ」から改めた理由**（2026-08-03）。初版は「`囲み枠` に倣い、カタカナ語を避ける」としていたが、その原則は実際には守られていなかった — コールアウトはメニューでは `囲み枠`、自分の拒否通知では `コールアウト` と、同じ機能が 2 つの名前で呼ばれており、この機能の通知文（`折りたたみは引用やリスト、コールアウト、表の…`）自身がカタカナで書いていた。倣うべき先が一貫していないのに倣っていたことになる。

慣習がその程度である以上、**著者が実際に使っている語**を採る。この文書の題も「アコーディオン（折りたたみ）機能 要件定義」でアコーディオンが先に来ている。`折りたたみ` は検索キーワードとして残すので、どちらの語でもメニューから引ける（受け入れ基準 8）。

**`囲み枠` は変えない**（2026-08-03 決定）。メニューに `囲み枠` と `アコーディオン` が並ぶ不揃いは承知のうえで、和語かカタカナかという軸をそろえるより、それぞれ最も通りのいい名前を選ぶ。コールアウト側の名前を見直すなら、それはこの機能とは別の判断として行うこと。

`aria-label` は公式の `renderToggleButton` オプションで差し替える（既定は `"Collapse details content"` / `"Expand details content"`）。通知は `useEditorNotice` へ、callout の `CALLOUT_NESTING_BLOCKED` と同じ経路で出す。

**プレースホルダの `::before` は `float: left; height: 0` にすること。** 生成内容は既定でインラインに流し込まれるため、素の `::before` で書くとプレースホルダが行の上で実際に幅を持ち、キャレットがその後ろに描かれる（実測 52.5px ＝「タイトル」の幅ぶん右）。文書上の位置は最初から 0 で正しく、ずれているのは描画だけなので、受け入れ基準 18 もピクセルで測っている。高さ 0 の float はどの行ボックスも削らないので、文字は自分の占める位置に描かれたまま行は 0 から始まる — `@tiptap/extension-placeholder` が同じ形を使っているのはこのためである。

### 7.4 挿入直後は開いた状態にする（2026-08-03 決定）

**§7.1 の 2 経路（スラッシュメニューと `:::details `）で挿入したアコーディオンは、開いた状態で出す。** 読み込んだ文書、貼り付け・ドロップで入ってきたものは対象外で、閉じたまま（§5）。前者は「これから本文を書く」操作であり、後者は移動してきた内容だからである。

これが要るのは §7.2 の Enter と噛み合っているため。閉じたタイトル欄で Enter を押すとアコーディオンの下に抜ける（見えない場所に文字を打たせないための公式の判断で、そのまま採っている）。挿入直後が閉じていると、挿入 → タイトルを打つ → Enter という最も自然な流れが、本文ではなくアコーディオンの外に着地する。開けておけば同じ流れが本文の先頭に着く。

**実装は「トグルを 1 回クリックする」以外に無い。** §5 の `persist: false` では公式拡張の `addAttributes()` が `[]` を返し、`open` 属性がスキーマに存在しない。ノードに立てる先が無く、裏を返せば開閉が文書に漏れる経路も無い。開閉状態は NodeView の DOM だけが持ち、外から触れる口はトグルの `<button>` だけである。ノードが作られた直後は NodeView がまだ無いので、1 フレーム遅らせて呼ぶ。遅延中に undo される可能性があるため、位置は取り置かずコールバックの中で選択位置から取り直す（アコーディオンが消えていれば何もしない）。

**併せて Enter を 1 か所だけ狭める。** 公式の Enter は「本文の先頭へ移る」ではなく「本文の先頭に行を作って移る」実装である。ほとんどの形では見えない差だが、挿入直後の本文は空段落 1 つなので、そこに行を作ると元の空段落が 1 つ後ろに残る。Markdown には出ない（空段落は直列化されない。実測）が、エディタにだけ在って公開ページに無い行になり、「書いている時と公開後で見え方が変わらないこと」という §8.2 の前提と食い違う。開いた状態で挿入するようにした結果、この経路が例外ではなく既定になったため、ここで直す。

**本文がちょうど 1 つの空ブロックのときに限る。** その形では「先頭に行を作る」と「既にある行へ入る」はキャレットの着地点が同じで、違いは余りが残るかどうかだけである。つまり公式の挙動からの逸脱ではなく、同じ結果を重複なく出しているにすぎない。本文に中身があれば両者は別の操作になり、そこは公式が正しいので触らない。閉じている場合も同様に触らない — 見えない本文へキャレットを送らないという §7.2 の判断は、この上書きが**奪ってはならない**ものである。

実装は公式のキーマップを置き換えず、条件に当たらなければ公式のハンドラへ委譲する。@tiptap のバンプで公式側が変わっても、狭めているだけなので壊れ方が穏やかになる。境界の 2 つ（本文に中身がある場合・閉じている場合）は §9 の 13 に、狭めた側の挙動そのものは 14 に固定してある。

### 7.5 空タイトルの解除は、タイトルの段落を残さない（2026-08-03 決定）

**Backspace でアコーディオンを解除するとき、タイトルが空なら段落を作らない。** 公式の `unsetDetails` は無条件にタイトルを段落へ変えるので、一度も書かなかったタイトルが何も表さない空段落として残る。スラッシュメニューで挿入 → 気が変わって Backspace、で 1 行だったところが 3 行になる（実測 `doc(paragraph, paragraph, paragraph)`）。

§7.2 の規則は「タイトルの文字が段落として残る」ことであって、文字が無ければ残すものも無い。`details-slice-guard.ts` の `detailsUnwrapped` は最初からその読み方をしていて（`if (child.content.size > 0)` のときだけ段落を作る）、つまりキーボード経路と貼り付け・ドロップの修復経路が食い違っていた。同ファイルの「どちらの経路でも読み手には同じものが見える」というコメントは、タイトルが埋まっている場合にだけ正しかった。新しい規則ではなく、既にある規則をもう一方の経路に適用しただけである。**両者は対で維持すること。**

上書きするのは空タイトルの場合だけで、残すべき文字があるときは公式のコマンドがそのまま走る。

**残る空行 1 つは直さない。** 解除後は `doc(paragraph, paragraph)` になり、末尾の段落は TrailingNode のものである（2026-08-04 以降は自前の `trailing-node-extension.ts`。§7.7。文書の最後がテキストブロック以外だった間に足され、解除しても引っ込まない）。このエディタのブロックノードはすべてこれを残す — callout を同じ手順で測るとまったく同じ形になる（実測）。アコーディオン固有の問題ではないので、ここで特別扱いはしない。

### 7.6 入力ルールを取り消したあとのキャレット（2026-08-03 決定）

**`:::details ` を Backspace で取り消したとき、キャレットは打っていた位置に戻す。** 直さないと次の段落の先頭へ飛ぶ（実測）。

`undoInputRule`（@tiptap/core）は**選択位置を設定しない**。ルールのステップを逆再生し、文字列を戻し、キャレットはマッピング任せにする。包むショートカットではそれで足りる — 段落ノードが生き残るので位置がその中へ戻る（`:::info ` と `> ` はどちらも復元した文字列の末尾に着く、実測）。こちらのルールは包めない（`details` は `detailsSummary detailsContent` なので行を丸ごと置き換える）うえ、§7 に従ってキャレットを新しいノードの中へ移す。逆再生すると、既に存在しないノードの中を指していた位置は潰れ、次の段落の先頭に着地する。

**つまり「キャレットをタイトルに置く」という §7 の要求と、`undoInputRule` のきれいなマッピングは構造的に両立しない。**取り消しの後に置き直すしかない。

置く先は「復元された文字列の末尾から、ルールが本文へ運んだ文字数を引いた位置」。素の `:::details ` なら本文は空なので行末、`:::details本文` ならトリガと本文の境目で、どちらもルールが発火した瞬間にカーソルがあった場所である。

**コアの `undoInputRule` は上書きしない。** あれは Details 拡張のコマンドではなくコアのコマンドで、拡張側で定義すると置き換えになり元の実装を呼べなくなる。見出し・リスト・コードフェンスを含む全入力ルールの取り消しに影響するため、採らなかった。キーマップで先回りする案も採れない — 実測ではコアの Backspace が Details 拡張の Backspace より先に走る。残る手段が自前プラグインの `appendTransaction` で、条件が狭いので他には当たらない（アコーディオンが選択を持っていた／入力ルールの逆操作が在ったのに無くなった／その位置が今はテキストブロック）。最後の 1 つが、同じく逆操作を消費する「新しいアコーディオンのタイトルに文字を打つ」を除外している。

**実装上の罠**: TipTap は入力ルールを持つ**拡張ごとに 1 つ**プラグインを作る（このエディタでは 13 個）。逆操作を持っているのは発火したルールの持ち主だけなので、**最初の 1 つだけを見ると永遠に見つからない**（最初はそう書いて、まったく発火しなかった）。コアの `undoInputRule` が全部を舐めているのはこのためである。

**2026-08-04 以降は文書末尾でも同じ経路になる**（§7.7）。それまでは末尾で TrailingNode の段落が逆操作を先に消していたため、Backspace は取り消しではなく解除になり、この節のプラグインは `hasUndoableInputRule` の条件で落ちて何もしなかった。いまは末尾でも取り消しが起き、キャレットも同じ規則で置き直される（実測 2026-08-04：末尾で `:::details ` → Backspace で `doc(paragraph(":::details "))`、キャレットは絶対位置 12 ＝復元した文字列の末尾）。なお `hasUndoableInputRule` は `components/editor/input-rule-undo.ts` に移し、TrailingNode 側と共有している。

### 7.7 文書末尾で取り消しが効かないのは、アコーディオン側では直さない（2026-08-03 決定 / 2026-08-04 解消）

**Backspace の結果が位置によって変わることは、仕様として受け入れる。** 直せる場所がここではないためである。

実測（2026-08-03）。文書末尾で各ショートカットを打った直後に Backspace を押し、元の文字列に戻るかを見た。

| 打ったもの    | 末尾での Backspace の結果              |
| ------------- | -------------------------------------- |
| `:::details ` | `doc(paragraph, paragraph)` — 戻らない |
| `:::info `    | 同じ — 戻らない                        |
| `> `          | 同じ — 戻らない                        |
| `- `          | 同じ — 戻らない                        |
| `## `         | 同じ — 戻らない                        |

**1 つも戻らない。** 文書末尾では TrailingNode が段落を足す後続トランザクションを走らせ、それが入力ルールの逆操作を消すからで、**このエディタの全ブロック系ショートカットに共通**の挙動である（`editor-codeblock-language.spec.ts:63` にコードブロックの文脈で同じ記録がある）。つまり受け入れ基準 10 の元の文面は、アコーディオンだけが満たしていなかった条件ではなく、書いた時点で誰も満たしていなかった条件である。テストが無かったので気づかれなかった。

直すなら「TrailingNode の追記と入力ルールの逆操作の順序」という全ショートカット共通の場所であり、アコーディオンの作業として抱えるには大きすぎる。§7.5 の「解除後に残る空行」とまったく同じ形の判断であり、そろえる。

**逆に「末尾でも解除に統一する」も採らない。** callout も引用もリストも末尾以外では文字列に戻るので、アコーディオンだけが別の規則になる。位置による差より、兄弟ノードとの一貫性を優先する。

今の挙動自体は壊れていない。 末尾での Backspace は解除になり、§7.5 を入れた後は `doc(paragraph, paragraph)` に落ちる。著者から見れば「作ったものを取り消せた」で筋が通る。壊れていたのは基準の文面だけだった。

やるとしたら全ショートカット共通の課題として切り出すこと。そのときの受け入れ条件は上の表そのもの（5 つのトリガすべてが末尾でも文字列に戻る）である。

**2026-08-04、切り出して解消した。この節の判断（アコーディオン側では直さない）は変わっていない** — 直した場所が、この節の指定どおり全ショートカット共通の TrailingNode だからである。

`components/editor/trailing-node-extension.ts` が StarterKit の TrailingNode を置き換え、末尾段落の追記を**入力ルールの取り消しが生きている間は見送る**。記録は次に文書か選択が動いた時点で消えるので、待つのは 1 トランザクションぶんで、キー入力・クリック・矢印キーのいずれでもその同じトランザクションで段落が現れる。逃げ道の段落が無い状態は著者の操作をまたがない。

再実測（2026-08-04、`e2e/editor-input-rule-undo.spec.ts`）。文書末尾で打った直後の Backspace：

| 打ったもの          | 末尾での Backspace の結果              |
| ------------------- | -------------------------------------- |
| `:::details `       | `doc(paragraph(":::details "))` — 戻る |
| `:::info `          | 同 — 戻る                              |
| `> `                | 同 — 戻る                              |
| `- `                | 同 — 戻る                              |
| `## `               | 同 — 戻る                              |
| ` ``` `（フェンス） | 同 — 戻る                              |

6 つとも戻り、余りの空段落も残らない。 取り消しで最後のノードが段落に戻るため、そもそも追記が起きないからである。

**アコーディオンにだけ固有の事情が 1 つあった。** 挿入直後に開く処理（§7.4）が 1 フレーム後にトグルをクリックし、公式拡張の `persist: false` 経路が `editor.commands.focus(…)` を呼ぶ。文書も選択も変えない空のトランザクションだが、TipTap はそれを dispatch する。「入力ルールが発火したラウンドだけ見送る」という実装だとこれが追記を起こして記録を消すので、アコーディオンだけ直らない。記録が生きている間ずっと見送る形にしてあるのはこのためで、他の 5 つでは差が出ない。

**Ctrl+Z の粒度は修正前と同じに揃えた。** 追記が undo に相乗りすると、次の Ctrl+Z が履歴のステップをその追記の周りに再マップするため、ブロックだけ消えて空行が残る（当初の実装で実測）。undo/redo のトランザクション中は追記しない（`isHistoryTransaction`）ことで、修正前と同じ `doc(paragraph)` に落ちる。redo は追記も含めて完全に戻る。

### 7.8 本文の先頭の Backspace — 型による差は揃えない（2026-08-10 決定）

**本文の先頭で Backspace を押したときに何が起きるかは、本文の先頭ブロックの型で変わる。揃えない。** 初版はこの位置について何も書いておらず、§7.2 の表にも §9 にも行が無かった。以下は後から測った結果と、揃えないという判断である。

実測（2026-08-10。最初は使い捨てのプローブで測り、段落の 3 形は同日 `e2e/editor-details-insert.spec.ts` に基準 16b・16c として残した）。`pageerror` はどのケースでも 0 件で、byte-identical な文書が例外を隠している形ではない。

| 本文の先頭ブロック             | Backspace の結果                                            |
| ------------------------------ | ----------------------------------------------------------- |
| 段落（中身あり）               | 何も起きない（文書もキャレットも動かない）                  |
| 空段落（本文がそれ 1 つだけ）  | 何も起きない                                                |
| 空段落（後ろにブロックがある） | その空行が消え、キャレットが**タイトルの末尾**へ移る        |
| 箇条書き                       | 先頭の項目が持ち上がり、段落 1 つと残りのリストに割れる     |
| 引用                           | 引用が本文の直下へ持ち上がる                                |
| コードブロック                 | ブロック全体が NodeSelection される（もう一度押すと消える） |
| callout / 表                   | 何も起きない                                                |

**「何も起きない」の出どころはスキーマである。** `detailsSummary` が `isolating` なので prosemirror-commands の `deleteBarrier` では join も wrap も `isolated` で落ち、`details` が `isolating` なので `liftTarget` はそこで break し、`detailsSummary` が `selectable: false` なので `selectNodeBackward` も降りる。3 行目だけは `joinBackward` の `$cursor.parent.content.size == 0` の分岐が通るが、この分岐は正当な削除ステップを作れることが条件なので、`block+` の唯一の子は消せず、本文が 1 行のときは発火しない。

**揃えない理由は 3 つ。**

- **ばらつきの大半はアコーディオンの挙動ではない。** リストの持ち上げ、引用の持ち上げ、コードブロックの自己選択は、どれも任意のコンテナの先頭でそのノードがやることで、callout の中でも引用の中でもトップレベルでも同じになる（アコーディオン内は実測、他は導出）。ここで揃えると、アコーディオンだけが「箇条書きの先頭で Backspace を押しても項目が外れない唯一の箱」になる。§7.7 が「位置による差より、兄弟ノードとの一貫性を優先する」と決めた取引を、逆向きに踏むことになる
- **「何も起きない」は境界の正しい答えである。** 本文の 1 行目のマージ先になり得るのはタイトルだが、`detailsSummary` は `text*` であり、しかも `<summary>…</summary>` という生 HTML 1 行として往復する（§6.5・§4.1）。そこへ本文を吸わせるのは構造としても保存形式としても壊れる方向で、`isolating` が拒否しているのは正しい。callout も同じ位置で同じデッドキーになる（導出）
- **`code-block-extension.ts:263-275` の「不便より悪い」は、この形には移せない。** あちらで問題だったのはブロックから出る Backspace 経路が 1 つも無かったことである。こちらはタイトル先頭の Backspace が解除経路として在り（§7.2）、本文の 1 行目も選択して消せる。閉じ込められてはいない

**この表のうちアコーディオン固有なのは 3 行目だけで、それは `detailsSummary` が前の兄弟として在るために生まれる。** callout には前の兄弟が無いので同じ位置で何も起きない（導出）。3 行目は残す — 自分が立っている空行が消えるのは Backspace の素直な意味であり、§7.2 が束縛しないと決めた本文 → タイトルの移動が、鍵を奪わない形でここに 1 つだけ在ることになる。

**閉じている間は本文にキャレットが入らない**（実測）。隠れた `detailsContent` の中を `setTextSelection` で直接指してもタイトルの末尾へ正規化されるので、受け入れ基準 26 が心配している「見えない場所が動く」種類の危険はこの位置には無い。同じ正規化は測定側の罠でもあり、テキストブロックでない生の位置（`detailsContent` の直後など、最初のブロックの前）を指すと黙って別の場所に着く。最初の測定はそれで「タイトル末尾の Backspace」を測っていた。**最初のテキストブロックを解決して `pos + 1` を使い、キーを送る前に state 側のキャレットを `expect.poll` で待つこと。**

**再検討するとしたら、アコーディオン単独ではやらない。** 「空行の先頭での Backspace が箱によって効いたり効かなかったりする」という callout と共通の課題として切り出すこと。§7.7 が TrailingNode で採ったのと同じ形である。

### 7.9 モバイルの＋ドロワーには行を足す（2026-09-20）

§7 のツールバー不採用は、囲み枠と違って型を選ばせる必要がないという理由に立っており、モバイルの＋ドロワー（囲み枠・表・リンク・画像の行がある `InsertMenu.tsx`、docs/editor-requirements.md §12.5）はその対象ではない。ドロワーはスクロールする列であって、ポインタ用ツールバーのように行を増やすと折り返しが増える幅制約の中にはいない。**囲み枠・表も型選択とは無関係にスラッシュメニュー・入力ルールを両方持ちながらドロワーの行を持っており、アコーディオンだけ外す理由は無い。**

配置はリンクと画像の間。アイコンは `AccordionIcon.tsx` — タイトル行と本文の境界線、タイトルの前に公開側のマーカーと同じ形の三角を置いた、`<details>`/`<summary>` の形そのもの。

`setDetails` はキャレットをタイトルへ置く挙動を含めてそのまま呼ぶ（§7 冒頭）。ポインタ用ツールバーには出さない — `InsertControls`（`Toolbar.tsx`）の `labelled` 分岐で、ドロワー（`InsertMenu.tsx`）だけがこの行を描く。

## 8. 公開側

- 変換処理の追加は不要。生 HTML がそのまま出る（§2.2）
- **CSS は要素セレクタで書く。** sanitize が `details` / `summary` の `class` を通さないため、`globals.css` に `.prose details` / `.prose summary` として書く。既定の三角マーカーを Zenn 風の見た目に置き換えるのもここ
- **アコーディオン内の見出しは目次に載せない**（2026-08-03 決定。§8.1）
- 閉じた内容はブラウザの Ctrl+F と印刷に出ない。仕様として許容する

### 8.1 目次から外す理由と、その帰結

見出しをスキーマで禁じることはできない（§6.3 と同じ理由 — 禁じれば `<details>` の中に `##` を含む Markdown を開いた瞬間に見出しが落ちる）。エディタでも中で H2/H3 がそのまま打てる。決めるのは目次に載せるかどうかだけであり、載せない。

- 目次は「見えている構造」の一覧である。著者が畳んだのは「本筋ではない」という判断なのに、目次はそれを本筋の見出しと同じ列に並べてしまう
- 閉じた `<details>` の中の id へフラグメント遷移したとき折りたたみが開くかはブラウザ依存である。Chrome 151 は自動的に展開してスクロールする（実測）が、Firefox / Safari は未検証で、非対応なら「リンクを踏んでも何も起きない」という最悪の壊れ方をする。目次に載せないかぎり、既定の導線からこの経路には入らない

**id は今までどおり付く。** `rehypeSlug` は場所を問わず h2/h3 に id を振り、sanitize が `user-content-` を付ける。目次は id を読み取って一覧を作っているだけなので、外しても id は消えず、本文中の `[…](#見出し)` も外部からの `#user-content-…` も従来どおりその見出しを指す（実測）。

**`hashchange` で祖先の `<details>` を開くスクリプトは入れない**（2026-08-03 決定）。目次から外した時点で、ブラウザ依存が残るのは著者が自分で本文に書いたリンクだけになる。折りたたみの中を指すリンクを書くこと自体が稀で、書いた本人が動作を確かめられる。**この判断は見落としではないので、Firefox で開かないことを理由に再検討しないこと。**

**実装**: `lib/rehype-collect-toc.ts`（29 行）に、`details` を先に走査して配下の h2/h3 を Set に集め、収集時にスキップする処理を足す。祖先を辿らずに済むので `unist-util-visit-parents` のような依存追加は不要。

### 8.2 見た目

`class` 属性が sanitize を通らない（§8）ため、すべて要素セレクタで書く。既存の callout / コードブロックのカードと同じ角丸・境界・余白の系列に載せること。折りたたみだけ違う語彙で描くと、記事の中で浮く。

| 対象           | 仕様                                                                                                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 既定の状態     | 閉じている（§5）                                                                                                                                                                                             |
| マーカー       | ブラウザ既定の三角は消す（`summary { list-style: none }` と `::-webkit-details-marker { display: none }`）。開閉方向を示す記号は自前で描く（§8.3）                                                           |
| タイトル行     | `cursor: pointer`、クリック領域は行全体、hover で塗りが一段変わる。フォーカスリングは残す（キーボード操作で位置が分かること）。**ただし公開側だけ** — エディタ側は §8.3                                      |
| 本文           | 開いている間だけタイトルとの境界を 1 本引く。閉じている時に引くと、下に何も無いところに線が残る。余白はカードの内側余白に合わせる                                                                            |
| 塗り           | タイトル行だけ塗り、本文はページの地のまま（2026-08-03 決定）。カード全面を塗るとコードブロックと同じ重さで記事に立ってしまう。折りたたみは「本文の一部」なので、そこまで独立した塊に見せない                |
| 左のインセット | **callout の 2 カラムをそのまま写す**（2026-08-03 決定）— カードの `1em`、アイコン列 `1.1em`、`gap: 0.6em`。記事の中で callout と折りたたみが並んだとき、本文の左端がそろう                                  |
| ダークモード   | 既存のカードが使っている値をそのまま参照する。折りたたみ用に新しい色を足さない — 塗りと境界はコードブロックのカード、hover とフォーカスリングはエディタの既存クロム（ドラッグハンドル、diff トグル）から取る |

エディタ側の NodeView も同じ見た目に揃える（callout が「公開ページと同じ 2 カラム DOM を NodeView でも作る」方針を採っているのと同じ理由 — 書いている時と公開後で見え方が変わらないこと）。ただしエディタ側だけはタイトル欄のプレースホルダ（§7.3）を持つ。

### 8.3 2 つの DOM で違ってよい所と、違ってはいけない所（2026-08-03 実測）

**違ってよい**のは、片方だけが操作子だからである。公開側のタイトル行はクリックで畳まれるので `cursor: pointer` と hover の塗りを持つ。エディタ側は同じクリックがキャレットを置くだけなので、`cursor: text` にして hover の塗りも与えない — 起きない折りたたみを予告してしまう。開閉を担うのは `<button>` の方で、hover とフォーカスリングはそちらに付く。

**違ってはいけない**のはマーカーの位置と本文のインセットで、どちらも実測で一致させてある（カード左端からの距離 px）。

| 測った値                     | エディタ | 公開 |
| ---------------------------- | -------- | ---- |
| マーカーの中心               | 25.8     | 25.8 |
| タイトルの文字左端           | 44.2     | 44.2 |
| タイトル行の高さ             | 41       | 41   |
| 本文（段落）の左右インセット | 17       | 17   |
| 箇条書きの行頭               | 43       | 43   |

一致させるために必要だった点が 4 つある。

- **`summary { min-height: 計算値 }` で 1 行分の高さを保証する。** §5.1 が無題のまま公開することを許しているので、公開側には `<summary></summary>` が出る。インライン内容が無い＝行ボックスが作られないので、タイトル行が padding だけの高さに潰れる（実測 16px。エディタ側は ProseMirror が空のタイトルに末尾 `<br>` を入れるので 40px のまま）。マーカーは下の計算で置いていて流れに従わないため、一緒には縮まず、12px の三角形が本文の上に 11px はみ出した。`min-height` はその計算と同じ 2 項（行送り＋行の padding）で書いてあるので、余白を変えても連動する
- **`summary { line-height: 1.5 }` を固定する。** マーカーの縦位置は「タイトル行の padding-top ＋ 行送りの余りの半分」で両方に書いてあるので、行送りが両者で同じ数字である必要がある。この計算にしてあるのは、タイトルが折り返しても 1 行目の中心に留まるため（以前は公開側が静的位置、エディタ側が `top: 0.5em` 固定で、折り返すとずれた）
- **横のインセットは公開側が margin、エディタ側が padding。** 公開側は本文ブロック自身に効くので、padding にすると `.prose details > :not(summary)` が Tailwind Typography の `:where()` 付きリスト規則に競り勝ち、`ul` の 1.625em のインデントを 1em で上書きしてしまう（箇条書きの行頭がカードの境界に乗る）。margin なら prose の padding の外側に付くので触らない。エディタ側は padding がラッパー（`[data-type="detailsContent"]`）に付くので元から起きない
- **`<button>` に `font: inherit` を付ける。** ボタンはページのフォントを継承しないので、上の位置指定（すべて em）が UA の小さいボタン用 font-size で解決され、公開側とずれる

**既知の差**: 本文が箇条書きで始まる場合だけ、タイトルとの間が 4px 違う（公開 16px / エディタ 20px）。原因は TipTap の `listItem` が中身を `<p>` で包み、公開側の Markdown は包まないというサイト全体の差だが、差として見えるのはアコーディオンの中だけである — 上の `padding-top: 0.5em` が公開側ではブロック自身に付くので、普段は外に抜けて消える `li` の margin がここでは中に閉じ込められる（トップレベルの箇条書きでは両者とも 0 で一致する、と実測）。4px のために公開側だけ余白の付け方を変えるほうが壊れやすいので、特別扱いはしない。本文が段落で始まる通常の場合は完全に一致する。

**callout との既知の差**（§8.2 の「左のインセット」）: 本文の左端は一致する（43.2 対 44.2 で、差の 1px はアコーディオンのカードが持つボーダー。callout にはボーダーが無い）が、グリフの右端から文字までは 12.4px と 9.6px で 2.8px 違う。callout のアイコンは 1.1em で列を埋め切るのに対し、こちらの三角形は 0.75em で同じ列の中央に置くため、左右に余りが出るからである。三角形を 1.1em に拡げると、単純な図形なので重く見える（0.75em はそのために選んだ値）。**列の中央に置くことを優先し、文字までの間隔を callout に合わせるための微調整はしない**（2026-08-03 決定）。

## 9. 受け入れ基準

E2E（`e2e/`）で確認する。エディタはブラウザ専用なので、tsc も vitest も実行時の振る舞いを見られない。

**往復（最重要 — §4.3）**

1. 挿入 → 保存 → 再読み込み → 保存で Markdown が不動点になる
2. 本文に callout を含むアコーディオンが往復する
3. 本文にフェンスコードブロック / テーブルを含むアコーディオンが往復する
4. タイトルが空、本文が空のアコーディオンが往復する
5. タイトルに `<` と `&` を含むアコーディオンが往復し、文字が消えない（§4.1）
6. 文書末のアコーディオンが往復する
7. 保存された Markdown が、公開ページで `<details>` として描画される

**導線**

8. `/` メニューから挿入でき、キャレットがタイトル欄に入る。旧称 `折りたたみ` で検索しても同じ行が引ける（§7.3 でキーワードとして残した）
9. どちらの経路で挿入しても開いた状態になり、そのぶん文書も Markdown も変わらない（§7.4。`can()` の空打ちで開かないことも含む）。読み込んだアコーディオンは閉じたままであること — 開くのは挿入という操作に属し、ノードに属さない
10. `:::details ` の入力ルールが発火し、直後の Backspace は文書のどこでも入力ルールの取り消しになる（元の文字列に戻り、キャレットは打っていた位置へ。§7.6）。末尾だけ解除になっていた差は 2026-08-04 に解消した（§7.7。エディタ全体の修正で、`:::info ` / `> ` / `- ` / `## ` / フェンスも同じ）。§7.5 の解除は、取り消しの窓が閉じたあと（他所を触ったあとや、書き進めたあと）にタイトル先頭で押す Backspace の話であり、この項目とは別の分岐である。取り消し後のキャレットは 11 が、解除の形は 16 が押さえているので、この項目に固有のテストは持たない
11. 取り消したあとのキャレットが、打っていた位置に戻る（§7.6。次の段落の先頭に飛ばないこと。空行どうしは論理位置で見分けられないので絶対位置で比べること）
12. テーブルセル内・引用内・callout 内・リスト項目内では、入力ルールもメニュー行も出ない。テーブルセルとリスト項目は、上書き前の `setDetails` が `true` を返す経路なので必ず確認する（§7.1）。入力ルールとメニューの両方を見ること（拒否経路が 2 つある）

**キー操作（§7.2）**

13. タイトル欄で Enter を押すと、開いていれば本文の先頭へ移り、閉じていればアコーディオンの下に新しいブロックができる（閉じたまま本文へキャレットが入らないこと）。本文に中身があるときは先頭に行が作られること — §7.4 の上書きが広がっていないことの確認
14. 挿入直後のアコーディオンで「タイトル → Enter → 本文」と打つと、本文が段落 1 つだけになる（§7.4。空段落が後ろに残らないこと。`toContain` ではなく本文全体で比べないと、残った空段落を見逃す）
15. タイトル欄の先頭で Backspace を押すとアコーディオンが解除され、タイトルの文字が段落として残る
16. タイトルが空のまま解除すると、タイトルのぶんの段落は残らない（§7.5。文書全体で比べること — 余分な空ノードは部分一致では見えない。末尾の段落は TrailingNode のもので、callout も同じ形になるので許容）
    以下の 2 つは 15・16 の下位項目ではなく、同じ Backspace の別の分岐（タイトルではなく本文の先頭で押した場合）。番号を振り直さないために字下げしてある。
