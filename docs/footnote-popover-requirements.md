# 脚注ポップオーバー（公開ページ）要件定義

- 状態: **実装済み**（2026-08-09。設計もこの日）
- 実装: `components/FootnotePopover.tsx`、`app/posts/[slug]/page.tsx`、`app/globals.css`、`e2e/public-footnote-popover.spec.ts`
- 関連: `docs/footnote-requirements.md`（§4.2 が公開側の脚注の見た目を決めている）、`components/CodeCopyButtons.tsx`（最も近い前例 — 同じ形で書いた）

公開ページで脚注の参照から本文の位置を失わずに注釈を読めるようにするための要件。**この文書は設計の記録であり、実装後もそのまま維持する** — 判断とその理由が書いてあり、コードだけでは復元できないのはそちらだからである。

実測していないことは実測していないと書いてある。設計時点で測定値があったのは既存のもの（公開ページの寸法・`-webkit-line-clamp` の挙動、いずれも §4.3 系）だけだった。**実装で分かったことは、日付を添えてその節に書き足してある** — §3.5.1（支援技術から隠さない。`inert` を一度足して同じ日に外している。**現行は「どちらにも付けない」**）、§4.1.1（ポインタを箱に置いたままのスクロールでは閉じない。推論で逆を書いていたので実測して直した）、§6.1（開く遅延を 120ms から 200ms へ）、§8（タッチの検証手段）がそれである。

## 0. 前提 — この機能を作るべきかどうか

**投稿 3 件、脚注を含む投稿 1 件、定義 3 件**（2026-08-09 に `data/blog.db` を集計）。しかもその 1 件はタイトルが「テスト」である。脚注機能自体が 2026-08-04 に入ったばかりで、**実投稿での使用は実質ゼロ**である。

この事実は記録しておく価値がある。記事検索を「~2 投稿では早すぎる」として見送った 2026-06-29 と同じ形の状況であり、**普通ならこれは「まだ作らない」と判断される**。

それでも作ると決めたのは、これが優先順位の話であって設計の話ではないためである。読める形が先にあれば脚注を使う気になる、という順序はあり得る。ただし帰結として、**設計判断の一部は想像上の注釈に向けて行われている** — 特に §4.3（長さの上限）と §4.1（注釈にリンクが入るか）は、実際の注釈を数本書いたあとで見直す前提で読むこと。

## 1. 目的と非目標

**目的**: 脚注の参照から、本文の位置を失わずに注釈を読めるようにする。

`↩`（backref）が存在すること自体が、ジャンプに往復コストがある証拠である。プレビューはその往復の大半を消す。

**非目標**（初版では明示的に対象外）:

- エディタ側のプレビュー。これは**公開ページだけの機能**である。エディタでは定義が常に画面内の同じ文書にあり、`data-paired` のハイライトが既に対応関係を示している
- 参照から参照への移動（「次の脚注へ」のようなナビゲーション）
- 注釈の中の脚注（そもそもスキーマ上作れない。`docs/footnote-requirements.md` §1）
- ポップオーバー内での編集
- URL への反映（`#user-content-fn-1` へのハッシュ変更）。プレビューは移動ではないので履歴を汚さない

## 2. 前提 — 公開ページのマークアップは既に揃っている

remark-gfm が出す形（`lib/render.test.ts` が固定しており、2026-08-09 に実物を確認した）:

```html
<p>
  本文<sup
    ><a
      href="#user-content-fn-1"
      id="user-content-fnref-1"
      data-footnote-ref=""
      aria-describedby="user-content-footnote-label"
      >1</a
    ></sup
  >。
</p>

<section data-footnotes="" class="footnotes">
  <h2 class="sr-only" id="user-content-footnote-label">Footnotes</h2>
  <ol>
    <li id="user-content-fn-1">
      <p>
        注釈。<a
          href="#user-content-fnref-1"
          data-footnote-backref=""
          aria-label="Back to reference 1"
          class="data-footnote-backref"
          >↩</a
        >
      </p>
    </li>
  </ol>
</section>
```

**新しいデータの流れは要らない。** 注釈は既にページ内にあり、参照の `href` がその `id` を指している。ポップオーバーの中身は `document.getElementById(href.slice(1))` の複製で足りる。サーバー側の変更もパイプラインの変更も不要である。

`data-footnote-ref` が sanitize を通ることは確認済み（`hast-util-sanitize` の defaultSchema が `a` に対して `dataFootnoteRef` を許可しており、`lib/render.ts` のスキーマは div/p/span しか広げていない）。

## 3. 操作モデル（確定）

**この節が本機能の中心である。** 位置決めや見た目より先に、ここが決まっていないと全体が中途半端になる。

| 入力       | 参照への操作 | 結果                                                                                                        |
| ---------- | ------------ | ----------------------------------------------------------------------------------------------------------- |
| マウス     | ホバー       | **一時的なプレビュー**。離れたら閉じる。中身には触れない                                                    |
| マウス     | クリック     | **今までどおり定義へジャンプ**。介入しない                                                                  |
| タッチ     | タップ       | **ピン留めしたポップオーバー**。明示的に閉じるまで残る。中身のリンクは押せる（スクロールはしない — §4.3.1） |
| キーボード | フォーカス   | 一時的なプレビュー（マウスのホバーと同じ）                                                                  |
| キーボード | Enter        | 定義へジャンプ（マウスのクリックと同じ）                                                                    |

### 3.1 デスクトップのクリックは奪わない

**これが最も重要な決定である。** 検討の途中で「クリックでピン留め、ジャンプはポップオーバー内の『定義へ』」という案を採りかけたが、退けた。

理由は、**その案がデスクトップで既存の挙動を奪うから**である。現状の参照は普通のアンカーで、クリックすればジャンプする。プレビューを足すのは純粋な足し算にできるのに、ピン留め案はそこに引き算を混ぜていた。

そして素のクリックに触らないことで、**修飾キー付きクリック・中クリック・「新しいタブで開く」が構造的に守られる**。`preventDefault` しなければ壊しようがない。この種の実装が最も雑に壊すのがここである。

**この決定は今も生きている。** 素のクリックは奪わない。

当初はここに「代償は 1 つだけある: デスクトップではプレビュー内のリンクに触れない（§4.1）」と書いていた。**その代償は 2026-08-09 に取り消した** — プレビューを操作可能にしたので、リンクは押せる（§4.1、§6）。ピン留め案を退けた理由は「クリックを奪うこと」であって「中に入れること」ではなかったので、**この節の判断は何も変わらない**。変わったのは、その判断が支払っていた代償のほうである。

### 3.2 判別は `pointerType`、端末ではない

タッチかマウスかは `pointerdown` イベントの `pointerType`（`'touch'` / `'mouse'` / `'pen'`）で判別する。**`@media (hover: hover)` や `(pointer: coarse)` による端末判定は採らない。**

メディアクエリは**主たる入力**しか表さない。タッチ対応ノート PC やトラックパッド付きタブレットはどちらのバケツにも落ち得るし、入力は途中で変わる（マウスを挿す）。`matchMedia` の change を追えば追随はできるが、そもそも「この端末はどちらか」を当てにいく設計になる。

イベントで分けると**ハイブリッド端末で毎回正しくなる**。同じ端末で、指で触ればポップオーバー、トラックパッドでクリックすればジャンプ。筋も通っている — **ホバーできない入力にだけ、プレビューへの入口を用意する**。

`'pen'` は `'mouse'` と同じ扱いにする（ホバーを持つため）。

### 3.2.1 フォーカスで開いたものは「ホバー側」に分類する

**Tab キーは pointer イベントを発火しない。** したがってキーボードのフォーカスで開いたプレビューは `pointerType` で分類できず、そのままでは「デスクトップ側」の扱い（一時的に開き、§4.2 の「定義へ」を持たない）とピン留めのどちらに転ぶかが決まらない。タブレットに Bluetooth キーボードを挿した読者が具体例である。

**モードは「直前に観測した `pointerType`」ではなく、開いた入口そのもので決める。** `pointerdown` が `'touch'` だったときだけタッチ扱いにし、`focus` で開いたものは常にホバー側とする — すなわち一時的に開き（フォーカスが外れるか Escape で閉じる。§6）、中は操作でき、支援技術からも隠さない（§3.5.1）。**この括弧の中身は 2026-08-09 に 2 つ入れ替わっている**（当初は `pointer-events: none` と `aria-hidden` を挙げていた。どちらも §4.1.1 と §3.5.1 で外れた）。**分類の判断そのものは変わっていない。**

これで §3.2 の筋がそのまま通る — **端末を当てにいかず、入口ごとに決める**。同じタブレットでも、Tab で来ればプレビュー、指で触ればポップオーバーになる。フォーカスで開いた側に残る差は「定義へ」を持たないことだけで、Enter を押せば定義へ飛べる（§3.5）。**当初ここには「中身に触れないことは後退ではない」と書いていたが、その代償は §4.1.1 で消えた** — フォーカスで開いたプレビューにも入れる。

以降この文書で「デスクトップ」と書いてある箇所は、正確には**ホバーまたはフォーカスで開いたポップオーバー**を指す。

### 3.3 `preventDefault` はタッチのときだけ

タップでポップオーバーを開くには既定の遷移を止める必要がある。**それを行うのは `pointerType === 'touch'` のときに限る。**

この制限には意味がある。修飾キー付きクリックが存在しない文脈だけで介入することになるので、§3.1 で守った性質と**衝突する組み合わせが構造的に発生しない**。

### 3.4 JS が無ければ従来どおり

マークアップは機能するアンカーのままなので、スクリプトが読まれなければ（読み込み前・失敗・無効）タップもクリックも定義へジャンプする。**プログレッシブエンハンスメントが無料で付いてくる形なので、これは維持する。**

具体的には、参照の `href` も `id` も書き換えない。振る舞いはイベントリスナだけで足す。

### 3.5 キーボードは「デスクトップ側」に揃える

フォーカスでプレビュー、Enter でジャンプ。アンカーとしての意味を変えない。

**ポップオーバーはスクリーンリーダーにとっての唯一の経路にしてはならない。** 注釈はページ下部に既に存在し、既存のアンカーで到達できる。ポップオーバーは上乗せであり代替ではない、という位置づけにすることで、a11y の負担が現実的な範囲に収まる。既存の `aria-describedby` は触らない。

### 3.5.1 どちらのポップオーバーも支援技術から隠さない（2026-08-09 改訂）

**`aria-hidden` も `inert` も付けない。両方に付けない。**

`aria-hidden` の中にフォーカス可能な要素を置くと、支援技術からは存在しないのに Tab では止まる要素ができる。これは好みではなく ARIA の一般則の違反である。そして**両方のポップオーバーがフォーカス可能な要素を持つ** — ピン留めは §4.2 の「定義へ」を、プレビューは**注釈自身のリンク**を持つ。

この節は 2 度書き換わっており、経緯自体が記録に値する。

1. 当初は「プレビューは `aria-hidden` でよい（中に操作できる要素が無いので）」と書いていた。**これは §4.1 と矛盾していた** — 注釈はリンクを含み得るし、含み得ることこそが §4.1 が複製を選んだ理由である
2. 実装時（2026-08-09）に気づき、`inert` を併せて付けることで解いた。`pointer-events: none` は Tab に対して無力なので、到達できないことを保証できるのは `inert` だけだった
3. 同日、**プレビューを操作可能にする**と決めたことで（§4.1.1、§6）、`inert` は前提ごと消えた。中に入って読み、リンクを押せる箱を「到達できない」と宣言することはできない

| 開き方              | `aria-hidden` | `inert`  | 中の操作可能な要素               |
| ------------------- | ------------- | -------- | -------------------------------- |
| ホバー / フォーカス | 付けない      | 付けない | 注釈のリンク（押せる）           |
| タップ              | 付けない      | 付けない | 注釈のリンクと「定義へ」（§4.2） |

**代償**: 支援技術の読者が、ページ下部の定義と同じ内容をポップオーバーでも読む可能性がある。これは受け入れる — 内容は同じページにある注釈の複製であって新しい情報ではなく、フォーカスが参照から外れた時点で閉じる（§6）ので、Tab で中に迷い込むことはない。**§3.5 の原則（ポップオーバーは上乗せであって唯一の経路ではない）は変わらない。**

### 3.6 参照先の定義が無ければ何も足さない

`href` の指す `id` がページに無い場合、**リスナを付けず素のアンカーのまま残す**。

参照だけが残った Markdown は実在し得る。`docs/footnote-requirements.md` §5.4（外部由来の異常入力）と §5.5（孤児定義の救済は第 3 段階に置けない）が、**この形が既に一度起きたこと**を記録している。§2 の「注釈は既にページ内にある」は通常の経路についての前提であり、不変条件ではない。

答えは §3.4 が既に決めている — マークアップは機能するアンカーのままなので、**何もしなければ従来どおりジャンプする**。空のポップオーバーを出すより正しい。複製から `↩` を除いた結果が空になる場合（注釈が `↩` だけの定義）も同じ扱いにする。

## 4. 中身

### 4.1 定義の HTML を複製する（テキストではなく）

注釈はリンク・インラインコード・強調を含み得る。`textContent` で抜くとそれらが落ちる。`cloneNode(true)` して **`.data-footnote-backref`（`↩`）だけ取り除く** — ポップオーバーの中では帰る先が「今いる場所」なので意味を持たない。

複製した中身は既に sanitize 済みである（`lib/render.ts` を通っている）。新しいサニタイズは不要で、**足してもいけない** — 二重にかけると通っていたはずのものが落ちる。

### 4.1.1 プレビューには入れる（2026-08-09 改訂）

**ポップオーバーは操作可能にする。`pointer-events: none` は掛けない。** ポインタをプレビューの中へ移動でき、注釈のリンクを押せる。

当初はこの節に「デスクトップでは `pointer-events: none` を掛ける」と書いていた。**その 1 つの指定が 4 つのことを同時に満たしていた**（当初は 3 つと書いていたが、4 つ目を数え落としていた）。外した以上、それぞれに別の答えが要る。

| 失われたもの                         | 代わりの答え                                                           |
| ------------------------------------ | ---------------------------------------------------------------------- |
| 中に入る導線が無いこと               | **閉じ遅延**でポインタを橋渡しする（§6.1）                             |
| クリックを食べないこと（§5.3）       | **幾何で守る** — 箱は参照に重ならない位置にしか置かない（§5.2 / §5.3） |
| 支援技術から隠してよいこと（§3.5.1） | **隠さない** — 中に押せるリンクがある以上、隠すことが違反になる        |
| **箱の下の本文が生きていたこと**     | **答えが無い。代償として受け入れる**（下記）                           |

**4 つ目に答えが無い。** `pointer-events: none` は「箱の下は常に生きている」ことも保証していた。外した以上、**プレビューが開いているあいだ、それが覆っている本文はポインタを受け取らない** — 1 行上にある別の参照や本文中のリンクはホバーもクリックもできず、その範囲を横切るテキスト選択のドラッグも途切れる。

これは幾何では消せない。**箱はどこかを覆うために存在する**からである。受け入れる理由は、覆っている時間が読者の操作に従属していること — 箱はポインタが参照か箱の上にあるあいだしか存在せず、離れれば 200ms で消える。読者が「下にあるものを触りたい」と思って動いた時点で、箱はもう無い。

**この正当化はポインタのある側にしか効かない。** タッチのピン留めには「ポインタが離れる」が無いので、箱は読者が明示的に消すまで残り、しかもモバイルでは画面のほぼ全幅を占める。**§6.0 のスクロールで閉じる規則は、この代償にタッチ側の歯止めを与えるためのものである** — 見落としており、指摘を受けて足した。

**参照そのものだけは例外で、幾何が守る**（§5.3、基準 16）。ここだけは「覆ってもよい」と言えない — ホバーの直後にクリックが来ると分かっている場所だからである。

代償を測る基準を 31 として置く。**望ましい挙動だからではなく、意図した状態だからである** — `pointer-events: none` を戻せばこの基準が赤くなり、戻した人はこの節を読むことになる。

**スクロールしても、ポインタが箱の中にあるうちは閉じない（2026-08-09 実測）。ここはプレビューの話であり、ピン留めは §6.0 でスクロールで閉じるようになった。**

当初この段落には「スクロールすると箱がポインタの下から抜けて閉じる — 読んでいたのに消えた」と書いていた。**推論で書いて実測していなかったので、実際より強い主張になっていた。** 測ったところ、箱の中央にポインタを置いたままホイールで 303px スクロールしても開いたままで、閉じたのは**ポインタを箱の外へ動かした時点**だった。

理由は §5.2.3 の追随そのものである。箱は参照に付いて動くので、**ポインタが箱の中にいる限り `pointerleave` が発火しない**。閉じるのは §6.1 の規則どおり「参照からも箱からも離れたとき」だけであり、スクロールはその条件を自動的には満たさない。

**ただし、その追随の途中で箱は参照の上から下へ反転し得る**（参照が画面上端に近づくため。§5.2）。実測でも反転しており、**反転してもポインタが箱の中にあれば閉じない**。読者から見れば、読んでいる箱がカーソルの下で一度跳ぶ。**現状維持とする** — 追随（基準 20）と反転（基準 17）はどちらも独立に望ましく、両立させると「読んでいる間は動かさない」という 3 つ目の規則が要る。§4.3.1 と同じ判断で、規則は少ないほうを採る。

箱がポインタから離れる経路自体は残っている（反転先がポインタを含まない、参照ごと画面外へ出る、など）。その場合は 200ms 後に閉じる — これは仕様どおりであって、スクロールに固有の挙動ではない。

**得たものは 2 つある。** デスクトップの読者が注釈内のリンクを押せるようになった（§3.1 が支払っていた唯一の代償がこれで消えた）。そして **WCAG SC 1.4.13 の Hoverable を満たすようになった** — 同 SC はホバーで出た内容の上にポインタを移動できることを求めており、以前の設計はここを満たさないと明記していた。

**失ったものも 1 つある。** §9 が「この手の実装が壊れるのはたいていこの遅延まわり」として避けていた機構が、まさにその形で入った。**閉じ遅延は仕様の一部であって最適化ではない**ので、消したり短くしたりすると参照とポップオーバーの隙間でプレビューが落ちる。§6 に数値と理由を置き、受け入れ基準（§8 の 29・30）で押さえる。

なお **§10 のボトムシートは逃げ道として残る**。これはタッチ側の話であり、ここで解いたのはポインタ側の問題である。

### 4.2 タッチのポップオーバーには「定義へ」を置く

ピン留めされたポップオーバーだけが操作可能な要素を持つ（§3.5.1）。置くのは**「定義へ」1 つだけ**である — 参照の `href` をそのまま持つリンクで、§3.1 で移動したジャンプの導線であり、§4.3.1 により**タッチで続きを読む唯一の経路**でもある。注釈の下、読み終えた先に置く。

クランプ（§4.3.2）の外側に置く — 注釈が 8 行に切られても導線は消えない。文言は日本語（この repo の既存の UI 文言に揃える）。ホバー・フォーカスで開いた側には出さない。

**閉じるボタンは置かない**（§9）。閉じ方は light-dismiss に任せる。

### 4.3 長い注釈は 8 行で切り、末尾に `…` を出す

**上限は 8 行。超えた分は `…` で省略し、続きを読みたい読者は定義へジャンプする。**

寸法の根拠（2026-08-09、公開ページで実測）:

| 実測値                |                            |
| --------------------- | -------------------------- |
| 本文カラム            | 750px                      |
| 注釈の文字 / 行の高さ | 14.4px / 23.04px           |
| 全角 1 行あたり       | 約 52 字（750px 幅のとき） |

ポップオーバーの幅を `min(30rem, calc(100vw - 2rem))`（上限 480px）、内側のパディングを `1rem` とすると、使用幅は約 448px、全角で約 31 字/行。**8 行で約 248 字**になる。パディングは幅によらず `1rem` で固定する — §4.3.1 のモバイル側の見積もりも同じ値で出しているので、2 箇所の数字が同じ前提から出ることになる。

**行数で切るのは、字数や高さより「注釈とはどれくらいのものか」に近いためである。** 480px の箱で 8 行に収まらない注釈は、もう注釈ではなく脱線である。このサイトには `:::details`（アコーディオン、`docs/accordion-requirements.md`）があるので、上限は切り捨ての規則であると同時に**書き方の指標**として働く。

### 4.3.1 開き方によらず切る。ポップオーバーはスクロールしない

**ホバーでもタップでも 8 行で切る。** ポップオーバーの中に内部スクロールは持たせない。規則は 1 つ — **ポップオーバーは常に最大 8 行、`…` が出たら続きは定義にある**。

**当初ここには「ホバー側にはそもそも選択肢が無い — `pointer-events: none` なので、スクロール可能にしても触れない箱にスクロールバーが出るだけである」と書いていた。その指定は §4.1.1 で外したので、この理由は消えた。** いまはホバーの箱にも内部スクロールを持たせられる。**それでも持たせない** — 下の 3 つはどちらの開き方にも同じく当てはまり、3 つ目はまさに両者を揃えることを求めているからである。**規則が 1 つであることは、選択肢が無かったことの結果ではなく、選択の結果になった。**

「クランプを外して `overflow-y: auto`」は採れたが、採らない。理由は 3 つある。

**小さな浮動ボックスの内部スクロールは、スマホで扱いにくい。** スクロールチェーン（端まで来ると背後のページが動き出す）を `overscroll-behavior: contain` で塞ぐ必要があり、塞いでもなお「このスワイプは注釈が動くのかページが動くのか」が指を置くまで分からない。読者が事前に判断できない操作は、実装ではなく設計の問題である。

**長い注釈は浮動ボックスより本文の流れで読むほうが良い。** 8 行を超える注釈を 360px 幅の箱でスクロールして読むより、定義セクションへ飛んで全幅で読むほうが快適である。`↩` はその往復のために存在している — **ジャンプは劣った経路ではなく、長い注釈にとってはむしろ適した経路である**。

**振る舞いが 1 つになる。** ホバーとタップで同じ注釈が違って見えることがなく、ハイブリッド端末でも一貫する。§0 の状況（実使用ゼロの段階で作る機能）では、規則が少ないほど確実である。

副次的に、**検証がひとつ易しくなる**。スクロールさせる仕様なら、受け入れ基準はタッチのポインタ合成に加えてスクロールの合成まで要った（§8 が「手段が未確認」と書いている 5・6 の、さらに一段上）。切ると決めたことで、その基準は「内部スクロールを持たないこと」に置き換わる — 静的に測れる。基準を下げたのではなく、仕様を単純にして難しい基準を不要にした形である。

**切るときはフェードではなく `…` にすること。** グラデーションのフェードは、最終行が短いと余白の上にかかるだけで**続きがあることが読者に伝わらない**。`…` は必ず出る。

`…` は「続きがある」とは言うが「どうすれば読めるか」とは言わない。ホバーではそれでよい — **読者のポインタはその時点で参照の上にあり、クリックすればジャンプする**。必要な操作がカーソルの真下にある。タップ側では §4.2 の「定義へ」がその役を担う。**この決定により「定義へ」はタッチで続きを読む唯一の経路になる**ので、省略できない要素になった。

**代償 — モバイルのほうが早く切られる。** 幅が `calc(100vw - 2rem)` なので、390px の端末では使用幅が約 326px、全角 22 字/行、8 行で約 180 字。デスクトップ（480px 幅）は約 248 字である。**その間の長さの注釈は、デスクトップでは全部見えてモバイルでは切られる。** 画面が小さいほど早く切れるのは筋として正しいので、受け入れる。

### 4.3.2 機構は `-webkit-line-clamp`（2026-08-09 実測で確認）

`display: -webkit-box` / `-webkit-box-orient: vertical` / `-webkit-line-clamp: 8` / `overflow: hidden`。`…` は自動で付く。

**注釈のインライン要素が `-webkit-box` の中で壊れないことを実測した** — リンク（クリック可能なまま）・インラインコード（等幅フォントのまま）・強調（`font-weight: 600` のまま）がすべて残り、クランプ後の高さは 184px、すなわち 23.04 × 8 行にちょうど一致した。ここは机上で決めずに測るべき箇所だったので、確認してある。

**クランプは複製した `<p>` そのものに掛ける。** 定義はインライン内容のみなので（`docs/footnote-requirements.md` §2。改行は hard break）、複製の中身は常に単一の `<p>` である。これを `div` で包み直してそちらに `-webkit-box` を掛けてはならない — **ブロックの子を持つ `-webkit-box` は行数の数え方が不安定**で、上で測った 184px はその形では保証されない。§4.2 の「定義へ」がクランプの外に出るのはこのためでもある。

**行数で切るので、`45vh` のようなビューポート基準の保険とは合成できない。** `max-height` を併用すると、そちら側で切れたときに `…` が付かない。背の低いビューポート（横向きスマホなど）では、メディアクエリでクランプの行数自体を減らすこと — 2 つの機構を混ぜない。（唯一の例外は §5.2.2 の第 3 の枝である。上にも下にも入らないときだけ `max-height` が引き継ぐ — 順序どおり、メディアクエリで行数を下げたあとの最後の手段としてである。）

**複製の中に `<p>` が 2 つ以上あった場合は、先頭だけを出して残りは捨てる**（2026-08-09、実装時に決定）。このエディタの定義はインライン内容のみなのでこの形は書けず、起こり得るのは外部由来の Markdown だけである。段落ごとに 8 行ずつ切ると 1 つの注釈が画面を覆い、**プレビュー自身が §1 の目的を壊す** — §4.3 が上限を設けた理由がそのまま当てはまる。捨てた側もクリック 1 回（タッチなら「定義へ」）で読めるので、失われるのは経路ではなく手間である。

### 4.3.3 この 8 行は初期値である

**実際の注釈をまだ 1 本も見ていない状態で決めた数値である**（§0）。最初の実投稿を書いたあとに見直す。判定は後から効く形で残っている: `…` で切られる注釈が頻発するなら上限が低すぎ、一度も発動しないなら上限を書いた意味が無かった、ということである。

## 5. 表示と位置

### 5.1 native Popover API を使う

`popover` 属性による top layer 表示を使う。自前のオーバーレイに対して 3 つ得がある: **top layer**（`overflow: hidden` や `z-index` を持つ祖先に切られない）、**light-dismiss**（外側クリックで閉じる）、**Escape**。いずれも自前で書くと壊しやすい部分である。

これは §5.2 の「テーブル・callout・アコーディオン内の参照」に対する答えでもある — top layer に出る限り、祖先のクリッピングは関係しなくなる。

### 5.1.1 ピン留めは `auto`、プレビューは `manual`

**入口が 2 つある以上、モードも 2 つになる。**

`popover="auto"` が持つ light-dismiss と Escape は、**ピン留めが求めている閉じ方そのもの**である（§6 の「外側のタップ」「Escape」）。一方ホバー／フォーカスのプレビューは「ポインタが離れたら閉じる」だけを閉じ方に持つ。ここを `auto` にすると**閉じる条件が 2 箇所になり**、§5.2.3 が原則として禁じた状態（どちらが効いたのか読者にも実装者にも分からない）をプレビュー側に作ってしまう。したがってプレビューは `popover="manual"` とし、閉じるのは自分のリスナだけにする。

**代償は Escape である。** light-dismiss は外側クリックと Escape の両方を含み、`manual` はそのどちらも受け取らない。**プレビューは自前で `keydown` を拾って Escape で閉じること**（§6。WCAG SC 1.4.13 の Dismissible が要求している）。これは `manual` を選んだ判断を弱めるものではない — **どの閉じ方を持つかを自分で決める形になった**というだけで、`auto` のように閉じ方が勝手に 2 つ付いてくるのとは違う。

`auto` の副次的な利得として、**同時に開くのは 1 つ**という制約がブラウザ側で保証される。`manual` にはそれが無いので、**プレビューは開く前に自分で閉じる**（参照から参照へポインタが移ったとき）。ピン留めを開くときも、先に開いているプレビューを閉じてから開く — ハイブリッド端末では両方が同時に存在し得る。

### 5.2 位置決め — 参照の上、左右中央、入らなければ下へ反転

**既定は参照の上。左右は参照の中央に揃える。上に入らなければ下へ反転する。**

上を既定にするのは、**そちらが既に読んだ側だからである**。参照は文の途中にあり、読者の視線はそこから右下へ続く。下に出すとこれから読む本文を覆うが、上なら覆うのは読み終えた行になる。「本文の位置を失わずに読む」（§1）は、位置を思い出せることまで含む。

### 5.2.1 中央揃えと画面端は両立しない

**参照が画面端から `ポップオーバー幅 / 2` 以内にあるとき、中央揃えとビューポート内への収まりは同時に満たせない。** 390px の端末では幅が `100vw - 2rem` なので、実際には**モバイルではほぼ常にクランプが勝つ**（中央揃えが効くのはデスクトップの、端から 240px より内側にある参照だけである）。

**クランプを優先する。** 画面外に出た箱は読めないが、中央からずれた箱は読める。

したがって規則は「中央に置く」ではなく、**「中央に置き、はみ出すぶんだけ内側へ寄せる」**である。左右のマージンは 1rem 取る（§4.3 の幅計算 `100vw - 2rem` と同じ数値）。

**吹き出しの三角は初版では付けない。** 中央揃えが崩れた場合に参照との対応が弱まるので付ける動機はあるが、三角自体もクランプに追随して動かす必要があり、部品が 1 つ増える。**対応が分かりにくいと感じたときの逃げ道として記録しておく**（§10 と同じ扱い）。ホバーではポインタが参照の上にあり、タップでは直前に触れた場所なので、初版では足りると見ている。

### 5.2.2 上にも下にも入らない場合

**上を優先し、入らなければ下へ、どちらにも入らなければ広いほうを採ってそちらに合わせて高さを詰める。**

3 つ目の枝は横向きスマホのような背の低いビューポートで実際に起きる。§4.3.2 が「背の低いビューポートではメディアクエリでクランプの行数を減らす」と決めているので、**まずそちらで高さを下げ、それでも入らない場合の最終手段としてこの枝がある**。2 つの機構が同じ問題を別々に解こうとしないよう、順序をここに書いておく。

### 5.2.3 実装は自前で測る（CSS anchor positioning は採らない）

上の規則は `position-area` と `position-try` で宣言的に書けるが、対応状況が不均一で結局フォールバックが要る。**求めているものが「矩形を 2 つ測って `min`/`max` で挟む」程度の計算なので、自前のほうが確実で、分岐も全部ここに書いた形のまま書ける。**

top layer に出るので `position: fixed` と同じビューポート座標系で扱える。参照の `getBoundingClientRect()` がそのまま使えるので、祖先のスクロール量やオフセット親を辿る必要がない — **§5.1 が「テーブル・callout・アコーディオン内の参照」を解いたのと同じ理由が、ここでは座標計算を単純にしている**。

**リサイズでは位置を再計算する。閉じない。** 再計算は `scroll` / `resize` で `requestAnimationFrame` に載せる。

**スクロールの扱いは 2 つに分かれた（2026-08-09 改訂）** — プレビューは再計算して追随し、**ピン留めは閉じる**（§6.0）。当初はここに「スクロールでも閉じない。閉じる条件が 2 箇所にあると、どちらが効いたのか分からなくなる」と書いていた。**その原則は今も正しく、例外の理由が原則の側にある**: ピン留めには他に出口が無く、「閉じる条件を増やすな」は十分な出口がある前提の規則だからである。プレビューには出口があるので、こちらは原則どおり追随のままにしてある。

満たすべき条件（上の規則が満たすもの）:

- 参照の近くに出る（どの参照のものか分かること）
- 上下を反転できる（画面上端・下端で切れない）
- 左右をビューポートにクランプする（画面端の参照で切れない）
- **参照そのものに重ならない**（§5.3）

### 5.3 デスクトップでは参照の上に重ねない

デスクトップの読者は「ホバーでプレビューが出た直後にクリックする」流れになる。ポップオーバーが参照に重なっていると**そのクリックを食べる**。

**参照からずらして配置することで守る。** 以前はこれに加えて `pointer-events: none` を掛けており、二重に守られていたが、その指定は §4.1.1 で外した。**残った幾何のほうが本体である** — 箱が参照に重ならなければ、間に何も無いのだから食べようがない。`pointer-events: none` は「重なっていても大丈夫」という保険であって、重ならないことの代わりではなかった。

したがって §5.2 の「参照そのものに重ならない」は、見た目の要求から**クリックを守る要求に格上げされた**。受け入れ基準 16 がこれを押さえる。

### 5.4 見た目

`docs/footnote-requirements.md` §4.2 の判断を引き継ぐ。中身は注釈そのものなので `.prose` の見た目をそのまま使い、ポップオーバーの枠だけを新たに定義する。ダークモードは既存の `@media (prefers-color-scheme: dark)` ブロックに足す。

## 6. 閉じ方

| 開き方     | 閉じ方                                                                 |
| ---------- | ---------------------------------------------------------------------- |
| ホバー     | ポインタが**参照からもポップオーバーからも**離れる（遅延つき）、Escape |
| フォーカス | フォーカスが外れる、Escape                                             |
| タップ     | 外側のタップ（light-dismiss）、**24px を超えるスクロール**、Escape     |

### 6.0 タッチだけスクロールで閉じる（2026-08-09 追加）

**ピン留めは 24px を超えるスクロールで閉じる。プレビューは閉じない（追随する）。**

非対称だが、理由は 1 つである — **閉じ方を実質 1 つしか持たない側にだけ、閉じ方を足している**。

ホバーのプレビューには「ポインタが離れる」という出口が常にあり、読者がポインタを箱の中に置いているあいだは「まだ読んでいる」と読める。**タッチにはその状態が無い。** Escape が無く、「定義へ」は移動なので、実質「外側をタップ」しか残らない。結果として、ピン留めの箱は読者が明示的に消すまで、**スクロールする本文の上に乗ったまま付いて回る**ことになる。モバイルでは幅が `100vw - 2rem` あり、§4.1.1 の 4 つ目の代償（箱の下はポインタを受け取らない）を、読み進めるあいだずっと払い続ける。

**§4.1.1 の正当化がタッチでは成立していなかった。** あそこには「箱があるのは読者のポインタがそこにあるあいだだけだから受け入れる」と書いたが、**ポインタの無い側にはその歯止めが無い**。この節はその穴を塞ぐものである。

**しきい値は 24px（本文 1 行分）を初期値とする。** 0 にしない理由があって、iOS はアドレスバーの収縮やラバーバンドで `scroll` を出す — どちらも読者が何かを決めた瞬間ではない。**「理由もなく消える」は、消えないことより悪い。** リサイズはしきい値の基準を更新するだけで、決して閉じない（ビューポートの形が変わることは読者の意思表示ではない）。

ホバー側にしきい値を持ち込まなかったのは、あちらの相手が**微動の多いトラックパッド**だからである。指のスワイプは事情が違う（§9 の「スクロールで閉じる」の項も参照）。

**プレビュー側の Escape は WCAG 2.1 AA の SC 1.4.13（Content on Hover or Focus）の Dismissible が要求している。** ホバー／フォーカスで出た内容は、**ポインタを動かさず・フォーカスを移さずに消せる**必要がある。`manual` には light-dismiss が無いので自前で拾う（§5.1.1）。Escape で閉じてもフォーカスは参照に残す — 移すと Dismissible の要件そのものを外す。

これは §5.2.3 の「閉じる条件を 2 箇所に置かない」に反しない。**Escape は読者の明示的な操作であり、周囲の状態から勝手に効く閉じ方ではない** — 「どちらが効いたのか分からない」という問題が起きるのは後者どうしが並んだときである。

### 6.1 ホバーの遅延は開くほうと閉じるほうに 1 つずつ（2026-08-09 改訂）

**開く: 200ms。閉じる: 200ms。**

**開く遅延は「意図したホバーか」を見る。** 参照は `sup` の小さな的なので、別の場所へ向かうポインタが偶然その上を通ることがある。遅延が無いと、そのたびに top layer の箱が一瞬出る。参照から離れた時点で保留中のタイマーを捨てるので、**通り過ぎたホバーは開いてから閉じるのではなく最初から開かない**。

**閉じ遅延は「橋を渡り切れるか」を見る。** プレビューに入れるようになった以上（§4.1.1）、参照から離れた瞬間に閉じることはできない — 箱は参照に重ならない位置にある（§5.3）ので、**ポインタは必ず一度どちらにも属さない隙間を通る**。したがって規則はこうなる:

- 参照から離れる → 閉じるのを**予約**する
- ポップオーバーに入る → 予約を**取り消す**
- ポップオーバーから離れる → 閉じるのを**予約**する
- 参照に戻る → 予約を**取り消す**
- **別の参照に入る → 予約を取り消し、前の注釈を即座に閉じる**（開く遅延を待たない）

最後の 1 行は遅延を足したことで生まれた穴を塞いでいる。これが無いと、**移った先の参照の上に前の注釈が 200ms 居座る**（`文[^1][^2]` のように参照が隣接していれば必ず見える）。さらに悪いことに、ピン留めが開いている端末では開く遅延の中で早期リターンするため、**閉じる予約を取り消したまま誰も閉じない状態**が残る。基準 32 がこれを押さえる。

**この機構は §9 が避けていたものである。** 「この手の実装が壊れるのはたいていこの遅延まわり」と書いて退けた案が、方針転換（§4.1.1）でそのまま必要になった。**閉じ遅延は最適化ではなく仕様の一部**であり、消すとプレビューは隙間で落ちて「入れない箱」に逆戻りする。受け入れ基準 29・30 がこれを押さえる。

フォーカスで開くときは遅延を置かない。Tab の移動は偶然ではないので、抑えるべき誤発火が無い。フォーカスが外れたとき・Escape のときは**即座に閉じる** — どちらも明示的な操作で、橋を渡る途中ではない。

どちらの 200ms も初期値である（§4.3.3 と同じ扱い）。開く側は当初 120ms と書いていたが実装後に 200ms へ引き上げた（2026-08-09）。閉じる側を短くすると隙間で落ち、長くすると読み終えた箱が残る。

## 7. 実装の形

`components/CodeCopyButtons.tsx` と同じ形にする。`'use client'`、`useEffect` で `#post-body` を走査し、`a[data-footnote-ref]` にリスナを付け、クリーンアップで全部外す。**本文はサーバーレンダリングのまま**（`dangerouslySetInnerHTML`）で、コンポーネント自身は React の木に何も描かない。

**ポップオーバーの要素（プレビュー用の `manual` と、ピン留め用の `auto`）は命令的に作る。** 前例がコピーボタンを注入しているのと同じ形である。ピン留め用は §4.2 の「定義へ」を含むので「何も描かない」わけではないが、描く先は React の木ではない。2 つを参照ごとに作る必要は無い — **文書に 1 つずつあれば足りる**（プレビューは同時に 1 つしか出さず、ピン留めは `auto` がそれを保証する。§5.1.1）。

前例と同じく:

- **冪等にすること**（同じ参照に二度付けない。ポップオーバーの要素も二度作らない）
- クリーンアップで足したものを完全に戻すこと（**注入した 2 つのポップオーバー要素の除去まで**）
- `targetId` を props で受けること

## 8. 受け入れ基準

`e2e/` に置く。既存の `public-footnote.spec.ts` と同じく、エディタで書いて公開し、公開ページで測る。

1. マウスのホバーでポップオーバーが出て、注釈の文字が入っている
2. ポインタが参照からもポップオーバーからも離れると閉じる（§6.1）
3. **マウスの素のクリックは今までどおり定義へジャンプする**（§3.1 — 最も守りたい性質）
4. 修飾キー付きクリックが `preventDefault` されていない
5. タッチのタップではジャンプせず、ポップオーバーが残る
6. タップで開いたポップオーバーの中のリンクが押せる
7. ホバーで開いたポップオーバーはクリックを食べない（§5.3。`pointer-events: none` を外したので、これを守るのは配置だけになった — 16 と対になる）
8. `↩` がポップオーバーの中に入っていない
9. 注釈内のリンク・コード・強調が要素として残っている（テキストに潰れていない）
10. Escape と外側タップで閉じる
11. キーボードのフォーカスでプレビューが出て、Enter でジャンプする
12. スクリプトを無効にしても参照がジャンプする（プログレッシブエンハンスメント）
13. 8 行を超える注釈が 8 行に切られ、末尾に `…` が出る（§4.3。ホバー・タップとも同じ）
14. 切られたあとも 9 の要素が残っている（`-webkit-box` がインライン要素を潰していない）
15. ポップオーバーが内部スクロールを持たない（`scrollHeight` が `clientHeight` を超えない）
16. 既定では参照の上に出て、参照と重なっていない（§5.2 / §5.3）
17. 画面上端に近い参照では下へ反転する
18. 画面中央付近の参照では、ポップオーバーの中心が参照の中心に一致する
19. 画面左端・右端の参照でも、ポップオーバーがビューポートからはみ出さない（中央揃えより優先される）
20. **スクロールしてもプレビューが参照から離れない**（追随する。§5.2.3。**ポインタを箱の中に置いたまま**測ること — 参照の上に置いたままでは、ページが下から滑り出た時点で正当に閉じる。ピン留めでは測れなくなった、33 のとおり）
21. ウィンドウをリサイズしてもポップオーバーが参照から離れない（20 のリサイズ版。**リサイズは 33 の対象外**であることも同時に押さえる — ビューポートの形が変わることは読者の意思表示ではない）
22. ピン留めされたポップオーバーに「定義へ」があり、その `href` が参照の `href` と一致する（§4.2 — タッチで続きを読む唯一の経路なので、欠けると 13 の `…` が行き止まりになる）
23. **どちらのポップオーバーも `aria-hidden` も `inert` も持たない**（§3.5.1。2 度書き換わった基準である — 経緯は §3.5.1 に残してある）
24. 定義の無い参照（`href` の指す `id` がページに存在しない）ではポップオーバーが出ず、クリックが従来どおり動く（§3.6）
25. 上にも下にも入らない背の低いビューポートで、ポップオーバーがビューポートに収まる（§5.2.2 の第 3 の枝）
26. 背の低いビューポートではクランプの行数自体が減っており、切られた注釈に `…` が出る（§4.3.2 — `max-height` で切ると `…` が出ないので、この基準がその混入を検出する）
27. ダークモードでポップオーバーの枠と文字が本文と同じ扱いになっている（§5.4）
28. **フォーカスで開いたプレビューが Escape で閉じ、フォーカスは参照に残る**（§6。WCAG SC 1.4.13 Dismissible。`manual` には light-dismiss が無いので、自前の `keydown` が抜けると静かに落ちる基準である）
29. **参照からプレビューへポインタを移してもプレビューが消えず、注釈のリンクが押せる**（§4.1.1、§6.1。WCAG SC 1.4.13 Hoverable。以前の設計が満たしていなかった条項そのもの）
30. **プレビューからポインタが離れると閉じる**（§6.1。29 と対。閉じ遅延が「閉じない」に化けていないことを見る — 29 だけでは、開きっぱなしのバグが合格する）
31. **プレビューが開いているあいだ、箱が覆っている本文はポインタを受け取らない**（§4.1.1 の 4 つ目の代償。望ましさではなく**意図した状態**を固定する基準であり、`pointer-events: none` を戻すと赤くなる）
32. **別の参照へポインタを移すと、前の注釈は開く遅延を待たずに消える**（§6.1。移した先の参照の上に前の注釈が居座らないこと。ピン留めが開いている場合に閉じる予約ごと消える穴も、同じ 1 行が塞いでいる）
33. **ピン留めがスクロールで閉じる。ただし 24px 以下の動きでは閉じない**（§6.0。後半が本体である — しきい値が効いていないと、アドレスバーの収縮やラバーバンドで消える）

**5・6 の検証手段は確認済み（2026-08-09、実装時）。** 未確認と書いていたが、`test.use({ hasTouch: true })` の下で `page.touchscreen.tap()` がページに `pointerdown` / `pointerType === 'touch'` として届くことを使い捨ての probe で実測した（タップ経路が見ているのはこの 1 つだけである）。CDP は要らなかった — `native-drag.ts` がテーブルのドロップガードで CDP に行き着いた（`07763bb`）のは、headless Chrome が `Input.dragIntercepted` を発火しないという別の欠落によるもので、タッチには当てはまらない。同じ probe で、クリックを `preventDefault` すればアンカーの遷移が止まること、`manual` の popover が Escape でも外側クリックでも閉じないこと（§5.1.1 の代償の裏付け）も確認している。したがって **5・6・22・23 のピン留め側はすべて実測されている**。

**この一覧は §3〜§6 の決定を 1 つずつ写している。** 脚注本体で「21/21 測定」が定義の順序という決定を 1 つ丸ごと取り落とした（`docs/footnote-requirements.md` §10.1）ので、決定を足したら基準も足すこと。

## 9. 却下した案

**ホバーのプレビューもスクロールで閉じる**（§6.0）。ピン留めと揃うので一見きれいだが、揃える理由が無い — プレビューには「ポインタが離れる」という出口が既にあり、**ポインタが箱の中にあるあいだは「まだ読んでいる」と読める**。加えて、微動の多いトラックパッドを相手にしきい値を決めることになり、外すと「理由もなく消える」ほうのバグを作る。実測でも、ポインタを箱に置いたまま 303px スクロールして開いたままだった挙動は、読者の意図に反していない。**非対称なのは、2 つのポップオーバーが持っている出口の数が違うからである。**

**クリックでピン留め、ジャンプはポップオーバー内へ**（§3.1）。デスクトップの既存挙動を奪い、素のクリックへの介入が必要になり、修飾キー付きクリックを壊す危険を自分で作る。プレビューは足し算にできるのに引き算を混ぜていた。

**メディアクエリによる端末判定**（§3.2）。主たる入力しか表さず、ハイブリッド端末で外れる。

~~**ホバーのポップオーバーを操作可能にする（遅延つき）**~~ — **却下を撤回し、採用した（2026-08-09）。§4.1.1 と §6.1 がその決定である。**

却下時の理由はこう書いてあった: 「§3.1 を採った時点で不要になった — デスクトップの読者はクリックで定義へ飛べる。この手の実装が壊れるのはたいていこの遅延まわりなので、要らなくなったのは素直に利得である」。

**この理由のうち、正しかった部分と間違っていた部分を分けて残す。**

- **正しかった**: 遅延まわりが壊れやすいという見立て。実際、閉じ遅延・その取り消し・両方向の予約という 3 つの状態が入った。だから**仕様として書き、基準 29・30 で測る**（§6.1）
- **間違っていた**: 「不要になった」という判断。定義へ飛べば読めるのは事実だが、それは**往復を消すという §1 の目的そのものを、リンクを押したい読者に対してだけ諦めていた**。しかも §4.1 は、その諦めが WCAG SC 1.4.13 の Hoverable を満たさないと自分で書いていた — **却下の根拠と、既知の未達が同じ 1 つの指定から出ていた**

**却下を撤回する判断は、新しい情報ではなく重みの変更である。** 壊れやすさより、読者が注釈のリンクを押せることを取った。

**注釈をプレーンテキストで表示する**（§4.1）。リンク・コード・強調が落ちる。複製すれば済む話で、失うものに見合わない。

**はみ出しをグラデーションのフェードで切る**（§4.3.1）。見た目は柔らかいが、**最終行が短いとフェードが余白の上にかかるだけで何も見えない** — 続きがあることが読者に伝わらない場合がある。`…` は必ず出る。信号としての確実さを優先する。

**上限を設けず、ホバーでも全文を出す**。初版の案だったが、8 行を超える注釈は本文を覆い、「本文の位置を失わずに読む」という §1 の目的をプレビュー自身が壊す。

**ホバー用のポップオーバーも `popover="auto"` にする**（§5.1.1）。light-dismiss が付いてくるのは得に見えるが、プレビューには既に「ポインタが離れる」という閉じ方があるので、閉じる条件が 2 箇所になる。§5.2.3 が原則として避けた形である。

**ピン留めに閉じるボタン（`×`）を置く**（§4.2）。`popover="auto"` の light-dismiss が既に外側のタップで閉じており、しかも**閉じる的は画面のほぼ全部**である。加えて、読者が注釈を読んだあとに次にする操作（本文へ戻る）がそのまま閉じる操作になっている。対して代償は具体的で、モバイルの使用幅は約 326px しかないので（§4.3.1）、右上のボタンは 1 行目を削るかパディングを増やすかのどちらかになる — **8 行の上限を自分で削ることになる**。§5.2.1 で吹き出しの三角を「部品が 1 つ増える」として退けたのと同じ判断であり、動機はあちらより弱い。WCAG SC 1.4.13 の Dismissible はホバー／フォーカスで出た内容にしか掛からないので、ここでは要求されていない（プレビュー側の Escape は §6 のとおり必要である）。

買っていたものは 1 つある: **浮いている箱を消したいとき、人はまず箱そのものを触る**。外側を触るのが正解だと知らない読者は、注釈の上をタップして何も起きないのを引く。**「そのときは内側のタップでも閉じる」で回収できる**（部品は増えない）が、規則を 1 つ足すことになるので初版では採らない。§10 と同じく逃げ道として記録しておく — 判定の材料は「閉じ方が分からない」という実際の声である。

**両方のポップオーバーに `aria-hidden` を付ける**（§3.5.1）。ホバー側の理屈をピン留めにも延長する案だが、ピン留めの中にはフォーカス可能な要素が 2 つある。支援技術からは存在せず Tab では止まる要素を作ることになる。

**タップで開いたときはクランプを外し、内部スクロールで全文を読ませる**（§4.3.1）。スクロールチェーンを塞いでもなお、スワイプが注釈を動かすのかページを動かすのかが読者に予測できない。加えて、長い注釈を 360px 幅の箱で読ませるより定義セクションへ飛ばすほうが読みやすい。

## 10. エスカレーション先 — タッチのボトムシート

実使用で「注釈が長く、モバイル読者が毎回ジャンプしている」と分かった場合、**直し方は小さなポップオーバーに内部スクロールを足すことではない**（§9 で退けたばかりの案に戻ることになる）。**タッチのときだけボトムシートにする**のが定石である — 全幅で、スクロールが自然で、スワイプで閉じられる。

初版でやるには大きすぎるので採らないが、逃げ道をここに書いておく。書いておかないと、症状が出たときに「とりあえずスクロールを足す」で解決しようとして、退けた理由ごと踏み直すことになる。

判定の材料は §4.3.3 と同じ — `…` がどれくらいの頻度で出るかである。
