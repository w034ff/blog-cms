**この文書はアコーディオン・脚注の 2 つと違い、実装前の設計記録ではない。** 実装が先にあり、判断とその理由はコードのコメントとコミットメッセージに散っていた。それを 1 か所に集めたものである。したがって**数値はすべて「その時点での実測」であり、この文書を書いた時点で測り直したものではない**。出典（コミット / コメント）を各所に付けてある。

## 1. 目的と非目標

**目的**: 長い記事で、読者が全体の構造を把握し、任意の節へ飛べるようにする。併せて「今どこを読んでいるか」を示す。

**対応していない範囲**（この文書は事後の記録なので、以下は「そう決めた記録がある」ではなく**現状そうなっている**という整理である。§13 の制約と対になる）:

- h4 以下の見出し（§2）
- 目次の折りたたみ・ピン留め・幅の変更といった読者側の設定
- 記事一覧やトップページなど、記事ページ以外での目次
- エディタのプレビュー側の目次
- 見出し以外（画像・コードブロック等）を目次に載せること

## 2. データモデル

```ts
export type TocEntry = { id: string; text: string; level: 2 | 3 };
```

`lib/rehype-collect-toc.ts` が定義し、`lib/render.ts` が再エクスポートする。`renderMdxToHtml()` の戻り値が `{ html, toc }` になっており、**目次は描画済み HTML を再パースして作るのではなく、同じ 1 回の変換から副産物として出てくる**（§3）。

vfile の `DataMap` を `declare module` で拡張して `file.data.toc` に型を付けている。unified のプラグインが結果を返す唯一の正規の口がここであり、`unknown` を挟まずに済む形はこれしかない。

**レベルは 2 と 3 だけである。** エディタが `Heading.configure({ levels: [2, 3] })`（`components/editor/extensions.ts` の `postEditorExtensions`）で本文の見出しを h2/h3 に制限しているため、記事が生み出しうる見出しはこの 2 つに限られる。収集側にフィルタは無く、`h2` / `h3` 以外を単に見ていない。

**帰結**: 著者が生 HTML で `<h4>` を書いた場合、`rehypeSlug` は id を振り sanitize も通すが、**目次には出ない**。壊れないが載らない、という扱いにしてある。h4 を目次に載せたくなったら、収集側とエディタ側の両方を変えることになる。

## 3. 収集 — パイプライン内の位置が仕様である

`rehypeCollectToc` は `lib/render.ts` の unified パイプラインの中で、**`rehypeSanitize` より後**に置かれる。これは並び順の好みではなく**要件**である。

sanitize のスキーマ（GitHub の `defaultSchema`）は DOM クロバリング対策として、すべての `id` を `user-content-<id>` に書き換える。目次より前で id を読むと、実際に描画される見出しの id とは違う文字列の一覧ができ、リンクがどこも指さなくなる。

同じ理由で `rehypeClobberFragmentLinks` も sanitize の後に置かれている。ただし**両者の役割は違う**:

| プラグイン                   | 対象                     | 目次との関係                                                       |
| ---------------------------- | ------------------------ | ------------------------------------------------------------------ |
| `rehypeClobberFragmentLinks` | 本文中の `<a href="#…">` | 本文のリンクだけを直す。目次のリンクは通らない                     |
| `rehypeCollectToc`           | h2/h3 の `id`            | 書き換え**後**の id を読む。目次の `href` は最初から正しい形になる |

つまり**目次のリンクは接頭辞の書き換えを一切受けない**。`TocNav` が `href={`#${entry.id}`}` として組み立てる時点で `entry.id` が既に `user-content-…` だからである。本文のリンクが書き換えを要するのは、著者が書いた `#見出し` が sanitize の前の名前を指しているからであって、2 つの経路は同じ問題に別々の場所で答えている。

この不変条件は `lib/render.test.ts` が押さえている（§12）。収集した id と、同じ呼び出しが返す HTML の中の id を、同じテストで突き合わせている。

## 4. 目次から外すもの

`rehypeCollectToc` は 2 段構えで走る。先に `<details>` と脚注セクション（hast 上の判定は `node.tagName === 'section' && 'dataFootnotes' in node.properties`。`data-footnotes` 属性の hast 表現である）を走査して配下の h2/h3 を `Set` に集め、次に文書順で h2/h3 を拾いながらその集合をスキップする。

**ここで外した見出しは、表示条件の頭数からも外れる**（§5）。

祖先を辿らないのは依存を増やさないため。 `visit` は親を 1 つ渡すが祖先の連なりは渡さないので、見出し側から「自分は `<details>` の中か」を答えられない。答えさせるには `unist-util-visit-parents` を足すことになる。述語 1 つのために依存を増やすより、先に外側から集めるほうが安い。

### 4.1 アコーディオン（`<details>`）の中の見出し

**判断の本体は `docs/accordion-requirements.md` §8.1 にある。ここでは繰り返さない。** 要点だけ:

- 目次は「読者に見えている構造」の一覧であり、著者が畳んだものは本筋ではないという判断の結果である
- 閉じた `<details>` の中の id へフラグメント遷移したとき折りたたみが開くかは**ブラウザ依存**であり、既定の導線をその経路に通さない

**`hashchange` で祖先の `<details>` を開くスクリプトは入れない**という判断も同節にある。**Firefox で開かないことを理由に再検討しないこと。**

### 4.2 脚注セクションの見出し

判断の本体は `docs/footnote-requirements.md` §8 にある。 remark-gfm が脚注セクションに自前の `<h2 class="sr-only" id="footnote-label">Footnotes</h2>` を付けるため、これを外さないと日本語記事の目次に英語の "Footnotes" が 1 行増える（実測、`c7757fc`）。著者が書いた節ではなく、読み上げ専用のクロムである。

### 4.3 外さないもの

引用・コールアウト・テーブルセルの中の見出しは**外さない**。これらはどれも閉じておらず、読者に見えているからである。除外規則は「畳まれているか」「著者が書いたか」の 2 点だけに立っており、入れ子の深さは見ていない。

### 4.4 id は必ず残る

**目次から外しても id は消えない。** `rehypeSlug` は場所を問わず h2/h3 に id を振り、sanitize が接頭辞を付ける。目次は id を読み取って一覧を作っているだけなので、本文中の `[…](#見出し)` も外部からの `#user-content-…` も従来どおり解決する（実測、`13f6e83`）。**これは §4.1 / §4.2 の判断が成立する前提である** — 「目次に載せない」は「到達できない」を意味しない。

## 5. 表示条件 — 見出し 3 つ以上

```ts
const MIN_HEADINGS_FOR_TOC = 3; // components/PostArticle.tsx
```

`toc.length >= 3` のときだけ目次を出す。1〜2 個の記事では、飛ぶ先が少なすぎて目次が案内ではなく余分な部品になる。

**数えているのは §4 で除外した**後**の項目数である。** `page.tsx` は `renderMdxToHtml()` が返す `toc` をそのまま数えており、その配列からはアコーディオンの中の見出しと脚注セクションの見出しが既に落ちている。したがって:

- 見えている h2 が 2 つ、アコーディオンの中に 3 つある記事は、**短い目次が出るのではなく目次が出ない**
- 脚注を持つ記事は、脚注セクションの見出しを 1 つとして数えない（数えていたら、見出し 2 つの記事が脚注を付けた瞬間に目次が現れることになる）

**この結び付きはどのファイルにも書かれていない** — `page.tsx` は除外の存在を知らず、収集側は閾値の存在を知らないため、片方だけを読むと見えない。閾値を動かすときも除外規則を足すときも、もう一方を見ること。

**この判定は 3 か所を同時に切り替える**（`showToc`）:

- `<article>` のクラス（3 トラックのグリッド ↔ 素の `mx-auto max-w-site`）
- `TocNavMobile` の描画有無
- `TocNavDesktop` の描画有無

したがって目次が出ない記事は、レイアウトの上でも他のページと完全に同じになる。目次のためのグリッドが空のまま残ることはない。

## 6. レイアウト — 3 トラックのグリッド

ここがこの機能でいちばん多くの案を潰した場所である。

### 6.1 満たすべき条件

**目次を出す記事でも、本文の左端が他のページ・SiteHeader と 1px もずれないこと。** これが唯一かつ最大の制約である。目次のためのレールは本文の右側の余りだけを食ってよい。

採用した形（`components/PostArticle.tsx`）:

```
grid-cols-[calc((100% - var(--container-site))/2)  var(--container-site)  1fr]
```

- トラック 1（左の余白）はレールの幅と無関係に列幅だけから計算される。素の `mx-auto max-w-site` が作る左余白（`(container − column) / 2`）と同じ式なので、同じ幅では必ず同じ左端に着く
- トラック 3 が `1fr`（固定幅ではない）なので、3 つの合計は常にちょうど 100% になり、どの幅でも横方向のオーバーフローが起きない

### 6.2 却下した案（いずれも同じ理由で落ちた）

| 案                                                    | 落ちた理由                                                                                   |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `mx-auto max-w-[65.5rem]` で記事ページだけ広げる      | 広い箱を左右対称に中央寄せするので、**本文の列ごと約 124px 左へ動く**（SiteHeader とずれる） |
| 4 トラック（`minmax(1rem,1fr)` の余白を左右に置く形） | 同じバグ。**対になった伸縮する余白は、増えたレール幅を必ず両者で分け合う**ため左が動く       |

**「レールの大きさと独立に計算された余白」だけがこれを避けられる。** `--container-site` を読む `calc()` にしてあるのはそのためである。`docs/` の外にも記録があり、この落とし穴は独立した知見として残っている（CSS breakout-grid gutter pitfall）。

### 6.3 サイト全体への波及

グリッドを成立させるために、**幅を決める責任が `<main>` から各ページへ移った**（`32c366a`）。

- `app/layout.tsx` の `<main>` は幅を**キャップしない**（`flex-1 w-full px-4 py-8`）。各ページの根が自分で `max-w-site` を持つ
- `SiteHeader` / `SiteFooter` は外側の要素に `px-4` を置き、中央寄せの箱には置かない。内側に置くと、その箱の幅が padding 込みになり、**サイト名が本文より 16px 右へずれる**（実測、`32c366a`）

この 2 点は目次のためだけの変更であり、目次を消すなら一緒に戻すことになる。

### 6.4 結び付いている 2 つの値（**変更時は必ず一緒に見ること**）

```css
--container-site: 50rem; /* 本文の列。サイト全体がこれを見る */
--breakpoint-toc: 85rem; /* これ以上の幅でだけ目次を出す */
```

**目次の nav は `w-60`（240px）の固定幅で、レールの幅は `(ビューポート − --container-site) / 2` である。** nav は `ml-6` と合わせて 16.5rem を要るので、境界は `50 + 2 × 16.5 = 83rem` に、スクロールバーの分の 2rem を足した 85rem にしてある。メディアクエリはスクロールバーを含む幅を見るが、グリッドの 100% は含まない（`html` の `scrollbar-gutter: stable`）。この 2rem が無いと、境界のすぐ上で nav がページを横にはみ出す。2026-10-03 に、幅が `1fr` で 168〜240px に伸び縮みする形から固定幅に変えた。参考にした他サイトの目次がどれも固定幅で、狭い幅で目次だけが痩せるのを作者が退けたためである。代わりに 1232〜1359px の幅では折りたたみの目次になった。

**列を再び広げるなら、この境界も上げること。** 上げなければ、境界のすぐ上で nav がページを横にはみ出す。

`toc:` バリアントは**ちょうど 3 か所**から参照される — グリッド本体、`TocNavMobile` の非表示、`TocNavDesktop` の表示。**3 つは同時に動かすこと。**

### 6.5 グリッドで効いている 2 つの指定

| 指定                    | 無いとどうなるか                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `toc:items-start`（親） | グリッド項目が行の高さいっぱいに伸び、**`sticky` が張り付く余地を失う**。目次が追従しなくなる                    |
| `min-w-0`（本文の列）   | グリッド項目の既定 `min-width:auto` により、**横に広いコードブロックが入った瞬間に列が固定トラックより広くなる** |

どちらも「無くても普通の記事では動いてしまう」種類の指定なので、消さないこと。

## 7. 2 つの DOM — どちらも常にマウントする

| コンポーネント  | 出る幅      | 形                                                   |
| --------------- | ----------- | ---------------------------------------------------- |
| `TocNavMobile`  | `toc:` 未満 | 本文カードの先頭に置く、**既定で閉じた** `<details>` |
| `TocNavDesktop` | `toc:` 以上 | グリッド 3 列目の `sticky` な nav（枠なし）          |

**切り替えは CSS の表示制御であって、条件付き描画ではない**（`toc:hidden` / `hidden toc:block`）。したがってどの幅でも両方がマウントされ、`useActiveHeadingId` の効果が 2 つ走る（登録されるのは `scroll` と `resize` の 2 種類 × 2 インスタンス）。

これは意図的である。 サーバーで描画するマークアップはビューポート幅を知り得ないので、条件付きにするには境界を JS に持ち込むしかない。両者は同じ見出しの位置を同じ基準線で読むため、**独立に同じ id へ到達し、食い違いようがない**。代償は 1 フレームにつき余分な rAF 1 回で、これは「常に 1 つしか正解が無い状態」のために context/provider を足すより安い。

アクセシビリティ上の重複は起きない。 表示されていない側は `display:none` なのでアクセシビリティツリーから外れる。読み上げに `目次` という nav が 2 つ現れることはない。

### 7.1 モバイル側を既定で閉じる理由

本文カードの**先頭**、記事本文の手前に出るため。開いた状態で出すと、読み始める前に本文をその高さぶん押し下げる。

枠ではなく下線 1 本で区切ってあるのも同じ流儀の判断で、カードの中に角丸の枠をもう 1 つ描くと「箱の中の箱」に見える。

## 8. アクティブな項目の判定

```ts
const BAND_TOP_PX = 64; // components/TocNav.tsx
```

**規則: 上端が `BAND_TOP_PX` を越えた最後の見出しが「今読んでいる節」である。** まだ最初の見出しより上にいる間は先頭の項目を指す。

**毎回の走査で位置から導出し、前回の答えを覚えない。** これが仕様の中心である。

### 8.1 却下した案 — IntersectionObserver

初版は IO が「帯の中にあると最後に報告した見出し」を保持し、その集合が空になったら前の値を維持していた。これは 2 つの意味で壊れていた（`32c366a` の実測）:

- 答えがそこへどう来たかに依存する。スクロールで戻ると先頭が点いたままなのに、読み込み直後は何も点かない
- 答えがウィンドウの高さに依存する。最初の見出しがたまたま帯に入るかどうかで変わり、約 1080px では入るが約 800px では入らなかった

「最後に越えたもの」に変えると、状態を持たないので**どちらの依存も消える**。

### 8.2 却下した案 — IO のまま基準線だけ変える

**IO は「交差していない → 交差していない」の遷移で何も報告しない。** 2 フレームの間に見出しが帯を飛び越える瞬間移動 — `prefers-reduced-motion` 下の目次リンク、`#hash` 付きでの着地 — でハイライトが古いまま残る。

このページでは通常 `html:has(#post-body)` のスムーススクロール（§9）が跳躍を帯の中を通してくれるので隠れるが、**その規則が切れるのはまさに `prefers-reduced-motion` のとき**、つまり跳躍が瞬間移動になるときである。よってスクロールイベントを採る。rAF で間引くので、1 スクロールフレームあたりの費用は見出し 1 走査に収まる。

### 8.3 `BAND_TOP_PX = 64` の根拠

- 見出しが画面下端に現れた瞬間に点かない程度には下にある
- 飛んだ見出しが落ち着く位置より十分下にある（`#post-body h2, h3` の `scroll-margin-top` は 1rem）。したがって**目次のリンクを踏めば、必ずその項目自身がアクティブになる**

この 2 つ目が実質的な要件であり、`scroll-margin-top` を大きく変えるならこの値も見直すことになる。

## 9. スクロール挙動 — スムーススクロールは記事ページに閉じ込める

```css
@media (prefers-reduced-motion: no-preference) {
  html:has(#post-body) {
    scroll-behavior: smooth;
  }
}
```

**`<html>` に無条件で書いてはならない。** `app/layout.tsx` の `<html>` は全ルートで共有されており、かつ:

- CSSOM View では `element.scrollTop` への代入は behavior `auto`、すなわちその要素の計算値でスクロールする
- prosemirror-view はキャレットを画面内に保つためにスクロール親の `scrollTop` を直接書く（`scrollRectIntoView`）
- エディタは自前の内部スクロール領域を持たない（`components/PostEditor.tsx` の枠は、sticky なツールバーのために意図的に `overflow-hidden` ではない）。**したがってエディタのスクロール親は `<html>` である**

つまり全体に `smooth` を置くと、**入力のたびにキャレット追従が滑らかに animate され、打っている文字がそれを追い越す**。`:has(#post-body)`（記事ページだけが持つ id）で範囲を絞ってあるのはこのためである。

`motion-safe` 相当のメディアクエリは、これが置き換えた Tailwind のクラスと同じ扱いを維持するためのもの。

| 幅                   | `w-60` の固定幅（§6.4）、`ml-6` が本文との間隔                                                                                                                                                                                                                                                                                                                                                        |
| 階層                 | h3 の項目だけ字下げする。デスクトップでは h2 の項目を一段濃くする（明 `zinc-800` / 暗 `zinc-300`。暗で `zinc-200` にすると、アクティブな項目との差が太さだけになる）                                                                                                                                                                                                                                  |
| 縦線（デスクトップ） | 一覧の左に 1px の線を引き、アクティブな項目にはその上に `--accent` の 3px のバーを重ねる。h3 の項目でもバーはレールの位置に出し、字下げはリンクの内側にかける                                                                                                                                                                                                                                         |
| 間隔（デスクトップ） | 項目の間に隙間を置かず、リンク自身の上下に 4px の余白を付ける（項目の間隔 28px）。バーが項目の高さいっぱいに伸びる                                                                                                                                                                                                                                                                                    |
| アクティブ           | `font-weight: 600`。デスクトップでは `--accent` のバーを印にし、文字は濃い色（明 `zinc-900` / 暗 `zinc-50`）にする。本文を読む横で赤い語が跳ばないようにするためと、本文でアクセントの文字が意味する「強調」と混ぜないため（2026-10-03）。バーの無いモバイルの `<details>` では文字を `--accent`（明 `#9f1239` / 暗 `#ec7a92`）にする。色とバーは 150ms で移り、`prefers-reduced-motion` では移らない |

### 10.1 却下した案 — `truncate`

**1 行省略では足りない**（`9e264bb` の実測）。h3 の項目の文字に使える幅は、nav の 240px から `p-1` の 8px と字下げの 28px を引いた約 200px で、日本語で約 14 文字である。見出しは容易にそれより長い。

`line-clamp-2 break-words` に変えた。

- 高さが増えても安全なのは、レールが元から `max-h-[calc(100vh-2rem)] overflow-y-auto` を持っているため。長くなった一覧は、元から巻ける枠の中で巻けるだけであり、sticky な列がそれを超えて伸びることはない
- `block` は**付けない**。clamp ユーティリティ自身が `display:-webkit-box` を宣言し、いずれにせよ li を埋めるブロックレベルの箱になる（＝項目全体がクリックできる）。`block` を残すと競合するだけである
- `break-words` は折り返しだけでは足りない場合のためにある。日本語はほぼどの 2 文字の間でも折り返せるが、見出しの中の長い英数字 1 語（API 名など）は折り返し機会を持たず、clamp のオーバーフローで**切れる**

## 12. 検証状況とギャップ（**「受け入れ基準」ではない**）

**この節を「満たしている項目の一覧」として読まないこと。** 脚注機能で「21/21 測定済み」が、どの基準も定義の順序を測っていなかったという穴を隠した前例がある（`docs/footnote-requirements.md` §10.1）。ここでは同じ声で書かないために、測ってある / 測っていないを分けて書く。

### 12.1 自動で測ってあるもの（`lib/render.test.ts`、vitest 5 ケース）

いずれも**収集側だけ**である。

1. h2/h3 を文書順に集め、id が描画後の（接頭辞付きの）形と一致する（§3）
2. 同じ文言の見出しが `-1` 付きで重複回避され、目次の id も同じ規則に従う
3. 見出しが無ければ空配列
4. アコーディオンの中の見出しが外れ、外の見出しは残る。かつ中の見出しの id は描画される（§4.1 / §4.4）
5. 脚注セクションの見出しが外れる。かつその id は描画される（§4.2 / §4.4）

（4 と 5 は、除外そのものと「外しても id は残る」を同じケースの中で見ている。）

### 12.2 測っていないもの（**E2E は 1 本も無い**）

以下は**すべて未検証**である。ブラウザでしか観測できず、`e2e/` に目次の spec が存在しない。

- 表示条件（`MIN_HEADINGS_FOR_TOC`）— 見出し 2 個の記事で目次が出ないこと、3 個で出ること
- その閾値が除外後の数を見ていること（§5）。見えている見出し 2 つ＋アコーディオンの中に 3 つ、という記事で目次が出ないこと。ここは vitest でも測れる（収集結果の長さの問題なので）が、現状は測っていない
- 本文の左端が、目次あり記事・目次なし記事・SiteHeader で一致すること（§6.1。この機能で最も多くの案を潰した条件が、自動では測られていない）
- `toc:` の境界で表示が切り替わること、どの幅でも横スクロールが出ないこと
- アクティブ判定（§8）— 読み込み直後に先頭が点くこと、スクロールで移ること、目次リンクを踏んだ先でその項目自身がアクティブになること、`prefers-reduced-motion` 下でも古いままにならないこと
- `aria-current` が 1 つだけ付くこと
- 2 行の clamp と、長い英数字 1 語の折り返し（§10.1）
- モバイル側が既定で閉じていること
- エディタでの入力が滑らかにスクロールしないこと（§9 の逆側）

書くとしたら `e2e/public-toc.spec.ts` が置き場所になる（`public-callout.spec.ts` / `public-codeblock-*.spec.ts` と同じ系列）。ただし**幅に関わる項目は既存のハーネスの流儀とは別種**（ビューポートを変えて px を測る）なので、そこは新しい型になる。

## 13. 既知の制約

- h4 以下は載らない（§2）。エディタが作れないため実害は無いが、生 HTML で書けば載らない見出しが作れる
- アコーディオンの中の見出しは載らない（§4.1）。折りたたみの中の節へは、本文中のリンクからしか到達できない
- `toc:` 未満では常に折りたたまれた状態で始まる。読者の開閉状態は保存しない
- 目次の項目は見出しのテキストそのままである。長い見出しは 2 行で切れる（§10.1）。見出し側を短くする以外の手当ては無い
- どの幅でも 2 つのインスタンスが同時に生きている（§7）。意図的だが、`scroll` / `resize` のリスナがそれぞれ 2 組登録されることは、目次を持つページの費用として認識しておくこと
- 見出しが 3 つ未満に「見える」記事では目次が出ない（§5）。畳んだ中に見出しが何本あっても数に入らない
