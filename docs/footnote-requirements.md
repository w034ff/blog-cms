## 0. 前提 — 表示側の脚注を復活させること（2026-08-04 撤回済み）

この機能は公開ページ側の脚注を必要とする。前提は満たされた。

2026-08-03 の議論で一度「表示側の脚注は不要」と判断し、その判断が現行の実装（脚注記法を構造にせず、ただの文字として保持する）を選ばせた。エディタで脚注を編集できても公開ページで脚注として組版されないなら意味がないため、本要件はその判断を撤回する前提でのみ成立する — **2026-08-04 に撤回され、公開側にも脚注を出す方針が確定した。**

撤回のコストは低いという見立ては実測で裏付けが取れた（2026-08-04）。`lib/render.ts` に `本文[^1]` と定義行を通すと、remark-gfm が `<section data-footnotes>`・backref・相互ジャンプまで揃った形を出す（`lib/render.test.ts` の「links a GFM footnote to its definition and back」が既にそれを固定している）。`lib/rehype-clobber-fragment-links.ts` がジャンプリンクの id を解決する。

**つまり公開側に新規実装は要らない。** 現状で脚注が出ないのは、エディタが保存する本文が `\[^1\]` とエスケープされているからで、素の `[^1]` が保存されれば公開側はそのまま組む（同じく 2026-08-04 に `lib/render.ts` へ両方の形を通して確認）。

## 1. 目的と非目標

**目的**: 本文の流れを切らずに補足を書ける手段を、WYSIWYG のまま提供する。

**非目標**（初版では明示的に対象外とする）:

- 脚注の入れ子（脚注の中の脚注）
- 脚注内のブロック要素（表・コードブロック・callout）。初版はインライン内容のみ
- サイドノート／余白注釈のような別レイアウト
- 既存記事の自動マイグレーション（対象記事が存在しないため不要）
- **`^[インライン脚注]` 記法**（下記）
- **脚注の中の脚注**。定義は inline 内容を持つのでスキーマ上は参照が入ってしまう。配置判定（§6）が `footnoteSection` / `footnoteDefinition` も拒否対象に含めることで塞いだ（2026-08-04）

`^[…]` は「作らない」では足りない。`markdown-it-footnote` は `footnote_def` と同時に `footnote_inline` ルールも登録するので（§7.2）、プラグインを入れた時点でこの記法がパースされる。

**ただし、当初ここに書いた「著者が書いた文字が保存で消える」は誤りだった**（2026-08-04、スパイクで実測）。この記法は通常の脚注に正規化される — `本文^[インライン注]` は参照 1 つと定義 1 つになり、注釈の文字はそのまま残る。失われるのは**文字ではなく記法**で、保存すると `[^inline-0]: インライン注` という GFM 形に書き換わる。

したがって判断すべきは「データ消失をどう防ぐか」ではなく、「著者が選んだ記法をエディタが書き換えてよいか」である。GFM 側にこの記法は無いので、保存形式（§2）としては書き換えるほうが筋が通る。スパイクは書き換える側を採っている。

**実装上の罠**（実測）: 参照と定義は別々のレンダラ規則が描くので、ラベルの生成をカウンタで行うと**両者に違うラベルが渡り、次回の読み込みで対が壊れる**。参照が `[^inline-1]`、定義が `[^inline-2]` として保存され、注釈が孤児になった。ラベルはトークンの `meta.id`（脚注の通し番号）から導くこと。

## 2. データモデル

**保存形式**: GFM 脚注（本文中の `[^label]` と、定義行 `[^label]: 注釈`）。Markdown を記憶形式とする既存方針は変えない。

**ProseMirror スキーマ**: 2 ノード構成。

| ノード               | 種別                                 | 備考                                 |
| -------------------- | ------------------------------------ | ------------------------------------ |
| `footnoteReference`  | インライン、`atom: true`、selectable | 本文中に置かれる。識別子を属性に持つ |
| `footnoteDefinition` | ブロック、インライン内容のみ         | 本文とは別の場所に住む（§3）         |

参照を `atom` にすることは必須要件。内部にキャレットが入れると番号の一部だけを削除できてしまい、壊れた参照が作れる。

### 2.1 パースは HTML を経由する（2026-08-04 確認）

`tiptap-markdown` は Markdown を直接 ProseMirror ノードにしない。`this.md.render(content)` で **HTML 文字列に落としてから** `elementFromString` で DOM を作り、`DOMParser.fromSchema(…).parseSlice(…)` に渡す（`node_modules/tiptap-markdown/dist/tiptap-markdown.es.js:830-831, 938`）。

この事実が読み込み側の設計を決める。 markdown-it のトークンではなく、**プラグインが出す HTML に合わせた `parseHTML` を両ノードに書く**ことになる。`markdown-it-footnote` の既定出力は `<sup class="footnote-ref">…` と `<section class="footnotes"><ol class="footnotes-list"><li id="fn1" class="footnote-item">…` である。

2 点、帰結がある。

- 公開側の HTML とは別の形になる。 remark-gfm は `<section data-footnotes="" class="footnotes">` と `user-content-fn-1` を出す（§8）。同じ Markdown に対して 2 つの HTML 形が存在するが、エディタが公開側の HTML を読むことはないので衝突はしない。混同しないよう書き留めておくだけでよい
- **レンダラ規則の差し替えは必須である**（2026-08-04 確定。当初は「どちらを採るかはスパイクで決める」と書いていた）。`[^fn-a3f]` は既定では `id="fn1"` としか描かれず、**ラベルが ProseMirror に届かない** — §4.1 の「ラベルは書き換えない」が既定出力のままでは実装できない。ラベルはトークンの `meta.label` にあり、読めるのはレンダラ規則だけ。加えて既定の定義は末尾に `↩︎` の backref リンクを含み、そのままでは著者の文書に入り込む。規則は差し替え可能（プラグインが公開している 8 つ）なので、スキーマが素直に読める形を出させる

## 3. 定義の置き場所 — 文書末の自動セクション

全定義を本文末の専用ノードに集約し、並び順は本文中の参照順で自動整列する。

Markdown の出力形と一致し、印刷物の脚注と同じメンタルモデルになる。加えて、既存の `BlockDragHandle`（ブロックのドラッグ並べ替え）と衝突しない点が大きい — `block-drag-handle.ts` の `DRAGGABLE_TYPES` は明示的な許可リストなので、新しいノードは登録しない限りハンドルを持たない。「参照直下にインライン展開」「サイドパネル」の案は、参照を移動したときに定義がどう追随するかという問いを新たに生むため採らない。

### 3.1 `TrailingNode` を先に直さないと「文書末」が成立しない

**このセクションは、現行コードのままでは実装できない。** `components/editor/trailing-node-extension.ts` は `doc.lastChild` が段落でなければ空段落を追加する。定義セクションを文書末に置けば毎回それが条件に合致し、セクションの後ろに空段落が付き、消しても打鍵のたびに復活する。

採る解: **`TrailingNode` の判定を「定義セクションを除いた最後のノード」に対して行う。** 結果として、定義セクションは常に最後に来て、その 1 つ手前には段落が保たれる。

この形にしないと、退けた 2 案がそれぞれ別の形で壊れる。

**案 1: 判定を素通しにして、定義セクションを末尾段落の直前に置く。** 上のとおり、セクションの下に常に打てる空段落が居座る。そこに書いた本文はエディタでは脚注の下に見え、公開ページでは脚注の上に出る — remark-gfm は出典位置に関係なく脚注セクションを最後に組むためである。エディタと出力で順序が食い違い、しかもその段落は文書の一番下、書き続けるときに人がクリックする場所にある。同種の食い違いは既に一度、切り捨てを選んでいる（`underline` は「publish で黙って消える WYSIWYG の嘘で、直す UI も無い」という理由で無効化されている。`components/PostEditor.tsx` の `StarterKit.configure` 周辺のコメント）。

**案 2: 「最後が定義セクションなら何もしない」とだけ書く。** 定義セクションの直前がテーブルやコードブロックのとき、その下に段落が用意されない。`Gapcursor` は有効（StarterKit の既定で、無効化していない）なのでキャレットの置き場が消えるわけではないが、残るのはギャップカーソルだけになる。テーブル直下はクリックがセルに吸われてギャップカーソルが最も扱いにくい場所であり、`TrailingNode` はギャップカーソルがあってもなお「最終ブロックの下に置き場を用意する」ために作られた拡張である。その存在理由を満たさない。

代償は明示しておく: `TrailingNode` が脚注のスキーマを知ることになる。許容する。判定を汎用化する（「末尾に固定されるノード」という概念を導入する）ほど、そのようなノードは他に無い。

修正箇所は 2 つあり、**両方を同時に直さないと壊れる**: 判定（`doc.lastChild` を見ている条件）と、挿入位置（`doc.content.size`）である。このファイルは 4 つの相互作用（入力ルールの記録、アコーディオンの空トランザクション、Backspace 先着、history 便乗）を抱えていて `efeebc5` で取れたばかりなので、変更は受け入れ基準 9 で押さえる。

### 3.2 スキーマでも末尾を宣言する

`TrailingNode` の修正に加えて、**doc の content 式で `footnoteSection` を末尾限定にする**（例 `block+ footnoteSection?`）。「定義セクションは最後にしか来ない」という不変条件が §6.2 の調停ステップ頼みでなく、スキーマとして宣言される。

**これは `TrailingNode` の修正の代わりにはならない。** スキーマ側だけを入れると、`TrailingNode` の挿入がセクションの後ろで content 式に弾かれるだけで、段落は「セクションの手前」には移動しない — 案 2 と同じ、定義セクション直前に置き場が無い状態になる。順序としては `TrailingNode` の修正が本体で、こちらはその不変条件を二重に守るもの。

## 4. 採番と参照の同一性

- 画面上の番号は**文書順で常に自動採番**する。著者は番号を編集できない
- **番号は属性ではなく decoration として描く**（2026-08-04 実装時に確定）。ノードの属性に書くと、段落を入れ替えるたび・読み込みで振り直すたびに文書が変わったことになり、autosave が走る。アコーディオンが `persist: false` を選んだのと同じ理由 — 読むための操作がデータベースに書いてはいけない。decoration なら番号は文書にも Markdown にも入らない
- Markdown のラベルは**生成した安定 ID**（例 `[^fn-a3f]`）とする。`[^1]` のような連番をそのまま保存すると、段落を入れ替えるたびに全行が差分になる
- **同一の定義を複数の参照から指せる**（2026-08-11、§6.2）。初版は「1 参照 = 1 定義」とし、GFM が許すこの形を「削除時の意味論が一気に複雑になる」として持たなかった。**その根拠は、実装されたコードに対しては成立していなかった。** `footnotePairing` の生存判定は `order.has(label) || !previous.has(label)` で、`order` は現在の文書の参照から作る — つまり同じラベルの参照が 1 つでも残っていれば定義は残り、最後の 1 つが消えたときだけ定義が消える。参照カウントは 1:1 を守るための実装から副産物として既に出ていた。採番も `scanFootnotes` がラベル単位で重複排除しており（`if (!order.has(label))`）、複数参照は同じ番号を持ち後続の番号も詰まらない。`orderedInsertPoint` / `sortDefinitions` は最初の参照の順位で並べ、`incompleteFootnotes` はラベルで畳む。**残っていたのは「参照をコピーしたとき何が起きるか」だけで、それが §6.2 である。**

### 4.1 外部由来のラベルは書き換えない

上の「生成した安定 ID」は**エディタが新しく作る参照に対する規則**であり、読み込んだ文書に対する規則ではない。§5.4 が扱う外部由来の Markdown は `[^1]` や `[^note]` を持って来る。

**それらのラベルはそのまま保持する。開いた瞬間に生成 ID へ書き換えることはしない。**

書き換えると、著者が何も編集していない文書を開いただけで脚注を含む全行が差分になる — これは §4 が連番ラベルを避けた理由そのものであり、避けた先で同じことを起こしては意味がない。

したがって不変条件は「ラベルは常に生成 ID である」ではなく、「ラベルは一度決まったら書き換えない」である。ラベルの体系が 2 つ同居することは受け入れる。ラベルは著者にも読者にも見えない不透明な識別子で、画面と公開ページに出る番号は文書順から常に導出されるため（§4 冒頭）、体系が混ざっても観測できる影響が無い。

2 点、実装時に落とすと壊れる:

- **新規 ID は既存ラベルと衝突させない。** 生成時に文書内の既存ラベルを見て回避する
- 保持したラベルは並べ替えに追随しない。`[^2]` が画面上「1」と表示される状態は正常であり、バグではない。差分を読む人が驚くので、この点だけは記憶しておく

### 4.2 参照の見た目は両面で揃える。定義は揃えない

**参照はエディタと公開ページで同じ `[n]` を同じ色で描く。定義側は揃えない**（2026-08-09 追加）。

§4 は「番号をどう決めるか」だけを書いていて、それがどう見えるかは、どちらの面についても一度も決めていなかった — 破られた規則ではなく、存在しなかった規則である。結果、エディタには青い `[1]` を描く CSS があり、公開ページには参照用の規則が 1 行も無く、@tailwindcss/typography のリンク既定（`--tw-prose-links` は prose-zinc の zinc-900）に落ちて**ほぼ黒の下線付きの `1`** になっていた。参照については、これは揃える。

**ただし揃えるのは装飾だけで、振る舞いの差は残す。** 公開側の参照は本物のリンク（クリックで定義へ飛ぶ）で、エディタ側は atom（`cursor: default`、NodeSelection の対象）である。太さとカーソルはその差が表に出たものなので残す。同じ理由で、エディタ専用の状態表示（`[data-incomplete]`、`ProseMirror-selectednode`、空定義のプレースホルダ）は公開側に持って行かない。

**下線はホバー時のみ**とする（2026-08-09）。prose は全ての `a` に下線を引くが、0.75em の上付き数字では下線が数字にほぼ接し、参照がそれを抱えている文よりも重く見える。青は既に本文から参照を分けているので、下線はポインタのために取っておく。

**このとき `:hover` と `:focus-visible` は必ず対で書く。** 常時の下線を外した時点でホバーが唯一の手がかりになり、そしてホバーはキーボードには存在しない操作である。片方だけにすると、他の誰にも起きない不利益をキーボード利用者だけが被る。検証も対で行うこと — `.focus()` ではなく実際の Tab で確かめる。`:focus-visible` は「ブラウザが表示に値すると判断したフォーカス」にのみ一致する規則で、スクリプトからのフォーカスはまさにそれが外してよい場合だからである。

**定義末尾の `↩`（backref）も参照と同じ扱いにする**（2026-08-09）。同じ青、同じホバー限定の下線。これは位置ではなく役割で括っている — `↩` は定義の見た目の一部ではなく、参照の往復の帰り側だからである。定義側のリストを prose のままにする決定（下記）とは矛盾しない。行きと帰りで見た目の規則が違うと、対になっているものが対に見えない。記号 1 文字に常時下線が付くと記号より線のほうが目立つ、という理由も参照側より強く効く。

`↩` については `:focus-visible` の重みも参照側より大きい。参照には角括弧付きの数字という「これはナビゲーションだ」という形があるが、`↩` にはそれが無く、フォーカスリングと下線だけが手がかりになる。

**定義側は公開ページの見た目を変えない**（2026-08-09、実物を見て確定）。エディタは `[1]`、公開ページは `<ol>` の既定マーカーで `1.`、インデントも prose のまま — この食い違いは残す。「両面で揃える」を定義にも延ばすことは一度やって戻した（`::marker` の `content` と、`--footnote-marker` 相当のインデント予約の両方）。公開側には既に落ち着いた見た目があり、しかもそちらは読者が見る面である。著者しか見ないエディタに合わせるために読み物のリストを動かすのは、揃える理由として弱い。

したがって不変条件は「番号の見た目は常に両面で一致する」ではなく、**「参照は一致させ、定義は各面の文脈に従う」**である。定義側の食い違いは見落としではなく決定であり、次に気づいた人が「揃っていない」を理由に揃えに行かないよう、ここに書いておく。

実装は `app/globals.css` の参照 2 ブロックのみ。検証は `e2e/public-footnote.spec.ts`（定義側が prose の `1.` のままであることも含めて押さえてある）。

## 5. 編集操作と「空の定義」の扱い

### 5.1 基本操作

| 操作                            | 要件                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 挿入                            | §9 の 2 経路。参照を挿入すると同時に空の定義を作る。**キャレットは本文に留まる**                       |
| 参照の削除                      | **最後の 1 つなら**対応する定義も削除する。1 回の undo で両方戻ること（単一トランザクション）          |
| 定義の削除                      | 単独では削除させない。参照側からのみ消える                                                             |
| 並べ替え                        | 本文の参照順が変われば、番号と定義の並びが追随する                                                     |
| 取り消し                        | 変換直後の Backspace 一回で元の文字列に戻る（入力ルールの undo は ProseMirror の既定の振る舞いに乗る） |
| 定義内の Enter                  | **分割せず hard break にする**（2026-08-05 追加 — 下記）                                               |
| 定義の端での Backspace / Delete | **連結させない。通知して拒否する**（2026-08-05 追加 — 下記）                                           |
| 定義の右側のクリック            | **注釈の末尾にキャレットを置く**（2026-08-09 追加 — 下記）                                             |

キャレットを定義へ飛ばさないのは、脚注が「本文を書きながら補足を思いつく」場面の道具であり、変換のたびに文脈が切れるのを避けるため。代償として空の定義が残りやすくなるので、5.2 で担保する。

**定義内の Enter は分割させてはならない**（2026-08-05 実測）。ここも §6 冒頭が警告している「同じイベントに別々の規則が答える」形の見落としで、要件側に Enter の扱いが書かれていなかった。ProseMirror の既定 Enter は `footnoteDefinition` を分割するが、分割は属性をコピーするので両方が同じラベルを持つ — セクションに同じ番号の定義が 2 つ並び、Markdown にも `[^a]:` 行が 2 本出る。`markdown-it` の `footnote_def` は同じラベルに対して最後の定義を採るので、再読み込みで前半が消える。実測: `[^a]: 注釈` + `[^a]: テキスト` が、注釈の文字を失って「テキスト」1 つになった。単なる表示の乱れではなくデータ消失である。

**代わりに hard break にする。** テーブルセルが既に出している答え（issue #8）と同じで、理由も同じ — どちらも「シリアライズ先の Markdown の行形式がブロック構造を持てない」ためにインライン限定になっている。新しい形を持ち込むわけでもない: `Shift+Enter` は以前からここで hard break を作れており、`[^a]: 注A\` と継続行は同じ hardBreak ノードとして往復する（実測）。Enter を 3 つ目の経路としてその形に合流させるだけである。

キーマップは文書全体に張られるので、**定義の外では必ず false を返して baseKeymap に渡すこと**。本文の Enter を飲み込むのは、直そうとしているバグより遥かに悪い。

**定義の端での Backspace / Delete は連結させてはならない**（2026-08-05 実測）。Enter の分割のちょうど裏返しで、同じ穴（定義内のキー操作が要件に書かれていなかった）から出た 2 件目である。連結は片方のラベルだけを残すので、2 つ目の注釈の文字が 1 つ目のラベルの下に移る。実測: `[^a]: 注A` と `[^b]: 注B` が `[^a]: 注A注B` になり、`[^b]` は空になって公開が拒否される状態になった。1 つ目の定義の先頭では連結が起きないが、これはセクションが `isolating` である副作用にすぎず、規則としてはどこにも書かれていなかった。

**通知して拒否する。** 拒否は文書を変えないので、通知が無ければ壊れたキーと区別できない — 配置ガードと同じ扱いにする（「脚注を削除するには、本文中の参照を削除してください。」）。これは同時に死んだキーを 1 つ無くす: 注釈を全消しした後の定義で Backspace は今まで完全な無反応だった。

**定義の右側をクリックしたら注釈の末尾に入ること**（2026-08-09 実測・修正）。定義は flex 行だった。マーカーが `flex: none` のアイテムで、注釈は隣の匿名アイテム — そして匿名 flex アイテムは中身の幅に縮む。実測で、幅 766px の定義に対して注釈のテキストボックスは 103.9px しかなく、残り約 617px はどの行ボックスにも属していなかった。そこをクリックするとブラウザは当てるテキストを持たないので `caretRangeFromPoint` がコンテナを返し、ProseMirror がオフセット 0 として解決する — キャレットが末尾ではなく先頭に入る。エディタの他のどのブロックとも違う挙動である。

**マーカーを流れの外に出し、定義を普通のブロックにする。** `display: flex` + `gap` をやめ、`padding-left: calc(marker + gap)` と `::before { position: absolute; left: 0; width: marker }` にする。注釈の行ボックスが行全体に伸びるので、右側のどこをクリックしても末尾に入る。見た目は変わらない — テキスト左端・マーカー幅・折り返しのぶら下げインデントを変更前後で実測し、すべて同一だった。

この flex 行が代償を払わせたのは 2 度目である。§5.2 のプレースホルダが `position: absolute` なのも、素の flex アイテムにすると書かれた注釈の左端より数ピクセル右にずれたからで、同じ縮みを 1 つの規則だけ逃がして対処していた。今回それを仕組みごと無くした。

**失敗の仕方が変わった点だけ記憶しておく。** flex ではマーカーが幅を持つアイテムだったので、桁あふれは注釈を右へ押した（ずれとして見える）。流れの外では何も押さないので、あふれたマーカーは注釈の先頭に重なる。天井（`[999]`）は同じだが症状が違うので、検証も「押されていないか」ではなく「予約幅を超えていないか」を測る（`e2e/editor-footnote-definition-layout.spec.ts`）。

**「空になったら脚注ごと削除」は採らない**（検討済み）。参照は本文の別の場所にあり画面外かもしれず、しかも Backspace はオートリピートするので、注釈をキー押しっぱなしで消した著者がそのまま参照まで消してしまう。空の定義は打ち直しの途中で必ず通る一時状態でもあり、`lib/posts-write.ts` の autosave が「一瞬空になったタイトル」で既存タイトルを上書きしないのと同じ理由で、意図として読んではならない。空の定義は残し、§5.2 の 3 層で担保する。

**範囲選択の融合は `isolating` で解決した**（2026-08-05）。上のキーマップはキャレットが端にある場合しか見ないので、2 つの定義にまたがる範囲選択の削除には届かず、実測で定義が融合していた（`footnoteDefinition("注")` 1 つになり、`[^b]` は定義ノードごと消えた）。これは callout とコードブロックについて §6 が記述しているのと同じ欠陥で、`isolating-boundary.ts` がノードの `isolating` フラグを見て 7 つの入口すべてでクランプしている。したがって規則を 6 つ目として足すのではなく、`footnoteDefinition` をそのクランプが守るノードの 1 つにするのが解である。セクションも isolating なのでテーブルと同じ 2 階層になるが、`isolatingCutDepth` は内側を採るので既に対応済みの形である。

**ただし `isolating` を付けると hard break が死ぬ。** `@tiptap/extension-hard-break` の `setHardBreak` はキャレットの親ノードが isolating なら無条件で false を返す（`dist/index.js:39`。目印は `selection.$from.parent.type.spec.isolating`）。定義は「isolating なノード」と「キャレットのいる textblock」が同一なのでこれに当たる — 実測で Enter が黙って無反応になり、続けて打った文字がそのまま繋がった。テーブルのセルがこれを免れているのは、セルの中の textblock が別の段落ノードだからである。

したがって Enter は `setHardBreak` ではなく hardBreak ノードの直接挿入で行う。**`Shift+Enter` と `Mod+Enter` も同じ経路に通すこと** — `HardBreak` はこの 2 つを `setHardBreak` に直結しているので、放置すると本来の改行キーが 2 つとも死ぬ（テーブルが 3 キーすべてを自前に通しているのと同じ理由）。

**最後の 1 つを消すときはセクションごと消すこと**（2026-08-04 実測）。`footnoteSection` の content は `footnoteDefinition+` なので、中身が空のセクションは ProseMirror が組み立てられる文書ではない。最後の定義だけを消す削除は黙って何も起きない — 参照は消えたのに定義が残る、という形で観測した。生き残る定義が 0 になる場合はセクションの範囲を消す。

### 5.2 空の定義を残さない仕組み

3 層で担保する。これは新しい仕組みではなく、`app/actions/posts.ts` に既にある方針（必須項目の検証は公開時に行い、autosave は寛容にして作業途中を失わせない）にそのまま乗る。

1. **執筆中 — 本文側で未完了が見える**
   定義側のプレースホルダだけでは足りない。著者が見ているのは本文だから、参照の見た目そのものを未完了状態にする（番号が確定していない参照として、通常の上付き番号と区別できる表示）。「まだ 2 つ空のままだ」が本文を書きながら視界に入ること。

   **その「だけでは足りない」と言っていたプレースホルダ自体が、実装されていなかった**（2026-08-05 に追加）。この項は参照側の表示を足す論拠として定義側を引き合いに出しているが、引き合いに出された側が存在せず、注釈を書こうとして定義に立った著者には未完了であることを示すものが何も無かった。番号と同じく decoration で `data-empty` を渡し、CSS の `::after` で描く — **空の ProseMirror textblock は末尾に `<br>` を持つので `:empty` では当たらない**。位置は `position: absolute` で、その `<br>` が flex アイテムとして幅を持つため、素の flex アイテムにすると書かれた注釈の左端より数ピクセル右にずれた（当時のマーカーの `min-width` が防いでいたずれの再来になる）。マーカーの予約幅と gap は custom property にして、レイアウトと位置指定が同じ数値を見るようにしてある。なお、ここで逃げていた flex 行そのものが 2026-08-09 に無くなった（§5.1 の「定義の右側のクリック」）。絶対配置は残す — 今度は flex を避けるためではなく、注釈の行と同じ 2 つの custom property から位置を決めるためである。

2. **下書き保存・autosave — 許容する**
   空のまま保存できないと執筆を中断できない。既存の寛容な方針を適用する。
3. **公開 — 拒否する**
   空の定義が 1 つでもあれば公開させない。これが「空の定義にならない」の実質的な保証。公開は既に必須項目を検証している地点なので、検証を 1 つ足すだけで済み、エラーは既存の `PostFormState` の経路で返せる。**ただし検証の対象は「空の定義」そのものではない — 理由と実際に見るものは §5.3 に書く。**

### 5.3 公開時の検証が必須である技術的理由

当初の理由は「**空の定義は Markdown の往復で生き残らない可能性が高い**」だった。`[^fn-a3f]: ` のように内容が空の定義行はパーサに落とされ得て、そうなると参照だけが残って孤児化する、という見立てである。

**この見立ては、エディタ側については誤りだった**（2026-08-04、スパイクで実測）。`[^x]:` も `[^x]: ` も markdown-it-footnote は問題なく読み、参照は定義に結びついたまま残り、往復も不動点になる。空の定義は少なくともエディタの経路では「壊れる入力」ではない。

**それでも公開時の検証は残す。** 理由が変わるだけである:

- 空の注釈は読者にとって意味を成さない。公開前に潰す価値は見た目の理由だけで十分にある（§5.2 の第 1 層・第 3 層はこの理由で立つ）
- 公開側（remark-gfm）が空の定義をどう扱うかは**未測定**。エディタ側で生き残ることは分かったが、`lib/render.ts` の経路は別のパーサであり、同じ答えとは限らない

検証の実装が「空の定義」ではなく `body` の文字列を見るという点は変わらない。以下はその理由。

そしてこの事実が、検証を何に対して書くかを決める。 公開は `app/actions/posts.ts` のサーバーアクションで、受け取るのは `contentSchema` を通った文字列群 — 本文については `body: z.string()`、すなわち **Markdown のテキストだけ**である。ProseMirror の文書はそこに存在しない。空の定義行が直列化で落ちているなら、サーバーに届く時点でそれは空の定義ではなく**定義を失った参照**になっている。

したがって:

- **検証はサーバー側（公開経路）に置く。** 送信前のクライアント検証にはしない。autosave と公開で本文の扱いが分かれている既存の構造に素直に乗り、エディタを経由しない経路も同じ規則で守れる
- **見るのは `body` の文字列であり、判定は「定義の無い参照、または定義の内容が空の参照」**とする。空定義が落ちた場合（前者）と生き残った場合（後者）の両方を 1 つの規則で捕まえる
- エラーは `PostFormState` の既存経路で返す。どの脚注かを著者が特定できる文言にすること

「空の定義があれば拒否する」という §5.2 の言い方は著者から見た仕様の説明であって、実装が書く述語ではない。ここを取り違えると、サーバーに見えないものを検証しようとして詰まる。

### 5.4 外部由来の異常入力

エディタ外で書かれた Markdown を読み込む経路があるため、以下を扱う。

- **孤児定義**（参照のない定義）: 末尾に残したうえで `useEditorNotice` で通知する。実装済み（2026-08-04）。 ラベルごとに 1 回だけ報せる — 孤児を抱えた文書は「出来事」ではなく「状態」なので、トランザクションごとに出すと打鍵のたびにトーストが本文にかぶる。孤児でなくなったラベルは忘れるので、参照を書いて消せばまた報せる
- **未定義参照**（定義のない参照）: 参照を残し、空の定義を生成して補う。以後は 5.2 の対象になる

### 5.5 孤児定義の救済は第 3 段階に置けない（2026-08-04、スパイクで判明）

**`markdown-it-footnote` は孤児定義を削除する。** `footnote_tail` は全定義をトークン列から私有のマップに抜き出し、参照が 1 つも無ければ早期に return する（`if (!state.env.footnotes.list) { return }`）。参照されなかった定義は、放出ループが `list` を歩くため二度と戻らない。実測: `本文\n\n[^x]: 注釈\n` は `本文` だけになった。注釈の文字が消える。

これは §5.4 の孤児定義の扱いと正面から衝突するだけでなく、現状（平文として保持するガード）より悪い。プラグインを入れた瞬間にこのデータ消失が生まれるので、**救済を第 3 段階に先送りできない。プラグインと同じ段階に入れること。**

スパイクでは実装済み。`footnote_tail` の前後に公開 API の 2 規則（`ruler.before` / `ruler.after`）を挟み、走る前に定義を捕まえ、走った後に参照されなかったものを footnote トークンとして戻す。結果、孤児定義は参照を持たない `footnoteDefinition` ノードになり、`[^x]: 注釈` としてそのまま往復する — §5.4 が求める状態そのものである。残る作業は `useEditorNotice` での通知だけ。

**戻す位置はセクションの内側でなければならない**（2026-08-04、ブラウザ確認で発覚）。定義が住めるのは定義セクションの中だけなので（§3.2 の content 式、および `footnoteDefinition` が `block` グループに属さないこと）、`footnote_block_close` の後ろに足すとセクションの外に出て、ProseMirror が置き場を見つけられず再び削除される。

**この誤りは、参照付きの脚注が同じ文書に無いと現れない。** 参照が 1 つも無ければ `footnote_tail` はラッパーを出さずに早期 return し、ProseMirror が欠けたセクションを自分で補うので孤児は生き残る。普通の脚注を 1 つ足した途端にラッパーが存在し、孤児はその後ろに落ちて注釈の文字が消える。**スパイクの受け入れテストは単独ケースしか見ておらず、しかも「文字が含まれるか」しか確認していなかったので通っていた。** 文書構造まで確認すること。

## 6. 既存ガードとの関係

ここは「後で考える」で済ませてはならない。同種の見落としが過去に 2 回、実バグになっている（テーブルの clamp が内側の isolating を取り違えた件、drop/paste/Enter がセル内で別々の規則に答えていた件）。

| 場所                                                 | 判断                                                                                           | 理由                                                           |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| テーブルセル内（`table-cell-rules.ts`）              | 参照を置けない                                                                                 | セルは Markdown のパイプ形式を壊しやすく、既に専用ガードがある |
| コードブロック内（`code-block-extension.ts`）        | 参照を置けない                                                                                 | テキストのみを保持する場所                                     |
| callout 内（`callout-slice-guard.ts`）               | 参照を置ける。定義は callout の外（文書末）に出る                                              | 本文の一部として扱う                                           |
| アコーディオンのタイトル内（`details-extension.ts`） | 参照を置けない（§6.5）                                                                         | `detailsSummary` が `text*` で、スキーマが拒む                 |
| アコーディオンの本文内                               | 参照を置ける。定義は文書末に出る                                                               | callout と同じ、本文の一部                                     |
| `isolating-boundary.ts`                              | 脚注のための追加はしない。ドロップは §6.1 の経路を通るので孤児は生まれない                     | 1 つの事象に 2 つの規則を置かない（§6.4）                      |
| 貼り付け・ドロップ                                   | **参照は自分の定義をクリップボード経由で運ぶ**（§6.1）。運んで来なかった参照だけを平文に落とす | 文書内の複製を壊さず、定義なしの参照も流入させない             |

判定には `components/editor/selection-scan.ts` の `selectionTouches(state, ...typeNames)` が使える（選択が特定ノードに触れているかを答える既存の道具）。

**判定は必ず state 側の選択を読むこと。** クリックによるキャレット確定は `state.selection` に対して 20ms 遅れる。同じ罠で過去に「貼り付けが効かない」バグを出している。

### 6.1 参照は定義を持って移動する

素朴な規則（「スライスに定義が無ければ参照を平文に落とす」）は、**外部からの貼り付けだけを想定すると正しく、文書内の貼り付けに適用すると壊れる。**

定義は文書末の別セクションに住む（§3）。だから脚注を含む段落を選択してコピーしても、**スライスに定義は入らない**。素朴な規則のままだと、脚注入りの段落を複製するというごく普通の操作で参照が平文に落ちる。切り取りはさらに悪い: §5.1 により切り取った時点で定義が消え、貼り付けでは参照が平文になるので、注釈が丸ごと失われる。§9 が代替導線として案内している「選択 → 切り取り → 脚注作成 → 貼り付け」も、この規則の下では成立しない。

**採る解: 参照ノードがコピー時に自分の定義の内容を抱えて出て、貼り付け時にそれを展開する。**

- `transformCopied` — スライス内の各参照に、対応する定義の内容と元のラベルを載せる
- `transformPasted` — 載っていればその参照を残す。載っていなければ平文に落とす
- **ラベルの確定と定義セクションの再構成は、貼り付け時ではなく調停ステップで行う**（§6.2）

### 6.2 ラベルを決めるのは貼り付けではなく調停ステップ

`transformPasted` はスライスしか見ない。文書に入った後の状態を知らないので、そこでラベルを確定させると常に新規発行するしかなく、切り取って貼り直しただけでラベルが変わる — §4.1 の「ラベルは一度決まったら書き換えない」に反し、位置を変えただけの編集が Markdown 上は別の脚注に見える。

§3（参照順で定義を自動整列）と §4（文書順で自動採番）は、どのみち文書全体を走査して定義セクションを組み直すステップを要求している。ラベルの確定もそこに置く:

**2026-08-11 に規則を反転した。以下は現行。** 問うのは**定義**であって参照ではない（旧規則は逆で、参照だけを数え、定義は数えなかった）。

- **同じラベルの定義があり、その内容が運ばれて来た注釈と一致する** → そのラベルをそのまま使い、定義は作らない。同じ脚注だからである。これが**共有**の全体で、コピー＆貼り付けが「1 つの注釈への 2 つ目の参照」を作るジェスチャになる
- **同じラベルの定義があるが、内容が違う** → 新しい ID を発行する。偶然の衝突である（下記）
- **そのラベルの定義が無い** → そのラベルをそのまま使い、運ばれて来た注釈から定義を作る。切り取り → 貼り付け（移動。定義は参照と一緒に消えている）と、そのラベルを見たことのない文書への貼り付けが、ここに落ちる

**内容が違うのに同じラベル、を「衝突」として扱うのは、著者の文字を失わないため。** ラベルは不透明だが、全てが生成 ID なわけではない — §4.1 が外部由来のラベルを保持するので、2 つの記事がそれぞれ `[^1]` を持っている状況は偶然ではなく普通である。ラベルだけで一致と見なすと、貼り付けた参照の下に貼り付け先の注釈が並び、運んで来た注釈は捨てられる。共有と衝突を分ける線はここに引く。

**移動が壊れないのは、この形が「定義の一致」で答えるからである。** ドラッグでの移動は削除と挿入が単一トランザクションなので、着地の時点で元の定義がまだセクションに残っている。旧規則ではこれが罠で、定義を「ラベルが埋まっている証拠」と数えると移動のたびに新しいラベルが発行され、定義が二重になり元の定義が孤児になった（2026-08-04 実測）。現行では同じ定義がそこにあることがそのまま答えになる。

**発行はスライス内のラベルごとに 1 回で、参照ごとではない。** 1 つのスライスに同じラベルの参照が 2 つあるとき（＝段落内で 1 つの注釈を共有している状態）、参照ごとに発行すると別々のラベルが当たり、同じ文字を持つ独立した 2 件に割れる。`Map<運ばれたラベル, 発行したラベル>` をスライス内で使い回す。

**注釈の文字で比べることは、出自を追跡しないための選択である。** `pendingNote` の隣にエディタのセッション ID を載せれば厳密に判定でき、この節の末尾が退けている「出自を追跡する規則」には当たらない — 属性を持たないスライスは既に平文に落ちるので、追跡できない経路が破綻を持ち込む形にならない。それでも採らないのは、文字の比較が誤るのは2 つの注釈が同じ文字を持つときだけで、そのとき共有と複製は読者にも著者にも区別が付かないからである。属性 1 つと配線を、観測できない差のために払わない。

**取りこぼす形を 1 つ書いておく**（バグではなく決定）。コピーした後に定義を編集してから貼り付けると、運ばれた注釈は編集前の文字なので一致せず、共有ではなく新しい脚注になる。同じクリップボードでも 1 回目と 2 回目で結果が変わる。`transformCopied` はコピーの時点の定義を読むので原理的にそうなる。非破壊（文字は失われない）で、頻度も低いため許容する — 次に気づいた人が「共有されないことがある」をバグとして追わないよう、ここに書いておく。

**「衝突」は、調停の時点で貼り付け先の文書に存在するラベルとの衝突だけを指す。** スライスがどこから来たか（同じ文書か、別のタブか、公開記事の原文か）は問わない。別文書から運ばれたラベルが貼り付け先でたまたま空いていればそのまま使う — ラベルは不透明な識別子で、意味は持たない（§4.1）。出自を追跡する規則にすると、追跡できない経路（外部からの貼り付け）で必ず破綻する。

### 6.3 置ける場所の判定が先、定義の復元は後

**§6 の配置ガード（テーブルセル内・コードブロック内は参照を置けない）を先に問う。** 定義を抱えた参照であっても、セルやコードブロックに着地するなら平文に落とし、抱えていた定義は捨てる（定義セクションに足さない — 参照の無い定義を自分で作ることになる）。

順序を書かずに済ませると、1 つの貼り付けに対して「平文に落とす」と「定義を復元する」の 2 つの規則が別々に答える。§6 の冒頭が挙げている過去 2 件の実バグは、まさにその形をしていた。

**実装（2026-08-04、当初案は誤りだったので訂正）**: 当初ここには「拒否は `transformPasted` の中で判定する」と書いた。**貼り付けには正しく、ドロップには成立しない。**`transformPasted` が走る時点で `view.state.selection` はまだドラッグ元の範囲であり、着地先ではない。選択に対して問うと別の場所について答えることになり、実測では脚注が表のセルにそのまま入った。

採る形は 2 つに分かれる:

- **貼り付け**: 着地後の appendTransaction で、参照の位置そのものに対して配置を問う（`hostRefusalAt`）。ここで初めて着地先が分かる。拒否した参照は平文に落とし、抱えていた注釈は捨てる
- **ドロップ**: `handleDrop` でジェスチャごと拒否する。ドロップは移動なので、着地先で平文に落とすと移動元が削除された後であり、定義が参照を失って孤児になる — 何もしなかった場合より悪い文書になる（実測）。拒否すれば移動元も削除されない。テーブルの drop guard が採っているのと同じ形

どちらも「配置の判定が先」という §6.3 の原則は変わらない。変わったのはどこで問えば着地先が分かるかである。

**平文化は `transformPasted` の中で済ませること**、つまり §6.2 の調停ステップより前に。そうすれば参照はそもそも文書に入らず、調停ステップはそれを見ない。落とすのが遅れて調停まで生き延びると、今度は §5.4 の「定義のない参照には空の定義を生成して補う」が拾ってしまい、捨てたはずの脚注が空の定義として復活する。

### 6.4 ドロップも同じ経路を通る

prosemirror-view の drop ハンドラは `parseFromClipboard` を呼び、エディタ内のドラッグでもドラッグ中のスライスに `transformPasted` を適用する（`prosemirror-view` dist の 3812・3815 行で確認）。**したがってドロップは §6.1〜§6.3 でそのまま処理され、脚注のための追加ガードは要らない。**

`isolating-boundary.ts` に「参照だけが移動して定義が孤立する経路を塞ぐ」規則を足してはならない。孤立はここで既に起きない。塞ぐ規則を重ねると、同じドロップに 2 つの規則が答える状態を自分で作ることになる。

### 6.5 アコーディオンのタイトルには置けない（2026-08-08、実測）

脚注とアコーディオンは 4 日違いで入り、**互いを見ていなかった**。この表にアコーディオンの行が無かったのはそのためで、判断を先送りしたわけではない。

**拒む理由は Markdown ではなくスキーマである。** `detailsSummary` は `@tiptap/extension-details` で `content: "text*"` と宣言されている。このエディタのテキストブロックのうちインラインの atom を受け取れないのは `codeBlock` とこれの 2 つだけで（全テキストブロックに対して `contentMatch.matchType(footnoteReference)` を問うて確認、`components/editor/footnote-placement.test.ts` で固定してある）、ガードが無いと**挿入は静かに失敗せず、ProseMirror の整形アルゴリズムがアコーディオンを 2 つに割って場所を作る**。タイトルの途中にキャレットを置いて実測:

```
details(summary("タイトル"), content(p("本文")))
  → details(summary("タイ"), content(p([^1], "トル")))
  + details(summary(""),     content(p("本文")))
```

タイトルの後半が本文に落ち、空のタイトルを持つ 2 つ目のアコーディオンが元の本文を抱えて生える。テーブルセルの拒否（単に置けないだけ）より悪い壊れ方である。

保存側も同じ結論を出す。タイトルは `<summary>…</summary>` という生 HTML の 1 行として往復するので（アコーディオン要件 §2.1）、そこに書かれた `[^label]` は HTML ブロックの内側にあり、読み込み時の markdown-it-footnote にも公開ページの remark-gfm にも届かない。加えて `serializeDetails` はタイトルを `textContent` で読むため、参照ノードは保存の時点で消える。仮にスキーマが通しても静かな消失になる。

**経路は 3 つあり、既存のガード 2 つでは 2 つしか塞げない。**`placementRefusal` に 1 行足せばショートカットと `[^` 入力規則が、`hostRefusalAt` に 1 行足せばドロップが塞がる（`handleDrop` は `posAtCoords` を挿入前の文書に対して問うので、タイトルがまだそこにあり、祖先として見つかる）。

**貼り付けだけは着地後の修復が原理的に効かない。**§6.3 が採った形は「参照が着地してから、その位置に対して配置を問う」であり、セルやコードブロックではそれで足りる — 参照が実際にそこに着地するからである。タイトルには着地しない。`text*` が受け取らない以上、参照は必ず引き裂かれた本文の段落に落ち、そこには `detailsSummary` という祖先が無い。実測（スライスの 3 形状すべて）: 文書は裂けたうえで `hostRefusalAt` は `null` を返す。**修復が遅いのではなく、盲目である。**

したがって貼り付けはスライスが置かれる前に答える必要があり、着地先がその時点で分かるフックは `handlePaste` だけである（`transformPasted` はドロップ経路でも走り、そこでは選択がまだドラッグ元を指す — §6.3 の訂正そのもの）。そこで参照を平文に落として自分で dispatch する。**落とすのであって拒否しない**のは §6.3 のままで、貼り付けは移動元を消さないので語は着地してよい。平文 `[^label]` は `text*` に収まるので、平文化したスライスはタイトルを裂かない（実測）。

一般化すると: **「着地後に位置を問う」修復は、拒否したいノードがその位置の祖先に残る場合にしか成立しない。**内容表現が受け取らない場所では、参照はそこに留まらないので祖先に現れない。

**名指しするのは `detailsSummary` であって `details` ではない。** 本文は `block+` → 段落 → `inline*` なので脚注はそのまま置け、既にそう動いている。ここを `details` で塞ぐと動いているものを壊す。

支援する側に倒すなら、タイトルを `inline*` に広げ、タイトル専用のシリアライザを書き、公開側のレンダラがそこにマーカーを描けるようにする必要がある。それは機能追加であってこのバグの修正ではない。

| ---------------------------------- | ---------------------------------------------------------------------------------- |

### 7.2 プラグインを入れるとガードは自動的に無害化する

プラグインは `md.block.ruler.before('reference', 'footnote_def', …)` で登録する（`index.mjs:349`）。定義行は `reference` に届く前に `footnote_def` が取るので、`keepFootnoteDefinitionsLiteral` は呼ばれても何もしなくなる。

**ただしこれは `footnote_def` が受け取る形に限った話で、ガードを撤去してよいという意味ではない。§7.4 を必ず読むこと。**

したがって §7 冒頭の順序の警告は、片方向にだけ効く:

- **ガードだけ先に外す → 危険**（元のデータ消失が復活する）
- **プラグインを先に入れる → 無害**（ガードは残っていても不活性）

スパイクは後者の順序で始められる。

プラグインが登録する規則は 4 つある（`index.mjs:349-352`）。

| 規則              | 登録先                                  | 扱い                                                       |
| ----------------- | --------------------------------------- | ---------------------------------------------------------- |
| `footnote_def`    | `block.ruler.before('reference')`       | 定義行。本命                                               |
| `footnote_ref`    | `inline.ruler.after('footnote_inline')` | 本文中の `[^label]`。本命                                  |
| `footnote_inline` | `inline.ruler.after('image')`           | `^[…]` 記法。**§1 の非目標。無効化するか扱いを決めること** |
| `footnote_tail`   | `core.ruler.after('inline')`            | 定義を末尾に集めて採番する。**孤児定義を削除する（§5.5）** |

### 7.3 スパイクの結果（2026-08-04、実測）

`components/editor/footnote-extension.ts` と `e2e/editor-footnote-spike.spec.ts`（後者は `d60b185` で削除済み — 第 1 段階の実装がスパイクをそのまま吸収したため。以下はその時点の測定結果であり、いま同じファイルを探しても無い）。Markdown 層だけを登録し、定義セクション・ガード・導線・スタイルはいずれも入れていない。**往復は成立した**（8 ケース、うち不動点の確認を含む）。

確認できたこと:

- 素の GFM 脚注として往復する。`\[^1\]` のエスケープは消え、2 周目は不動点になる
- **ラベルは書き換わらない**（§4.1）。`[^fn-a3f]` が保存後もそのまま
- 文書末に脚注があっても往復する
- 空の定義でも参照が孤児にならない（§5.3 の訂正の根拠）
- 孤児定義の文字が残る（§5.5 の救済を入れた後）

文書の記述を 3 つ訂正した: §1（`^[…]` はデータ消失ではなく記法の書き換え）、§5.3（空の定義はパーサに落とされない）、§5.5（孤児定義は逆に削除される — 新規）。

**設計判断が 1 つ、選択肢から必然に変わった。** §2.1 は「既定の HTML に合わせるか、レンダラ規則を差し替えるか」をスパイクで決めるとしていたが、差し替えは必須である。`[^fn-a3f]` は既定では `id="fn1"` としか描かれず、ラベルが ProseMirror に届かない。§4.1 の不変条件は既定出力のままでは実装できない。ラベルはトークンの `meta.label` にあり、そこを読めるのはレンダラ規則だけである。

**新しく分かった落とし穴**: 定義の内容はブロックとしてトークン化されるので `<p>` に包まれて届くが、**ProseMirror は inline 専用ノードとの不一致を平坦化しない**。定義を早じまいして本文を兄弟の段落に置き（`doc(…, footnoteDefinition, paragraph("注釈テキスト"))`）、空の定義と迷子の行として保存された。`parse.updateDOM` で `<p>` を剥がす — アコーディオンの `updateDetailsDOM` と同じ手当て。

**§3.1 は実測で裏付けられた。** 定義が文書末に来ると `doc(…, footnoteDefinition("注釈テキスト"), paragraph)` となり、`TrailingNode` の段落が定義の下に付く。

スパイクの範囲外（意図的に入れていない）: 定義セクション（§3）、`TrailingNode` の修正（§3.1）、末尾限定の content 式（§3.2）、ガード群（§6）、導線（§9）、スタイル。定義は暫定的にトップレベルのブロックとして置いている。

### 7.4 ガードは撤去できない — プラグインが拒否する形が残る（2026-08-04 実測）

§7.2 の「ガードは呼ばれても何もしなくなる」は**整形式のラベルに限った話**であり、撤去してよいという意味ではなかった。

`footnote_def` は**ラベルに空白があると受け取らない**（`index.mjs` の走査が空白で `return false` する）。行はブロックルールに戻され、`reference` が拾い、元のデータ消失がそのまま復活する。実測:

```
入力: 本文[^a b]\n\n[^a b]: 注釈テキスト
ガード撤去時の出力: <p>本文<a href="%E6%B3%A8%E9%87%88%E3%83%86%E3%82%AD%E3%82%B9%E3%83%88">^a b</a></p>
```

注釈の文字が href に消える — 2026-08-02 に測ったバグと同じものである。

したがって §7 の 2 案のうち「孤児ケース専用に縮小」を採る。 コード自体は変更していない（`reference` に対する `[^` 始まりの辞退は、ルール順序によって既に「プラグインが拒否した行だけ」に絞られている）。変えたのは役割の記述とテストで、テストはプラグインと同居させた状態で、ガードが今も守っている形だけを見るようにした。

## 8. 公開側

- remark-gfm の既定出力（`<section data-footnotes>`）をそのまま使う
- 目次（`lib/rehype-collect-toc.ts`）に脚注セクションを載せない。2026-08-04 に実装済み。 remark-gfm はセクションに読み上げ専用の `<h2>Footnotes</h2>` を付けるので、放置すると日本語記事の目次に著者が書いていない英語の項目が現れる（実測）。エディタが本物の脚注記法を保存し始めるまで、この見出しが収集器の前に来たことは一度も無かった
- 本文 ⇄ 定義の相互ジャンプは `lib/rehype-clobber-fragment-links.ts` が担保する
- **同一定義への複数参照は公開側に何も要らない**（2026-08-11 実測）。remark-gfm は両参照を `1` と描き、id を `fn-a` / `fnref-a` / `fnref-a-2` と振り、定義に backref を 2 本（`↩` と `↩<sup>2</sup>`、`aria-label="Back to reference 1-2"`）出す。clobber prefix は id と href の両側に揃って付く。CSS も追加不要 — 2 本目の入れ子 `<sup>` は 0.85em × prose の 0.75em で描かれるが、GitHub の見た目と同じなのでそのままにする

### 8.1 エディタ側は「飛ばす」のではなく「示す」（2026-08-05）

公開側の相互ジャンプに対応するものをエディタにも置くか検討し、**移動はさせず、対の定義をハイライトするだけ**とした。参照を選択している間、その定義に `data-paired` を渡して色を付ける。

理由は 3 つある。

- **戻り導線が無い。** 公開ページが飛べるのは backref があり、失うキャレットが無いからである。エディタで定義へ飛ぶと、著者は書きかけの文の途中に戻る手段を持たない。§5.1 が挿入時にキャレットを本文に留めているのと同じ理由で、著者自身が押したクリックであっても、戻れないなら動かさないほうがよい
- **クリックは既に埋まっている。** 参照は selectable な atom で、クリックすると NodeSelection ができる。これが §5.1 の「削除は参照側からのみ」を成立させている唯一の導線で（実測: クリック → Backspace で参照も定義も消える）、ジャンプに割り当てると潰れる。ハイライトはその同じ選択に乗るので、何も奪わない
- **表示だけなので decoration で足りる。** 文書が変わらず、autosave も undo 履歴も汚れない（§4 が採番を decoration にしたのと同じ線）

**キャレットを動かさずに定義までスクロールする案は見送った。** クリックは削除のためにも押されるので、消すつもりだった著者の足元でページが動くのは、ハイライトが不要な人に色が付くより悪い取引である。記事が長くなって定義が同一画面に収まらなくなったら、クリック以外のジェスチャに割り当てる形で再検討する。

**発火は NodeSelection のみ。** 参照の隣のキャレットは本文を書いている著者がほとんどの時間いる場所であり、そこで光らせるのは答えではなく雑音になる。

## 9. 導線

このエディタにはインライン要素にツールバーボタンを置かない前例がある。インラインコードはツールバーになく、`Mod-E` とバッククォートの入力ルールだけで使う。脚注も同じ扱いとする。

| 経路                            | 採否   | 備考                                                                                                                                                                                                      |
| ------------------------------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Mod-Shift-F`                   | 採用   | 既定と衝突しない空き（`Mod-Shift-X` は打ち消し線、`Mod-Shift-B` は引用、`Mod-Alt-C` はコードブロック）。独自ショートカットの前例は `accent-emphasis-extension.ts` の `Mod-Shift-E`                        |
| `[^` の入力ルール               | 採用   | 2 文字打った時点で確定する（§9.1）                                                                                                                                                                        |
| ツールバーボタン                | 不採用 | インラインコードに倣う                                                                                                                                                                                    |
| スラッシュメニュー              | 不採用 | `slash-command.ts` の Suggestion が `startOfLine: true` で行頭専用。脚注は文の途中に入れるものなので噛み合わない。この設定は行ごとに切り替えられず、外すと callout とコードブロックの発火条件まで巻き込む |
| バブルメニュー / 選択範囲の変換 | 不採用 | 本文が減る唯一のコマンドになり、undo の原子性・マークの引き継ぎ・複数ブロック選択の扱いと要件が芋づる式に増える。同じ結果は「選択 → 切り取り → 脚注作成 → 貼り付け」で得られる                            |

いずれの経路も動作は同じ: **キャレット位置に参照を挿入し、空の定義を作り、キャレットは本文に留める。**

### 9.1 `[^` の 2 文字で確定する理由

- `[^` という並びは日本語の文章にも Markdown にもほぼ現れない。`[` 単独なら「[注]」のような表記と衝突するが、直後に `^` が来る組み合わせは事実上、脚注記法の意図しかない
- 閉じ括弧まで待つ案（`[^1]` を打ち切ってから変換）は**ラベルを著者に入力させることになり、§4 の「ラベルは生成した安定 ID」と衝突する**。打った `1` に意味がないなら、最初の 2 文字で確定するほうが正直
- 2 文字で確定すれば「`[^` を打ったが脚注をやめた」中間状態が存在しない。やめたければ undo 一回で戻る

### 9.2 UI 実装上の既知の落とし穴

定義の編集欄に独自コントロールを置く場合、以下を踏まないこと。

- **`<form>` の入れ子は不可**。`PostEditor` は全体を 1 つの `<form>` で包んでおり、入れ子の `<form>` はブラウザに落とされて submit が無言で no-op になる
- **NodeView 内の `<input>` / `<select>` はサーバーアクション保存で初期化される**（React 19 のフォーム自動リセット）。`form` 属性を存在しない id に向けて切り離す必要がある

### 9.3 「この参照を独立させる」は保留（2026-08-11）

§6.2 が共有を既定にしたことで、**「段落を複製して、文字を引き継いだ別の脚注を得る」1 操作が無くなった**。新しい脚注は `[^` でいつでも作れるが、元の注釈の文字は手で運ぶことになる。より効くのは手数ではなく事故のほうで、段落を複製した著者が「貼り付けた側の注釈」を直したつもりで共有相手も書き換える。画面上、定義が 1 行しかないことでしか区別が付かない。

**塞ぐなら、参照を選んで「独立させる」コマンドを 1 つ足す**（ラベルを発行し、定義の内容を写した新しい定義を作る。1 トランザクション）。参照のクリックは既に NodeSelection を作っており（§8.1）、そこに乗る。§9 が退けたピッカーとは別物である — ピッカーは中間状態を持ち込むので §9.1 が `[^` の 2 文字確定で消したものを呼び戻し、選択後の 2 つ目のトランザクションが `hasUndoableInputRule` の罠（§10.1）に入る。独立コマンドにはどちらも無い。

**保留する理由は導線が未決だから。** §9 はインライン要素にツールバー・スラッシュ・バブルを置かないと決めているので、残るのは独自ショートカットか、参照を選択したときだけ出る何かである。共有が入った状態で上の事故が実際にどれだけ起きるかを見てから決めるほうが、良い判断ができる。**先送りにした課題であって、見落としではない。**

そして保留のままでよい、というのが現時点の判断である。 共有脚注が実際に使われるのは同じ出典を繰り返し引く学術文章や仕様書で、ブログ記事にはまず現れない。それが正しいなら、この blog にとって §6.2 の変更が持つ意味は「共有できるようになった」ではなく、**「脚注入りの段落を複製したときの既定が裏返った」**ほうである。失敗の質は対称ではない — 共有したかったのに複製になれば定義が 2 行並んで見えば分かるが、複製したかったのに共有になると、貼り付けた側を直したつもりで元も変わり、気づくのは公開の後になり得る。ただし脚注入りの段落を複製する操作自体この blog では滅多に起きず、起きても注釈は書き換わるだけで消えず（undo が効く）、その一度きりである。天秤は釣り合っている。

**実際に一度でも踏んだときの最初の手当ては、独立コマンドではなく decoration である。** 参照が 2 つ以上あるラベルの定義に印を付けるだけでよい（`data-shared` 相当。§4 の番号と `data-empty` が既に通っている経路に 1 つ足す）。文書を変えないので autosave も undo 履歴も汚さず、新しいジェスチャも導線の決定も要らない。上の事故は「編集する前に共有だと分かる」だけで起きなくなるので、独立コマンドはそれでも足りなかったときの 2 手目である。段階が用意できている以上、今この場で決める必要は無い。

## 10. 受け入れ基準

E2E（`e2e/`）で確認する。エディタはブラウザ専用なので、tsc も vitest も実行時の振る舞いを見られない。

**基本の往復**

1. 参照を挿入し、定義に文字を入れて保存すると、GFM 脚注として Markdown を往復する
   - 1b. 同一定義への複数参照が 1 つの定義として往復する（§6.2。2026-08-11 追加。Markdown 層には何も足していない — `markdown-it-footnote` は参照ごとに `footnote_ref` を出し、パースはレンダラ規則が書く `data-label` で索くため、両方の参照が同じ定義に着く。定義行が 1 本であることを数えて確認する — 番号は文書順から毎回計算し直す decoration なので、セクションが何を持っていようと両参照は `[1]` に見える）
2. 参照を削除すると定義も消え、1 回の undo で両方戻る
   - 2b. 参照が 2 つあるとき、1 つ目の削除では定義が残り、最後の 1 つで定義とセクションが消える（§4・§5.1。2026-08-11 追加。参照カウントは `footnotePairing` の生存判定から既に出ていたので、これは新機能の確認ではなく**既にそうなっていたことの固定**である）
3. 段落を入れ替えると番号が振り直され、Markdown のラベルは変わらない
   - 3b. 定義の並びも参照順に追随する（§3。2026-08-05 追加 — 下記）
4. 外部由来のラベル（`[^note]`）を含む文書を開いて保存しても、ラベルが生成 ID に書き換わらない（§4.1）

**導線**

5. `[^` を打つと参照になる
6. `Mod-Shift-F` で参照が入る
7. テーブルセル内・コードブロック内では入力ルールもショートカットも発火せず、`useEditorNotice` で理由が出る（拒否経路が 2 つあることに注意）
   7b. アコーディオンのタイトル内でも同じく発火しない（§6.5。2026-08-08 追加。ここは Markdown ではなくスキーマが拒む場所で、ガードが無いとアコーディオンが 2 つに割れる。本文内では今までどおり脚注が入ることまで確認する — 塞ぐのは `detailsSummary` であって `details` ではない）
   7c. タイトルへの貼り付けとドロップでもアコーディオンが割れない（§6.5。2026-08-08 追加。経路は 3 つあり、キー 2 つだけ塞いでも残りの 2 つから同じ破壊に入れる。ドロップは `posAtCoords` がタイトルの上で summary の内側を指すかどうかがブラウザ側の事実なので、**CDP のネイティブドラッグで実測すること** — 基準 14 で一度払った授業料と同じ）
8. 文書末で変換した直後の undo が効く。 この罠は `efeebc5`（2026-08-04）で一般に解消済み（`TrailingNode` が入力ルールの記録が生きているあいだ追加を待つ）だが、定義セクションは**「文書末」が指すものを変える**（§3.1）ため、脚注を入れた状態で改めて確認する
   8b. 定義の末尾でも途中でも Enter が定義を分割せず、注釈の文字が失われない（§5.1。2026-08-05 追加。定義の外の Enter が今までどおり段落を分けることまで確認する — 文書全体のキーマップなので）
   8c. 定義の端での Backspace / Delete が定義を連結させず、通知が出る（§5.1。2026-08-05 追加。定義の外の Backspace が今までどおりブロックを連結することまで確認する）
   8d. 2 つの定義にまたがる範囲を削除・上書きしても定義が融合しない（§5.1。2026-08-05 追加。あわせて `Shift+Enter` / `Mod+Enter` が定義内で hard break を作れることを確認する — `isolating` を付けると `setHardBreak` が拒否するため、ここが対で壊れる）
9. 定義セクションの直前に段落が保たれ、セクションの後ろに空段落が生まれない（§3.1。テーブルやコードブロックを定義セクションの直前に置いた場合も確認する）。あわせて `efeebc5` が取った挙動が退行していないこと — 文書末のブロックショートカットが Backspace 一回で戻る

**空の定義**

10. 空の定義があると公開が拒否される（判定は `body` の文字列に対して行われる。§5.3）
    10b. 空の定義側にもプレースホルダが出る（§5.2 の第 1 層。2026-08-05 追加。書かれた注釈の左端と揃うことまで確認する — `::after` は空の textblock が持つ末尾 `<br>` の分だけ右にずれる）
11. 空の定義があっても下書き保存は成功する
12. 空の定義を含む文書を往復しても、参照が孤児にならない

**ガード**

13. callout 内の参照が、定義を文書末に持ったまま成立する
14. 参照を含む選択範囲を境界をまたいでドロップしても、孤児定義が生まれない（§6.4。**CDP でネイティブドラッグを合成して実測すること** — この基準は推論では通らなかった。`e2e/native-drag.ts` の機構を使う）
15. 定義のない参照を含む Markdown を読み込んでも壊れない
16. 脚注を含む段落を文書内で複製すると、参照だけが増えて定義を共有する（§6.2。2026-08-11 に反転 — 旧: 参照と定義が対で増え、ラベルは新規発行される）
    - 16b. 貼り付け先に同じラベルで別の注釈があるとき、それを共有せず新しい ID を発行する（§6.2。2026-08-11 追加。運んで来た注釈の文字が失われないことまで確認する。外部由来のラベルは保持されるので（§4.1）、2 つの記事がどちらも `[^1]` を持つのは普通の状況である）
    - 16c. 1 つのスライスに同じラベルの参照が 2 つあるとき、発行される ID は 1 つ（§6.2。2026-08-11 追加。参照ごとに発行すると、段落内で共有していた 1 つの注釈が同じ文字を持つ独立した 2 件に割れる）
17. 脚注を含む段落を切り取って貼り付けても、注釈の文字が失われず、ラベルが変わらない（§6.2）
18. 脚注を含む段落をテーブルセル／コードブロックに貼ると、参照は平文に落ち、定義セクションに残骸が残らない（§6.3）
19. `^[インライン脚注]` を含む Markdown を読み込むと、注釈の文字が残り、GFM 形の脚注に正規化される（§1・§7.2。参照と定義に同じラベルが渡ることまで確認する — 別々のレンダラ規則が描くため、ここが対で壊れる）
20. 孤児定義（参照のない定義）の文字が残る（§5.5。プラグインはこれを削除するので、救済を入れないと現状より悪化する）

**公開側**

21. 公開ページで本文 ⇄ 定義の相互ジャンプが機能する
    - 21b. 同一定義への 2 参照が同じ番号で描かれ、定義から両方への backref が出る（§8。2026-08-11 追加。`lib/render.test.ts` — 公開側の脚注はパイプラインの既定出力そのものなので、clobber や sanitize の変更が 2 つ目の id を壊しても他に気づくものが無い）

**エディタ側**

22. 参照を選択すると対の定義がハイライトされ、本文中のキャレットでは光らない（§8.1。2026-08-05 追加。移動はしない）

### 10.1 基準 3b — 測っていなかった項目（2026-08-05）

**§3 の「並び順は本文中の参照順で自動整列する」は、実装されないまま全段階が完了扱いになっていた。** 上の 21 項目に定義の**並び**を見るものが 1 つも無かったためである。基準 3 は「番号が振り直され」までしか要求しておらず、番号はデコレーションとして毎回文書順から計算し直されるので、そこは常に正しく見える。取り残されるのは並びだけだった。

実測した症状（既存の脚注 2 つの間に脚注を足す）:

|                | 上から順に  |
| -------------- | ----------- |
| 本文の参照番号 | 1, 2, 3     |
| 定義セクション | **1, 3, 2** |

公開ページに出なかったのは remark-gfm がレンダリング時に参照順でセクションを組み直すためで、食い違っていたのはエディタと**保存された Markdown** の側である。

修正は 2 箇所に分かれ、両方が要る:

- **挿入時**（`applyFootnoteInsertion`）— 定義を参照順の位置に挿す。これを調停ステップ任せにできないのは、`[^` の入力ルールが記録を残している間 `footnotePairing` が手を引くから（§9.1、基準 8）。追加トランザクションで並べ替えると、次のキー入力まで定義が誤った位置に見えるか、基準 8 の Backspace を壊すかのどちらかになる
- **調停ステップ**（`sortDefinitions`）— 貼り付け・切り貼り・削除が並びを崩す経路。**materialize の後に別トランザクションとして並べ替えを返しても実行されない**（実測）。prosemirror-state は自分が append した時点で `seen[i].n` をトランザクション列の長さに進めるため、その後に別のプラグインが append しない限り、同じ apply の中で 2 度目の `appendTransaction` は呼ばれない。既に組み立て中のトランザクションに畳み込むこと

定義セクション内にキャレットがある間は並べ替えない。並べ替えはセクションの中身をまとめて置換するので、注釈を書いている最中の選択がマップし直されてしまうためである。これで取りこぼす編集は今のところ無い — 参照は定義の中に置けず（§6.2）、そこでの編集が参照順を変える経路が存在しない。将来そういう経路ができたときのための保険であって、既知のケースを先送りしているわけではない。

**読み込み時の整列は不要**（2026-08-05 実測）。`markdown-it-footnote` の tail は `env.footnotes.list` を走るので、この列は参照で索かれており、ファイル上の定義の並びが何であれパーサは参照順で渡してくる。したがってこの修正より前に保存された記事も、開いた時点で正しい並びに見える。実エディタは `useEditor({ content })` で内容を受け取りトランザクションを経由しないため、仮に整列が必要だったとしても調停ステップは走らなかった — 開いただけで文書が変更扱いになり autosave が走る事態を避けられているのは、この 2 つが噛み合っているからである。
