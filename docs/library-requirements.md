# ライブラリ 要件定義

- 状態: 設計済み、未実装（2026-10-15）
- 作成: 2026-10-15、note・Zenn の管理画面にある「ライブラリ」のようなページを、複数の著者より先に作る相談から
- 関連: `docs/project-status.md` §7（複数の著者）、`docs/scribble-requirements.md` §9、`lib/dal.ts`、`app/admin/(list)/AdminSideNav.tsx`

ログイン中の人が、他の人の記事と走り書きに付けた印と、読んだ履歴を、管理画面の 1 つのページにまとめる機能の設計記録。画面での名前は「ライブラリ」、コードと URL での名前は `library`。

---

## 1. 目的と前提

**目的**: 複数の著者（`docs/project-status.md` §7）が入ると、著者は互いの記事を読む読者にもなる。そのとき要る「取っておく」「評価を届ける」「さっき読んだものに戻る」の 3 つを、管理画面に先に作っておく。

**前提**: 今ログインできるのは管理者だけで、読者はログインしない（`docs/project-status.md` §7.1）。v1 の時点では、他の人の記事はまだ無い。ライブラリは利用者ごとに作るので、著者がログインできるようになった時点で、何も足さずに著者にも効く。

## 2. 決定

- **タブは 3 つ。** ブックマーク、いいね、閲覧履歴、の順に並べる。
- **入れるのはこのサイトの記事と走り書きだけ。** 外部の URL は入れない（作者、2026-10-15）。
- **ブックマークとは、本人にしか見えない保存のことである。** 自分の記事にも付けられる。
- **いいねとは、書き手に届く評価のことである。** 自分の記事には付けられない。数は書き手の管理画面に出し、公開側には出さない（§6.3）。
- **閲覧履歴には、他の人の記事だけを残す。** 自分の記事を開いた記録は残さない。
- **ライブラリは管理画面だけにある。** 公開側に一覧は無い。印を付けるボタンは公開側の記事のページにあるが、ログイン中の人にしか出ない（§5）。

## 3. データ

変更はどれも `npm run db:generate` から `npm run db:migrate` で行う（`docs/project-status.md` §2）。

### 3.1 `posts.authorId`

記事の書き手を表す列を `posts` の末尾に足す。いいねで「自分の記事か」、閲覧履歴で「他の人の記事か」を判定するのに要る。`docs/project-status.md` §7.3 の骨組みにある列のうち、これだけを先に入れる。

- 移行は既存の行を、最も id の小さい管理者で埋める。
- 新しい行には、作成するときにセッションの利用者を入れる。走り書きも同じである。
- 編集と削除の所有の確認は、この列を使って `docs/multi-author-requirements.md` §4 が行う。

### 3.2 3 つのテーブル

| テーブル     | 列                                 | 一意                 |
| ------------ | ---------------------------------- | -------------------- |
| `bookmarks`  | `user_id`、`post_id`、`created_at` | `(user_id, post_id)` |
| `likes`      | `user_id`、`post_id`、`created_at` | `(user_id, post_id)` |
| `post_views` | `user_id`、`post_id`、`viewed_at`  | `(user_id, post_id)` |

- 日時はエポックミリ秒で持つ（`postRevisions.createdAt` と同じ）。
- `posts` が受け付けるのは末尾への列の追加だけなので、3 つとも別のテーブルにする（`lib/db/schema.ts` の `posts` のコメント）。
- 外部キーは張らない。記事を消すときは、`deletePost` が同じトランザクションで 3 つのテーブルの行も消す。理由は `postRevisions` と同じで、カスケードは `foreign_keys` が有効な接続でしか効かず、テストの DB では何も測らなくなるためである（`lib/db/schema.ts` の `postRevisions` のコメント）。

### 3.3 閲覧履歴の持ち方

1 人につき 1 つの記事は 1 行にする。開くたびに `viewed_at` を書き換える。残すのは利用者ごとに新しいものから 100 件（`RECENT_VIEWS_LIMIT`）で、書き込みのたびにそれより古い行を消す。

## 4. 書き込みの経路

**機構**: 書き込みはどれも ライブラリ用の Server Action が受け、セッションと条件をサーバで確かめる。Action は直接 POST できるので、ボタンを出さないことは境界にならない（`docs/project-status.md` §7.3 のテストの項と同じ考え）。

| 操作                   | 受け付ける条件                                   | 受け付けないときの答え |
| ---------------------- | ------------------------------------------------ | ---------------------- |
| ブックマークの切り替え | ログイン中、対象が公開中                         | 存在しない記事と同じ   |
| いいねの切り替え       | ログイン中、対象が公開中、対象が自分の記事でない | 存在しない記事と同じ   |
| 閲覧の記録             | ログイン中、対象が公開中、対象が自分の記事でない | 何もしない             |

- 非公開の記事には、存在しない記事と同じに答える。id を順に試して、非公開の記事があるかを知られないようにするためである（`docs/link-card-requirements.md` §6.1 と同じ考え）。
- 閲覧の記録は、記事のページがマウントされた後に、`useEffect` から Server Action（`recordViewAction`）を呼んで行う。描画の中では書き込まない。先読みは部品をマウントしないので、記事のページを先読みしただけでは履歴に残らない。Next.js の文書が閲覧数の記録に挙げている形である（`node_modules/next/dist/docs/01-app/01-getting-started/07-mutating-data.md` の「useEffect」）。プレビュー（非公開の記事をログイン中に開いたもの）では送らない。
- 印の Action は切り替えではなく、付けるか外すかを引数で受け取る。二重のクリックや、2 つのタブで開いたページが、ボタンの最後の見た目と逆の状態に戻さないためである。

## 5. 公開側

- 記事のページ（`/posts/<slug>`）と走り書きのページ（`/scribbles/<slug>`）に、ブックマークといいねのボタンを置く。どちらのページも既にセッションを読んでいる（`getOptionalSession`）。
- ボタンはログイン中にだけ出す。ログインしていない人には何も出さない（「ログインしていいね」のような誘いも出さない）。
- 自分の記事には、いいねのボタンを出さない。ブックマークのボタンは出す。
- プレビューではどちらも出さない。公開中でない記事には付けられないためである（§4）。
- 押した状態はボタンの見た目で分かるようにし、もう一度押すと外れる。
- 押した瞬間に見た目を切り替え、Action が拒んだときだけ元に戻す。通信中の表示は出さない。
- hover はマウスの端末でだけ背景を濃くし、押している最中の色はタッチの端末でだけ出す。サイトの他のボタンと同じ分け方である（`app/globals.css` の `.button-secondary:hover` と `.toolbar-button:active`）。キーボードで選んだときはアクセントの色の枠を出す。
- ボタンは本文のカードの下に、文字の付いた丸いボタンを「いいね」「ブックマーク」の順に中央に並べる（2026-10-15 に 3 案から選んだ）。読み終えて評価を決める位置で、目次の有無にも走り書きかどうかにも左右されない。目次の欄の上に固定する案は、目次の無いページと狭い画面に別の置き場所が要るので選ばなかった。

## 6. 管理画面

### 6.1 メニュー

左メニュー（`AdminSideNav`）の「走り書き」の下に「ライブラリ」を置く。管理者にも著者にも出す。並びは `adminNavItems` で決める。

### 6.2 ライブラリのページ

- URL は `/admin/library`。タブは `?tab=` で選び（`bookmarks`・`likes`・`history`）、無いときはブックマークを開く。記事一覧の状態のタブ（`?status=`）と同じ形である。
- 各行は、タイトル、種類（記事か走り書きか）、書き手が書いた日付、公開側のページへのリンクを持つ。
- 並びは、ブックマークといいねは付けた日時、閲覧履歴は開いた日時の新しい順。
- 印を付けた日時と開いた日時は、行に出さない。並び順が新しさを示しており、公開日と並ぶと取り違えやすいためである（2026-10-15）。note の閲覧履歴も、読んだ日時ではなく記事の公開からの時間を出している。
- 出すのは今公開中のものだけ。非公開に戻された記事の行はテーブルに残し、一覧からは外す。再び公開されれば戻る。
- ブックマークといいねの行の右端に、塗られたしおりとハートのアイコンを置く。押すと塗りが消えて印が外れ、もう一度押すと戻る。記事のページのボタンと同じ部品の形なので、確認のダイアログは出さない。枠付きの「外す」のボタンにしないのは、行の右端が枠の無い「表示」と「⋯」だけの記事一覧の中で、それだけが浮くためである（2026-10-15）。閲覧履歴の行は消せない（§7）。
- ページ分けは v1 では作らない。閲覧履歴は 100 件で止まり、ブックマークといいねは書き手が 1 人のうちは件数が増えない。
- 空のタブには、走り書きの一覧と同じ形の空の表示（`EmptyPostList.tsx`）を、タブごとの絵で出す。新規作成のボタンは出さない。文言は次のとおり（2026-10-15）。補足は、本人が自分のライブラリを振り返る視点で書く。いいねが書き手に届くことは、記事のページで押すときに伝われば足りる。「ほかの人の」は、書き手が 1 人の今いいねと閲覧履歴が空である理由も兼ねる。

  | タブ         | 見出し                     | 補足                                                                 |
  | ------------ | -------------------------- | -------------------------------------------------------------------- |
  | ブックマーク | 読み返したい記事を、ここに | 記事や走り書きのページでブックマークすると、ここに集まります。       |
  | いいね       | 心に残った記事を、ここに   | ほかの人の記事や走り書きにいいねすると、あとからここで振り返れます。 |
  | 閲覧履歴     | 読んだ記事を、もう一度     | ほかの人の記事や走り書きを開くと、新しい順に 100 件まで残ります。    |

  閲覧履歴の「100」は `RECENT_VIEWS_LIMIT` から作る。

### 6.3 いいねの数

記事一覧と走り書きの一覧の各行に、その行についたいいねの数を出す。0 件の行には何も出さない。誰が付けたかは出さない。

## 7. 先送り

- **公開側のいいねの数**: 記事のページに数を出すかは、著者が増えてから決める。読者がログインしない今は、数が書き手の内輪の評価だけになる。
- **読者のいいね**: ログインしない読者が付けるいいね。重複の防ぎ方（cookie か IP か）と、荒らしへの備えを決める必要がある。
- **閲覧履歴の消去と停止**: 1 件ずつ消す操作、全部消す操作、記録を止める設定。
- **種類での絞り込み**: 「すべて／記事／走り書き」の切り替え。カテゴリでは絞らない。走り書きはカテゴリを持たず、カテゴリで絞ると一覧から消えるためである（2026-10-15）。件数が増えてから足す。
- **ブックマークの整理**: フォルダやメモ。件数が増えてから考える。
- **カードの一覧**: note の閲覧履歴のように、行ではなく画像付きのカードを 2 列に並べる形を検討している（作者、2026-10-15）。カードは画像、タイトル、本文の書き出し、書き手の名前とアイコン、印を付けた日時、いいねの数とブックマークのボタンを持つ。切り替える前に決めること:
  - 画像の無い記事と走り書き（サムネイルを持たない、`docs/scribble-requirements.md` §3.2）のカードの見た目。記事一覧では、画像の無い記事をカテゴリ色のマークで埋めた（`docs/category-mark-requirements.md`）。走り書きはカテゴリを持たないので、そのままは使えない。
  - 書き手のアイコン。名前は表示名（`docs/multi-author-requirements.md` §6）を使えるが、アイコンはまだ無い。
  - カードにいいねの数を出すか。出すと書き手以外にも数が見えるので、上の「公開側のいいねの数」と一緒に決める。

  v1 は行の一覧にする（§6.2）。書き手が 1 人のうちは、並ぶのがほぼ自分の記事のブックマークだけで、カードにする利点が小さい。

- **ライブラリの検索**: タイトルで絞り込む欄。閲覧履歴の 100 件から「前に読んだあれ」を探すときに、日時を出す代わりになる。件数が増えてから足す。

## 9. 複数の著者との関係

**そのまま効くもの**: 3 つのテーブルは利用者ごとの行なので、著者がログインできるようになれば、各著者が自分のライブラリを持つ。ボタンの条件（§5）といいねの数（§6.3）も、`authorId` が本物の書き手を指すようになれば、そのまま正しくなる。

**複数の著者を入れる前に決めること**:

- いいねの数を書き手以外に見せるか（§7）。
- 著者を BAN したとき、その人が付けたいいねを数に含め続けるか。BAN の設計（`docs/project-status.md` §7.1）と一緒に決める。
