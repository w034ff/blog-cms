# 複数の著者 要件定義

- 状態: 第 1 段（§1〜§8）は実装済み（2026-10-17）。OAuth の段（§9）も実装済み（2026-10-18）
- 作成: 2026-10-17、`docs/project-status.md` §7 の複数の著者のうち、OAuth なしで作れる部分を先に作る相談から
- 関連: `docs/project-status.md` §7、`docs/site-header-requirements.md` §3.3・§8、`docs/library-requirements.md`、`lib/dal.ts`、`lib/posts.ts`

複数の著者が 1 つのサイトに書けるようにするための設計記録。全体の方針（Google でのログイン、役割、参加方針）は `docs/project-status.md` §7 が持つ。この文書はその実装を、OAuth の前に作れる第 1 段（この文書の §1〜§8）と、OAuth の段（§9）に分けて書く。

---

## 1. 目的と前提

著者がログインできるようになる前に、ログインした著者ができることの境界を固める。今は役割（`users.role`）と記事の著者（`posts.authorId`）の列があるだけで、境界はほとんど強制されていない。ログインした利用者なら誰でも、他人の記事を編集・公開・削除でき、他人の下書きのプレビューや版の履歴も開ける。

今の本番に著者はおらず、管理者 1 人だけである。著者のアカウントは E2E の準備（`e2e/prepare-db.mts`）が作るテスト用のものだけで、第 1 段の強制はそれで確かめる。

## 2. 決定

- **記事の編集・公開・非公開化・削除・版の復元は、その著者か管理者だけ**。著者の無い行（`authorId` が null）は管理者だけ。他人の行への操作は、DB を変えずに拒む。
- **停止は、ログインと書き込みを止め、公開側からその著者の行を外す**。行は消さず、公開状態も書き換えない。停止を解けば、元の公開状態にそのまま戻る（オーナー、2026-10-17）。消したい行は、管理者が 1 本ずつ消す。
- 管理者は停止できない。管理者が自分を締め出さないため。
- **表示名を持ち、空でなければ記事と走り書きのページに署名として出す**（オーナー、2026-10-17）。表示名は本人が「アカウントの設定」で決める。空のうちは署名を出さないので、管理者が表示名を入れるまで今の見た目は変わらない。
- エディタのタグ欄から辞書にタグを足す操作（`/api/tags`）は、著者にも許す（今と同じ）。辞書の編集・統合・削除は管理者だけのまま。
- 利用者の管理画面（`/admin/users`）は OAuth の段で作る（§9.5）。第 1 段の停止は、データと強制とテストまでである。

## 3. データ

移行は `db:generate` → `db:migrate` の経路で作る（`docs/project-status.md` §2）。

| 列                   | 型                       | 中身                                                                   |
| -------------------- | ------------------------ | ---------------------------------------------------------------------- |
| `users.display_name` | TEXT NOT NULL DEFAULT '' | 公開側に出す名前。前後の空白を除き 0〜20 文字、改行なし。`''` は未設定 |
| `users.suspended_at` | TEXT NULL                | 停止した時刻（ISO 8601）。null なら停止していない                      |

- 上限の 20 は、署名が幅 360px の画面で日付の行に収まる長さから決めた（§6.2。オーナー、2026-10-17）。日本語の名前と、英字のハンドルや併記がおおむね入る。上限は名前の付いた定数にする（`DISPLAY_NAME_MAX_CHARS`）。数え方は `docs/site-settings-requirements.md` §3 と同じく文字（コードポイント）。
- `username` はログイン用のまま、公開側には出さない。

## 4. 所有の強制

### 4.1 判定

「この利用者がこの行を書き換えてよいか」を、1 つの純粋な関数が答える（`lib/` の下）。入力は、利用者の id と役割、行の `authorId`。管理者なら常に可、著者なら `authorId` が自分の id のときだけ可。この関数を vitest で確かめ、各経路はそれを呼ぶだけにする。

### 4.2 経路ごとの扱い

| 経路                                                                          | 他人の行に対して                                                     |
| ----------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `submitPostAction`（公開・更新・非公開化）                                    | 拒む。結果に `forbidden` を返し、エディタは理由を出す                |
| `deletePostAction`                                                            | 拒む。DB を変えない                                                  |
| `/api/drafts`（自動保存）                                                     | 403。エディタは「保存に失敗」を出す                                  |
| `restoreRevisionAction`                                                       | 拒む。DB を変えない                                                  |
| 編集画面、版の履歴の画面、Markdown の書き出し（`/admin/posts/<id>/markdown`） | 404                                                                  |
| 下書きのプレビュー（`/posts/<slug>`、`/scribbles/<slug>`）                    | ログインしていない人と同じく 404                                     |
| 管理画面の記事一覧と走り書きの一覧                                            | 著者には自分の行だけを出す。管理者にはすべてを出す                   |
| カードの検索（`/api/posts/search`）                                           | 公開中の行と自分の下書きだけを返す。他人の下書きのタイトルを出さない |

- 新しい行は、作成した利用者を著者にする（今と同じ。`lib/posts-write.ts` の `createPost`）。
- `forbidden` の文言は「この記事を編集する権限がありません。」。
- 他人の行を 403 や `forbidden` で拒むのは、操作の結果だけである。ページを開く経路は、行の有無を明かさないため 404 にする（`verifyAdmin` が 403 ではなく 404 にしているのと同じ理由）。

### 4.3 ログインしていれば誰でもよい経路

画像のアップロード（`/api/uploads`）、タグの追加（`/api/tags`）、リンクの情報の取得（`/api/link-preview`・`/api/link-title`・`/api/link-image`）、ライブラリの操作（`app/actions/library.ts`）。停止中の利用者はログインしていない扱いになるので（§5）、ここも止まる。

## 5. 停止

- **ログイン**: パスワードが合ったうえで停止中なら、セッションを作らず「このアカウントは停止されています。」を返す。パスワードが違うときの文言は今のまま。
- **既存のセッション**: セッションの読み込み（`lib/dal.ts` の `getOptionalSession`・`verifySession`）が利用者の行を DB で確かめ、行が無いか停止中なら、セッションが無いものとして扱う。ページは `/login` へ送り、Route Handler は 401 を返す。役割と同じく、停止は次の要求から効く（`isAdmin` が DB を読むのと同じ理由）。
- **公開側**: 公開中の行の読み込み（`lib/posts.ts` の `listed` と `publishedBySlug`）に「著者が停止中でない」を足す。これで次のすべてから外れる: ホーム、タグとカテゴリのページ、走り書きの一覧と各ページ（404）、記事のページ（404）、検索、RSS、リンクカード（`resolveCard` は存在しない記事と同じく普通のリンクにする）、件数。著者の無い行は外さない。
- **ライブラリ**: ほかの利用者のライブラリからも、停止中の著者の行を外す（公開中でない行を出さないのと同じ扱い）。いいねとブックマークの行は消さない。
- 停止と解除の操作は第 1 段では画面に出さない（§2）。テストは DB の列を直接書いて確かめる。

## 6. 表示名と署名

### 6.1 アカウントの設定

- `/admin/account`。見出しと画面のタブのタイトルは「アカウントの設定」。ログインしていれば誰でも開ける（自分の行だけを扱う）。
- ヘッダーのアカウントのメニューに「アカウントの設定」を足す。位置は「ライブラリ」の上。管理画面の左メニュー（`AdminSideNav`）には足さない。
- 欄は「表示名」の 1 つと「保存」のボタン。補足に「記事と走り書きのページに著者名として出ます。空にすると出しません。」。欄の下に「8 / 20」の形で文字数と上限を出す（`docs/site-settings-requirements.md` §5 と同じ）。
- 保存は Server Action。セッションの利用者の行だけを書き、値を検証してから書く。結果は「保存しました」、または欄ごとの理由（「20 文字以内で入力してください」「改行は使えません」）。空は許す。

### 6.2 署名

- 記事のページでは、日付・更新日・カテゴリが並ぶ行の先頭に表示名を置く。この行は項目を間隔だけで区切っているので、表示名もほかの項目と同じ間隔で並べ、「・」は使わない。版の履歴のプレビューも同じ部品（`components/PostArticle.tsx`）で描くので、同じ位置に出る。
- 走り書きのページでは、日付の後ろに「・」で区切って表示名を置く。日付が単独で置かれた行なので、区切りが要る。
- 色と大きさは、それぞれの行の日付と同じ。リンクにはしない（著者のページはまだ無い）。
- 表示名が空なら、区切りごと出さない。
- 一覧のカード、RSS、`og:` のメタデータには出さない（§9.10）。
- 署名はページを描くたびに `users` から読む。表示名を変えれば、次に開いたページから変わる。

## 9. OAuth の段

- 状態: 実装済み（2026-10-18）。本物の Google での確認（基準 22）は未実施

著者が Google でログインできるようにし、管理者が「誰が著者になれるか」と「誰が著者か」を 1 つの画面で扱えるようにする。全体の方針（管理者はパスワードのまま、役割、`open` / `allowlist`）は `docs/project-status.md` §7.1 にある。

### 9.1 決定

- **この段で作るのは、Google でのログイン、参加方針と招待、利用者の画面（`/admin/users`）、管理画面の一覧の著者の列**。役割の変更や署名の公開側への展開は §9.10 に残す。管理者はオーナー 1 人で足り、著者が増える前に要るのは「入れる」「止める」の 2 つだからである。
- **招待（許可リスト）が絞るのは、アカウントを作れる人だけ**。既に行がある著者は、招待が無くても、方針が `allowlist` でもログインできる。招待は、その人が最初にログインして利用者の行ができた時点で消える。著者を締め出すのは停止（§5）の 1 つだけにする。招待を毎回確かめる形にすると、`open` から `allowlist` に戻した時点で、それまでの著者が一斉にログインできなくなるためである。
- **方針の既定は `allowlist`。公開側のヘッダーにログインの入口は出さない**。招待した人には `/login` の URL を伝える。`allowlist` のときに入口を出すと、押した人の大半が Google でログインした後に断られる。入口は `open` に切り替えるときに決める（`docs/site-header-requirements.md` §6）。
- Google の著者は、`username` と `password_hash` を持たない（null）。どちらもパスワードでログインするための列で、使わない値で埋めると、ログインに使える値のように見えるためである。
- Google の著者のメールは保存しない（オーナー、2026-10-18）。メールは、ログインのその場で招待と照らし合わせるためだけに使う。使わない情報を持たなければ、DB やそのバックアップ（`data/backups/`）から漏れることもない。招待した数人が相手なら、メールが無くても困る場面が無い。表示名は Google の `name` で最初から埋まるので、利用者の画面では表示名で誰か分かる。
- Google のプロフィール画像は保存せず、出さない。外部の画像を読むと、CSP と読者の追跡の論点が増える。アカウントのボタンは頭文字のままにする。
- OAuth のライブラリは足さない。既に入っている `jose`（`createRemoteJWKSet` と `jwtVerify`）と `fetch` で書く（`docs/dev-environment.md` §4）。
- リダイレクト URI は `SITE_ORIGIN` から作る（`<SITE_ORIGIN>/auth/google/callback`）。環境変数を別に持つと、ホストを移すとき（`docs/project-status.md` §5）に 2 か所がずれうるためである。
- 利用者の画面は、招待を利用者の一覧に「招待中」の行として並べる形にする（オーナー、2026-10-18）。比べた案は 2 つあった。方針と許可リストを「サイトの設定」に置く案は、「誰が入れるか」と「誰が入ったか」が別の画面に分かれる。利用者の画面をタブで 2 つに分ける案は、数行の招待のためにタブを使い、招待中の人がクリックの奥に隠れる。

### 9.2 データ

移行は `db:generate` → `db:migrate` の経路で作る（`docs/project-status.md` §2）。`username` と `password_hash` の NOT NULL を外すので、`users` は表の作り直しになる。

| 列・表                                 | 型                                   | 中身                                       |
| -------------------------------------- | ------------------------------------ | ------------------------------------------ |
| `users.username`                       | TEXT NULL UNIQUE                     | パスワードでログインする利用者だけが持つ   |
| `users.password_hash`                  | TEXT NULL                            | 同上                                       |
| `users.google_sub`                     | TEXT NULL UNIQUE                     | Google の `sub`。Google の著者を見つける鍵 |
| `author_allowlist`                     | 表（`email` が主キー、`created_at`） | 招待。画面では「招待」と呼ぶ               |
| `app_settings` の `author_access_mode` | `allowlist` / `open`                 | 参加方針。行が無ければ `allowlist`         |

- メールは前後の空白を除いて小文字にし、そのまま比べる。Gmail の「.」や「+」の正規化はしない。
- 利用者を見つける鍵は `google_sub`。Google の著者のメールは `users` に保存しない（§9.1）。
- 新しい Google の著者の `display_name` は、Google の `name` から改行を除き、§3 の上限（`DISPLAY_NAME_MAX_CHARS`）で切ったもの。`name` が無ければ空。
- セッションの中身は `userId` だけにする。`username` は Google の著者に無いので、名前はページを描くたびに `users` から読む（§9.7）。今の cookie に入っている `username` は読まずに捨てる。ログインし直しは要らない。

### 9.3 ログインの流れ

1. `/login` の「Google でログイン」は `GET /auth/google` に進む。この Route Handler は `state`、`nonce`、PKCE の `code_verifier` を作り、10 分で切れる cookie に入れる。cookie は `httpOnly`・`SameSite=Lax`・`path=/auth/google` で、`Secure` はセッションの cookie と同じく `SESSION_COOKIE_SECURE` に従う。そのうえで Google の認可のページへ送る。スコープは `openid email profile`。ログイン中なら `/admin` へ送る。
2. `GET /auth/google/callback` は、`state` が cookie と一致することを確かめ、cookie を消す。次に、コードを Google のトークンのエンドポイントで交換する（クライアントのシークレットと `code_verifier`）。
3. `id_token` の署名を Google の JWKS で検証し、`iss`（`https://accounts.google.com` か `accounts.google.com`）、`aud`（クライアントの ID）、`exp`、`nonce` を確かめる。`email_verified` が true でなければ拒む。
4. 受け入れるかどうかは、1 つの純粋な関数が決める（`lib/` の下）。入力は主張（`sub`・`email`・`name`）、`sub` で見つかった利用者、方針、招待の有無。順に次のように答える。
   - `sub` の利用者がいる: 停止中なら拒む。そうでなければログインさせ、その人のメールの招待が残っていれば消す。著者になった後に同じメールを招待しても、行が「招待中」のまま残らないようにするためである。
   - いない: 方針が `open` か、メールが招待されていれば、著者の行を作り、招待を消してログインさせる。どちらでもなければ拒む。
5. ログインできたら既存の `createSession` を呼び、`/admin` へ送る。拒んだときと、2・3 で失敗したときは、`/login?error=<理由>` へ送る（§9.6）。

- Google の著者の役割は常に `author`。管理者は Google でログインしない（`docs/project-status.md` §7.1）。パスワードの利用者の行には `google_sub` が無いので、4 の判定がその行を返すことはない。
- 環境変数 `GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET` の両方が無ければ、Google でのログインは無いものとして扱う。ログインのページはボタンを出さず、`/auth/google` と `/auth/google/callback` は 404 を返す。開発のサーバーと E2E は、これらを設定せずに動かす。
- パスワードのログインの回数制限（`lib/login-throttle.ts`）は Google の経路にかけない。総当たりの相手は Google 側である。

### 9.4 参加方針と招待

- 方針を変えられるのは管理者だけ。変えても既存の行には何も起きない（§9.1）。
- 招待は、メールアドレスの形を確かめてから足す。既に招待したメールは断る。利用者のメールは保存していないので、既に著者になった人のメールかどうかは確かめない（その人が次にログインした時点で招待が消える。§9.3）。
- 招待してもメールは送らない。管理者が本人に `/login` の URL を伝える。
- 方針が `open` の間も、招待の欄と招待の行はそのまま出し、消さない。`allowlist` に戻したとき、そのまま使える。
- Google の同意画面が「テスト」の状態の間は、Google 側のテストユーザーに登録した人しかログインできない。そのため、招待した人を Cloud Console のテストユーザーにも足す必要がある（§9.8）。

### 9.5 利用者の画面

- `/admin/users`。見出しとタブの名前は「利用者」。管理者だけが開け、著者には 404 を返す（§4.2）。左メニューの「タグの管理」と「サイトの設定」の間に「利用者」を足し、管理者だけに出す（`adminNavItems`）。
- 上から順に、「参加」の囲み、「招待する」の欄、一覧を置く。
  - 「参加」の囲み: 選択肢「招待した人だけ」と「誰でも」の 2 つ。それぞれに補足を付け、下に「保存」を置く。保存したら「保存しました」を出す（`docs/site-settings-requirements.md` §5 と同じ）。
  - 「招待する」の欄: メールアドレスの 1 行の欄（見本は `name@example.com`）と「招待する」のボタン、補足が 1 行。理由は欄の下に出す。
  - 一覧の並びは、招待の行（新しい順）、利用者の行（`id` の順）。
- 行の 1 行目は表示名で、空なら「（表示名なし）」（記事一覧の「（無題）」と同じ形）。その後ろに札を並べる: 「管理者」「停止中」「招待中」。
- 行の 2 行目:
  - Google の著者: 「Google でログイン」、「記事 N 本」、「走り書き N 本」。数は下書きも含めた、その著者の行の数。
  - パスワードの利用者: 「パスワードでログイン」と、同じく記事と走り書きの数。
  - 招待の行: メールと「まだログインしていません」。メールは幅 360px で語の途中でも折り返す。
- 行のメニュー（ボタンの名前は「その他の操作」。記事の行と同じ）:
  - 著者の行: 「停止する」。押すと、メニューの中に確認を出す（記事の削除と同じ形で、「やめる」に初めから焦点を置き、赤い「停止する」を並べる）。
  - 停止中の行: 「停止を解除」。確認は無い。
  - 招待の行: 「招待を取り消す」。確認は無い。
  - 管理者の行: メニューを出さない（§2）。
- 操作は `app/actions/users.ts` の Server Action で行う。どれも、サーバー側で管理者であることを確かめ直す。停止は管理者の行を拒む。

### 9.6 ログインのページ

- 見出しを「管理者ログイン」から「ログイン」に変える。タブの名前は「ログイン」のまま。
- 上から順に、理由の行（あるとき）、「Google でログイン」のボタン、「または」の区切り、今のユーザー名とパスワードのフォームを置く。
- Google のボタンの形と G のマークは、Google のログインのボタンのブランドの決まりに従う。
- `?error=` の値ごとの文言:

| `error`       | 文言                                                        |
| ------------- | ----------------------------------------------------------- |
| `not_invited` | このメールアドレスは招待されていません。                    |
| `suspended`   | このアカウントは停止されています。（§5 と同じ）             |
| `unverified`  | Google のメールアドレスが確認されていません。               |
| `failed`      | Google でのログインに失敗しました。もう一度お試しください。 |

それ以外の値は無視し、理由の行を出さない。

### 9.7 アカウントの名前

管理画面とヘッダーで利用者を指す名前は、表示名、ユーザー名の順で、最初の空でないものにする。どちらも空（表示名を消した Google の著者）なら「（表示名なし）」で、ヘッダーの頭文字は「?」にする。1 つの関数（`lib/` の下）が決め、次の 3 か所がそれを使う。

- ヘッダーのアカウントのボタンの頭文字と、「… でログイン中」（`docs/site-header-requirements.md` §8）。
- 管理画面の記事一覧と走り書きの一覧の著者。管理者にだけ出す。2 行目の、状態の札の後ろの先頭に置く。著者には自分の行しか出ないので出さない。
- 利用者の画面には使わない。一覧の 1 行目は表示名そのもの（空なら「（表示名なし）」）で、ログインの手段は 2 行目に別に出るためである。

### 9.8 Google Cloud の設定（オーナー）

- OAuth クライアントは「ウェブ アプリケーション」の種類で作る。承認済みのリダイレクト URI には、`http://localhost:3001/auth/google/callback` と `<SITE_ORIGIN>/auth/google/callback` の 2 つを登録する。
- `.env` に `GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET` を入れる。
- 同意画面は「テスト」のままにする。テストユーザーは 100 人まで登録できる。スコープが `openid`・`email`・`profile` だけなら、テストユーザーの許可は 7 日で切れない（Google Cloud のヘルプ https://support.google.com/cloud/answer/15549945 の publishing status の説明、2026-10-18 に確認）。
- `open` にするには、同意画面を「本番」にする必要がある。本番にするときに承認済みのドメインの所有の確認が要るかと、`*.ts.net` の名前で通るかは確かめていない。そのため、`open` への切り替えは、自分のドメインに移ってから行う（§9.10）。

### 9.10 先送り

- 役割の変更と、管理者の Google でのログイン。
- 停止中の著者の行をまとめて消す操作。アカウントの削除と、Google の連携の解除。
- 署名を一覧のカード、RSS、`og:` に出すこと。著者のページ。
- `docs/embed-requirements.md` §24.9 の「自分の記事 / 全記事」のタブ。
- アップロードの所有と、参照の表による掃除（`docs/project-status.md` §7.3）。
- 公開側のヘッダーのログインの入口と、同意画面の「本番」への切り替え。どちらも `open` に切り替えるとき、自分のドメインに移った後に行う（§9.8）。
- 招待のメールを送ること。
- `open` に切り替えるときの、保存する情報と記録の見直し。知らない人が書けるようになると、ログインできない人の本人確認、権利侵害の報告と開示請求に答えるための記録（IP アドレスなど）、問い合わせの受け方、利用規約が要る。ガジェッターは、使っていないメールのハッシュを消し、本人確認と開示請求に要るものだけを残している（https://gadgeteer.jp/u1/articles/4202 、2026-10-16）。招待制の間は、書く人を管理者が知っているので、どれも要らない。
