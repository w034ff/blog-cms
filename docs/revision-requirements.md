# リビジョン履歴 要件定義

- 状態: 実装済み（2026-09-22）
- 作成: 2026-09-22、「自動保存から復元する機能は要るか」の相談から
- 関連: `lib/revisions.ts`（版の保存・整理・戻す処理）、`lib/posts-write.ts`（版を残す呼び出し元）、`docs/editor-requirements.md` §12.27（公開スイッチ）、`scripts/gc-uploads.mts`

記事の過去の版を残し、著者がそこへ戻せるようにする。未公開の変更の破棄は、独立した機能ではなくこの履歴の一操作（公開中の版に戻す）として持つ。

---

## 1. 目的と前提

**前提**: 自動保存は保存先そのものに書く。下書きは本体の列に、公開済みの記事は `draft_content` に書き、編集画面はそこから開く。したがって「自動保存から復元するか」を尋ねる場面は無く、WordPress 型の復元プロンプトは採らない。

**目的**: 自動保存は上書きなので、次の 2 つが失われうる。

- 大きく消したあとにリロードした場合の、消す前の内容。同じセッションの中なら元に戻す（undo）で戻せるが、リロードで undo 履歴は消える
- 公開済みの記事の、前に公開していた版。更新と公開スイッチのオフ（§12.27）は本体の列を上書きする

加えて、公開済みの記事の書き直しを途中でやめる手段（未公開の変更の破棄）が無かった。

## 2. 決定

- **履歴を持ち、破棄はその一操作にする。** 公開済みの記事では本体の列がそのまま公開中の版なので、「公開中の版に戻す」は `draft_content` を空にすることと同じである。破棄を別の機能にすると、同じ操作が 2 つの名前で並ぶ。
- **戻す操作は公開しない。** 戻した内容は自動保存と同じ書き先に入り、公開は今までどおりヘッダの `更新` から行う。
- **戻す前の内容も必ず版として残す。** 戻す操作も元に戻せるので、確認ダイアログは置かない。
- **差分表示は持たない。** 著者が知りたいのは「この版で合っているか」であり、読める表示があれば足りる。

## 3. 版を残す時点

版は、失われうる内容が生まれる時点でだけ残す。定期的には残さない。

| 種類（`reason`） | いつ                                                                     | 何を                     |
| ---------------- | ------------------------------------------------------------------------ | ------------------------ |
| `publish`        | 公開済みの記事の本体の列が置き換えられる直前（更新・公開スイッチのオフ） | 置き換えられる公開版     |
| `session`        | エディタを開いてから最初の自動保存の直前                                 | 上書きされる保存先の内容 |
| `restore`        | 戻す操作の直前                                                           | 上書きされる保存先の内容 |

**公開した版は「置き換えられる直前」に残す。** 公開した時点で残す形にすると、この機能より前に公開した記事の版が一度も残らない。置き換えの直前なら、それらも最初の更新で残る。公開中の版は本体の列にあるので、履歴には入れない。下書きの初回公開では何も残さない — 置き換えられるのは下書きで、それは公開される内容そのものだからである。

**`session`** はクライアントが最初の自動保存にだけ `sessionStart: true` を付けて知らせる。保存に失敗したら次の保存にも付け続け、成功した時点で外す。

- 公開済みで `draft_content` が空の記事では残さない。上書きされるのは空の作業コピーで、公開中の版は本体の列に残っている
- 新規記事の最初の保存（行を作る保存）では残さない。上書きされる内容が無い
- 新規記事の最初の公開ではエディタが作り直される（§12.27「残っている挙動」）ので、次の自動保存がもう一度 `sessionStart` を送る。このとき公開済みで `draft_content` が空なので、上の規則で何も残らない

**重複は残さない**: 同じ枠（§4）の直前の版と中身が同じなら足さない。枠をまたいで比べないのは、`publish` の版が `session` の版と同じ中身だったときに、押し出されやすい `session` の枠にしか残らなくなるためである。比較は `lib/draft-content.ts` の `sameDraftContent` で、`hasUnpublishedEdits` と同じ関数を使う。

## 4. 保存と件数

**保存先**: テーブル `post_revisions`（`id`, `post_id`, `created_at`（エポックミリ秒）, `reason`, `content`（`DraftContent` の JSON））。`posts` の列にしないのは、1 記事に何件も付くためと、`posts` は末尾に列を足す形しか安全に変更できないためである。

**書き込み時に正規化する**: 本文の改行を LF に揃えてから保存する。公開経路はフォーム送信なので CRLF で届き、そのままだと直後の `session` の版と改行だけが違う版になり、重複の判定を素通りする。読むときは `normalizeDraftContent` を通す（後から足したフィールドが `undefined` で読める問題への手当て、`lib/posts.ts` と共通）。

**件数**: 記事ごとに、`publish` を 5 件、それ以外（`session`・`restore`）を合わせて 5 件残す（`REVISION_KEEP`、`lib/revisions.ts`）。上限を超えた古い版は、新しい版を足すのと同じトランザクションで消す。

- 種類で枠を分けるのは、編集のたびに増える `session` が公開版を押し出さないためである
- 日数では消さない。件数の上限で総量は「記事数 × 10 件」に頭打ちになり、日数の上限はそれを下げずに、久しぶりに直す記事の履歴だけを空にする
- 5 件は「使う頻度は低い」という前提で選んだ（2026-09-22）。3 件未満だと、戻して違ったので戻し直す、を 2 回するだけで探していた版が押し出される

**記事の削除**: `deletePost` が同じトランザクションで版も消す。外部キーの `ON DELETE CASCADE` には頼らない — テスト用 DB（`test/db.ts`）は `foreign_keys` を有効にしていないので、cascade に頼ったテストは何も測らない。

## 5. 戻す操作

**入口**: 記事の設定の「履歴」から、履歴のページ（`/admin/posts/<id>/revisions`）へ移る（`docs/editor-requirements.md` §12.31）。

- `unsaved` の間（自動保存の待ち・送信中・失敗）は押せない。送っていない編集を置き去りにしないためと、送信中の自動保存が戻した内容を後から上書きしないためである。自動保存が失敗しているあいだも押せないが、その原因（通信切れ・401）では戻す要求も同じ理由で失敗する
- まだ行が無い新規記事でも押せない

**履歴のページ**: 公開済みの記事では、先頭に「公開中の版」を置き、その下に版を新しい順に並べる。各行は日時（JST）・種類・タイトルを出し、表示のページへ移る。

**表示**: 下書きのプレビューと同じ経路で、`/posts/<slug>?rev=<id>`（公開中の版は `?rev=live`）が版の本文を公開ページと同じ描画で見せる。セッションが無いリクエストでは `rev` を無視する。上部の帯に「この版に戻す」ボタンを置く。見出しの下の日付は記事のもの（初回公開日と更新日）のままで、版の時点は帯が示す。

**戻す**: Server Action（`restoreRevisionAction`）が次を 1 つのトランザクションで行い、編集画面へリダイレクトする。

1. 保存先の今の内容を `restore` の版として残す（重複なら残らない）
2. 選んだ版を保存先に書く。公開済みの記事では `draft_content` に書き、中身が公開中の版と同じなら `null` にする。下書きでは本体の列に書く

編集画面へは新しいページとして移るので、エディタは戻した内容で作り直される。再検証（`revalidateBlog`）は呼ばない — 公開面は何も変わらない。

**公開中の版に戻す**（＝未公開の変更の破棄）は `draft_content` を `null` にする。下書きの記事には公開中の版が無いので、この行は出ない。

## 6. 画像

アップロード画像のファイル名は中身の SHA-256 なので、同じ画像を参照する版がいくつあってもファイルは 1 つである。履歴が増やすのは、今の版から消したが残っている版には載っている画像だけで、その量も §4 の件数で頭打ちになる。

`scripts/gc-uploads.mts` は `post_revisions.content` も参照として数える。数えないと、戻した版の画像が消えている。

## 7. 導入

新しいテーブルはマイグレーション（`drizzle/0007_*.sql`）で作る。**本番の DB へは、コードを入れ替える前に `npm run db:backup && npm run db:migrate` を実行する。** テーブルが無いまま新しいコードが動くと、公開と最初の自動保存が失敗する。E2E は `e2e/prepare-db.mts` がコピーにマイグレーションを当てるので、手元の DB の状態に依らない。
