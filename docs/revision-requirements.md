# リビジョン履歴 要件定義

- 状態: 実装済み（2026-09-22）
- 作成: 2026-09-22、「自動保存から復元する機能は要るか」の相談から
- 関連: `lib/revisions.ts`（版の保存・整理・戻す処理）、`lib/posts-write.ts`（版を残す呼び出し元）、`docs/editor-requirements.md` §12.27（公開スイッチ）、`scripts/gc-uploads.mts`

記事の過去の版を残し、著者がそこへ戻せるようにする。未公開の変更の破棄は、独立した機能ではなくこの履歴の一操作（公開中の版に戻す）として持つ。

---

## 1. 目的と前提

**前提**: 自動保存は保存先そのものに書く。下書きは本体の列に、公開済みの記事は `draft_content` に書き、編集画面はそこから開く。したがって「自動保存から復元するか」を尋ねる場面は無く、WordPress 型の復元プロンプトは採らない。

**目的**: 公開済みの記事の、前に公開していた版を取り戻せるようにする。更新と公開スイッチのオフ（§12.27）は本体の列を上書きするので、読者に見えていた内容はそれまで二度と戻らなかった。加えて、公開済みの記事の書き直しを途中でやめる手段（未公開の変更の破棄）が無かった。

**書きかけの内容は対象にしない**（2026-09-22）。当初は編集を始めるたびに上書き前の内容を `session` の版として残していたが、外した。役に立つのは「大きく消し、気付かないまま編集を始め直し、後で気付く」ときだけで、利用者が 1 人のこのブログでは想定しにくい。同じ編集の中は元に戻す（undo）が、それより後は DB のバックアップが受け持つ。残す数を 1 件に減らす案も検討したが、編集を始め直した時点で置き換わるのでその場面すら救えず、量と一覧の煩雑さだけが残るので採らなかった。

## 2. 決定

- **履歴を持ち、破棄はその一操作にする。** 公開済みの記事では本体の列がそのまま公開中の版なので、「公開中の版に戻す」は `draft_content` を空にすることと同じである。破棄を別の機能にすると、同じ操作が 2 つの名前で並ぶ。
- **戻す操作は公開しない。** 戻した内容は自動保存と同じ書き先に入り、公開は今までどおりヘッダの `更新` から行う。
- **戻す前の内容も必ず版として残す。** 戻す操作も元に戻せるので、確認ダイアログは置かない。
- **差分表示を持つ**（§9）。戻す操作はエディタの内容を置き換えるので、押す前に何が変わるかを見せる。当初は「この版で合っているか」は読める表示で足りるとして持たなかったが、置き換えで消えるものは本文を読んでも分からないので加えた（2026-09-23）。

## 3. 版を残す時点

版は、失われうる内容が生まれる時点でだけ残す。定期的には残さない。

| 種類（`reason`） | いつ                                                                     | 何を                     |
| ---------------- | ------------------------------------------------------------------------ | ------------------------ |
| `publish`        | 公開済みの記事の本体の列が置き換えられる直前（更新・公開スイッチのオフ） | 置き換えられる公開版     |
| `restore`        | 戻す操作の直前                                                           | 上書きされる保存先の内容 |

自動保存は版を残さない。

**公開した版は「置き換えられる直前」に残す。** 公開した時点で残す形にすると、この機能より前に公開した記事の版が一度も残らない。置き換えの直前なら、それらも最初の更新で残る。公開中の版は本体の列にあるので、履歴には入れない。下書きの初回公開では何も残さない — 置き換えられるのは下書きで、それは公開される内容そのものだからである。

**重複は残さない**: 同じ種類の直前の版と中身が同じなら足さない。種類をまたいで比べないのは、公開版が `restore` の版と同じ中身だったときにも、公開版として残すためである。比較は `lib/draft-content.ts` の `sameDraftContent` で、`hasUnpublishedEdits` と同じ関数を使う。

## 4. 保存と件数

**保存先**: テーブル `post_revisions`（`id`, `post_id`, `created_at`（エポックミリ秒）, `reason`, `content`（`DraftContent` の JSON））。`posts` の列にしないのは、1 記事に何件も付くためと、`posts` は末尾に列を足す形しか安全に変更できないためである。

**書き込み時に正規化する**: 本文の改行を LF に揃えてから保存する。公開経路はフォーム送信なので CRLF で届き、自動保存（戻す操作が置き換えるもの）は LF のままなので、そのままだと同じ文章が改行だけ違う版になり、重複の判定を素通りする。読むときは `normalizeDraftContent` を通す（後から足したフィールドが `undefined` で読める問題への手当て、`lib/posts.ts` と共通）。

**件数**: 記事ごとに、`publish` を 5 件、`restore` を 3 件残す（`REVISION_KEEP`、`lib/revisions.ts`）。上限を超えた古い版は、新しい版を足すのと同じトランザクションで消す。

- 種類で枠を分けるのは、戻す操作を何度か試しても公開版が押し出されないためである
- 日数では消さない。件数の上限で総量は「記事数 × 8 件」に頭打ちになり、日数の上限はそれを下げずに、久しぶりに直す記事の履歴だけを空にする
- `publish` の 5 件は「使う頻度は低い」という前提で選んだ（2026-09-22）。探すのはたいてい直前の 1〜2 件である。誤字直しのような小さな更新も 1 件ずつ使うので、公開後に 5 回直すとそれより前は消え、そこから先は DB のバックアップが受け持つ
- `restore` は直前の復元・破棄を取り消すための控えで、要るのはほぼ最新の 1 件なので 3 件にした（2026-09-22）。3 件あれば、戻して違ったので戻し直す、を 2 回しても最初の控えが残る

**記事の削除**: `deletePost` が同じトランザクションで版も消す。外部キーの `ON DELETE CASCADE` には頼らない — テスト用 DB（`test/db.ts`）は `foreign_keys` を有効にしていないので、cascade に頼ったテストは何も測らない。

**版を手で消す操作は持たない**（2026-09-22）。件数の上限で古い版は自動で消え、履歴のページの操作をすべて取り消せるものに保つためである。秘密や個人情報を公開してしまい、本文から消しても版に残る場面が起きたら、1 件ずつではなく「この記事のリビジョンをすべて削除」を 1 つだけ足す。

## 5. 戻す操作

**入口**: 記事の設定の「リビジョン履歴」から、履歴のページ（`/admin/posts/<id>/revisions`）へ移る（`docs/editor-requirements.md` §12.31）。

- `unsaved` の間（自動保存の待ち・送信中・失敗）は押せない。送っていない編集を置き去りにしないためと、送信中の自動保存が戻した内容を後から上書きしないためである。自動保存が失敗しているあいだも押せないが、その原因（通信切れ・401）では戻す要求も同じ理由で失敗する
- まだ行が無い新規記事でも押せない

**履歴のページ**: 題は「リビジョン履歴」で、その下に記事のタイトルを出す — タイトルが版をまたいで変わらないと、ほかにどの記事の履歴かを示すものが無い。公開済みの記事では「公開中の記事」を枠で囲んだ 1 行として一覧から離して置き（過去の時点ではなく今の状態なので）、未公開の変更があるあいだは記事一覧と同じ印「未公開の変更」を付ける。その下の小見出し「過去のリビジョン」に版を新しい順に並べ、これも枠で囲む — 押せる行はすべて枠の中という規則で揃える。公開中の記事だけに枠がある形は、同じ種類の行が別の部品に見えた（2026-09-22、スクショで比較）。どの行も右端に `›` を付ける — タッチ端末にはカーソルを乗せたときの背景色が無く、押せる印がほかに無い。何がいつ残るかの説明と公開中の記事の最終更新日時も試したが、一覧が始まるまでの行が増えるだけなので置かない（2026-09-22）。版が 1 件も無いときは「リビジョンはまだありません。」とだけ出す。下書きでは空のページになるが、ドロワーの行を隠す案は、件数を編集画面まで運ぶ手間と「件数はエディタが開き直されるときにしか変わらない」という見えない前提に見合わないので採らなかった（2026-09-22）。各行は 1 行の中に、日時（JST。今年の日付は年を省く — どの行も同じ 4 桁になるだけなので）・種類の印（「以前の公開記事」は緑、「復元する前」は灰色）を並べ、表示のページへ移る。タイトルは、エディタで今開く記事のタイトルと違う行でだけ印の後ろに出す — 版をまたいでほとんど変わらず、どの行にも出すと版を見分ける役に立たない。本文の文字数と増減を 2 行目に出す形も試したが外した（2026-09-22）。増減が効くのは大きく削った版を探すときで、それは外した `session` の版の用途だった。版を見分けるのはプレビューで、一覧はそこへの入口である。種類は `publish` が「以前の公開記事」、`restore` が「復元する前」。今エディタで開く内容と同じ行には、右端の `›` の手前に空色のチェックを付ける（緑は「成功」と読め、灰色は隣の `›` と紛れるため）（2026-09-23）— 復元した直後にどの版にいるかが分かり、開いても「復元する」が押せない行を開く前に見分けられる。種類の印と見分けるため文字ではなくアイコンにし、「編集中と同じ」はスクリーンリーダー向けの文字とツールチップで持つ。判定はプレビューの「復元する」を押せなくする判定（`diffRevision(…).identical`）と同じものを使い、両者が食い違わないようにする。

**履歴のページはエディタと同じ固定ヘッダーを持ち、左端の ← で編集画面へ戻る**（2026-09-23）。ヘッダーの帯はプレビューと共有する（`components/RevisionHeaderBar.tsx`）ので、エディタ・履歴・プレビューのどこへ移ってもヘッダーは入れ替わらず、← は 3 画面とも同じ位置に来る（幅 360px・1280px で高さと ← の位置が一致することを実測）。見出し「リビジョン履歴」と記事のタイトルは本文側に置く。2026-09-22 には右上の文字「編集に戻る」のままとしていたが、それはプレビューがまだ公開ページの帯だったときの比較で、プレビューがエディタのヘッダーになってからは履歴だけが別の見た目になっていたので揃えた。

**画面の文言に「版」を使わない**（2026-09-22）。書籍や仕様書の言葉で、画面の文章では見慣れない。この文書では内部の用語として使い続ける。

**表示**: `/admin/posts/<id>/revisions/<id>`（公開中の版は `…/revisions/live`）が、版の本文を公開ページと同じ描画で見せる。記事本体の描画は `components/PostArticle.tsx` を公開ページと共有し、リンクカードの解決も同じ `lib/resolve-card.ts` を通る。管理画面の下にあるので、セッションの確認は管理画面のレイアウトが受け持つ。サイトのヘッダー（Tech Blog・Tags など）は出さず、エディタと同じ形の固定ヘッダーを置く: 左にエディタと同じ位置の ←（リビジョン履歴へ。開いた一覧へ一つ戻る操作なので、時計ではなくエディタと同じ ← にした — 2026-09-23）と鉛筆（編集に戻る）、「差分／本文」、右端に実行ボタン（「復元する」、公開中の記事では「変更を破棄」）。画面の名前（「プレビュー」）は置かない — エディタと履歴のヘッダーも名前を持たず、何の画面かは ← と「差分／本文」と実行ボタンが示す。種類の色も時刻も出さない（一覧で選んで開くため）。実行ボタンの文言は、幅 360px で 1 行に収まるよう決めた（2026-09-23 実測。「未公開の変更を破棄」は 156px あり、幅 455px 前後まで見出しを 2 行にしていた）。何の変更かは差分の上の文が言う。見出しの下の記事の日付（初回公開日と更新日）は出さない — 版の見出しの下では版の日付に読め、版の時点は一覧で見られる。

**公開ページの帯から移した**（2026-09-23）。当初は下書きのプレビューと同じ `/posts/<slug>?rev=` に帯を載せていたが、帯はページの先頭にしかなく、長い記事を読み進めると「復元する」も「本文／差分」も画面の外に出た。サイトのヘッダーはレイアウトが描くので `?rev=` からは差し替えられず、公開ページの見た目を CSS で消す案は採らなかった。固定ヘッダーにしたことで、帯の段組み・色・戻り先の置き場所の議論も同時に片付いた。版の名前（時刻）も種類も文字では書かない — 著者は時刻と種類を示した一覧から選んで開いている。種類は一覧の印と同じ色の縦棒にだけ残す（`components/revision-kinds.ts` で共有）。

**戻す**: Server Action（`restoreRevisionAction`）が次を 1 つのトランザクションで行い、編集画面へリダイレクトする。

1. 保存先の今の内容を `restore` の版として残す（重複なら残らない）
2. 選んだ版を保存先に書く。公開済みの記事では `draft_content` に書き、中身が公開中の版と同じなら `null` にする。下書きでは本体の列に書く

編集画面へは新しいページとして移るので、エディタは戻した内容で作り直される。再検証（`revalidateBlog`）は呼ばない — 公開面は何も変わらない。

**公開中の記事を復元する**（＝未公開の変更の破棄）は `draft_content` を `null` にする。下書きの記事には公開中の版が無いので、この行は出ない。

## 6. 画像

アップロード画像のファイル名は中身の SHA-256 なので、同じ画像を参照する版がいくつあってもファイルは 1 つである。履歴が増やすのは、今の版から消したが残っている版には載っている画像だけで、その量も §4 の件数で頭打ちになる。

`scripts/gc-uploads.mts` は `post_revisions.content` も参照として数える。数えないと、戻した版の画像が消えている。

## 7. 導入

新しいテーブルはマイグレーション（`drizzle/0007_*.sql`）で作る。**本番の DB へは、コードを入れ替える前に `npm run db:backup && npm run db:migrate` を実行する。** テーブルが無いまま新しいコードが動くと、公開済みの記事の更新・非公開と、戻す操作が失敗する。E2E は `e2e/prepare-db.mts` がコピーにマイグレーションを当てるので、手元の DB の状態に依らない。

## 9. 差分

**決定**（2026-09-23）: プレビューのヘッダーに「差分」と「本文」の切り替えを置き、差分では本文の位置に、今エディタで開く内容からそのリビジョンへの差分を出す。見出しとヘッダーはそのまま残す。プレビューは差分で開き、本文は `?view=body` である — プレビューを開く目的はボタンを押すかどうかの判断で、それに答えるのは差分だからである。当初は本文で開いていた（2026-09-23 に変更）。

- **比べる相手は今の内容**である。判断が要るのは復元するときで、そのとき知りたいのは「復元したら何が変わるか」だからである。公開中の記事では、これがそのまま未公開の変更の中身になり、破棄するかどうかの材料になる。向きはボタンを押す前から後で、今の内容にしか無いもの（押すと消えるもの）が削除（赤）、リビジョンにしか無いもの（押すと戻るもの）が追加（緑）として出る。差分の上には「復元すると、次のように変わります。」（公開中の記事では「未公開の変更を破棄すると、次のように変わります。」）の文と、「− 消える　+ 戻る」の凡例を差分と同じ地の色で置く — たまにしか開かない画面なので、矢印の向きを読み解かせず、色の意味をそのまま言う。同じなら「復元しても何も変わりません。」（公開中の記事では「破棄しても…」）だけを出し、「復元する」は押せない。
  向きは当初、古い方から新しい方（リビジョン → 今の内容）だった。公開中の記事だけ未公開の変更を追加として見せる案もあったが、ページで色の意味が逆になり、たまにしか開かない画面では覚えていられないので、全体をこの向きに揃えた（2026-09-23）。
- **描画した表示ではなく、保存した markdown のまま出す。** 描画した表示の上に色を付ける形は、埋め込みやカードのように比べる文字を持たないブロックを扱えず、手間も数倍になる。diff2html は使わない — コードレビューの見た目がこの画面から浮くうえ、依存が 2 つになる。
- **計算**（`lib/revision-diff.ts`）: `diff`（jsdiff、9.0.0）で行単位に比べ、隣り合う削除と追加を 1 つの変更として組にし、その中を `DIFF_TOKEN` の単位で比べる。ASCII の英字・数字・`_` の並びは 1 語、それ以外は 1 文字が 1 単位である。日本語には単語の区切りの空白が無いので文字で比べるが、識別子や言語名まで文字で比べると、2 つの名前にたまたま共通する文字だけが残って細切れになる（`diff_python` → `ts` で `t` が残った。2026-09-29、UI 評価）。組の長さが `DIFF_INLINE_LIMIT` を超えると単位ごとの比較はやめて行ごと出す（長い別物どうしの細かい差分は遅く、細切れで読めない）。変わらない部分は変更の前後 `DIFF_CONTEXT_LINES`（2 行）を残して「N 行省略」と畳む。畳んだ行も結果に持ち、`<details>` で開ける。本文以外（タイトル・カテゴリ・タグ・サムネイル）は違う項目だけ「前 → 後」で並べる。
- **表示**（`components/RevisionDiffView.tsx`）: 変更ごとに前と後を赤と緑の地の 2 段で出し、行頭に − と + を置く（色だけに頼らない）。変わった文字は `<del>` と `<ins>`。スクリーンリーダーはどちらも読み上げないので、− と + の代わりに視覚的に隠した「削除:」「追加:」を置く。保存した markdown をそのまま見せるので等幅フォントで出す — コードブロックのインデントや表の `|` はそうでないと揃わない。
