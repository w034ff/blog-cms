## 1. 目的と非目標

**目的**: 著者が任意のテキストにリンクを付け・URL を直し・リンクを外せるようにする。読者はそれを公開ページで辿れる。

**非目標**（この文書では対象外）:

- 記事間リンクの補完・記事タイトルの自動取得（内部リンクは相対パスや `#見出し` を手書きする。§5.4 の入力ルール（2026-08-17）と §5.5 のバブル（2026-08-11）がこれを成立させている。§2.1.1）
- リンクカード／URL の展開表示（Zenn の `@[card]` に相当するもの）— 2026-08-12 に `docs/link-card-requirements.md` へ分離した。あちらが決めたのは内部記事のカードと保存形式で、外部 URL のカードは同 §8 で延期している
- リンク切れ検査（理由を 2026-08-27 に書き足した。**外部と内部で別の話であり、非目標なのは外部のほうである**）
  - **外部は精度が構造的に出ない。** §5.5.10 のタイトル取得を作るとき 10 サイトを実測して、2 件が Cloudflare の 403 を返した — ブラウザの UA を騙っても同じである。検査は同じ応答を見るので、この 2 件を「切れている」と報告する。10 件に 2 件の誤報は読まれなくなる検査であり、しかも著者に直せる種類の指摘でもない。「まだ早い」ではなく、信号そのものが当てにならない
  - 内部は安く、部品は既にある — `headingForFragment`（§5.5.18）、公開側の出力と照合して固定してある `document-headings.ts`（§5.5.17）、`/posts/<slug>` の存在確認はカードの経路が既にやっている DB 参照 1 本である。ネットワークに出ないので誤報が原理的に無い。**それでも今は作らない**: 2026-08-27 の集計で投稿 3 件・テキストリンク 5 本（全部が投稿 36 の中、fragment は 1 本）で、§0 の判断基準がそのまま当たる。作る価値が出るのは記事どうしが実際に参照し合い始めたときで、最初の版は「検査」ではなく、解決しない fragment を公開の経路が警告する形でよい
  - 塞がっていない穴は §5.5.18 が名指ししている — **見出しを改名すると既存のリンクは黙って死に、今の検出点はバブルの「見出しへ移動」を押すことだけである**
- `title` 属性を著者が編集する UI（§5.3 で「壊さない」ことだけ要求する）

## 2. 現状（2026-08-09）

### 2.1 リンクが付く経路は 4 つ、任意のテキストに付くのは 1 つだけ

`link` マークは StarterKit 経由で登録されている（`@tiptap/starter-kit/dist/index.js:70` が `Link.configure(options.link)` を push、`PostEditor.tsx:219-234` の `configure` は `link: false` を渡していない）。他の多くのノード／マークは明示的に無効化して自前版に差し替えてあるのに、link だけは方針が書かれないまま既定値で残っている — この文書はその穴を埋めるものでもある。

**経路には (a)〜(d) の記号を使う。** §3 以降の①②は「決定した項目」の番号であり、別物である。

| 経路                           | 機構                              | 任意のテキストに付くか       |
| ------------------------------ | --------------------------------- | ---------------------------- |
| (a) 選択範囲に URL をペースト  | `pasteHandler`                    | **○ 単一段落の選択に限る**   |
| (b) URL をタイプ               | `autolink`                        | × リンク文字列 = URL         |
| (c) URL を含む文章をペースト   | `addPasteRules` / `markPasteRule` | × URL 部分だけがリンク化     |
| (d) `<a>` 入り HTML をペースト | `parseHTML: 'a[href]'`            | × 選択範囲を置換して差し込む |

(a) は見た目より狭い。`pasteHandler`（`handlePasteLink` という `PluginKey` を持つプラグイン、`extension-link/dist/index.js`）は選択が空でないことに加えて **`item.value === textContent`** を要求する。ペースト内容が URL ちょうど 1 個でないと発動せず、末尾に空白が付いていたり `参考: https://…` の形だと、リンクにならず選択範囲がそのテキストで置換されるだけである。

**2026-08-25 に、選択範囲が複数段落にまたがるときは (a) 自体が発動しないよう狭めた（§11）。** `pasteHandler` は選択の広さを一切見ないので、Ctrl+A で投稿全体を選んで URL を貼ると全段落がそれぞれ独自にリンク化していた——しかもテキストは置き換わらず、元の段落の文言がリンクの見出しとして残る形で。単一段落に収まる選択では (a) は今までどおり動く。

(c) は (a) と別のプラグインで、**選択が空でも発動する**。ただし生成されるのは常にリンク文字列 = URL のリンクである。

### 2.1.1 内部リンクを作る経路が無い（実測 2026-08-11）

(a)(b)(c) は 3 つとも linkifyjs の判定を通る。 そして linkifyjs は URL とメールアドレスしか見つけないので、このブログが実際に書きたい 2 種類はどれも通らない:

| 文字列                | `linkifyjs.find()` | 選択範囲にペーストした結果（E2E）      |
| --------------------- | ------------------ | -------------------------------------- |
| `/posts/foo`          | `[]`               | 選択が置換されるだけ。リンクにならない |
| `#見出し`             | `[]`               | 同上                                   |
| `https://example.com` | url として検出     | `link("ここ")`（経路 (a)）             |

2026-08-11 の時点では `[](  )` と手で打つ道も塞がっていた（§2.2.1。開けたのは §5.4、2026-08-17）。経路 (d)（`<a>` 入りの HTML をクリップボードに持っている場合）は使えるが、これも fragment には使えない:

著者が自分の公開ページから見出しリンクをコピーしても、**経路 (d) が受け取る href は `#user-content-見出し` ではない。ブラウザはコピー時に解決済みの `a.href` プロパティを直列化するので、渡ってくるのは絶対 URL である**（実測 2026-08-27、基準 16d）— `https://…/posts/hello-world#user-content-%E3%81%AF…` の形になる。機構はリテラルの属性ではなくプロパティを書くことにあり、したがって経路 (d) は相対パスも裸の fragment もそのままでは運べない。

そのため二重接頭辞は起きない。`rehypeClobberFragmentLinks` は `href.startsWith('#')` でしか働かないので、絶対 URL は素通りする。代わりに起きるのは、同じ文書の中の跳躍だったものが、自分のサイトへの外部リンクになることである — §7.2 の規則 1 が `http` で始まる href に当たるので、新しいタブでページごと開く。リンク自体は当たる（`user-content-…` は sanitize が実際に付けた id である）。

**著者はオリジンを手で消している**（2026-08-27、著者報告。`data/blog.db` の投稿 36 に `[aa](/posts/f377f7a9a768a5b4d6f2#user-content-aaaaaaaaaaaaaaaaaaaaa)` として残っている）。消せば `http` で始まらなくなるので、§7.2 の規則 1 に当たらず同一タブのサイト内リンクに戻る。**つまりこの段落の「知っている必要がある」は生きていて、剥がす対象が変わっただけである** — `user-content-` ではなくオリジンのほうである。

2026-08-11 から 2026-08-27 まで、この段落は「href は `#user-content-見出し` で、貼ると接頭辞が二重に付く」と書いていた（`cf34f57`）。その二重接頭辞は今も真だが、それは markdown にその文字列を書いた場合の話である（§2.3 の表の最終行はそのまま正しい）。**偽だったのは、経路 (d) がその入力を作るという因果のほうで、当時それを測った器具が合成 `ClipboardEvent` だったことによる**（§9）。

§1 が非目標の側で前提にしている書き方（相対パスを手書き）は、この時点では成立していなかった。

**この穴は 2026-08-11 に §5.5 のバブルで塞いだ。** URL 入力欄に `#見出し` / `/posts/foo` を直接打てる（`setLink` の `isAllowedUri` はスキームの無い相対パスと fragment を通すので、狭めた述語の側でも落ちない — 実測）。**ただし上の「公開ページから `#user-content-…` をコピーすると接頭辞が二重に付く」は変わっていない。** 入力欄は著者が打った文字列をそのまま href にするだけで、`user-content-` を剥がしはしない。

**2026-08-17 に 2 本目の経路が入った。** §5.4 の入力ルールで、`[断片](#見出し)` と打てば同じリンクになる。§1 が前提にしていた「手書き」が、書いたとおりに成立するようになったのはこちらである。

UI は存在しない。 `setLink` / `toggleLink` / `unsetLink` コマンドは実装されているが、呼ぶ導線がツールバー（`components/editor/Toolbar.tsx`）にもスラッシュメニュー（`slash-command.ts`）にも無い。`extension-link` に `addKeyboardShortcuts` が無いので Mod-k も無反応である。

| オプション             | 既定値                                               |
| ---------------------- | ---------------------------------------------------- |
| `autolink`             | `true`                                               |
| `linkOnPaste`          | `true`                                               |
| `openOnClick`          | `true`                                               |

`HTMLAttributes` の `target` / `rel` は**エディタの DOM 上にしか出ない**。公開 HTML には出ない（§2.3）。

### 2.2 保存形式 — markdown の往復

保存側は `tiptap-markdown` が `defaultMarkdownSerializer.marks.link` を使う（`tiptap-markdown.es.js:701`）ので `[text](href "title")` になる。`title` も直列化される。ただしリンクの文字列が href とちょうど同じときは `<https://example.com>`（山括弧の autolink 形式）になる — 2026-08-09 実測。経路 (b)(c) が作るリンクは常にこの形である。公開側は remark-gfm がどちらも同じくリンクにするので、見た目に差は出ない。`target` / `rel` は markdown に書けないので落ちる — これは損失ではなく、そもそも公開されない属性である（§2.3）。

読み込み側は markdown-it が解釈する。`Markdown.configure({ linkify: false })`（`PostEditor.tsx:266`）は**裸 URL の自動リンクだけを切るもので、`[]()` 記法には効かない** — markdown-it に `linkify:false` を渡しても `[任意のテキスト](https://example.com)` は `<a href>` になることを実測済み。

**帰結**: text ノードとして残った `[text](url)` は、保存の時点で `\[text\](url)` に潰れる（§2.2.1）。打った記法を受け止めるのは §5.4 の入力ルールであり、打っている最中に片が付く — 保存の往復には何も期待していない。`transformPastedText` / `transformCopiedText` は既定 `false` のまま（`tiptap-markdown.es.js:923`）なので、**ペーストした** `[text](url)` は今もリテラルのテキストである。

### 2.2.1 直列化は `[` `]` を無条件にエスケープする（実測 2026-08-11、§5.4 の側は 2026-08-17）

`e2e/editor-link-markdown-syntax.spec.ts` で測った:

| 操作                                             | `doc`                        | `getMarkdown()`                        |
| ------------------------------------------------ | ---------------------------- | -------------------------------------- |
| `[断片](#見出し)` とタイプ                       | `paragraph(link("断片"))`    | `[断片](#見出し)`                      |
| ↑ を保存 → 再読込                                | `paragraph(link("断片"))`    | `[断片](#%E8%A6%8B%E5%87%BA%E3%81%97)` |
| `[断片](#見出し)` を**エスケープ無しで**読み込み | `paragraph(link("断片"))`    | 同上                                   |
| `[電話](tel:…)` とタイプ（§5.4 が断る記法）      | `paragraph("[電話](tel:…)")` | `\[電話\](tel:…)`                      |

**機構**: text ノードの直列化は `state.text(escapeHTML(node.text))`（`tiptap-markdown.es.js:628`、第 2 引数省略なので escape は `true`）で、`prosemirror-markdown` の `esc()` は `[` と `]` を**無条件に**エスケープする（`dist/index.js:821`。`startOfLine` 条件付きの側ではない）。text のまま残った記法を markdown-it が `[]()` として読む機会は永久に来ない — 4 行目がそれである。

**このエスケープは直さない。** リンクカードがこの上に建っており（`docs/link-card-requirements.md` §4.1 (b)）、脚注が専用の node serializer で迂回しているのも同じ理由である（`e2e/editor-footnote.spec.ts:58` の `not.toContain('\\[')` がそれを固定している）。壊れているのがパーサではなく直列化側であることは 3 行目の対照実験が示していて、**§5.4 が入力ルールという形になったのはこの非対称のためである** — 直せる側（打っている最中）で答え、直さない側（保存）には触れていない。

2026-08-11 の実測が消したもの: §2.2 は当初「打って保存 → 再読込で初めてリンクになる」という 2 段階の迂回路を想定していた。**その迂回路は無い。** 保存された `\[断片\](#見出し)` は再読込しても同じ文字列に戻るだけで、4 行目は今もそう振る舞う。

括弧の中の URL は autolink されない。`autolink` は URL の後ろに語境界を要求し、直後に打たれた `)` はそれではない。`[ここ](https://example.com)` がリンクになるのは入力ルールの仕事であって、autolink の仕事ではない。

本文の CRLF 化（`form-submission-crlf-body.md`）はこの結論に影響しない — ブラケットのエスケープは改行コードと無関係なので、`setContent` による保存 → 再読込の再現は忠実である。

### 2.2.2 fragment を含むリンクは往復で percent-encode される（実測 2026-08-11）

上の表の 2 行目と 3 行目。`[断片](#見出し)` を読み込むと markdown-it が href を正規化し、書き戻しは `[断片](#%E8%A6%8B%E5%87%BA%E3%81%97)` になる。打った直後の保存形は読める形のままなので（1 行目）、**この書き換えは最初の再読込で起きる。**

**公開結果は変わらない** — 両形式とも `#user-content-%E8%A6%8B%E5%87%BA%E3%81%97` に落ちることを `renderMdxToHtml()` で実測した（§2.3 の表）。

**保存形式は open/close について冪等ではない。ただし書き換えは自発的には起きない**（2026-08-27 実測、`e2e/editor-fragment-encode.spec.ts`）。記事を開いて何も触らなければ、encode された形はエディタの中に留まり、保存本文は読める形のまま残る — オートセーブが arm するのは編集（`onDirty`）であって、文書の読み込みはそれではない（基準 15b）。**書き換えが載るのは著者の次の編集である。** 別の段落を 1 つ足しただけの保存でも本文は丸ごと書き戻されるので、触っていないリンクの行が `#見出し` から `#%E8%A6%8B%E5%87%BA%E3%81%97` に変わる（基準 15c）。**著者が編集していない行が差分に出る** — この節が書かれているのはそのためである。

2026-08-11 から 2026-08-27 まで、この節は「開いて放置するだけで書き換わる」と書いていた。測っていなかったのはそこだけで、機構（読み込み時の `normalizeLink`）は当時から正しい。 実害は「著者の操作なしに diff が出る」から「著者の次の無関係な編集に相乗りする」に狭まっている。

### 2.4.1 2 つのリストの出所（判断の前提）

**どちらが「正しい」というものではない。別の系譜のリストが両端に置かれているだけである。**

- 公開側は GitHub の方針である。`hast-util-sanitize/lib/schema.js` の `defaultSchema` には `Follows GitHub style sanitation.` と書いてある。`irc` / `ircs` が入っていることがこのリストの年代を示している。GitHub の脅威モデルは「見ず知らずの他人が書いた markdown を大量の閲覧者に描く」であり、`tel:` に電話をかけさせる・`sms:` に本文を仕込ませるのは、その規模では濫用経路になる。コード実行の穴ではなく、プラットフォーム上の濫用対策としての判断である。
- エディタ側は汎用 HTML サニタイザ系統の顔ぶれで、`tel` / `sms` / `callto` / `cid` を含む。

`tel:` は RFC 3966 の正規のスキームであり、単著のブログで危険な要素は何もない。 したがって塞ぐ理由は「危険だから」ではなく「**このブログでは使わないから**」である。将来 `tel:` リンクを書きたくなったら、この判断はセキュリティ判断ではないので、素直に公開側（sanitize のスキーマ）を広げてよい。

### 2.5 VS Code からのペーストがコードブロックになっていた（修正済み 2026-08-09、§2.5.2）

**これはリンク機能の不具合ではない。** あらゆるペーストに効くもので、リンクはたまたまこれを踏んだ入口である。

**現象**: VS Code（および Cursor / VSCodium など Monaco 系）でコピーしたテキストをエディタに貼ると、コードブロックになる。URL 1 個でもそうなる。2026-08-09 に E2E で再現測定した（§2.5.1）。

**機構**: `@tiptap/extension-code-block` に組み込みの `codeBlockVSCodeHandler`（`dist/index.js:284-309`）。

```js
const text = event.clipboardData.getData('text/plain');
const vscode = event.clipboardData.getData('vscode-editor-data');
const language = vscode ? JSON.parse(vscode).mode : undefined;
if (!text || !language) return false;
// → 内容を見ずに codeBlock を作り replaceSelectionWith
```

判定は **`vscode-editor-data` というクリップボード形式の有無だけ**で、貼り付ける中身は一切見ていない。VS Code はコピー時にこの形式を必ず付ける。ブラウザのアドレスバーや Web ページからのコピーには付かないので、同じ URL でもコピー元によって結果が変わる。

コードブロックの `language` はコピー元ファイルの言語（`mode`）になる。この文書からコピーした URL なら `markdown` になる。

**このプラグインは自前の code block にも生きている。** `CodeBlockWithLanguage` は `addProseMirrorPlugins` で `...(this.parent?.() ?? [])` として親のプラグインを引き継いでいる（`code-block-extension.ts:523`）。

### 2.5.1 実測（2026-08-09、E2E で `vscode-editor-data` 付きのペーストを合成）

| 選択     | text/plain         | VS Code 形式 | 結果                                             |
| -------- | ------------------ | ------------ | ------------------------------------------------ |
| なし     | URL 1 個           | あり         | `codeBlock`（`language: "markdown"`）            |
| あり     | URL 1 個           | あり         | **`link("ここ")`** — リンクになる                |
| あり     | URL 1 個           | なし         | `link("ここ")` — 経路 (a) の基準線               |
| あり     | `const x = 1;`     | あり         | `codeBlock` — **選択していた「ここ」は消える**   |
| あり     | URL + 末尾スペース | あり         | `codeBlock` — 同上                               |
| あり     | URL + 末尾スペース | なし         | 選択が置換され、URL 部分だけリンク化（経路 (c)） |
| コード内 | URL 1 個           | あり         | そのまま挿入（`isActive` で早期 return）         |

**経路 (a) は壊れていない。** リンクの `handlePaste` が先に訊かれるため、選択があって貼り付け内容が URL ちょうど 1 個なら、コピー元が VS Code でもリンクになる。

**順序の理由**（実測: `handlePasteLink` が index 5、`codeBlockVSCodeHandler` が index 33）: ExtensionManager は `sortExtensions([...this.extensions].reverse())` の順にプラグインを集める（`@tiptap/core/dist/index.js:4547`）。反転が先、優先度のソートが後なので、配列上の位置ではなく優先度が効く。`Link` は `priority: 1000`（dist の字面は `priority: 1e3`。`extension-link/dist/index.js:240`）で既定の 100 を持つ全員より前に出る。

> **注意**: 「配列の後ろにあるものが先に訊かれる」という規則（`PostEditor.tsx:256-260` が IsolatingBoundary の位置について述べているもの）は**優先度が同じ者どうしの間でしか成り立たない**。優先度を明示している拡張はその規則の外にある。

実害はここにある: リンクの `handlePaste` が断る形（選択が空、または貼り付け内容が URL ちょうど 1 個でない）だと VS Code ハンドラが取り、`replaceSelectionWith` なので**選択していたテキストが消えてコードブロックに置き換わる**。VS Code から 1 単語コピーして選択範囲に貼る、という日常操作がこれに当たる。

## 3. 決定① — `openOnClick` を `false` にする（実装済み 2026-08-09）

**決定**: `StarterKit.configure({ link: { openOnClick: false } })` とする。

**理由**: 既定ではエディタ内でリンクをクリックすると `window.open` が走り（`dist/index.js:165`）、**キャレットが置けない**。UI が無いこと（§2.1）と合わせて「一度付いたリンクに手が出せない」状態を作っている。②の UI（§5）はキャレットがリンク内に入れることを前提にするので、これは②の前提条件でもある。

**機構**: `enableClickSelection` の既定が `false` なので、`openOnClick` も `false` にすると `handleClick` は何もせず `false` を返し、ProseMirror の通常のキャレット配置に落ちる。追加の手当ては要らない。

**これは純粋な改善ではない。** 引き換えにエディタからリンク先を開く手段が無くなる。代替はブラウザ自身のホバー時ステータスバー表示（リンク先の確認）と、テキストを選んでコピーすることである。

**この取引は 2026-08-11 に解消した。** §5.5 のバブルが href を文字で見せ、その文字を押せば開く（§5.5.1-1、§5.5.6-2）。①は今や一方的な改善である。

`'whenNotEditable'` という第 3 の値もあるが、このエディタは常に編集可能なので `false` と等価であり、選ぶ理由がない。

## 4. 決定 — `autolink` は残す

**決定**: `autolink: true` のまま変えない。

**理由**: §2.3 の実測どおり、公開側は remark-gfm の autolink literals で裸 URL をリンクにする。エディタ側の `autolink` を切ると、エディタでは素のテキスト、公開ではリンクという WYSIWYG のズレが生まれる。`autolink` を残せばタイプした URL は `<url>` として保存され（§2.2）、公開側の結果と一致する。**`autolink` はズレを作る側ではなく塞ぐ側である。**

`PostEditor.tsx:210-212` が underline を無効化した理由と同じ判断基準（エディタで見えるものと公開されるものを食い違わせない）を、逆向きに適用している。

**位置を限って切る案も同じ理由で却下した**（2026-08-17、§10）。`[テキスト](` の後ろに貼られた URL だけ autolink を止める案で、切れるのはエディタの表示だけであり、公開側は同じ URL を同じくリンクにする（§2.3 の表）。全体を切る場合と部分的に切る場合で、ズレの向きは変わらない。

**帰結（既知の制約、§5.2 に引き継ぐ）**: ②が入るまで、著者は**自分で作ったリンクを外せない**。

## 5. ② — 付与・編集・解除 UI（2026-08-11 実装、§5.5 の形）

### 5.1 なぜ延期していたか、そして何が延期を追い越したか

実投稿でのリンク使用がゼロだから（§0）。作るとしたら付与・編集・解除の 3 つで一組であり（§5.2）、ダイアログ 1 つでは済まない。3 投稿・実リンク 0 件の段階で払うコストとしては大きい。

追記 2026-08-11: このコスト見積もりは「ダイアログを複数」という実装形態を前提にしていた。 §5.5（Google Docs 型のバブル）なら 3 つが 1 コンポーネントに収まり、土台も既に repo にある。延期の根拠のうち「使用がゼロ」は動かないが、「コストが大きい」のほうは弱まっている。

**実装に踏み切った理由は、上の 2 つのどちらでもない。** 「使用がゼロ」は今も真である。延期を追い越したのは §2.1.1（この節より後の 2026-08-11 に実測）である — **内部リンクを作る経路がひとつも無い**のに、§1 は著者がそれを手書きする前提で非目標を切っていた。これは投稿数と無関係に成り立つ機能の穴で、§0 の「まだ作らない」判断が答えるべき種類のものではない。§5.5.3 のとおりバブルはそれ単独でこの穴を塞ぐ。

**したがって「使用がゼロなら作らない」という §0 の判断基準は撤回されていない。** 撤回されたのは「②が要るのは使い勝手のためだけだ」という前提のほうである。

### 5.2 延期の帰結（解消済み）— 外せないリンクが残っていた

`autolink` を残す（§4）ため、著者が URL をタイプするとその場でリンクになる。外す手段はバブルの「解除」である（§5.5）——`toggleLink` / `unsetLink` は `extendEmptyMarkRange: true` を持つため（`dist/index.js:387,390`）、リンク内にキャレットを置くだけでリンク全体に効く。**2026-08-11 に解消。** `extendMarkRange('link').unsetLink()` はリンクの右端にキャレットがあるときもリンク全体を外すことを実測した（`editor-link-bubble.spec.ts`）— そこは `getMarkRange` が解決できない位置なので、確かめずに済ませてよい種類のものではなかった。

### 5.3 作るときの制約（先に記録しておく）

この節は「ダイアログを出す」形を暗黙に前提している。 §5.5 のバブルを採る場合、1 と 2 は編集モード（URL 入力欄を出しているとき）にだけ当てはまる — §5.5.4-1。

1. **ダイアログはネストした `<form>` にしてはならない。** PostEditor 全体が単一の `<form>` であり、ネストした form はブラウザに捨てられて submit が無言で何もしない。前例は `components/editor/TableGridMenu.tsx:77-79` — `<dialog>` の中は素の `<div>` で、ボタンの `onClick` と Enter キーで submit 関数を呼んでいる。同じ形にする。
2. **オートセーブ中に開いたままのダイアログに注意。** そのフォーム内の `<input>` は server action 保存時に React 19 のフォーム自動リセットの影響を受けうる（コードブロックのファイル名入力が実際に踏み、`form` 属性に存在しない id を指す回避策で対処済み）。リンクダイアログは開いている時間が短いが、URL を貼って考え込む操作は起こりうるので、実機で確認すること。
3. **既存リンクの URL を編集するとき、`title` を消してはならない。** §0 の唯一の実リンクは `title` を持ち、それは公開まで生き残る（§2.3）。`title` の既定値は `null` なので、`setLink({ href })` が既存マークの属性をマージしないならURL を直すと `title` が黙って消える。TipTap の `setMark` の挙動を確かめること。投稿 id 36 がそのままフィクスチャになる。
   → **実測 2026-08-11: マージされる。** `setLink({ href })` は既存マークの属性の上に書くので `title` は残り、`[リンク](https://changed.example "タイトル")` として保存された。手当ては要らなかったが、要らないことが分かったのは測ったからである — 基準 4c として固定してある（§8）。
4. Mod-k を割り当てるならローカル `.extend()` が要る（`extension-link` にキーマップが無い）。ただし Ctrl+K は Chrome のアドレスバーのショートカットなので、tsc が通っても意味がなく**ブラウザでの実機確認が必須**である。
   → 実装では `.extend()` ではなく、`editor.view.dom` への capture 段階の keydown リスナ（`LinkBubble.tsx`）にした。機能が 1 ファイルに収まるほうを採っている。エディタ側に Mod-k の先客が無いことは実測済み（押しても doc もキャレットも動かない）。ブラウザが譲ることも 2026-08-11 に実機で確認した（§9）。
5. ダイアログの `<input>` への URL 貼り付けは §2.5 の影響を受けない（ProseMirror ではなく素の DOM 入力なので）。②が入れば、VS Code からコピーした URL を安全に付けられる経路が初めてできる。ただし §2.5 が直るわけではない — ②を §2.5 の修正の代わりにしてはならない。

### 5.4 「①.5」 — `[]()` の入力ルール（2026-08-17 実装）

**決定**: 打った `[text](url)` はその場でリンクになる。`components/editor/link-input-rule.ts`。

**理由は編集器自身の語彙の中の不整合である。** 見出し・引用・フェンス・`:::details`・`[^` と markdown 記法を受け付ける編集器で、`[]()` だけが黙って無反応だった。しかも保存の時点で `\[…\]` に潰れる（§2.2.1）ので、打った著者に返ってくるのは「効かない」ではなく「壊れた」である。

**②の代わりではなく、②の後に入れた砂糖である。** §5.5 のバブルが先（2026-08-11）で、§2.1.1 の穴も、この案への最大の反論だった「外す手段が無いまま任意テキストのリンクを量産する」も、そちらが引き取っている（§5.5.3）。

**機構**: `extension-link` は `addPasteRules` しか持たず（`dist/index.js:394`）入力ルールの席が空いているので、そこに 1 本置いた。Link 拡張の `.extend()` ではなく独立した Extension にしてある — 機能が 1 ファイルに収まるほうを採る、`Mod-k` と同じ判断である（§5.3-4）。

捕まえる形は `/(?<!!)\[([^[\]]+)\]\(([^\s()]+)(?:\s+"([^"]*)")?\)$/`:

- **`title` を取るのは、直列化がその形で書くからである**（§2.2 の `[text](href "title")`）。保存された本文から 1 行コピーして打ち直した著者に、元と同じリンクが返る。投稿 id 36 の実リンクがその形である（§0）。
- 本文が空の `[](url)` は取らない。 マークの掛かる先が無く、見えないリンクだけが残る。
- `![alt](src)` は後読み否定で外に置く。 画像記法には持ち主がいて、画像拡張自身の入力ルールが答える（実測 2026-08-17）。`[^!]` と書くと 1 文字を消費してハンドラの計算する位置が全部 1 ずれるので、幅ゼロの表明でなければならない。
- **除外するのは `!` だけである。** 手で打った `@[card](url)` は `@` + 普通のリンクになる（実測 2026-08-17）。`docs/link-card-requirements.md` §4.1 (b) がその記法を却下した理由は動いていない — 手で打ったものがカードにならないことは変わらず、死に方が「`\[` に潰れる」から「リンクになる」に変わっただけである。あちらの (b) の項をその形に書き直した。

**拒否は 1 つの述語に集約した**: `can().setLink({ href })`。拡張自身のコマンドなので、公開できないスキームの検査（`isAllowedUri` → `isPublishableUri`、§2.4.2）と、マークを置けない場所の検査（`canSetMark`）が同時に効く。断ったときは打った文字列をそのまま残す — **filter される場所で適用すると href だけが黙って消え、著者が失うのは飾りではなく URL である。**

適用したあとに `removeStoredMark` を呼ぶ。 `autolink` が有効な間 `link` マークは inclusive なので（`extension-link` の `inclusive()`、§4）、これが無いと `)` の後に続けた文章がリンクに飲まれる。`preventAutolink` のメタも `setLink` と同じく立てる — リンク文字列自体が URL のとき（`[https://example.com](/posts/foo)`）に autolink が href を上書きしにくるためで、autolink は `appendTransaction` でバッチ内の全 transaction のメタを見るので、こちらが dispatch する 1 本に立てれば届く（基準 6j）。

**2026-08-11 に置いた 5 つの制約への答え**:

| #   | 制約                                       | 答え（2026-08-17）                                                                                                                                                                                             |
| --- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 捕まえた href を `isPublishableUri` に通す | `setLink` 経由で通している（基準 6f）                                                                                                                                                                          |
| 2   | 先頭の `!` を除外する                      | 後読み否定。画像拡張の入力ルールが取る（基準 6g）                                                                                                                                                              |
| 3   | `undoInputRule` で戻る                     | Backspace で literal に戻る（基準 6e）                                                                                                                                                                         |
| 4   | インラインの `code` マークは守られない     | **予想が外れた。** TipTap の runner が `$from` の隣接マークの `spec.code` を自分で見て、rule をそもそも呼ばない。素の prosemirror-inputrules が親ノードしか見ないのは事実だが、ここに届く前に止まる（基準 6h） |
| 5   | アコーディオンのタイトルを spec に含める   | 含めた。`marks: ''` なので `canSetMark` が断り、記法は literal のまま残る（基準 6i）                                                                                                                           |

**入口はタイプだけである。** `transformPastedText: true`（tiptap-markdown）は代案ではない — リンク記法だけでなくあらゆるペーストを markdown として解釈するグローバルな変更であり、範囲が違う。ペーストした `[text](url)` は今もテキストのままである。

**閉じ括弧を先に打った順序だけは拾えない**（実測 2026-08-17）。ルールが見るのはキャレットより手前のテキストだけなので、`[テキスト]()` と枠を先に作ってから中に URL を入れても、後ろにある `)` は一致に含められない。**手癖のもう半分は通る** — `[テキスト](` まで打って URL を貼り、`)` を自分で打つ経路で、貼った URL が autolink で既にリンクになっていてもルールがその上から正しい href を書く（基準 6k）。

**先に `)` がある場合を `handlePaste` で拾うことはしない。** その位置のペーストは既に URL 自体をリンクにしているので、拾うのは空きを埋めることではなく既存の挙動に勝つことになる（ペースト経路の干渉は §2.4.2 と §2.5 で 2 度出ている）。加えて「キャレットが `](` と `)` の間にいる」はテキスト近傍の走査で、この編集器の他の述語がすべてスキーマとノード型を訊いているのと種類が違う — マークで 2 つに割れた text ノードだけで崩れる。回避は `)` を先に打たないことの 1 点であり、その 1 点は基準 6k が固定している。

**形**: リンクの中にキャレットが入ったら、その `<a>` の下に小さな浮遊カードが出る。中身はリンク先の表示 + コピー / 編集 / 解除の 3 アイコンボタンで、**表示の 1 行目それ自体が「開く」ボタンを兼ねている**（§5.5.6、§5.5.10）。編集を押したときだけ URL 入力欄に変わる。付与は選択して `Mod-k`、同じカードが空の URL 欄で開く。

#### 5.5.1 なぜこの形か

1. **①の借りを返す。** §3 は `openOnClick: false` の代償として「エディタからリンク先を開く手段が無くなる、代替はブラウザのステータスバー」と明記している。このカードは href を文字で見せ、開く手段を戻す（その文字自体が開くボタンである — §5.5.6-2）。①＋バブルは既定より一方的に良く、§3 の「取引」が取引でなくなる。
2. ①が前提条件だった。 キャレットがリンク内に入れなければ発動しない。§3 が「②の前提条件でもある」と書いたとおりの順番になっている。
3. 選択操作を要求しない。 `unsetLink` は `extendEmptyMarkRange: true` なので（§5.2）、キャレットが中にあれば足りる。
4. **付与・編集・解除の 3 つが 1 コンポーネントに収まる。** §5.1 のコスト見積もりが前提にしていた「ダイアログ複数」ではなくなる。

#### 5.5.2 土台は既に repo にある

`components/editor/TableToolbar.tsx` が `@tiptap/react/menus` の `BubbleMenu` を使っている。**新規依存はゼロ** — `@tiptap/react` → `@tiptap/extension-bubble-menu` → `@floating-ui/dom` の順に引かれており、`package.json` にはどれも直接載っていない（TableToolbar が現に動いていることがその証拠）。あの実装が払った授業料はそのまま効く:

- **`shouldShow` / `appendTo` / `options` は参照を安定させる。** 毎レンダー新しい inline props を渡すと `shouldRerenderOnTransaction` と往復して "Maximum update depth" で落ちる。
- `appendTo: document.body`。 エディタラッパの `overflow-hidden` に切られないため。
- z-index: TableToolbar は `z-20`（sticky ツールバーの `z-30` より下）。リンクのカードもその取り決めの中に入れる。
- **選択ではなくノードにアンカーする。** TableToolbar はテーブルの左上セルに固定している。リンクなら `<a>` 要素に固定すれば、キャレットが中を動いてもカードが揺れない。
- `updateDelay={0}`。 ブロックドラッグ直後の位置飛びを避けるための既定 250ms からの変更。同じ理由が当てはまるかは要確認。

`shouldShow` は `() => editor.isActive('link')` で足りるが、それが成り立つのは §4 で `autolink` を残したからである。TableToolbar の `isActive('table')` はノードの判定だが、リンクはマークなので、空選択のときの判定は `storedMarks ?? $from.marks()`（`@tiptap/core` の `isMarkActive`）に落ちる。`extension-link` の `inclusive()` は `this.options.autolink` をそのまま返す（`dist/index.js:261-263`）ので、今の設定ではマークが inclusive であり、リンク末尾にキャレットを置いても active と読める — クリックで最も普通に落ちる位置がそこなので、これは効いている。

**逆に言えば、この 1 行は §4 の決定に couple している。** `autolink: false`（§10 で却下済み）に転ぶとマークが非 inclusive になり、末尾のキャレットで判定が落ちるので、`shouldShow` はリンクの range を明示的に解決する形に書き直す必要がある。§5.2 の `extendEmptyMarkRange: true` が存在する理由と同じ種類の縁である。

**実測 2026-08-11 — 上の予想はどれも当たっていたが、2 つ足すことがある。**

| キャレット位置                   | `isActive('link')` | `getAttributes('link')` | `domAtPos` から `closest('a')` |
| -------------------------------- | ------------------ | ----------------------- | ------------------------------ |
| リンクの**左端**（`前\|リンク`） | `false`            | `{}`                    | 取れない                       |
| リンクの中                       | `true`             | 全属性                  | 取れる                         |
| リンクの**右端**（`リンク\|後`） | `true`             | 全属性                  | **取れない**                   |

1. **inclusive は右端にしか効かない。左端は active にならない。** カードが出るのは「中と右端」であって「リンクの両端」ではない。実害は無い（左端はまだリンクの外だと読める）が、`shouldShow` が対称だと思って書くと E2E が食い違う。
2. **その右端では `<a>` 要素が引けない。** `domAtPos(selection.from)` が段落を返すためで、アンカー解決は `from - 1` → `from` の 2 手で試す必要がある。`extendMarkRange` を使うコマンド（解除・編集）は右端でも正しく効くので、**壊れるのはカードの位置決めだけ**という分かりにくい形になる。

**`getMarkRange` はその右端でも解決する**（実測 2026-08-17）。`@tiptap/core` の `getMarkRange` は `childAfter` が空振りすると `childBefore` に落ちるので、リンクに接する 3 つの位置（左端・中・右端）すべてで範囲を返す。**この節は当初これを「`domAtPos` と同じ理由で失敗する」と書いていた。誤りを残しておくのは、それが逆向きに効くからである** — 左端でも解決するということは、カードの表示判定を `getMarkRange` に載せると、カードが今まで出たことのない位置に出るということでもある（§5.5.12）。

**`isActive` を使い続けている理由**: 右端は「クリックで最も普通に落ちる位置」であり、そこでカードが出ないほうが害が大きい。`getMarkRange` に寄せると右端が丸ごと落ちる。

autolink 直後に書き続けてもカードは出続けない（実測）: `https://example.org` を打って空白を入れると、キャレットはリンクの外（空白の後ろ）に出るので `isActive` は false に戻る。**「URL を打った直後からカードが本文の上に居座る」という懸念は現実にならない。**

#### 5.5.3 これが §5.4 と §2.1.1 に対して持つ意味

`Mod-k` で開いた URL 欄には `#見出し` も `/posts/foo` も直接打てる。したがって §2.1.1 の穴（内部リンクを作る経路が無い）はバブルだけで塞がる。

| 役割                  | §5.5 バブル | §5.4 入力ルール |
| --------------------- | ----------- | --------------- |
| 付与                  | `Mod-k`     | `[]()` を打つ   |
| 内部リンク            | ○           | ○               |
| 確認（href が見える） | ○           | ×               |
| 編集                  | ○           | ×               |
| 解除                  | ○           | ×               |

§5.4 の「外す手段が無いまま任意テキストのリンクを量産する」という最大の反論も、バブルが答えている — しかも見えている本文を消さずに URL だけ直せるので、打ち間違いの修復コストがゼロになる。§5.4 は「markdown の手癖を受け止める砂糖」であり、2026-08-17 にその位置づけのまま実装した。

**実測 2026-08-11: `setLink({ href: '#見出し' })` は通る。** `isAllowedUri` に渡している `isPublishableUri` は既定判定の前に置いた引き算でしかなく（§2.4.2）、スキームを持たない fragment / 相対パスは既定側が通すので、狭めた述語はここでも邪魔をしない。**§2.1.1 の穴は塞がった。**

#### 5.5.4 作るときの制約（§5.3 に足す）

1. **表示モードには `<input>` を置かない。** ボタンだけのモードなら §5.3-1（ネストした `<form>`）も §5.3-2（React 19 のフォーム自動リセット）も無関係である。編集モードを明示的に開く段階分けが、そのまま防御になっている — Docs の形をそのまま写せばよい。入力欄を出した瞬間に §5.3-1/-2 が生きる。
   → 実装では §5.3-1/-2 はどちらのモードでも成立しない。 BubbleMenu は自分の要素を `document.body` へ portal するので、URL 入力欄は PostEditor の `<form>` の**外**にあり、そもそも form に association されない。段階分けは残してあるが、それは UI としての理由（表示を先に見せる）であって防御ではない。フォーム自動リセットを踏まないことは E2E で測ってある（基準 4k、オートセーブを跨いで入力値が残る）。
2. **テーブル内のリンクでは浮遊メニューが 2 枚同時に出る。** TableToolbar と競合する。どちらを優先するか、オフセットをずらすか、`shouldShow` で排他にするかを決める必要がある。これは新しい設計判断で、前例が無い。
   → **決定: セル内ではリンクのカードが勝つ。** より具体的な対象であり、キャレットがリンクを出ればテーブルの操作は戻る。**機構は `shouldShow` ではなく CSS** — `body.link-menu-open .table-toolbar { display: none }`（`app/globals.css`）を BubbleMenu 自身の `onShow` / `onHide` で着け外しする。`shouldShow` に項を足す形は付与のとき（`Mod-k` で URL 欄を開く操作）に効かない: bubble menu プラグインは選択か文書が変わる transaction でしか `shouldShow` を訊き直さず、入力欄を開く操作はそのどちらでもないからである。ブロックドラッグ中の同じ抑止（`body.block-dragging`）がまさに同じ理由で CSS になっており、前例が無いのは「どちらが勝つか」の判断だけだった。
3. **ホバー起動は入れない。** Docs はホバーでもカードを出すが、ホバー／フォーカス起動の追加コンテンツは WCAG SC 1.4.13 の dismissible / hoverable / persistent を全部背負う（`popover-api-pitfalls` の教訓）。キャレット起動なら編集アフォーダンスなので義務が軽い。 ただし Escape で閉じるのは入れる。
   → そのまま実装した。Escape はエディタ側（`view.dom` の capture リスナ）とカード側（ボタンにフォーカスがある場合）の両方に置いてある。**閉じたことはキャレットがリンクを離れるまで保持し、離れたら忘れる** — さもないと次の transaction で即座に戻ってくる。表示モードを閉じる手段はこの Escape だけでよい（キャレットがリンクを出れば勝手に消える）が、**URL 入力欄には別の箇所のクリックでも閉じる経路がある** — §5.5.7。
4. **`Mod-k` は実機確認が必須**（§5.3-4）。Chrome の検索バーに取られる既定があり、tsc も E2E も答えを持たない。Docs は現に奪えているので不可能ではない。
   → **2026-08-11 に実機で確認、奪えている**（§9）。`preventDefault()` だけで足りた。E2E の `Control+k` は CDP 合成なのでブラウザ UI に届かず「奪えた」の証拠にならない、という事情は変わらないので、**この確認は spec に持ち込めず、§8 の表にも入らない**。
5. **`title` を消さないこと**（§5.3-3）。投稿 id 36 がフィクスチャである。
   → **実測 2026-08-11、残る。** `setLink({ href })` は既存マークの属性の上に書くのでマージされ、手当ては要らない（§5.3-3、基準 4c）。
6. **キャレットを置くクリックは `state.selection` への反映が 20ms 遅れる**（§8 の 1b と同じ落とし穴）。カードの出現が 1 フレーム遅れるのは許容だが、**E2E で「出ない」を測るときは DOM のキャレットを見てはならない**。
   → spec はキャレットをほぼすべて `setTextSelection` で置いている（クリックの落ち先ではなく、どの位置で何が起きるかを測りたいので）。唯一クリックで測っているのはセル内のリンク（§5.5.4-2）で、そこは待って測っている。
7. **（実装中に見つかった、設計時に無かった制約）カードの中のイベントから `.key` を読んではならない。** `@tiptap/react` の menu は prop のコールバックに `Object.create(実イベント)` を渡すので、プロトタイプ経由で届く native なアクセサ（`.key` もそれ）が本物でない `this` で呼ばれ "Illegal invocation" を投げる。カード内の打鍵のたびに投げていたのに、**カードは正常に動いて見えた** — DOM ハンドラの中の例外は「何も起きない」と同じ顔をするからである。`event.nativeEvent.key` を読む。見つけたのは `page.on('pageerror')` で、`clearNodes` の RangeError（`tiptap-editor-pitfalls`）と同じ発見のされ方をしている。spec はこの watch を常設にした。
8. **（同上）セル内抑止の E2E は、body のクラスと `toBeHidden()` の両方を書く。** この spec を書いている途中、`toBeHidden()` がタイムアウトいっぱい "visible" を返し続ける形で 4 回連続再現した。ファイルが育つと（どちらのコンポーネントにも触っていないのに）再現しなくなった。**失敗中のページの状態は取れていないので、当時クラスが付いていたのかどうかは分からない** — 分からないことを分かったように書かないために、spec には両方の assertion を置き、次に赤くなったときにどちらが壊れたのか分かるようにしてある。

#### 5.5.5 写さないもの

リンク候補の検索、リンクプレビューのサムネイル。**この列には元々 favicon とページタイトルも入っていたが、どちらも 2026-08-16 に出た**（§5.5.8 と §5.5.10）。**残っているのは「候補を検索して選ばせる」ほうだけ**で、それは §1 の非目標そのものである — カードは今あるリンクについて答える道具で、リンク先を探す道具ではない。

#### 5.5.6 見た目を Docs に寄せた（2026-08-16）

**決定**: §5.5 のカードは形としては最初から Docs 型だったが、見た目は「枠付きの箱にテキストボタンが 4 つ」だった。2026-08-16 に外観だけを Docs に合わせた。**機能は増減していない** — 操作は 4 つのまま、押す場所が変わっただけである。

1. **テキストボタン 3 つをアイコンボタンにした。** コピー / 編集 / 解除 が `components/editor/svg/` の `CopyIcon` / `PencilIcon` / `UnlinkIcon`（既存アイコンと同じ 24 viewBox・`currentColor`・thin stroke）になり、ラベルは `ToolbarButton` の `title` 経由のツールチップに移った。`title` は `aria-label` になるので、アクセシブル名は「コピー」「編集」「解除」のまま変わらない — §8 の E2E が role + name で引いているのはそのためで、アイコン化しても赤くならない。
2. **リンク先の表示が「開く」ボタンを兼ねる。** Docs と同じで、押すと開く。専用の「開く」ボタンは無くなった。**押せるのは表示の 1 行目**で、それはタイトルがあればタイトル、無ければ URL である（§5.5.10）。アクセシブル名は `aria-label='リンク先を開く'` で明示している — 可視テキストが URL やページ名なので、読み上げただけでは何をする控えかが分からないからである。`<a>` ではなく `<button>` + `window.open` のままにしてある（noopener/noreferrer を手で渡している理由は元のコメントのとおり）。E2E はこの名前で引き直した（`editor-link-bubble.spec.ts`、旧「開く opens the href in a new tab」）。
3. **`ToolbarButton` に `round` を足した。** 丸いホバー領域（`rounded-full p-1.5`）。カードの中でボタンが 3 つしかないと、角丸矩形のホバー塗りはセグメンテッドコントロールに見える。ツールバー側の見た目は変えていない（opt-in）。
4. **写さなかったもの**: ページタイトルの取得（§1 の非目標。favicon はこの時点では同じ列にあったが、2026-08-16 に分かれた — §5.5.8）、ホバー起動（§5.5.4-3 の WCAG の理由は動いていない）。**編集モードの「テキスト」欄もこの列にあったが、2026-08-17 に実装した**（§5.5.13）。保留の理由は「リンク文字列の中に脚注参照や入れ子のマークが入りうるので、置換の設計が別に要る」で、それは今も正しい — 答えは、置換が範囲のマーク集合を運び、それが途中で変わるリンクにだけ欄を出さないことである。
5. カードの色は本文のリンク色（`#0969da` / `#4493f8`、§7.1）を借りている。`.prose` の外なのでカスケードの関係は無く、単に同じ値を書いている。

#### 5.5.7 対象のハイライトと、クリックでの取り消し（2026-08-16）

**決定**: カードが出ている間、そのカードが対象にしているテキストを薄く塗る。**そして URL 入力欄は、別の箇所をクリックすると閉じる。** §5.5.6 と違ってこちらは挙動の変更である。

きっかけは実測されたバグである。 URL 入力欄を開いたまま本文の別の場所をクリックすると、欄は開いたままキャレットの新しい位置へ付いて回った（実測 2026-08-16: カードの x が 266 → 550 へ移動し、それでも「元のリンクを編集中」のつもりでいる）。`shouldShow` は編集中なら無条件に `true` を返し、`getReferencedVirtualElement` はリンクが無ければ選択範囲の矩形に落ちるので、両方が揃うとカードは行の上を滑っていく。

**機構**:

- **ハイライトは Decoration である。** `components/editor/link-highlight-extension.ts` — レンジを 1 つ持つだけのプラグインで、判断はしない。描画済みの `<a>` に `classList` で class を足す形は採らない: ProseMirror の MutationObserver は自分が管理している内容の属性変更を見ており、それは文書に伝えずに塗るための経路ではない。前例は `footnote-extension.ts`（番号も Decoration である）。
- **レンジは `LinkBubble` が押し込む。** 何を塗るべきかは文書の性質ではないからである — Escape で閉じたときはキャレットがリンクの中にいてもマークは active のままだし（塗ってはいけない）、`Mod-k` の直後にはまだリンクが無い（選択範囲を塗る）。この 2 つを知っているのは `LinkBubble` だけなので、プラグインは置き場に徹する。**ただし「カードが実際に出ているか」は `shouldShow` では分からない** — プラグイン自身の `onShow` / `onHide` を併せて見る（§5.5.9）。
- **レンジは `linkAtCaret` が返す**（§5.5.12）。2026-08-17 まではこれが `from` → `from - 1` の 2 手の `getMarkRange`（`linkRangeAt`）で、理由は「右端では `getMarkRange` が解決に失敗する」だった。**その理由は成り立っていない**（§5.5.2 の追記）。いま判定がキャレットの前のテキストを見るのは別の理由で、マークが inclusive でなくなったからである。基準 4p が固定しているもの — **クリックが最も普通に落ちる位置で塗りが出ること** — は変わっていない。
- **取り消しの経路は 2 つある。** クリックは `mousedown` で取る — `click` の時点では選択が既に動いており、`isActive` が「今どこにいるか」を答えてしまう。カードは `<body>` へ portal されているので、内外の判定は ref の包含ではなく `closest('.link-bubble')` で行う。キーボードでカードを抜ける経路（唯一のボタン「適用」から Tab すると、portal 先の後ろには何も無いのでフォーカスは行き先を失う）は `focusout` で取るが、判定は `relatedTarget` ではなく 1 フレーム後の `document.activeElement` で行う — **入力欄を開く操作それ自体が focusout である**（フォーカスの載っていた「編集」ボタンが外れる）ため、イベントの上では「Tab で離れた」と区別が付かない。1 フレーム後なら入力欄にフォーカスが移った後なので区別できる。表示モードの閉じ方は §5.5.9 にある（この節を書いた時点では「キャレットがリンクを出れば消えるので足す必要が無い」と考えていたが、本文の外をクリックした場合には成り立たない）。
  **この 2 つと Escape（§5.5.4-3）が、適用せずに抜ける手段のすべてである** — カードにその役のボタンは無い（§5.5.16）。

- **どちらの経路でもカードは消えない。** 消えるのは入力欄だけで、キャレットがリンクの中にいる限り表示モードに戻る（塗りもそのまま残る）。ツールバーや記事タイトル欄など、エディタでもカードでもない場所へ移ったときも同じである（基準 4u）。
- **アンカーの凍結は要らなかった。** クリックで閉じるなら、入力欄が開いている間に選択が動くことがそもそも無い。

**塗りの濃さは好みではなく contrast で決まる。** 塗るのはリンク色の文字の背面であり、§7.1 が `#0969da` / `#4493f8` を決めたときの余裕はどちらの scheme にも多くない。実測（2026-08-16、実際の地色 `#fff` / `#0a0a0a` に対して）: **light は黒 6% で 4.54:1、dark は白 10% で 5.10:1、いずれも AA の 4.5:1 を上回る。** 数字が良いのは dark のほうだが、**限界が近いのも dark である** — 14% では 4.49:1 で落ちる（light はまだ保つ）。濃くするなら比を計算し直すこと。値と数字は `app/globals.css` の `.link-bubble-target` に置いてある。

**写さなかったもの**: ホバーでカードを出すこと（§5.5.4-3 の WCAG の理由は動いていない）。今回の変更はカードの**消え方**を Docs に合わせたのであって、出方は変えていない — 出方はキャレットのままである。クリック起動にすると矢印キーでリンクに入った著者からカードが取り上げられ、§5.5.1-2 が前提にしている順番（①がキャレットを置けるようにしたから②が成り立つ）が崩れる。

#### 5.5.8 favicon を href の左に出す（2026-08-16）

**決定**: カードの左端に、リンク先オリジンの `/favicon.ico` を 16px で出す。**§5.5.5 が「写さないもの」に入れていた項目のうち、favicon だけがこの列から外れた。** 一緒に挙げられていた「ページタイトルの自動取得」は外れていない。

**この 2 つを分ける線は「取りに行く必要があるか」である。** ページタイトルは対象ページの HTML を取得して解析する必要があり、それは `link-card-requirements.md` §8.1 が延期している外部 URL カードそのもの（取得・キャッシュ・**SSRF**・失敗表示）である。favicon はブラウザの `<img>` が直接引くので、**サーバは 1 行も関与せず、したがって SSRF の面も増えない。** §8.1 の延期はこの節によって崩れていない。

**機構**:

- **ルートの `/favicon.ico` だけを見る。** `<link rel="icon">` を読むには HTML の取得が要り、それは上で払わないと決めたコストである。代わりに、HTML でしかアイコンを宣言していないサイトでは何も出ない。
- **相対パスと fragment は自分のオリジンに解決される。** `/posts/foo` や `#見出し` はこのブログのアイコンを出す。特別扱いではなく、「リンクが解決するオリジンのアイコンを出す」という 1 つの規則の帰結である。オリジンを持たないスキーム（`mailto:`）では `<img>` 自体を作らない — 隠れた `<img>` が既にどこかへ要求を投げている状態にはしない。
- **読み込みに成功するまで何も描かない。** 場所を空けて待つと壊れた画像に見える。カードは左端でアンカーされているので、アイコンの到着はカードを右へ伸ばすだけで、著者が読んでいる文字を動かさない。
- **`referrerPolicy='no-referrer'`。** 要求は著者のブラウザから第三者オリジンへ飛ぶ。相手が知ってよいのは「誰かが favicon を要求した」までで、このブログのどのページを編集中かではない。
- **`loaded` は key による再マウントで捨てる。** 別のリンクへ移ったとき、前のリンクで成功した状態を次の失敗に貸してはならない（基準 4z）。

**プライバシーの代償は残る。** 著者がリンクにキャレットを置くたびに、そのオリジンへ要求が 1 本飛ぶ。**これは `posts.thumbnail` が第三者画像のホットリンクを拒んでいるのと逆向きの判断である**（あちらは読者のブラウザから飛ぶ話で、公開ページに載る。こちらは著者自身のブラウザから飛ぶ話で、管理画面にしか出ない）。この違いを理由に採ったので、**公開側に favicon を出す話が来たときにこの節を根拠にはできない。**

**実測 2026-08-16**: corpus の 2 ホスト（zenn.dev / wikiwiki.jp）はどちらも実ブラウザにルートの favicon を返す。**同じ 2 つを `curl` で叩くと wikiwiki.jp は 403 を返す** — この件の測定器はブラウザであってシェルではない、という形で残しておく。

#### 5.5.9 表示モードはフォーカスに従う（2026-08-16）

**決定**: 表示モードのカードは、**フォーカスがエディタにもカード自身にも無くなったとき**に消える。著者が編集していないなら、キャレットの周りを説明するカードに用は無い。**カードは著者が居られる場所の 1 つである** — 判定を「エディタがフォーカスを持っているか」だけで書くと、カード自身のボタンが押せなくなる（下記、2026-08-16 に修正）。

報告は「ボタン系の要素をクリックしてもメニューが消えないことがある」で、名前が挙がったのは**「下書きに戻す」**（投稿自身のフォーム）と**リンクカードの「変更」**（NodeView の中のボタン）だった。**この 2 つは DOM 上の位置がまるで違うのに同じ理由で壊れる** — どちらもクリックが transaction を起こさないので、プラグインは `shouldShow` を訊き直さず、カードはそのまま置き去りになる。だから規則は「エディタの外か中か」ではなく**フォーカス**で書いてある。

**ツールバーは除外する。** 除外は列挙ではなく測定から出ている。 実測 2026-08-16 — ツールバーのボタンは `blur` と `focus` の両方を出す（コマンドが `.focus()` を繋いでいるため）が、リンクカードの「変更」は `blur` だけを出す。したがって判定は **1 フレーム待ってフォーカスの落ち着き先を訊く**形になる。生の `blur` で消すと、著者が「太字」に手を伸ばすたびカードが消える。ツールバーはエディタの外で唯一、カードが説明しているまさにその選択に作用する場所なので、ここで残るのは我慢ではなく正しさである。

##### カード自身への離脱は離脱ではない（2026-08-16、報告と修正）

報告は「コピー・編集・解除が押せない」。カードは `<body>` へ portal されているので、**その中のボタンを押すことは、エディタから見ればページの外へ出るのと同じ形をしている** — `mousedown` でフォーカスがボタンへ移り、その 1 フレーム後に上の規則がカードを消し、`mouseup` の時点で押した相手が存在しないので `click` はどこにも届かない。判定にカードの中（`closest('.link-bubble')`）を足すのが修正で、離脱の判定は 1 つの述語（`focusLeft`）にまとめ、blur 規則と入力欄の畳み込みの両方がそれを訊く。

**エディタ側は `view.hasFocus()` のままにする — `view.dom.contains(active)` に広げてはならない。** ProseMirror のこの答えはエディタ要素そのものについてのもので、だからこそ本文の中にある NodeView のボタン（リンクカードの「変更」）が「離れた」側に入る。これは上の 3 段落が直した当のケースである。

**35 件の spec が全部緑のまま通り抜けた。** Playwright の `.click()` は `mousedown` と `mouseup` を 1 つのタスクの中で出すので、消える前に `click` が終わってしまう — 人間の押下だけが遅い。基準 5q・5r・5s は押しっぱなしを 150ms 作り、かつ押している最中にカードが見えていることを測る。「クリックが効いた」だけを測ると、カードが `z-20` でツールバー（`sticky z-30`）に潜る別の欠陥と区別が付かないので、リンクは文書の下の方に置く。

**カードにフォーカスが残った状態からの離脱には、`focusout` 側の規則が要る。** ボタンを押した後、エディタは既に blur しているので、そこからページの余白へ移っても blur は飛ばない。表示モードでも `focusout` を見る（`editing` のときだけ張っていたものを、カードが出ている間は常に張る）ことで、フォーカスがエディタにもカードにも無くなった時点でカードが消える。これを入れずにボタンだけ直すと、報告 1 つを別の報告 1 つと取り替えることになる（基準 5s の後半）。

**`dismissedRef` を使う（`signal('hide')` だけでは足りない）。** 「変更」が開くピッカーは自前の transaction を出し、その 1 本ごとに `shouldShow` が訊き直されてカードが戻ってきてしまう。フォーカスがエディタに戻ったときに `dismissedRef` は解除されるので、リンクに戻ればカードも戻る — **Escape との違いはここである。** あちらの取り消しはクリックを跨いで残ることが目的なので、フォーカスでは解除されない。

**URL 入力欄からの離脱は blur 規則に乗らない。** 欄がフォーカスを取った時点でエディタは既に blur しているので、そこから第三の場所（記事タイトル欄など）へ移っても blur は飛ばない。入力欄を畳む処理の側で同じ判定（1 フレーム後の `focusLeft`）をもう一度行う。これを入れる前は、**入力欄は閉じるのに表示カードだけが本文の上に残っていた** — 報告と同じ症状に別経路で到達していた。「適用」はエディタにフォーカスを戻すので、この判定を通ってもカードは残る。

同じ調査で、塗りだけが残る欠陥が見つかった（2026-08-16 に修正）。 本文の外側の余白をクリックすると、プラグインは（フォーカスが行き先を失うので）カードを消すが、**`shouldShow` は true のままなので塗りが残り**、リンクにカードの無いハイライトだけが点いた状態になっていた。次に何か編集するまで消えない。原因は §5.5.7 が塗りを `shouldShow` から導いていたことで、**カードが実際に出ているかは `shouldShow` だけでは決まらない** — プラグインは blur でも消すし、`shouldShow` を訊き直すのは選択か文書が変わる transaction のときだけである。塗りはプラグイン自身の `onShow` / `onHide` に従わせた（`body.link-menu-open` を着け外しているのと同じ 2 つで、実測でカードの表示状態と完全に一致する）。基準 5a がこれを固定している。

#### 5.5.10 リンク先のタイトルを URL の上に出す（2026-08-16）

**決定**: カードの左側を 2 行にし、上にリンク先ページのタイトル、下に URL を出す。**タイトルが取れないときは 1 行のまま**で、その場合のカードはこの節が入る前と同一である。

**URL は消さない。** §5.5.1-1 はこのカードの存在理由を「`openOnClick: false` の代償に**リンク先がどこか**を見せる」と定めている。タイトルが答えるのは「それが何か」であって「どこへ行くか」ではないので、置き換えると①の借りを返した当のものを手放すことになる。だから足す。

**押せるのは 1 行目だけである。** タイトルが出ているとき、URL の行は表示専用で、リンク色も持たない（青いのは 1 行目）。**規則は「URL は押せない」ではなく「1 行目が押せる」という位置の規則**であり、この差は効く: 前者で書くと、タイトルが取れないリンク（Cloudflare の 403 は実測 2/10）には押せる場所がひとつも無くなり、§3 が手放して §5.5 が返したものをもう一度手放すことになる。カードの中で押せるものは常に 1 つで、常に上にあって、常に青い。基準 5n がこれを固定している。

**ツールチップはエディタ自身のものを使う。** 2 行とも `max-w-72` で切り詰められるので、全文はホバーで読ませる必要がある。ネイティブの `title` 属性は使わない — `ToolbarButton` が既にそれを捨てている理由（カーソルの近くに、ブラウザが決めた遅延で出る）に加えて、**色を合わせられない**からである。そのツールチップを `components/editor/EditorTooltip.tsx` に切り出し、`ToolbarButton` と 2 行の両方が同じものを描く。

**`https://` は表示から落とす（2026-08-16）。落とすのは `https://` だけである。** `http://` は残るので、**暗号化されていない方だけがスキームを見せる** — Chrome のアドレスバーと同じ取引で、これが「整理」ではなく安全側である理由である。相対パス・fragment・`mailto:` は触らない。

**表示だけの話であり、幅のためではない。** 実測（2026-08-16）で表示幅の利得はゼロだった: 列幅はタイトル行と URL 行の広い方で決まり、タイトルは 12px・URL は 10px なので**たいていタイトルが幅を決めていて、URL はその内側に収まっている**（corpus と主要な候補 5 件はいずれも切り詰められていない）。唯一溢れる zenn の fragment 付き URL も、削って 314px でなお上限 288px を超えるので救えない。**採った理由は Docs に合わせることと、http が目立つことの 2 つだけである。**

**開く先・`コピー` の内容・markdown が保存する文字列は生の href のままで、ホバーのツールチップもそれを見せる** — 行は読むため、ツールチップは確かめるため。表示が保存値とずれること自体は残るが、Chrome が同じ取引をしている（普段は短く、編集に入ると全部）。基準 5o・5p がこの両方を固定している。

2 つ踏んだ: **ツールチップを行の内側に置くと、その行のテキストが要素の中に二重に入る**（見えないが実在し、ボタンのテキストを読み返した最初のものが両方を受け取った）。同じ大きさのラッパーに出して兄弟にしてある — `ToolbarButton` が内側に置けるのは、あちらのボタンが持つのがアイコンだからである。もう 1 つは **`left-1/2` の絶対配置は包含ブロックの半分に縮められる**ので、`whitespace-nowrap` を外した途端どのラベルも 2 語幅の縦棒に折り返した（実測: 288px の行で「ブログ開設の / お知らせ」）。`w-max` で内容幅を先に決め、`max-w-xs` だけを上限にしている。

| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 日本語サイトは Shift_JIS / EUC-JP がある | **10/10 が UTF-8。** デコーダ切り替えは要らない                                                                       |

##### 機構

- **ガードは解決済みアドレスに対して書く。文字列検査ではない。** `http://evil.example/` の A レコードが `127.0.0.1` なら綴りの検査はすべて素通りするし、302 でそこへ飛ぶのも同じである。`dns.lookup` で自分で解決し、**全レコード**を検査し（公開アドレスと私有アドレスを両方返す名前は、最初の 1 件で止まる検査を抜ける古典的な手口）、`redirect: 'manual'` で各ホップを解決し直す。`lib/link-title.test.ts` はこれを「null が返ること」ではなく**「リクエストが 1 本も出ないこと」**で測っている。
- **自サイトへのリンクは DB から答える。速度ではなく安全性の話である。** fetch すると、サーバが Funnel 越しに自分自身へ要求を出すことになる。判定は**ブラウザが送った `Host` ヘッダ**と比べる — `req.nextUrl.origin` は正規化しており、実測では `127.0.0.1` 宛の要求に対して `localhost` を返した。両者が食い違うと内部リンクが「外部」になり、ガードがループバックとして拒み、**どこでも内部リンクにタイトルが出なくなる。**
- **2xx でなければタイトルは読まない。** Cloudflare のチャレンジは 403 でありながら `<title>Just a moment...</title>` を持つ（実測）。状態を見ずに拾うと、**URL を出すより悪い結果**になる。
- **失敗はキャッシュする。** 落ちる 2 件は速く落ちるので、しなければキャレットがそのリンクに入るたび取りに行く。favicon がブラウザキャッシュに任せている部分を、サーバ fetch は自前で持つ必要がある。TTL は成功より短い（403 のほうが、タイトルより先に変わりうる）。
- 本文は 64KB で打ち切る。`<title>` は先頭にあり、それ以上は使い道の無いダウンロードである。タイトルは 120 字で切る — 第三者のテキストが DOM に入るが、React が escape するので問題は injection ではなく**レイアウト**である。

##### 1 行から 2 行への切り替わりは見える（実測 2026-08-16）

カードは文書から即座に描かれ、タイトルは後から届くので、**タイトルが載る瞬間に 1 行から 2 行へ変わる。** 報告された「稀に以前の URL だけのデザインが一瞬見える」はこれである。**キャッシュが古いものを見せているのではなく、キャッシュに当たらなかったときだけ実装本来の姿が見えている。**

|                     | キャッシュ有 | キャッシュ無 |
| ------------------- | ------------ | ------------ |
| 自サイト（DB）      | 17ms         | 86ms         |
| 外部（example.com） | 13ms         | 196ms        |
| 外部（MDN）         | 10ms         | 216ms        |

当たれば知覚できず、外れると見える。外れるのは「その URL に初めてキャレットを置いたとき」「6 時間の TTL 切れ」「200 件から溢れたとき」「サーバのプロセスが変わったとき」である。**遅い相手ならこれより長くなる**（打ち切りは 5 秒）。

**受け入れている。** 切り替わりの間もカードは完全に使える（URL もボタンも出ている）。**ボタンがずれる量は実測 dx 3〜8px・dy 2px で、ボタン 1 個（28px）より小さい** — 移動中のクリックが別のボタンに当たることはない。`link-card-notes` の「2 状態の NodeView でボタンが動いて実際にカードを壊した」前例はここには当てはまらない。

**代案はどれも別のものを悪くする**ので採らなかった: タイトル行の高さを先に確保すると、タイトルが永久に来ないリンク（Cloudflare の 403 は実測 2/10）で空行が残り、favicon で「空の枠は壊れた画像に見える」と判断したのと同じ問題になる。タイトルが解決するまでカードを出さない案は、**現在 8ms で出ているカードを全リンクで遅らせて**、冷たいリンクの一瞬と引き換えにする。文書を開いた時点で全リンクを先読みする案は冷える場面自体を消せるが、**著者が触ってもいないリンク先へ要求を投げる** — §5.5.8 で「キャレットを置いたときに 1 本」と決めた線を越える。

##### カードは上に出す（2026-08-16 決定）

2 行になったぶんカードは 47px になり、**下に出していたときは直下の 2 段落を覆っていた**（実測、通常の行間）。§5.5 が `bottom-start` を選んだ理由は「上だと読んでいる行を覆う」だったが、**現在の大きさではその理由が成り立たない。** 読んでいる行はリンク自身の行で、カードは 8px のオフセットを置くので、この大きさではどちら側に出てもその行は覆わない（1 行だった当時に上へ出すと近接して見づらかったかどうかは測っていない — 測ったのは 2 行のカードである）。実際に覆われるのは隣の段落で、**下なら「これから読む段落」、上なら「もう読んだ段落」**である。後者のほうが軽い。

`placement: 'top-start'` に変えた結果、覆う段落は 2 つから 1 つに減り、その 1 つは既読の側になった（実測）。

**上に出すことの唯一の危険はツールバーである。** ツールバーは `sticky top-0 z-30` で本文の真上にあるので、1 行目のリンクには「ビューポート上の余地はあるが空いていない」という状態が生じる。`flip` は既定でビューポートしか見ないためここでは働かず、カードはツールバーの帯に置かれ、`z-20` なので**その下に潜った — 画面上にあって見えない**（実測）。`flip` の `boundary` にエディタの要素を渡してこれを解いている。ピクセル定数を置かずに済み、ツールバーの高さが変わってもずれない。基準 5l・5m がこの 2 つを固定している。

##### 追いきれなかった観測（2026-08-16）

`editor-link-card.spec.ts` の `Backspace / Delete at a card's edge …（4e）` が、この節の作業中に複合実行で **2 回落ちた**（1 回目は Backspace 側、2 回目は Delete 側）。**そのあと 17 回連続で緑であり、再現していない。**

**分かったこと、分からないこと。** 変更を stash したベースラインは 3 回とも緑だったが、変更ありでも 17 回連続で緑なので、**この比較はもう何も言っていない。** 残っている材料は 2 つだけである:

- 失敗した当時のあの spec は `loadMarkdown` のあと 700ms 待って prosemirror-history のグルーピングから抜ける作りで、`newGroupDelay` の既定は 500（`prosemirror-history/dist/index.js`、`newGroupDelay: config.newGroupDelay || 500`）。**余裕は 200ms しかなかった**（この待ちは現在ない — 下記）。

**機構としては繋がっていない。** あの spec に出てくるのはリンクカードであってテキストリンクのバブルではなく、タイトル取得は走っていない（実行ログで確認）。

**余裕を広げて緑にすることはしていない。** 原因が分からないまま待ち時間を伸ばすのは、回帰があった場合にそれを隠す操作である。**代わりに時間依存そのものを外した（2026-08-16）。** 700ms の待ちの位置に `closeHistory` の meta を入れて履歴の区切りを明示し（`closeHistoryKey = new PluginKey("closeHistory")`、prosemirror-state の `createKey` が `name + "$"` で名付ける文字列を `setMeta` にそのまま渡す。プラグインは `if (tr.steps.length == 0) { return history; }` の手前で meta を読むので空のトランザクションで足りる）、削除が独立した 1 イベントであることと、undo が戻すのがその 1 イベントだけであることを `done.eventCount` で数える。判定は強くなっている — 待ちは「実行が遅ければ通ってしまう」形だったが、イベント数は遅くても速くても同じ答えを返す。区切りが入ったこと自体も `prevTime` の読み戻しで確かめており（`e2e/editor-authoring.ts` の `closeHistory`）、@tiptap の更新で meta の名前が変わればその場で落ちる。誤った名前を渡す実験で、この読み戻しが実際に落とすことを確認した。同じ待ちは `details-slice-guard` / `table-pipe-form` / `editor-isolating-boundary`（こちらは 600ms、余裕 100ms）にもあり、同じ手で同時に外している。

**これは原因の説明ではない。** 説明のつく唯一の機構だった 200ms の余裕が無くなっただけで、2 回の失敗が何だったかは分かっていない。

#### 5.5.11 `Mod-k` で開いたカードの位置（2026-08-17 報告・修正）

報告は 2 つだった。①autolink の上にキャレットを置いたあと、別の場所でテキストを選んで `Mod-k` すると、カードがその autolink の位置に出る。②その日最初の `Mod-k` ではカードの位置は正しいが、スクロールが先頭へ飛ぶ。**機構は 3 つある。**

**機構 1 — プラグインは出す前に置く。** `@tiptap/extension-bubble-menu` の `transactionHandler` は `meta === "show"` を `this.updatePosition()` → `this.show()` の順で処理するが、`updatePosition()` は `if (!this.isVisible) {` の早期 return で始まる。meta で出したカードは位置決めを 1 回落とすということである。`hide()` が戻すのは `visibility` と `opacity` だけで `left` / `top` は残るので、**カードは前にいた場所に出る**（実測 2026-08-17: キャレットが 948px 下にあるのに、カードは前のリンクの座標のままだった）。位置を訊き直す経路は「選択か文書が動く transaction・resize・scroll」の 3 つで、URL 欄を開く操作はそのどれでもないので、ずれたまま残る。

**機構 2 — 一度も置かれていないカードには座標が無い。** React 側のラッパが要素に与えるのは `bubbleMenuElement.style.position = "absolute"` と `visibility` だけなので、`left` / `top` が空のまま `<body>` へ挿さると文書の左上に出る。そこへ URL 欄のフォーカスが入るとブラウザがそれを見せようとし、**ページごと先頭までスクロールする**（実測: `scrollY` が 1121 → 0）。それでもカードが結局は正しい位置に出るのは、**そのスクロール自身が `resizeHandler` を焚く**からである — 60ms 後に置き直される。報告②が「位置は合っているのにスクロールだけ飛ぶ」形になるのはこのためで、症状としては 1 つでも、直す先は 2 か所ある。

**機構 3 — 隣のリンクを掴む。** `linkElementAt` は `from - 1` を先に試す（リンクの右端にキャレットがあるときアンカーを引けなくなるため — §5.5.2）。**リンクの直後から始まる選択では、その `from - 1` がそのリンクの中に落ちる。** まだリンクでない選択のために隣のリンクの `<a>` を基準にしていたわけで、報告①の文面はこの経路でも同じに見える。

**機構（直し方）**:

- **位置は `editing` が切り替わったあとに訊き直す** — `updatePosition` の meta を `useLayoutEffect` から送る。`computePosition` の答えは microtask で返り、それは「古い位置のカード」を映すペイントより前に走る。表示モードと URL 欄では高さが違い `top-start` はカード自身の高さを使うので、**畳むときにも同じ理由で要る — ただしそれは測れていない**: URL 欄を閉じる経路はどれもエディタにフォーカスを戻し、それ自体がプラグインに置き直させる（`focusHandler` は `oldState` 無しで `update` を呼ぶので選択が動いたと読まれる）。実測では閉じる側の効果は 0 である。規則を「形が変わったら置き直す」と書いておく側を採って残してあるが、基準は置いていない。
- **URL 欄のフォーカスは `preventScroll: true` で取る。** 位置を頼んだ直後のこの行は、まだ古い座標の上にいる（floating-ui の答えは microtask 1 つぶん遅い）。**断ってよいのは、スクロールの行き先が「これから置き直される座標」だからである。** 選択範囲が画面の中にあれば、カードはその横に出る。選択を画面外へスクロールしてから `Mod-k` した場合はフォーカスが画面外に載ったままになるが、これは修正前も同じ（当時は左上へ飛んでいた）で、**この経路は測っていない**。
- **付与のときは DOM に訊かない。** `editingRef.current` かつ `linkAtCaret` が null なら `getReferencedVirtualElement` は null を返し、プラグインの選択矩形（`posToDOMRect`）に任せる。§5.5.2 の 2 手はキャレットのための解決で、選択範囲のための解決ではない。

基準 5t・5u・5v がこれを固定している。**3 つとも文書には何も起きない欠陥である** — spec は矩形と `window.scrollY` で測る。

#### 5.5.12 リンクの右端を外に出す（2026-08-17 決定・実装）

**決定**: `link` マークを inclusive でなくした（`components/editor/link-extension.ts`）。**リンクの右端で打った文字はリンクの外に出る。** 左端もほぼ元からそうで、両端が同じ答えを返すようになった。Google Docs も同じである。**例外は段落の先頭にあるリンクの左端で、そこは変わった**（実測 2026-08-17: `Xリンク` がリンクの中 → 外）— `ResolvedPos.marks()` は親ノードの先頭では後ろのノードのマークを拾うが、それは inclusive なマークに限られるからである。左端は外、に揃った側の変化である。

**きっかけ**: 日本語の本文でリンクの直後に来る文字はたいてい `。` か `、` で、それが飲み込まれていた — `前[リンク](…)後` が一打で `前[リンク。](…)後` になる（実測 2026-08-17）。左端に語を足せないこと（§5.5.2 の表）より頻度がずっと高い。

**機構**: `extension-link` は `inclusive() { return this.options.autolink; }` と書いており、§4 が autolink を残した決定がそのまま右端も決めていた。この 2 つは別の問いである。 `inclusive` はマークの schema spec のフィールドでオプションではなく、他の拡張から `extendMarkSchema` で足しても勝てない — `@tiptap/core` の `getSchemaByResolvedExtensions` は `extraMarkFields` を先に展開してから拡張自身の `inclusive` で上書きするからである。したがって StarterKit の `link` を切り、ローカルの `.extend()` に置き換えた（`guarded-toggle-marks.ts` と同じ形。`@tiptap/extension-link` は starter-kit の tree にあるものをそのまま import しており、`package.json` への追加は要らない — `-bold` / `-italic` / `-strike` / `-code` / `-blockquote` と同じ扱いである）。

**autolink は動いていない。** autolink プラグインは `appendTransaction` で変更範囲を走査し、`tr.addMark(link.from, link.to, …)` で明示的な範囲にマークを付ける — キャレットが何を持っているかを訊かない。URL を打って空白を入れる経路も、その後に打ち続ける経路も実測で変わらなかった（基準 7c・7d）。§10 で却下した `autolink: false` とは別の変更である。

**払ったものが 2 つある。**

1. **カードが右端でキャレットに訊けなくなった。** そこでは `isActive('link')` が false、`getAttributes('link')` が `{}` になる（実測、基準 7f）。§5.5.2 が「`autolink: false` に転んだら `shouldShow` を range 解決に書き直す必要がある」と予告していた借りが、ここで来た。書き直したのが `LinkBubble.tsx` の `linkAtCaret` で、探るのはキャレットの前のテキストである — `$from.parent.childBefore($from.parentOffset)` がリンクを持つのは「中」と「右端」、持たないのが「左端」で、inclusive だった頃のカードの出方とちょうど同じになる。`getMarkRange` 単体では代わりにならない（§5.5.2 の追記。左端でも解決するので、カードが今まで出たことのない位置に出る）。カードが訊いていた 4 か所（`shouldShow`・href の読み出し・`Mod-k`・適用）が全部この 1 つを通る。
2. **本文でリンクのテキストを丸ごと打ち直すとリンクが外れる。** 右端に届く置換は、右端に打つのと同じ規則に従うからである。最後の 1 文字を残せばマークも `title` も残り、届く置換では打った文字がリンクの外へ出る（実測の 4 通りは `e2e/editor-link-text-edit.spec.ts` の冒頭にある。基準 7g）。この代金は §5.5.13 のテキスト欄が払っている — 本文でも書き換えられるが、境界を知らずに書き換えられるのは欄のほうだけである。損失そのものは目に見える（青と下線が同時に消える）。

入力ルールの `removeStoredMark` は要らなくなった（`link-input-rule.ts`）。「inclusive だから `)` の後に打った字が入る」が理由だったので、外して打ち続けても外のままであることを確かめてから消してある（基準 7e）。

#### 5.5.13 カードの「テキスト」欄（2026-08-17 決定・実装）

**決定**: 編集モードを 2 欄にした。上が「テキスト」、下が「リンク先」で、Docs と同じ順である。**§5.5.6-4 が「未検討のまま残す」と書いていた項目がこれで、いま実装されている。**

**欄の名前は各欄の左に出す**（2026-08-17 報告・修正）。2 欄が並んだときどちらがテキストでどちらがリンク先か分からない、という報告である。**プレースホルダでは答えにならない** — 既存のリンクを編集するときは両方の欄が埋まっており、埋まった欄はプレースホルダを見せないので、名前は消えないものでなければならない。上ではなく左に置くのは、カードにとって高さが高い軸だからである（リンクの上に出るので、1 行伸びるぶんだけ著者が読んでいる段落を隠す — §5.5.10 が測った 47px と同じ話）。幅は `w-72` の欄の横に空くだけで済む。名前は `<label for>` で書き、欄のアクセシブル名もそれが与える（それまでは `aria-label` だった）。テキスト欄を出さない場合（下の 2 つ）も「リンク先」の名前は出る — 欄の名前が隣の欄の有無で現れたり消えたりする理由がない。

**URL 欄はプレースホルダを持たない**（2026-08-18 報告・決定。報告は「文字が多すぎる」だった）。書ける形（`https://… / /posts/… / #見出し`）を並べていたのは、**この欄が内部リンクを作る唯一の道だった頃の名残**である — それが欄の存在理由そのものだったことは §5.5 の冒頭に書いてある。いまは違う: `[]()` の入力ルールが `#見出し` まで通し（§5.4、基準 6a）、実際にリンクが作られるのはその記法と選択範囲へのペーストの 2 つなので、**この行が教えていた形は別の場所で学ばれている。** 残る仕事は欄の名前を言うことだけで、それは左の `<label>` が既にやっている。命令文（「リンクを入力してください」）も同じ理由で採らない — ラベルと同じことしか言わないなら、持たないほうが静かである。

**カードにしか無いものは `#` を打った瞬間に出る。** 見出し候補（§5.5.17）は `document-headings.ts` を使う唯一の場所で、`[]()` で fragment を書く著者はスラグ（小文字化・記号落とし・重複時の `-1`）を自分で再現するしかない。**つまりこの欄の固有の価値は「fragment が書ける」ではなく「スラグを計算する」ほうである**が、それは空欄のグレーの文字ではなく候補一覧が名乗るべきものだった。

なぜ砂糖ではないか。 リンクのテキストは atom ではなくマークの付いたテキストなので、本文で打てば書き換わる — だから最初の見積もりは「Docs パリティの砂糖」だった。その見積もりは前提を取り違えていた: 著者が本文でリンクの文字を直しに行くとは限らず、カードを開いている流れのままそこで直せることのほうが導線として自然である（2026-08-17 の判断）。§5.5.12 が本文側の全置換を外したので、いまは欄のほうが確実でもある。

**機構**:

- **適用は 1 本の chain で、テキストの置換と href の適用を両方やる。** 1 トランザクション = **undo 1 回**である（基準 8c は `historyState` の `undoDepth` で測る。Ctrl+Z を押して見るのでは、2 イベントに割れていても 1 回で戻ったように見えることがある）。
- **判定は何かを変える前に済ませる。** `can().setLink({ href })` を先に訊く。chain は途中で断られてもそれまでに通ったコマンドを dispatch するので、後から訊く形だと「テキストだけ書き換わって href は元のまま」が残る（基準 8g）。
- 置換テキストにはいまの**マーク集合を丸ごと**載せる。`title` はマークの側にあり、href から組み直すと落ちる（§5.3-3）。`setLink` は属性をマージするので、その上から新しい href だけが乗る。リンクの文字が一様に太字・斜体・取り消し線・強調のときにその装飾が残るのも同じ 1 行による（2026-08-18。それまではリンクマークだけを載せていた）。
- 置換のあとは新しいテキストを選択したままにする。`setLink` が当たる範囲であり、カードがその後もそのリンクを指し続ける理由でもある（基準 8d。カードが滑る・塗りが外れるのは §5.5.7 の形で、文書についての assertion では見えない）。
- **テキストを空にする適用は断る。** URL 欄を空にする操作が既に「解除」なので、隣の欄に同じ意味を持たせない（基準 8f）。

**欄を出さない場合が 2 つある。**

1. **範囲の途中でマーク集合が変わるリンク**、および中に脚注参照やインライン画像があるもの。欄は範囲を 1 個のテキストノードで置き換えるので、それらを平坦化してしまう。**適用で断るのではなく最初から出さない**ほうを採った（基準 8h）。述語はノードの側で書く — 「テキストノードが 1 個か」ではない。マークが同じでもテキストノードは割れうるので、それだと普通のリンクを断ってしまう（§10 末尾の却下項が挙げている崩れ方と同じ）。

   **一様なマークは出さない理由にならない**（2026-08-18 報告・修正。基準 8m）。それまでの述語は「リンクマーク 1 個だけ」で、`[**打率.077**](…)` のように別サイトから貼った太字のリンクでは欄が消えていた — 報告はペーストを疑うものだったが、手で打った `**…**` でも同じで、脚注定義の中かどうかとも関係がない。太字が置換を危険にしていたわけではなく、置換がそれを運んでいなかっただけである。いまは範囲の全テキストノードが同じマーク集合を持てば欄を出し、その集合ごと新しいテキストに載せる。太字・斜体・取り消し線・強調のいずれもこれに乗る（`code` は `excludes: '_'` で `link` と共存できないので最初から来ない）。**残る不可は「途中で変わる」ほうだけ**で、そこは 1 個のテキストノードにする以上どうやっても片方に寄る。

2. リンクを作っている最中（`Mod-k`）。`Mod-k` は非空の選択を要求するので、テキストは既にあり、しかも著者がいま選んだものである。そこに欄を出しても「選んだものを置き換えますか」としか訊けない（基準 8i）。

フォーカスは今までどおり URL 欄に入る（内容を選択した状態で）。テキスト欄へは Shift+Tab かクリックで届く。「編集」ボタンがこれまで意味していたのは「URL を直す」であり、そこは黙って動かしていない。

#### 5.5.14 IME で右端に打つとカードが残る（2026-08-17 報告・修正）

**報告**: リンクの右端に文字を足してもカードが閉じない。**再現するのは IME 経由の入力だけで**、`keyboard.type` で書いた spec は壊れたビルドでも通る（実測）。

**機構**: `@tiptap/extension-bubble-menu` の `updateHandler` は `const { composing } = view;` を読んで `if (composing || isSame) { return; }` で始まる。**変換で入った文字を運ぶ transaction は、そのフラグが立っている間に届く。** プラグインが訊き直す経路は「選択か文書が動く transaction・resize・scroll」だけなので、変換が確定したあとに訊く者がいない。カードはキャレットがリンクを出たあとも、出たままになる。

**§5.5.12 が表に出した欠陥である。** マークが inclusive だった頃は打った文字がリンクの中に入っていたので、カードは残っていて正しかった。

**直し方**: 塗りを決めている効果（§5.5.7）に 1 行足した。**プラグインが出しているのに `shouldShow` が断るなら、`hide` の meta を送る。** この不一致が起きる経路は上の 1 つだけなので、`compositionend` を直接聴くより狭くならずに済む — 変換の途中でも成り立ち（右端で変換を始めた時点でキャレットは既にリンクの外にある）、`compositionend` から `state` が更新されるまでの遅れ（prosemirror-view の `flushSoon`）を数える必要もない。

基準 7h・7i がこれを固定している。**7i は「変換したら閉じる」ではないことを測る側で**、リンクの中で変換したときにカードが残ることを見ている。合成は CDP の `Input.imeSetComposition` → `Input.insertText` で行う（`keyboard.type` は `view.composing` を立てない）。

#### 5.5.15 欄を閉じるときにカードが一瞬映る（2026-08-17 報告・修正）

**報告**: 本文の別の場所を押して URL 入力欄を閉じると、表示モードのカードが一瞬見える。

**機構**: 欄を畳む処理は同期で走るのに、カードを消す判断は 1 フレーム後（`focusLeft` の再判定）か、キャレットが動いた transaction まで来ない。その間、**カードは著者がいま離れたリンクの上に表示モードで描かれる**。実測（2026-08-17、ページの中で毎フレーム標本）: 本文を押したときは **3 フレーム**、エディタの外を押したときと Tab で抜けたときは 1 フレーム。

**直し方**: **本文の中への押下は、その場で「カードは出ていく」と分かる。** 押下はこれからキャレットをそこに置くので、そのリンク自身の `<a>` の中でない限り、カードの相手は変わる。だから欄を畳むのと同じタスクで `hide` の meta を送る — 描画の前に届くので、表示モードのカードは 1 フレームも出ない。キャレットが別のリンクに落ちたときはプラグインが自分で出し直す（`updateHandler` は `show()` → `updatePosition()` の順なので、位置が古いまま出ることはない — §5.5.11 で問題になったのは `"show"` の meta の側だけである）。

**エディタの外への押下はこの規則に入れない。** そこでは答えがまだ決まっていないからで、ツールバーのボタンはフォーカスをエディタに戻し、カードは残るのが正しい（§5.5.9）。**残る 1 フレームはその代金である。** 先に消しておいて残ると分かったら出し直す形も採れるが、そちらはツールバー経由の押下にカードが消えている時間（mousedown から mouseup まで）を作る — その長さは測っていない。

基準 5w・5x がこれを固定している。**5x は「押下で消す」ことにした側の逆を測る** — 同じリンクの中を押したときはカードが残る。

#### 5.5.16 編集モードのボタンは「適用」1 つ（2026-08-17 決定・実装）

**決定**: 編集モードのボタンは **適用** の 1 つで、他と同じ素のボタンである。2026-08-17 まで「保存」「やめる」の文字ボタン 2 つだった（同日、一度 ✓ / ✕ のアイコン 2 つを経ている）。

**保存ではない理由**: このボタンは何も保存しない。編集を文書に書き込むだけで、本文が DB に届くのはそのあとのオートセーブである。**そしてこの UI では「保存」が既にその層の名前である** — `PostEditor` のインジケータが 保存済み ✓ / 保存中… / 保存に失敗 で、記事側に保存ボタンは無い。押した直後にインジケータが「まだ保存されていない」側に変わるのに、押したボタンには保存と書いてある、という状態だった（当時の文言は 未保存…。2026-09-13 に 保存中… へ変更）。適用はこの操作が文書に対するものだと言う。

**取り消しを置かない理由**: **✕ が表示モードの「解除」と区別できない。** 解除はリンクを外す操作で、こちらは編集をやめるだけである — このカードで唯一、誤読すると著者が失うのが編集ではなくリンクになる組み合わせだった。語で書けば解けるが、それはカードを 448px に戻すということでもある。**幅を取り返す側を選んだ**（403px）。抜ける手段は Escape・カード外の押下・フォーカス離脱の 3 つが残っており、ボタンが持っていたのは「その手段が見えていること」だけであり、**それを捨てる判断である。**

**色は文字に乗せ、背景はホバーで出す。** 一度ボタンごとリンク色で塗って戻した（同日）— **このエディタのクロームは他がすべて素のボタンなので、塗ると このカードが持っていない重さに見える。** 記事側の主ボタン（公開する）だけが塗られている状態は保つ。文字だけなら、同じことを周りと同じ描き方で言える。**形は「解除」が赤で着ているものと同じ**（`ToolbarButton` の `destructive` と `accent`）で、1 つ上の面では赤が外す側、この面では青が確定する側になる。

実測のコントラストは 5.19（light 静止）/ 6.26（light ホバー）/ 4.81（dark 静止）/ 6.50（dark ホバー）で、いずれも AA。

基準 8l がこれを固定している。**ボタンが 1 つであること自体を測る** — 2 つ目が生えたらそれは上の判断を戻す変更であり、黙って起きてよいものではない。

#### 5.5.17 リンク先の欄で `#` を打つと見出しを選べる（2026-08-18 決定・実装）

**決定**: リンク先の欄の**先頭**に `#` を打つと、その文書の見出しが候補として並び、選ぶとその見出しに届くフラグメントが書き込まれる（`components/editor/document-headings.ts`、`LinkBubble.tsx` の `suggestions`）。

**理由**: **slug は見出しを見ても分からない。** 実測（2026-08-17、公開パイプラインに通した）:

| 見出し               | 実際の id                     | 手で書くと外す理由   |
| -------------------- | ----------------------------- | -------------------- |
| `導入`               | `user-content-導入`           | —                    |
| `Hello World`        | `user-content-hello-world`    | 小文字化・空白が `-` |
| `API と CLI（詳細）` | `user-content-api-と-cli詳細` | 全角括弧が落ちる     |
| `導入`（2 つ目）     | `user-content-導入-1`         | 重複に連番が付く     |

そして**外したフラグメントはどこでも断られない** — 普通のリンクとして描かれ、どこにも飛ばないだけである。§2.1.1 が塞いだのは「内部リンクを作れない」ことで、作れるようになった先に残っていたのがこの穴だった。

**同じ関数で作る。** `github-slugger` を直接依存に足した（2.0.0、`rehype-slug` が内部で使っているものと同一）。近似を書くと、ずれたときにずれたことが誰にも分からない。`components/editor/document-headings.test.ts` が `renderMdxToHtml` の出力そのものと突き合わせて両者を固定している — 期待値の表と突き合わせるのでは、2 つが離れた日にも同じように通ってしまう。

**書き込むのは接頭辞の付かない側**（`#導入`）。`user-content-` を付けるのは公開時の `lib/rehype-clobber-fragment-links.ts` で、著者が自分で書くと二重になる（実測 `user-content-user-content-導入`）。§2.2.2 の percent-encode も往復の側の話であり、欄に入るのは素の見出し名である。

**空の見出しも slugger に数えさせてから落とす。** 数えずに飛ばすと、そのあとに続く重複の連番が公開側とずれる。

**発火は先頭の `#` だけ。** 途中の `#` は URL 自身のフラグメント（`https://example.com/#section`）で、そこで候補を出すとフラグメント付きの外部リンクを打つたびに邪魔になる。

**Escape は候補だけを閉じる。** カードの Escape は編集ごと閉じるので、そのまま通すと著者は入力中の URL を失う — §5.5.16 が取り消しボタンを外したときに「抜ける手段は Escape がある」と書いた側の代金である。

**行を取るのは click で、mousedown ではない。** mousedown は既定を止めるだけにして、フォーカスを欄に残す（§5.5.9 の形）。実測 2026-08-18: mousedown で選ぶと押下と離上の間に行が消え、**離上が下の本文に落ちてキャレットがそこへ移り、カードと未適用の編集ごと消えた。**

**一致が無いときは 2 つの文言を出し分ける** — 「この文書には見出しがありません」と「一致する見出しがありません」で、著者がすることが違う（先に見出しを書く／打ち間違いを直す）。**これがフラグメントの誤りを著者に見せる唯一の場所である。**

**候補が Enter を取るのは、押して値が変わるときだけである。** 打ち切ったフラグメントに Enter を押した著者は適用を求めており、そこで候補が先に取ると同じ結果に 2 回押させることになる — `Mod-k` → `#見出し` → Enter（基準 4f）のような既存の手順がすべて 1 手増える。

**行はレベルで下げない。** h3 も h2 と同じ x から始まる。数時間だけ目次と同じ段差（h3 に `pl-6`）を付けていたが、**目次で段差が成立するのは一覧が完全で、h3 の上に必ず親の h2 が見えているからである**。この一覧は絞り込まれるので、`#導` と打った瞬間に親が消え、段差は一覧が見せていない関係を指す。「その行自身が小見出しだという印」と読み替えても当てにならない — 空白は隣と比べて初めて読めるもので、**絞り込みの結果が全部 h3 なら一覧全体が下がっているだけになる**。幅の側の代金も具体的で、288px の行で削られるのは先に truncate される見出しの文字のほうである。レベルが要るのは同名の見出しが 2 つのレベルにあるときだけで、そのときは絞り込みでも壊れない明示的な印で答える。`DocumentHeading` がレベルを持たないのはこの判断の帰結である。

**テキスト欄が空のときだけ、見出しの文字を入れる。** 著者が書いたテキストは触らない。

**一覧の位置はカードと同じ floating-ui に決めさせる**（2026-08-18 追加）。既定はカードの下、下に入らなければ上、どちらにも入らなければ広いほうへ寄せてその空きに高さを詰める（`flip({ fallbackStrategy: 'bestFit' })` + `size`）。

**報告と実測**: 720px のウィンドウで、リンクの行が下端から 90px の位置にあり見出しが 9 個あると、一覧（192px）の**下 70px が画面外**に出た。カードはクロームなのでスクロールしても追いつけず、ポインタも届かない。キーボードでは一覧自身がスクロールするので選べる — **壊れているのは「見えない・押せない」であって「操作不能」ではない**。同じ位置でも見出しが 3 個なら一覧は 90px で 52px 余って収まる。つまり条件は「下端付近」ではなく「下端付近 **かつ** 一覧が上限まで伸びている」である。

**基準要素はカードであって欄ではない。** 欄を基準に上へ反転させると、一覧がカード自身のテキスト欄を覆う。カードを基準にすれば重なる配置が存在しない。欄の真下という横位置は `offset` の `crossAxis`（ラベル列の幅を配置時に読む）で保つので、ピクセル定数は増えない。

**`flip` は `size` より前に置く。** 順序がそのまま優先順位で、`size` が先に走ると「どこにでも入る」状態を作ってしまい、`flip` は反転する理由を失う。結果は下に出たまま 4 行に縮んだ一覧になる。境界はカードと同じ `editor.view.dom` で、floating-ui がそれをビューポートと交差させるため、ツールバーの帯と画面下端の両方が一度に効く。

**`shift` は入れない。** 一覧はカードより狭く、欄の左端から始まり、カードは既に自分のプラグインに画面内へ寄せられている。横方向に残った問題が無いうえ、入れれば `crossAxis` のオフセットと争う。

**欄は `combobox` にしない。** 役割は欄に常に付くもので、この欄は 1 種類の値のときだけ一覧を出す URL 欄である。開いた著者全員にコンボボックスだと名乗るのは、カード自身の `role='group'` が断ったのと同じ取引になる（持っていないモデルを約束しない、§5.5.6）。役割が付いたり外れたりするのはさらに悪い。**代わりに `aria-activedescendant` を出す** — `textbox` が持てる状態で、いま選ばれている行を読み上げに伝えるのはこれである。**代金は一覧が出たこと自体は伝わらないこと**で、行に着いたときに初めて分かる。

基準 9a〜9l がこれを固定している。

#### 5.5.18 フラグメントのリンクでは、上の行がその見出しへ移動する（2026-08-18 決定・実装）

**決定**: href が `#…` のとき、カードの上の行は**この文書のその見出しへキャレットを移してスクロールする**。他の href（`https://…`、`/posts/…`）は今までどおり新規タブを開く。名前も分岐する（`見出しへ移動` / `リンク先を開く`）。

**報告と機構**: フラグメントで `開く` を押しても新しいタブが開くだけで、見出しまでスクロールしない（2026-08-18 報告）。`window.open('#導入')` は**現在の文書**に対して解決するので、開くのは編集画面（`/admin/posts/[id]/edit`）の複製であり、そこに `導入` という id を持つ要素は無い（`user-content-…` は公開側の sanitize が付ける）。**開くという操作がそもそも存在しない場所だった。**

**これが埋めるのは §5.5.17 とは別の穴である。** 候補リストは書くときに誤ったフラグメントを書けなくするが、**見出しを改名すれば既存のリンクは黙って死ぬ** — 公開ページでもクリックして何も起きないだけで、どちらの面にも知らせるものが無い。押して「この文書にその見出しはありません」と言うこの行が、その唯一の検出点である。

**一致は厳密に取る。** 大文字小文字を畳まず、percent-encode は先に解く（`headingForFragment`）。ブラウザが id と突き合わせる規則と同じにしてあるので、**ここで見つからないフラグメントは読者にとっても飛ばないフラグメント**である。寛容にすると「動くリンク」だとカードが嘘をつくことになる。

**畳まれたアコーディオンの中は、開かずに断る。** キャレットは置けるが `display: none` の中なのでスクロールは起きず、押しても画面が 1px も変わらない — このリポジトリが繰り返し踏んできた「黙って何も起きない」の形である。**著者が畳んだものをこの操作が開くことはしない**（頻度に対して、トグルのクリック・フレーム跨ぎ・入れ子の考慮が高すぎる）。判定は「描画されていない」（`offsetParent`）で、アコーディオン固有の知識を持たないので、折りたたむ仕組みが増えても同じ規則で答える。**リンク自体は無効ではない** — 公開ページの `<details>` は読者がフラグメントで飛ぶと自分で開く。行けないのは下見のほうだけである。

**スクロールは自分で中央へ寄せる**（2026-08-18 報告・修正）。transaction の `scrollIntoView()` は prosemirror-view の**最小スクロール**（`scrollRectIntoView`、既定の余白 5px）で、このエディタのツールバーが `sticky top-0` で**スクロールポートの上に重ねて描かれている**ことを知らない。実測: 飛んだ先の見出しは y=5 に着地し、ツールバーの下端は y=29 だった — **キャレットは指示どおりの場所にあり、その行は読めない。** ツールバーの高さを定数で持つ（ボタンが折り返した日に古くなる）代わりに、要素を `scrollIntoView({ block: 'center' })` で中央に置く。見に行った行の前後が一緒に見えるという点でも、中央のほうが正しい。公開ページ側の `#post-body h2 { scroll-margin-top }` と同じ問題に、別の面で答えている。

**カードは自分で消える。** 移動後のキャレットは見出しの中でリンクの外なので、プラグインが `shouldShow` を訊き直して閉じる。閉じる処理は書いていない。

**ついでに、フラグメントでは `/api/link-title` を叩かなくなった。** §5.5.10 の effect のコメントは「フラグメントは訊かない」と書いていたが、`new URL('#導入', origin)` が `https:` になるためガードを通過し、リクエストは飛んで `null` が返っていた（`ownTitle` は `/posts/<slug>` しか知らない）。カードの表示は変わらず、キャレットを置くたびの往復が 1 つ減る。

基準 10a〜10d がこれを固定している。

#### 5.5.19 カードは画面より広くならない（2026-08-21 報告・修正）

**決定**: カードに `max-width: calc(100vw - 1rem)` を与え、**幅は編集レイアウトのグリッドが持つ**（`w-96`）。入力欄は自分の列を埋めるだけで、幅を決めない。

**報告**: スマートフォンの幅でバブルが画面に収まらない。**実測（2026-08-21）**: 表示モードは 204px で収まっている。はみ出すのは編集モードだけで、幅 403px に対して 390px の画面で 13px、320px の画面で 83px。**切れるのは右端の 適用**で、320px では画面外に出て**編集を確定できない**。

**位置の問題ではない。** `shift` は有効で、実測では `left` が 0〜1px — 寄せきった状態である。中身が画面より広い以上、置き場所では解けない。

**幅を入力欄から取り上げたのが修正の要点である。** 最初は欄に `max-w-full` を足しただけで済ませようとしたが直らなかった: **グリッドのセルの中では、定値幅（`w-72` = 288px）に百分率の `max-width` を当てても縮まない** — 229px の列の中に 288px の欄が残ったまま、その先の 適用 が画面の外へ押し出される（実測）。そこで幅はグリッドに 1 か所だけ置き、欄は `w-full` にした。**幅を宣言している場所が 1 つになったので、画面に合わせて縮める操作もそこ 1 つで済む。**

縮ませるには連鎖の全員に許可が要る。カードは flex なので**グリッドに `min-w-0`**（flex アイテムは既定で min-content より狭くならない）、行の中では**リンク先の欄が `flex-1 min-w-0`** で伸び縮みし、**適用 は `shrink-0`**（付けないと押される側になり、390px で「適/用」と 2 行に割れた）。**ラベルは `whitespace-nowrap`** — 320px で「テキスト」が 1 文字ずつ 4 行に割れ、カードが 146px 丈になったのを直したものである。**縮む役は欄だけでよい。**

**実測（修正後、2026-08-21）**: 1280px で 402px（従来 403px。1px の差はグリッドが幅を宣言するようになった分）、390px で 374px、320px で 304px。高さはどの幅でも 70px で、割れは 1 つも残っていない。基準 12a・12c。

**続報 —「カード化できないリンクの次にできるリンクを開くとはみ出す。スマートフォンでのみ起きる」**（2026-08-21）。カードの幅はボタン 1 つにつき約 30px 変わる（見出しの中のリンクは単独行ではないので「カードにする」を持たない）ので、**上限に当たっている画面では、当たり方だけが変わって見える**。

**最初の上限は `calc(100vw - 1rem)` で、これが取りこぼしていた。** 幅の計算は合っていて、はみ出しは 0 だった — 実測（エミュレートした実機、412px）: 左 16px、幅 396px、**右端 412px**。カードは本文の左端（16px）に置かれ、幅の上限が `100vw - 16px` なのだから、**右端はちょうど `100vw` に着地する。** 画面の最後の 1px であって、外ではない。**ただし「ちょうど画面幅」は実機で最も危うい値である** — 角の丸め、セーフエリアの余白、レイアウトビューポートの端数のいずれか 1 つでも `100vw` と可視幅がずれれば、そのぶんが切れて見える。デスクトップでこれが起きないのは、幅 437px のカードが上限にまったく届かないからで、**実機だけで見えるのはそのためである。**

**修正（2026-08-21）**: 上限を `calc(100vw - 2rem)` にし、`shift` に `padding: 8` を渡す。**片側 8px ずつ空ける。** 幅の上限だけでは足りない — 上限は幅を決めるだけで、`shift` は「入っている」限り端に張り付いたままにするので、両方に同じ余白を教える必要がある。実測（同じ実機、修正後）: 左 24px、右 404px、つまり**画面の端から 8px**。表のツールバーも同じ 2 か所を同じ値にした（`docs/table-requirements.md` §12）。

**基準は「はみ出していないこと」ではなく「余白があること」を測る**（12a・12b・12d）。ちょうど画面幅に着地するカードは前者を満たしてしまい、それがこの報告そのものだったからである。**12e はエミュレートした実機で測る** — 狭くしたデスクトップの窓とは別の環境で、`isMobile`・端末のピクセル比・ビューポート meta の扱いが付いてくる。

**続報 —「見切れてはいないが横スクロールが出る」（2026-08-21）。出た。ただし犯人はカードではなく見出しの候補リストだった。** リストは `w-72`（288px）のまま上限を持たず、欄の左端から始まるので、**320px の画面で 35px ページを広げていた**（実測）。リストは `<body>` にぶら下がるので、広がるのはカードではなく**ページ**である — 著者が打っている最中にエディタが横に動く、という形になる。§5.5.17 が「`shift` は要らない」と書いていた根拠（リストはカードより狭く、カードは既に画面内にある）は、**カードだけが上限を持った時点で成り立たなくなっていた。**

**修正**: リストにも `max-w-[calc(100vw-2rem)]` を与え、`shift({ padding: 8 })` を足す。**両方が要る** — 画面より広い箱は動かしても入らないので上限が先で、上限だけでは欄の左端から始まったまま右へはみ出すので `shift` が要る。crossAxis のオフセット（欄の左端に揃える）は生きていて、`shift` は画面から出るときだけ引き取る。

**さらに続報 —「まだ横スクロールが残る」（2026-08-21）。残っていた。今度はメニューですらなかった。**

**犯人は `EditorTooltip` である。** ツールチップは `opacity: 0` で、**見えないまま場所を取る** — 絶対配置の箱はページのスクロール可能領域に数えられる。ボタンの真下に中央揃えで置かれ、幅は自分の文字数で決まるので、**ツールバーのボタンが右端の近くに来る幅では、見えない 95px のラベルが画面の外へはみ出す。** 実測（エミュレートした実機、360px）: 文書 366px 対画面 360px。**画面上には何ひとつ切れて見えない**ので、原因が目で追えない形をしている。

**幅ごとに出たり出なかったりするのは、ツールバーの折り返し位置が決めるからである。** 412px・390px・375px・320px はいずれも綺麗で、**360px（Android で最も多い幅）だけが汚れていた** — 私が最初に測った幅がすべて綺麗だった理由でもある。

**修正**: `@media (hover: none) { .editor-tooltip { display: none } }`。幅を詰めるのではなく消す — **hover の無い端末では、このツールチップははみ出しているだけでなく、そもそも出せない。** 内容はボタンの `aria-label` が持っているので失うものは無い。タッチスクリーンとマウスを両方持つノート PC は `hover: hover` を報告するので、そちらでは残る。

**基準 12g はこの 2 つの条件を両方持つ**（エミュレートした実機 × 360px）。片方だけでは通ってしまう — デスクトップの 360px はスクロールバーの分だけ内容幅が狭く、`hover: none` にも当たらないので、規則が無い状態でも緑になる。**メニューを 1 つも開いていない状態から測る**のも同じ理由で、これはメニューの問題ではなくページの問題だからである。

**最後の 1px（2026-08-22 に端末が報告した）。** ここまでの 3 回はいずれも実測した原因に当たっていて、それでも報告が残った — エミュレータで測れる幅がすべて綺麗だったからである。そこで**一時的な計測器をアプリに入れて実機に喋らせた**（`?wdebug=1` で隅に「ページ幅 / 画面幅 / はみ出している要素」を出すだけのもの。原因が分かった時点で削除した。入れたのは `6a4d45a`、消したのはこの節を書き終えた直後のコミットで、中身は `git show 6a4d45a` で読める）。返ってきた 1 行が `441/440 ⚠ link-bubble R=441 w=408` — **画面 440px、カードの左端 33px、幅は `100vw - 2rem` の上限ちょうどの 408px、右端 441px。1px だけ外に出ていた。**

**機構**: プラグインはカードを**自分の view update の中で**置く。それは React がそのリンク用にカードを描き直す**前**なので、**座標は 1 つ前のカードの幅に対して計算される。** 見出しの中のリンクは「カードにする」を持たず、単独行のリンクは持つので、移動するとボタン 1 つぶん（約 30px）**あとから**広がる。`shift` は既に走り終えていて、二度目は走らない。**カードは本文の左端（33px）に置かれたまま、右へ伸びる。**

**幅の帯でしか出ない。** 狭い側では移動の前後ともカードが上限に張り付いているので幅が変わらず、広い側では上限に届かないので伸びる余地がある。**帯は「細いほうは収まり、太いほうは収まらない」幅**（実測: 450px と 460px で再現、360 / 375 / 390 / 412 はいずれも綺麗）。私が最初に測った幅がすべて帯の外だったことが、4 回外し続けた理由である。

**修正**: **カードの箱そのものを `ResizeObserver` で見て、変わったら置き直す。** 依存配列に条件を足す形は採らない — タイトル行の到着（§5.5.10）、favicon、「埋め込みにする」も同じようにカードを広げるので、条件を数え上げる方式は必ず取りこぼす。**「形が変わったら置き直す」という §5.5.11 の規則を、原因ではなく結果の側で実装した。** 置き直しは `left` / `top` しか変えないので自分を焚きつけることはない。基準 12h。

**そして基準は 1 段上げた（12f）**: 個々の余白ではなく、**どのメニューを開いてもページが画面より広くならないこと**を測る。カード・欄・候補リスト・表のツールバーを 1 本の spec で順に開いて `scrollWidth` を見る形で、要素ごとの余白を測る基準（12a・12b）が構造的に取りこぼす — ツールチップやリストのように、メニューが自分の外にぶら下げるものは標本に入らない — 側を塞ぐ。

**表のツールバーが同じ形で壊れていた**（441px、`shift` は寄せきり）。直し方は違って、あちらは既にある `flex-wrap` に上限幅を与えて 2 段にする — `docs/table-requirements.md` §12。

#### 5.5.20 文書の先頭付近では、カードが次の行を覆う（2026-08-22 実測・受け入れ）

**決定**: このまま受け入れる。直さない。

**実測（2026-08-22、実機エミュレーション、390px / 360px / 320px で同一）**: 見出しの中のリンクにキャレットを置くと、カードは**見出しの下**に出る。カードは 371–413px、見出しの下端は 373px、すぐ下の段落のリンクは 399–420px — **14px 重なる**。そのリンクの中心を叩くと、`elementFromPoint` が返すのはカードである。**つまり下の行のリンクは、カードが出ている間は触れない。**

**機構**: 上に出せないので `flip` が下へ送っている。境界をエディタの箱にしているのは §5.5.9 の決定（sticky ツールバーの帯は「存在するが使えない場所」で、そこへ送るとカードは `z-20` のまま帯の下に潜って**画面上にあるのに見えない**）。文書の先頭付近には上の余地が無いので、下に回る以外の選択肢が無い。**そして下に回った時点で必ず次の行に乗る** — 見出しの下端と次の行の間は 26px しかなく、カードは 42px だからである。

**受け入れる理由**: カードは一時的で、Escape・キャレットの移動・少しのスクロールのいずれでも消える — 覆われた行に触るための出口が 3 つある。**そして代案は 2 つとも、これより悪いものを買う。**

- **カードの「操作でない部分」をタップ透過にする**（土台を `pointer-events: none` にし、ボタンと href 行だけ `auto` に戻す）。下の行は触れるようになるが、**ボタンを狙って少し外したタップがキャレットを動かし、カードごと消える。** これは §5.5.17 が一度踏んだ事故（行が mousedown で消え、mouseup が文書に落ちてキャレットが飛ぶ）と同じ筋である。
- **下に回るとき、次の行ではなく自分の行に重ねる。** 隠れるのが編集中のリンク自身になるので損失は小さい（内容はカードが文字で見せている）が、`flip` の落とし先を自前で補正することになり、§5.5.9 と §5.5.11 の置き直しの規則に枝が 1 本増える。**頻繁に踏むなら投資する価値はある。そのときはこの節を書き換える。**

**spec を書く人への注意**: この重なりは、E2E では「下の行のリンクへの `click()` が 15 秒待って落ちる」という形で出る。**画面上は何も壊れていない**ので原因が見えにくい。狭い幅でカードを出したまま下の行を触る spec は、クリックではなくキャレットを直接置くこと（`e2e/editor-narrow-menus.spec.ts` の 12d・12e がその形にしてある理由でもある）。

#### 5.5.21 スマホで「適用」を押すとスクロールが飛ぶ（2026-08-22 報告・修正）

**報告**: 実機（スマホ）でリンクの編集メニューの `適用` を押すと、画面が別の場所へ動く。

**機構**: `editor.commands.focus()` は、**スマホでだけ 2 回スクロールする。** @tiptap/core の `focus` コマンドは `isiOS() || isAndroid()` のとき `view.dom.focus()` を **`preventScroll` 無しで**呼び、その 1 フレーム後に `view.focus()` と `editor.commands.scrollIntoView()` を続ける。前者が見せようとするのはエディタの要素そのもの（リンクではない）で、後者は prosemirror-view の最小スクロールである。デスクトップはこの枝に入らない（Safari は `focus({ preventScroll: true })`、それ以外は `view.focus()` だけ）ので、**同じ操作がスマホでだけ壊れる。**

**実測（エミュレートした Pixel 7、埋め草 20 段落の中のリンク）**: `適用` の押下で `scrollY` が 1055 →（同一タスク）303 →（次のフレーム）651。**押す前に見ていた行は画面から出る。**

**修正**: `適用` の 2 つの出口（href を書く側と、欄を空にしてリンクを外す側）は `editor.view.focus()` を呼ぶ。prosemirror-view の `focus()` は `focusPreventScroll` でフォーカスを取り、選択は `selectionToDOM` で自分で同期する — **スクロールはどちらの意味でも起きない。** ここが動かしたいものは何も無い: 編集していたリンクこそ著者が見ている場所である。`focus(null, { scrollIntoView: false })` では足りない — このオプションが黙らせるのは後者だけで、`preventScroll` 無しの `view.dom.focus()` はそのまま残る。

**同時にフォーカスが同期になる。** カードが `適用` のあとも残る根拠（§5.5.9）は「欄の unmount が起こす `focusout` を 1 フレーム後に `focusLeft()` で判定する」ことなので、フォーカスがより早くエディタへ戻る分には答えは変わらない。

`close()`（欄での Escape）と、カードのボタン上での Escape は `editor.commands.focus()` のままにした。 前者は 1 フレーム遅れてフォーカスが戻ることに依存している — `abandonField` の rAF がその時点で「フォーカスは離れた」と読むから Escape でカードが消える — ので、同期にすると表示モードのカードが残るという別の変化を買う。スマホに Escape キーは無く、報告もされていない。**測った経路だけ直す。**

**spec はスマホのエミュレーションでしか赤くならない**（`editor-link-bubble.spec.ts` の `on a phone`）。デスクトップの Chrome は上記のとおり別の枝を通り、修正前でもスクロールは 1px も動かない。`test.use` にはデバイス記述子を丸ごと展開できない（`defaultBrowserType` と `channel` は worker スコープで、describe の中では拒否される）ので、`viewport` / `userAgent` / `deviceScaleFactor` / `isMobile` / `hasTouch` だけを渡す。枝の判定は `navigator.userAgent` なので、この機構はこれで測り切れる。**ソフトキーボードも実機で確認した（2026-08-27、著者報告）— 症状は残っていない。** `適用` のボタンは mousedown を止めていないので、押下が URL 欄からフォーカスを奪い、キーボードが引っ込んでからフォーカスと一緒に戻ってくる。この往復は原理的にはスクロールを動かせるが、実機では動いていない。エミュレーションにソフトキーボードは存在しないので、**この確認は spec に持ち込めず、§8 の表にも入らない**（`Mod-k` と同じ理由、§9）。再発したときの直し方は mousedown を止める側である。

### 7.1 リンクの色（2026-08-11）

**決定**: `app/globals.css` の `.prose a` に `#0969da`（dark は `#4493f8`）を当てる。**下線は残す。**

**覆した理由**: 「特別扱いする理由が今のところない」と書いた時点で、実は理由はもう存在していた。`app/globals.css:1557-1560` が、脚注参照の zinc-900 下線付き数字は「ordinary link that happens to be raised」＝ ただのリンクに見えると記録し、まさにこの青で直している。結果としてページ上でいちばんリンクらしい色をしているのが脚注参照で、本物のリンクは本文と同色、という逆転が残っていた。色数は増やしていない — 青のペアはその脚注参照の規則から取っており、青がサイト内で一つの意味を持つ状態を保っている。

**実測（変更前）**: prose-zinc の `a` は固有の色を持たない。ライトで zinc-900 対 本文 zinc-700 = **1.7:1**、ダークで white 対 zinc-300 = **1.5:1**。リンクを文中から分けていたのは事実上下線だけだった。

**アクセシビリティは論点ではない**（§7.2 の `target` と同じく）。下線という非色の手がかりがあるので変更前も SC 1.4.1 は満たしていた。これは適合の話ではなく可読性と一貫性の話である。**だから下線を外してはならない** — 脚注参照が下線を落とせたのは 0.75em の上付き数字という固有の事情（`globals.css:1578-1581`）であって、本文サイズのリンクには当てはまらない。

**エディタ側の追加の利得**: `openOnClick: false`（§3）でエディタ内のリンクは飛ばず、リンクカード（§5.5）はキャレットがリンク内に入って初めて出る。つまり「どこからどこまでがリンクか」を先に目で見つける必要があるのに、その手がかりが下線だけだった。

**エディタと公開の両方に一度で効く。** `PostEditor.tsx:358` と `app/posts/[slug]/page.tsx:116` は同じ `prose prose-zinc dark:prose-invert` を着ている。片側だけに寄せる案は採らなかった — それは `PostEditor.tsx:210-212` の underline 無効化と §4 の autolink が二度拒否した「WYSIWYG のウソ」そのものになる。

**`.prose a` が巻き込む `<a>` は数え上げてある**（汎用セレクタなので、ここが事故る側）:

| 経路                                                                | 結果                                                                                                                                                                                                          |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本文・表・callout・アコーディオン内の著者のリンク                   | 対象。意図どおり                                                                                                                                                                                              |
| 脚注参照 / 戻りリンク                                               | 属性セレクタ (0,2,1) が明暗とも勝つ。不変                                                                                                                                                                     |
| 脚注ポップオーバー内（`FootnotePopover.tsx:139` が `prose` を着る） | クローンした本文中のリンクは青になる（一貫していてよい）。`.footnote-popover-jump` (0,1,0) はこの規則 (0,1,1) に負けるが**色は明暗とも同値**で、`color` しか宣言していないので `text-decoration: none` は残る |
| ブロックドラッグのプレビュー（`block-drag-handle.ts:131`）          | 本体と同じ色になる。意図どおり                                                                                                                                                                                |
| 目次                                                                | `.prose` の外（`globals.css:900` に明記）。不変                                                                                                                                                               |

**この数え上げには裏側がある。** 「この規則がどの `<a>` に届くか」だけでは半分で、もう半分は「この規則が今どの既存宣言に勝ってしまうか」である。`.prose a` は (0,1,1) かつ unlayered で、置き換えた typography の規則は (0,1,0) かつ layered だったので、`.prose` 内で単一クラスの `color` を持つものはすべて候補になる。

`.accent-emphasis`（`#cf222e`、(0,1,0)）が**唯一「別の色を失いうる」相手**で、しかも `accent-emphasis-extension.ts` の `excludes` は bold/italic/strike/code を挙げるが **`link` を挙げていない** — リンク＋強調は仮定ではなく到達可能である。

**詳細度の争いはそもそも起きない。** 強調の span は `<a>` の**内側**に入る（`<a …><span class="accent-emphasis">…</span></a>`、エディタ・公開とも）ので、2 つの規則は別々の要素に当たる。2026-08-11 の実測はここまでで、結論は「文字は `#cf222e` のまま」だった。**この結論は入れ子の順序に依存していて、それを固定しているものは repo に他に無い。** だからコメントではなく 5f として spec に置いた。

**その結論をいま覆している（2026-08-18 報告・修正）。報告は「文字と下線の色が違う」である。** 下線を引いているのは `<a>` 自身で（`@tailwindcss/typography` の `a: { … textDecoration: 'underline' … }`）、text-decoration は**それを宣言した要素**の色で描かれる — 子孫の `color` は文字には届くが、その下の線には決して届かない。つまり span 側に何を書いても直らず、選べるのは「下線を赤にする」か「文字を青にする」かの 2 つしかなかった。

**青を採った。** リンクにおける色は「押せる」という信号そのもので、両面で青がその意味を担っている（この §7.1 の決定）。対して赤は 強調 が持つ 2 つの手がかりの一方にすぎず、もう一方の 700 の太さはここでも無傷で残る。`accentEmphasis` はもともと bold/italic/strike を**置き換える**マークで、往復の安全と引き換えに自分の一部を捨てる作りなので（`accent-emphasis-extension.ts`）、その延長でもある。実装は `.prose a .accent-emphasis { color: inherit }` の 1 本 — `inherit` なのでダークの counterpart が要らず、(0,2,1) で `@media` 内の `.accent-emphasis`（0,1,0）も上回る。**代金は、リンクの上では 強調 と 太字 が見分けられないこと。** リンクを強調する機会は稀で、リンクがリンクの色でないほうが失うものが大きい、という判断である（基準 5f・5g）。

**一般形**: 新しい規則が既存の色を奪えるのは、その既存の規則が `<a>` **自身**を狙っているときだけである。`app/globals.css` でそれに当たるのは脚注参照・戻りリンク（属性セレクタで勝つ）と `.footnote-popover-jump`（負けるが同値）の 2 つしかない。それ以外の色宣言は `<a>` を**含む**側（`.markdown-alert-title` など）か**含まれる**側（`.accent-emphasis`）で、前者は typography の `a` 規則が元から直接宣言で継承に勝っていたためこの変更の前後で何も変わらない（zinc-900 が青になるだけで、それは意図した変更そのものである）。

### 7.2 新しいタブで開くリンク（2026-08-21 決定・実装）

**決定**: 2 つの形に `target="_blank"` を付ける。**外部の規則** — サイトを離れるリンク（`href` が `http://` か `https://` で始まるもの）— と、**カードの規則** — リンクカードは行き先がサイト内でも別タブ — である。**本文の語に付いたサイト内リンク・目次・脚注参照と戻りリンクは同一タブのままである。**

この節は 2026-08-18 まで「全リンクが同一タブのまま（延期）」だった。移動の経緯は §6 の注（冒頭）にある。

**理由**: 記事が脚注と引用を持つ。同一タブで外部へ飛ぶと戻ったときにスクロール位置と文脈を失い、脚注ポップオーバーに払ったコストは同じ問題への回答なので、外部参照だけ扱いが違うのは一貫しない。**同一タブに留まる側の理由も残す**（覆した判断なので）: WCAG 3.2.5「新しいウィンドウは利用者が要求したときだけ」は AAA なので AA 適合の障害ではなく、読者は Ctrl+クリックで自分で選べる。**セキュリティは論点ではない** — 現代のブラウザは `target="_blank"` に `noopener` を暗黙適用する。

**カードの規則を外部の規則と別に立てる理由**（2026-08-21。外部の規則を入れた直後に決めた）: カードは**ブロックとして置いた「別の記事そのもの」**で、本文の語に付いたリンクとは別の道具である。外部カードだけが別タブだと、**同じ見た目の部品が行き先によって挙動を変える** — 外部カードは最下行にドメインが出るので見分けは付くが（`docs/link-card-requirements.md` §14.4）、それに気付いて挙動を予測しろというのは無理である。ここは「サイトを離れるか」より「カードか」で揃えるほうが読者の予測に合う。**逆に、本文中の内部リンクを別タブにする案は採らなかった**: 同一オリジンの通常遷移は戻るで復元でき、`target="_blank"` を読者の側から同一タブに戻す手段は無い（Ctrl+クリックの逆が無い）ので、非対称な分だけ付けない側が安全である。内部リンクを 3 つ踏むとタブが 4 枚になる、という素朴な代金もこちら側にある。

**機構**: `lib/rehype-new-tab-links.ts`。判定は**この 1 か所にしかない** — カードを作る `cardElement` は `target` を持たない（`docs/link-card-requirements.md` §14.8）。sanitize は `target` を落とすので、付けられるのはその後段だけである（§2.3-1）。

1. **外部の規則の判定は「`href` が `http://` か `https://` で始まるか」だけである。** 自サイトを指す書き方は相対パスか fragment なので集合として既に分かれており（§2.3 で実測）、`lib/site.ts` の `siteOrigin` と突き合わせる必要はない — あれは dev で `localhost:3001`、本番で別ホストと変わるため環境依存を持ち込むだけである（§10 で却下）。この判定なら公開 HTML が環境に依存しない。

   **例外が 1 つあり、直していない**: `[x](//example.com)` はスキームを持たないので sanitize は相対 URL として通し、この判定にも当たらないので同一タブで開く（2026-08-21 実測）。プロトコル相対 URL は「相対パスか fragment なら自サイト」という分割を破る唯一の形で、`lib/link-card-href.ts` も同じものを名指している（`//evil.example`）。**これは今までどおりの挙動で、退行ではない。** 判定を `new URL()` に替えれば拾えるが、そのぶん判定は「href の中身で細かく分ける」側へ寄り、項目 2 の安全性が前置詞 1 つに乗らなくなる。著者が手で打てば書ける（2026-08-27 実測: §5.5 の URL 欄と §5.4 の入力ルールが関門にしている `isPublishableUri` は `//example.com` を通す。`DIES_ON_PUBLISH` はスキーム付きの 6 つしか引かないためで、測ったのは述語までである — ブラウザでの往復は測っていない）。**それでも直さない** — 直前の 2 つ（退行ではないこと、判定を前方一致に保つこと）が動いていないうえ、この形を生成するコードは repo に無く、書かれるとすれば著者が意図して打った 1 本だからである。次に測り直す理由になるのは、それが実際に書かれたときである。

2. **事故ポイントは目次・脚注参照・戻りリンクを巻き込むことで、外部の規則を上の形に保てば自動的に避けられる。** 著者が `#user-content-…` を手書きした場合も同じで（§2.1.1 のとおり、公開ページから href をコピーすると起こる）、生成された ToC リンクと文字列上は見分けが付かないが、どちらも `http` で始まらない以上その判定の外にあり、カードでもない。基準 11b がこの 4 種類をまとめて測っている。
3. **`mailto:` と `xmpp:` — sanitize が通す残りのスキーム — も判定の外である。** 新しいタブを開いてもメールクライアントの横に空のタブが 1 枚残るだけで、これは「戻ったときに文脈を失う」問題を持たない（基準 11c）。
4. **カードの規則が見るのは `link-card` クラスであって、参照ではない。** したがって**解決に失敗して素のリンクに落ちたカードはこの規則の外**である（未知のスラッグ・下書き、`docs/link-card-requirements.md` §6.1 の扱い。この文書の §6 は欠番なので混同しないこと）。カードの見た目を失った以上、今そこにある素のリンクとして扱うのが筋で、内部なら同一タブ、外部なら外部の規則で別タブになる（基準 11e・11f）。

   **著者がこのクラスを名乗ることはできない**（2026-08-21 実測）。`link-card` を許しているのは `div` だけで（`lib/render.ts` の `divClasses`）、`a` で通る `className` の値は `data-footnote-backref` 1 つだけである（hast-util-sanitize の `defaultSchema`）。生 HTML で `<a class="link-card" href="/posts/foo">` と書くと `class=""` だけが残り、規則には当たらない。

5. **段はパイプラインの最後に置く。** カードの規則はカードを作る段が置いたノードを読み、外部の規則はカードと埋め込みのフォールバックが作る `<a>` に当たるので、両方より後ろでなければ届かない。各段が自分で決める形にはしない（`docs/link-card-requirements.md` §14.8）。
6. **sanitize のスキーマは広げていない**（§7 の 3 点目）。著者が生 HTML に書いた `target` は今までどおり除去され、外部リンクに残るのはこの段が付けた `_blank` である（基準 11d）。
7. **a11y の予告（WCAG G201）は入れていない。** CSS の `::after` アイコンでは済まない — 生成コンテンツはスクリーンリーダーに届かないので予告にならない。sr-only テキストを入れるならこの段が注入するしかなく（それより前だと sanitize の `span` クラス許可リストが `markdown-alert-title-label` と `accent-emphasis` しか通さないので消える）、入れるならここが場所である。3.2.5 が AAA であること、そして別タブで開くリンクすべてに読み上げが 1 つずつ増える代金を見て、今は入れていない。

**この段が届く先は 1 つだけである。** `renderMdxToHtml()` の呼び出し元は `app/posts/[slug]/page.tsx` しかない（2026-08-21 に grep で確認。エディタは TipTap で描いていて、このモジュールを通らない）。脚注ポップオーバーはその公開 DOM を複製するので、注の中の外部リンクも同じ属性を持つ — 一貫していてよい。エディタ本体のリンクは `openOnClick: false`（§3）の別経路なので、影響しない。

**`e2e/editor-link-markdown-syntax.spec.ts` は 2 種類のものを持っている。** 18 件のうち 14 件は §5.4 の受け入れ基準（下の 6 群 11 行。6a は 2 件、6k は 3 件で測る）で、残り 4 件は**測定の記録**である — エスケープ無しで読めばリンクになるという対照実験（§2.2.1）、`/posts/foo` / `#見出し` をペーストしてもリンクにならないこと（§2.1.1）の 2 件、そして手で打った `@[card](url)` が `@` + 普通のリンクになること（`docs/link-card-requirements.md` §4.1 (b)）。この 4 件は基準ではない。機能の不在を固定しているので、赤くなったら仕様が変わった合図であって、壊れた合図とは限らない。

5a・5b の色は `rgb()` で固定しているが、5c・5e の「変わっていない」は色の不一致でしか述べていない。 変わらない側の色は Tailwind v4 のパレット由来で、`getComputedStyle` から `lab(...)` として返る（実測: zinc-700 は `lab(26.8019 1.35387 -4.68303)`）。その文字列を書くのは値ではなく直列化形式を固定することになる。巻き添えとは「この青で塗られること」なので、「この青ではない」が測るべき主張そのものでもある。

**6k はこの表で唯一、「作った」のではなく「たまたま通っている」経路を固定している行である。** 貼った URL に autolink が先に触っていても入力ルールが上から書き直すという協調の上に成り立っていて、正規表現や `preventAutolink` を動かすと他を壊さずにここだけが壊れうる。壊れた姿が「エスケープされた括弧の中に autolink 済みの URL が残る」— リンクが 1 本できているので、目視では成功に近く見える形 — であることが、測る側に置いた理由である。

**9g・9h は「候補が出ないこと」を測る 2 行である。** 9 群で唯一、機能ではなく検証を測っている側で、出ない理由が 2 通りあって著者がすることも違うので、文言まで含めて固定した。**フラグメントが外れていることが著者に見える場所は、エディタにも公開ページにも他に無い。**

**1a は「新規タブが開かなかった」を待って確かめてはいない。** `window.open` を差し替えて呼び出し回数を数えている — 「まだタブが出てこない」と「出ない」は待つだけでは区別できず、間違った理由で通る形の代表例だからである。

**1b の測り方に注意。** キャレットを置くクリックは `state.selection` への反映が遅れる（この落とし穴はテーブルのセル選択で一度踏んでいる — 2026-07-29 の修正の教訓は「DOM のキャレットではなく state のキャレットをポーリングする」だった）。DOM の選択位置を読むと、①が効いていても失敗と判定されうる。

1b は「キャレットが置ける」までしか測っていない（置いたあとに何ができるかは 4 の側で測る）。②が入った今もこの分担のままでよい。

**4 の表に「`Mod-k` がブラウザに取られない」は無い。** 測れないからである（§5.5.4-4）。**測れないものを基準の表に入れると、通ったことが答えの代わりになってしまう。**

2026-08-11 に実機で答えは出た（奪えている、§9）が、行は足していない。 答えが出たことと spec で測れることは別で、表は後者だけを載せる場所だからである。「コピー」ボタンも同じ理由で表の外にある（§9）。**実機でしか分からないことは §9 に置く。**

## 9. 未実測のこと

**実機でしか答えの出ないことは、答えが出たあともここに残る**（§8 末尾）。開いた問いは 2026-08-27 にすべて下ろしたので、以下に並んでいるのは、打ち消した 4 項（答えは各項の参照先にある）と、spec に持ち込めない実機の確認結果、および測定範囲の但し書きである。

**論証を持っているのは決定した節のほうで、ここは原則としてその索引である**（§ を持たない項だけは、ここが唯一の記録である）。

- **ペーストがリンクの全域を置き換えたときにマークを継承させる** — 2026-08-17。実測: リンクのテキストを全選択してプレーンテキストを貼るとマークが落ち、一部でも残して貼れば残る。つまり「ペーストがリンクを尊重しない」のではなく、**マークの全域をスライスで置き換えると継承元が残らない**。却下の理由は 4 つある。①**損失は目に見える** — `.prose a` の色と Tailwind typography の下線が同時に消え、§7.1 が決めた青がそのまま feedback になっている（§2.4 / §2.5 の silent death は画面が 1 ピクセルも変わらない種類のもので、これはそれではない）。②リンクのテキストを全選択して貼る操作自体が稀である。③**Ctrl+Z 1 回で戻る**（実測）。④直すなら「マークの全域をスライスで置換したとき周囲のマークを継承する」という規則になり、**`link` だけの話にできない** — 太字の語を全選択してプレーンテキストを貼ったら太字で戻ってくる、が同時に決まる。`handlePaste` で `link` だけ特別扱いする形は、述語がテキスト近傍の走査に落ちる点で下の却下項と同じ手触りになる。`e2e/editor-link-text-edit.spec.ts` が挙動を固定しているが、**受け入れたからであって望ましいからではない**。

**このリストに `[]()` の入力ルールは無い。却下していないからである。** 単に検討から抜けていた選択肢で、2026-08-17 に §5.4 として実装した。

## 11. 決定 — 経路 (a) を単一段落の選択に狭める（2026-08-25 決定・実装）

**決定**: `linkOnPaste`（経路 (a)、§2.1）は選択範囲が単一段落に収まっているときだけ発動する。複数段落にまたがる選択への URL のペーストは、URL を含まないテキストのペーストと同じく、選択範囲を置き換えるだけになる。

**理由**: 投稿全体を Ctrl+A で選択し、クリップボードの URL を貼ってしまった事故が実際に起きた。`pasteHandler` は選択の広さを一切見ずに `setMark` を呼ぶだけなので、選択されていた全段落がそれぞれ独自にリンク化され——しかもテキストは置き換わらず、元の段落の文言がリンクの見出しとして残ったまま href だけ貼った URL になる。段落ごとに見出しと行き先が食い違うリンクが投稿全体に散らばり、次のオートセーブ（`useAutosave.ts`、800ms）が気づかれる前にそれを保存してしまうため、書き直す以外に戻す手立てがない。

単一段落の選択に絞るのは、②のバブル（`Mod-k`、§5.5）が任意の選択にリンクを付ける正式な入口として既に実装済みだからでもある。経路 (a) が担っていた「選択範囲の広さを問わずリンクにする」という役目は、今はもう (a) だけの専売ではない。単語ひとつを選んで URL を貼るとリンクになる利便性は実測でも壊れていないので残し、Mod-k を要求するのは広い選択のときだけにした。

**機構**: `components/editor/link-paste-paragraph-guard.ts` の `LinkPasteParagraphGuard`。`handlePaste` で、選択が非空・貼り付け内容が URL 単体（`@tiptap/extension-link` が公開している `pasteRegex` で判定——`pasteHandler` 自身の `item.value === textContent` と同じ関門を、依存に無い `linkifyjs` を直接 import せずに近似したもの）・`doc.textBetween(from, to, '\n')` に `\n` が含まれる（=選択が段落境界をまたぐ）の 3 条件が揃ったときだけ、`isolating-boundary.ts` の `replaceSelectionClamped` で選択を貼り付け内容に置換し、`pasteHandler` に渡さない。

**測って分かった落とし穴**: 最初の実装は `extensions.ts` の配列内で `Link.configure` より下に置けば済むと考えていた——配列は逆順に問い合わせられる（同ファイルの冒頭コメント）ので、後ろに置けば先に訊かれるはずだった。実測（`e2e/editor-link-paste-paragraph-guard.spec.ts`）では効かず、複数段落の選択でも従来どおり全段落がリンク化された。原因は `@tiptap/extension-link` の `Mark.create` が `priority: 1000`（`dist/index.js` の `priority: 1e3`）を宣言していたことで、`sortExtensions`（`@tiptap/core`）は配列順より先に priority で並べ替える。既定の 100 は 1000 に勝てないため、配列の位置は無意味だった。`LinkPasteParagraphGuard` に `priority: 1001` を明示して解決している——この経緯は `link-paste-paragraph-guard.ts` 側にも残してある。

**副作用として `autolink`（§4）が追い打ちする。** 置換後の段落が URL 単体になった場合、`autolink` はそれをタイプされた URL と区別できずリンクにする。ラベルと href が一致する形なので、この文書が問題にしてきた「見出しと行き先が食い違うリンク」ではなく、**受け入れている**（2026-08-25 に協議のうえ決定。止めるにはペースト直後の 1 トランザクションに限定して `autolink` を抑える別のガードが要る）。

**受け入れ基準**: §8 の基準 13。

## 12. autolink のリンクは打鍵と同じ undo イベントに入る（2026-08-27 実測）

**Ctrl+Z はリンクのマークだけを剥がせない。** 打った文字列・貼った文字列ごと、直前の区切りまでが戻る。§9 が 2026-08-09 から未測定で持っていた問いの答えであり、きっかけは著者の報告（2026-08-27、「ペーストは全部消える。手書きは autosave が掛かったところまで戻る」）である。

**機構**: autolink はコマンドではない。`appendTransaction`（`key: new PluginKey("autolink")`）の中で `tr.addMark` を呼び、返すのは素の `tr` である — `addToHistory: false` も履歴を閉じる meta も立てていない。したがってマークは打鍵と**同じ dispatch** に乗り、prosemirror-history はそれを打鍵と同じイベントに畳む。「別のトランザクションだから別の undo イベント」にはならない。

**autosave は原因ではない。** 区切りを入れているのは prosemirror-history の `newGroupDelay`（`newGroupDelay: config.newGroupDelay || 500`）で、autosave の debounce は 800ms（`components/editor/useAutosave.ts` の `AUTOSAVE_DELAY_MS`）である。800ms 止まった時点で 500ms はとうに過ぎているので、autosave が走ったところには区切りが必ず既にある — **autosave は原因ではなく、区切りが入ったことの目に見える印である。** そのうえ `useAutosave.ts` はエディタに一切触らない（`editor.` も `dispatch` も `commands` も無く、本文を読んで POST するだけである）。触らないものが履歴に区切りを入れることはできない。

基準 14b はこれを時間の帯ではなく構造で測る。`/api/drafts` を abort したうえで休止を挟み、autosave が要求を出して断られた（試行回数を数えている）状態でも区切りが現れることを見る。ブロックしてあるので休止に上限が要らず、500〜800ms を狙う 300ms 幅の帯を踏まずに済む — §5.5.10 が 200ms の余裕で払った授業料と同じ形を避けている。**休止は 1500ms である**（`newGroupDelay` の 500 と autosave の debounce の 800 を両方越える必要があり、上限が無いのだから余裕は取れるだけ取る）。1000ms で書いた最初の版は 2026-08-27 に 1 度落ち、6 回の繰り返しでは再現せず、そのときにはトレースが消えていた — **広げたのは診断ではなく、この case が持つ唯一の時間依存を外したという主張である。**

**ペーストは別のプラグインだが、著者から見た結果は同じである。** 貼った URL をリンクにするのは `markPasteRule`（経路 (c)、§2.1）であって autolink ではない。履歴への入り方は変わらず、Ctrl+Z 1 回で貼った文字列ごと戻る（基準 14c）。

**リンクだけを外す手段はバブルの「解除」である**（§5.2、§5.5）。§5.2 が「外せないリンクが残っていた」制約を 2026-08-11 に解消したと書いているのはその経路のことで、Ctrl+Z はその代わりにならない。

**受け入れている。** autolink の `tr` を独立したイベントにすれば剥がせるようになるが、それは URL を打ち終えるたびに undo の粒度が 1 つ増えるということでもある。リンクを消したい稀な場合のために、打ち直しの undo を常に細かくする取引になり、解除の導線は既にある。**この代案は測っていない。**

**受け入れ基準**: §8 の基準 14。
