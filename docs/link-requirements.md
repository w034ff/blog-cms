## 1. 目的と非目標

**目的**: 著者が任意のテキストにリンクを付け・URL を直し・リンクを外せるようにする。読者はそれを公開ページで辿れる。

**非目標**（この文書では対象外）:

- 記事間リンクの補完・記事タイトルの自動取得（内部リンクは相対パスを手書きする — **ただしその「手書き」が現状どの経路でも成立しないことが 2026-08-11 に判明した。§2.1.1**）
- リンクカード／URL の展開表示（Zenn の `@[card]` に相当するもの）
- リンク切れ検査
- `title` 属性を著者が編集する UI（§5.3 で「壊さない」ことだけ要求する）

## 2. 現状（2026-08-09）

### 2.1 リンクが付く経路は 4 つ、任意のテキストに付くのは 1 つだけ

`link` マークは StarterKit 経由で登録されている（`@tiptap/starter-kit/dist/index.js:70` が `Link.configure(options.link)` を push、`PostEditor.tsx:219-234` の `configure` は `link: false` を渡していない）。**他の多くのノード／マークは明示的に無効化して自前版に差し替えてあるのに、link だけは方針が書かれないまま既定値で残っている** — この文書はその穴を埋めるものでもある。

**経路には (a)〜(d) の記号を使う。** §3 以降の①②は「決定した項目」の番号であり、別物である。

| 経路                           | 機構                              | 任意のテキストに付くか       |
| ------------------------------ | --------------------------------- | ---------------------------- |
| (a) 選択範囲に URL をペースト  | `pasteHandler`                    | **○ 唯一の直接手段**         |
| (b) URL をタイプ               | `autolink`                        | × リンク文字列 = URL         |
| (c) URL を含む文章をペースト   | `addPasteRules` / `markPasteRule` | × URL 部分だけがリンク化     |
| (d) `<a>` 入り HTML をペースト | `parseHTML: 'a[href]'`            | × 選択範囲を置換して差し込む |

(a) は見た目より狭い。`pasteHandler` は選択が空でないことに加えて **`item.value === textContent`** を要求する（`extension-link/dist/index.js:195`）。ペースト内容が URL ちょうど 1 個でないと発動せず、末尾に空白が付いていたり `参考: https://…` の形だと、リンクにならず選択範囲がそのテキストで置換されるだけである。

(c) は (a) と別のプラグインで、**選択が空でも発動する**。ただし生成されるのは常にリンク文字列 = URL のリンクである。

### 2.1.1 内部リンクを作る経路が無い（実測 2026-08-11）

**(a)(b)(c) は 3 つとも linkifyjs の判定を通る。** そして linkifyjs は URL とメールアドレスしか見つけないので、このブログが実際に書きたい 2 種類はどれも通らない:

| 文字列                | `linkifyjs.find()` | 選択範囲にペーストした結果（E2E）      |
| --------------------- | ------------------ | -------------------------------------- |
| `/posts/foo`          | `[]`               | 選択が置換されるだけ。リンクにならない |
| `#見出し`             | `[]`               | 同上                                   |
| `https://example.com` | url として検出     | `link("ここ")`（経路 (a)）             |

`[](  )` と手で打つ道は §2.2.1 で塞がっている。したがって**残るのは経路 (d)（`<a>` 入りの HTML をクリップボードに持っている場合）だけ**だが、これも fragment には使えない:

著者が自分の公開ページから見出しリンクをコピーすると href は `#user-content-見出し` である。それを貼って公開すると `rehypeClobberFragmentLinks` が `#` の後ろに無条件で接頭辞を足すので**二重に付く**（実測 2026-08-11、§2.3 の表の最終行）。著者が `user-content-` を手で剥がすことを知っている必要がある。

**帰結: この編集器で自サイトの見出しへのリンクを作る正しい方法はひとつも無い。** §1 が非目標の側で前提にしている書き方（相対パスを手書き）が、そもそも成立していない。§5.4 はこれに対する候補である。

**この穴は 2026-08-11 に §5.5 のバブルで塞いだ。** URL 入力欄に `#見出し` / `/posts/foo` を直接打てる（`setLink` の `isAllowedUri` はスキームの無い相対パスと fragment を通すので、狭めた述語の側でも落ちない — 実測）。**ただし上の「公開ページから `#user-content-…` をコピーすると接頭辞が二重に付く」は変わっていない。** 入力欄は著者が打った文字列をそのまま href にするだけで、`user-content-` を剥がしはしない。

**UI は存在しない。** `setLink` / `toggleLink` / `unsetLink` コマンドは実装されているが、呼ぶ導線がツールバー（`components/editor/Toolbar.tsx`）にもスラッシュメニュー（`slash-command.ts`）にも無い。`extension-link` に `addKeyboardShortcuts` が無いので **Mod-k も無反応**である。

既定値（`@tiptap/extension-link` 3.28.0、`dist/index.js:266-277`）:

| オプション             | 既定値                                               |
| ---------------------- | ---------------------------------------------------- |
| `autolink`             | `true`                                               |
| `linkOnPaste`          | `true`                                               |
| `openOnClick`          | `true`                                               |
| `enableClickSelection` | `false`                                              |
| `HTMLAttributes`       | `target="_blank" rel="noopener noreferrer nofollow"` |
| `isAllowedUri`         | プロトコル検査あり                                   |

`HTMLAttributes` の `target` / `rel` は**エディタの DOM 上にしか出ない**。公開 HTML には出ない（§2.3）。

### 2.2 保存形式 — markdown の往復

保存側は `tiptap-markdown` が `defaultMarkdownSerializer.marks.link` を使う（`tiptap-markdown.es.js:701`）ので `[text](href "title")` になる。`title` も直列化される。**ただしリンクの文字列が href とちょうど同じときは `<https://example.com>`（山括弧の autolink 形式）になる** — 2026-08-09 実測。経路 (b)(c) が作るリンクは常にこの形である。公開側は remark-gfm がどちらも同じくリンクにするので、見た目に差は出ない。`target` / `rel` は markdown に書けないので落ちる — **これは損失ではなく、そもそも公開されない属性である**（§2.3）。

読み込み側は markdown-it が解釈する。`Markdown.configure({ linkify: false })`（`PostEditor.tsx:266`）は**裸 URL の自動リンクだけを切るもので、`[]()` 記法には効かない** — markdown-it に `linkify:false` を渡しても `[任意のテキスト](https://example.com)` は `<a href>` になることを実測済み。

**帰結**: エディタで `[text](url)` と手で打っても、`transformPastedText` / `transformCopiedText` が既定 `false`（`tiptap-markdown.es.js:923`）なのでその場ではリテラルのまま残る。**保存して再読込すればリンクになる、という 2 段階の迂回路を当初この節は想定していたが、2026-08-11 の実測でそれは存在しないと分かった**（§2.2.1）。

### 2.2.1 打った `[]()` はリンクにならない — 保存の時点で潰れる（実測 2026-08-11）

`e2e/editor-link-markdown-syntax.spec.ts`（7 件）で測った:

| 操作                                             | `doc`                            | `getMarkdown()`                        |
| ------------------------------------------------ | -------------------------------- | -------------------------------------- |
| `[断片](#見出し)` とタイプ                       | `paragraph("[断片](#見出し)")`   | `\[断片\](#見出し)`                    |
| ↑ を保存 → 再読込                                | `paragraph("[断片](#見出し)")`   | 同じ（安定）                           |
| `[断片](#見出し)` を**エスケープ無しで**読み込み | `paragraph(link("断片"))`        | `[断片](#%E8%A6%8B%E5%87%BA%E3%81%97)` |
| `[ここ](https://example.com)` とタイプ           | `paragraph("[ここ](https://…)")` | `\[ここ\](https://…)`                  |

**機構**: text ノードの直列化は `state.text(escapeHTML(node.text))`（`tiptap-markdown.es.js:628`、第 2 引数省略なので escape は `true`）で、`prosemirror-markdown` の `esc()` は `[` と `]` を**無条件に**エスケープする（`dist/index.js:821`。`startOfLine` 条件付きの側ではない）。したがって保存されるのは `\[断片\](#見出し)` であり、markdown-it が `[]()` として読む機会は永久に来ない。

**壊れているのはパーサではなく直列化側である。** 3 行目の対照実験がそれを示している — 同じ文字列をエスケープ無しで読ませればちゃんと `link` になる（§2.2 の markdown-it 実測どおり）。脚注が専用の node serializer を持ってこのエスケープを迂回しているのも同じ理由で、`e2e/editor-footnote.spec.ts:58` の `not.toContain('\\[')` がそれを固定している。

4 行目の補足: 括弧の中の URL すら autolink されない。`autolink` は URL の後ろに語境界を要求し、直後に打たれた `)` はそれではない。

**本文の CRLF 化（`form-submission-crlf-body.md`）はこの結論に影響しない** — ブラケットのエスケープは改行コードと無関係なので、`setContent` による保存 → 再読込の再現は忠実である。

### 2.2.2 fragment を含むリンクは往復で percent-encode される（実測 2026-08-11）

上の表の 3 行目。`[断片](#見出し)` を**読み込む**と markdown-it が href を正規化し、書き戻しは `[断片](#%E8%A6%8B%E5%87%BA%E3%81%97)` になる。

**公開結果は変わらない** — 両形式とも `#user-content-%E8%A6%8B%E5%87%BA%E3%81%97` に落ちることを `renderMdxToHtml()` で実測した（§2.3 の表）。

**ただし保存形式は open/close について冪等ではない。** 既存記事を開いて何も触らずオートセーブが走るだけで、保存本文が読める形から encode された形に書き換わる。実リンク 0 件（§0）なので現状これを踏む記事は無いが、②を作るときの前提として効く（差分が本文の変更に見える）。

### 2.3 公開側の実測

`renderMdxToHtml()`（`lib/render.ts`）に流した結果（2026-08-09）:

| 入力                                                          | 出力                                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `[**打率.077**](https://wikiwiki.jp/x "グロ")`                | `<a href="https://wikiwiki.jp/x" title="グロ"><strong>…</strong></a>`                                              |
| 裸の `https://example.com/a`                                  | `<a href="https://example.com/a">…</a>`（remark-gfm の autolink literals）                                         |
| 裸の `www.example.com/b`                                      | `<a href="http://www.example.com/b">…</a>`                                                                         |
| `[内部](/posts/foo)`                                          | `<a href="/posts/foo">` — 相対のまま                                                                               |
| `[断片](#見出し)`                                             | `<a href="#user-content-%E8%A6%8B%E5%87%BA%E3%81%97">`                                                             |
| `[断片](#%E8%A6%8B%E5%87%BA%E3%81%97)`                        | 同上 — 二重 encode はされない（2026-08-11、§2.2.2）                                                                |
| `[断片](#user-content-見出し)`                                | `<a href="#user-content-user-content-%E8%A6%8B…">` — **接頭辞が二重に付き、id に当たらない**（2026-08-11、§2.1.1） |
| 生 HTML `<a href="…" target="_blank" rel="opener" title="t">` | `<a href="…" title="t">` — **`target` と `rel` は除去、`title` は残る**                                            |
| `[js](javascript:alert(1))`                                   | `<a>js</a>` — **`href` ごと除去**                                                                                  |

読み取れること:

1. **公開リンクは `href` と `title` しか持たない。** sanitize のスキーマ（GitHub の `defaultSchema`）が `a` に許すのは aria 系・脚注用の data 属性・`href` だけで、`title` はタグ非依存の `*` 許可リストに入っているため通る。したがって**公開ページのリンクは同一タブ遷移で、`rel` は付かない**。
2. **`target="_blank"` が付かない以上、`rel="noopener"` の欠落は攻撃面ではない。** 逆タブナビングの前提が存在しない。
3. **`javascript:` は二重に止まる。** エディタ側は `isAllowedUri`、公開側は sanitize のプロトコル許可リスト。後者は属性ごと落とすので、公開後は**リンクですらなくなる**。
4. **ただし 2 つの許可リストは一致していない**（§2.4）。
5. **裸 URL の扱いがエディタと公開で食い違う。** エディタは `linkify: false`、公開は remark-gfm がリンク化する。§4 はこの差を埋める側の判断である。

### 2.4 プロトコル許可リストのずれ（修正済み 2026-08-09、§2.4.2）

2 つの層は同じ集合を守っていない。

| 層       | 許可するプロトコル                                                             | 出典                                   |
| -------- | ------------------------------------------------------------------------------ | -------------------------------------- |
| エディタ | `http` `https` **`ftp` `ftps`** `mailto` **`tel` `callto` `sms` `cid`** `xmpp` | `extension-link/dist/index.js:211-222` |
| 公開     | `http` `https` **`irc` `ircs`** `mailto` `xmpp`                                | `hast-util-sanitize/lib/schema.js:143` |

**エディタだけが通す 6 つ（`ftp` / `ftps` / `tel` / `callto` / `sms` / `cid`）は、公開時に `href` ごと消えて中身のないリンクになる。** 2026-08-09 実測:

| 入力                         | 公開後               |
| ---------------------------- | -------------------- |
| `[電話](tel:+81312345678)`   | `<a>電話</a>`        |
| `[ftp](ftp://example.com/x)` | `<a>ftp</a>`         |
| `[irc](irc://example.com/x)` | `<a href="irc://…">` |

**これは `PostEditor.tsx:210-212` が underline について書いている「WYSIWYG のウソ」と同じ形である** — エディタでは正しいリンクに見え、公開すると黙って死ぬ。

エディタ側も 2026-08-09 に E2E で実測し、往復が成立してしまうことを確認した:

| 経路 (d) でペーストした HTML            | エディタの結果         | 保存される markdown          |
| --------------------------------------- | ---------------------- | ---------------------------- |
| `<a href="tel:+81312345678">電話</a>`   | `link("電話")`         | `[電話](tel:+81312345678)`   |
| `<a href="ftp://example.com/x">FTP</a>` | `link("FTP")`          | `[FTP](ftp://example.com/x)` |
| `<a href="javascript:alert(1)">JS</a>`  | リンクにならず素の文字 | `JS`                         |

つまり `tel:` / `ftp:` は**エディタが受け入れ、markdown にも保存され、公開時にだけ href を失う**。`javascript:` はエディタが入口で止めるので、二重防御が効いているのはこちらだけである（§2.3-3）。

### 2.4.1 2 つのリストの出所（判断の前提）

**どちらが「正しい」というものではない。別の系譜のリストが両端に置かれているだけである。**

- **公開側は GitHub の方針**である。`hast-util-sanitize/lib/schema.js` の `defaultSchema` には `Follows GitHub style sanitation.` と書いてある。`irc` / `ircs` が入っていることがこのリストの年代を示している。GitHub の脅威モデルは「見ず知らずの他人が書いた markdown を大量の閲覧者に描く」であり、`tel:` に電話をかけさせる・`sms:` に本文を仕込ませるのは、その規模では濫用経路になる。**コード実行の穴ではなく、プラットフォーム上の濫用対策としての判断である。**
- **エディタ側は汎用 HTML サニタイザ系統の顔ぶれ**で、`tel` / `sms` / `callto` / `cid` を含む。

**`tel:` は RFC 3966 の正規のスキームであり、単著のブログで危険な要素は何もない。** したがって塞ぐ理由は「危険だから」ではなく「**このブログでは使わないから**」である。将来 `tel:` リンクを書きたくなったら、この判断はセキュリティ判断ではないので、素直に公開側（sanitize のスキーマ）を広げてよい。

### 2.4.2 修正（2026-08-09）

**採った案: エディタを狭める。** 公開側のスキーマには触れていない。

`components/editor/link-protocols.ts` の `isPublishableUri` を Link の `isAllowedUri` に渡す（`PostEditor.tsx`）。

- **`protocols` オプションでは狭められない。** あの配列は固定リストに `push` するだけで、広げる方向にしか効かない（`dist/index.js:223-229`）。狭める口は `isAllowedUri` の差し替えだけである。
- **既定の判定を捨てず、前に置いて 6 つを引く**（`ctx.defaultValidate(url) && !DIES_ON_PUBLISH.test(…)`）。スキームを持たない相対パス（`/posts/…`）と fragment（`#見出し`）は既定側が通すので、**著者が自サイトを指す書き方は一切変わらない**。
- **判定前に Unicode 空白を除去する。** 拡張自身が判定前に同じ除去をしているので、こちらが生の文字列を見ると `" tel:+81…"` がこの述語をすり抜け、背後の既定判定に受理される。`\s` では代用できない（C0 制御文字を含まない）ので、文字クラスを upstream からそのまま持ってきている。
- 逆向きのずれ（公開だけが通す `irc` / `ircs`）は無害なので触っていない。エディタがそもそも作らせない。

**`isAllowedUri` だけでは経路 (a) が塞がらない。** リンク拡張の 4 つの関門のうち、`linkOnPaste` のプラグインだけは `setLink` ではなく**生の `setMark` を呼ぶ**ので `isAllowedUri` を一切参照しない（`dist/index.js:199-201`）。選択範囲に URL をプレーンテキストで貼る経路がここに当たる。

到達するのは `ftp` / `ftps` だけである（実測 2026-08-09）— linkifyjs は `tel:` / `sms:` をリンクと認識せず、`cid:a@example.com` はメールアドレス `a@example.com` として読むため `item.value === textContent` を満たさない。

**答えは `PostEditor.tsx` の `editorProps.handlePaste` に置いた。** `priority: 1000` の拡張より前に出る唯一の方法がこれである — prosemirror-view の `someProp` は `_props` を directPlugins・state.plugins より先に読む（`prosemirror-view/dist/index.js:5638-5652`）。条件はそのプラグインが主張する場合だけに絞ってある（選択が空でない、かつ 1 行）。それ以外は既に関門のある経路へ行く。

`shouldAutoLink` を差し替える手もあるが、既定の実装（裸の IP・ドットの無いホスト名を弾く 15 行）を写して同期し続けることになるので採らなかった。

**著者から見た変化**: `tel:` リンクを含む HTML を貼ると、リンクにならずアンカーのテキストだけが入る。**黙って死ぬ代わりに、入口で入らない。**

保存済みの投稿は書き換えていない（該当ゼロ、§0）。仮に `[電話](tel:…)` を含む markdown を読み込んだ場合は、`parseHTML` の `getAttrs` が同じ関門を通るのでリンクにならず、注釈のテキストとして残る。

E2E: `e2e/editor-link-protocols.spec.ts`（`tel` / `ftp` / `sms` / `cid` の拒否、空白による回避の封じ、`https` / `mailto` / 相対 / fragment が無傷であることの確認）。

### 2.5 VS Code からのペーストがコードブロックになっていた（修正済み 2026-08-09、§2.5.2）

**これはリンク機能の不具合ではない。** あらゆるペーストに効くもので、リンクはたまたまこれを踏んだ入口である。

**現象**: VS Code（および Cursor / VSCodium など Monaco 系）でコピーしたテキストをエディタに貼ると、コードブロックになる。URL 1 個でもそうなる。2026-08-09 に E2E で再現測定した（§2.5.1）。

**機構**: `@tiptap/extension-code-block` に組み込みの `codeBlockVSCodeHandler`（`dist/index.js:284-309`）。

```js
const text = event.clipboardData.getData('text/plain');
const vscode = event.clipboardData.getData('vscode-editor-data');
const language = vscode ? JSON.parse(vscode).mode : undefined;
if (!text || !language) return false;
// → 内容を見ずに codeBlock を作り replaceSelectionWith
```

判定は **`vscode-editor-data` というクリップボード形式の有無だけ**で、貼り付ける中身は一切見ていない。VS Code はコピー時にこの形式を必ず付ける。ブラウザのアドレスバーや Web ページからのコピーには付かないので、**同じ URL でもコピー元によって結果が変わる**。

コードブロックの `language` はコピー元ファイルの言語（`mode`）になる。この文書からコピーした URL なら `markdown` になる。

**このプラグインは自前の code block にも生きている。** `CodeBlockWithLanguage` は `addProseMirrorPlugins` で `...(this.parent?.() ?? [])` として親のプラグインを引き継いでいる（`code-block-extension.ts:523`）。

### 2.5.1 実測（2026-08-09、E2E で `vscode-editor-data` 付きのペーストを合成）

| 選択     | text/plain         | VS Code 形式 | 結果                                             |
| -------- | ------------------ | ------------ | ------------------------------------------------ |
| なし     | URL 1 個           | あり         | `codeBlock`（`language: "markdown"`）            |
| あり     | URL 1 個           | あり         | **`link("ここ")`** — リンクになる                |
| あり     | URL 1 個           | なし         | `link("ここ")` — 経路 (a) の基準線               |
| あり     | `const x = 1;`     | あり         | `codeBlock` — **選択していた「ここ」は消える**   |
| あり     | URL + 末尾スペース | あり         | `codeBlock` — 同上                               |
| あり     | URL + 末尾スペース | なし         | 選択が置換され、URL 部分だけリンク化（経路 (c)） |
| コード内 | URL 1 個           | あり         | そのまま挿入（`isActive` で早期 return）         |

**経路 (a) は壊れていない。** リンクの `handlePaste` が先に訊かれるため、選択があって貼り付け内容が URL ちょうど 1 個なら、コピー元が VS Code でもリンクになる。

**順序の理由**（実測: `handlePasteLink` が index 5、`codeBlockVSCodeHandler` が index 33）: ExtensionManager は `sortExtensions([...this.extensions].reverse())` の順にプラグインを集める（`@tiptap/core/dist/index.js:4547`）。**反転が先、優先度のソートが後**なので、配列上の位置ではなく優先度が効く。`Link` は `priority: 1000`（`extension-link/dist/index.js:240`）で既定の 100 を持つ全員より前に出る。

> **注意**: 「配列の後ろにあるものが先に訊かれる」という規則（`PostEditor.tsx:256-260` が IsolatingBoundary の位置について述べているもの）は**優先度が同じ者どうしの間でしか成り立たない**。優先度を明示している拡張はその規則の外にある。

**実害はここにある**: リンクの `handlePaste` が断る形（選択が空、または貼り付け内容が URL ちょうど 1 個でない）だと VS Code ハンドラが取り、`replaceSelectionWith` なので**選択していたテキストが消えてコードブロックに置き換わる**。VS Code から 1 単語コピーして選択範囲に貼る、という日常操作がこれに当たる。

### 2.5.2 修正（2026-08-09）

**採った案: 改行を含むペーストのときだけ発動させる。** `components/editor/code-block-extension.ts` が base CodeBlock のハンドラをプラグインリストから取り除き、同じ動作に「本文が 2 行以上にまたがること」という条件を足したものに差し替える。

- **プラグインごと落とさず、キーで 1 つだけ除外している。** `this.parent?.()` を丸ごと捨てると base 拡張の他の貢献も失う。
- **末尾の改行は数えない。** VS Code の Ctrl+C は選択が無いとキャレット行を改行込みでコピーするので、素朴に `includes('\n')` で判定すると「1 行コピー」という最も多い操作がそのままコードブロックに戻ってしまう。
- **`JSON.parse` を全域化した。** upstream は無防備で、壊れた flavour が DOM イベントハンドラの中で例外になる。
- **除外はキー名の前方一致なので、upstream がリネームすると黙って元の挙動に戻る。** 見つからなければ `console.warn` を出し、`e2e/editor-vscode-paste.spec.ts` の単一行ケースが常設の検知役になる。

**残るコスト**: VS Code からコピーした**1 行のコードスニペットはコードブロックにならない**。```フェンスと`/` メニューがその場合の入口である。

## 3. 決定① — `openOnClick` を `false` にする（実装済み 2026-08-09）

**決定**: `StarterKit.configure({ link: { openOnClick: false } })` とする。

**理由**: 既定ではエディタ内でリンクをクリックすると `window.open` が走り（`dist/index.js:165`）、**キャレットが置けない**。UI が無いこと（§2.1）と合わせて「一度付いたリンクに手が出せない」状態を作っている。②の UI（§5）はキャレットがリンク内に入れることを前提にするので、これは②の前提条件でもある。

**機構**: `enableClickSelection` の既定が `false` なので、`openOnClick` も `false` にすると `handleClick` は何もせず `false` を返し、ProseMirror の通常のキャレット配置に落ちる。追加の手当ては要らない。

**これは純粋な改善ではない。** 引き換えに**エディタからリンク先を開く手段が無くなる**。代替はブラウザ自身のホバー時ステータスバー表示（リンク先の確認）と、テキストを選んでコピーすることである。②が入るまでの間、エディタでリンク先を開きたければ公開ページ／プレビュー側で開くことになる。この取引を承知のうえで決めている。

**この取引は 2026-08-11 に解消した。** §5.5 のバブルが href を文字で見せ、「開く」ボタンを戻した（§5.5.1-1）。①は今や一方的な改善である。

`'whenNotEditable'` という第 3 の値もあるが、このエディタは常に編集可能なので `false` と等価であり、選ぶ理由がない。

## 4. 決定 — `autolink` は残す

**決定**: `autolink: true` のまま変えない。

**理由**: §2.3 の実測どおり、公開側は remark-gfm の autolink literals で裸 URL をリンクにする。エディタ側の `autolink` を切ると、**エディタでは素のテキスト、公開ではリンク**という WYSIWYG のズレが生まれる。`autolink` を残せばタイプした URL は `<url>` として保存され（§2.2）、公開側の結果と一致する。**`autolink` はズレを作る側ではなく塞ぐ側である。**

## 5. ② — 付与・編集・解除 UI（2026-08-11 実装、§5.5 の形）

### 5.1 なぜ延期していたか、そして何が延期を追い越したか

**実投稿でのリンク使用がゼロだから**（§0）。作るとしたら付与・編集・解除の 3 つで一組であり（§5.2）、ダイアログ 1 つでは済まない。3 投稿・実リンク 0 件の段階で払うコストとしては大きい。

**追記 2026-08-11: このコスト見積もりは「ダイアログを複数」という実装形態を前提にしていた。** §5.5（Google Docs 型のバブル）なら 3 つが 1 コンポーネントに収まり、土台も既に repo にある。**延期の根拠のうち「使用がゼロ」は動かないが、「コストが大きい」のほうは弱まっている。**

**実装に踏み切った理由は、上の 2 つのどちらでもない。** 「使用がゼロ」は今も真である。延期を追い越したのは **§2.1.1（この節より後の 2026-08-11 に実測）**である — **内部リンクを作る経路がひとつも無い**のに、§1 は著者がそれを手書きする前提で非目標を切っていた。これは投稿数と無関係に成り立つ機能の穴で、§0 の「まだ作らない」判断が答えるべき種類のものではない。§5.5.3 のとおりバブルはそれ単独でこの穴を塞ぐ。

**したがって「使用がゼロなら作らない」という §0 の判断基準は撤回されていない。** 撤回されたのは「②が要るのは使い勝手のためだけだ」という前提のほうである。

### 5.2 延期の帰結（解消済み）— 外せないリンクが残っていた

`autolink` を残す（§4）ので、著者が URL をタイプすると**その場でリンクになり、テキストごと消す以外に外す手段が無い**。これは②が入るまで解消しない（**あるいは §5.4 の「①.5」まで** — あれは解除の口を 1 つだけ先に出す案なので、この制約を先に消しうる。②を §5.5 の形で作るなら、その解除の口はバブルそのものである）。

**この制約は新しく作られるものではなく、現状そうなっている。** ①（§3）はこれを悪化させない — キャレットが置けるようになる分だけ改善する。したがって「①だけ入れる」は安全に成立する。

②を作るときは、これが解消すべき筆頭の問題である。`toggleLink` / `unsetLink` は `extendEmptyMarkRange: true` 付きなので（`dist/index.js:387,390`）、**リンク内にキャレットを置くだけでリンク全体に効く** — ①でキャレットが置けるようになっていれば、選択操作を要求しない UI が組める。

**2026-08-11 に解消。** バブルの「解除」がこれである。`extendMarkRange('link').unsetLink()` は**リンクの右端にキャレットがあるときも**リンク全体を外すことを実測した（`editor-link-bubble.spec.ts`）— そこは `getMarkRange` が解決できない位置なので、確かめずに済ませてよい種類のものではなかった。

### 5.3 作るときの制約（先に記録しておく）

**この節は「ダイアログを出す」形を暗黙に前提している。** §5.5 のバブルを採る場合、1 と 2 は**編集モード（URL 入力欄を出しているとき）にだけ**当てはまる — §5.5.4-1。

1. **ダイアログはネストした `<form>` にしてはならない。** PostEditor 全体が単一の `<form>` であり、ネストした form はブラウザに捨てられて submit が無言で何もしない。前例は `components/editor/TableGridMenu.tsx:77-79` — `<dialog>` の中は素の `<div>` で、ボタンの `onClick` と Enter キーで submit 関数を呼んでいる。同じ形にする。
2. **オートセーブ中に開いたままのダイアログに注意。** そのフォーム内の `<input>` は server action 保存時に React 19 のフォーム自動リセットの影響を受けうる（コードブロックのファイル名入力が実際に踏み、`form` 属性に存在しない id を指す回避策で対処済み）。リンクダイアログは開いている時間が短いが、URL を貼って考え込む操作は起こりうるので、実機で確認すること。
3. **既存リンクの URL を編集するとき、`title` を消してはならない。** §0 の唯一の実リンクは `title` を持ち、それは公開まで生き残る（§2.3）。`title` の既定値は `null` なので、`setLink({ href })` が既存マークの属性をマージしないなら**URL を直すと `title` が黙って消える**。TipTap の `setMark` の挙動を確かめること。**投稿 id 36 がそのままフィクスチャになる。**
   → **実測 2026-08-11: マージされる。** `setLink({ href })` は既存マークの属性の上に書くので `title` は残り、`[リンク](https://changed.example "タイトル")` として保存された。**手当ては要らなかったが、要らないことが分かったのは測ったからである** — 基準 4c として固定してある（§8）。
4. Mod-k を割り当てるならローカル `.extend()` が要る（`extension-link` にキーマップが無い）。ただし Ctrl+K は Chrome のアドレスバーのショートカットなので、tsc が通っても意味がなく**ブラウザでの実機確認が必須**である。
   → 実装では `.extend()` ではなく、`editor.view.dom` への capture 段階の keydown リスナ（`LinkBubble.tsx`）にした。機能が 1 ファイルに収まるほうを採っている。**エディタ側に Mod-k の先客が無いことは実測済み**（押しても doc もキャレットも動かない）。**ブラウザが譲ることも 2026-08-11 に実機で確認した**（§9）。
5. **ダイアログの `<input>` への URL 貼り付けは §2.5 の影響を受けない**（ProseMirror ではなく素の DOM 入力なので）。②が入れば、VS Code からコピーした URL を安全に付けられる経路が初めてできる。**ただし §2.5 が直るわけではない** — ②を §2.5 の修正の代わりにしてはならない。

### 5.4 未決の候補「①.5」 — `[]()` の入力ルール（2026-08-11 追加）

**まだ決めていない。** ②より遥かに小さく、②の代わりにもならない中間案として、材料だけ置く。

**§5.5 を先に読むこと。** バブル案を採るなら、この節の位置づけは「§2.1.1 の穴を塞ぐ最小の道具」から「**markdown の手癖を受け止める砂糖**」に下がる（穴のほうはバブルが塞ぐ）。下の「最大の反論」もバブルが答えてしまうので、**§5.5 を作らない場合にだけ、この節は単独で意味を持つ**。

**→ §5.5 は 2026-08-11 に作った。したがってこの節は既に砂糖である。** 以下は当時の材料をそのまま残したもので、「作る理由」の節が §2.1.1 を根拠にしている部分は**もう有効でない**（穴は塞がっている）。今なお生きているのは「編集器自身の語彙の中の不整合」のほうだけである。

**この案は元々検討されていない。** §10 の却下リストにも入っていない（`autolink: false` / sanitize の `target`・`rel` / `siteOrigin` / `whenNotEditable` / sanitize 拡張 / `protocols` / VS Code ハンドラ撤去 の 7 つ）。一度却下された案の蒸し返しではなく、単に抜けていた選択肢である。

**作る理由**: 使い勝手ではなく、§2.1.1 の穴である。**内部リンクを作る経路が今ひとつも無い**のに、§1 はそれを著者が手書きする前提で非目標を切っている。入力ルールはこの穴を塞ぐ最小の道具で、`extension-link` は `addPasteRules` しか持っておらず（`dist/index.js:394`）入力ルールの席は空いている。同時に、ヘッダ・引用・フェンス・`:::details` と markdown 記法を受け付ける編集器で `[]()` だけ黙って無反応、という**編集器自身の語彙の中の不整合**も消える。

**作らない理由（この案への最大の反論）**: **外す手段が無いまま、任意テキストのリンクを量産する。** 今の外せないリンク（§5.2）は autolink 産でテキスト = URL なので、消したければその文字列を消せば済む。`[任意のテキスト](url)` は違い、URL を打ち間違えたら見えている本文ごと消して打ち直すことになる。`undoInputRule` は直後の 1 打鍵しか救わない。

→ **やるなら `unsetLink` の口を 1 つだけ添えて出す**（ツールバーのボタン 1 個か `Mod-Shift-K`）。①でキャレットが置けるようになった今、`extendEmptyMarkRange: true`（§5.2）によりリンク内にキャレットを置くだけで効く。これでも②の 3 点セットには遠く及ばないので、**②の一部ではなく「①.5」として切り出す**。

**作るときの制約**:

1. **捕まえた href を `isPublishableUri` に通す。** 入力ルールは `isAllowedUri` を経由しないので、通さないと §2.4.2 で塞いだ `tel:` / `ftp:` が別口から復活する — `linkOnPaste` の穴（§2.4.2）と同じ形である。
2. **先頭の `!` を除外する。** `![alt](src)` を奪わないため。
3. **`undoInputRule` で戻ることを spec で固定する。** TrailingNode の干渉は解消済みだが、ここは実績のある落とし穴。
4. **インラインの `code` マークは守られない。** `prosemirror-inputrules` の除外判定は `$from.parent.type.spec.code`、つまり**親ノードだけ**を見るので `codeBlock` は安全だが、`` `[x](y)` ``（code マーク）は素通りする。何が起きるか測って決める。
5. **アコーディオンのタイトル（`detailsSummary`、`marks: ''`）を spec に含める。** マークは fitter に渡らず filter されるはずなので脚注のときのような分断は起きない見込みだが、この 2 機能は一度お互いを想定せずに事故を起こしているので、仮定ではなくケースとして置く。

**`transformPastedText: true`（tiptap-markdown）は代案ではない。** リンク記法だけでなく**あらゆるペーストを markdown として解釈する**グローバルな変更であり、範囲が違う。

**この案が入ると `e2e/editor-link-markdown-syntax.spec.ts` の 3 件が反転する**（「打ってもリンクにならない」「保存 → 再読込でもリテラル」「https でも同じ」）。機能の不在を固定している spec なので、**壊れたのではなく入った合図**である。残る 4 件（エスケープ無しで読めばリンクになる／`/posts/foo`・`#見出し` はペーストでリンクにならない）はどちらでも成立する。

### 5.5 ②の実装形態 — Google Docs 型のバブル（2026-08-11 決定・実装）

**この形で実装した**（`components/editor/LinkBubble.tsx`）。§5.3 が暗黙に前提していた `<dialog>`（`TableGridMenu.tsx` の形）は採らなかった。

**形**: リンクの中にキャレットが入ったら、その `<a>` の下に小さな浮遊カードが出る。中身は **href の表示 + 開く / コピー / 編集 / 解除の 4 ボタン**。編集を押したときだけ URL 入力欄に変わる。付与は選択して `Mod-k`、同じカードが空の URL 欄で開く。

**設計から変わった点は 2 つだけである**（どちらも下に理由を書いた）: カードは上下ではなく**下に固定**（`placement: 'bottom-start'`。上だと読んでいる行を覆う）、`Mod-k` は拡張の keymap ではなく **DOM リスナ**（§5.3-4）。

#### 5.5.1 なぜこの形か

1. **①の借りを返す。** §3 は `openOnClick: false` の代償として「エディタからリンク先を開く手段が無くなる、代替はブラウザのステータスバー」と明記している。このカードは **href を文字で見せ、開くボタンを戻す**。①＋バブルは既定より一方的に良く、§3 の「取引」が取引でなくなる。
2. **①が前提条件だった。** キャレットがリンク内に入れなければ発動しない。§3 が「②の前提条件でもある」と書いたとおりの順番になっている。
3. **選択操作を要求しない。** `unsetLink` は `extendEmptyMarkRange: true` なので（§5.2）、キャレットが中にあれば足りる。
4. **付与・編集・解除の 3 つが 1 コンポーネントに収まる。** §5.1 のコスト見積もりが前提にしていた「ダイアログ複数」ではなくなる。

#### 5.5.2 土台は既に repo にある

`components/editor/TableToolbar.tsx` が `@tiptap/react/menus` の `BubbleMenu` を使っている。**新規依存はゼロ** — `@tiptap/react` → `@tiptap/extension-bubble-menu` → `@floating-ui/dom` の順に引かれており、`package.json` にはどれも直接載っていない（TableToolbar が現に動いていることがその証拠）。あの実装が払った授業料はそのまま効く:

- **`shouldShow` / `appendTo` / `options` は参照を安定させる。** 毎レンダー新しい inline props を渡すと `shouldRerenderOnTransaction` と往復して "Maximum update depth" で落ちる。
- **`appendTo: document.body`。** エディタラッパの `overflow-hidden` に切られないため。
- **z-index**: TableToolbar は `z-20`（sticky ツールバーの `z-30` より下）。リンクのカードもその取り決めの中に入れる。
- **選択ではなくノードにアンカーする。** TableToolbar はテーブルの左上セルに固定している。リンクなら `<a>` 要素に固定すれば、キャレットが中を動いてもカードが揺れない。
- **`updateDelay={0}`。** ブロックドラッグ直後の位置飛びを避けるための既定 250ms からの変更。同じ理由が当てはまるかは要確認。

`shouldShow` は `() => editor.isActive('link')` で足りる**が、それが成り立つのは §4 で `autolink` を残したからである**。TableToolbar の `isActive('table')` はノードの判定だが、リンクはマークなので、空選択のときの判定は `storedMarks ?? $from.marks()`（`@tiptap/core` の `isMarkActive`）に落ちる。`extension-link` の `inclusive()` は **`this.options.autolink` をそのまま返す**（`dist/index.js:261-263`）ので、今の設定ではマークが inclusive であり、**リンク末尾にキャレットを置いても active と読める** — クリックで最も普通に落ちる位置がそこなので、これは効いている。

**逆に言えば、この 1 行は §4 の決定に couple している。** `autolink: false`（§10 で却下済み）に転ぶとマークが非 inclusive になり、末尾のキャレットで判定が落ちるので、`shouldShow` はリンクの range を明示的に解決する形に書き直す必要がある。§5.2 の `extendEmptyMarkRange: true` が存在する理由と同じ種類の縁である。

**実測 2026-08-11 — 上の予想はどれも当たっていたが、2 つ足すことがある。**

| キャレット位置                   | `isActive('link')` | `getAttributes('link')` | `domAtPos` から `closest('a')` |
| -------------------------------- | ------------------ | ----------------------- | ------------------------------ |
| リンクの**左端**（`前\|リンク`） | `false`            | `{}`                    | 取れない                       |
| リンクの中                       | `true`             | 全属性                  | 取れる                         |
| リンクの**右端**（`リンク\|後`） | `true`             | 全属性                  | **取れない**                   |

1. **inclusive は右端にしか効かない。左端は active にならない。** カードが出るのは「中と右端」であって「リンクの両端」ではない。実害は無い（左端はまだリンクの外だと読める）が、`shouldShow` が対称だと思って書くと E2E が食い違う。
2. **その右端では `<a>` 要素が引けない。** `domAtPos(selection.from)` が段落を返すためで、`getMarkRange` も同じ理由でここでは解決に失敗する（`childAfter` が非リンクのテキストを返して打ち切る）。**アンカー解決は `from - 1` → `from` の 2 手で試す**必要がある。`extendMarkRange` を使うコマンド（解除・編集）は右端でも正しく効くので、**壊れるのはカードの位置決めだけ**という分かりにくい形になる。

**`isActive` を使い続けている理由**: 右端は「クリックで最も普通に落ちる位置」であり、そこでカードが出ないほうが害が大きい。`getMarkRange` に寄せると右端が丸ごと落ちる。

**autolink 直後に書き続けてもカードは出続けない**（実測）: `https://example.org` を打って空白を入れると、キャレットはリンクの外（空白の後ろ）に出るので `isActive` は false に戻る。**「URL を打った直後からカードが本文の上に居座る」という懸念は現実にならない。**

#### 5.5.3 これが §5.4 と §2.1.1 に対して持つ意味

`Mod-k` で開いた URL 欄には `#見出し` も `/posts/foo` も直接打てる。**したがって §2.1.1 の穴（内部リンクを作る経路が無い）はバブルだけで塞がる。**

| 役割                  | §5.5 バブル | §5.4 入力ルール |
| --------------------- | ----------- | --------------- |
| 付与                  | `Mod-k`     | `[]()` を打つ   |
| 内部リンク            | ○           | ○               |
| 確認（href が見える） | ○           | ×               |
| 編集                  | ○           | ×               |
| 解除                  | ○           | ×               |

**§5.4 の「外す手段が無いまま任意テキストのリンクを量産する」という最大の反論も、バブルが答えてしまう** — しかも見えている本文を消さずに URL だけ直せるので、打ち間違いの修復コストがゼロになる。§5.4 は「markdown の手癖を受け止める砂糖」に格下げされる。

**実測 2026-08-11: `setLink({ href: '#見出し' })` は通る。** `isAllowedUri` に渡している `isPublishableUri` は既定判定の前に置いた引き算でしかなく（§2.4.2）、スキームを持たない fragment / 相対パスは既定側が通すので、狭めた述語はここでも邪魔をしない。**§2.1.1 の穴は塞がった。**

#### 5.5.4 作るときの制約（§5.3 に足す）

1. **表示モードには `<input>` を置かない。** ボタンだけのモードなら §5.3-1（ネストした `<form>`）も §5.3-2（React 19 のフォーム自動リセット）も無関係である。**編集モードを明示的に開く段階分けが、そのまま防御になっている** — Docs の形をそのまま写せばよい。入力欄を出した瞬間に §5.3-1/-2 が生きる。
   → **実装では §5.3-1/-2 はどちらのモードでも成立しない。** BubbleMenu は自分の要素を `document.body` へ portal するので、URL 入力欄は PostEditor の `<form>` の**外**にあり、そもそも form に association されない。段階分けは残してあるが、それは UI としての理由（表示を先に見せる）であって防御ではない。**フォーム自動リセットを踏まないことは E2E で測ってある**（基準 4k、オートセーブを跨いで入力値が残る）。
2. **テーブル内のリンクでは浮遊メニューが 2 枚同時に出る。** TableToolbar と競合する。どちらを優先するか、オフセットをずらすか、`shouldShow` で排他にするかを決める必要がある。**これは新しい設計判断で、前例が無い。**
   → **決定: セル内ではリンクのカードが勝つ。** より具体的な対象であり、キャレットがリンクを出ればテーブルの操作は戻る。**機構は `shouldShow` ではなく CSS** — `body.link-menu-open .table-toolbar { display: none }`（`app/globals.css`）を BubbleMenu 自身の `onShow` / `onHide` で着け外しする。`shouldShow` に項を足す形は**付与のとき（`Mod-k` で URL 欄を開く操作）に効かない**: bubble menu プラグインは選択か文書が変わる transaction でしか `shouldShow` を訊き直さず、入力欄を開く操作はそのどちらでもないからである。**ブロックドラッグ中の同じ抑止（`body.block-dragging`）がまさに同じ理由で CSS になっており、前例が無いのは「どちらが勝つか」の判断だけだった。**
3. **ホバー起動は入れない。** Docs はホバーでもカードを出すが、ホバー／フォーカス起動の追加コンテンツは WCAG SC 1.4.13 の dismissible / hoverable / persistent を全部背負う（`popover-api-pitfalls` の教訓）。**キャレット起動なら編集アフォーダンスなので義務が軽い。** ただし Escape で閉じるのは入れる。
   → そのまま実装した。Escape はエディタ側（`view.dom` の capture リスナ）とカード側（ボタンにフォーカスがある場合）の両方に置いてある。**閉じたことはキャレットがリンクを離れるまで保持し、離れたら忘れる** — さもないと次の transaction で即座に戻ってくる。
4. **`Mod-k` は実機確認が必須**（§5.3-4）。Chrome の検索バーに取られる既定があり、tsc も E2E も答えを持たない。Docs は現に奪えているので不可能ではない。
   → **2026-08-11 に実機で確認、奪えている**（§9）。`preventDefault()` だけで足りた。E2E の `Control+k` は CDP 合成なのでブラウザ UI に届かず「奪えた」の証拠にならない、という事情は変わらないので、**この確認は spec に持ち込めず、§8 の表にも入らない**。
5. **`title` を消さないこと**（§5.3-3、未実測）。編集ボタンの実装で最初に測る項目。投稿 id 36 がフィクスチャ。
   → **実測して残ることを確認済み**（§5.3-3、基準 4c）。
6. **キャレットを置くクリックは `state.selection` への反映が 20ms 遅れる**（§8 の 1b と同じ落とし穴）。カードの出現が 1 フレーム遅れるのは許容だが、**E2E で「出ない」を測るときは DOM のキャレットを見てはならない**。
   → spec はキャレットをほぼすべて `setTextSelection` で置いている（クリックの落ち先ではなく、どの位置で何が起きるかを測りたいので）。**唯一クリックで測っているのはセル内のリンク**（§5.5.4-2）で、そこは待って測っている。
7. **（実装中に見つかった、設計時に無かった制約）カードの中のイベントから `.key` を読んではならない。** `@tiptap/react` の menu は prop のコールバックに `Object.create(実イベント)` を渡すので、プロトタイプ経由で届く native なアクセサ（`.key` もそれ）が本物でない `this` で呼ばれ **"Illegal invocation" を投げる**。カード内の打鍵のたびに投げていたのに、**カードは正常に動いて見えた** — DOM ハンドラの中の例外は「何も起きない」と同じ顔をするからである。`event.nativeEvent.key` を読む。**見つけたのは `page.on('pageerror')`** で、`clearNodes` の RangeError（`tiptap-editor-pitfalls`）と同じ発見のされ方をしている。spec はこの watch を常設にした。
8. **（同上）セル内抑止の E2E は、body のクラスと `toBeHidden()` の両方を書く。** この spec を書いている途中、`toBeHidden()` が**タイムアウトいっぱい "visible" を返し続ける形で 4 回連続再現**した。ファイルが育つと（どちらのコンポーネントにも触っていないのに）再現しなくなった。**失敗中のページの状態は取れていないので、当時クラスが付いていたのかどうかは分からない** — 分からないことを分かったように書かないために、spec には両方の assertion を置き、次に赤くなったときにどちらが壊れたのか分かるようにしてある。

#### 5.5.5 写さないもの

リンク候補の検索・記事タイトルの自動取得（§1 の非目標そのもの）、リンクプレビューのサムネイル。**ボタンは 開く / コピー / 編集 / 解除 の 4 つで足りる。**

## 6. 延期 — 公開ページの外部リンク別タブ化

**現状**: 全リンクが同一タブ（§2.3）。**これはバグではなく、コストゼロで防御可能な既定である。**

**将来やるなら**の形だけ決めてある:

1. **sanitize のスキーマは広げない。** 広げると著者が生 HTML で `target` を書けてしまい、`lib/render.ts:70` の「著者を信用しない」前提が弱まる。代わりに **sanitize の後段に自前の rehype プラグインを置き、パイプライン自身に付けさせる**。`rehypeClobberFragmentLinks` / `rehypeCollectToc` / `rehypeCodeFilename` が既に post-sanitize の前例を作っている。
2. **外部の判定は「`href` が `http://` か `https://` で始まるか」だけでよい。** `lib/site.ts` の `siteOrigin` と突き合わせる必要はない — 自サイトを指す書き方は相対パスか fragment なので集合として既に分かれており（§2.3 で実測）、`siteOrigin` は dev で `localhost:3001`、本番で別ホストと変わるため環境依存を持ち込むだけである。この判定なら `lib/render.ts:66-67` の「プレビューと公開が一致する」不変条件も自明に保てる。
3. **目次・脚注参照・戻りリンクを巻き込まないこと**が事故ポイント。2 の判定を守れば自動的に避けられる。**著者が `#user-content-…` を手書きした場合も同じで**（§2.1.1 のとおり、公開ページから href をコピーすると起こる）、生成された ToC リンクと文字列上は見分けが付かないが、どちらも `http` で始まらない以上 2 の判定の外にある。**外部判定を href の中身で細かく分けようとしない限り安全である。**
4. **a11y の予告を CSS の `::after` アイコンで済ませてはならない。** CSS 生成コンテンツはスクリーンリーダーに届かないので、WCAG の G201 が求める予告にならない。sr-only テキストが要るなら**同じ post-sanitize プラグインが注入する**しかない（それより前だと sanitize の `span` クラス許可リストが `markdown-alert-title-label` と `accent-emphasis` しか通さないので消える）。

**判断の中身**（結論は出ていない。決めるときの材料として残す）:

- 別タブに寄せる理由: 記事は脚注と引用を持つ。同一タブで外部へ飛ぶと戻ったときにスクロール位置と文脈を失う。脚注ポップオーバーに払ったコストは同じ問題への回答であり、外部参照だけ扱いが違うのは一貫しない。
- 同一タブに留まる理由: WCAG 3.2.5 は「新しいウィンドウはユーザーが要求したときだけ」と言う（AAA なので AA 適合の障害ではない）。読者は Ctrl+クリックで自分で選べる。何もしなければコードも増えない。
- **セキュリティは論点ではない**。現代のブラウザは `target="_blank"` に `noopener` を暗黙適用する。

- **リンクの見た目は Tailwind typography の既定のまま。** 脚注参照のように特別扱いする理由が今のところない。

**1b は「キャレットが置ける」までしか測っていない**（置いたあとに何ができるかは 4 の側で測る）。②が入った今もこの分担のままでよい。

**4 の表に「`Mod-k` がブラウザに取られない」は無い。** 測れないからである（§5.5.4-4）。**測れないものを基準の表に入れると、通ったことが答えの代わりになってしまう。**

## 10. 却下した案

- **`autolink: false` にして②までの安全側に倒す** — §4。公開側との WYSIWYG のズレを再び開くため却下。
- **sanitize のスキーマに `target` / `rel` を足す** — §6-1。著者制御になり、`render.ts:70` の前提を弱めるため却下。post-sanitize のプラグインで同じ結果が、著者に触らせずに得られる。
- **`siteOrigin` で内部/外部を判定する** — §6-2。環境依存を持ち込むだけで何も買わないため却下。
- **`openOnClick: 'whenNotEditable'`** — §3。このエディタは常に編集可能なので `false` と等価。
- **公開側の sanitize スキーマを広げて `tel:` などを通す** — §2.4。エディタを狭めるほうを採った。スキーマに手を入れずに済み、許可リストの説明が「GitHub と同じ」のまま保てるため。**セキュリティ判断ではないので、電話番号リンクが本当に要るようになったらこの却下は覆してよい**（§2.4.1）。
- **`protocols` オプションで狭める** — §2.4.2。あのオプションは広げる方向にしか効かない。
- **VS Code のペーストハンドラをプラグインごと外す** — §2.5.2。複数行のペーストは本当にコードブロックであり、言語の出所は他に無いため、条件付きで残した。

- **②のカードを `shouldShow` の項でテーブルツールバーと排他にする** — §5.5.4-2。付与のとき（URL 欄を開く操作）は選択も文書も変わらないので `shouldShow` が訊き直されず、そこだけ 2 枚出る。CSS による抑止を採った。
- **右端でもアンカーを引くために `shouldShow` を `getMarkRange` ベースにする** — §5.5.2。リンクの右端が丸ごと落ち、クリックで最も普通に落ちる位置でカードが出なくなるため却下。位置決めの側を 2 手にした。
